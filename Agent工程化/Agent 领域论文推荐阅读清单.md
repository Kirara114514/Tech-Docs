# Agent 领域论文推荐阅读清单

## 摘要

这是一份面向想系统理解 agent 领域的研究者与工程师的推荐阅读清单。它不是文献综述，不追求覆盖所有发表过的论文；它的目标是帮助读者用有限的时间建立判断力——知道什么论文值得读、为什么值得读、以及读完后能形成什么样的认知框架。

清单按三级推荐体系组织。T0 是建立判断框架的 5 篇核心论文——读完这些，能理解 agent 领域的关键问题是什么、度量 agent 能力的基本方法是什么、以及为什么现有的评测方式需要被重新审视。T1 是工程与评测方向的 13 篇实用论文，覆盖 coding agent 基础设施、企业级评测、通用 benchmark、web agent 和 AI R&D agent 五个专题组。T2 是 11 篇专题补强论文，涉及记忆系统、技能审计与安全、agent 后训练和 web agent 专题深入。

三级体系的设计逻辑是：先建立判断框架（T0），再按工程需求选择专题（T1），最后在特定方向上深入（T2）。如果只读 5 篇，读 T0 就够了——不需要读 30 篇才能形成观点。

## 正文

### 背景

2022 年底 ChatGPT 发布后，大语言模型（LLM，Large Language Model）的能力让整个行业开始思考一个问题：如果模型能理解指令、生成代码、进行推理，那它能不能不只回答问题，而是去完成一个完整的任务？这个追问直接催生了 agent 这个概念。这里的 agent 指的是一种具备自主性的 AI 系统——它接收一个目标，自己决定下一步做什么、用什么工具、怎么判断结果是否正确、以及什么时候停下来。这和传统的聊天模型有本质区别：聊天模型是被动回应的，agent 是主动执行的。

从 LLM 到 agent 的演进不是简单的"让模型调用工具"。一个聊天模型可以调用搜索 API 回答"今天天气怎么样"，但它不会主动规划、不会在出错后重新尝试、不会在信息不足时决定去收集更多信息。agent 的核心特质是自主性：它在一个目标驱动下，持续地与外部环境互动——调用工具、读取文件、执行代码、查询数据库——并在每一步根据环境的反馈调整自己的行为。这种交互不是一次性的问答，而是一个可能持续几十步甚至几百步的任务链。

这种自主性带来了全新的工程挑战。一个 chatbot 的好坏可以通过单轮回答质量来衡量——看回答是否准确、是否完整、是否流畅。但一个 agent 的好坏需要看它在一个可能长达几十步的任务链上的表现——中间任何一步出错都可能导致最终失败。而且错误不一定是模型"答错了"，可能是模型在正确的时机选择了错误的工具，或者在应该停下来的时候继续执行了多余的操作。这种错误模式在传统 NLP 评测中几乎不存在，但在 agent 场景中是常态。

举个具体的例子。一个 coding agent 被要求"修复一个 bug 并更新对应的单元测试"。这个任务大概需要以下步骤：理解 bug 描述 → 定位相关代码 → 分析根因 → 修改代码 → 运行现有测试确认不引入新错误 → 更新单元测试覆盖修好的 bug → 再次运行全部测试。每一步都有可能出错：理解错 bug 的含义、定位到错误的文件、修改了正确的代码但引入了新问题、更新测试时覆盖了不该改的断言。最麻烦的是，这些错误之间会相互影响——前面的错误可能导致后面的步骤在完全错误的前提下展开，最终整个任务链崩溃。而这种累积性的错误传播效应，在单轮问答中是不存在的。

当前 agent 研究已经分化出多个方向，每个方向解决这个问题的一个侧面。评测方向关注如何度量 agent 能力——是用 benchmark 分数、任务成功率、还是更细粒度的行为分析指标。这个问题比看起来复杂得多：不同的 benchmark 设计会导致同一模型拿到完全不同的分数；同一个 benchmark 在不同 scaffold 下跑也会得到不同结果。如果评测本身不靠谱，整个领域就是在黑暗中摸索。框架方向关注 agent 的执行基础设施——如何设计 agent-computer interface（ACI，agent 与计算机之间的交互界面）、如何管理工具调用和沙箱环境。一个好的框架能让普通模型表现得像优秀模型，而一个差的框架能让优秀模型寸步难行。安全方向关注 agent 的自主性带来的新风险——当 agent 可以执行 shell 命令、修改文件、调用外部 API 时，如何确保它不会造成破坏。这不是 hypothetic 的担忧：已有案例显示 agent 可能在执行任务过程中意外删除文件、泄露敏感信息、或被恶意 prompt 注入诱导执行危险操作。记忆方向关注 agent 如何在长任务中保持上下文、如何记住过去的交互、如何在信息过载时做选择性遗忘。这听起来像是一个工程优化问题，但实际上它定义了 agent 的能力上限——如果一个 agent 只能记住最近 100 轮交互的内容，那任何需要跨越多轮交互的任务它都无法可靠完成。训练方向关注如何通过后训练（post-training，在模型完成预训练后进行的定向微调）让模型在 agent 场景中表现更好。通用 LLM 在训练时并没有接触过大量的 agent 交互数据，它们是作为"语言模型"被训练的，而不是作为"行动模型"被训练的。如何弥补这个 gap 是一个活跃的研究方向。

在这些方向中，评测是特别关键的基础设施问题。评测定义了"什么是好的 agent"——如果评测指标本身有问题，整个领域的研究方向就会被带偏。历史上在 NLP 领域就有过类似的教训：当一个 benchmark 成为事实标准后，研究会围绕"如何在这个 benchmark 上刷分"展开，而不是"如何解决真正的问题"。而 agent 评测的困难在于：和传统 NLP benchmark 不同，agent 的表现不仅取决于模型能力，还取决于它使用的 scaffold（agent 的执行框架层，包括工具定义、提示模板、沙箱环境配置等）、工具质量、环境设计和任务选择。同一模型在不同 scaffold 下可能得到完全不同的分数。这就意味着，当你看到一篇论文声称"我们的 agent 在某 benchmark 上达到 90% 成功率"时，你无法直接判断这个数字意味着什么，除非你知道它用了什么 scaffold、这个 scaffold 是否给了该模型不公平的优势、以及这个 benchmark 的任务分布是否合理。

这就引出了阅读论文的核心价值：读论文建立的不是"最新 SOTA（State-of-the-Art，当前最优结果）是谁"的知识，而是判断力。当一篇新论文声称"我们的 agent 在某 benchmark 上达到 90% 成功率"时，有判断力的读者会去追问：这个 benchmark 的任务分布是否合理？scaffold 是否给了不公平的优势？成功率是如何定义的——是一次尝试成功就算，还是多次尝试的平均？任务难度是否经过人类基线校准？这些追问只能通过阅读那些认真思考评测方法论的论文来建立，而不是靠追排行榜。排行榜告诉你"谁跑得快"，方法论论文告诉你"跑道是不是歪的"——后一种知识远比前一种持久。

### 核心内容

#### 三级推荐体系总述

T0、T1、T2 的分级不是按论文的"重要性"排的——重要性是主观的，不同方向的研究者会对不同论文有不同的重视程度。分级的逻辑是："如果你时间有限，先读什么最能建立判断力"。这是一个面向阅读效率的设计，不是学术价值排序。

T0（优先读——建立判断框架）：5 篇论文。这些不是某个 benchmark 的评测报告，而是关于"怎么评估 agent"和"agent 的真实使用形态"的论文。读完 T0，能理解 agent 领域的测量哲学——度量的是什么、怎么度量、以及现有度量方式的局限性。这些论文的共同特点是：它们都在追问评测本身，而不是在评测中刷分。这种元层次的思考是建立判断力的基础。

T1（强烈推荐——工程与评测）：13 篇论文。这些是工程上最实用的论文——如果你在搭建 agent 系统、设计评测、或者选择技术路线，T1 提供直接的参考价值。这些论文的共同点是：它们都在解决一个具体的工程问题——怎么设计 agent 的开发平台、怎么构建对企业级任务有效的 benchmark、怎么评测 agent 在不同环境（终端、网页、多应用）中的表现。读 T1 不需要按顺序，挑你当前最需要的专题组直接读。

T2（专题补强——深入特定方向）：11 篇论文。当你在某个子方向上有具体需求时（比如设计记忆系统、做安全审计、优化后训练管线），T2 的论文提供该方向的入口。T2 的论文不是每个方向都选了最前沿的那篇——而是选了最有助于你"进入这个方向"的那篇。读完 T2 的一篇后，通常需要顺着它的引用链继续追踪才能达到该方向的前沿。

这个三级体系的隐含假设是：在 agent 领域，建立判断力比获取信息更重要。信息是易过时的——今天的 SOTA 明天就可能被超越。但判断力是累积的——一旦你理解了"怎么评估一个 agent"的方法论，你就可以用它评估任何新的 agent 系统、任何新的 benchmark、任何新的论文。

#### T0：优先读——建立判断框架

**T0 的第一篇：The Shift to Agentic AI: Evidence from Codex。** 很多 agent 研究是从 benchmark 出发的——设计一个评测集，让 agent 去跑，看谁分数高。但这篇论文走了相反的方向：它从真实产品数据出发，观察用户在现实中如何使用 agentic AI。agentic AI 指的是具有 agent 特性的 AI 系统——不只是回答问题，而是主动执行任务、使用工具、在目标和行为的循环中自主运作。

Codex 是 OpenAI 的 coding agent 产品。论文报告了一个关键数据：2026 上半年 Codex 的活跃用户增长超过 5 倍。这个数字本身不算特别惊人——新产品增长快是正常的。但比用户增长更有趣的是使用形态的变化：用户从"和 AI chat 讨论代码问题"逐步迁移到"把整个任务委托给 AI"。代理（delegation）替代了对话（conversation）成为主要交互模式。用户不再是一行一行地问"这段代码怎么写"，而是直接说"帮我实现这个功能"，然后等 agent 完成整个任务回来报告结果。

这个变化有深刻的含义。在对话模式下，用户控制着任务的每一步——什么时候开始、用什么方法、检查什么结果。用户是 driver，AI 是 navigator。在代理模式下，用户只给出目标和约束，AI 自己决定整个执行过程。用户从 driver 变成了 reviewer——只审查最终结果。这种交互范式的迁移对整个 agent 系统的设计提出了全新的要求：在对话模式下，AI 犯错了用户会立刻发现；在代理模式下，AI 可能运行了 20 分钟后才带着一个错误结果回来，用户需要花时间审查才能发现问题。这就对 agent 的可靠性提出了比 chatbot 高得多的要求。

这篇论文值得读的原因不是那些增长数字，而是它提供了一个 grounded 的视角：在真实产品环境中，用户把什么样的任务交给 agent？agent 在哪些任务上表现好、哪些上经常失败？用户如何建立对 agent 的信任？这些问题在 benchmark 研究中常常被忽略——benchmark 假设任务是给定的，但现实中"什么任务值得委托给 agent"本身就是个需要研究的问题。用户不会把任何事都交给 agent——他们会根据历史经验、任务的复杂度、容错率来选择性委托。这些选择行为本身就是 agent 能力边界的一种隐性度量。

从方法论的递进关系来看，这篇论文是 T0 的起点：它建立了"为什么要从真实数据出发思考 agent 评估"的问题意识。接下来 METR 的论文会从这个意识出发，提出一套度量 agent 长任务能力的方法论——如果我们接受了"用户委托真实任务给 agent"这个现实，那评测就应该围绕"agent 能在多长时间内保持可靠"来设计。

arXiv: https://arxiv.org/abs/2606.26959

**T0 的第二篇：Measuring AI Ability to Complete Long Tasks。** 这是 METR（Model Evaluation & Threat Research）提出的长任务能力度量框架。论文的核心贡献是提出一个简洁但有力的度量指标：50%-task-completion time horizon——AI 能以 50% 成功率完成的人类任务的最长时长。

这个指标的巧妙之处在于它把一个复杂的评价问题——"这个 agent 到底有多强"——简化为一个可以直接比较的数字。比如，如果模型 A 的 time horizon 是 50 分钟，模型 B 的是 30 分钟，那么在有 50 分钟预算的任务上，选 A 比选 B 合理。这个数字比任何一个 benchmark 的百分制分数都更容易转换为工程决策——当你需要决定在生产环境中部署哪个模型时，"它能以 50% 的把握完成 X 分钟的任务"比"它在某个 benchmark 上得了 85 分"有用得多。

论文估计，Claude 3.7 Sonnet 附近模型的时间跨度约为 50 分钟，并且观察到这个时间跨度大约每 7 个月翻倍。按照这个趋势外推，到某个时间点 agent 将能独立完成需要数天甚至数周的任务。不过值得注意的是，这种趋势外推总是非常不确定的——技术发展的曲线很少是一条平滑的指数线。可能存在我们目前没有看到的瓶颈（比如模型推理能力的上限、工具生态的成熟度瓶颈、安全合规的限制），这些瓶颈可能在任何一个时间点让增长趋势减速甚至停滞。

但这篇论文真正值得读的不是那个"7 个月翻倍"的数字——趋势外推总是不准确的。值得读的是它的度量哲学：它不问"agent 能做多少任务"，而是问"agent 能在多长时间尺度上保持可靠"。这个视角的转换有深刻的含义。传统的 benchmark 评测问的是"agent 能不能做这个任务"——这是一个二元的、任务粒度的度量。METR 的框架问的是"agent 能维持多久的有效性"——这是一个连续的、时间粒度的度量。后者更接近 agent 在生产环境中面临的真实挑战：不是"能不能做"某个具体的事，而是"在持续执行任务的过程中，出错概率会如何随时间和步骤数累积"。

长任务中的错误累积效应是 agent 区别于 chatbot 的核心问题。假设一个任务需要 100 个步骤，每一步的独立成功率是 99%。看起来很高——每一步 99% 很难出错。但 100 步累积下来，整体成功率只有 0.99^100 ≈ 37%。也就是说，在一个需要 100 步的任务中，即使每步几乎没有出错的可能，最终也只有大约三分之一的概率能完整走完全程。而现实中 agent 的每步成功率远不到 99%——在复杂任务中，每步可能有 10%-20% 的概率做出次优或错误的决策。这意味着对于需要 50 步以上的任务，当前最强 agent 的整体成功率也可能低到个位数。METR 的框架把这种累积效应直接编码在度量指标中——它不让你用"每步 95%"来自我安慰，它强制你面对"任务整体只有不到 10% 成功率"的现实。

从 T0 的递进逻辑看，这篇论文承接了 Codex 论文的产品视角——"用户委托真实任务给 agent"——并将其转化为可操作的度量框架。Codex 论文告诉我们用户确实在这样做，METR 论文告诉我们如何量化 agent 在这种使用场景下的能力。下一篇 HAL 论文则进一步把这个框架落地为标准化评测基础设施——有了度量框架，还需要能让所有人都能用相同方式执行度量的平台。

arXiv: https://arxiv.org/abs/2503.14499

**T0 的第三篇：Holistic Agent Leaderboard (HAL): The Missing Infrastructure for AI Agent Evaluation。** agent 评测领域有一个长期问题：不同论文报告的成绩很难直接比较。一个 agent 在 SWE-Bench 上得分高，可能是模型能力强，也可能是 scaffold 设计得好，还可能是 benchmark 的任务恰好匹配了该模型的长处。这三个变量——模型能力、scaffold 设计、benchmark 特性——在传统评测中被混在一起。这就好像你要比较两个运动员的跑步速度，但一个在塑胶跑道上跑、一个在沙地上跑、而且跑的距离还不一样——你拿到的名次毫无意义。

HAL 的目标就是拆开这三者。它标准化了 scaffold 层，在同一 scaffold 下运行不同模型，在同一 benchmark 上比较。论文报告了 21,730 条 agent rollout（一次完整的 agent 任务执行过程，从接收任务到产出结果或终止），并公开了大量日志数据。这个规模的标准化评测以前是不存在的，因为运行 agent 的成本——API 调用费用、沙箱环境维护、时间成本——远高于跑传统 NLP benchmark。跑一个传统 benchmark 可能只需要几秒钟的 GPU 推理时间；跑一个 agent rollout 可能需要几分钟到几小时的实时交互。21,730 条 rollout 意味着可能消耗了数千小时的 wall-clock 时间和相当可观的 API 费用。这种投入在 agent 研究刚起步时是不可想象的。

HAL 的核心发现之一是 scaffold 的影响比很多人以为的大。同一个模型在精心设计的 scaffold 下和在简陋的 scaffold 下，表现可以相差 20 个百分点以上。这意味着什么？意味着你看到的一篇论文说"我们用模型 X 在 Y benchmark 上达到了 Z 分"——这个 Z 可能有一大半是 scaffold 贡献的，而不是模型贡献的。如果你不知道 scaffold 的具体设计，你是无法复现这个结果的，甚至无法判断这个数字是否有意义。

这个发现对 agent 研究生态有深远的影响。它意味着 benchmark 排行榜在 scaffold 没有被标准化之前，基本没有可比性。一篇来自大公司的论文可能用了精心优化过的 scaffold，而一篇学术论文可能用了最简单的 scaffold，两者的分数差异反映的可能不是模型差异，而是工程投入差异。HAL 试图通过"标准化 scaffold"来解决这个问题——让所有人都用同样的执行基础设施，这样至少可以把 scaffold 这个变量固定住，让分数差异更真实地反映模型能力差异。

这篇论文在 T0 中的位置是评测方法论从理论到实践的桥梁。METR 提出了"度量什么"的框架——用 time horizon 来度量 agent 能力。HAL 解决了"怎么标准化地度量"的问题——固定 scaffold 和 benchmark 来消除混杂变量。下一篇 AgentAtlas 则进一步追问：即使度量标准化了，"成功率"这个指标本身是不是有问题？一个成功率 80% 的 agent 真的比一个成功率 75% 的 agent 更值得信任吗？

arXiv: https://arxiv.org/abs/2510.11977

**T0 的第四篇：AgentAtlas: Beyond Outcome Leaderboards for LLM Agents。** 绝大多数 agent benchmark 只报告一个数字：成功率（或 Pass@k，即在 k 次尝试中至少成功一次的概率）。但"成功了"和"失败了"这两个标签背后隐藏了大量信息。一个 agent 以正确的方式成功和以碰运气的方式成功，对工程实践的意义完全不同。同样，一个 agent 在第 3 步就做错了但后面碰巧修正了，和一个 agent 每一步都正确但最后一步格式错误导致失败，两者需要的改进方向完全不同。

AgentAtlas 的核心贡献是提供了一套分析 agent 行为轨迹（trajectory，即 agent 执行任务过程中每一步的状态、决策和行动序列）的框架。它定义了 6 类控制决策状态，用于分类 agent 在每一步中做出的决策类型。Act（执行操作）表示 agent 选择了执行一个具体的行动——比如调用一个工具、运行一段代码。Ask（请求用户输入）表示 agent 判断当前信息不足，主动向用户请求更多信息。Refuse（拒绝执行）表示 agent 认为当前操作超出了自己的能力或安全边界，选择不执行。Stop（主动停止）表示 agent 认为任务已经完成，主动终止执行。Confirm（请求确认）表示 agent 在继续之前需要用户确认——通常出现在高风险操作前。Recover（从错误中恢复）表示 agent 在检测到自己的上一步操作出了问题后，主动采取修正行动。这 6 种决策类型描述了一个 agent 在每一步"选择了什么策略"，而不只是"结果是什么"。

更重要的是，AgentAtlas 定义了 9 类 trajectory failure taxonomy（失败分类体系），用轨迹行为解释 agent 失败。这个分类体系从"为什么失败了"的角度来理解 agent 行为，而不是简单地说"没成功"。其中几个关键类别包括：过早停止——agent 在任务还没完成时就认为完成了，这是 agent 过度自信的一种表现；工具误用——agent 使用了正确的工具但传入了错误的参数，说明 agent 理解了"该用什么"但没有掌握"怎么用"的细节；工具错选——agent 在需要工具 A 时调用了工具 B，说明 agent 对工具能力的边界理解有误；循环困境——agent 在几步之间反复徘徊，无法推进任务，通常是错误恢复机制失效的表现。这种细粒度的失败分类让研究者可以从"哪里出错了"反推"需要改进什么"，而不是对着一个"成功率 60%"的冷冰冰的数字无从下手。

这篇论文的方法论意义在于：它把 agent 评估从"看结果"推进到"看过程"。在 T0 的递进中，它直接回应了 HAL 论文中隐含的问题——即使标准化了 scaffold 和 benchmark，只看成功率仍然是粗糙的。两个 agent 都可以在同一个 benchmark 上有 70% 的 Pass@1（一次尝试的成功率），但一个是通过稳定的、正确的行为模式达成，另一个是靠几次幸运的恢复从边缘拉回来。只看 70% 这个数字，你会觉得两者差不多；看 trajectory 分析，你会发现两者需要的改进方向截然不同。下一篇 Open-World Eval 论文则从另一个角度质疑基准评测：不是度量方法的问题，而是基准环境本身的问题——一个标准化的、可重复的 benchmark 环境，到底能不能反映 agent 在真实世界中的表现？

arXiv: https://arxiv.org/abs/2605.20530

**T0 的第五篇：Open-World Evaluations for Measuring Frontier AI Capabilities。** 所有的 benchmark 都有一个共同假设：任务可以被提前定义、评估标准可以被量化、环境可以被控制。但在真实世界中，一个被部署的 agent 面对的任务是开放的——没有人提前定义正确答案、环境会动态变化、任务目标本身可能模糊。举个简单的例子：一个 benchmark 可能测试 agent "在指定文件夹中找到名为 report.pdf 的文件"。但在真实世界中，用户可能说的是"帮我找一下上次那个报告"——文件名不确定、位置不确定、甚至"那个报告"指的是什么都需要 agent 自己判断。

这篇论文的核心论点是对传统 benchmark 的批判性补充，而不是替代。它指出 benchmark 有两个方向的风险：一方面，benchmark 可能会高估部署能力——因为 benchmark 任务相对干净、结构化，边界清晰，而真实世界的任务充满了噪声和边缘情况。在 benchmark 上做到 90% 的 agent，可能在真实场景中连 50% 都做不到。另一方面，benchmark 也可能会低估部署能力——因为 benchmark 只测了设计者认为重要的能力，而 agent 可能在其他维度上表现出色。比如一个 web agent 在购物的 benchmark 上表现一般，但在实际使用中，用户发现它在"找到最便宜选项 + 自动比较规格"这个 benchmark 没测过的能力上非常强。

论文主张引入 open-world evaluation（开放世界评测）作为传统 benchmark 的补充。这种评测有四个特征：长周期——不是几小时，而是几周甚至几个月，以此来观察 agent 在持续运行中的行为退化；脏任务——数据不干净、环境不稳定、目标模糊，贴近真实世界的混乱程度；小样本——不以统计显著性为核心目标，而是追求深度的定性理解（因为样本量大到有统计显著性在 open-world 场景下成本过高）；定性分析——不只是数字，要结合人类专家判断，因为很多 open-world 任务没有唯一的"正确"输出。

论文还介绍了 CRUX 项目作为 open-world eval 的一个实例。这篇论文适合作为 T0 的收尾——它在读完前面四篇建立起的"度量和分析 agent 的方法论"基础上，提醒读者：所有这些方法都有边界，真实世界永远比评测环境复杂。最好的评测策略可能不是选一个"最准的 benchmark"，而是组合使用标准化 bench（如 HAL 下的 SWE-bench）和开放世界评测，让两种视角互相校正。

arXiv: https://arxiv.org/abs/2605.20520

#### T1：强烈推荐——工程与评测

**T1-1：Coding Agent 基础设施**

在所有的 agent 应用方向中，coding agent 是工程化最成熟、研究产出最密集的方向。它的成熟有一个结构性的原因：代码是一个封闭的、可自动验证的领域——代码能不能运行、测试能不能通过、功能是否符合预期，这些都可以在不依赖人类判断的情况下自动完成。这使得 coding agent 成为 agent 研究的理想试验场——你可以用近乎零人工成本的方式运行数百条 agent rollout 并自动获得客观的评测结果。

**OpenHands: An Open Platform for AI Software Developers as Generalist Agents**（原 OpenDevin）是这个方向的代表性基础设施论文。OpenHands 提供了一个完整的 agent 开发平台——agent 可以在沙箱（sandbox，一种隔离的执行环境，agent 在其中的任何操作不会影响宿主机）中写代码、执行 shell 命令、浏览网页、操作文件系统，并且支持多 agent 协作和主流 benchmark 集成。

OpenHands 值得读的原因不在于它的技术有多新——它的很多组件在其他平台中也有——而在于它展示了一个完整的 agent 系统需要哪些基础设施层。对正在搭建 agent 系统的工程师来说，这篇论文相当于一份"checklist"：你需要一个代码执行沙箱，确保 agent 的错误操作不会破坏宿主环境；你需要一个浏览器环境，因为现代软件开发大量依赖在线文档和 web 界面；你需要一个可观测的 action 空间（agent 可以执行的所有操作类型的集合及其观测方式），让你能追踪和理解 agent 做了什么；以及你需要和评测系统的集成接口，让你能持续评估 agent 的表现。漏掉任何一层都会在未来成为瓶颈。很多团队在搭 agent 系统时只关注了"模型选哪个"，然后发现 agent 在沙箱里把自己搞崩溃了、或者无法访问需要的 web 资源、或者执行了什么操作完全不透明——这些都是基础设施层的缺失，不是模型的问题。

arXiv: https://arxiv.org/abs/2407.16741

**SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering** 是 coding agent 领域的经典论文。它的核心观点简洁但深刻：agent 需要专门的 Agent-Computer Interface（ACI），而不是简单地在模型和计算机之间加一层 API 调用。ACI 是 agent 与计算机系统之间的交互界面——它决定了 agent "看到"什么样的信息、能以什么格式执行什么样的操作。

传统的做法是给模型一套工具（tool set），模型决定调用哪个工具。这种做法的问题是：工具是为人类程序员设计的接口，不是为 LLM 优化的。人类程序员看到一段代码输出能自动忽略无关信息、聚焦关键错误；但 LLM 可能会被冗长的日志淹没，或者在格式混乱的输出中找不到关键信号。SWE-agent 的做法是设计一个专门为 agent 优化的计算机界面——文件查看器设计成方便模型"看到"代码结构的格式；搜索功能返回模型容易解析的结构化结果；编辑操作设计为原子化且可撤销，避免一步编辑失误导致整个代码库被破坏。

论文的核心发现是：ACI 的界面设计对 agent 表现的影响和模型能力本身至少同等重要。这不是夸张——在各种实验中，同样的模型在优化过的 ACI 下和在朴素的 ACI 下可以达到 20%-30% 的成功率差距。这意味着 engineering effort 在 ACI 上的投入，其回报率可能不低于升级到更昂贵的大模型。对资源有限的团队来说，这是一个非常有价值的信息——与其花大价钱用最强的模型，不如花时间把 ACI 做好，用中等模型拿到不错的成绩。

这篇论文和 OpenHands 有天然的互补关系：OpenHands 回答"需要什么组件"，SWE-agent 回答"这些组件应该怎么设计界面"。OpenHands 告诉你需要 sandbox、browser、action space；SWE-agent 告诉你 sandbox 里的文件查看器要格式化成什么样、action space 里的编辑操作要设计成什么粒度。两篇合在一起读，能形成对 coding agent 基础设施的完整理解。

arXiv: https://arxiv.org/abs/2405.15793

**T1-2：Coding Agent 企业级评测**

基础设施搭建完成后，自然的问题是：怎么评估 coding agent 在真实工程场景中的表现？T1-2 的三篇论文从不同角度回答了这个问题。

**Terminal-Bench: Benchmarking Agents on Hard, Realistic Tasks in Command Line Interfaces** 的视角很特别：它不测 agent 写代码的能力，而是测 agent 在命令行终端中解决实际问题的能力。Terminal-Bench 2.0 包含 89 个任务，每个任务提供独立的 Docker 环境、人类解法参考和自动化测试。

为什么终端环境值得单独做一个 benchmark？因为在真实工程中，大量问题是通过命令行解决的——调试构建错误、配置环境变量、分析日志文件、管理进程、排查网络问题。这些任务和"写一个函数"完全不同：它们要求 agent 理解系统状态（比如当前 shell 环境、进程列表、文件权限），处理不确定性（比如日志可能有噪音、错误信息可能误导），并在信息不完整的情况下做出判断（比如不知道是否是权限问题还是配置问题时，需要一步步排查）。这些能力在传统的"给一个 repo 和一个 issue，让 agent 修 bug"的评测中完全得不到测试。

arXiv: https://arxiv.org/abs/2601.11868

**SWE-Bench Pro: Can AI Agents Solve Long-Horizon Software Engineering Tasks?** 是 SWE-bench 系列的企业级升级。原始 SWE-bench 已经成为 coding agent 的事实标准评测——几乎所有主要的 coding agent 论文都会报告 SWE-bench 分数。但它有一个被广泛讨论的局限：大部分任务来自开源仓库的 issue，任务规模偏小，通常涉及 1-2 个文件的修改，依赖关系简单。

SWE-Bench Pro 把门槛提高了几个量级：1,865 个问题来自 41 个真实维护的企业级仓库，任务涉及多文件修改、跨越多个模块的依赖追踪、以及需要理解整个代码库架构才能解决的问题。即使是最强的 coding models，Pass@1 仍然低于 25%——这意味着每四次尝试只有不到一次能成功完成一个真实企业级任务。这个数字应该让所有对 agent 能力过度乐观的人冷静下来。在开源小任务上拿到 50%、60%、甚至 70% 的成功率是可能的，但在企业级多文件依赖任务上，最顶尖的模型也只能做到不到四分之一。

这篇论文值得读的地方是它定义了什么算"难"——不是代码行数多，而是任务需要跨文件理解、需要处理隐式依赖、需要在多个可能的解决方案中做出工程判断。一个"修改一行代码就能修好的 bug"可能只有 10 行 diff，但它难在定位那一行；一个"实现一个新功能"可能有 500 行代码，但每一步的方向都比较明确，反而不一定比前者难。SWE-Bench Pro 的任务设计抓住了"难"的本质——信息分散、依赖隐晦、需要全局理解。

arXiv: https://arxiv.org/abs/2509.16941

**SWE-EVO: Benchmarking Coding Agents in Long-Horizon Software Evolution Scenarios** 从另一个维度补充了 coding agent 评测：软件演进（software evolution）。现实中工程师不只是修 bug，还需要做版本升级、依赖迁移、API 适配、功能迭代。这些任务的共同特点是：不是从零到一，而是在已有的复杂系统上做增量修改——你面对的不是一个空白画布，而是一张已经画满了、需要你在特定位置修改、同时不能破坏其他部分的画。

SWE-EVO 的设计很有针对性：它不给定一个独立的 issue，而是给定 release notes 或 version history——也就是真实软件项目中的版本变更记录——要求 agent 理解"从这个版本到那个版本之间发生了什么变化"，然后在新代码库中完成对应的演进操作。比如，一个库从 v2 升级到 v3，API 签名变了，agent 需要找到所有使用旧 API 的地方，理解新旧 API 的语义映射，然后逐个修改。这测试的不是 coding 能力本身——写代码实现在这里只是最后一步——而是"理解软件变更上下文"的能力。在真实工程中，这往往比写出正确代码更难。

arXiv: https://arxiv.org/abs/2512.18470

**T1-3：通用 Agent Benchmark**

coding agent 之外，还有大量 agent 应用场景需要评测支持。不是所有的 agent 都是写代码的——有的 agent 负责客服、有的负责数据分析、有的负责工作流自动化。T1-3 的四篇论文覆盖了 tool-use agent、stateful 环境、多 app 交互和 computer-use 四个维度。

**τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains**（tau-bench）的独特之处在于引入了"用户"作为评测的一部分。大多数 benchmark 假设任务是自包含的——给 agent 一个任务描述，它自己完成，中间不需要和人交互。但现实中很多 agent 任务需要和用户交互——询问偏好、确认操作、报告进度。τ-bench 模拟了这种三方交互：agent + 工具 + 用户。agent 使用工具完成任务，同时需要和用户对话来获取必要信息或确认关键操作。

更有意思的是，τ-bench 要求 agent 遵守领域 policy——比如在航空订票系统中，agent 必须遵守关于退改签的规则。这引入了合规性的维度：agent 不只是要"完成用户说的"，还要在完成的同时不违反领域规则。这比单纯的任务完成更接近真实部署场景——企业 agent 几乎总是需要在 policy 约束下运作。

τ-bench 还提出了 pass^k 指标：在 k 次对话尝试中至少成功一次。这个指标承认了 agent 行为的不确定性——同一个 agent 对同一个任务可能得到不同的结果，所以单次尝试的偶然性需要被统计方法消化。pass^k 的值总是高于 pass@1（因为给了多次机会），但它更贴近实际部署的心理预期——一个用户使用 agent 时，如果第一次失败了，可能会再试一次；但如果试了 k 次还不行，大概就放弃了。

arXiv: https://arxiv.org/abs/2406.12045

**ToolSandbox: A Stateful, Conversational, Interactive Evaluation Benchmark for LLM Tool Use Capabilities** 强调的是"状态"（state）。很多 tool-use benchmark 是无状态的——每次工具调用互不影响，像是一次次的独立函数调用。但在现实中，工具调用会改变系统状态：创建了一个文件、修改了数据库记录、发送了一条消息、开启了某个系统服务。后续的工具调用必须在正确的状态基础上进行——如果你第一步创建了一个文件，第二步就需要知道这个文件在哪里、里面有什么。

ToolSandbox 引入了三个关键设计来测试这种状态感知能力。第一是状态依赖——工具调用的结果影响后续可用的操作。比如 agent 查询了数据库获得了某个 ID，后续操作需要使用这个 ID 来更新对应的记录。如果 agent 在第二步用了错误的 ID，说明它不只是在"选工具"上出了问题，而是在"追踪状态"上出了问题。第二是用户模拟器——模拟真实用户的对话和需求变更。用户可能在交互中改变需求，agent 需要适应这种变化。第三是中间里程碑评价——不只评价最终结果，还评价中间步骤的正确性。这很重要，因为有时候 agent 最终结果是对的，但中间走了不必要的弯路（比如重复查询了多次同样的信息），这说明 agent 的效率存在问题。

这个设计让 tool-use 评测从"模型能不能选对工具"升级为"模型能不能在状态变化的环境中持续做出正确决策"。前者是静态的、单步的判断能力；后者是动态的、多步的追踪能力。两种能力完全不在同一个维度上。

arXiv: https://arxiv.org/abs/2408.04682

**AppWorld: A Controllable World of Apps and People for Benchmarking Interactive Coding Agents** 是目前最接近"数字生活模拟"的 agent benchmark。它构建了一个微型但完整的数字世界：9 个日常 app——邮件、日历、文档、地图等；457 个 API；约 100 个虚拟用户的日常活动在持续运行；以及 750 个跨应用的任务。

AppWorld 的设计哲学是：真实世界的 agent 不会只在一个 app 里操作。一个典型的场景是——你需要准备一个会议：在邮件中找到参会者发来的议题、在日历中确认每个人的空闲时间、在地图中查会议地点的路线、然后在文档中汇总议程。每一个步骤的输出都是下一个步骤的输入：邮件中的信息驱动日历查询、日历查询结果驱动地图搜索、地图信息最终汇总到文档。这个跨 app 的信息流动和操作链是对 agent 的真正考验——每一跳的信息传递都可能出错，而任何一个环节的出错都会级联到后续所有步骤。

AppWorld 也测试了 agent 的一个关键但常被忽视的能力：权限和隐私边界。在真实世界中，agent 不应该访问所有数据——它应该只访问和当前任务相关的数据。AppWorld 通过设计"不需要访问的 app"来测试 agent 是否过度读取信息。

arXiv: https://arxiv.org/abs/2407.18901

**OSWorld: Benchmarking Multimodal Agents for Open-Ended Tasks in Real Computer Environments** 是 computer-use agent 方向的经典 benchmark。computer-use agent 指的是能操作真实操作系统图形界面的 agent——它需要看到屏幕上的按钮、理解视觉布局、模拟鼠标点击和键盘输入。

OSWorld 的核心实验设置很直观：让 agent 在真实的 Ubuntu/Windows 虚拟机中完成日常操作任务——比如改系统设置、整理文件、安装软件、填写﻿表单——然后和人类的表现对比。这是极少数同时有 agent 和人类在同一环境下的表现数据的 benchmark。

结果非常说明问题：人类在 OSWorld 上的成功率是 72.36%，而论文发表时最好的模型只有 12.24%。即使到了今天，差距仍然巨大。这个差距来自多个层面：视觉理解——agent 需要"看懂"屏幕上的按钮和文字，但当前的视觉语言模型在小元素识别、模糊文本、动态界面上的准确率远不如人类；操作精度——点击位置是否准确、拖拽方向是否正确、滚动幅度是否合适，这些精细操作对人类来说是本能，但对 agent 来说需要精确的坐标预测；以及任务规划——在操作系统中完成一个任务通常需要多步规划，每一步依赖于上一步的结果，任何一步的视觉误判或操作失误都会导致后续步骤在错误的前提下展开。

OSWorld 在今天仍然值得读，因为它提出的问题还没有被解决——computer-use agent 的可靠性和人类相比还有数量级的差距。与 coding agent 不同（代码环境干净、可自动验证），GUI 环境充满视觉噪声和操作歧义。你不知道 agent 是"没看到"那个按钮，还是"看到了但不知道要按"，还是"知道要按但按错了位置"。这三种失败模式需要完全不同的解决方案，但粗略的"成功率"数字不会告诉你它们各自的占比。

arXiv: https://arxiv.org/abs/2404.07972

**T1-4：Web Agent**

Web agent 是 agent 研究中一个相对独立但高度活跃的子方向。它的核心挑战是：在开放、动态、异构的网页环境中执行任务。和 coding agent 不同，web agent 不能假设环境是确定的——同一个网页在不同时间可能显示不同内容（比如新闻网站会更新、购物网站价格会变动），网站结构会更新（前端改版后元素的 CSS selector 全变了），页面元素的位置和样式没有统一规范（每个网站有自己的设计语言）。这些不确定性让 web agent 的评测和训练都比 coding agent 复杂得多。

**The BrowserGym Ecosystem for Web Agent Research** 为 web agent 研究提供了标准化的实验环境。BrowserGym 的核心设计是统一 observation space（agent "看到"的网页信息格式）和 action space（agent 可以执行的网页操作类型），让不同模型和 scaffold 可以在相同的 gym-like 环境下比较。gym-like 指的是类似 OpenAI Gym 的强化学习环境设计——标准化的环境接口、可重复的实验、自动化评估。

这听起来和 HAL 的理念相似——都是标准化评测基础设施。但 BrowserGym 面临的挑战更大——网页环境的多样性远超代码环境。代码可以是 Python 或 JavaScript，但它们的结构和语义是相对规则的。网页则完全不同：同一个"搜索商品"的操作，在淘宝和京东上是完全不同的 DOM 结构、不同的按钮 ID、不同的页面流。一个统一的 observation/action space 需要在"保留足够信息让 agent 操作"和"标准化到可以跨网站比较"之间做艰难的权衡。保留太多网站特有的信息，就会让不同网站上的结果无法比较；标准化过头，agent 就没有足够的信息来完成操作。

arXiv: https://arxiv.org/abs/2412.05467

**WebGym: Scaling Training Environments for Visual Web Agents with Realistic Tasks** 则从训练角度切入。和只做评测的 benchmark 不同，WebGym 提供了近 30 万个真实网站上的任务，目标不只是评测 agent 表现，而是作为强化学习（RL，Reinforcement Learning）的训练环境。RL 是一种通过试错来学习的方法——agent 执行操作，环境给出奖励或惩罚信号，agent 根据信号调整策略。

这对 web agent 的发展有特殊意义：大部分 web agent 依赖模型的预训练能力——模型在预训练时看过大量网页内容，知道网页通常是什么样子、按钮是什么意思。但它们很少经过专门的 web 任务 RL 训练——也就是在真实的网页上反复尝试执行任务、从成功和失败中学习。这就像一个从来没开过车但读过所有汽车手册的人——知道刹车和油门在哪，但真正上路时还是会手忙脚乱。WebGym 的规模意味着大规模 RL 训练 web agent 在工程上成为可能。而经过 RL 训练的 visual web agent 是否比只靠预训练的 agent 有质的提升，是一个值得关注的问题——如果 RL 训练能让成功率从 30% 提升到 60%，那它就是必须投入的方向；如果只从 30% 提升到 33%，那可能这条路本身有问题。

arXiv: https://arxiv.org/abs/2601.02439

**T1-5：AI R&D Agent**

最后一个 T1 专题可能是最"元"的：用 agent 来做 AI 研究本身。如果 agent 能写代码、做实验、分析结果，那它能不能做 ML 研究？这个方向的评测比 coding agent 更难，因为 ML 研究的"正确答案"本身就不确定——两个不同的模型架构哪个更好，往往没有唯一答案，而是取决于数据集、计算预算、评估指标等几十个变量。

**RE-Bench: Evaluating frontier AI R&D capabilities of language model agents against human experts** 设计了 7 个开放式的 ML research engineering 环境，并和 61 位人类专家在 8 小时尝试中的表现进行了对比。每个环境对应一类 ML 研究任务——比如优化一个训练 pipeline 的 GPU 利用率、改进一个小模型的 fine-tuning 策略、分析一个数据集的标注质量问题。

RE-Bench 的环境设计很讲究：不是"训练一个 MNIST 分类器"这种教科书任务——这种任务太简单，任何看过教程的人都能做，区分度太低。而是需要做架构选择（为什么要用这个优化器而不是那个）、超参调优（Learning rate 应该设多大、batch size 怎么选）、性能优化（如何让训练速度更快、显存使用更少）等真实 ML 工程判断的开放式任务。和人类专家的对比让评测结果有了有意义的参照——不是"agent 得了 80 分"（不知道 80 分意味着什么），而是"agent 在 8 小时内达到了人类专家 8 小时内能达到的什么水平"。这个参照让抽象的数字有了具体的含义。

arXiv: https://arxiv.org/abs/2411.15114

**HCAST: Human-Calibrated Autonomy Software Tasks** 的校准方法更进一步：它收集了 189 个软件/安全/ML 工程任务的人类完成时间数据——总共 563 个人类 baseline，来自具有不同经验水平的工程师——然后用这些时间来校准 agent 的能力。具体来说，HCAST 不只看 agent "能不能完成"，而是看"完成同样质量的工作，agent 花了多长时间，和人类花了多长时间"。

HCAST 的方法论价值在于它把度量从"会不会做"推进到"做得多快"。在评估 autonomous agent 时，速度是一个和成功率同样重要的维度——一个能做所有事情但每件事都比人类慢 10 倍的 agent，在实际部署中的价值是有限的。如果你让 agent 做一个需要人类 1 小时的任务，它花了 10 小时，那你实际上是花了更多时间而不是节省了时间——别忘了你还得花时间审查 agent 的输出。HCAST 的 time-based 校准让这个维度变得可量化。

arXiv: https://arxiv.org/abs/2503.17354

#### T2：专题补强——深入特定方向

**T2-1：记忆系统**

如果一个 agent 每次对话都从零开始，它的能力上限就是单次上下文窗口的大小。记忆系统试图突破这个上限——让 agent 能记住之前的交互、从过去的经验中学习、在长任务中保持关键信息的可访问性。这个问题听起来简单，但在工程实践中极其复杂：记忆太多了会淹没当前任务的相关信息（信息过载）；记忆太少了又会丢失关键时刻需要的上下文（信息缺失）；记忆组织方式不对会导致检索不到（虽然"存了"但"找不到"）。

**Agentic Memory: Learning Unified Long-Term and Short-Term Memory Management for LLM Agents (AgeMem)** 的核心创新是让记忆管理本身成为 agent policy 的一部分。传统做法是设计一个独立于 agent 的记忆模块——agent 通过特定的 API 读写记忆，记忆模块自己决定存储策略。AgeMem 的做法是让 agent 自主决定何时 store（存储当前交互的关键信息到记忆库）、retrieve（从记忆库中搜索和当前任务相关的历史信息）、update（更新已有记忆——因为新信息可能和旧记忆冲突或补充）、summarize（将多条相关记忆压缩为一条摘要，节省存储空间）、discard（丢弃那些不再相关或已被摘要替代的记忆）。

这个设计的洞察在于：不同的任务对记忆的需求是不同的。一个需要频繁切换上下文的客服 agent 需要一个快速检索的短期记忆——上一个用户问的是退货，这一个用户问的是换货，两者的 policy 不同；一个做长期项目追踪的 agent 需要一个结构化的长期记忆——三个月前做过的技术选型决策及其理由，现在做类似决策时需要参考。让 agent 自己决定记忆策略，比设计一个"一揽子"记忆模块更灵活——agent 可以针对当前任务的特性选择性地使用记忆，而不是被一个笨重的记忆系统拖慢。

arXiv: https://arxiv.org/abs/2601.01885

**A-MEM: Agentic Memory for LLM Agents** 从组织方式上切入记忆问题。它受 Zettelkasten（卢曼卡片盒笔记法）启发，把记忆组织成动态链接网络——每条记忆不是孤立的条目，而是和其他相关记忆通过语义链接关联在一起。Zettelkasten 的核心理念是：知识的力量不在于你存了多少条笔记，而在于笔记之间的链接密度。两条孤立的笔记各有用处，但当你把"强化学习在 agent 训练中的应用"这条笔记链接到"BERT 预训练中的 MLM 目标函数设计"时，你就可能产生新的洞见。

这个设计的优势在于检索：当 agent 需要回忆某件事时，它可以从一条记忆沿着链接网络找到相关记忆，而不是在 flat（扁平）的记忆库中做关键词搜索。flat 搜索的问题是：你搜"tool use"，只会返回包含 "tool use" 的记忆，但这些记忆之外的所有背景知识都丢失了。而链接网络允许 agent 从"tool use 的评测方法"这条记忆跳转到"HAL 论文的 scaffold 标准化设计"，再跳转到"ACI 设计的基本原则"——前一条是评测相关的具体知识，后两条提供了理解评测方法的上下文。对于需要跨领域知识关联的复杂任务，这种网络化的记忆组织方式更接近人类联想记忆的工作机制。

arXiv: https://arxiv.org/abs/2502.12110

**Evaluating Memory in LLM Agents via Incremental Multi-Turn Interactions / MemoryAgentBench** 则从评测角度拆解记忆能力。这篇论文的价值在于它不笼统地说"测记忆"，而是把记忆能力分解为四个可以独立评测的维度：accurate retrieval（精确检索——从记忆中准确找到需要的信息，比如第 3 轮对话中用户提过一个偏好，第 15 轮时 agent 能否准确回忆起来）、test-time learning（测试时学习——在交互过程中从新信息中学习，比如用户纠正了 agent 的某个错误理解，agent 是否能在后续交互中不再犯同样的错误）、long-range understanding（长程理解——理解跨多轮对话的信息关联，比如第 2 轮讨论了项目 A 的架构，第 20 轮讨论项目 B 的架构，agent 能否正确区分两者而不混淆）、selective forgetting（选择性遗忘——丢弃不相关信息以保持记忆效率，比如 50 轮前的闲聊内容不应该挤占当前关键任务的记忆空间）。

这四维分解很有工程价值：当你的 agent 表现出"记忆问题"时，"它记性不好"是一个模糊的诊断——你只知道有问题，但不知道从哪里修。但如果你能定位到是 retrieval 差（存了但找不到）还是 selective forgetting 差（什么都记导致重要的被挤掉了），就能针对性地改进——retrieval 差就优化搜索 ranking，forgetting 差就实现记忆优先级和过期策略。

arXiv: https://arxiv.org/abs/2507.05257

**T2-2：技能审计与安全**

给 agent 一个 skill（技能定义——一段指令、工具、提示模板的组合，让 agent 能完成特定类型的任务），它就能执行对应的操作。但 skill 对 agent 的实际行为有什么影响？一个看起来无害的 skill 会不会在特定上下文中导致不安全的行为？这就是技能审计要回答的问题。这个问题的重要性体现在：agent 系统通常由数十甚至上百个 skill 组成，每个 skill 单独看都是安全的，但组合在一起可能产生意外的不安全交互。

**Counterfactual Trace Auditing of LLM Agent Skills** 提出了一个直接的方法：对比有和没有某个 skill 时 agent 的行为轨迹。counterfactual（反事实）的意思是"如果情况不同会怎样"——具体做法是，同一个任务、同一个输入，跑两次：一次有 skill X，一次没有。然后对比两次的 trajectory 差异。如果添加一个 skill 后 agent 在相同任务上的行为发生了变化，这种变化的方向和幅度就是该 skill 的影响。比如，添加了一个"自动执行 shell 命令"的 skill 后，agent 在相同的 coding 任务上突然开始执行之前不会执行的危险命令——这说明该 skill 在整体系统中引入了之前未预料到的风险路径。

这篇论文的实用价值在于：它提供了一个系统化审计 agent skill 的方法论，而不只是"运行看看有没有问题"——后者的问题是，你可能在测试中碰巧没触发不安全的路径，但生产环境中某个特殊的输入组合会触发。对于维护大型 agent skill 体系的工程师来说，counterfactual trace auditing 相当于给 skill 库加了一套单元测试——每当你添加或修改一个 skill，跑一遍对照实验，确认行为变化的方向和幅度在预期之内。

arXiv: https://arxiv.org/abs/2605.11946

**ATBench: A Diverse and Realistic Trajectory Benchmark for Long-Horizon Agent Safety** 提供了 1,000 条安全和不安全的行为轨迹，平均每条轨迹 9.01 轮交互。ATBench 的价值在于它的轨迹（trajectory）级别标注——不是标注"这个 agent 安全/不安全"（这种二元标签信息量太低），而是标注"在这一步 agent 的行为开始偏离安全边界"。比如一条轨迹可能在前 5 轮都在正常完成任务，第 6 轮 agent 遇到了一个它不理解的操作，它没有选择 Ask（询问用户），而是选择了 Act（自行猜测执行），这一步就是安全偏离的起点。

这种细粒度标注让安全研究从"分类"升级为"定位"——不只是判断 agent 是否安全，而是找到 agent 在哪一步开始走向不安全的方向，以及是什么触发了这种偏离（是遇到了陌生的工具？是 context 中出现了误导信息？是任务的复杂度超过了 agent 的处理能力？）。定位到触发点，才能设计针对性的防护机制。

arXiv: https://arxiv.org/abs/2604.02022

**TRACES: Proactive Safety Auditing for Multi-Turn LLM Agents via Trajectory-State Modeling** 提出了一个更有前瞻性的方法：不等 agent 做出不安全行为再去审计，而是在行为发生之前就预测轨迹是否会滑向危险。它使用一个 observer LLM（观察者模型）的隐藏表征（hidden representations——模型中间层的向量表示，编码了模型对当前状态的理解）来建模 trajectory state，在风险显性爆发之前发出预警。

这个思路类比于自动驾驶中的"碰撞预警系统"——不是等撞上了再分析为什么会撞，而是在可能发生碰撞的几秒前就发出警报。在生产环境中，reactive 审计（出事了再查）的价值有限——损失已经造成了。proactive 审计（出事前预警）才能真正保护系统安全。TRACES 的目标是在 agent 执行第 N 步时，observer LLM 就能判断出"按照目前的 trajectory state，agent 有较高概率在第 N+5 到 N+10 步之间做出不安全操作"，从而提前干预——可以是暂停 agent 等待人工审核，也可以是注入额外的安全提示。

arXiv: https://arxiv.org/abs/2605.27690

**ToolPrivacyBench: Benchmarking Purpose-Bound Privacy in Tool-Using LLM Agents** 关注一个具体但重要的安全问题：agent 在使用工具时是否会泄露私有信息。论文设计了 2,150 个测试案例，审计 agent 是否将私有信息只发送给了被授权的工具。

这个问题的微妙之处在于：agent 可能不是"恶意"泄露信息，而是在完成任务的过程中无意中把私有数据传给了不该接收的工具。比如，用户让 agent 调用一个第三方翻译 API 来翻译一段文本——但这段文本中包含用户的真实姓名和地址。agent 照做了，翻译 API 的日志中记录了这段文本。从 agent 的角度，它完成了任务；从隐私的角度，一次信息泄露已经发生了。ToolPrivacyBench 的系统化审计能帮助发现这种非恶意的信息泄露——它模拟各种"合法任务 + 敏感信息"的组合场景，检查 agent 在处理这些任务时是否会将敏感信息传给未授权的工具。

arXiv: https://arxiv.org/abs/2606.28061

**T2-3：Agent 后训练**

**Let It Flow: Agentic Crafting on Rock and Roll, Building the ROME Model within an Open Agentic Learning Ecosystem** 介绍了一个完整的 agent 后训练生态系统（ALE，Agentic Learning Ecosystem）。这个系统包含三个核心组件：ROLL 负责 post-training——在后训练阶段优化模型的 agent 能力，通过注入大量 agent 行为数据让模型习得 agent 场景下的行为模式（什么时候该用工具、什么时候该停下来、怎么从错误中恢复）；ROCK 负责 sandbox trajectory generation——在隔离的沙箱环境中生成训练用的 agent 轨迹数据，这些轨迹包含了 agent 的成功和失败案例，两者都是宝贵的训练信号；iFlow CLI 作为 agent 框架的统一命令行接口，提供标准化的交互方式。

这篇论文的价值在于它展示了一条从"通用模型"到"agent 专用模型"的工程路线。大多数 agent 是基于通用 LLM + prompt engineering 构建的——拿一个训练好的通用模型，用精心设计的提示模板引导它表现出 agent 行为。这个做法的问题是：通用模型在预训练时几乎没有见过 agent 行为数据。它擅长续写文本、回答问题、总结文章，但不擅长"这个任务需要分 5 步、第 2 步可能需要回退并重新规划"的 agent 思维模式。prompt engineering 相当于在一张白纸上画了一条路——路是好路，但纸上从来没出现过路，模型需要"硬推"才能走在路上。

如果要在 agent 能力上有质的突破，可能需要在后训练阶段系统性地注入 agent 行为数据。这不只是"多训练几轮"的问题——而是需要在训练数据中引入 trajectory（完整的行为序列）、错误恢复路径（agent 做错了然后自我纠正）、以及决策权衡（什么时候继续、什么时候放弃、什么时候求助用户）。这些数据在通用模型的预训练语料中几乎不存在，但在 agent 后训练中可以被大规模合成。

arXiv: https://arxiv.org/abs/2512.24873

**T2-4：Web Agent 专题**

**WebArena: A Realistic Web Environment for Building Autonomous Agents** 是 web agent 领域的早期经典。它在 2023 年就构建了包含电商、论坛、协作开发、内容管理等真实网页的环境，为 web agent 研究奠定了实验基础。

WebArena 的历史价值大于它的技术新颖性——在今天读它，更多是为了理解 web agent 研究的起点在哪里，以及这个领域从 2023 年到 2026 年之间走了多远。2023 年，web agent 只能完成最简单的导航和搜索任务；到 2026 年，web agent 已经能在多网站之间协调完成复杂的多步任务。WebArena 设定了一个初始的坐标系，后来的研究在这个坐标系上不断推进边界。

arXiv: https://arxiv.org/abs/2307.13854

**SecureWebArena: A Holistic Security Evaluation Benchmark for LVLM-based Web Agents** 把安全视角引入 web agent。LVLM（Large Vision-Language Model）是 web agent 常用的模型类型——它能同时理解视觉信息（网页截图）和文本信息（HTML 结构）。它构建了 6 个模拟但真实的 web 环境，设计了用户级攻击（如钓鱼页面——一个看起来像正规银行但实际是恶意的网页，诱导 agent 输入敏感信息）和环境级攻击（如恶意脚本注入——网页中隐藏了 JavaScript 代码，在 agent 访问时自动执行危险操作），测试 agent 能否识别和抵御这些威胁。

随着 web agent 被越来越多地用于自动浏览、购物、信息收集，它们面对的安全威胁也在增加。一个被恶意网页诱导的 web agent，可能比一个人类用户更容易上当——因为它没有"这个页面看起来不太对劲"的直觉。SecureWebArena 填补了"web agent 安全性评测"这个之前几乎空白的领域。

arXiv: https://arxiv.org/abs/2510.10073

**WebChoreArena: Evaluating Web Browsing Agents on Realistic Tedious Web Tasks** 关注一个被大多数 benchmark 忽略的场景：无聊但费时的网页任务。532 个任务涉及大量信息检索、数据计算和跨网页长期记忆——这些不是在做一个"聪明"的决定，而是在保持长时间的专注和准确性。比如，从 50 个不同的产品页面中提取规格信息并汇总到一张表；或者在多个不同格式的网页中查找同一类信息（不同网站把"价格"放在不同位置、用不同标签）。

这个方向的现实意义是：很多企业部署 agent 的第一个场景不是做创造性工作，而是替代人工做繁琐重复的网页操作——数据录入、信息汇总、报表生成。这些任务对智能的要求不高（人类实习生都能做），但对准确性和耐心的要求极高（需要持续几小时不出错）。如果 agent 在这些"无聊"任务上不可靠，它的商业价值就会大打折扣。企业不会为了"agent 有时能写出漂亮的代码但经常犯低级错误"买单，但会为"agent 能 24 小时不间断做数据录入且错误率低于人类"买单。

arXiv: https://arxiv.org/abs/2506.01952

### 阅读路径与建议

如果时间只够读 5 篇：读 T0 全部 5 篇。顺序建议按上述 T0 部分的叙述顺序读——从 Codex 的产品观察开始，到 METR 的度量框架，到 HAL 的标准化评测，到 AgentAtlas 的行为分析，最后到 Open-World Eval 的批判性反思。这个顺序有内在的递进逻辑：从"看到了什么现象"到"怎么度量"到"怎么标准化地度量"到"度量结果怎么分析"到"度量本身的局限性"。跳着读也可以，但按顺序读能感受到方法论是如何层层推进的。

如果时间够读 10 篇：T0 全部 + T1 中选一个最相关的专题组。做 coding agent 的从 T1-1 开始读——先理解基础设施（OpenHands + SWE-agent），再理解评测（T1-2 的三篇）。做通用 agent 评测的从 T1-3 开始读——τ-bench、ToolSandbox、AppWorld、OSWorld 覆盖了从对话式 tool-use 到全 GUI 操作的光谱。

最大化阅读收益的实践建议：每读完一篇论文，尝试回答三个问题。第一个问题——这篇论文的核心观点是什么？用一句话说出来，如果说不出来就说明你没读懂。第二个问题——它挑战了我之前的什么假设？大部分方法论论文的价值不在于告诉你新事实，而在于纠正你之前没意识到的错误假设。第三个问题——如果让我用这篇论文的方法评估一个我熟悉的 agent 系统，会得到什么结果？这第三个问题特别重要，因为它把"读别人的经验"转化为"我可以做的实验"。如果你读完 AgentAtlas 后尝试用它的 6 类决策状态分析你自己的 agent 的 trajectory，你会得到远比"读完记住了"深刻的理解。

另外，建议配合一个实际的 agent 项目来读——可以是自己搭建的一个简单 agent 系统，或者是一个开源 agent 框架的源码阅读。当论文中的概念（scaffold、trajectory、stateful tool-use、memory retrieval）在你自己的代码中有了对应物时，阅读的深度会完全不同。你会意识到"原来我写的那个简易沙箱就是 scaffold 的一部分""原来我的 agent 每次重试都从零开始是因为我没有 memory 系统"。这种"概念映射到代码"的体验是纯阅读无法替代的。

### 总结

这份清单的核心观点在前言中已经点明：读论文是为了建立判断力，不是为了追热点。

T0 的 5 篇论文建立的是判断力的基础框架——读完它们，当你看一篇新的 agent 论文时，会自然地追问：这个评测的度量指标合理吗？scaffold 设计是否被交代清楚？成功率背后隐藏了什么行为模式？这些追问比"这篇论文的分数是多少"重要得多。因为分数会变——下个月可能就有模型在同一个 benchmark 上刷新记录——但追问的能力不会过时。

T1 的论文提供的是工程上的实用参考。每篇论文解决一个具体的问题：怎么设计 ACI、怎么构建企业级 benchmark、怎么评测有状态的 tool-use。它们不要求全读，而是按需取用——你需要什么，就读对应的那组。如果你不做 web agent，T1-4 可以不读；如果你不做 AI R&D agent，T1-5 可以跳过。这不是课程大纲，是工具箱。

T2 的论文是入口，不是终点。它们每个专题（记忆、安全、后训练）都有自己的论文生态——记忆方向有几十篇后续论文探讨不同的检索策略和存储架构，安全方向有几十篇论文覆盖从 prompt injection 到 sandbox escape 的各种威胁模型。这里列的只是帮助你找到入口的那几篇。深入任何方向都需要继续追踪后续论文——通过被引列表向前追（"这篇论文引了谁"）、通过施引列表向后追（"谁引了这篇论文"）。

最后，论文是会过时的——评测数字会变、SOTA 会刷新、框架会被替代。2023 年最好的 coding agent 在今天可能连中等都排不上。但那些认真思考"怎么度量""怎么分析""怎么设计"的论文，它们的价值不会过时。因为方法论的寿命比数字长得多。SWE-agent 提出的 ACI 设计原则，在今天仍然指导着最新的 agent 框架设计。METR 的 time horizon 度量哲学，在模型能力再提升 10 倍之后仍然适用——只不过时间轴上的数字会变化而已。

选择读什么论文，本身就是一种判断力的体现。希望这份清单能帮助读者少花时间在"不知道该读什么"上，多花时间在"读完之后知道怎么用"上。

## 知识缺口

这份清单覆盖了 agent 评测、基础设施、记忆、安全、后训练和 web agent 等方向，但 agent 领域远不止这些。以下几个重要方向在本文中未被覆盖，读者可以根据兴趣自行追踪。

首先是多 agent 协作与协调（multi-agent coordination）。当一个系统中存在多个 agent 时，它们如何分工、通信、协商、解决冲突，是一个完整的研究子领域。相关的核心问题包括：agent 之间的消息协议设计、任务分解与分配策略、共享记忆与私有记忆的边界、以及当 agent 之间出现目标冲突时的仲裁机制。这个方向的研究和博弈论、分布式系统理论有深度交叉。

其次是 agent 经济学。当 agent 被大规模部署时，它们会消耗计算资源、API 调用配额、以及时间成本。如何在有限的预算内最大化 agent 的任务产出，涉及到 cost-aware planning（成本感知的规划）、tool selection with pricing（考虑价格的工具选择）、以及 inference-time compute allocation（推理时的算力分配决策）。agent 经济学的实用价值在于：它决定了一个 agent 系统在商业上是否可行——技术上能做到和商业上能赚钱是两回事。

第三是 human-agent interaction（人机交互）的 UX 研究。大多数 agent 论文关注的是 agent 的能力，但很少关注 agent 和人类用户之间的交互体验。agent 应该以什么频率向用户报告进度？在什么情况下中断用户比继续自主执行更合理？如何设计 agent 的输出让用户能快速审查和信任？这些问题不只是"界面好不好看"，而是直接影响用户是否愿意持续使用 agent。

第四是 agent 的评估驱动开发（evaluation-driven development）。本文涵盖了大量评测 benchmark，但"如何在日常开发中持续使用这些 benchmark 来驱动 agent 的迭代"是一个工程方法论问题。包括：如何选择适合当前 agent 的评测集、如何在 CI/CD 流程中嵌入 agent 评测、如何设计 A/B 测试来比较不同的 scaffold 或 prompt 设计、以及如何从评测结果反向推导改进方向。

第五是领域特定的 agent 应用。医疗 agent 需要处理 HIPAA 合规、诊断准确性、以及不可逆操作的后果；法律 agent 需要处理管辖权的差异、判例引用的准确性、以及律师-客户特权；金融 agent 需要处理实时市场数据、合规监管、以及交易操作的不可撤销性。每个领域都有自己的约束和挑战，通用 agent 方法论在这些领域中需要做出大量适配。

第六是 agent 的可解释性（explainability）。当 agent 做了一个错误的决定，人类操作者需要理解"它为什么这么做"才能决定是信任它、修改它的行为、还是停用它。可解释性不只是打印一个 log，而是需要在 agent 的决策层面提供可理解的理由——比如"我选择了工具 A 而不是工具 B，因为工具 A 的延迟更低且结果更结构化"。

这些缺口意味着：读完 T0-T2 的论文后，能建立的判断力主要集中在"单个 agent 的能力评估"上。如果读者的工作需要涉及多 agent 系统、成本优化、领域适配、或用户交互设计，需要在上述方向中继续深入。
