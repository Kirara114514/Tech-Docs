# AI编程中的上下文管理与记忆系统

## 摘要

AI 编程进入工程化阶段后，如何让 AI 有效理解大型项目的结构与规范，成为制约生产力的核心瓶颈。现有做法——将完整项目文档或长篇 skill 文件整体丢入模型上下文——在项目规模较小时勉强可用，但一旦项目膨胀、模块增多、协作周期拉长，这种方式很快暴露出上下文窗口短缺、注意力稀释、Token 成本失控、跨会话记忆断裂等一系列问题。本文从 Claude Context MCP 等现有方案的局限性出发，讨论一种以语义单元替代文件单元、以向量检索替代全量加载、以分层上下文模型替代单一大 Context 的新思路，并延伸至多 Agent 协作场景下的上下文传递与记忆共享问题。本文不提供具体实现代码，而是讨论价值判断与架构选择：哪些问题值得解决、哪些路径已经被验证是死路、哪些取舍在工业级场景下不可妥协。

## 正文

### 背景

#### 问题的起点：AI 编程的上下文瓶颈

AI 编码助手（Claude Code、Cursor、Windsurf 等）正在改变软件开发的日常流程。开发者从亲自写代码，逐渐转变为"描述需求 → AI 生成代码 → 审阅修改"。但这个工作流的效率，极度依赖一个前提：**AI 必须准确理解项目上下文**。

这里的"上下文"至少包括以下几层：

- 项目的整体架构：模块划分、层次关系、依赖方向
- 编码规范与约定：命名规则、错误处理方式、代码风格
- 已有代码的具体实现：函数签名、类结构、接口定义
- 正在进行或计划中的变更：当前分支的目标、尚未合并的改动

当项目规模在几千行代码以内时，直接将项目文件放入模型上下文（或者通过 RAG 检索相关片段）通常足够。但现实中的工业项目不是这个量级。一个中等规模的游戏客户端项目，源码量轻松达到数十万甚至上百万行。即使使用 200K Token 上下文的模型，也无法完整覆盖。

更致命的是，**上下文越满，模型的表现越不可靠**。这不是直觉判断，而是有明确研究支撑的——"大海捞针"测试中，长上下文模型的检索精度会随上下文长度增加而显著下降。对于编程这类需要精确引用接口签名、参数顺序、依赖关系的任务，注意力稀释直接导致代码质量下降。

#### Token 成本的现实约束

除了技术层面的上下文短缺，经济层面同样存在硬约束。

每个向大模型发起的请求，Token 消耗取决于 prompt 长度。如果每次编码请求都要附带数万 Token 的项目背景，成本会迅速失控。对于个人开发者或小团队，这部分成本可能尚可接受；但对于将 AI 编码嵌入到 CI/CD 流水线中的企业团队，Token 消耗会成为一笔不可忽视的账单。

更隐蔽的问题是：**成本不是线性的**。AI 编程的工作流是"尝试 → 反馈 → 修正"的循环。每次尝试的 prompt 都包含项目上下文 + 具体问题，每次修正的 prompt 又包含更多上下文 + 历史反馈。如果上下文没有有效的缓存或分层机制，实际 Token 消耗会远超直觉估算。

#### 现有方案的局限

当前开发者应对上下文瓶颈的方式主要有以下几种，各有缺陷：

**方式一：手动裁剪上下文**
开发者自行判断哪些文件与当前任务相关，手动粘贴到 prompt 中。这种方式在小任务中可行，但高度依赖人的判断力，且容易遗漏关键信息——开发者往往在"这个文件肯定相关"和"这个文件应该不用"之间犯错。

**方式二：制作 Skill 文档**
将项目的架构说明、规范约定、核心模块导读整理成一份 Markdown 文档，作为 AI 的固定背景知识。这是目前最普遍的做法。

但 Skill 文档有一个结构性矛盾：当项目规模变大后，文档本身也会膨胀。一篇覆盖整个项目的 Skill 文档可能达到数千甚至上万 Token，放入 prompt 后既消耗预算又稀释注意力。如果拆成多个 Skill 文档（每个模块一个），则面临"AI 不知道当前任务应该读哪个 Skill"的问题——开发者需要额外判断并指定 Skill，回到了方式一的老路。

**方式三：全量代码喂入**
将整个代码库（或核心部分）塞入模型上下文。这种方式仅在项目极小时有效。一旦项目膨胀，不仅是 Token 成本问题——模型本身的长上下文推理能力也会到达极限。

**方式四：零上下文纯聊天**
不给 AI 任何项目背景，直接提问。这种方式的输出质量完全取决于问题的具体程度和模型的通用知识。对于框架级别的问题（"如何用 UE5 的 Gameplay Ability System"）尚且可用，但对于项目特有的逻辑（"为什么 UserService 要绕一层 AuditInterceptor"）则毫无办法。

#### 一个朴素但正确的直觉

上述四种方式都有一个共同点：它们把"文件"或"文档"作为上下文的基本单元。这个直觉来自人类的工作习惯——人类通过阅读整个文件来理解代码。但 AI 的"理解方式"和人类完全不同。

人类读代码：逐行阅读，建立心智模型，线性理解。
AI 用代码：需要精确命中相关片段才能进行正确推理。

这意味着，**对 AI 的上下文投喂，不应该沿用"给人看"的文件式思维**。一个更合理的思路是：预先扫描全部源码，将函数、类、接口、注释、配置文件各自向量化存储，AI 提问时通过语义检索只拉取最相关的片段作为上下文。这样每次调用只花少量 Token，而且检索到的内容精确相关，远胜于在完整上下文中"大海捞针"。

这个直觉——用一个预构建的代码语义索引来替代全量上下文——就是本文讨论的核心起点。

### Claude Context MCP：一个现成的参考实现

#### 项目概况

Claude Context MCP（zilliztech/claude-context，开源，MIT 协议，GitHub 11K+ Stars）是 Zilliz（Milvus 向量数据库的原创团队）开发的开源项目。它做的事情就是上面描述的那个朴素直觉：扫描代码库，建立向量索引，通过 MCP 协议暴露给 AI 编码助手。

其架构可以概括为：

```
项目源码 → 文件扫描 → BM25 + Dense Vector 混合索引 → Milvus（Zilliz Cloud）
                                                       ↓
AI 编码助手 ← MCP 协议 ← claude-context-mcp 服务
```

四个核心 MCP 工具：

1. **index_codebase** — 扫描并索引整个代码库，BM25 词法检索与稠密向量语义检索混合
2. **search_code** — 通过自然语言查询搜索代码，返回最匹配的代码片段
3. **clear_index** — 清除已建立的索引
4. **get_indexing_status** — 查看索引进度

#### 设计选择与可借鉴之处

**BM25 + Dense Vector 混合检索**

这是 Claude Context MCP 最值得关注的设计。纯向量检索在代码场景有两个硬伤：

- 代码中的标识符（`isAuthenticated`、`checkUserAuth`）彼此语义相似，但功能不同。向量 embedding 可能将它们混为一谈。
- 函数签名、关键词（`virtual`、`override`、`const`）需要精确匹配才能正确理解代码结构。

BM25 解决了精确匹配问题（关键词、标识符、签名），Dense Vector 解决了语义泛化问题（"找负责用户权限检查的部分"）。两者混合后，召回率和精度通常比单一策略更好。

**MCP 协议作为接口规范**

通过 MCP（Model Context Protocol）暴露代码搜索能力，而不是做成一个库或插件，是另一个明智的设计。MCP 正在成为 AI 编码工具的标准协议接口——Claude Code、Cursor、Windsurf、VS Code、JetBrains 都支持 MCP 集成。这意味着同一个代码索引服务可以同时服务于不同的 AI 编码工具，不需要为每个工具单独适配。

**按项目隔离索引**

索引是按项目维度隔离的，而不是所有代码混入一个全局向量库。这在大规模使用场景下非常重要：不同项目有完全不同的命名体系、架构约定、技术栈，混合索引会引入大量噪声。

#### 它的边界与不足

Claude Context MCP 是目前这个方向上最成熟的开源实现，但它有明确的边界——理解这些边界，比直接照搬更有价值。

**缺乏代码依赖关系感知**

Claude Context MCP 本质上是一个"智能搜索"工具，不是"代码理解"工具。当你搜索 `AuthenticateUser()` 时，它能告诉你这个函数定义在哪里、参数是什么、注释写了什么，但它不会告诉你：

- 谁调用了这个函数
- 这个函数依赖哪些外部模块
- 修改它的返回值会影响哪些下游调用

这些信息需要调用链分析或代码图谱——纯向量检索做不到。

**托管服务依赖问题**

Claude Context MCP 默认依赖 Zilliz Cloud（Milvus 的托管版本）。虽然 Milvus 本身可以自建部署，但项目默认的安装路径指向了托管服务。对于企业开发团队来说，代码仓库是企业最核心的资产之一，将代码的向量索引放到第三方云服务上，在数据安全层面几乎是不可接受的。

**索引更新的触发机制不够完善**

代码是会变化的。每天有新的 commit、新的分支、新的重构。索引如何与代码变更保持同步，是向量化上下文方案必须回答的问题。Claude Context MCP 目前依赖手动触发 `index_codebase`，没有自动的增量索引更新机制。这意味着要么人工周期重建，要么在 CI 中增加重建步骤——两者都有摩擦。

**没有跨会话长期记忆**

Claude Context MCP 解决的是"当前会话中 AI 如何快速找到相关代码"的问题。它不解决"AI 如何记住上次会话中讨论过的技术决策"的问题。后一个问题属于长期记忆的范畴，是比代码搜索更复杂的问题。

### 核心理念重构：从文件单元到语义单元

#### 文件单元为什么错了

人类组织知识的方式是"文档"——我们把相关信息写进一个文件，通过目录和标题来组织。这个名字叫"用户登录模块.md"的文件就应该包含登录相关的所有信息，这是符合直觉的。

但 AI 不是这么工作的。大语言模型的注意力机制，让它们更擅长从分散的信息中"发现"关联，而不是从线性结构的信息中"读取"关联。一篇精心组织的长文档对 AI 的阅读效率，远低于分散在不同文件中的、被精确检索到的短片段。

这个差异在编码场景中尤为明显。一个功能可能散落在多个文件中：一个头文件声明接口，一个实现文件包含逻辑，一个配置文件包含开关，一个测试文件包含用例。将它们组织进同一个文档需要大量人为的"重新包装"工作——这就是 Skill 文档困境的根源。

**所谓 Skill 文档困境**：当项目模块职责清晰时，Skill 文档工作得不错。但随着项目演进，模块间产生交叉，职责开始模糊。一个函数可能涉及多个模块的知识，一个 Bug 修复可能横跨三层结构。这时 Skill 文档的组织者面临两难：
- 如果保持模块独立，AI 在处理跨模块问题时需要手动引用多篇 Skill，但 AI 不知道当前问题该引用哪篇
- 如果把相关模块合并为一篇超级 Skill，文档膨胀到数万 Token，放入上下文后注意力稀释

这个两难没有出口，因为它源于一个错误的出发点——**我们在用人类组织信息的方式，试图满足机器的信息需求**。

#### 语义单元是什么

语义单元不是文件，不是文档，也不是文件夹。它是一个概念层面的信息包：一个可被独立索引、独立检索、独立引用的知识片段。在代码场景中，语义单元可以是：

- 一个函数的完整定义（签名 + 注释 + 实现）
- 一个类的公开接口
- 一个模块的目录结构和职责描述
- 一个架构决策记录（ADR）
- 一段配置约定的解释

这些单元之间通过**元数据**建立关联：一个函数属于哪个类，一个类属于哪个模块，一个模块遵循哪些架构约定。元数据可以是显式的（写在索引中），也可以隐式的（通过命名约定或目录结构推断）。

**语义单元的检索与组装**

当 AI 需要回答一个问题时，系统不是把"相关文档"丢给它，而是：

1. 分析问题，提取检索意图（是搜代码？搜规范？搜历史决策？）
2. 根据意图，选择检索策略（语义检索 / 精确匹配 / 调用链查询）
3. 检索到若干相关语义单元
4. 将语义单元组装成当前任务的上下文
5. （可选）将本次检索的"过程和结果"记录到长期记忆中，用于后续优化

这个流程与传统方案的核心区别在于：**上下文是被"计算"出来的，而不是被"挑选"出来的**。

#### 语义单元方案的优势

- **精确性**：检索到的内容直接相关，没有噪声。模型不会在"看看其他文件也许有相关信息"的猜测中消耗注意力。
- **成本可控**：每次请求的 prompt 大小 ≈ 检索结果片段的 Token 和，而不是项目背景全量。
- **抗膨胀**：项目规模越大，语义索引的优势越明显。百万行代码的索引可能占用几百 MB 存储，但单次检索的消耗几乎不变。
- **天然支持增量更新**：只重新索引变更的文件，不需要重建全局索引。

### 工程边界：自建向量数据库的选型考量

语义单元方案依赖一个基础设施：向量数据库。如果选择自建（企业数据安全不可妥协的前提），需要面对几个具体的工程选型问题。

#### 向量数据库选型

代码索引场景对向量数据库的要求不同于通用 RAG 场景：

**查询负载特征不同。** 代码场景的查询特点是高频次、低延迟、小批量。一个开发者在编码时可能每分钟触发多次代码搜索，每次只检索少量结果（通常 5-10 个片段足够）。这与通用 RAG 场景中"用户问一个问题，系统从海量文档中召回 Top-K 段落"的模式不同。代码索引需要的是亚秒级的单次查询响应，因为它是嵌入到开发流程中的——开发者不会等三秒才看到代码搜索结果。

**数据量级可控。** 一个中型项目的代码量在 10-50 万行之间。提取出函数和类级别的语义单元后，索引条目数大约在数千到数万条。这个量级对于 Milvus、Qdrant、Weaviate 等现代向量数据库来说都很轻松，远未达到它们的性能上限。这意味着选型的核心考量不是"谁处理海量数据更快"，而是"谁对自建部署更友好"。

**混合检索是刚需。** 如前所述，纯向量检索在代码场景有硬伤。必须支持向量检索与 BM25（或类似词法检索）的混合查询。Milvus 原生支持 Hybrid Search，Qdrant 通过稀疏向量也可以实现类似能力。选型时这是必须验证的能力，不是"可有可无"的加分项。

**增量索引能力。** 代码每天都在变。全量重建索引在代码量小的时候可以接受（几分钟），但在大型 monorepo 中可能长达数十分钟。支持增量 upsert 和自动过期机制的方案，在运维成本和开发体验上有本质差别。

#### 嵌入模型的选型

向量检索的质量不取决于向量数据库，而是取决于嵌入模型——这是"垃圾进垃圾出"最显著的环节。

在代码场景中，通用文本嵌入模型（如 text-embedding-3-small）通常能给出尚可的结果，但存在一个系统性偏差：它们对自然语言理解好，对代码结构理解差。一个函数体内部的实现细节和它的接口签名，在通用嵌入模型的向量空间中可能距离很远——但代码检索时，开发者常常需要从"功能描述"找到"实现位置"，再找到"调用方式"，这三者的语义跨度远大于自然语言场景。

专门针对代码的嵌入模型（如 voyage-code-3、codebert 的变体）在处理这个问题上更好，但它们也有代价：部分模型需要额外的部署成本，而且开源选项不如通用嵌入模型丰富。

#### 自建部署的成本边界

自建向量数据库意味着需要维护一个额外的基础设施组件。对于小型团队（< 10 人），这个维护成本可能超过收益——不如用本地文件索引 + BM25 做一个简化版，在数据隐私和部署复杂度之间找到平衡点。

简化的替代方案：使用 SQLite + FTS5 做全文搜索，配合简单的命名匹配规则来模拟语义检索。这个方案没有向量化的语义理解能力，但对于标识符命名规范的项目（如"在函数名中使用动词-名词对"的团队），实际效果并不差。当团队成长到需要语义检索时，再迁移到完整的向量数据库方案。

### 多 Agent 协作中的上下文传递

#### "干净的上下文"是一个需要重新审视的假设

在多 Agent 协作场景中，一种常见的做法是：A Agent 理解全貌 → 将任务拆分为独立子任务 → B Agent 收到一个"干净"的子任务 → B 在独立的上下文中执行。

这个做法有一个隐含假设：**拆分任务时，A 已经包含了 B 所需的全部上下文**。

这个假设在简单任务中成立——如果 A 说"去把 utils.js 第 42 行的拼写错误修了"，B 不需要额外的上下文。但在复杂的软件工程任务中，这个假设经常不成立：

- A 分配给 B 的任务是"重构 UserService 的数据访问层"，但 B 不知道公司架构规范要求所有数据库操作必须经过 AuditInterceptor。这个规范对 A 来说过于显然，A 没有意识到需要传递。
- B 在执行任务时需要理解某个设计决策的来源——为什么数据访问要绕一层 DTO 转换而不是直接暴露实体。这个决策记录在 C Agent 的讨论历史中，A 不知道。
- B 修改了 AuthModule 中的一个接口签名。这个修改会影响到 ConsumerModule 中的调用方。但 B 的任务上下文里只有 AuthModule，没有 ConsumerModule。

这些场景说明了同一个问题：**上下文的完备性不能依赖于"上游 Agent 的自觉"**。A 不是故意遗漏信息，而是它根本不知道自己遗漏了什么——它的"显然"对 B 来说是"未知"。

#### 一个分层上下文模型

解决这个问题需要一个分层模型，让上下文不再是一条扁平的消息或一个文档，而是多个层次的组合：

```
第一层：指令层（不可选，每次必带）
  ├── 安全边界（不可修改的内容）
  ├── 身份约束（当前 Agent 的角色）
  └── 输出格式要求
  示例：DocManager 的 AGENTS.md 中关于安全边界和输出风格的部分

第二层：结构背景（可选，按任务类型动态检索）
  ├── 代码语义索引（函数/类/模块的向量化表示）
  ├── 项目规范和架构决策
  ├── 模块间的依赖关系
  └── 存储形式：向量数据库 + 代码图谱，按任务语义检索

第三层：会话记忆（可选，按关联度筛选）
  ├── 历史决策的原因和背景
  ├── 用户偏好修正
  └── 之前讨论中沉淀的关键结论
  存储形式：RAG 检索（带时间衰减权重）

第四层：执行上下文（每次任务独立，用完即弃）
  ├── 当前任务的源码片段
  ├── 临时讨论记录
  └── 中间计算结果
```

这个分层模型的价值在于：**它不假设"全部"或"没有"**。每一层都有独立的检索策略和加载时机。指令层永远跟着 Agent，不依赖检索；结构背景在任务开始时加载；会话记忆只在需要回溯历史决策时才检索；执行上下文在任务完成后清除。

#### 分层模型的落地挑战

分层模型在概念上清晰，落地时有两个核心难题。

**难题一：如何判断"该带哪层"**

不同任务需要不同的上下文组合。一个简单的类型修正任务只需要指令层 + 执行上下文；一个架构级重构任务可能需要全部四层。判断"当前任务属于哪一类"，本身就是一个问题。

一种可行的方案是通过任务的描述文本进行语义分类："修复拼写错误"→ 轻量级，"重构数据访问层"→ 全量级。但这个分类器需要训练或精调，且存在边界分类错误的风险。

另一种更鲁棒的方案是**渐进式加载**：先只带指令层 + 执行上下文，如果 AI 在执行过程中发现自己缺少信息（表现为"我不确定 X 是否 Y"），再触发额外的检索来补充缺失的层。这个方案的优点是不需要预先分类，缺点是增加了交互轮次和延迟。

**难题二：检索策略的动态选择**

代码上下文的检索与知识文档的检索，是完全不同的两件事：

| 维度 | 知识文档检索 | 代码上下文检索 |
|------|------------|--------------|
| 典型问题 | "什么是工厂模式？" | "改这个函数会影响什么？" |
| 有效手段 | 语义检索 | 调用链分析 + 依赖图谱 |
| 匹配粒度 | 段落级 | 函数/类/模块级 |
| 关联维度 | 主题相关度 | 调用关系、继承关系、数据流 |

不同问题需要不同的检索策略。Agent 问"这个函数的用途"→ 语义检索就够了。Agent 问"改了它会影响到哪里"→ 需要依赖图谱，语义检索无效。Agent 问"这个接口的规范是什么"→ 需要精确匹配文档，而不是语义相似搜索。

理想的系统应该能不依赖人工标注，根据问题本身的特征动态选择检索策略或策略组合。这本质上是一个查询路由问题——在大规模代码库中，查询路由的准确度直接决定了上下文质量。

### 长期记忆：一个比代码检索更难的问题

代码检索解决的是"AI 如何快速找到当前需要的代码"的问题。长期记忆解决的是"AI 如何记住上次会话中讨论过的结论"的问题。后者比前者难一个数量级。

#### 长期记忆在 AI 编程中的价值

长期记忆不是代码检索的替代，而是补充。它们覆盖不同的场景：

代码检索回答的是"这个代码是做什么的，在哪里"。
长期记忆回答的是"为什么当初决定这样做，谁决定的，讨论了哪些替代方案"。

前者可以通过静态分析从源码中提取。后者不存在于源码中——它存在于讨论记录、设计评审、架构评审会议中。如果这些信息没有被 AI 记住，AI 在面对"为什么不直接用 ORM 而要手写 SQL"这类问题时，只能基于通用知识回答，无法结合项目特有的决策上下文。

#### 记忆存储的结构选择

长期记忆的存储结构是一个被低估的问题。目前主流的选择有两个方向：

**方向一：知识图谱（如 MCP Memory Server）**
将记忆存储为实体-关系三元组（"UserService → 使用 → DTO 转换"），通过图查询来检索。优点是关系表达能力强，支持多跳推理；缺点是建图和维护的成本高，且对自然语言表述的容错性差（同一个概念的不同表述方式会导致图谱断裂）。

**方向二：向量化记忆（RAG）**
将记忆片段向量化后存入向量库，通过语义检索来获取。优点是实现简单，对自然语言表述的变化不敏感；缺点是缺乏结构化的关系表达能力——"DTO 转换的存在原因是安全审计"这条记忆能够被检索到，但检索到的只是一个文本片段，没有直接的链接指向"安全审计的具体实现是什么"。

代码索引和长期记忆是否应该共用同一套向量数据库？从运维角度看，共用更省事。但从职责分离的角度看，两者有不同的检索模式（代码检索的高频、低延迟 vs 记忆检索的低频、高召回要求），混合存储可能导致互相干扰。更干净的设计是独立存储，但通过一个统一的查询接口来屏蔽底层差异。

#### 记忆的衰减与遗忘

人类记忆不是等权的。上周的决定比去年的决定更常被引用。

长期记忆系统需要引入时间衰减机制：新写入的记忆具有较高的检索权重，随着时间推移权重逐渐降低。但衰减不能是简单的时间线性衰减——一个被频繁引用的记忆（"项目的目录结构是这样划分的"）即使很久没有被重新写入，也应该保持高权重。这需要结合引用频率和时间两个维度来计算权重。

更棘手的问题是：什么记忆应该被遗忘？不设遗忘机制的长期记忆系统，最终会积累大量噪音——每天讨论中的"嗯""好的""这里不太对"这样的对话片段，如果都被持久化为记忆，检索时会产生大量低质量干扰。主动遗忘——或者说不将所有对话都持久化为记忆——是长期记忆系统必须做的一个设计选择。只有明确标记为"值得记录"的信息才进入长期记忆，或者通过一个事后筛选机制（"这条讨论似乎涉及架构决策，值得持久化"）来减少噪音。

#### 短期记忆与长期记忆的衔接

在 AI 编程场景中，短期记忆（当前会话中的讨论上下文）和长期记忆（跨会话持久化）之间的衔接是一个容易断裂的环节。

当前会话中讨论的技术决策，应该在什么时机转入长期记忆？这个时机决定了记忆的完整性。如果只在会话结束时一次性转储，可能会遗漏中途的细微决策；如果在每次交互后都尝试提取记忆，则会有大量噪音（大部分交互不产生值得记住的信息）。

一种折中方案是：每次 AI 的回复中，如果涉及"结论性"的表述（如"因此决定采用方案 A"、"这里的选择是出于 X 原因的考虑"），由 AI 自身标记为"值得记录"。这依赖于 AI 的自我判断能力，并非 100% 可靠，但比定时全量转储和每轮全量提取都要合理。

### 总结

#### 技术判断

AI 编程的上下文管理正在经历一次从"文件思维"到"索引思维"的范式转换。这不是一个渐进式改进，而是一个结构性变化：

- **旧的假设**：让 AI 能用的上下文，需要从项目文件中选择或整理后喂给它
- **新的假设**：让 AI 能用的上下文，应该从索引中自动检索并组装

Claude Context MCP 是这条路上的一个重要参考实现，但远非终点。它的混合检索策略值得借鉴，它的托管服务依赖需要警惕，它的增量索引和长期记忆缺失是需要补上的能力。

#### 实践建议

对于正在将 AI 深度嵌入开发工作流的团队，以下几条建议值得考虑：

1. **不要用"给人看"的文档来满足 AI 的信息需求**。如果正在写一份长到需要滚动很久的 Skill 文档，这说明需要换一套方案。
2. **向量化代码索引是值得投入的方向**，但不要只做向量。BM25 + 向量 + 代码图谱的混合方案，效果远好于任意单一策略。
3. **多 Agent 场景下，主动思考"哪些上下文被遗漏了"比"哪些上下文给对了"更重要**。A Agent 的"显然"往往是 B Agent 的"缺失"。
4. **企业级场景下数据安全不可妥协**。代码向量索引必须自建部署，不能依赖第三方托管服务。
5. **索引的增量更新和长期记忆的跨会话持久化，是方案是否可用的分水岭**。不能自动同步变更的索引和不能记住昨天的讨论的 Agent，本质上是玩具。
6. **增量索引至少有两种实现路径：**
   - **Git Hook 方案**：在 post-commit 或 post-merge 时触发变更文件重新索引。优点是与现有 Git 工作流无缝集成，Agent 不需要感知索引的存在。缺点是只跟踪 Git 操作，本地实验性改动不会被索引。
   - **文件系统 Watchdog 方案**：利用 inotify 或 ReadDirectoryChangesW 监听源码目录，文件保存即触发重新索引。优点是实时性强，实验改动也被覆盖。缺点是系统资源开销更大，且容易误触发生成文件（如 UE UHT 输出的 .generated.h）。
   - 实践中通常是两者混合：Git Hook 做准实时基准同步，Watchdog 做本地开发的即时反馈。变更统一进入异步处理队列，避免频繁触发全量重建。
7. **小型团队不必一上来就上向量数据库**。SQLite + FTS5 全文搜索配合命名规范匹配规则，对于标识符命名规范的项目来说效果够用。等到团队成长到需要语义理解能力时再迁移，远比一开始就维护 Milvus 集群务实。

#### 开放问题

以下几个问题仍然没有理想答案，值得持续关注和实践探索：

- 代码调用链分析应该嵌入索引（预计算），还是应该在检索时实时计算？两者的成本权衡在哪里？
- 不同任务需要不同层级的上下文，如何自动判断"当前任务要带多少信息"？
- 长期记忆的存储和检索，是否应该和代码索引共用同一套向量数据库，还是分别独立？如果独立，同步机制该如何设计？

这些问题没有标准答案。但可以肯定的方向是：以语义单元替代文件单元、以向量检索替代全量加载、以分层上下文替代单一大 Context——这个方向在逻辑上是自洽的，在工程上是可行的。
