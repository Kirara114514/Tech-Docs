# AI编程中的上下文管理与记忆系统

## 摘要

AI 编程进入工程化阶段后，如何让 AI 有效理解大型项目的结构与规范，成为制约生产力的核心瓶颈。现有做法——将完整项目文档或长篇 skill 文件整体丢入模型上下文——在项目规模较小时勉强可用，但一旦项目膨胀、模块增多、协作周期拉长，这种方式很快暴露出上下文窗口短缺、注意力稀释、Token 成本失控、跨会话记忆断裂等一系列问题。

本文讨论的核心命题是：权威知识源、检索索引和运行时上下文组装应该解耦为三个独立层次。权威知识源（文档、代码、测试、配置）定义事实与约束；检索索引（BM25、向量、符号、AST、repo map、依赖图谱）负责高效发现相关证据；上下文组装将检索结果组合为当前任务的即时信息包。这三层各自独立演进，为不同消费者派生定制视图——人类读者浏览完整文档，AI 获取按需检索的精确片段。向量检索是工具箱中的一种工具，不是范式替代者。

本文不提供具体实现代码，而是讨论架构层面的价值判断：哪些信息组织形式匹配 AI 的检索模式、哪些路径在工业级场景下不可妥协、多 Agent 协作中上下文传递的风险维度，以及长期记忆系统的工程化难题。

## 正文

### 背景

#### 问题的起点：AI 编程的上下文瓶颈

AI 编码助手——Claude Code、Cursor、Aider、Codex CLI 等——正在改变软件开发的日常流程。开发者从亲自写代码，逐渐转变为"描述需求 → AI 生成代码 → 审阅修改"。但这个工作流的效率，极度依赖一个前提：**AI 必须准确理解项目上下文**。

这里的"上下文"至少包括以下几层：

- 项目的整体架构：模块划分、层次关系、依赖方向
- 编码规范与约定：命名规则、错误处理方式、代码风格
- 已有代码的具体实现：函数签名、类结构、接口定义
- 正在进行或计划中的变更：当前分支的目标、尚未合并的改动
- 历史技术决策：为什么选择方案 A 而非 B、当时讨论了哪些替代方案

当项目规模在几千行代码以内时，直接将项目文件放入模型上下文通常足够。但现实中的工业项目不是这个量级。一个中等规模的游戏客户端项目，源码量轻松达到数十万甚至上百万行。即使使用百万 Token 上下文的模型，也无法完整覆盖。

更致命的是，**上下文越满，模型的表现越不可靠**。在"大海捞针"测试中，长上下文模型的检索精度会随上下文长度增加而显著下降。对于编程这类需要精确引用接口签名、参数顺序、依赖关系的任务，注意力稀释直接导致代码质量下降。

#### Token 成本的现实约束

除了技术层面的上下文短缺，经济层面同样存在硬约束。

每个向大模型发起的请求，Token 消耗取决于 prompt 长度。如果每次编码请求都要附带数万 Token 的项目背景，成本会迅速失控。对于个人开发者或小团队，这部分成本可能尚可接受；但对于将 AI 编码嵌入到 CI/CD 流水线中的企业团队，Token 消耗会成为一笔不可忽视的账单。

更隐蔽的问题是：**成本不是线性的**。AI 编程的工作流是"尝试 → 反馈 → 修正"的循环。每次尝试的 prompt 都包含项目上下文 + 具体问题，每次修正的 prompt 又包含更多上下文 + 历史反馈。如果上下文没有有效的缓存或分层机制，实际 Token 消耗会远超直觉估算。

#### 现有方案的局限

当前开发者应对上下文瓶颈的方式主要有以下几种，各有缺陷：

**方式一：手动裁剪上下文**

开发者自行判断哪些文件与当前任务相关，手动粘贴到 prompt 中。这种方式在小任务中可行，但高度依赖人的判断力，且容易遗漏关键信息——开发者往往在"这个文件肯定相关"和"这个文件应该不用"之间犯错。

**方式二：制作 Skill / 项目背景文档**

将项目的架构说明、规范约定、核心模块导读整理成一份 Markdown 文档（如 Claude Code 的 CLAUDE.md、自定义的 SKILL.md），作为 AI 的固定背景知识。这是目前最普遍的做法。

这类文档有一个结构性矛盾：当项目规模变大后，文档本身也会膨胀。一篇覆盖整个项目的背景文档可能达到数千甚至上万 Token，放入 prompt 后既消耗预算又稀释注意力。如果拆成多个文档（每个模块一个），则面临"AI 不知道当前任务应该读哪个文档"的问题——开发者需要额外判断并指定，回到了方式一的老路。

**方式三：全量代码喂入**

将整个代码库（或核心部分）塞入模型上下文。这种方式仅在项目极小时有效。一旦项目膨胀，不仅是 Token 成本问题——模型本身的长上下文推理能力也会到达极限。

**方式四：零上下文纯聊天**

不给 AI 任何项目背景，直接提问。这种方式的输出质量完全取决于问题的具体程度和模型的通用知识。对于框架级别的问题（"如何用 UE5 的 Gameplay Ability System"）尚且可用，但对于项目特有的逻辑（"为什么 UserService 要绕一层 AuditInterceptor"）则毫无办法。

### 核心理念：三层解耦模型

上述四种方式共同面对一个结构性问题：它们未能在"知识存储""知识发现"和"知识交付"之间建立清晰的边界。一篇项目背景文档同时承担了这三重职责——它既存储了架构知识，又充当了检索入口（开发者通过目录和标题定位信息），还直接以全文形式交付给 AI。当这三个职责耦合在同一个文件中时，任何一个职责的变化都会迫使其他职责随之调整。

一个更合理的架构是将它们解耦为三个独立层次：

| 层次 | 作用 | 典型形式 |
|---|---|---|
| 权威知识源 | 定义事实与约束 | 代码、文档、测试、配置、ADR、数据库 schema |
| 检索索引 | 帮助发现相关证据 | BM25、向量索引、符号索引（LSP）、AST 解析、依赖图谱、repo map |
| 上下文组装 | 为当前任务交付信息 | 原文片段、摘要、带来源标注的引用、结构化状态快照 |

**权威知识源**是唯一的真相来源。一条架构约束（"所有数据库操作必须经过 AuditInterceptor"）只存在于一处——可能是一篇架构决策记录（ADR），也可能是一个 lint 规则。无论以什么形式呈现给 AI，权威知识源本身是稳定的。

**检索索引**不替代权威知识源，而是为它提供多通道的发现能力。同一个权威知识源可以派生多种索引：文档段落做向量嵌入用于语义搜索；函数签名做符号索引用于精确跳转；模块依赖做图谱索引用于影响分析。不同索引服务于不同的问题类型，不存在"一种索引取代所有"的情况。

**上下文组装**是运行时环节——根据当前任务的特征，从不同的索引通道拉取相关证据，组合成一次性的上下文包。这个过程是计算性的：不是"挑一篇文档丢过去"，而是"根据问题类型选择合适的检索策略，跨多个权威来源组装答案"。

这个三层模型的核心理念是：**人类文档和 AI 上下文不必是两套相互替代的知识体系。共享权威来源，为不同消费者派生索引和视图。** 同一个人，浏览文档时需要完整的章节结构和前后文语境；同一个 AI，解决具体问题时需要精确命中相关片段。它们从同一个权威知识源出发，走不同的检索路径，到达各自需要的信息形态。

#### 三层解耦的实际收益

**知识源独立维护。** 当代码变更时，只需更新对应的权威知识源（代码本身、相关文档、测试），不用去改一堆专门为 AI 准备的上下文文件。反之亦然——当 AI 的上下文组装策略优化时，不需要修改权威知识源的结构。

**检索策略可按问题类型选择。** "这个函数的签名是什么"→ 符号索引（LSP）秒级精确命中。"有哪些地方调用了这个函数"→ 依赖图谱或 grep 搜索调用点。"为什么当初选择方案 A 而非方案 B"→ 对 ADR 文档做语义检索。不同问题走不同通道，不是"一个向量索引包打天下"。

**上下文组装可按任务预算动态调整。** 简单拼写修正任务 → 只带被修改文件 + 相关符号定义。架构级重构任务 → 全模块依赖图谱 + 相关 ADR + 编码规范。同一个权威知识源，在不同任务中组装出不同大小的上下文包。

**抗膨胀。** 项目规模越大，三层解耦的优势越明显。百万行代码的索引可能占用几百 MB 存储，但单次检索的消耗几乎不变——检索时间与索引大小呈亚线性关系。

### 多通道检索：当前主流方案的实际工具箱

理念层面的三层解耦描述了"应该是什么"。在工程实践中，当前主流的 AI 编码助手已经各自走出了一套多通道检索的路径——没有任何一个主流工具只依赖向量检索。

#### 通道一：Grep / 精确文本搜索

**代表方案：Claude Code（默认）。**

Claude Code 默认使用 grep 进行代码搜索。Anthropic 团队对此的立场是——在某些场景下，精确的文本匹配比语义检索更可靠。搜索一个函数名、一个类名、一个特定的字符串常量，grep 不会漏掉任何出现，也不会因为"语义相近"而返回大量噪声。

Grep 的优势在于确定性和速度。对于"找到所有调用 `AuthenticateUser()` 的地方"这类问题，grep 给出的是精确的、可验证的答案。它的劣势也明确：无法处理自然语言描述的查询（"找到处理用户权限检查的代码"），对重构后的重命名没有弹性。

#### 通道二：Repo Map / 图排序

**代表方案：Aider。**

Aider 的 repo map 是一种独特的方案：它构建整个仓库的符号关系图（文件为节点，依赖关系为边），使用类似 PageRank 的图排序算法，选出与当前任务最相关的符号和文件，将它们以紧凑格式（函数签名 + 关键定义行）发送给模型。

这个方案的精妙之处在于，它不是"检索"，而是"排序后裁剪"——Aider 不是等模型提问后再去搜索，而是在每次交互前主动提供一个"代码库的浓缩地图"，让模型在开始推理时就已经知道相关的文件结构和符号分布。Aider 每天处理约 150 亿 Token 的代码交互，这个方案在大规模使用中已被验证稳定。

Repo map 适合"模型需要知道代码库整体有哪些东西"的场景。它的局限在于：图排序基于静态依赖分析，不考虑语义相似性——两个功能相似但无直接依赖的模块不会被图排序拉近。

#### 通道三：符号索引 / LSP

**代表方案：Cursor、多数 IDE 内建 AI 功能。**

LSP（Language Server Protocol）提供的是语言层面的结构化信息：跳转到定义、查找引用、查看类型层次、获取文档注释。对于"这个函数的参数类型是什么""这个接口有哪些实现类"这类问题，LSP 是最精确且最快速的通道。

Cursor 将 LSP 符号索引与向量语义搜索结合使用——前者处理精确的结构查询，后者处理模糊的语义查询。两者各有各的命中范围，不存在替代关系。

#### 通道四：向量语义检索

**代表方案：Cursor（通过 Turbopuffer）、Claude Context MCP（通过 Milvus）、各种代码 RAG 方案。**

向量检索的核心能力是处理自然语言描述到代码片段的映射——"找到处理用户会话超时的逻辑""搜索错误重试策略的实现"。这类查询无法用 grep 或 LSP 直接处理。

在代码场景中，纯向量检索有两个固有缺陷：一是标识符层面的精确匹配（`isAuthenticated` 和 `checkUserAuth` 语义相近但功能不同，向量可能混淆）；二是函数签名、关键词（`virtual`、`override`）的精确匹配需求。因此实际部署中，向量检索通常与 BM25 或精确文本匹配组合使用（混合检索），让词法匹配和语义匹配各自覆盖自己的优势区间。

**独立评测对比。** 2026 年 5 月的一项独立评测[^1]显示，在 Claude Code 上使用语义索引方案（grepai），输入 Token 消耗减少了 97%；CodeGraph 在独立评测中减少了 58–70% 的工具调用次数。但这不意味着"向量检索替代 grep"——它只是在 grep 作为默认通道之外增加了一个新的检索通道。实际生产环境的最佳实践是组合使用。

#### 通道五：依赖图谱 / 调用链分析

**代表方案：各 IDE 的代码智能功能、CodeGraph。**

"修改这个函数会影响哪些下游调用方"——这类问题既不能靠 grep（需要跟踪多层间接调用），也不能靠向量检索（语义相似不等于有调用关系），也不能单靠 repo map（静态依赖图通常只到文件级，不到函数级）。调用链分析需要构建完整的函数级调用图谱，支持正向追踪（谁调用了它）和反向追踪（它调用了谁）。

这是目前成本最高的索引类型——大型 monorepo 的函数级调用图谱构建和增量更新都是工程难题。但它覆盖了其他通道无法回答的问题类型。

#### 现实是多通道的组合

| 问题类型 | 最适合的通道 | 示例 |
|---|---|---|
| "找到函数 X 的定义" | 符号索引（LSP） | "UserService.Authenticate 的参数有哪些" |
| "哪里调用了 X" | Grep / 调用链分析 | "哪些地方调用了 AuditInterceptor" |
| "这个项目有哪些模块" | Repo Map | "帮我理解项目的整体结构" |
| "找处理权限的代码" | 向量语义检索 | "找到处理用户权限检查的部分" |
| "改 X 会影响什么" | 依赖图谱 | "修改 AuthModule 接口会影响哪些模块" |
| "为什么当初这样设计" | 语义检索 ADR | "为什么不直接用 ORM" |

理想状态下，AI 编码助手应该根据问题类型自动路由到合适的检索通道或通道组合。这本质上是一个查询路由问题——查询路由的准确度直接决定了上下文质量。目前，多数工具的做法是为每种通道暴露一个独立的 MCP tool 或内部 API，由 AI 自己决定调用哪个——AI 在"选择合适的工具"这件事上的判断力，是当前架构中的一个隐性瓶颈。

### 工程考量：向量数据库的部署评估

多层索引架构依赖一个基础设施选择：向量数据库的部署模式。代码向量索引的存储和检索需要一个向量数据库。选型时需要评估多个维度的风险与收益，不存在"一律自建"或"一律托管"的通用答案。

#### 部署模式的风险评估表

| 评估维度 | 自建部署（Milvus / Qdrant / pgvector） | 云托管（Pinecone / Zilliz Cloud / 各云厂商） |
|---|---|---|
| 数据驻留与合规 | 数据完全在自有基础设施内，满足严格的数据主权要求（GDPR、HIPAA 等） | 需审查 DPA、静态加密、私网链路、SOC2/ISO 认证；部分监管框架下不可用 |
| 运维负担 | 需要专人维护：部署、升级、备份、监控、扩缩容 | 零运维，由服务商负责 |
| 成本结构 | 固定基础设施成本（服务器/实例），规模大时单位成本低 | 按用量计费，规模大时成本可能显著高于自建（自建约 $500-1000/月 vs 托管可达 $3500+/月，50M 向量规模量级） |
| 性能调优 | 完全可控：索引参数、硬件选型、查询优化 | 受限于服务商提供的配置选项 |
| 故障响应 | 依赖内部 on-call 能力 | 依赖服务商 SLA（通常 99.9%–99.95%） |
| 混合索引能力 | 需自行整合 BM25 + 向量 + 图谱等多通道 | 部分服务商提供原生混合搜索（如 Milvus Hybrid Search） |

**决策框架：** 部署模式的选择不是技术优劣问题，而是组织能力、合规约束和规模预期的函数。

- **金融、医疗等强监管行业**，或处理受数据主权法律管辖的代码时，自建部署在合规层面几乎不可绕过。
- **10 人以下小型团队且不涉及敏感代码**，托管方案可以让团队聚焦业务而非基础设施。甚至可以考虑更轻量的替代方案——SQLite + FTS5 全文搜索配合命名规范匹配，对于标识符命名规范的项目来说，效果够用。等到团队成长到需要语义理解能力时再迁移。
- **中型以上团队**，许多采用混合策略：核心代码索引自建部署，非敏感的文档索引使用托管服务。

**简化替代方案（小型团队）：** 在团队规模有限时，SQLite + FTS5 全文搜索配合命名规范匹配规则，可以模拟语义检索的大部分日常需求。这个方案没有向量化的语义理解能力，但零运维——它不需要额外的基础设施组件。当团队成长到需要语义检索时，再迁移到完整的向量数据库方案。

### 多 Agent 协作中的上下文传递

#### "干净的上下文"需要重新审视

在多 Agent 协作场景中，一种常见的做法是：A Agent 理解全局 → 将任务拆分为独立子任务 → B Agent 收到一个"干净"的子任务 → B 在独立的上下文中执行。

这个做法隐含一个假设：**拆分任务时，A 已经包含了 B 所需的全部上下文**。

这个假设在简单任务中成立——如果 A 说"去把 utils.js 第 42 行的拼写错误修了"，B 不需要额外的上下文。但在复杂的软件工程任务中，这个假设经常不成立：

- A 分配给 B 的任务是"重构 UserService 的数据访问层"，但 B 不知道架构规范要求所有数据库操作必须经过 AuditInterceptor。这个规范对 A 来说过于显然，A 没有意识到需要传递。
- B 在执行任务时需要理解某个设计决策的来源——为什么数据访问要绕一层 DTO 转换而不是直接暴露实体。这个决策记录在 C Agent 的讨论历史中，A 不知道。
- B 修改了 AuthModule 中的一个接口签名。这个修改会影响到 ConsumerModule 中的调用方。但 B 的任务上下文里只有 AuthModule，没有 ConsumerModule。

这些场景说明了同一个问题：**上下文的完备性不能依赖于"上游 Agent 的自觉"**。A 不是故意遗漏信息，而是它根本不知道自己遗漏了什么——它的"显然"对 B 来说是"未知"。

#### 上下文质量的多维风险

影响上下文质量的不是单一维度，而是多个独立因素的组合：

- **相关性。** 上下文中的信息与当前任务的匹配程度。
- **时效性。** 上下文反映的是当前代码状态还是过时的状态。
- **冲突。** 上下文中是否存在矛盾的指令或信息（新旧规范并存、不同来源的冲突声明）。
- **状态一致性。** B 的上下文中描述的系统状态，是否与实际运行环境一致。
- **来源可信度。** 上下文中的每条信息从哪里来、是否可追溯、是否被篡改。
- **证据可恢复性。** 当上下文压缩或摘要后，关键细节是否仍然可以回溯到原始来源。

"干净的上下文"在实践中不是指"上下文更短"，而是指这几个维度上风险可控。一个 200 条消息但每条都高度相关且无冲突的上下文，比一个 20 条消息但包含过时信息和矛盾指令的上下文更"干净"。

#### 上下文隔离策略矩阵

不同任务需要不同级别的上下文隔离：

| 隔离级别 | 适用场景 | 做法 | 代价 |
|---|---|---|---|
| 无隔离 | 简单续写、单文件小改 | 在当前会话中直接执行 | 上下文持续累积 |
| 轻量隔离 | 中等复杂度独立任务 | 新会话 + 最小结构背景（任务描述 + 相关符号索引） | 丢失完整历史讨论上下文 |
| 深度隔离 | 架构级重构、跨模块变更 | 新会话 + 全量结构化背景（依赖图谱 + ADR + 规范 + 相关测试） | 上下文构建成本高，交互轮次增加 |
| 渐进式隔离 | 不确定复杂度的探索性任务 | 先轻量隔离，AI 在执行中发现自己缺少信息时触发额外检索补充 | 增加交互轮次和延迟 |

没有一种策略在所有场景下最优。隔离级别的选择取决于任务的可分解性、子任务的信息耦合度、验证成本与协调开销。

### 长期记忆：工程化难点

代码索引解决的是"AI 如何快速找到当前需要的代码"的问题。长期记忆解决的是"AI 如何记住上次会话中讨论过的结论"的问题。后者比前者难一个数量级——代码是结构化的、可静态分析的；记忆是模糊的、上下文的、需要判断"什么值得记住"的。

#### 记忆存储的核心工程维度

一个可落地的长期记忆系统至少需要覆盖以下维度，每个维度都有未完全解决的设计难题：

**写入策略：什么值得记住。**

每轮对话都存入长期记忆 → 大量噪声（日常寒暄、中途被否定的方案、临时性的探索代码）污染索引，检索质量随之下降。只存储"结论性"的表述 → 依赖 AI 的自我判断能力，不可靠。一种更合理的方向是让记忆系统通过反馈信号学习写入策略——SelfMem 的思路是：在优化迭代中，向模型提供记忆策略和聚合训练反馈，由模型自己修订"写什么、忽略什么、何时合并、何时替换"的程序性规则。这种自优化写入策略将"什么值得记"从人类预设变成了系统可学习的参数。

**检索策略：如何找到该记的。**

代码索引的检索是高频、低延迟、小批量（开发者在编码时可能每分钟触发多次搜索）。记忆检索是低频、高召回需求（偶尔需要回溯历史决策时，希望找到所有相关信息）。两者不适合简单地共用同一套检索参数。Memex(RL) 的思路是：在摘要中保留稳定索引，必要时回取完整原始证据——用索引代替全量存储，用回取代替全量投喂。

**衰减与遗忘。**

人类的记忆不是等权的——上周的决定比去年的决定更常被引用。时间衰减机制是必需的，但不能是简单的时间线性衰减：一个被频繁引用的记忆（"项目目录结构是这样划分的"）即使很久没有重新写入，也应该保持高权重。需要结合引用频率和时间两个维度来计算权重。

遗忘同样重要。不设遗忘机制的长期记忆系统最终会积累大量过时信息——代码已经被重构，旧的设计决策不再适用，但旧记忆仍占据检索空间。墓碑标记（tombstone——标记已废弃的记忆而非直接删除，保留审计轨迹）、TTL（过期自动降权或删除）和定期审查机制是三种互补的遗忘策略。

**出处（Provenance）与污染治理。**

每条记忆必须携带来源信息：谁记录、何时记录、基于什么上下文记录。当一条记忆被检索到时，使用者需要知道它的可信度——是经过多方验证的架构决策，还是某次讨论中随口提到的想法。

记忆污染是一个伴随长期记忆必然出现的问题：如果 AI 依据自己的输出生成记忆、再依据这些记忆生成新的输出，错误会循环放大。防护机制包括：来源标注（区分"用户明确确认的""AI 推断的""从代码静态分析提取的"）、污染检测（检索到的记忆是否与当前权威知识源矛盾）、定期审计。

**访问控制与分支管理。**

不同 Agent、不同团队成员、不同项目分支，应该看到不同的记忆子集。一个实验分支上的架构讨论，不应该污染主分支的长期记忆。ACL 过滤（按用户/Agent/角色控制可见性）和分支隔离（每个 Git 分支对应独立的记忆命名空间）是记忆系统从单用户走向多用户协作时必须解决的问题。

#### 短期记忆与长期记忆的衔接

当前会话中讨论的技术决策，在什么时机转入长期记忆？这个时机决定了记忆的完整性。

如果只在会话结束时一次性转储，可能会遗漏中途的细微决策；如果在每次交互后都尝试提取记忆，则会有大量噪音。一种折中方案：每次 AI 的回复中，如果涉及"结论性"的表述（如"因此决定采用方案 A""这里的选择是出于 X 原因的考虑"），由 AI 自身标记为"值得记录"。这依赖于 AI 的自我判断能力，并非 100% 可靠，但比定时全量转储和每轮全量提取都要合理。

### 总结

#### 技术判断

AI 编程的上下文管理不是单一工具的选型问题，而是一个架构分层问题。核心思路可以概括为三条：

1. **权威知识源、检索索引和上下文组装应解耦为三个独立层次。** 共享权威来源，为不同消费者（人类读者、不同类型的问题查询）派生不同的索引和视图。不专门为 AI 维护一套独立的知识体系。
2. **多通道检索优于一切单一策略。** 向量语义检索只是工具箱中的一种工具，与 grep、符号索引（LSP）、repo map、依赖图谱等通道互补。不存在一个通道可以替代其他所有通道。当前主流编码助手（Claude Code 用 grep + CLAUDE.md，Aider 用 repo map，Cursor 组合 LSP + 向量）已经在各自的实践中验证了这一点。
3. **长期记忆的核心挑战不在存储，在治理。** 写入策略、检索策略、衰减遗忘、出处溯源、污染防护、访问控制和分支管理——这些问题没有标准答案，但它们是决定记忆系统是否可用的关键维度。

#### 实践建议

对于正在将 AI 深度嵌入开发工作流的团队：

1. **先盘点已有的权威知识源。** 代码、文档、测试、ADR、配置文件——这些已经存在的信息，不需要为 AI 重新复制一份。需要增加的是索引层，而不是知识源。
2. **根据团队规模和问题类型选择检索通道组合。** 小型团队可以从 grep + 简单的全文搜索开始；规模扩大后逐步加入符号索引、repo map、向量语义检索、依赖图谱。
3. **向量数据库的部署模式是一个风险评估决策，不是技术禁令。** 评估的维度应包括数据主权要求、合规约束、团队运维能力和成本预期。
4. **多 Agent 场景下，把"哪些上下文可能被遗漏"作为主动思考项。** 上游 Agent 的"显然"往往是下游 Agent 的"缺失"。上下文的完备性不能依赖传递者的自觉。
5. **长期记忆系统从第一天就需要治理设计。** 版本、分支隔离、TTL、出处和 ACL 是基础能力，不是"等以后需要了再加"的可选功能。
