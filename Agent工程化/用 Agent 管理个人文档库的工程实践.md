# 用 Agent 管理个人文档库的工程实践

## 摘要

本文分享一套真实运行中的、由 Agent 全流程管理的个人文档库系统。整套系统围绕"入口判断 → 日常记录 → 讨论 → 独立审阅 → 归档 → 自维护"六环节流水线运转，配套三档公开性分层、暂存保真、纯净上下文写作、十六条质量门控、执行与维护分离等机制。文章按内容生命周期逐环节讲清楚"做什么、为什么这么设计、哪些细节是被事故倒逼出来的"，并在最后诚实地讨论当前瓶颈与未来方向。写作目的是分享而非论证——作者公开邀请读者就任何环节联系他讨论或提出建议。

## 正文

### 背景

#### 为什么写这篇文章

先交代写作目的，免得读者误判。这篇文章不是要论证"用 Agent 管理文档库比人工管理更好"——那是一个很难严谨证明的命题，也不是作者想讨论的重点。这篇文章的目的是单纯的**分享**：作者在过去一段时间里，用 Agent 搭建并运行了一套个人文档库管理系统，包括三座按公开性分层的文档仓库、一条从想法捕获到正式文档归档的内容流水线，以及一套让流水线自身持续进化的自维护机制。系统已经真实运行了一段时间，经历了多次事故与迭代，作者认为这套系统的设计决策、运行经验和踩过的坑，对同样对"Agent 与个人知识管理结合"感兴趣的人可能有参考价值。

因此，这篇文章是一份**公开的邀请讨论帖**。读者如果对其中任何一个环节有疑问、有不同做法、或者发现了作者没有考虑到的漏洞，都欢迎联系作者讨论。作者明确表示：他分享的是一套"真实运行中的系统"，不是一套"理想化的方案"——它有很多妥协、很多被事故倒逼出来的补丁、很多作者自己也知道还不够好的地方。这些妥协和补丁恰恰是本文最有信息量的部分，因为它们是真实运行的证据，而不是纸面设计的推演。

为了忠实，作者会尽量把流程讲细：每个环节做了什么、为什么这么设计、遇到过什么事故、事故如何改变了设计。有些细节在"讲道理"的文章里会被省略，但在这里不会——因为正是这些细节决定了系统能不能真实运转。

#### 系统环境：这套系统在什么条件下运转

任何工程实践都有它的适用边界。在讲系统本身之前，先交代这套系统运转的**前置条件**，读者才能判断哪些设计可以借鉴、哪些设计在自己环境下需要调整。

这套系统的运行环境可以概括为三点：

- **单人使用 + 多 Agent 协作。** 系统的使用者只有作者一个人，但参与系统运转的自动化组件（下文统称 Agent）不止一个。它们分工不同：有的负责日常记录与讨论管理，有的负责归档前的独立审阅，有的在文档写作时作为独立执笔者被临时唤起。这是一个"一个人 + 一群自动化助手"的协作结构，不是多人团队协作。这一点很重要：系统里很多设计（比如宁可牺牲一点效率也要保证过程可追溯）是单人场景下的理性选择，放到多人团队里可能就不成立。
- **三座独立的文档仓库，按公开性分层。** 作者的内容并不都放在同一个地方，而是分成三座相互独立的仓库，公开性从高到低排列。具体分层方式在下一章"入口判断"里详细讲。这里先记住结论：**公开性分层是整个系统的地基**，几乎所有的后续机制（脱敏、审阅、归档）都是围绕"内容该以什么公开程度存在"展开的。
- **Linux 环境 + 命令行工作流。** 系统运行在 Linux 服务器上，文件操作以命令行和版本控制命令为主。编码处理、文件读写、版本管理都遵循严格的纪律（后面会讲到）。这套系统不是图形界面工具，它更接近一套"可编程的文档处理管线"。

这三个前置条件决定了系统的气质：它是一套**给工程师用的、可迭代的、可观测的系统**，而不是一套"开箱即用"的软件。作者会在最后"当前局限与未来方向"一节里诚实地讨论这套系统在多用户、多平台等场景下的不适配。

#### 术语约定：先认识几个词

为了保证零上下文可读，本文中首次出现的核心概念都会给出解释。这里先把最常用的几个术语集中定义一次，后面用到时不再重复解释：

- **Agent：** 泛指系统内的自动化组件。作者使用 Agent 框架承载多个分工不同的自动化助手（有的在读者看来更像"流程组件"而非"智能体"，但为了表述统一，本文统称 Agent）。具体的技术框架名与本文论点无关，一律不出现。
- **文档库：** 存放文档的仓库，分为公开、半公开、私有三档。每个文档库内部有固定的目录结构，包括日常记录目录、正式文档分类目录、历史记录目录和模板目录。
- **日常记录：** 想法的第一落点。当用户（作者）说"记录一下"时，系统创建的一个轻量文件，作用是快速捕获想法、防止想法在对话中蒸发。
- **暂存文件：** 讨论过程中保存"每一轮对话原文"的单一文件。它是整个讨论体系的心脏，也是归档时正式文档的唯一原料。
- **入口判断：** 任何内容进入系统后的第一步处理——判断它属于哪座文档库、哪个分类。这一步不产生文件，只输出判断结论。
- **正式文档：** 经过完整归档流程、达到公开质量标准、进入分类目录的文档。日常记录是"原料态"，正式文档是"资产态"。
- **历史记录：** 归档动作本身留下的可追溯记录，承载"某个话题已在何时归档为哪篇正式文档"的痕迹。
- **归档：** 把讨论内容从"过程态"转变为"资产态"的完整流程，本文中指一条六步流程，缺一不可。
- **心跳（Heartbeat）：** 由定时任务驱动的周期性检查机制。本文指自维护系统中的三层周期性巡检/维护/治理。
- **有界修改（有界 patch）：** 对系统规则（Agent 的操作协议、提示词配置）的一种受控修改方式，每次修改有明确的规模上限（涉及的文件数、章节数、行数），防止修改失控。
- **操作协议（skill）：** Agent 执行特定任务的结构化操作说明，包含入口说明、执行步骤、参考文档、质量检查清单等。可以理解为"Agent 的岗位手册"。文中提到具体协议时用功能描述称呼（如"入口判断协议""记录创建协议"），不出现内部协议名。

这些术语定义好后，下面的叙述就不再反复解释。

### 核心内容

#### 1. 入口判断：这条内容属于哪里？

任何内容进入系统——无论是作者随口说的一句"记一下这个想法"，还是想展开讨论的一个话题——系统做的第一件事都不是"写文件"，而是判断：**这条内容属于哪里？**

这套系统的内容存放遵循"三档公开性"分层，对应三座相互独立的文档仓库：

| 档位 | 定位 | 展示面 | 说明 |
|------|------|--------|------|
| 公开 | 技术内容与工程实践 | 网站展示 + 仓库可见 | 面向面试官、同行、任何路过的陌生人，是"能力展示面" |
| 半公开 | 个人思考、读书笔记、社会观察 | 仓库可见，但不在网站展示 | 开源可克隆，但作者主观上不希望被主动推送 |
| 私有 | 简历、密钥、纯私人内容 | 完全不上云，纯本地 | 物理隔离，任何自动化流程都不推送 |

为什么要把内容体系拆成三座仓库，而不是放在一个大仓库里用目录区分？核心动机是**公开性分层**：同一套内容体系里，不同内容的敏感度和用途完全不同。技术文章可以大大方方展示，个人对社会现象的思考作者并不想被陌生人主动看到，简历和密钥则连上云都不应该。如果混在一个仓库里，要么为了迁就最敏感的内容把所有东西都锁死（失去展示价值），要么为了展示技术内容而冒隐私泄露的风险。拆成三座仓库，每座仓库的公开策略独立演进，是这套系统的地基决策。

**入口判断的决策流程**是三步走：关键词匹配 → 决策树 → 公开性检验。

第一步，**关键词匹配**。系统维护了一份关键词对照表，把待判断的内容与三座仓库的关键词逐条比对，统计每座仓库的命中数。技术内容命中技术类关键词（编程语言、引擎、算法、架构、性能、AI 等），个人思考命中思想类关键词（哲学、社会观察、感悟、读书笔记等），隐私内容命中隐私类关键词（简历、密钥、密码、敏感话题等）。这一步是粗筛，命中数给出一个初步倾向。

第二步，**决策树判断**。关键词命中之后，用几条硬规则收束判断。其中最重要的一条是：**凡是涉及 AI、Agent、LLM 的内容，一律只允许进入技术文档库，不存在"放到个人思考仓库"的选项**——除非内容涉及个人隐私，才转入私有仓库。这条规则看起来武断，实际是作者有意为之：AI 相关的内容是这个时代的技术热点，也是作者希望持续积累和展示的方向，混入个人思考仓库会造成分类漂移。混合内容则看主要意图的权重。

第三步，**公开性检验**，这是一切判断的兜底。系统会问自己一个问题：**"这条内容如果被面试官或 HR 看到，合适吗？"** 合适且偏向技术 → 公开仓库；不太合适（个人观点、思想感悟）→ 半公开仓库；极端敏感 → 私有仓库。这一步是纯主观判断，但它恰恰是最重要的一道闸门——它负责拦截那些"技术上没问题、但公开出来会后悔"的内容。

判断完成后，如果置信度足够高，系统输出归属结论（哪座仓库、哪个分类）；如果置信度低或分类无法确定，系统**必须询问作者，不自作主张**。分类名也不是凭空想象的——系统会先列出目标仓库的真实目录结构，再从已有目录中选择最匹配的分类，绝不静默创建新分类目录。这个"从真实目录树选分类"的纪律，避免了分类体系在长期使用中悄悄膨胀出一堆近义目录。

入口判断还有一层设计哲学，值得单独点出，因为它会**贯穿全文**：

> **零上下文可读原则：对外公开的文档，必须让一个完全陌生的读者也能完整理解。**

这条原则的意思是：任何一段内容，如果去掉"我""我们""我的项目"这层私有上下文之后就不成立了，那它就不属于公开文档。入口判断的分类逻辑、后面讲到的暂存保真、纯净上下文写作、内部代号替换机制，本质上都是这条原则在不同环节的落地。它是整个系统最重要的设计原则，不是一条可有可无的写作规范。

入口判断的局限也很明显：关键词匹配是"死"的，它只能识别词表里的词。作者偶尔说一句"我有个想法"——没有命中任何技术词、也没有命中任何思想词——关键词匹配就会失灵，需要决策树和公开性检验兜底。这个局限在"当前局限与未来方向"一节里还会再讨论。

#### 2. 日常记录：轻量捕获

入口判断完成后，如果作者的需求只是"记录一下"，系统就走**日常记录**流程。

日常记录的目标可以用一句话概括：**用最轻的动作，把想法变成文件。** 它是想法的第一落点，是整条内容流水线的起点。

具体流程是：读取日常记录模板（带空模板检测，后面会讲为什么模板会空、空了怎么办）→ 从作者原话中提取核心观点 → 按模板格式写入文件 → 提交到版本库并推送。文件命名是 `日期-主题.md`，统一平铺在文档库的日常记录目录下，不分子目录。一条日常记录通常只有几十到几百字，不需要结构完整，不需要论证充分——它只需要"把这一刻的想法固定下来"。

**为什么需要这么轻的一步？** 因为想法最大的敌人是"对话的蒸发"。作者和 Agent 讨论一个问题，讨论得再深入，如果讨论结束时没有落盘，几小时后这个想法就只剩一个模糊的印象，再想捡起来就得从头开始。日常记录提供了一个"几秒钟就能完成"的捕获动作：作者不需要组织语言、不需要规划结构，说一句"记一下"，Agent 就把当前想法写成文件。这个动作的成本足够低，所以作者愿意频繁使用；因为频繁使用，所以没有想法会真正蒸发。它是整个流水线的"保险丝"——宁可多记、记得粗糙，也不能漏记。

日常记录有一个强制步骤：**敏感内容脱敏**。因为日常记录写在公开或半公开的文档库里，作者原话中如果出现内部代号（系统内组件的名称、作者的身份代号等），记录时就必须按映射表替换成公开表述后再写入，禁止原样照抄。这一步在记录阶段就执行，而不是拖到归档阶段——因为日常记录本身就已经是"对外可见"的文件了，从落盘那一刻起就要经得起陌生人查看。作者对内部代号的脱敏管理有一套专门的机制，在"归档"一章还会详细讲。

日常记录还有一条重要边界：**它不讨论、不归档、不创建正式文档**。它只是捕获。想法记录下来之后，如果作者想深入讨论，就进入下一个环节；如果不想，记录就静静地躺在日常记录目录里，成为文档库的一部分。流水线的每一段只做自己的事，不越界——这个"职责分层的单行道"设计，是整条流水线不堵塞的关键。

#### 3. 讨论：对话中的保真

当作者说"我们来聊聊这个话题"时，系统进入**讨论**流程。讨论是想法深化的主战场，也是这套系统设计上最用心、事故教训最深刻的一个环节。

**四种讨论模式。** 根据作者的意图，讨论分为四种模式：

- **直接讨论：** 作者直接与文档管理 Agent 对话，深化一个话题。
- **Agent 间讨论：** 作者要求文档管理 Agent 与另一个 Agent（本文统称"审阅 Agent"）讨论一个话题。
- **归档前审阅：** 作者要求"归档，并且先跟审阅 Agent 讨论一下"，即归档前强制走一轮独立审阅。
- **仅归档：** 作者只要求归档，不经过独立审阅，直接进入归档流程。

四种模式的区分看起来只是"要不要拉审阅 Agent 进来"，实际背后是作者对话题风险的判断：越重要、越容易被陌生人审视的话题，越需要独立的第二视角。

**暂存保真机制——讨论体系的心脏。** 无论哪种模式，讨论的核心机制都是一个：**暂存文件**。系统把每一轮讨论的内容——包括作者的原话和 Agent 的回复——**完整、原文**地写入一个单独的暂存文件。这个文件是讨论过程的唯一记录，也是后面归档时正式文档的**唯一原料**。

为什么必须存原文、严禁压缩总结？因为讨论的参与者事后需要"原始信息"，而不是"二手摘要"：

- **归档时的写作 Agent 不参与讨论。** 归档时，系统会唤起一个"纯净上下文"的写作 Agent 来撰写正式文档（详见第 5 章）。这个写作 Agent 没有参与过讨论，它了解话题的唯一途径就是读暂存文件。如果暂存里存的是压缩过的摘要，写作 Agent 就丢失了讨论中的细节、论证过程和作者的原话——文档的质量必然受损。
- **审阅 Agent 依赖完整记录。** 归档前审阅模式下，审阅 Agent 也需要通过暂存文件理解讨论的完整来龙去脉，才能给出有意义的审阅意见。压缩会丢信息，信息不完整审阅就是空转。

所以暂存文件的写入有两条铁律：**原文写入，禁止压缩；先写暂存，再输出给用户。** 这两条铁律不是一开始就有的，它们是被一次真实的事故逼出来的——这个事故值得完整讲一遍。

**事故：最后一轮讨论永久丢失。** 系统早期，暂存写入是"自动触发"的：Agent 生成回复后，系统自动把回复写入暂存。某一次讨论中，Agent 先生成了回复并**先输出给了用户**，然后再执行暂存写入——而在"输出给用户"和"写入暂存"之间的中间环节出了差错，写入失败。结果是：那一轮讨论的内容——作者的发言和 Agent 的回复——**永久丢失**。因为讨论是对话，对话过时不候，丢失了就无法重来。那次事故之后，系统把写入机制改成了强制规则：

1. **写入时机必须是手动的、显式的，不再依赖自动触发。** 每一轮讨论结束后，Agent 必须显式执行"读暂存 → 拼接本轮内容 → 写回 → 验证"四个动作，中间任何一步都不能省。
2. **时序铁律：先写暂存，再输出给用户。** 生成回复文本 → 写入暂存 → 输出给用户，三个动作的顺序固定，不可调换。先输出后写暂存 = 本轮操作不合格，必须当场回退补写，不存在"下轮再补"的选项。
3. **写入后必须验证。** 写完后要读回暂存，逐句对比原文，确认没有压缩、没有遗漏。发现压缩立即用原文覆写纠正。

这个事故的完整因果链是：自动触发 → 先输出后写暂存 → 中间环节出错 → 数据丢失 → 改为手动执行 + 强制时序 + 写入后验证。作者特意把这个故事完整讲出来，是因为它说明了一个普遍规律：**凡是"靠系统自动做"但"做错的代价是永久丢失"的操作，都应该改成"靠纪律显式做"**。自动化的省事是有价格的，当丢失的代价远大于省下的那点事，就要把自动化让位给纪律。

暂存文件的另一个细节是它的**生命周期**：新讨论开始时清空旧内容、写入新讨论的元信息（记录类型、主题、创建时间）；同一话题的延续讨论则跳过清空；归档完成后再开新讨论时自动清空。暂存文件始终只有一个，它永远是"当前进行中的讨论"的唯一载体。

**为什么讨论环节要这么重？** 因为讨论是整条流水线里信息密度最高的环节——作者的真实想法、即时反应、对细节的追问，都发生在这里。前面的日常记录是"轻捕获"，讨论是"深化"，深化过程中的每一句话都可能成为正式文档的素材。所以系统宁可牺牲一点执行效率，也要保证讨论过程的完整保真。这是"过程资产化"的核心：**讨论不只是聊天的记录，它本身就是资产**——是可追溯、可复用、可归档的原料。

#### 4. 独立审阅：跨 Agent 的视角分离

讨论深化到一定程度后，作者可能决定"这个话题值得归档成正式文档"。如果作者要求先审阅再归档，系统就会进入**独立审阅**环节——拉一个与文档管理 Agent 相互独立的"审阅 Agent"来审视讨论内容。

独立审阅环节有两个核心设计，都很值得讲。

**第一个设计："记者而非指挥官"原则。** 当文档管理 Agent 委托审阅 Agent 干活时，它的角色定位是"记者"而不是"指挥官"：给审阅 Agent 提供完整的前因后果——发生了什么、为什么需要审、已有哪些线索和结论——然后**让审阅 Agent 自己判断**根因、修法、范围，而不是替它做判断、给它下指令。这个原则听起来简单，执行起来很反直觉：作为委托方，文档管理 Agent 天然倾向于"我已经知道答案了，你按我说的做就行"。但作者刻意禁止这种倾向。原因是：如果委托方已经想好了答案，那审阅就失去了意义——它只是让另一个 Agent 替自己执行已经定好的结论，盲点还在。记者式委托把判断权留给审阅方，才能真的发现委托方看不到的问题。

**第二个设计：上下文隔离。** 审阅 Agent 在被唤起时，**不继承文档管理 Agent 的对话历史**，只接收与本次审阅直接相关的输入（讨论暂存内容、必要的工作区文件）。这个设计动机是防止"对话历史偏见"污染审阅判断：文档管理 Agent 的上下文里装着整个讨论过程、作者之前说过的所有话、以及它自己的倾向——如果这些全部灌输给审阅 Agent，审阅 Agent 的"独立视角"就被污染了，它看到的其实是文档管理 Agent 想让它看到的世界。纯净上下文启动，审阅 Agent 只能基于客观输入做判断，这才叫"独立的第二视角"。这也是"提议者与评测者分离"思想的一次轻量落地：**写的人不评自己写的东西，参与讨论的人不审自己参与的讨论。**

**三轮固定讨论的约束。** 归档前审阅不是无限循环的对话，而是**固定三轮**：第一轮，审阅 Agent 读取素材，给出完整的审阅意见（结构建议、遗漏机制、盲点、脱敏注意事项）；第二轮，文档管理 Agent 把作者的优先级校准传达给审阅 Agent，请它基于校准后的方向重新给出写作骨架；第三轮，审阅 Agent 收束意见，确认骨架与脱敏清单无遗漏，给出最终写作建议。三轮结束后即进入归档。固定轮次的设计避免了审阅无限拖延——审阅是手段，不是目的，它服务于"把文档写好"这个最终目标，而不是成为流程本身。

审阅完成后，讨论内容进入归档阶段——这也是整条链路中最重的一个环节。**审阅是归档的前置步骤**：只有在审阅确认方向之后，归档才启动；两者不是并列关系，而是先后关系。下面详细讲归档。

#### 5. 归档：从原料到正式文档

归档是把讨论内容从"过程态"变成"资产态"的环节，也是整条流水线里最重的一环。它是一套**六步流程，缺一不可**。为了不把六步讲成流水账，这里按"轻 → 重 → 轻"分组来讲：轻的步骤一段带过，重的步骤重点展开。

**轻：第一步，读暂存。** 归档动作启动后，系统先读暂存文件，确认暂存非空——**暂存为空则不能归档**。这一步是归档的前提：暂存是正式文档的唯一原料，没有原料就没有归档。看起来是例行检查，实际是在执行入口判断的"先看原料再看产出"原则：先确认材料齐全，再谈加工。

**重：第二步，创建正式文档——归档的核心。** 这是整个归档流程的核心，也是整条流水线里信息密度最高、设计最讲究的一步。它本身又是一条内部小流程，包含几个关键机制：

**机制一：分类目录存在性校验。** 系统先列出目标文档库的全部分类目录，**逐条通读完毕**之后，才做匹配判断——匹配的目标只能是真实存在的目录，严禁凭空想象分类名。如果精确匹配未命中，系统把完整目录列表交给作者选择，绝不静默创建新目录。这条纪律看起来繁琐，实际堵住了文档库长期使用中最大的腐化源：分类目录悄悄膨胀，近义目录互相打架，文档散落得到处都是。宁可每次归档多花十秒钟确认目录，也不能让分类体系在三年后变成一个无法检索的乱摊子。

**机制二：二次分析。** 系统先审视暂存内容，形成四维判断：正确点是什么、错误或偏差是什么、遗漏了什么、哪些地方不足需要补充。这个分析不直接决定文档内容（文档由独立的写作 Agent 撰写），但它决定了写作任务书的质量——任务书写得准，写作 Agent 才写得准。

**机制三：纯净上下文写作。** 正式文档由独立的写作 Agent 撰写。这个写作 Agent **不带任何对话历史**，它的全部输入是：暂存文件（讨论原料）、模板、写作指南、验证清单、以及明确的写作要求。为什么必须这样？因为文档是**独立作品**，不是讨论记录的搬运：讨论记录是原料，文档是作品。让一个不参与讨论、不被对话历史污染的 Agent 来写，才能保证文档的视角是"面向陌生读者的完整作品"，而不是"讨论过程的忠实复述"。这个设计与独立审阅的上下文隔离同源：**要得到独立的产出，就必须有独立的上下文。** 写作任务书里还必须包含显式的写入指令——写作 Agent 有文件写入能力，但只有任务书明确要求它写文件时它才会写；不给指令，它不会动文件。写完以后，主 Agent 还要自己读文件验证——"写完了"不能由执行者自证。

**机制四：十六条质量门控。** 写作 Agent 完成初稿后，必须逐条对照十六条质量标准自查。这十六条标准覆盖结构、内容、安全、编码四个方面，包括：结构完整（模板段落名和顺序一致）、中文字数达标、正文与元数据无内部代号、无来源标签（不出现"谁说""谁认为"句式）、元数据完整规范（标签用英文逗号分隔、作者用笔名、来源标注为标准值）、零上下文可读、知识缺口节存在且非空、编码正确等等。作者之所以把这十六条做成"可检查的规则"，而不是依赖"写作者认真一点"，是因为**用可检查的规则替代主观判断**是这套系统的一个基本信念：质量不是靠态度保证的，是靠机制保证的。规则可以逐条打勾，态度没法量化。

十六条里最有代表性的一条是**零上下文可读检查**：写完文档后退一步看，有没有任何一段话需要读者知道"你是谁"才能理解？如果有，删掉它或重写。这条规则直接对应整篇文档的"灵魂原则"——入口判断时的设计哲学，在这里落地成一条可执行的验收标准。

还有一条值得单独说：**来源标注透明**。正式文档的元数据里有一个固定字段"来源简注"，标准值是"由作者的 Agent 整理"。这个字段的存在是为了诚实：文档虽然是"作者"署名，但实际由 Agent 辅助完成，这个事实必须在元数据里对读者透明。作者特意强调，这个字段的填写有严格纪律——只有作者明确写过其他表述时才替换，严禁把内部文件路径、内部组件名写进元数据。

**为什么第二步不可跳过？** 因为归档的产出物——正式文档——是整套系统的最终价值所在。日常记录是原料、讨论是过程、审阅是质检，而正式文档是唯一对外展示的"资产"。如果归档时跳过正式文档创建，那前面所有的环节都白做了——讨论过程再保真，没有落成正式文档，就只是一堆躺在暂存文件里的聊天记录。所以归档六步中，第二步是强制步骤：**归档必须有正式文档产出，没有产出不算归档。**

**中：第三步，创建历史记录。** 正式文档创建后，系统在历史记录目录下新建一条归档记录，命名格式为"文档标题-归档记录"，记录这次归档动作的痕迹（何时、哪个话题、归档成了哪篇文档）。这一步的目的是**可追溯**：几个月后回看，还能查到"某个话题确实被处理过、归档成了什么"。

**中：第四步，删除原始日常记录。** 如果归档来源是日常记录，归档完成后删除这条日常记录。这里有一个极容易被忽视的细节：**删除必须用版本库的删除命令（git rm），不能用普通的文件删除命令（del/rm）**。原因很实际：普通删除只删本地文件，不会把删除操作记录进版本库；而文档库是推送到远程的，本地删了、远程没删，就会造成"远程残留"——别人在公开仓库里还能看到这条本该被归档掉的内容。用版本库删除命令，删除动作才会被版本库跟踪，推送后远程才真正删掉。这个细节是版本库语义的坑，作者在这个坑上栽过跟头，所以把它写进了强制流程。

**中：第五步，版本库提交与推送。** 归档涉及多个文件变更（正式文档新增、日常记录删除、历史记录新增），需要提交并推送到远程。这里执行**原子化逐步提交**纪律：每次文件操作后立即提交，一个操作一个 commit，严禁批量累积。更重要的是另一条铁律：**版本库的暂存命令必须逐文件指定，严禁"暂存全部"（git add .）**——这条铁律的由来，是下面这个事故。

**事故：模板被清空事件。** 某次操作中，系统执行了"暂存全部"命令（git add .），结果把不该暂存的内容也暂存了，连锁反应导致模板文件被清空。模板是整套系统的只读参照——日常记录模板、正式文档模板——一旦为空，后续所有文档操作都会失去依据。修复方式是立刻用版本库命令恢复模板文件，然后重读、继续。这个事故的根因就是**批量暂存**：批量暂存让你以为自己在"省事"，实际上它把所有文件的选择权交给了版本库，任何一个意外文件都可能引发连锁事故。修复规则是永久性的：**严禁批量暂存，每次暂存必须逐文件指定**。配套的还有空模板检测机制：任何流程读模板时，先检查模板是否为空，为空立即停止、恢复、重读，严禁在空模板下继续执行。

**事故：上下文泄露事件。** 系统早期，某篇公开文档的正文中出现了内部代号——系统内组件的真实名称——被提交到了公开仓库。这个代号对作者来说是日常用语，但对陌生读者来说，它泄露了系统的内部结构，而且让文档显得"自说自话"。这次事故催生了**内部代号替换机制**：系统维护了一份"内部代号到公开表述的映射表"，凡是系统内部使用的组件名、代号、路径，在进入公开文档之前必须按映射表替换成公开表述；归档的清理检验步骤里，还有一道强制扫描——搜索正式文档和历史记录是否残留内部代号，命中即修正后重新推送。上下文泄露事件说明了一个残酷的事实：**对作者来说太熟悉的内容，恰恰是陌生读者最容易困惑、也最容易泄露隐私的内容**。零上下文可读不是洁癖，是安全需求。

**轻：第六步，清理检验。** 归档的最后一步是收尾检验：确认删除已正确暂存到版本库、确认正式文档和历史记录已创建、执行内部代号扫描确认零残留。全部通过，归档才算完成。暂存文件本身保留不清空——它承载的是"本次讨论的过程资产"，下次新讨论开始时才自动清空。

六步流程走完，"轻 → 重 → 轻"的结构也讲完了：读暂存是轻前提，创建正式文档是重核心，历史记录、删除、推送是中间件，清理检验是轻收尾。读者如果只记住一句话，那就是：**归档的核心是正式文档，正式文档的核心是质量门控，质量门控的核心是可检查的规则。**

#### 6. 自维护闭环：让系统自己长出经验

前面五章讲的都是"系统如何管理文档"。这一章讲的是最后但最关键的一点：**这套管理流程自己也在被管理**。作者称之为自维护闭环——让系统在真实运行中持续积累经验、修正自己的规则。

**执行/维护分离理念。** 自维护闭环的第一条设计原则是**执行与维护分离**：执行者只负责记录问题，不负责判断归属、不负责修改规则；维护者只负责蒸馏和修改，不负责日常执行。具体地说，当系统在执行文档操作时出了问题——执行偏差、工具使用错误、用户纠正、自己发现可优化点——执行者只做一件事：**把原始问题上下文原样写入问题收件箱**（一个集中的原始记录文件），不做任何判断、不蒸馏、不修改。然后由独立的维护进程在维护期读取收件箱，逐条判断归属、蒸馏成规则修改。为什么要这样分离？因为"自己改自己"是人类和系统共同的自我合理化陷阱：执行者刚犯了错，让它立刻修改规则，它大概率会为自己辩解，而不是客观地修问题。执行/维护分离把"犯错"和"改规则"从时间上和角色上隔离，让规则修改始终由"干净的上下文"做出。

**三层链路：原始问题记录 → 分流 → 有界修改。** 自维护闭环的完整链路是三层：第一层，原始问题记录（执行者写收件箱，只记事实不判断）；第二层，分流（维护进程读取收件箱，逐条判断问题归属——是某个操作协议的问题、还是提示词配置的问题、还是无需处理——并更新记录状态）；第三层，有界修改（对确认需要修改的规则执行有界修改，每次修改有明确的规模上限，如最多涉及几个协议文件、每个文件最多改几个章节、每个改动最多多少行）。三层链路环环相扣：第一层保证问题不丢失，第二层保证问题被正确归位，第三层保证修改不失控。

**三层心跳。** 驱动自维护闭环的是一套周期性定时机制，作者称之为"三层心跳"：

- **每日巡检：** 每天触发一次，扫描问题收件箱中的未处理记录与新出现的问题，做聚类标记，**只观察不修改**。日检的价值是及时发现问题苗头，但不急着动手改。
- **每周维护：** 每周触发一次，按维护阈值执行有界修改——处理达到阈值的问题，执行受控的规则修改。周维护是"动手"的一层，但严格受规模上限约束。
- **每月治理：** 每月触发一次，做全量审计：检查规则之间的冲突、评估协议的合并与拆分、做安全审计。月治理是"反思"的一层，关注的是系统整体的健康度。

三层心跳的核心思想是**渐进式维护**，它避免两个极端：一个是"每次犯错当场改规则"——改得太频繁、太多，规则系统失去稳定性，而且无法验证每次修改的效果；另一个是"从不维护"——规则系统慢慢腐烂，旧规则失效没人清理，新问题没人处理。渐进式维护在"改太多"和"不改"之间找到一条中间路线：及时记录、定期处理、受控修改。

自维护闭环还有一个值得一提的约束：**阈值是最后防线，不是拖延借口。** 系统对同一类问题设定处理阈值——出现一次低影响问题只记录不修改，出现两次相同根因问题标记为复发，出现三次相同模式强制生成维护建议，出现五次则在下一次维护时强制优先处理。阈值的本意是避免"一有风吹草动就大改"，但它也可能被滥用成"再等等"的借口。作者遇到过这样的情况：某个维护项被反复提及，但每次都因为"再等等"被跳过——问题明明到了该处理的阈值，却一直拖下去。事后总结的教训是：**阈值是"至少该处理"的最低线，不是"可以不处理"的挡箭牌**。记录问题不是为了存档，是为了解决问题；如果只记不改，收件箱就变成了一个不断膨胀的坟墓。

到这里，六环节流水线讲完了：入口判断决定内容去哪，日常记录轻量捕获，讨论保真深化，独立审阅提供第二视角，归档锻造正式文档，自维护让系统自我进化。接下来进入这篇文章的配角部分——当前局限与未来方向。

### 实现方案

#### 7. 当前局限与未来方向

这一章是全文的配角，占篇幅不多，但作者认为它是整篇文章里最有讨论价值的部分之一。原因很简单：**一套系统最诚实的部分，不是它做到了什么，而是它承认自己还没做到什么。** 作者按"已知瓶颈 → 探索中的改进 → 开放问题"三层来写。

**已知瓶颈一：规则膨胀。** 这套系统运行至今，已经积累了几十个操作协议、五十余条执行铁律、十六条质量门控标准。规则系统的规模本身已经成为一个维护负担：规则之间可能冲突，新规则可能和旧规则隐性打架，规则太多导致执行者在真实操作时"记不过来"。作者必须承认一个反直觉的事实：**规则越多，不等于系统越安全。** 每条规则都有成本——它要被执行者记住、要与其他规则兼容、要在维护期被审计。当规则总量超过某个临界点，新增规则带来的收益可能小于它带来的认知负担。读者如果照搬这套系统，第一件要意识到的事就是这个：规则不是免费的，规则膨胀是系统长大的必然代价，管理规则本身是一项持续的工作。

**已知瓶颈二：暂存的自动化张力。** 第 3 章讲过，暂存写入被事故逼成了"手动执行 + 强制时序"。这个设计保证了保真，但代价是每一轮讨论都要手动执行四步操作（读、拼、写、验证）。作者一直在"靠纪律"和"靠系统"之间挣扎：把暂存写入自动化，省事但高风险——自动触发时机判断可能出错、自动压缩可能丢信息、写入顺序可能出错；保持手动，安全但累。这个张力是整套系统里"自动化与可靠性"矛盾的最典型样本，也是作者认为最值得读者一起讨论的问题。

**探索中的改进。** 针对上面的瓶颈和运行中观察到的其他问题，作者有几个正在探索的改进方向，这里简要列出：

- **文档库全局索引：** 维护一份全库索引（目录树 + 文件清单 + 标签映射 + 最近更新），入口判断和内容查询先查索引再落盘，减少重复的目录扫描。这直接回应"文档库越大，查找越慢"的现实痛点。
- **知识缺口闭环：** 每篇正式文档文末标注"知识缺口"（未覆盖的知识点），但这个标注目前只是"标注"，没有"行动"。改进方向是把知识缺口升级成待更新清单，带优先级，维护期检查是否有新信息可补——让"我知道我哪里不知道"变成"我计划去补上"。
- **风格案例库：** 沉淀一批高质量正式文档作为风格参考，新文档写作时参考其结构、语言、深度控制——让"好文档"可复制，而不是每次都从零摸索。
- **版本库操作封装：** 把"暂存指定文件 + 提交 + 推送"封装成单一动作，但仍然强制"一次只提交本次操作的文件"——便利和纪律兼得。封装不能是黑箱，底层操作仍然可见可审计。
- **触发识别升级：** 当前入口判断和记录触发依赖关键词匹配，改进方向是引入辅助判断兜底：关键词未命中时，用额外的判断机制给出置信度，低置信度走人工确认。关键词层保留，不替换——它是可预测性的保证。

**开放问题。** 最后是两个作者目前没有答案、但觉得值得公开提出来的问题：

- **自动化层失效时，人工兜底的最低保障是什么？** 当模型的更新、框架的升级、外部服务的变化导致自动化组件行为异常时，系统的底线保障是什么？目前作者靠"执行后验证"兜底，但这是事后补救，不是事前保障。
- **跨 Agent 协作时，如何保证各方信息一致？** 参与同一话题的多个 Agent 看到的是不同的上下文（文档管理 Agent 有完整对话历史，审阅 Agent 只有传入的部分输入），上下文不对称可能导致协作脱节。如何在不牺牲独立性的前提下，保证协作各方对事实的理解一致？

这两个问题作者没有答案，写在这里，本身就是邀请讨论。

### 总结

这篇文章分享了一套真实运行中的、由 Agent 全流程管理的个人文档库系统。回顾全文的核心内容：

系统的地基是**三档公开性分层**——内容按敏感度分成公开、半公开、私有三座独立仓库，公开性判断由"入口判断"环节负责，其灵魂原则是**零上下文可读**：对外文档必须让陌生人也能完整理解。内容的生命周期是一条六环节流水线：**日常记录**轻量捕获想法，**讨论**通过暂存保真机制保存每一轮对话原文，**独立审阅**用"记者而非指挥官"原则和上下文隔离提供真正的第二视角，**归档**用六步流程（核心是十六条质量门控的正式文档创建）把原料锻造成资产，**自维护闭环**用执行/维护分离、三层心跳和有界修改让系统自己长出经验。

系统里几乎每条重要规则都是被事故倒逼出来的：最后一轮讨论永久丢失催生了"先写暂存再输出"的时序铁律，模板被清空催生了"严禁批量暂存"和空模板检测，内部代号泄露进公开文档催生了代号替换机制。作者特意把这些事故完整讲出来，是因为它们比设计本身更有借鉴价值——**设计告诉你系统应该长什么样，事故告诉你系统为什么会长成这样。**

最后，作者必须诚实地标注这套系统的局限性：**它为单人 + 多 Agent 场景设计**，放到多人团队协作下很多设计需要重新评估；它的质量标准（包括一万字以上才算正式文档）是**作者的特定偏好**，不代表普适标准；它的许多规则是**事故倒逼的补丁**，不是深思熟虑的规划——补丁有效，但补丁与补丁之间可能有作者还没发现的冲突。作者不美化这套系统，因为它还在成长，还在踩坑，还在自我修正。

分享这篇文档的目的，在开头说过，这里再说一次：**这是一份公开的邀请讨论帖。** 读者如果对入口判断的分类逻辑、暂存保真的成本收益、独立审阅的上下文隔离、十六条质量门控的取舍、自维护闭环的阈值设计、或者那两个开放问题有任何想法，都欢迎联系作者讨论。作者最期待听到的，不是"这套系统很完善"的赞美，而是"为什么不用另一种做法"的质疑。

## 知识缺口

本文未覆盖以下知识点，留待后续补充：

- 多用户/多人协作场景下的适用性：当前设计针对单人使用，团队场景的权限、冲突、责任划分均未讨论。
- 系统的可迁移性：整套机制在 Agent 框架之外的载体（纯脚本、人工流程）上如何落地，未做验证。
- 文档库的容量规划：当文档总量达到数百篇时，目录结构、检索性能、版本库体积的变化趋势，本文没有实测数据。
- 安全审计的细节：三层心跳中的月度治理涉及的安全审计项，本文只提了原则，未展开具体审计清单。
- 质量门控十六条标准的完整清单：本文只展开了其中几条有代表性的，完整清单是系统内部实现，未逐一列出。
