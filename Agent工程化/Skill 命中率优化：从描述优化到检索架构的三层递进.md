# Skill 命中率优化：从描述优化到检索架构的三层递进

## 摘要

Skill 命中率是衡量 Agent 系统能否准确响应用户意图的核心指标——用户说了一句话，系统能否选中正确的 Skill 并成功执行。这个看似单一的问题，实际上横跨"描述→路由→检索→执行"四个环节，任何一个环节的偏差都会被逐级放大，最终表现为命中失败。这篇文章面向 Agent 开发者、Skill 作者和框架设计者，提出一个三层递进的优化框架：内容层（零依赖，每个 Skill 作者都能独立优化 name 和 description——按 Agent Skills 开放规范，description 同时承担"做什么、何时使用、何时不用、与相近 Skill 如何区分"四重职责）、架构层（通过大类包裹、路由 Skill、子文档分离和 Gate 机制，体系化地压缩路由空间）、引擎层（混合检索、LLM 精排、动态候选列表和自动化评测闭环，从框架层面提升检索与排序能力）。三层并非替代关系，而是叠加关系——内容层做好的精度基础，是架构层压缩路由空间的前提；架构层提供清晰的结构信号，是引擎层检索增强的地基。核心主张是：从今天就能动手的第一层开始，逐步向下推进，每一层都解决上一层无法解决的问题。

## 正文

### 背景

当 Agent 系统只包含少量 Skill 时，路由不是一个值得讨论的问题——LLM 在 2~3 个候选中几乎不可能选错。但当 Skill 数量膨胀到数十甚至上百时，路由精度就从一个边缘问题迅速升格为系统可用性的核心瓶颈。

Skill 命中率的完整定义是：从用户输入自然语言指令开始，到系统选中正确的 Skill 并使其成功完成预期任务为止的全链路成功率。它与传统 NLP 领域讨论的"意图识别准确率"有本质区别——意图识别只关心"用户想干什么"的分类标签是否正确，而 Skill 命中率还关心：候选池里有没有这个 Skill（召回）、选中的 Skill 在候选列表中排在多靠前的位置（排序质量）、LLM 在拿到候选列表后是否确实选择了正确的 Skill（执行成功）、以及 Skill 内部的子步骤是否按预期完成。换句话说，意图识别准确率只是 Skill 命中率的一个必要但不充分的条件。

这个问题越来越紧迫，原因有三。第一，Skill 数量的非线性增长导致路由空间急剧膨胀——从 3 个 Skill 中选一个和从 50 个中选一个，难度不是线性增加的，因为 Skill 之间的边界模糊区域随数量平方增长。第二，多 Skill 协作场景中出现了"串扰"问题——一个 Skill 的执行结果被另一个 Skill 误读为新的触发条件，形成连锁错误。第三，Skill 作者的来源越来越多元化——不同作者有不同的写作风格、不同的术语习惯、不同的抽象层次，这些差异作为噪声注入路由系统，使得语义匹配的难度进一步上升。

从系统性视角看，Skill 命中率的问题可以按层次拆解。最表层是内容问题：Skill 的 name 和 description 写得好不好——信息是否足够充分、边界是否足够清晰。中间层是结构问题：Skill 之间如何组织——是 50 个 Skill 平铺在一个路由层，还是有层级化的入口和子模块。最底层是检索问题：框架用什么算法把用户输入映射到候选 Skill 列表——是纯关键词匹配、纯语义向量、还是混合检索加精排。这三层之间存在一种有趣的依赖关系：上层优化不到位，会掩盖下层的能力；上层优化到位后，会暴露下层此前不可见的瓶颈。因此，Skill 命中率优化不是一个"挑一层做"的选择题，而是一个"从第一层开始，逐层推进"的递进工程。

典型的失败模式可以分为四类。未触发：用户表达了明确的需求，但系统没有匹配到任何 Skill，导致静默失败或通用兜底回复。误触发：用户的需求被路由到了错误的 Skill——比如用户想"查看最近的文档修改记录"，但被路由到"创建新文档"的 Skill。串扰：两个功能相近的 Skill 在边界场景上反复被选错，且错误模式不稳定——同一条用户输入，有时命中 A 有时命中 B。空转：Skill 被正确选中但执行失败——比如 Skill 内部的前置条件检查不通过、必要的上下文缺失、或子步骤编排逻辑有 bug。这四种失败模式分别对应了命中率链路上不同的断裂点，需要不同层次的手段来修复。

### 核心内容

#### 第一层：内容层 — 描述与触发词的优化

内容层是整个三层框架的基石。它回答一个根本问题：在不改任何代码、不改任何框架逻辑的前提下，仅通过优化 Skill 的 name 和 description（按 Agent Skills 开放规范，description 同时承载触发条件、排除规则和 Skill 间区分），能把命中率推到多高？答案是：在很多实际场景中，内容层的优化收益被严重低估了。一个写得好的 description 可以让 LLM 在 3 个候选 Skill 中做出近乎完美的判断；而一个写得模糊的 description 会让 LLM 在候选列表只有 2 个 Skill 时仍然选错。

##### 2.1 description 的四个核心职责

在 Agent Skills 开放规范中，Discovery 阶段（即路由阶段）只加载两个字段：`name` 和 `description`。系统根据这两个字段判断用户请求是否匹配某个 Skill，匹配后才加载完整的 SKILL.md 执行指令。这意味着 `description` 是路由精度最根本的单一决定因素——它必须在有限的篇幅内同时承担四重职责：做什么、何时使用、何时不用、与相近 Skill 如何区分。

先说规范要求。Agent Skills 标准（agentskills/agentskills）规定，SKILL.md 的 YAML frontmatter 至少包含 `name` 和 `description`，Agent 在启动时只扫描这两个字段建立能力索引。`description` 的作用不是详述 Skill 的所有功能（那是 SKILL.md 正文的事），而是让 Agent 在路由阶段做出两个判断：这个 Skill 是不是当前任务所需的？有没有其他 Skill 更合适？[规范要求]

四重职责的拆分如下。

**做什么（What）：** 用 1–2 句话描述 Skill 的核心功能，聚焦于"这个 Skill 解决什么问题"而非"这个 Skill 有哪些子步骤"。好的示例："创建轻量日常记录文件——保存想法、备忘或待办，不做结构化整理或归档。"差的示例："此 Skill 负责记录管理，包含创建、编辑、删除、归档、搜索功能。"后者把自己描述得像一个大类而非具体 Skill，在路由时会被 LLM 当作万能选项而频繁误触发。

**何时使用（When to use）：** 描述触发条件——用户输入表达了什么样的意图时应该激活此 Skill。关键是以意图模式而非例句列表为核心。写作原则是"用户表达了 X 意图且未表达 Y 意图时触发"，而非"用户说了这些词时触发"。具体方法见 2.2 节。

**何时不用（When not to use）：** 写出明确排除的场景。LLM 的路由判断中最有价值的信息往往是负面的——知道"在什么情况下绝对不要选这个 Skill"。排除规则应具体到场景级别："当用户同时表达了记录意图和讨论意图时，不应触发此 Skill——讨论场景应由讨论类 Skill 处理。"单条件排除太宽泛，多条件组合排除更精确。

**与相近 Skill 如何区分（Differentiation）：** 如果存在功能相邻的 Skill，显式写出区分规则。"与 [Skill B] 的区别：本 Skill 处理 X 场景，[Skill B] 处理 Y 场景。当用户输入中同时包含 X 和 Y 的信号时，优先判断主导意图。"引用对方时要同时写出对方的核心功能描述，让 LLM 不需要去读对方的完整 SKILL.md 就能理解分界。区分规则要双向——两个 Skill 各自在 description 中引用对方，LLM 的路由判断就从模糊的独立评估变成了清晰的两两对比。

一个符合四重职责的 description 示例：

```yaml
name: record-note
description: >
  创建轻量日常记录文件，保存想法、备忘或待办。
  当用户希望快速保存当前想法且未要求讨论、整理归档或查询已有记录时使用。
  查询已有记录应使用 record-search；正式归档应使用 document-archive；
  当用户同时表达"讨论"和"记录"意图时，优先判断为讨论场景。
```

这条 description 回答了全部四个问题：做什么（创建轻量记录）、何时用（快速保存、未要求讨论/归档/查询）、何时不用隐含其中（要求了讨论/归档/查询）、如何区分（显式引用 record-search 和 document-archive 并给出优先判断规则）。

一个常见的误区是**把 description 写成功能列表**——"此 Skill 支持创建、编辑、删除、归档文档"。这种写法的问题在于：它没有告诉 LLM 什么时候该选这个 Skill 而不是其他 Skill。在 50 个 Skill 的候选池中，功能列表没有区分度——很多 Skill 都可以声称自己"支持文件操作"。description 的价值不是罗列能力，而是画出边界。

##### 2.2 意图模式优于例句穷举

很多 Skill 作者有一个直觉：例句越多，命中越准。于是 description 里塞了大量例句——"记一下""备忘""保存这个话题""写下来""存一下""mark 一下"……但问题在于，用户永远有新的说法，而例句穷举本质上是用过去见过的模式去硬匹配未来的变体。

意图模式提供了另一种思路：不给 LLM 例句，而是给它一个判断框架。比如："以简短指令形式要求存储一段信息，且未指定存储格式或存储位置时，匹配此 Skill。"这个框架不依赖任何具体措辞——用户说"帮我记个东西""存一下刚才说的""这个留着后面看"，框架都能覆盖。LLM 的推理能力强于匹配能力——给它规则让它推理，比给它例子让它匹配，容错性更高、泛化性更强。

实操建议：从 20 条例句中提取 3 条意图模式。提取的方法是：将例句按用户意图做聚类，然后对每一类写一条模式描述。比如 20 条例句可以聚类为三类——"快速记录型"（记一下、备忘、写下来）、"指定内容型"（把这个存起来、刚才那段话保存）、"延迟处理型"（先留着、后面再看）——然后对每一类写一条意图模式，用"或"逻辑连接放入 description 的"何时使用"段。这 3 条意图模式覆盖的范围，比 20 条例句大一个数量级。

##### 2.3 互斥引用：用对比判断替代绝对判断

在 Skill 命中率的内容层手段中，互斥引用是投入产出比最高的——往往只需要在 description 中加一两句区分规则，就能解决两个 Skill 之间反复误触发的顽疾。它的原理基于一个对 LLM 行为模式的观察：LLM 的对比判断力显著强于绝对判断力。单独判断"这个 Skill 是否匹配当前用户输入"时，LLM 容易犹豫和出错；但如果同时给它两个相近的 Skill 并问"哪一个更匹配"，LLM 的判断精度会大幅提升。[实践观察] 互斥引用的作用，就是在 description 中显式构造这种对比场景。

具体做法是：在 Skill A 的 description 的"何时不用"或"与相近 Skill 如何区分"段中，明确引用 Skill B 并说明区分规则；反之亦然。例如，假设有两个 Skill——一个负责"查看已有记录"，另一个负责"创建新记录"——两者的触发条件在"用户想看点什么"的场景下有重叠。在"创建"Skill 的 description 中写："查询已有内容时应使用 record-search，不应匹配本 Skill。"在 record-search 的 description 中写："创建、写入、保存新内容时应使用 record-create，不应匹配本 Skill。"这两条互斥引用一加，LLM 在边界场景的判断就不依赖于模糊的全局评估，而是有明确的排除信号。

互斥引用的书写有几个注意事项。第一，引用对方时不要只写名字——要同时写出对方的核心功能描述，让 LLM 不需要去读对方的完整 description 就能理解分界。第二，区分规则要具体到"用户输入中同时包含 X 和 Y 时""用户意图偏向 Z 方向时"这个粒度，不要写"用途不同"这种没有信息量的区分。第三，引用要双向——单方面的引用只能让一方避开另一方，双向引用才能形成清晰的边界。

##### 2.4 skill name 对路由判断的影响

Skill name 是 LLM 在路由决策时看到的第一行信息，它的权重远高于大多数 Skill 作者的直觉。一个常见的误区是：认为 name 只是一个标识符，真正的匹配逻辑在 description 里——所以 name 可以起得随意一点、有创意一点。但在 LLM 的注意力机制下，位置靠前的信息天然获得更高的权重，而 name 字段在路由 prompt 中通常出现在最前面。[机制假设] 一个模糊的 name 会让 LLM 从一开始就带着偏差去读 description——这就像看了一篇文章的标题之后，正文的理解已经被标题框定了。

命名原则可以简化为两条。第一，功能性命名优于创意性命名——`record_create` 比 `QuickNote` 更好，因为前者直接传递了功能信息，后者需要 LLM 额外做一步"创意→功能"的翻译。第二，清晰度优于简洁度——`data_stash_manager` 比 `stash` 更好。但这不意味着 name 越长越好——关键是 name 中的每个词都承担了明确的功能区分作用。`skill_create_from_template` 中的 `from_template` 是关键的区分信息，不能省；但 `helper` 或 `util` 这样的通用后缀在大多数情况下不增加区分度，可以精简。

一个实用的命名策略是"域前缀 + 功能主体 + 区分后缀"三段式：域前缀标明 Skill 的归属领域（如 `doc`、`qa`、`browser`、`cron`），功能主体描述核心能力（如 `record`、`discuss`、`lookup`、`compliance`），区分后缀在同类 Skill 中提供区分度（如 `create`、`update`、`delete`、`export`）。这样，LLM 在看到 name 的第一刻就能完成粗粒度的领域归类，为后续的 description 精判提供正确的前提。[实践观察]

##### 2.5 负面信息：排除场景的价值

绝大多数 Skill 的 description 只写了正向信息——"这个 Skill 能做什么""什么时候该用它"。但 LLM 在路由决策时，最需要的信息往往是负面的——"这个 Skill 不能做什么""在哪些情况下绝对不要用它"。正向信息帮 LLM 缩小候选范围，但真正避免误触发的往往是负面信息。

负面排除的写法需要具体到场景级别："当用户输入中同时包含'讨论'和'记录'两个关键词时，优先判断用户意图是讨论而非记录——不应匹配记录类 Skill。"这里的要点是"同时包含 X 和 Y"——单条件排除太宽泛，会导致正常场景也被误排除；多条件组合排除则精确得多。

更系统的失败条件写法："在以下情况下，此 Skill 不应被匹配：①用户输入中包含明确的文件路径引用——文件操作应由文件管理类 Skill 处理；②用户输入以问号结尾且核心动词为'怎么''如何''为什么'——这属于咨询场景而非操作场景；③用户连续两次取消了此 Skill 的执行——这表明用户不认为此 Skill 是当前需求的正确选择。"这样的失败条件越具体，LLM 在路由时的误判率越低。

这些负面信息应写入 description 的"何时不用"段，作为互斥引用和意图排除规则的补充。

##### 2.6 description 写作模板

综合以上原则，以下是一个经过实践验证的 description 写作模板，按四重职责组织。

```yaml
name: <域前缀>-<功能主体>-<区分后缀>
description: >
  <做什么 — 1~2句描述核心功能和不做什么。>
  当<触发条件 — 意图模式，非例句列表>时使用。
  <何时不用 — 2~3条排除规则，含互斥 Skill 引用。>
  <区分 — 与相近 Skill 的区分规则，双向引用。>
```

展开示例：

```yaml
name: doc-record-create
description: >
  创建轻量日常记录文件，保存想法、备忘或待办——不涉及讨论、不涉及结构化归档。
  当用户以简短指令形式要求存储一段信息，且未指定存储格式或位置时使用——
  意图模式包括快速记录型（"记一下""备忘"）、指定内容型（"把这个存起来"）、
  延迟处理型（"先留着后面看"）。
  当用户同时表达讨论意图时应使用 doc-discuss；当用户要求查询已有记录时应使用
  doc-lookup；当用户要求归档整理时应使用 doc-archive。
  与 doc-discuss 的区别：本 Skill 处理纯记录意图，doc-discuss 处理讨论+整理意图；
  与 doc-lookup 的区别：本 Skill 写入新内容，doc-lookup 读取已有内容。
  当用户输入中同时包含"记录"和"讨论"时，优先判断为讨论场景。
```

这个模板直接对应了 description 的四重职责。Skill 作者按照这个结构填写，就能产出路由友好度远高于平均水平的 description。[实践观察]

关于模板的一个补充：有些人可能会问"description 是不是太长了"——在 Agent Skills 规范的 progressive disclosure 设计下，Discovery 阶段每个 Skill 只加载 name 和 description，不加载完整 SKILL.md。因此 description 的长度应在保证区分度的前提下尽量精简——通常 4–8 句话足以覆盖四重职责，远小于动辄几百行的 SKILL.md 正文。如果 description 膨胀到超过 150 个 token，往往说明里面混入了执行细节（应该放在 SKILL.md 正文中）或例句列表（应该用意图模式替代）。

#### 第二层：架构层 — Skill 体系的结构设计

当内容层的优化到达天花板——即每个 Skill 的 name 和 description 都已经按最佳实践写好，但命中率仍然不理想——瓶颈往往转移到了架构层。内容层优化的是单个 Skill 的信息质量，架构层优化的是 Skill 之间的组织方式。核心命题是：同样的 50 个 Skill，平铺在一个路由层和分层组织在一个树形结构中，路由精度可以有显著差异。

##### 3.1 大类包裹子 Skill

50 个 Skill 平铺在一个路由层的问题不是"LLM 看不过来"——LLM 的上下文窗口足够容纳 50 个 Skill 的元数据。真正的问题是语义混淆：50 个 Skill 中，有大量 Skill 共享相近的语义空间，LLM 在它们之间做选择时缺乏清晰的分类边界。大类包裹就是在这个层面提供分类边界：将 50 个 Skill 归入 5~8 个大类，每个大类作为一个一级路由入口，大类内部再路由到具体 Skill。

这个设计的决策核心是大类的粒度选择。粒度过粗——比如只有 2 个大类——大类内部的 Skill 数量依然很多，混淆问题没有实质性缓解。粒度过细——比如 15 个大类——大类之间的边界开始模糊，路由的第一级就出现了精度问题。最优粒度取决于 Skill 集合的自然聚类结构：如果 Skill 之间有明显的功能域划分（如"文档管理""浏览器操作""定时任务""问答咨询"），大类数量应等于自然功能域的数量；如果 Skill 的功能边界是连续的而非离散的，则需要做人为的切分并承担切分边界的模糊代价。

大类的 description 需要采用与普通 Skill 一致的写法——但内容应该更宽泛，覆盖整个功能域，同时必须与相邻大类的 description 形成明确的互斥。比如"文档管理"大类的 description 写"负责文档的全生命周期管理：创建、查看、修改、讨论、归档"，"浏览器操作"大类的 description 写"负责基于浏览器的网页交互：打开、导航、截图、内容提取"。两个大类在语义上几乎没有重叠，LLM 在它们之间做选择几乎不可能出错。大类之间的可区分度越高，一级路由的精度就越高，留给二级路由的候选空间就越干净。

一个常被忽略但至关重要的设计细节是：大类与子 Skill 的归属关系**不应是严格互斥的**。A 大类下可以有 a、b、c 三个子 Skill，B 大类下可以有 b、c、d 三个子 Skill——子 Skill b 和 c 同时属于两个大类。这种重叠设计直接回应了"一级路由选错大类，子 Skill 就永远没机会"的担忧：如果一级路由误选了 A 大类，但用户真正需要的实际上是 B 大类下的 d，虽无法命中；但如果用户需要的是 b 或 c，即便选错了大类，仍然能命中正确的子 Skill。

重叠设计的代价是增加了体系维护的复杂度——每个子 Skill 需要声明自己所属的所有大类，大类之间的边界也不再是清晰的分割线而是有交集的区域。但对于功能域边界天然模糊的 Skill 集合而言，这种复杂度是必要的。实际落地时，不需要所有子 Skill 都做多归属——只需要对那些"确实可以被合理归入多个大类"的 Skill 做重叠声明。一个实用的判断标准：如果一个子 Skill 在语义上距离两个大类的中心点都很近（相似度差距低于预设的相似度阈值，该阈值需在本地路由环境中校准），就值得做多归属。[经验参数]

##### 3.2 路由 Skill（纯转发）

路由 Skill 是一种特殊的 Skill：它不做任何业务逻辑，只做一件事——读取用户意图，然后调用正确的子 Skill。在架构上，路由 Skill 可以看作一个大类的入口——大类 Skill 本身就可以扮演路由 Skill 的角色。

路由 Skill 的核心风险是"抢夺效应"：如果路由 Skill 的 description 写得过于宽泛，它会在应该触发其他 Skill 的场景中被选中——路由 Skill 命中后把请求转发给子 Skill，就多绕了一圈，增加了延迟和出错概率。更糟的是，路由 Skill 可能"吞掉"本该由特定 Skill 直接处理的请求——比如用户明确说"帮我创建一个文档"，如果路由 Skill 先命中再转发给"创建文档"Skill，就比"创建文档"Skill 直接被命中多了一次转发的失败概率。

缓解措施的核心是路由 Skill 的 description 中必须明确优先级："仅在系统无法直接确定应调用哪个具体 Skill 时使用此路由 Skill。如果用户的意图清晰指向某个具体 Skill 的操作范围，应直接调用该 Skill 而非通过本 Skill 中转。"这段描述的作用是告诉 LLM：路由 Skill 是最后的手段，不是默认入口。但需要注意——这个优先级描述需要框架层面在路由 prompt 中强制执行，仅写在路由 Skill 的 description 里可能被 LLM 忽略。

##### 3.3 路由信息精简与子文档分离

在 Agent Skills 规范的 progressive disclosure 设计下，路由阶段（Discovery）只加载 name 和 description，完整 SKILL.md 在 Skill 被激活后才加载。这意味着 SKILL.md 正文的篇幅理论上不影响路由精度——前提是 description 确实只包含路由所需的关键信息。但实践中，部分 Skill 作者会把执行细节（子步骤、参数说明、错误处理、示例）塞进 description，从而使路由阶段的信息噪声增大。

因此，应做一次主动的精简：确保每个 Skill 的 description 严格限于四重职责（做什么、何时用、何时不用、如何区分），将子步骤、参数说明、错误处理、完整示例、模板等执行细节全部保留在 SKILL.md 正文中——这些内容只在 Skill 被选中后才加载，不参与路由阶段的匹配。

这个精简在提高命中率上的作用是间接但显著的：精简后的 description 让 LLM 在路由阶段看到的是高度浓缩的区分信息，信号密度大幅提升；同时路由 prompt 的总 token 数下降，让更多候选 Skill 可以被纳入列表而不突破上下文限制。注意，这依赖于 Agent 的执行纪律——Skill 被选中后必须主动读取 SKILL.md 正文（和关联子文档）才能正确执行。如果 Agent 的执行流程中没有"加载 Skill 后读取其关联子文档"这一步，精简 description 就会导致执行质量下降。因此，这一优化需要配套的流程约束。

##### 3.4 Gate 机制与 no_skill 基线

在所有架构层手段中，Gate 机制可能是收益最高但最容易被忽略的。它的核心洞察是：路由问题不应该被默认为"N 选 1"的分类问题——在路由之前，首先应该有一个二分类："是否需要调用任何 Skill？"

这个二分类问题的难度远低于 N 分类。在 N=50 的 Skill 集合中做选择，LLM 需要同时比较 50 个候选；但判断"用户是否需要任何 Skill"，LLM 只需要在"需要"和"不需要"两个标签之间做选择。许多看似"误触发"的案例，其实不是 LLM 选错了 Skill，而是 LLM 在不该选任何 Skill 的时候选了一个——比如用户只是说了句"好的，谢谢"，LLM 却触发了文档记录 Skill 试图把这句话存下来。Gate 机制在路由之前拦截这类请求，直接返回"不触发任何 Skill"。

no_skill 基线的价值在于：它为路由系统提供了一个"拒绝回答"的合理出口。没有 Gate 机制时，LLM 在路由阶段会默认"必须选一个"，这导致它即使在所有 Skill 都不匹配的情况下也会强行选一个最接近的——结果就是误触发。有了 Gate 机制，LLM 可以在第一步就判断"不需要 Skill"，从而避免后续所有可能的误触发。

Gate Skill 的 description 可以这样写："在所有 Skill 路由之前执行二分类判断：当前用户输入是否属于'需要调用任何 Skill 来处理'的范畴？如果用户输入为闲聊、确认、感谢、简单问候、纯信息性陈述等不涉及任务执行的交流，输出'no_skill'，不触发任何 Skill。仅当用户输入包含明确的操作意图——创建、修改、查询、删除、执行——或表达了需要系统协助完成某项任务时，输出'routed'，进入下一步路由。"

##### 3.5 兜底 Skill 的设计与风险

兜底 Skill 的定义是：当所有特定 Skill 都不匹配时，由兜底 Skill 接管请求。它的设计意图是好的——避免用户请求完全无人响应——但它的风险也非常真实：抢夺效应和退化效应。

抢夺效应是指兜底 Skill 的 description 过于宽泛，导致 LLM 在本该触发特定 Skill 的场景中也选择了兜底 Skill。因为兜底 Skill 的覆盖范围天然是所有 Skill 中最广的——"当没有其他 Skill 匹配时"——这个描述在语义空间中占据了一个巨大的区域，很容易侵蚀其他 Skill 的匹配空间。退化效应是指：一旦 LLM 发现兜底 Skill 可用，它可能倾向于减少对特定 Skill 的精细判断，直接走兜底路线——因为选兜底 Skill 的认知负担最低。

措辞技巧是抑制这两种效应的主要手段。兜底 Skill 的 description 必须使用限制性语言而非开放性语言。错误写法："当你不确定该调用哪个 Skill 时，使用此 Skill。"这个写法给了 LLM 一个退路——"不确定"是一个模糊的心理状态，LLM 可以在任何稍微有歧义的场景下宣布自己"不确定"然后走兜底。正确写法："当且仅当以下 Skill [列出所有特定 Skill] 的职责描述均不覆盖当前用户请求时，才使用本 Skill。如果用户的请求可以合理地归入上述任何一个 Skill 的职责范围，即使匹配度不是百分之百，也应选择该 Skill 而非本 Skill。"这个写法把"不确定"的判断标准从主观感受变成了客观枚举——LLM 需要先确认所有特定 Skill 都不匹配，才能选兜底。

兜底 Skill 的健康度应该用两个维度的指标来衡量：兜底调用占比 × 兜底后用户满意度。单独看兜底调用占比没有意义——占比 5% 可能意味着兜底 Skill 几乎没用，也可能意味着误触发极少。正确的解读是：兜底调用占比如果过高（比如超过 20%），说明大量本应被特定 Skill 处理的请求被兜底了——抢夺效应正在发生；兜底调用占比如果合理但是兜底后的用户满意度很低，说明兜底 Skill 本身的能力不足以处理被路由给它的请求——退化效应正在发生。两个指标交叉看，才能准确判断兜底 Skill 的健康状态。

##### 3.6 两层串行路由与一层平铺的精度分析

两层串行路由（先大类后子 Skill）和一层平铺（50 个 Skill 一起选）之间的精度差异，可以用一个简化的数学模型来理解。设总 Skill 数为 N，每个大类的子 Skill 数为 k（N = 大类数 × k）。在平铺路由中，LLM 需要在 N 个候选中做选择；在两层路由中，LLM 先在大类中做选择（选项数 = N/k），然后在选中的大类内做选择（选项数 = k）。

直观上，两层路由似乎总是优于一层平铺——"分而治之"嘛。但精度提升有一个关键前提：大类之间的可区分度必须显著高于大类内部 Skill 之间的可区分度。如果这个条件不成立——比如大类切得太细，大类之间的边界和大类内部的 Skill 边界一样模糊——两层路由不仅不提升精度，还可能放大错误：第一层选错大类，第二层在大类内部就不可能选对子 Skill。

实操上，两层路由的决策应该基于现有 Skill 集合的自然聚类结构，而非人为划分。评估方法：对 Skill 的 description 做两两语义相似度分析，如果确实形成了几个紧密的聚类——类内相似度高、类间相似度低——那两层路由几乎一定有正向收益。如果 Skill 的语义分布是均匀的而非聚类化的，强行分层只会引入额外的分类错误。因此，两层路由的适用前提不是"Skill 数量多"，而是"Skill 之间有清晰的功能域边界"。

#### 第三层：引擎层 — 检索与排序的框架能力

当内容层和架构层的优化都已经到位，进一步压榨命中率就需要深入到框架层面——检索和排序的算法能力。这一层的优化不再是个体 Skill 作者能独立完成的工作，而是需要框架开发者介入的系统级改造。

##### 4.1 命中率的三段拆解

将 Skill 命中率按时间顺序拆解为三个阶段，是定位瓶颈的关键方法论。

第一阶段：检索召回。框架的检索器根据用户输入，从全量 Skill 池中拉出一个候选列表。这个阶段的核心问题是：正确的 Skill 在不在这个候选列表里？如果不在，后续的排序和执行都无从谈起。提高召回率的手段包括扩展检索字段、引入混合检索、提升 embedding 质量等。

第二阶段：排序质量。候选列表中有正确的 Skill，但它排在什么位置？如果正确 Skill 排在候选列表的第 15 位，而 LLM 在路由 prompt 中只认真看了前 5 个，那等于召回失败。排序质量的核心指标是正确 Skill 在候选列表中的排名——MRR（Mean Reciprocal Rank）和 NDCG 是常用的衡量指标。

第三阶段：执行成功。正确 Skill 在候选列表中排在第一位，LLM 也确实选中了它，但 Skill 内部的执行步骤是否成功完成？这个阶段的失败通常与路由无关——问题出在 Skill 内部的逻辑、前置条件检查、参数传递或子步骤编排上。但它仍然会影响端到端的命中率统计，因此在优化时不能忽略。

三段是串行依赖关系：召回失败则排序无从谈起，排序失败则执行没有机会。优化优先级也遵循这个串行逻辑——先确保召回率达标（正确 Skill 在候选列表中的概率足够高），再优化排序质量（正确 Skill 排在靠前位置的概率足够高），最后再处理执行成功的问题。任何一个阶段的优化，收益上限都被前一个阶段的表现所限制。

##### 4.2 Skill 元数据字段与宿主侧检索索引

在 Agent Skills 开放规范中，标准 Skill 元数据仅包含 `name` 和 `description` 两个必填字段。这是跨框架互操作的最小公约数——任何符合规范的 Agent 框架都可以基于这两个字段完成路由。

但在宿主框架层面（以 QwenPaw 或其他具体实现为例），可以为检索和路由目的扩展额外的元数据字段。这些字段不属于 Skill 文件规范的一部分，而是宿主侧构建的检索索引。明确区分这两层是重要的：标准元数据保证跨框架可移植，宿主侧索引服务于特定框架的检索能力。[框架特定]

以下是在宿主侧检索索引中可扩展的字段及其检索价值：

- input_schema：Skill 需要的输入参数类型和结构。检索价值在于——如果用户输入中包含了特定结构的信息（比如一个文件路径、一个日期范围），可以通过 input_schema 快速匹配到需要这些参数的 Skill。
- output_schema：Skill 产出的输出格式。检索价值在于——如果用户的措辞暗示了期望的输出形式（比如"给我一个表格""列一个清单"），可以匹配 output_schema。
- negative_examples：明确不应该匹配此 Skill 的输入示例。价值已在前文详述。
- failure_conditions：Skill 执行可能失败的先验条件。检索价值在于——如果用户的输入场景已知会导致某些 Skill 失败，可以在路由阶段就排除这些 Skill。
- related_skills：与此 Skill 功能相邻的其他 Skill 列表。检索价值在于——当此 Skill 被命中时，related_skills 中的 Skill 可以被提升权重或加入辅助候选。
- capability_tags：Skill 能力标签（如"文件操作""网络请求""数据库查询""UI 交互"）。检索价值在于——作为结构化字段参与精确匹配和过滤。
- dependency_tags：Skill 的依赖声明（如"需要浏览器""需要文件系统权限""需要数据库连接"）。检索价值在于——如果当前环境不满足某个 Skill 的依赖条件，该 Skill 应被直接排除。

扩展检索索引的代价也是真实存在的：增加了存储成本、增加了索引构建时间。因此不是所有字段都适合放入路由 prompt。一个务实的策略是：完整索引存储在数据库中供检索使用；路由 prompt 中只放入 name 和 description；其余字段按需在 Skill 被选中后加载。

##### 4.3 混合检索：多字段加权匹配

纯语义检索（将 name 和 description 拼接后计算 embedding，与用户输入做余弦相似度匹配）在大多数场景下是一个合理的基线，但它有一个结构性缺陷：所有字段被等权重地压成了一个向量，丢失了字段级别的区分信息。name 字段的匹配度在语义上通常比 description 中其他部分的匹配度更重要——name 是 Skill 的高度浓缩标签——但纯语义检索无法体现这种差异。

混合检索解决的就是这个问题：不同字段被赋予不同的权重，最终相似度是各字段加权分数的组合。权重的具体取值需要根据本地路由环境和 Skill 集合特征进行校准，以下为一个初始参考值：name 权重最高（作为 Skill 的高度浓缩标签），description 中"做什么"和"何时使用"段次之（核心功能匹配），互斥引用和排除段再次之（边界判定信息）。[经验参数]

权重调优的方法有两种。轻量级方法：从路由日志中采样 200~500 条真实查询，人工标注正确 Skill，然后用网格搜索在评测集上找最优权重组合。重量级方法：如果标注数据足够（1000+ 条），可以用 learning to rank 训练一个小模型来学习最优的特征组合权重——特征可以包括各字段的语义相似度、关键词匹配数、Skill 的历史命中率、Skill 的使用频率等。

关键提醒：任何固定权重都是训练数据上的局部最优，迁移到不同的 Skill 体系、LLM 模型版本或用户群体后，必须重新校准。不应将特定权重组合当作通用经验法则使用。

##### 4.4 LLM 精排：从向量粗筛到语义精排

混合检索提升了召回的候选质量，但它仍然是基于"向量相似度"这一定量指标在排序。向量相似度有一个根本性的局限：它衡量的是文本的语义接近程度，但路由需要的是"功能匹配度"——用户说"帮我看看昨天的记录"，向量相似度可能把"查看历史"和"查看昨天天气"排在相近的位置，因为它们都包含"查看"和"昨天"，但功能匹配度显然完全不同。

LLM 精排的引入就是为了跨越这个鸿沟。两阶段流水线的工作方式是：第一阶段用混合检索从全量 Skill 池中拉出 Top-K（比如 K=15）的候选列表；第二阶段用一个专门的路由 LLM（可以是更轻量的模型）对这 15 个候选做逐对比较，输出排序后的列表。主 Agent 拿到的不是 50 个 Skill 的列表，也不是 15 个按向量相似度排列的列表，而是 15 个经过语义校验后的排序列表——正确 Skill 大概率在前 3 位。

精排 prompt 的设计要点：pairwise 比较优于 pointwise 打分。Pointwise 打分的思路是"给每个候选 Skill 打分，按分数排序"——LLM 在做这件事时缺乏参照系，打分的一致性很差（同一个 Skill 在不同上下文中可能被打出差异巨大的分数）。Pairwise 比较的思路是"对于候选 A 和候选 B，哪一个更匹配当前用户输入？"——LLM 在做两两比较时表现远好于独立打分。将 pairwise 的结果聚合为全排序有成熟的算法（如 mergesort 风格的插入排序），复杂度是 O(K log K) 次比较。

精排的触发决策也是重要的设计考量：不是每次路由都需要精排。如果混合检索的 Top-1 相似度分数显著高于 Top-2（差距超过预设的置信阈值），说明混合检索已经足够置信，可以跳过精排。只有当前几名候选的相似度分数接近时（差距小于阈值），才触发精排做更细致的区分。这个阈值的具体取值需在本地评测集上校准——目标是找到精排成本和误判损失之间的平衡点。[经验参数] 可以在保证精度的同时控制精排的延迟和成本。

##### 4.5 动态候选列表长度

固定 Top-K 的问题在于 K 的大小是一个全局参数，但不同查询的候选分布差异巨大。对于"帮我创建一份报告"这种高度聚焦的查询，Top-3 可能就已经包含了所有合理候选；对于"帮我处理一下那个东西"这种极度模糊的查询，Top-20 可能都找不到正确 Skill。

自然断崖切分法提供了一个动态的解决方案：不预设固定的 K，而是计算候选列表中相邻 Skill 之间的相似度分数差值。从第一名开始往下扫描，当遇到一个"断崖"——即当前 Skill 的分数与下一个 Skill 的分数差距超过预设的断崖阈值——就在断崖处切分，只保留断崖以上的候选。阈值的选择需要在评测集上做校准。阈值设得太低，断崖切分过于激进——可能只保留 1~2 个候选，但正确 Skill 因为语义相近排在第三位而被切掉。阈值设得太高，断崖切分退化为固定大 K——候选列表依然很长，精排成本没有下降。实践中的建议是：从本地评测集上选择一个初始阈值，观察正确 Skill 被切掉的频率；如果切掉率过高，下调阈值；如果候选列表长度仍然偏大，上调阈值。这个调参过程应该在评测集上进行，而非在线上直接试错。[经验参数]

动态候选列表的额外收益在于：候选列表的长度本身可以作为一个置信度信号。如果候选列表只保留了 1 个 Skill（说明 Top-1 与 Top-2 的差距超过了断崖阈值），这个路由决策的置信度就很高，可以跳过精排，直接返回 Top-1。如果候选列表保留了 10 个 Skill，说明前 10 名的相似度分数都很接近，需要精排介入做更细致的区分。

##### 4.6 自动化评测闭环

没有评测的命中率优化，本质上是盲调。开发者改了一个 desc、调整了一个权重、引入了一个新的路由规则，然后凭感觉判断"有没有变好"——这种方法在命中率 60% 的阶段可能有短期收益，但一旦命中率推到 85% 以上，边际改进就完全不可感知了。自动化评测闭环就是在这一点上改变游戏规则。

评测集的构造方法并不神秘：从路由日志中采样真实用户查询，按时间窗口或随机采样均可，数量视 Skill 规模而定——50 个 Skill 的体系建议 500~1000 条查询。对每条查询，人工标注"正确应该触发的 Skill"。如果存在边界模糊的场景（两个 Skill 都可以算正确），标注为"任一命中即可"。评测集构造完成后，需要按 8:2 或 7:3 的比例拆分为训练评测集（用于调参和优化）和保留评测集（用于最终验证，避免过拟合）。

评测指标的选择需要覆盖命中率链路的三个环节。Recall@K 衡量检索召回——K 通常取 5、10、15，Recall@K 越高说明正确 Skill 越大概率出现在候选列表中。MRR（Mean Reciprocal Rank）衡量排序质量——正确 Skill 排在候选列表的第几位。NDCG（Normalized Discounted Cumulative Gain）也衡量排序质量，但能区分"正确 Skill 排第 1 位且独一"和"正确 Skill 排第 1 位但第 2 位也差不多正确"的区别。End-to-End Hit Rate 是最终指标——LLM 在拿到候选列表后实际选了正确的 Skill 的概率。这个指标最接近真实用户体验，但受 LLM 的随机性影响，需要多次运行取平均值。

评测驱动的优化循环可以这样设计：①在训练评测集上运行当前路由系统，记录所有误判案例；②按误判类型聚类（未触发、误触发、串扰、空转），找到最高频的误判模式；③对最高频误判模式做针对性修复——内容层改 description，架构层调整大类划分或 Skill 归属，引擎层调权重或精排 prompt；④重新评测，验证修复效果；⑤在保留评测集上验证没有退化。这个循环的周期可以短到半天——上午发现问题，下午修复并验证。持续运行这个循环，命中率会呈现稳定的单调上升趋势。

评测驱动还有一个重要但容易被忽视的用途：反向优化 description。当评测数据积累到一定规模后（数千条查询），可以统计每个 Skill 的"被误触发"和"被漏触发"的模式。比如发现"记录 Skill"在高频词为"保存"的查询中被误匹配——这说明 description 中"保存"附近缺少足够的限定条件或排除规则，需要收紧。这种从统计数据到 description 修改的反馈链路，在纯人工优化的流程中几乎不可能实现，但评测闭环让它可以作为一个标准操作来执行。

##### 4.7 多层父子关系与任意层级接入检索

两层路由（大类 → 子 Skill）在大多数场景下足够用，但真实场景可能需要更深的层级——比如大类下有中类，中类下有具体的 Skill，具体 Skill 还有变体。多层父子关系对检索架构的挑战在于：子 Skill 是独立参与初始检索，还是只在父 Skill 被命中后才进入候选池？

两种策略各有利弊。独立参与检索：子 Skill 的触发机会最大化——即使用户的用词没有命中父 Skill 的大类描述，只要子 Skill 本身的 description 与用户输入匹配，就能被检索到。问题在于增加了候选池的噪声——大量细粒度 Skill 在初始检索中竞争注意力，削弱了粗粒度入口 Skill 的区分信号。只在父 Skill 命中后加入：候选池更干净，一级路由的精度更高。问题在于如果父 Skill 没有被正确命中，子 Skill 就完全没有机会——一级路由成为单点故障。

一种折中策略是：所有 Skill 都参与初始检索，但层级信息作为检索排序的附加特征。具体来说：父 Skill 命中时，其所有子 Skill 在排序中被提升权重（比如相似度分数乘以 1.2 的 boost 因子）；子 Skill 的初始检索分数不受影响，但如果它所属的父 Skill 也在候选列表中且排名靠前，子 Skill 的排名会被进一步拉高。这个策略的好处是：不会因为父 Skill 没有被命中而彻底丢失子 Skill；同时父子关系的信息被用来增强排序信号，而非作为绝对的过滤条件。

任意层级接入检索是指：用户可以从任意层级进入 Skill 体系——不需要从根节点开始一层层往下匹配。这要求框架的检索器在索引时保留完整的层级路径信息，并在检索时能够从任意层级匹配。实现上并不复杂：在 Skill 的 meta body 中增加一个"hierarchy"字段，记录从根到当前 Skill 的完整路径；检索器的索引中包含这个字段，允许任意层级的 Skill 参与初始匹配；路由 prompt 中保留层级关系信息，帮助 LLM 理解候选 Skill 之间的父子关系，做出更准确的选择。

与 3.1 节讨论的大类包裹同理，多层父子关系中的归属也不应要求严格互斥。一个子 Skill 可以同时属于多个父节点——Skill 的分类天然存在模糊地带，强制互斥只会制造误判。框架在索引时，将子 Skill 关联到其声明的所有父节点路径上；检索时，任一父节点被命中均可激活该子 Skill。这一设计将"一级路由选错父节点"的代价从"直接失败"降级为"仍有机会"，是对串行误差放大问题在结构层面的直接回应。

### 实现方案

#### 5.1 用户行为反馈闭环

评测集提供了稳定的离线优化信号，但评测集有一个根本性的局限：它永远是过去的快照。用户行为的变化、Skill 的增删、新使用场景的出现——这些动态因素评测集覆盖不到。用户行为反馈闭环就是在线上的实时补充：从用户与系统的交互中提取路由质量的信号，反馈回路由系统形成持续优化。

高置信度的反馈信号包括：用户在执行过程中主动取消 Skill（说明路由可能选错了）；用户在 Skill 执行完成后立即手动切换到另一个 Skill（说明路由确实选错了）；用户对同一需求重复发指令（说明上一次执行结果不符合预期——可能是路由问题也可能是 Skill 内部问题）；用户在对话中明确否定路由结果（"不对，我不是要这个"——这是最强的负反馈信号）。

反馈闭环的设计需要平衡信号的及时性和稳定性。实时反馈（每次用户取消或切换 Skill 都立即调整路由参数）虽然反应快，但容易受到偶然波动的影响——用户可能因为误触而取消，也可能因为改变主意而切换 Skill。批量反馈（积累一定量后再统一分析调整）更稳定，但反应滞后。实践中常用的策略是：实时收集反馈，按天或按周做批量分析；对于极高置信度的信号（如用户明确说"不对"），可以触发即时的人工 review 而非自动修改。

反馈信号的结构化存储也很关键。每条反馈至少应记录：用户输入的原始文本、路由系统选中的 Skill、用户最终实际使用的 Skill（如果切换了的话）、用户的显式反馈内容（如果有的话）、时间戳、会话上下文摘要。这些结构化数据不仅是路由优化的输入，也是评测集更新的来源——可以将高质量反馈案例直接补充进评测集。

#### 5.2 Skill 描述的语言一致性问题

不同 Skill 作者有不同的写作风格：有人喜欢用短句和列表，有人偏好复杂从句和长段落；有人倾向用动词开头，有人习惯用名词短语。这些风格差异在单个 Skill 内部不是问题，但当 50 个 Skill 的 description 放在同一个路由 prompt 中时，风格差异就变成了路由噪声——LLM 可能会被某个 Skill 更醒目的措辞风格吸引，而非基于功能匹配度做判断。

解决思路分为两个层面。第一个层面是模板约束——所有 Skill 的 name 和 description 必须遵循统一的模板结构（如 2.6 节描述的格式），这从源头控制了结构的差异性。第二个层面是自动检查——使用 LLM 或规则引擎对所有 Skill 的元数据做一致性扫描：description 的四重职责是否完整覆盖？互斥引用是否双向？术语使用是否一致（同一个概念在不同 Skill 中是否用了不同的词）？这些检查可以在 Skill 提交时自动运行，不符合标准的 Skill 被拦截或标记为需要修改。

#### 5.3 Skill 的确定性等级

并非所有 Skill 都需要走语义路由。有些 Skill 的触发条件是高度确定性的——比如一个"读取当前时间"的 Skill，用户说"现在几点了"和"当前时间"这两个变体就覆盖了 95% 以上的触发场景，用关键词精确匹配就足够了。把它放入语义路由的候选池，反而可能因为语义上与其他 Skill 的偶然相似而导致误触发。

确定性等级的三级划分：高确定性 Skill 走规则引擎——关键词匹配、正则匹配、或简单的 if-else 逻辑；中确定性 Skill 走混合路由——规则优先，规则未命中时回退到语义检索；低确定性 Skill 走纯语义路由——完全依赖 embedding 检索和 LLM 精排。确定性的判断标准可以基于 Skill 的触发词空间大小：触发词空间小且边界清晰 → 高确定性；触发词空间中等但意图模式可描述 → 中确定性；触发场景高度多变且边界模糊 → 低确定性。这个分级可以在 Skill 的 meta body 中用"certainty_level"字段标记，框架在路由时根据确定性等级选择不同的路由策略。

#### 5.4 优先级排序与实施路径

将三层的所有优化手段按投入产出比排列，可以得到一条清晰的实施路径。

第一阶段（零成本，当天可做）：部署 Gate 机制。增加一个二分类判断——"需要 Skill 还是不需要 Skill"——几乎不需要改动任何现有 Skill 的代码，只需在路由 prompt 的前端加入 Gate 判断逻辑。收益是立即消除所有"不该匹配时匹配了"的误匹配。

第二阶段（低成本，数天可做）：重写所有 Skill 的 description。按 2.6 节的模板统一重写，重点放在四重职责覆盖、意图模式替换例句、互斥引用补全和负面排除规则。需要投入的时间取决于 Skill 数量——50 个 Skill 大约需要 2~3 天的集中重写时间。收益取决于当前 description 的质量水平——质量越低，重写收益越大。

第三阶段（中成本，1~2 周）：搭建评测集和自动化评测流水线。从路由日志中采样、人工标注、构造训练集和保留集、搭建评测脚本。一次性投入后形成可持续运行的评测能力。评测本身不直接提升命中率，但它让后续所有优化都变得可量化、可验证——间接收益巨大。

第四阶段（中高成本，2~4 周）：分层路由改造。评估 Skill 的自然聚类结构，构建大类 Skill，实施两层路由（先大类后子 Skill）。同时精简 description，将执行细节保留在 SKILL.md 正文中。收益取决于 Skill 集合的聚类结构——类间区分度越高，分层收益越大。

第五阶段（高成本，持续迭代）：检索增强——引入混合检索、动态候选列表、LLM 精排、多层父子关系检索。这是框架层面的改造，需要框架开发者介入。收益在第四阶段基础上仍有提升空间。

各阶段的收益不是简单相加——后续阶段的收益是在前序阶段打下的基础上实现的。如果跳过前三个阶段直接做检索增强，效果会被劣质的 description 和不清晰的架构信号所限制，最终收益远低于预期。所有阶段的收益预估都依赖于具体的 Skill 集合、LLM 模型和用户行为分布，实际效果应在本地评测集上验证。[经验参数]

#### 5.5 衡量指标体系

Skill 命中率优化需要一个多维度的指标体系，而非单一的"命中率"数字。

核心指标只有一个：端到端命中率（End-to-End Hit Rate），即用户发起请求后正确 Skill 被选中并成功执行的比率。这个指标直接对应用户体验，是最重要的北极星指标。

过程指标有三个，分别对应命中率的三段拆解：Recall@K（检索召回）、MRR（排序质量）、LLM Selection Accuracy（LLM 在候选列表中选择正确 Skill 的概率）。过程指标的价值在于定位瓶颈——核心指标下降时，通过过程指标可以快速判断问题出在召回、排序还是执行阶段。

健康度指标用于监控系统的长期运行状态，而非衡量短期的优化效果。包括：Gate 拒绝率（被 Gate 判定为"不需要 Skill"的请求占比，反映了系统是否有过度触发的问题）、兜底 Skill 调用占比 × 满意度（兜底 Skill 的健康度）、误触发率（路由到错误 Skill 后用户取消或纠正的比率）、Skill 使用分布熵（衡量 Skill 调用是否集中在少数 Skill 上——熵过低说明大量 Skill 从未被触发，可能是 desc 写得不好或 Skill 本身价值存疑）。

指标之间的权衡也是必须考虑的。提高召回率的手段（扩大候选列表、放宽匹配阈值）往往会降低排序质量——候选列表变大，正确 Skill 的排名可能下降。提高精排投入（更多 LLM 调用、更长的精排 prompt）会提升排序质量，但增加延迟和成本。因此，指标体系不是用来单一最大化的，而是用来在多目标之间找到平衡点的——确定可接受的延迟上限后，在这个上限内最大化端到端命中率。

### 总结

Skill 命中率优化是一个看似简单实则纵深极深的问题。它的核心洞察可以归结为三点。

第一，Skill 命中率不是单一问题，而是"描述→路由→检索→执行"四环节的串行链路，任何一个环节的薄弱都会拉低整体表现。优化时必须拆解链路、定位瓶颈、逐个击破——用 Recall@K 判断检索是否召回，用 MRR 判断排序是否合理，用端到端命中率判断全链路是否通畅。

第二，三层递进框架的核心价值在于让优化工作有章可循。内容层是地基——name 和 description 写不好，架构再精巧、检索再智能也无济于事。架构层是骨架——Skill 的组织方式决定了路由空间的复杂度上限。引擎层是肌肉——检索和排序的算法能力决定了在给定的复杂度下能达到的精度上限。三层各司其职，不可互相替代。

第三，从第一层开始，从今天能做的事开始。Gate 机制几乎零成本，description 重写只需要 Skill 作者的投入，评测集构建是一次性投入但长期受益。这些前两层的工作不需要等框架支持、不需要等团队协调——任何一个 Skill 作者、任何一个 Agent 开发者都可以在今天动手。

最终建议是务实而直接的：先建立 Gate 机制消除不需要 Skill 时的误触发；再集中精力重写所有 Skill 的 name 和 description，把内容层做到极致；然后搭建评测体系让后续优化可量化；最后根据评测瓶颈决定是先做分层路由的架构改造，还是推动框架层面的检索增强。三层不是理论框架，是一张可以按步骤执行的任务清单。

## 知识缺口

以上内容覆盖了 Skill 命中率优化的三层方法论框架，但以下方向因篇幅和深度限制未充分展开，可作为后续深入探讨的主题：

- **各框架路由机制横向对比**：LangChain 的 Tool Selection、AutoGen 的 Skill Routing、CrewAI 的 Task Delegation、OpenAI Agents SDK 的 Tool Choice 等主流框架在路由机制上的具体实现差异和适用场景——以上仅做了通用方法论层面的讨论，未做框架级代码对比。
- **Learning to Rank 的具体落地**：混合检索中 L2 层 learning to rank 的特征工程、模型选择（LambdaMART vs 神经网络 ranker）、训练数据构造和冷启动策略未详细展开。
- **实验数据与 benchmark**：文中的精度提升估算基于经验推理，未提供真实系统的 A/B 测试数据或公开 benchmark。不同 Skill 体系、不同 LLM 模型、不同用户群体的实际收益可能存在显著差异。
- **反馈闭环的工程实现**：用户行为信号的自动采集管道、信号置信度评分模型、反馈到路由参数的自动更新机制等工程细节未展开。
- **精排 prompt 的完整设计**：LLM 精排的 pairwise 比较 prompt template、排序聚合算法（如 mergesort 插入排序）的具体实现、精排 LLM 选型的成本-延迟-精度 tradeoff 分析未详述。
- **多层父子关系的 Schema 设计**：hierarchy 字段的标准化格式、跨层级权重传递的数学定义、环形依赖和重复引用的检测机制未设计。
