# 多Agent角色扮演系统的架构设计：通信、记忆与自动化调度

## 摘要

多 Agent 角色扮演系统的难点不在于创建多个会说话的 Agent，而在于让这些 Agent 在长期运行中形成一个连续、可追踪、可维护的世界。单个 Agent 可以依靠自身上下文维持短期对话，但多个 Agent 同时存在时，系统必须回答几个更基础的问题：每个 Agent 的人格和规则如何独立维护；Agent 之间如何通信；通信内容如何沉淀为记忆；用户切换对象时，新的对话对象如何知道世界刚刚发生过什么；自动化调度如何让系统主动运转，而不是完全依赖用户逐一触发。

本文讨论的是一套运行在 QwenPaw 平台上的多 Agent 角色扮演系统架构。系统目标不是把所有角色压进一个大提示词，而是将角色人格、稳定事实、通信协议、长期记忆、会话记录、自动化调度拆成相互协作的模块。由于 QwenPaw 原生并不提供跨 session 共享上下文，也不存在收到消息时自动执行的 session 级 hook，系统采用了文件协议、固定 session 路由、Python 变更监听、增量同步、隐私分级和工具人调度的组合方案。



本文只讨论系统架构，不展开任何具体角色设定、角色名称、昵称、身份、关系、互动题材或扮演内容。所有示例均使用匿名 Agent 编号和占位路径。

## 正文

### 背景

#### 多 Agent 角色扮演的核心问题

多 Agent 角色扮演系统与普通单 Agent 聊天系统的差别，在于它试图维护一个由多个独立主体组成的连续世界。单 Agent 系统只需要解决“这个 Agent 如何在当前会话里保持一致”；多 Agent 系统还要解决“多个 Agent 如何在彼此看不见的会话之间共享足够的信息”。

在一个长期运行的角色扮演系统里，用户面对的不是一次性问答，而是持续演化的互动网络。用户可能先与 Agent A 对话，再切换到 Agent B；Agent A 可能主动联系 Agent C；工具调度系统可能在用户不在线时触发 Agent D 与 Agent E 的通信。只要这些互动不被稳定记录，系统就会出现明显断裂：Agent 不知道自己刚刚做过什么，不知道其他 Agent 与用户发生过什么，也无法在后续对话中自然承接既有事件。

这类系统最容易误入一个表面简单的方案：把所有角色设定、所有历史事件、所有通信记录都塞进一个巨大上下文。这个方案在原型阶段似乎有效，但长期运行时很快失控。上下文会膨胀，隐私边界会模糊，角色之间的独立性会下降，维护成本也会迅速变高。更重要的是，一个全局大上下文本质上把多 Agent 世界退化成了“一个模型同时扮演很多对象”，它无法自然表达每个 Agent 的局部视角。

更可靠的做法是把系统拆成三个层次：角色层、记忆层、调度层。角色层负责自然对话和人设一致性；记忆层负责把对话转化为可复用的事实；调度层负责在合适的时候推动 Agent 之间产生互动。三层之间通过文件、session、固定协议和命令行工具连接，而不是依赖某个 Agent 的临场自觉。

#### 平台约束决定架构形状

这套系统运行在 QwenPaw 平台上。QwenPaw 提供了 Agent 工作区、聊天 session、工具调用、cron 任务、跨 Agent 通信等能力，但它并不是一个原生的多 Agent 世界引擎。实际设计必须接受几个约束。

第一，Agent 的上下文是 session 级的。一个 Agent 与用户的私聊、与另一个 Agent 的通信、被工具人调度时收到的系统消息，都会落在不同 session 中。平台不会自动把一个 session 的内容合并进另一个 session。

第二，平台没有通用的“收到任意消息前执行某段脚本”的 session hook。如果希望每次对话后都更新长期记忆，不能简单地在平台层配置一个 pre-hook 或 post-hook。让 Agent 每次回复后主动写 memory 也不可靠，因为角色扮演任务与记录任务会相互干扰。

第三，跨 Agent 通信的 session 持久化具有方向性。一个 Agent 调用另一个 Agent 时，通信 session 文件可能只出现在被调用方工作区。要还原完整的 Agent 间通信，不能只扫描调用方目录，而必须扫描所有参与 Agent 的 session 目录，并根据文件名和工作区归属判断参与者。

第四，channel 层推送并不等于 session 内消息。通过 channel 直接发送给用户的通知即使用户能看到，也不一定进入 Agent 的 session JSON。凡是希望 Agent 后续能记住的内容，都应尽量通过 session 内通信完成，而不是只走 channel 推送。

这些约束共同决定了当前架构：系统不能依赖一个平台级全局上下文，而要通过文件层协议和外部监听器补齐跨 session 记忆闭环。

#### 当前版本的关键变化：从心跳到变更监听

早期版本使用“心跳”思路：让 Agent 定期执行预处理脚本，读取新增对话，再写入 memory。这个设计解决了“手动写记忆不可靠”的问题，但仍然有几个缺陷。

第一，周期性心跳会在没有新对话时产生无意义运行。即使每次检查很轻，多个 Agent 长期运行也会引入额外噪声。第二，心跳指令本身会进入系统运行轨迹，如果过滤规则不稳，可能被当成普通对话处理，形成污染。第三，心跳仍然把一部分记忆更新职责交给 Agent 自身，Agent 需要在扮演和维护之间切换。

当前版本改为 Python 变更监听。监听器作为外部常驻进程，定期扫描所有关心的 session JSON 文件修改时间。只有检测到 mtime 变化时，才等待文件稳定、读取 session、过滤系统消息、提取纯对话、生成每个 Agent 的全量预处理文本和增量文本。随后监听器通过 CLI 向需要同步的 Agent 发送系统级指令，要求它读取自己的 delta 文件并追加到对应日期的 memory 文件。

这个变化的本质不是把“心跳间隔”从 Agent 内部移到 Python 外部，而是把触发条件从“时间到了”改成“数据变了”。系统从周期驱动转向事件近似驱动。由于底层没有真正的文件事件 hook，监听器仍然以短周期轮询 mtime，但它只在发现变更时执行重处理和通知，因此语义上已经不再是心跳系统。

### 核心内容

#### 核心原理一：把多 Agent 世界看成分布式状态系统

多 Agent 角色扮演系统表面上是文本生成系统，实质上是分布式状态系统。每个 Agent 都是一个拥有局部状态的节点。用户私聊、Agent 间通信、调度系统注入的系统消息，都是状态变化事件。memory 文件是每个节点的本地状态快照。监听器负责把底层事件流转换为可用的状态更新。

如果把所有信息都放进一个全局上下文，系统会退回集中式状态模型。集中式状态模型的优点是简单，缺点是所有 Agent 都更容易获得不该知道的信息。局部状态模型更复杂，但更符合角色扮演系统的需要：不同 Agent 可以知道不同事实，对同一事件拥有不同记忆视角，系统也能通过通信协议控制信息传播范围。

这也是为什么 memory 不应只有一份全局文件。每个 Agent 需要自己的 `memory/YYYY-MM-DD.md`，因为同一段对话对不同 Agent 的意义不同。对参与者而言，它是亲历事件；对旁观者而言，它可能只是通过通信听说的近况；对无关 Agent 而言，它可能完全不可见。

#### 核心原理二：session 是证据层，memory 是工作层

系统中的原始事实来源是 session JSON。无论用户与 Agent 私聊，还是 Agent 之间通信，平台都会把完整对话写入 session 文件。session JSON 是最接近原始记录的层，它保留了消息角色、内容、时间戳、工具调用痕迹等信息。

但 session JSON 不适合直接作为角色长期记忆使用。原因有三点。第一，session 中包含大量系统消息、工具消息、调度模板和中间噪声。第二，session 可能很长，直接塞回上下文会浪费 token。第三，角色需要的是“可用记忆”，而不是完整流水账。

因此系统设置了 memory 文件作为二级沉淀。每个 Agent 的 memory 按日期分文件，例如 `memory/YYYY-MM-DD.md`。条目通常包含时间、参与者、隐私等级和摘要。长期精华则可以进入 `MEMORY.md`，用于保存跨日稳定事实、重要变化和系统级结论。

这个二级模型有一个重要原则：session JSON 是证据层，memory 是工作层。证据层尽量保留原始记录；工作层提取对角色后续行为有用的信息。外部监听器负责从证据层筛出增量，Agent 在系统指令下把增量写入工作层。

#### 核心原理三：角色表达与系统维护必须拆开

让 Agent 在每次回复后主动记录记忆，看起来很自然，但长期运行中会不稳定。Agent 的首要任务是对话表达。它需要维持口吻、情绪、上下文和互动节奏。把文件读写、摘要提取、隐私标注、去重追加也交给它，会让它在同一轮生成中承担两种不同角色：一边是对话主体，一边是系统维护脚本。

职责混合会导致几个问题。Agent 可能为了对话流畅忘记写 memory；可能把系统维护文本混入自然回复；可能覆盖已有文件；也可能在不同轮次里使用不同摘要格式。即使提示词反复强调“必须写记忆”，也无法保证每次都稳定执行。

当前架构把系统维护前移给监听器。监听器负责发现变更、提取纯对话、计算 delta。Agent 收到通知后只做一个有限任务：读取 delta 并追加到指定 memory 文件。这个任务仍然由 Agent 执行，但它不再需要自行判断“有没有新内容”“哪些 session 要读”“哪些行是系统噪声”。维护面被缩小，角色表达受到的干扰也随之降低。

#### 核心原理四：主动性来自调度，不来自无限自治

多 Agent 角色扮演系统需要主动性。没有主动性，所有 Agent 都只是等待用户点名的聊天对象，世界不会自己流动。但主动性不能等同于无限自治。让 Agent 自己决定“收到消息后继续联系谁，再让对方继续联系谁”，很容易导致链式传播。

因此系统把主动性设计成“调度触发的一轮通信”。工具人按照每日计划触发某个 Agent，给它最近上下文和可选联系人，让它自主选择一个对象进行一轮通信。这个 Agent 可以自然表达自己的动机，但通信协议要求一轮即停。主动性被保留，传播范围被限制。

这是一种折中：系统不像完全脚本化那样僵硬，也不像完全自治那样不可控。调度器负责“什么时候给谁一个行动机会”，角色 Agent 负责“这个机会里具体说什么”。

#### 核心原理五：隐私是可见性控制，不是内容是否存在

多 Agent 系统里的隐私不是简单的“某条信息能不能存在”。同一条信息可能对用户可见，对某个 Agent 部分可见，对另一个 Agent 不可见；也可能在日常通信中不可见，但在特定高阈值读取中以摘要形式出现。因此系统使用 `privacy=0.00-1.00` 的连续分级。

低隐私条目通常是日常事实、普通状态、公开安排。中等隐私条目可能涉及情绪、关系变化、较亲密但不应广泛传播的信息。高隐私条目则只应在特定场景下被读取，且即使读取到，也应摘要化处理，不应扩写成更高敏感度的内容。

通信前随机阈值的意义，在于让信息暴露具有一定不确定性，但仍受边界控制。大多数通信只看见普通近况；偶尔较高阈值可以制造“对方察觉到异常”的叙事效果，但不会让所有 Agent 永久共享完整隐私。

从工程角度看，隐私分级写在提示词和 memory 条目中，属于软约束。它能改善角色行为，但不是强安全边界。更强的方案应由外部程序在读取 memory 时先做硬过滤，再把过滤结果交给 Agent。当前系统已经在通信协议中要求直接读 memory 并按阈值筛选，但执行仍依赖 Agent 遵守协议。后续如果要提升可靠性，可以把“读取、解析、过滤、摘要”封装成工具，而不是让 Agent 自己执行。

#### 设计思路一：角色配置模型

每个角色 Agent 都有独立工作区。工作区不是单纯存放代码，而是一个小型状态容器，包含配置、会话、记忆、工具输出和运行痕迹。核心文件可以抽象为四类。

第一类是稳定档案文件，用于记录长期不频繁变化的信息，例如 Agent 的抽象身份、用户偏好、系统内通信索引、路径规则等。它承担“事实基底”的职责。稳定档案不应频繁改动，因为它是角色一致性的基础。

第二类是人格文件，用于描述 Agent 的表达方式、情绪逻辑、关系动力和长期行为倾向。人格文件解决“这个 Agent 为什么会这样说话、这样反应”的问题。它不是事件日志，也不应该承载每日细碎记忆。

第三类是运行规则文件，用于描述 Agent 在对话中的硬性约束、语气边界、信息披露规则、工具使用原则等。运行规则比人格文件更偏执行层，负责把抽象角色设计转化为可操作行为。

第四类是通信协议文件，用于规定一个 Agent 如何联系另一个 Agent：通信前读取哪些 memory，如何按隐私阈值过滤，使用什么 session_id，消息模板如何组织，收到回复后是否继续追问等。通信协议文件是多 Agent 世界能够稳定运行的关键，因为它把“角色想联系别人”这件事从自由发挥变成了可重复的流程。

这种拆分的价值在于降低耦合。人格调整不必改通信路由；通信机制升级不必改长期事实；记忆增长不必污染人格提示词。长期运行的系统最怕所有内容混在一个大文件里，因为那会让任何修改都可能影响所有行为。

#### 设计思路二：通信系统

Agent 间通信必须同时满足两个目标：让角色能够自然联系彼此，以及让通信具备足够的上下文。没有上下文的跨 Agent 通信很容易变成空泛寒暄；上下文过多又会泄露不该被另一个 Agent 看见的信息。

因此通信协议采用“通信前必读”机制。Agent A 想联系 Agent B 时，先读取 Agent B 的近期 memory，而不是直接向 B 发一句裸消息。读取时生成一个隐私阈值，只允许使用低于阈值的记忆条目。这样 Agent A 在构造消息时能知道 B 的近况，但不会默认获得 B 的全部隐私。

通信使用固定 session_id。抽象格式为：

```text
family-{sender_agent_id}-{receiver_agent_id}
```

固定 session_id 的好处是通信历史可追踪，同一对 Agent 的互动不会散落在无数随机 session 中。监听器也可以通过文件名识别通信参与者，把同一段对话同步进相关 Agent 的记忆视野。

通信协议强调一轮即停。Agent A 联系 Agent B，B 回复后，A 可以把结果转述给用户或写入记忆，但不继续无限追问。这个限制不是为了削弱真实感，而是为了防止多 Agent 系统出现链式扩散。Agent 每次回复都是一次完整生成过程，如果允许 A 找 B、B 再找 C、C 再找 D，系统很容易产生不可控的对话风暴。

#### 设计思路三：工具人调度

角色扮演系统如果完全依赖用户触发，多个 Agent 之间很难形成主动关系。工具人 Agent 的作用，是把“主动社交”从角色自觉中抽离出来，变成系统层的调度任务。

工具人不是角色，不承担人格表达，也不与用户闲聊。它只负责接收 cron 触发、读取上下文、构造系统消息、异步提交给目标 Agent，然后结束。工具人越中立，系统越稳定。它不应该在调度消息中临场发挥，也不应该替角色决定具体情绪，只提供足够上下文和明确任务。

每日主任务会生成当天的社交触发计划。计划包含若干条时间点、目标 Agent 和匿名显示标签。分配算法不是完全平均，而是先保证每个 Agent 的最低触发次数，再用偏差平方加权分配剩余次数。时间槽在全天范围内随机选择，并对特定低活跃时段降权，避免触发过于集中。

每个调度 cron 触发时，工具人执行以下步骤：解析目标 Agent，读取该 Agent 的预处理全量文本，读取该 Agent 最近 memory，获取外部环境信息，构造系统消息，要求目标 Agent 从可选联系人中选择一个进行一轮通信。工具人使用 `submit_to_agent` 异步提交，不等待目标 Agent 回复。后续通信内容会由变更监听器从 session JSON 中捕获并同步到 memory。

工具人使用异步提交的原因很直接：调度器不应该被角色回复阻塞。同步通信会让工具人等待模型生成，多个任务叠加时可能占用资源，甚至影响后续 cron。异步提交让工具人保持管道属性，提交后即可删除当前 cron 或结束当前任务。

#### 进阶讨论：为什么不用全局共享记忆

全局共享记忆看起来能简化系统：所有 Agent 都读一个数据库，所有事件都进去，任何 Agent 都能知道一切。但在角色扮演系统中，这会带来几个问题。

首先，全知会破坏局部视角。多 Agent 世界的真实感来自每个 Agent 知道的东西不同。其次，全局记忆会让隐私分级变复杂。每次读取都要动态判断“这个 Agent 此刻能不能知道这条信息”，如果没有硬过滤工具，很容易泄露。再次，全局记忆会让角色差异被稀释。每个 Agent 不再拥有自己的记忆重心，而是共享同一份世界摘要。

当前方案选择每个 Agent 拥有自己的 memory，同时通过通信前必读和监听器同步形成局部共享。这更接近分布式系统：每个节点有自己的状态，通过消息和同步机制逐步传播信息。它牺牲了一部分简单性，换来更好的边界和可维护性。

#### 进阶讨论：为什么不用链式自治通信

让 Agent 自己决定“我要联系谁、对方再联系谁”看似更自主，但工程上很危险。生成式 Agent 没有天然的全局任务终止意识。一个 Agent 收到消息后可能认为应该继续通知另一个 Agent，另一个 Agent 又继续扩散。链式通信很快从一轮互动变成不可控传播。

因此系统把主动性拆成两层：工具人负责制造触发机会，角色 Agent 负责在一次触发中完成一轮自然通信。主动性存在，但被调度器和协议约束在可观察范围内。

#### 进阶讨论：为什么不让监听器直接写 memory

当前监听器负责生成 delta 并通知 Agent，由 Agent 读取 delta 后追加 memory。另一种更工程化的方案是让监听器直接写入 memory 文件。直接写入的优点是更稳定、更可测试，也不依赖 Agent 执行文件操作指令。缺点是监听器必须承担摘要格式、隐私估值和文件合并策略，系统维护脚本会更复杂。

现阶段采用通知 Agent 写入，是一种折中。监听器已经完成最容易出错的部分：发现变更、解析 session、过滤噪声、计算增量。Agent 执行的只是较小范围的追加任务。后续若要提高稳定性，可以把这一步继续下沉到 Python，让监听器直接维护 memory，并把 Agent 完全从记忆写入职责中解放出来。

#### 进阶讨论：脱敏文档的边界

架构文档、维护文档和公开笔记不应包含具体角色设定、角色名、昵称、身份、关系、互动题材、私密内容、真实渠道 token、真实用户 ID 或可直接复原私有世界的映射表。技术实现可以在本地工作区保存这些内容，但对外文档应使用匿名占位。

脱敏不是简单替换几个名字，而是要避免暴露结构性信息。可以写“角色 Agent A 与角色 Agent B 通信”，不能写具体角色称呼；可以写“高隐私条目”，不能写高隐私条目的内容；可以写“即时通信渠道”，不能写真实 token；可以写“匿名工作区”，不能写能直接关联到角色设定的目录映射。

#### 进阶讨论：监听器的故障模式

变更监听器是当前记忆系统的核心组件，因此它的故障模式必须被单独分析。第一类故障是“无声失败”。例如 session JSON 结构变化后，解析函数仍然可以正常返回空列表，主循环也不会报错，但系统不再产生任何 delta。这类故障比显式异常更危险，因为表面上进程还在运行，实际记忆已经停止更新。应对方式是增加启动自检：随机抽取一个已有 session，确认至少能解析出若干条历史消息；如果解析结果长期为零，就输出醒目的错误日志。

第二类故障是“重复同步”。如果 prev 文件提交时机不正确，或者通知失败后仍然提交 prev，就会造成两种相反问题：一种是尚未写入 memory 的 delta 被标记为已处理，导致记忆丢失；另一种是同一批 delta 反复进入 pending，导致 Agent 被多次通知，memory 中出现重复条目。当前设计用“通知成功后提交 prev”降低第一种风险，用 pending 去重降低第二种风险。这个事务边界必须保持清晰：写 delta 不代表同步成功，CLI 返回成功也只能说明通知送达，不代表 Agent 已经完全正确写入 memory。

第三类故障是“文件半写入”。平台写 session JSON 时可能存在短暂的不完整状态。监听器如果在写入过程中读取文件，可能遇到 JSON 解析失败，也可能读到缺少尾部消息的内容。当前方案通过文件大小稳定等待缓解这个问题。更严格的做法是记录连续两到三次 stat 的大小与 mtime，均不变化后再读取；如果解析失败，不应清空 prev，也不应提交空 full。

第四类故障是“系统消息污染”。调度模板、同步指令、工具操作说明都可能进入 session。若过滤规则不够稳，memory 会逐渐混入非角色内容。污染一旦进入长期 memory，后续 Agent 会把它当成世界事实使用。因此过滤层应尽量保守：宁可少同步一条疑似系统消息，也不要把系统维护文本写成角色记忆。

#### 进阶讨论：可观测性与人工校验

多 Agent 系统一旦自动化运行，就必须有最低限度的可观测性。可观测性不是为了让系统变复杂，而是为了在记忆断裂、重复通知、调度异常时能定位问题。

变更监听器至少应输出四类日志：检测到哪些 session 文件变化；每次预处理为哪些 Agent 生成了多少 delta；哪些 Agent 因通知间隔进入 pending；哪些 Agent 通知成功或失败。日志不应包含具体角色内容，只需要记录匿名 Agent 标识、条数、时间和错误摘要。这样既能调试系统，又不会让日志成为另一份敏感内容泄露源。

每日调度也需要摘要记录。计划生成后，应记录总任务数、每个匿名 Agent 的任务数、时间范围和异常情况。这里的记录不是剧情记忆，而是系统运行日志。它不应该进入角色 memory，也不应该被角色在自然对话中引用。

人工校验可以采用抽样方式。每天或每次修改监听器后，抽取一个用户私聊 session 和一个 Agent 间通信 session，检查它们是否正确进入对应 Agent 的 full 文件；再检查 delta 是否只包含新增内容；最后检查 memory 是否追加到正确日期。这个流程不需要阅读具体内容，只需看时间戳、行数和文件路径是否符合预期。

#### 进阶讨论：从个人系统到可迁移系统

当前架构适合个人本地系统，因为大量路径、Agent 列表、用户 session 关键字和调度参数都是硬编码的。硬编码的优点是直观、稳定、减少生成式 Agent 替换变量出错的机会。缺点是迁移成本高，一旦换机器、换平台用户、换 Agent 数量，就需要同时修改多处文件。

如果要把系统迁移成通用框架，应把这些硬编码内容移入单独配置文件。例如 `agents.yaml` 保存匿名 Agent 列表、工作区路径、是否参与调度；`sessions.yaml` 保存用户私聊识别规则和 Agent 间通信前缀；`scheduler.yaml` 保存每日任务数、低权重时间段和最小间隔；`privacy.yaml` 保存隐私等级解释和默认阈值策略。监听器和工具人只读取配置，不再把本地路径写死在代码里。

迁移还需要处理平台差异。不同平台的 session JSON 结构、跨 Agent 通信保存位置、cron 语法、异步任务接口都可能不同。当前架构中真正可迁移的是原则：证据层与工作层分离、变更触发增量同步、固定 session 路由、通信前读取对方近期记忆、调度器只做管道。具体命令和文件格式需要按平台重写。

### 实现方案

#### 工作区结构

每个角色 Agent 可以抽象为如下目录结构：

```text
workspaces/
  agent_A/
    agent.json
    AGENTS.md
    SOUL.md
    PROFILE.md
    MEMORY.md
    agent_communication.md
    sessions/
      user_private_session.json
      family-agent_X-agent_A.json
    memory/
      YYYY-MM-DD.md
    heartbeat_pre_full.txt
    heartbeat_pre_delta.txt
    heartbeat_pre_full_prev.txt
```

其中 `agent.json` 决定 Agent 的运行配置、工具开关、渠道配置、模型配置和系统提示词文件列表。系统提示词文件列表通常包含运行规则、人格、档案、通信协议等文件。`sessions/` 由平台生成，是原始会话记录。`memory/` 是按日期保存的长期记忆。`heartbeat_pre_*` 是监听器生成的预处理文件，名称为历史遗留。

工具人 Agent 的工作区略有不同。它的核心文件包括调度规则、通讯录、每日计划生成脚本、每日计划 JSON 和 cron 任务状态。工具人不需要人格文件发挥角色作用，即使存在人格占位文件，也应明确写成“不是角色”。

#### 角色 Agent 的配置要点

角色 Agent 的配置重点不在某个具体字段，而在几个原则。

第一，系统提示词文件应显式列出。这样每个 Agent 的人格、档案、规则、通信协议可以独立维护，而不是在平台配置里写成长字符串。

第二，跨 Agent 工具必须启用。角色需要能够列出 Agent、读取文件、发起跨 Agent 通信、必要时提交任务。通信协议依赖这些工具存在。

第三，memory backend 与 daily memory 目录需要固定。无论平台内部 memory 管理如何，外部监听器都应知道每个 Agent 的按日记忆目录在哪里。

第四，渠道配置属于敏感运行配置。文档不应暴露真实 token、真实用户标识或具体渠道密钥。架构文档只说明“用户通过某一即时通信渠道与 Agent 交互”即可。

#### 变更监听器实现要点

监听器硬编码了工作区根目录、参与 Agent 列表、工具人 ID、用户私聊 session 关键字、Agent 间通信 session 前缀、轮询间隔、最小通知间隔和文件稳定等待时间。硬编码在个人系统中可接受，因为它降低了 Agent 推理时替换变量的风险；但如果系统要迁移给多人使用，应改成配置文件。

监听器解析 session JSON 时需要兼容平台实际结构。实际 session 可能不是顶层 `messages`，而是嵌套在某个记忆字段中，并且每个元素可能包含消息对象和工具结果。如果只按顶层 `messages` 读取，脚本语法可以通过，但运行时会提取不到任何对话。这类问题很隐蔽，因为它不会抛异常，只会表现为“监听器一直没有增量”。

提取文本时还要处理 speaker 映射。某些 session 中 assistant 的 `name` 可能是平台默认名，而不是角色显示标签。监听器应根据 session 所属工作区把 assistant 映射回对应 Agent 的匿名显示标签或内部名。脱敏文档中不记录实际显示名，只描述这一映射原则。

通知 Agent 时应检查 CLI 返回码。只要外部命令返回非零，就不能提交 prev，否则会出现“Agent 没同步，但监听器以为已同步”的记忆丢失。通知成功后再提交 prev，是增量同步系统的事务边界。

监听器的核心伪代码如下：

```text
while true:
    sleep(POLL_INTERVAL)
    files = scan_session_files()
    mtimes = stat(files)

    if changed(previous_mtimes, mtimes):
        wait_until_stable(files)
        delta_by_agent = preprocess(files)
        merge_into_pending(delta_by_agent)

    ready = select_agents_outside_notify_gap(pending)
    if ready:
        write_delta_files(ready)
        notified = notify_agents(ready)
        for agent in notified:
            commit_prev(agent)
            clear_pending(agent)

    previous_mtimes = mtimes
```

这个伪代码体现了三个关键点：变更触发、pending 缓冲、成功后提交。缺少任何一个，系统都会更容易丢记忆或重复通知。

#### 预处理文本与 delta 文件

监听器为每个 Agent 生成全量文本和增量文本。全量文本是从所有相关 session 中提取、去重、排序后的纯对话视图。增量文本是当前全量相对上次成功同步版本新增的行。

全量文本有两个用途。第一，它给工具人调度提供“最近对话”材料，让工具人注入给目标 Agent 的系统消息不是空的。第二，它作为 delta 计算的基础。增量文本则只用于通知 Agent 更新 memory。

delta 文件不应被视为长期存储。它是同步缓冲区，随时可能被下一次变更重写。真正的长期存储是 `memory/YYYY-MM-DD.md` 和长期精华文件。

#### Agent 收到同步通知后的行为

监听器通过 CLI 给目标 Agent 发送系统级指令。指令要求 Agent 读取自己的 delta 文件，提取属于自己的条目，按每条开头时间戳确定日期，追加到对应 memory 文件。完成后只回复同步数量。

这个设计看似仍然让 Agent 参与写 memory，但与旧版本不同：Agent 不需要自己判断何时写，也不需要从原始 session 中找新增内容。它只执行一个被外部监听器准备好的、范围很小的文件追加任务。职责已经从“主动记录员”降到“受控写入执行者”。

如果要进一步提高可靠性，可以让 Python 监听器直接写 memory，而不是通知 Agent 写。当前设计保留 Agent 写入，一方面是利用平台已有文件工具和权限模型，另一方面是让 memory 写入行为仍经过 Agent 工作区自身工具链。但从工程纯粹性看，直接由监听器写 memory 会更稳定，也更容易测试。

#### 工具人每日调度实现

每日调度由主 cron 启动。主 cron 触发工具人执行规则：清理旧任务，运行计划生成脚本，读取计划 JSON，逐条创建当天社交触发 cron，并记录摘要。

计划生成脚本的关键参数包括：总任务数范围、每个 Agent 最小和最大触发次数、时间槽间隔、低权重时段、分配权重函数。它先给每个 Agent 基础次数，再用偏差平方惩罚分配剩余次数。偏差平方的好处是既避免完全平均的机械感，也避免某个 Agent 被随机数连续选中过多。

时间槽选择使用全天候选池。选中一个槽后移除相邻槽，从而保证触发间隔更自然。随后按时间顺序为槽位分配 Agent，优先选择距离上次触发更久的 Agent，减少同一 Agent 连续出现。

每个子 cron 的消息体只包含目标 Agent 的匿名标识和内部 ID。工具人收到后解析目标，读取目标上下文，构造系统消息并异步提交。工具人不等待、不追问、不评价、不写角色记忆。

#### 工程教训

第一，链式传递会失控。多 Agent 通信应当是一对一、一轮、可观察。复杂信息流应由系统层管理，而不是让 Agent 自己扩散。

第二，channel 推送不是记忆写入。需要 Agent 后续感知的内容必须进入 session。否则用户可能看见了通知，但 Agent 自己在后续对话中不知道通知存在。

第三，模板变量对生成式 Agent 不可靠。路径、session_id、通信对象表等内容最好在协议文件中明确列出，或者由外部程序生成。不要假设 Agent 会稳定完成变量求值。

第四，配置更新应避免破坏渠道密钥。删除重建 Agent 可能导致运行配置丢失。长期系统更适合直接修改配置文件，或者提供可回滚的配置迁移脚本。

第五，文件命名会留下历史包袱。`heartbeat` 命名现在只是历史遗留，不代表系统仍使用心跳机制。维护文档必须解释这种语义漂移，否则后续维护者会按旧架构理解新系统。

#### 最小验收标准

这套系统是否正常运行，不能只看进程是否存在，也不能只看 Agent 是否能回复。更合理的验收标准应覆盖四条链路。

第一，用户私聊链路必须闭合。用户与任意角色 Agent 对话后，session JSON 应出现变更；监听器应检测到变更；该 Agent 的 full 文件应出现对应纯文本；delta 文件应包含新增行；memory 文件应追加到正确日期。

第二，Agent 间通信链路必须闭合。任意两名匿名 Agent 发生一轮通信后，通信 session 应能被监听器识别，且参与双方都能在自身可见范围内获得相关摘要。由于平台可能只在被调用方保存 session，验收时必须检查双向扫描是否生效。

第三，调度链路必须闭合。每日计划应能生成、创建、触发和结束。工具人提交任务后不应等待角色回复，也不应把调度日志写入角色 memory。调度带来的通信应由监听器事后捕获。

第四，脱敏链路必须闭合。正式文档、运行日志和调试摘要不得出现具体角色信息、真实渠道密钥、真实用户标识或可复原私有设定的映射表。系统可以在本地保存完整配置，但对外材料必须保持匿名。

### 总结

这套多 Agent 角色扮演系统的核心，不是某个复杂提示词，而是一组围绕平台约束建立的工程协议。角色人格通过独立文件维护，通信通过固定 session 路由发生，记忆通过 session JSON 到 memory 文件的二级沉淀形成，自动化调度通过工具人和 cron 注入主动性，隐私分级通过 memory 条目和通信阈值维持局部可见性。

当前版本最重要的架构变化，是全面弃用周期性心跳，改用 Python 监听 session 文件变更。这个变化让记忆更新从“时间到了就检查”变成“文件变了才处理”，减少空转，也让职责边界更清晰。监听器负责发现变化、过滤噪声、计算增量、通知同步；Agent 负责在收到明确指令后把 delta 追加进自身 memory；工具人负责调度主动互动；角色 Agent 负责自然表达。

系统仍有历史命名包袱，例如若干文件仍包含 `heartbeat` 前缀。维护时应以当前职责理解它们，而不是被名称误导。更进一步的演进方向，是把隐私过滤和 memory 写入从提示词软约束迁移到外部程序硬约束，让 Agent 更少承担文件维护任务，把角色表达与系统维护拆得更彻底。

这套架构的价值在于，它没有把多 Agent 角色扮演视为“多写几份人设”，而是把它当成一个长期运行的分布式状态系统。只有当通信、记忆、调度、隐私和维护边界都被设计出来，多个 Agent 才能从并列的聊天窗口，变成一个可以持续运转的角色世界。

## 知识缺口

1. 当前文档基于本地工作区可见配置和脚本行为整理，未验证 QwenPaw 在所有版本中的 session JSON 结构是否完全一致。若平台升级 session 格式，监听器解析逻辑需要重新检查。
2. 当前变更监听器采用 mtime 轮询，不是真正的操作系统文件事件订阅。若 session 写入频率极高，仍需评估轮询间隔、文件稳定等待和 pending 队列策略是否足够。
3. 当前隐私过滤主要依赖通信协议和 Agent 遵守提示词，尚未完全下沉为外部程序强约束。若系统需要更强隐私边界，应优先实现独立 memory 查询与过滤工具。
4. 当前文档不记录任何具体角色配置、角色名、昵称、身份、关系或互动题材，因此不覆盖角色创作层面的设计方法，只覆盖多 Agent 系统架构。
5. 当前工具人调度依赖 cron 与异步提交能力。若迁移到其他平台，需要重新评估任务创建、任务删除、异步分发和 session 持久化机制。
