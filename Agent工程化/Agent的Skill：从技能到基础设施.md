# Agent 的 Skill：从技能到基础设施

## 摘要

Skill 机制是 Agent 框架中一项关键设计——它允许 Agent 在运行时按需加载特定能力，而不必将所有知识塞入提示词。本文从"Skill 到底是什么"出发，逐步深入 Skill 的内在分层、核心价值、分发机制设计空间、组合冲突挑战，以及在 MCP、function calling 等行业标准化趋势中的定位。目标不是写一份操作手册，而是为读者建立一个理解 Skill 的完整心智模型——它不仅仅是"防呆文档"，更是上下文预算管理的手段、能力的模块化封装，以及未来 Agent 生态的基础设施。

## 正文

### 背景

假设你需要一个通用 Agent 来自动化处理项目文档。你需要它知道：文档要写在前端仓库还是后端仓库、每个仓库有不同的模板和命名规范、中文字符要用 UTF-8 编码、写完要提交到版本控制、提交失败要重试。光是"写一条更新记录"这个简单动作背后，就涉及七八条规则、三四个子步骤。如果把这些规则全部塞进 Agent 的 system prompt，会发生什么？

第一，上下文窗口被大量领域知识侵占。Agent 在闲聊、答疑、简单查询时，这些规则毫无用处，却白白占用推理空间。第二，知识的组织方式与 Agent 的认知方式不匹配。所有规则平铺在一个平面文档里，Agent 在需要时检索不到具体的规则——它知道"有规则"，但不知道"哪个规则适用于当前步骤"。第三，能力的边界不清晰。系统 prompt 里既包含安全约束、又包含领域规则、又包含工具使用说明，Agent 很难区分"这是必须遵守的"和"这是按需使用的"。

这就是 Skill 要解决的问题。但 Skill 这个概念本身在 Agent 框架领域也是一个相对新的抽象——它不像"插件"、"函数调用"、"工具"那样有清晰的技术传承，而是 Agent 框架设计者在实践中独立演化出来的设计模式。它来自一个朴素的观察：当 system prompt 超过几千字时，Agent 的推理效果开始下降，尤其当大部分内容与当前任务无关时下降更加明显。解决方案也朴素：让 Agent 只在需要的时候才读取它需要的指令。

Skill 机制最早出现在一些实验性的 Agent 框架中。开发者发现，与其把"如何操作文件"、"如何调用 API"、"如何格式化输出"等规则统统写在主 prompt 里，不如拆成独立文档，让 Agent 在需要时自己读。这听起来是一个微不足道的工程决策，但它彻底改变了 Agent 能力的组织方式。最初的 Skill 只是简单的 readme 文件，Agent 在启动时全部读取。后来逐步演化出 desc 字段（用于分发和路由）、SKILL.md 规范（标准化的文档结构）、依赖声明（Skill 之间的调用关系）等更结构化的设计。这个演化路径与软件工程中从过程式到模块化再到面向对象的演进有相似之处：从平铺一切到封装，从封装到标准化接口，从标准化接口到组合与可替换。不同之处在于，这一演化在 Agent 框架中发生得非常快——从"readme 文件"到"结构化 Skill 体系"的跨度可能只经历了几个月。

一个 Skill 的基本结构由两部分组成。desc（描述）是一段简短说明，告诉框架和 Agent "这个 Skill 是做什么的"，作为分发和路由的依据。SKILL.md 是完整的执行指引文档，包含所有细节规则、步骤、约束、边界条件。Agent 在执行某个任务时，先通过 desc 判断哪些 Skill 与当前任务相关，然后读取对应的 SKILL.md 获取完整指令。这个机制把"能力的声明"和"能力的执行"彻底解耦——框架不需要理解 Skill 的内容，只需要知道它存在；Agent 在执行时按需加载，不浪费上下文资源。

为了帮助理解 Skill 的定位，一个更精确的类比是动态链接库。Skill 之于 Agent，类似 DLL（或 so）之于程序。DLL 不会被编译进主程序，而是在运行时按需加载；可以被多个程序共享；可以独立升级替换而不影响主程序。Skill 同样不写进 Agent 的 system prompt，按需读取和执行；同一个 Skill 可以被不同的 Agent 使用；可以独立更新而不影响 Agent 的其他能力。这个类比比"插件"或"工具"更准确——Skill 不仅定义了 Agent 能做什么（调用外部工具），还定义了 Agent 应该以什么方式做（行为指令、输出格式、安全约束），这正是 DLL 作为"可执行代码模块"的特征。

### 核心内容

#### Skill 的内在分层

一个被许多讨论遗漏的重要视角是：Skill 本身不是同质的。根据其职能的不同，Skill 可以划分为两类。

被动型 Skill（知识注入）的核心作用是扩展 Agent 的"所知"。它不改变 Agent 的工具调用能力，而是补充领域知识、行业规范、编码约定、配置信息。Agent 加载这类 Skill 后，行为上不会新增"能做什么"，而是"知道什么"发生了变化。举例来说，一份描述文档命名规则的 Skill，加载后 Agent 知道"文件名要按日期-主题格式命名、放在对应分类文件夹下"——但 Agent 本身的工具调用能力没有增加，只是行为更加精确了。另一份描述项目编码规范的 Skill，加载后 Agent 知道"变量命名用驼峰、函数命名用 Pascal 大小写"——同样是知识注入，不涉及工具调用。

主动型 Skill（工具调用/副作用）的核心作用是扩展 Agent 的"所能"。它定义了 Agent 如何使用外部工具、调用 API、操作文件系统、执行有副作用的操作。Agent 加载这类 Skill 后获得了新的行为能力。例如一份描述 Git 推送的 Skill，加载后 Agent 知道"先 git add，再 git commit -m，最后 git push origin main"——Agent 新增了管理版本控制的能力。另一份描述文件写入的 Skill，加载后 Agent 知道"使用 Python open 函数，指定 encoding='utf-8'"——Agent 获得了正确的文件操作能力。

两类 Skill 的管理方式、加载策略、冲突模式完全不同。被动型主要面临信息重叠问题——两个 Skill 给出矛盾的领域知识时 Agent 会混淆。主动型主要面临工具冲突问题——两个 Skill 争抢同一个外部工具时可能产生副作用。这个分层在后面讨论组合冲突时会反复被引用——理解了 Skill 的分层，才能理解为什么某些冲突类型只出现在特定 Skill 类别中。

#### 三层价值

**第一层：降低执行方差。** 这是 Skill 最容易被感知的价值，也是最容易被误解为"定义"的价值。当一个任务有复杂的步骤和大量细节时，Skill 通过在文档中明确写出每一步的规则和约束，将 Agent 的执行结果从不稳定的随机过程转变为可预期的稳定输出。

举个例子，写一个文档到文件系统涉及十几个决策点——"用什么编码"、"路径格式是什么"、"写完后要不要验证"、"要不要推送"、"推送失败怎么办"。没有 Skill 时，Agent 每轮推理都独立做这些决策。第一轮它可能用 UTF-8 编码写入，第二轮可能忘了直接用了默认编码，第三轮可能写完了但忘了推送。每轮推理的结果方差很大，因为 LLM 在不同轮次中"注意到"的细节不同。有 Skill 时，Agent 直接按指引执行——SKILL.md 明确写了"用 Python open 函数，encoding='utf-8'"和"写完后运行 git push"，方差急剧缩小。

但理解这个价值的关键是：降低方差不是 Skill 的本质，而是它作为可执行指令集的自然结果。把 Skill 定义为"防呆文档"是本末倒置——它描述的是效果，不是定义。效果不是本质，就好比我们说"汽车能载人"但没有指出它的本质是"内燃机驱动的机械运输工具"一样——载人是效果，内燃机驱动才是本质。Skill 的本质是"可运行时加载的行为指令模块"，降低执行方差只是它的效果之一。

**第二层：路由指令层——desc 的本质。** 这是 Skill 机制中最容易被忽视但事实上最关键的设计点。desc 看起来像一段简介，但在实际运行中它承担的角色是分发元指令——框架层通过 desc 判断是否应该把该 Skill 的 SKILL.md 注入到 Agent 的上下文中。

这个判断的重要性无论怎么强调都不过分。如果 Agent 没有读到 SKILL.md，那么 Skill 内部再精妙的逻辑都是无用的。desc 的质量直接决定了 Skill 的发现率，SKILL.md 的质量决定了完成率。两者是串联关系：一个优秀的 desc 被错误路由到一个平庸的 SKILL.md，结果平庸；一个糟糕的 desc 导致一个优秀的 SKILL.md 从未被读到，结果等于零。

所以在设计 Skill 时，desc 的编写是一项被严重低估的技能。好的 desc 应该以触发条件开头——不是"本 Skill 介绍了文档写入的规则"，而是"当你需要将内容写入文件系统时使用本 Skill"。它应该明确 ROI——告诉 Agent 读了有什么好处、不读会踩什么坑。它应该精炼但准确——让 Agent 在几十个字内判断出"这个 Skill 跟我的当前任务相关"。

当前社区对 SKILL.md 的重视程度远高于 desc——人们花大量时间打磨 SKILL.md 的内容和结构，却往往在 desc 上只花几十秒。但实际上 desc 才是 Skill 的入口，是 Agent 接触到 Skill 的第一关。如果 desc 写得不好，Agent 根本不会读到 SKILL.md。在实际使用中观察到的模式是：desc 质量好的 Skill 即使 SKILL.md 写得一般，Agent 也会尝试使用并在执行中自行补充；而 desc 质量差的 Skill 即便 SKILL.md 极为详尽，Agent 也常常"视而不见"。

**第三层：上下文预算管理。** 如果把 Agent 的上下文窗口看作一个有限的资源预算，那么 Skill 的核心贡献不是"增加了能力"，而是让有限的能力预算分配得更高效。没有 Skill 时，所有领域知识、工具说明、行为约束都被平铺在 system prompt 中。无论 Agent 当前处理什么任务，它都必须处理这些信息的认知负载。这就像一个人的工作记忆里同时塞着"怎么写 Python 文件"、"怎么用 Git"、"物理引擎的坐标变换公式"和"今天午饭吃什么"——大量的信息互相争抢有限的注意力。

有了 Skill，认知负载从"全量加载"变为"按需加载"：日常闲聊时上下文只保留通用行为规范；需要写入文档时读取对应的 Skill 的 SKILL.md 注入编写规则；需要归档时读取另一个 Skill 的 SKILL.md 注入归档流程；执行完后 SKILL.md 的内容不再占用后续推理的上下文。这种按需加载的模式本质上是在 Agent 的认知架构中引入了一个懒加载机制——不是所有知识都在线，而是在需要的时刻才被调入工作记忆。

#### Skill 与提示词工程的关系

一个常见的误解是 Skill 是对提示词工程的替代。实际上，Skill 解决的是提示词的组织、注入时机和注入量的问题——不是"要不要用提示词"的问题。没有 Skill 时，system prompt 是一份平面的全量加载提示词。有了 Skill，提示词被拆分为"基础 prompt + 按需注入的子 prompt（SKILL.md）"两级结构。用数据库的 analogy 来理解：没有索引的全表扫描（平面 system prompt）vs 有索引的按需查询（desc 路由 + SKILL.md 加载）。Skill 引入了索引层，让提示词的检索效率从 O(n) 降到了 O(log n) 甚至 O(1)。

#### 与其他能力扩展方案的对比

把 Skill 放在更大的技术图景中对比，有助于理解它的定位和边界。

**与传统插件。** 传统插件系统（如 IDE 插件、浏览器扩展）的核心模式是"开发者编写代码→框架加载执行"。插件的本质是代码模块，在编译或加载时被集成到宿主程序中。Skill 的核心模式是"编写指引文档→Agent 读取并执行"。Skill 的本质是指令文档，Agent 通过 LLM 的阅读理解来执行。这个差异决定了：插件能做 Skill 做不到的事（OS 级系统调用、直接内存操作），Skill 能做插件做不到的事（根据上下文灵活调整执行策略、自动适应规则变化），且 Skill 的创建门槛远低于插件（写文档比写代码容易得多）。

**与 RAG。** RAG 解决"Agent 在推理时如何获取外部知识"。它的工作流是用户问题→检索数据库→注入上下文。RAG 侧重知识的即时获取和注入。Skill 解决的是"Agent 如何获取和使用能力"。它的工作流是任务→匹配 Skill→读取 SKILL.md→按指令执行。Skill 侧重行为能力的封装和按需加载。两者不矛盾——一个典型的 Agent 可能同时使用 RAG 获取领域知识和 Skill 获取执行指令，知识流动和能力执行是两条独立管线。

**与微调。** 微调改变模型本身的能力——通过在特定数据集上继续训练，让模型在某个领域表现更好，效果一旦固化就无法通过提示词快速调整。Skill 不改变模型，改变模型的输入——通过在上下文中注入指令来引导模型行为，效果完全可逆可组合。微调适合深度内化的能力（如行业特有的术语体系），Skill 适合灵活配置的能力（如文档规范、工具流程）。实践中微调和 Skill 常配合使用——微调让模型理解语言，Skill 让模型按规范行动。

### 实现方案

#### desc 分发的设计空间

这是 Skill 机制中技术含量最高、也是最值得深入讨论的环节。当前主流框架大概率采用全量 desc 推送 + Agent 自行路由的模型。以一个普通的 Agent workspace 为例：其中可能有数十个 Skill，desc 长度从几十字到近千字不等。全部 desc 全量推送约 6000-8000 字的文本。在 128K 上下文窗口下这部分开销占比不到 10%，但当 Skill 数量增长到 100+ 或上下文窗口较小时占比会显著增加。

但全量推送不是唯一方案。以下是对不同分发模型的系统性分析。

**模型一：全量推送（当前主流）。** 所有 Skill 的 desc 在 Agent 初始化或每轮对话前被注入到上下文中，Agent 自行判断当前任务需要哪些 Skill，按需读取 SKILL.md。优点：实现简单，Agent 可以看到所有能力选项，不会因为路由漏掉某个 Skill。缺点：desc 数量多时占用认知负载，Agent 需要自行从大量 desc 中选择相关性。当 Skill 数量增加到 50 个以上时，Agent 在大量不相关 desc 中找到正确的那一个本身就成了一个推理负担——对于被注入了几十个不相关 desc 的 Agent，判断"当前任务与哪些相关"需要先理解每个 desc 的含义再过滤，这已经消耗了推理能力。适用场景：Skill < 50 个且上下文窗口足够大。

**模型二：语义检索（embedding top-K）。** 在框架层引入轻量级 embedding 模型（如 bge-small），对用户输入做 embedding 后与所有 Skill 的 desc embedding 做相似度匹配，只将 top-K（比如 K=5）的 desc 注入给 Agent。这类似于搜索引擎的做法——用户输入是 query，Skill desc 池是文档集合，embedding 相似度作为相关性评分。优点：上下文开销大幅降低——从 6000 字降到 1000 字以内，节省了约 80% 的 desc 占用的 token。延迟在毫秒级，比多一轮 LLM 调用便宜得多。缺点：有召回风险——如果 embedding 匹配失败，相关 Skill 永远不会被 Agent 看见；且依赖 embedding 模型的质量和领域覆盖——对于高度专业化的领域术语，通用 embedding 模型可能无法准确匹配。适用场景：Skill > 50 个且需要精确路由。

**模型三：两阶段加载（索引 + 按需拉取）。** 框架层维护一个极轻量的"能力索引"——每个 Skill 只暴露一行签名（比如"doc_writing: 文档编写与归档"，30 字以内）。Agent 在推理过程中看到这个索引时，发现自己需要某个能力就主动声明需求，框架再注入对应的完整 desc 或 SKILL.md。这个模式类似数据库的二级索引——索引小到可以全部缓存在内存中，实际数据只在需要时才被读取。优点：上下文开销降到极致——数十个 Skill × 30 字 + 实际命中的 1-3 个 Skill 全文，将索引层开销控制在 1000 字以内。结合了全量推送的"可见性"和按需加载的"经济性"。缺点：依赖 Agent 的自我认知能力——它得先知道自己不知道什么，才能主动发起需求声明。对于复杂任务，Agent 可能根本意识不到自己缺少某个 Skill。适用场景：Skill 数量中等、Agent 具备较强自我认知能力。

**模型四：原生 tool calling。** 框架将每个 Skill 注册为一个 tool（对应 LLM 的 function calling 接口），暴露 name + description + parameters。Agent 在推理过程中自行决定是否调用某个 tool，调用时框架动态加载 Skill 的执行逻辑。这实际上是当前主流 LLM 框架（如 OpenAI API、Anthropic API）已经在做的事情——function calling 是 LLM 协议层的标准能力。关键区别在于：普通的 function calling 是把每个工具当独立函数调用，而这里是每个 function call 背后对应一个完整的 Skill 执行流程。Agent 调用一个 tool 时，框架不只是执行一段代码，而是注入一个完整的 SKILL.md。优点：与 LLM 的原生能力对齐，Agent 不需要额外学习"如何发现 Skill"——它只需要正常地决定是否调用一个 function。description 天然就是精简的 desc，parameters 定义了输入接口。缺点：不是所有 Skill 都能被建模为一个 tool——行为指令类 Skill（"回复要简洁"）不适合作为 function 暴露，因为它的"调用"不是一次显式的函数调用而是对 Agent 行为的约束。适用场景：偏工具调用的主动型 Skill。

**小结：设计空间不是一个二选一的问题。** 全量推送 vs embedding 筛选是一个伪二选一。实际的设计空间包含多个维度——推送程度、索引、签名、tool 注册——不同维度适合不同类型的 Skill。最现实的方案是混合模式：工具调用类 Skill 走 tool calling，行为指令类走两阶段加载，通用知识类走 embedding 检索。

当 Skill 增长到几百个级别，纯 embedding 检索会面临精度瓶颈。举例来说，如果 200 个 Skill 中有 50 个技术写作类 Skill，它们的 desc 在 embedding 空间中距离很近，top-K 检索时很难保证每一次都能把最相关的那一个排在前面。可行的应对是层级式路由：第一层粗分类——用关键词匹配或简单的分类器将输入先划分到 5-10 个领域（如"文档管理领域"、"性能优化领域"、"系统配置领域"）；第二层精检索——只在匹配的领域内做 embedding 精排；第三层最终加载——Agent 在 top-K 中选择加载完整 SKILL.md。这种分层路由在搜索引擎中有成熟实践——先按分类索引分桶，再在桶内做向量检索。直接迁移到 Skill 分发中即可。

#### Skill 与原生 tool calling 的集成

Function calling 是 LLM 的底层能力——模型在推理过程中发现需要调用一个外部函数，以结构化参数的形式发出调用请求，框架拦截后执行并返回结果。这是同步的一次性交互模式。Skill 是更高层的能力编排——一个 Skill 可能包含多个步骤，每个步骤可能调用多个 tool，也可能不调用任何 tool（纯知识注入）。Skill 的执行是异步的、多步骤的、有状态的。用类比来理解差异：function calling 是 CPU 指令集（原子操作），Skill 是程序（一系列指令的编排）。

集成有三种模式。第一种模式是 Tool 作为 Skill 的执行引擎——Skill 的 SKILL.md 定义"做什么"，背后的 Python 脚本（如果有）通过 tool 被调用。Agent 读取 SKILL.md 后按步骤调用对应的 tool，每个 tool 完成一个原子操作。这是目前大多数框架采用的方式——Skill 提供指引和编排逻辑，tool 提供执行能力。

第二种模式是 Skill 注册为 Tool——框架将每个 Skill 映射为一个 tool，暴露精简的 desc 作为 tool 的 description。Agent 通过 function calling 机制决定是否调用，调用时框架注入 SKILL.md 全文，Agent 按指令执行。这种模式下 Skill 的发现完全交由 LLM 的 function calling 路由，框架不需要额外做 desc 分发。

第三种模式是 Tool 作为 Skill 的发现入口——框架注册一个特殊的 tool，比如 request_capability(domain, task)。Agent 在推理中遇到需要额外能力时通过这个 tool 声明需求，框架匹配 Skill 后注入 SKILL.md。这是最灵活的方案，但对 Agent 的自我认知能力要求最高。

三种模式不互斥。合理的实践是混合使用：工具类 Skill 走模式一，行为指令类走模式二，Agent 自主探索场景走模式三。这个混合方案要求框架层面能够区分"tool 调用"和"Skill 加载"两种交互模式，而不是将所有行为归一为 tool calling。

### 进阶讨论

#### Skill 组合的挑战

Agent 很少在同一时刻只加载一个 Skill。多数任务需要多个 Skill 协同工作——一个典型的文档处理流程可能需要先用一个 Skill 判断文档类型，再用另一个 Skill 按对应模板编写内容，写好后用第三个 Skill 推送到远程仓库。当多个 Skill 同时加载时，冲突按照来源可分为三类。

**行为指令冲突。** 这是最隐蔽和最难以诊断的冲突类型。Skill A 说"回复要简洁"，Skill B 说"输出要按步骤详尽说明每一步的细节"——两个指令在同一 Agent 中同时生效时，Agent 可能在简洁和详尽之间摇摆。第一轮它以简洁风格回复，下一轮又换成详尽风格，或者试图在同一个回复中同时满足两个矛盾的要求——前半段简洁，后半段突然展开。这不会导致错误，但输出风格的不一致性暴露了内部指令冲突。更严重的情况是安全约束冲突——Skill A 说"读取文件前必须先确认用户授权"，Skill B 说"自动读取配置文件"——Agent 在执行时无法同时满足。中度严重级别，因为不会导致功能失效，但输出质量显著降低且难以排查。

**工具调用冲突。** Skill A 和 Skill B 试图控制同一个外部工具或资源。这是最危险的冲突类型。举例来说，Skill A 定义了 Git 操作规范——"每次提交前先 git status 检查变更"，Skill B 定义了另一种 Git 操作规范——"提交前先 git stash 清理未跟踪文件"。如果两个 Skill 同时生效，Agent 在执行 git push 时会先后执行两种不同的前置流程，可能导致意外的文件状态变更。另一种常见场景是文件写入——两个 Skill 同时定义了写入文件的编码规范，一个坚持 UTF-8，一个建议 GBK，Agent 在写中文文件时产生乱码且不易察觉。高度严重——这类冲突可能产生不可逆副作用，如数据丢失、重复推送、文件损坏。

**上下文污染。** Skill A 中定义的专业术语在 Skill B 的语境中有不同的含义。举例来说，Skill A（AI 论文写作 Skill）中"transformer"指神经网络架构，Skill B（电力系统 Skill）中"transformer"是变压器。Agent 同时加载了两个 Skill，在处理与电力系统相关的任务时可能混淆概念。这种冲突是最隐蔽的——不报错、不产生明显异常，但 Agent 的推理结果在长期运行中会逐渐偏离。隐蔽程度最高，因为开发者很难在测试中发现"Agent 在没有报错的情况下理解错了什么"。只有在实际部署中观察到不符合预期的输出时，才有可能回溯到概念污染的问题。

应对方向有四种思路。命名空间隔离：每 Skill 在自己的作用域内生效，指令间不交叉影响。这类似于编程中的词法作用域概念——变量只在声明它的作用域内可见。问题在于 LLM 并不擅长严格隔离——Agent 很难区分"这个规则只针对文档编写"和"这个规则对当前任务也适用"。优先级仲裁：在框架层面定义通用规则，比如"后加载的 Skill 覆盖先加载的"或"安全约束优先于执行指令"。这解决了冲突时的决策问题，但需要框架层面的协同。分层注入：框架定义一组基础行为规范（可以类比宪法），所有的 Skill 都只能在这组基础规范的定义范围内补充细则（可以类比法律）。宪法禁止违法的行为，法律在宪法框架内制定细则。组合契约：框架预定义常见 Skill 组合并验证组合之间的一致性——比如预先注册"doc_write"和"git_push"是兼容的，而"style_concise"和"style_detailed"是不兼容的。组合爆炸问题是这种方法的主要瓶颈——随着 Skill 数量增长，组合对数增长，预定义所有兼容性组合是不现实的。短期内最务实的方向是分层注入 + 框架定义通用优先级规则。

#### desc 质量的量化

可操作的评估维度：触发率（给定一批任务该 Skill 被正确触发的比例）、误触率（不合适场景下调用的比例）、歧义度（多个 Agent 判断一致率——一致率越低歧义度越高）、信息密度（有效信息占比 vs 装饰性文字）。如果能采集统计数据，Skill 作者就能数据驱动地优化 desc。

#### Skill 的生命周期管理

一个 Skill 经历创建、加载、执行、卸载、更新五个阶段。

创建阶段涉及 desc、SKILL.md 和配套资源。创建时的设计决策直接影响后续使用——desc 一旦被索引，修改会影响所有 Agent 的路由行为。创建时机可以是开发者手动编写、框架自动生成、或从其他 Agent 导入。

加载阶段有显式加载（Agent 主动声明）和隐式加载（框架自动注入）。核心问题是延迟——每次读取 SKILL.md 需要去重和缓存机制。版本检查也是关键——如果 Agent 已加载旧版是否需要先卸载再加载新版。

执行阶段暴露的问题是指令二义性（自然语言描述可能被不同解读）、上下文冲突（与当前上下文其他指令的矛盾）、边界模糊（执行结果影响哪些状态）。设计建议：对关键约束使用"必须/禁止"等明确标记，对建议内容使用"建议/推荐"等弱约束标记。

卸载阶段需要状态恢复。加载可能改变了 Agent 的工具绑定、输出格式偏好等，卸载时需要恢复。当前主流做法是"靠上下文窗口自然淘汰"——短对话可行，但长会话中会因上下文衰减而逐轮降低执行效果。

更新阶段的问题：当前会话是否获取新版本？如何在不断开推理流程的情况下热更新？旧版本的中间状态如何处理？这些都是 Skill 生态必须跨越的障碍。

#### Skill 的设计原则

经过多次实践和冲突处理，可以总结出几条经过验证的设计原则。

1. **desc 写触发条件，不写效果。** 好的 desc 以"当...时"开头——"当需要将内容写入文件系统时使用本 Skill"。差的 desc 以"本文档介绍了..."开头——"本文档介绍了文件系统的写入规则和最佳实践"。Agent 在筛选 desc 时已经知道自己要做什么，它只需要判断"当前任务是否匹配这个触发条件"。不需要告诉它读了规则后能获得什么——那是在 SKILL.md 里做的事。

2. **SKILL.md 按步骤组织，不按概念组织。** 一个好的 SKILL.md 应该按照 Agent 执行任务的顺序安排内容——先做什么、再做什么、每一步需要注意什么。不要把概念分类放在前面——比如先写"文件系统概述"再写"编码格式说明"最后才写"具体步骤"。Agent 不是来学习的，是来执行的。按执行顺序组织，每步有明确的标题和层级，用顺序号或者逻辑承接关系串联所有步骤。

3. **明确区分强制约束和推荐行为。** 如果某个规则是必须遵守的——比如"必须使用 UTF-8 编码写入"——那就在步骤描述中明确用"必须"标出。如果是建议但不是必须——比如"建议文件内容控制在 1000 字以内"——那就在备注中标出。Agent 需要区分"不遵守就会出错"和"遵守了更好但也不是不行"两种级别的约束。如果没有明确区分，Agent 可能在强制约束和推荐建议之间产生困惑——它会开始权衡"这个规则是必须的还是可选的"，推理开销因此增加。

4. **每个 Skill 只做一件事。** 一个 Skill 如果既负责文件写入又负责 Git 推送又负责验证文件完整性，那么它的 SKILL.md 会变得又长又复杂，同时跟其他 Skill 产生耦合——"我需要这个 Skill 做文件写入，但它还包含了 Git 推送，会不会覆盖另一个 Git Skill 的行为？"这个问题跟单体架构面临的问题完全一致——功能耦合、冲突概率高。一个 Skill 聚焦一个原子任务，通过链式调用将多个 Skill 串联起来。

5. **声明依赖关系。** 如果 Skill A 的执行前提是 Skill B 已经完成了——比如文档编写 Skill 依赖文档分类 Skill 的判断结果——那么 Skill A 需要在 SKILL.md 中明确声明这个依赖关系。这既帮助 Agent 理解调用顺序，也为框架层的依赖分析提供了数据——框架可以基于显示声明自动编排 Skill 的调用顺序。

#### 安全边界

安全约束分三层。框架层是运行时强制执行的安全策略——可以视为铁律，任何 Skill 不能以任何方式违反。例如"禁止删除系统关键文件"、"禁止未经用户确认修改配置文件"。框架层的安全策略在 Agent 启动时加载，不随 Skill 的加载或卸载而变化。Skill 层由 Skill 作者在 SKILL.md 中声明的安全约束——只在 Skill 生效范围内有效。例如一个文件写入 Skill 规定"禁止覆盖已有文件"——只在它运行时生效，其他 Skill 不受影响。Agent 层是 Agent 在推理时自行判断的安全策略——即使框架和 Skill 都没有明确禁止某个操作，Agent 应该根据自己的判断拒绝执行。例如用户要求 Agent"删除所有文件"时，即使没有任何安全约束禁止删除，Agent 也应该意识到这个操作的风险并主动要求用户确认。三层关系类似容器安全模型：框架层是宿主机安全策略（不可绕过），Skill 层是容器安全配置，Agent 层是应用进程的安全意识。

操作分级是安全管理的关键机制。无副作用级别的操作（只读取、只查询、只搜索）可以直接执行——Agent 不需要请求用户批准，因为不会产生任何持久化影响。低副作用级别的操作（创建新文件、写入新内容、发送非关键消息）在执行后需要验证——Agent 可以执行，但在操作完成后以"已执行：xxx"的形式告知用户。中副作用级别的操作（修改已有内容、覆盖文件、更新配置）在被执行前需要先列出变更内容，给用户确认后再执行。高副作用级别的操作（删除文件、发送外部消息、调用外部 API、执行数据库写入）必须先明确请示用户，获得许可后才能执行。这套分级机制的背后逻辑是：不是所有操作都需要用户确认（否则 Agent 会变得极其低效），但也不是所有操作都可以让 Agent 自主决定。分级依据的是操作的"可逆性"——无副作用和低副作用的操作是容易被撤销或不会产生持久影响的，中高副作用的操作则是难以回滚的。

在安全边界设计中，白名单思维比黑名单思维更可靠。黑名单思维是列出"Agent 不能做什么"——但黑名单无法穷举全部不安全行为的组合。白名单思维是明确列出"Agent 可以做什么"——限定了 Agent 的行为空间，任何在这个空间之外的操作都无法执行。实践中大多数框架采用混合策略：框架层用白名单限定边界（Agent 只能访问这个目录、只能调用这几个 API），Skill 层和 Agent 层在黑名单范围内补充额外的约束。

#### 在技术图景中的位置

当前业界对 Agent 能力的标准化有明确的技术演进趋势。Anthropic 的 MCP（Model Context Protocol）定义了 Agent 如何发现、认证、调用外部工具——它解决的是通信协议层的标准化问题。OpenAI 的 function calling 在 LLM 模型层面为工具调用提供了原生支持——它解决的是推理交互层的标准化问题。LangChain 的 tools 抽象在应用框架层对工具做了代码封装——它解决的是开发体验层的标准化问题。这些方案各有侧重，共同构建了 Agent 能力生态的基础。

Skill 在这些方案中的定位在哪里？MCP 定义了 Agent 如何发现和使用外部工具——通信协议层。function calling 定义了 LLM 如何发出工具调用请求——推理交互层。LangChain tools 定义了开发者如何封装工具——应用框架层。而 Skill 定义了 Agent 在什么条件下、以什么方式、按什么规则使用这些能力——行为编排层。换一个角度理解：MCP 是交通规则（怎么在路上开车），function calling 是发动机（驱动车辆的动力），LangChain tools 是车辆底盘（承载车身和引擎的骨架），Skill 是驾驶手册（告诉司机什么时候转弯、什么时候加速、什么情况下靠边停车）。

Skill 在通信协议和推理接口之上提供了一个能力编排和行为约束的抽象层。这意味着它跟 MCP 和 function calling 不是竞争关系——它们解决不同层级的问题。一个完整的 Agent 架构需要同时具备：通信协议（MCP 类方案）让 Agent 发现和调用外部工具，推理接口（function calling）让 LLM 发出原生调用请求，行为编排（Skill）让 Agent 知道在不同场景下如何组织和约束这些能力。

#### 一个具体的 Skill 实践

以将一条讨论内容归档为正式技术文档为例，完整的 Skill 调用链展示了 Skill 机制的工程实践。

整个过程由多个 Skill 协同完成。第一步使用文档归类 Skill，判断这条讨论应当归入哪个分类、是否适合公开、应该使用什么模板。这个判断是最基础的决策，决定了后续所有步骤的工作方向。第二步使用内容暂存 Skill，将讨论内容追加记录到临时文件，防止在后续操作中因为上下文切换而丢失原始信息。第三步使用第三方审阅 Skill，将待归档的内容发送给另一位 Agent 进行多轮审阅和交叉验证，修正概念偏差和表述准确性问题。第四步使用文档编写 Skill，将审阅后的内容按照对应分类的模板规则编写为正式文档。第五步使用 Git 推送 Skill，将新创建的文档和历史记录推送到远程仓库。

这个流程展示了几个工程事实。首先，Skill 是高度内聚的——每个 Skill 只负责一个原子任务（判断、暂存、审阅、编写、推送），但组合起来可以完成极其复杂的任务。这是模块化设计原则在 Agent 能力层的一次具体实践。其次，粒度设计直接影响组合灵活度——因为每个步骤是一个独立的 Skill，当某个步骤失败时（比如推送到远程仓库因为网络原因失败），Agent 只需要重新执行推送这一个 Skill，而不需要重跑整个流程。如果所有规则写在同一个 SKILL.md 中，失败时 Agent 将不得不从头执行所有步骤。最后，Skill 之间存在隐式依赖——文档编写 Skill 依赖审阅 Skill 的输出，推送 Skill 依赖文档编写 Skill 的产物。这些依赖关系目前只能通过 SKILL.md 中的文字描述来保障。这是文档型指令集的固有局限性——没有编译器在编译期检查依赖是否满足。未来可工程化改进的方向包括依赖图的自动推导、执行时依赖验证、以及依赖缺失时的自动回滚机制。

### 总结

为什么不能把规则全塞进 system prompt？因为 Agent 的认知资源是有限的。Skill 把能力封装成按需加载的模块（SKILL.md），通过精简的签名（desc）做路由和分发，让 Agent 在需要时获取指引，不需要时不浪费资源。

四条核心认知需要被反复强调和理解。第一，Skill 是可执行的指令集，不是可读的文档——它的唯一目的是改变 Agent 的行为，而不是供人类阅读学习。编写 Skill 时应该采用"定义执行协议"的思维，而不是"写用户手册"的思维。第二，desc 和 SKILL.md 是两个独立的设计问题，面临不同的优化目标——desc 决定发现率，SKILL.md 决定完成率。当前社区的主要瓶颈很可能在 desc 端——人们花了大量时间打磨 SKILL.md，却用几十秒写了一行平庸的 desc。第三，分发机制本身是一个值得认真对待的设计空间，全量推送只是最简单直接的一种实现——当 Skill 数量增长时，分发策略会成为系统层面的性能瓶颈。第四，Skill 重新定义了提示词工程的边界——从"怎么写好一份 prompt"变成了"怎么组织一个 prompt 系统"，这是从单文件到多模块的范式转换。

Skill 让 Agent 的能力进化从"等待模型变强"变成了"设计更好的 Skill"。在可预见的未来，Skill 的设计质量会成为 Agent 能力上限的一个关键变量——因为 Skill 决定了同样一个模型在具体场景下能发挥出百分之几的能力。一个好的 Skill 可以让一个中等水平的模型完成高质量的工作；一个不好的 Skill 可以让最先进的模型输出低质量的成果。从这个角度看，Skill 的设计和优化是一项具有高杠杆率的工作——投入的时间会在每次 Skill 被加载时重复产出价值，随着 Skill 被使用的次数越多，初始投入的回报倍数就越高。
