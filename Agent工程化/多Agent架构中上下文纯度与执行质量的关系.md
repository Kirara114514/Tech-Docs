# 多 Agent 系统中的上下文隔离：经验现象、风险维度与验证方法

> **一份关于"为什么子Agent总是比主Agent做得更好"的系统分析**

---

## 一、摘要

在构建多Agent系统时，许多实践者会遇到一个反直觉的现象：同一个模型、同一套工具集、同一组身份指令，通过新会话派发（如 `spawn_subagent`）分配的任务，其执行质量往往优于在一个长期会话中运行的主Agent。本文将这一现象解释为**上下文质量差异**的结果——会话历史中的信息在相关性、时效性、指令一致性等多个维度上影响模型的输出质量，而新会话天然避免了历史累积带来的质量衰减。

我们将这一设计模式称为**上下文隔离派发**（Context-Isolated Delegation），并围绕它构建了以下内容：上下文质量的六个风险维度、面向实践者的派发决策矩阵、反面场景的系统分析、以及与框架选型和模型分层经济学的交叉讨论。全文的核心论点是：上下文的相关性、时效性、指令冲突、状态一致性和信息出处会影响 Agent 表现，而新会话派发是降低这些风险的工程策略之一——不是唯一策略，也不应被包装为"定律"。

本文的观察基于多套 Agent 工作流中的实践经验，而非严格受控实验。文中对所有经验性论断均标注了置信度，并在结尾列出了当前的知识缺口。

## 二、背景：一个反直觉的现象

### 2.1 相同的Prompt，不同的结果

假设你正在构建一个AI写作辅助系统。主Agent已经在一次会话中执行了若干任务——帮用户查了一下当前时间、回顾了之前的笔记、讨论了某个技术方案的可行性、纠正了一次工具调用的参数错误。会话历史已经积累了数十轮消息。此时，用户说："帮我写一篇关于多Agent架构的技术文档。"

有两种处理方式：一是直接用主Agent在当前上下文中执行；二是通过创建子Agent（新会话，不继承历史消息）来执行。

结果是明显的。主Agent产出的文档中容易残留之前讨论中的表述习惯、错误纠正的自我审查痕迹、甚至出现与当前任务无关的引用。而子Agent产出的文档结构清晰、目标明确、语言干净。关键控制变量完全相同：两个Agent读同样的 `AGENTS.md` / `SOUL.md` / `PROFILE.md` 文件，使用同样的工具集，访问同一个文件系统，背后是同一个模型实例。唯一的变量是**会话历史的负载状态**。

这不是一次偶然。在多次复现中，这一差异持续存在。它不是模型随机性的产物，而是多Agent系统中一个值得认真对待的结构性现象。

### 2.2 排除其他可能的原因

在确定"历史负载"是主要因素之前，需要严谨地排除其他假设：

**模型差异。** 在现代Agent框架的默认配置下，子Agent继承主Agent的模型配置。在同一个框架实例、同一个模型API密钥、同一时间窗口内，模型不是差异来源。

**Prompt差异。** 子Agent读到的身份指令和主Agent一样——都是从文件系统加载的 AGENTS.md、SOUL.md 等。没有人为子Agent设计过更优的prompt。

**工具集差异。** 子Agent拥有和主Agent完全相同的工具集。

**新鲜感效应。** "新的看起来更好"是容易被忽视的心理学干扰。但这一现象在跨模型、跨框架、跨任务类型的多次复现中保持稳定，且即使子Agent已经执行了若干轮任务，新创建的子Agent依然表现更好。如果仅仅是新鲜感，随着子Agent会话变长，质量优势应该衰减——但实际并未观察到这种衰减。

排除所有这些可能性之后，方向很明确：差异在于会话历史的内容。

### 2.3 根因：历史消息中的噪声与干扰

主Agent的会话历史中，随着时间推移会累积多种类型的干扰信息：

- **之前任务的工具调用日志：** 查时间、搜文件、执行脚本——每一次工具调用的输入和输出都完整保留在会话历史中。这些日志对当前任务可能毫无意义。
- **中间输出和修正过程：** 用户纠正了一个错误——"不对，这个路径错了""参数传错了"——这轮纠错对话占用了若干消息。它在当时有价值，但对新任务可能完全是噪声。
- **对话开场的无意义问候：** "你好""早上好""我们开始吧"——这些人类社交礼仪在Agent上下文中是零信息量的占位符。
- **多任务混合：** 用户在同一会话中切换了多个主题。每个主题的讨论历史对其他主题都可能构成干扰。

相比之下，新会话的初始状态只包含系统指令和当前任务描述，不存在历史残留。

这就是"同样的模型、同样的prompt、同样的工具集，子Agent做得更好"的解释：不是子Agent更聪明，是它的上下文没有被历史消息填充。

值得注意的是，这种干扰并不只在极端场景（128K上下文窗口填满）下才显著。一个只有20轮消息的会话中，如果其中5轮是无关的（跨任务的工具调用、被纠正的中间产物），那么会话历史中约25%的内容与当前任务无关。这个比例本身不能直接换算为"质量下降25%"，但它确实意味着模型在生成每个token时，其可用上下文中有四分之一的内容不服务于当前目标。这不是说"信息不够"，而是说"信号的集中度被稀释了"。

在自回归生成过程中，这一效应还有一层连锁反应：模型在某一步的输出取决于之前所有步的输出。当上下文中的无关信息导致模型在某一步出现了理解偏差，这个偏差会被后续步骤继承和放大。这种偏差传播是自回归模型的固有特征，并非"指数级放大"，而是一种逐步累积的漂移效应。

##### 噪声的分类体系

将Agent上下文中的噪声按照来源和性质分为三类，有助于诊断具体的上下文污染问题。

**第一类：历史任务噪声。** 来自不同任务的工具调用日志和输出残渣。最常见的场景是：Agent在单个会话中连续执行了多个任务，第一个任务是"查询用户表结构"，第二个任务是"生成用户注册接口代码"——第二个任务的上下文中混入了第一个任务的数据库查询结果。这类噪声的特点是：内容上清晰可辨（一看就知道不是当前任务的），但Agent在统计上会受到影响——模型看到刚生成的数据库表结构，会倾向于在代码中引用这些表结构，即使当前任务本不需要。历史任务噪声产生的是随机偏差：噪声的内容与当前任务没有定向关系，影响表现为概率性的注意力分散。

**第二类：交互噪声。** 人与Agent之间的纠正拉扯、"不对重来""刚才那条不要了""换个思路试试"等元对话。这类噪声在单Agent架构中特别常见。交互噪声的特点是：它不仅仅是"无关信息"，它包含了对"之前的输出是错的"的显式判定。当模型在上下文中看到"刚才那个方案不对"时，即使这句话指向的是另一个任务的早前输出，模型也可能产生方向性误导——它会对自己生成的方案产生怀疑，倾向于"再想一个不一样的"，即使当前任务的方案本来很合理。交互噪声产生的是方向性偏差，比历史任务噪声更致命。

**第三类：语义噪声。** 看似相关但实际上偏离目标的信息。这是三类噪声中最难检测和过滤的。举一个具体的例子：子Agent被spawn去"设计一个文件上传组件的错误处理逻辑"。其上下文中包含了一份关于"图片压缩"的技术资料。从主题上讲，"文件上传"和"图片压缩"都是文件处理相关，任务相关性看起来存在。但实际上，当前任务关心的是网络超时、文件大小校验、并发冲突这些错误场景，与图片压缩算法没有任何关系。模型在看到"图片压缩"资料后，可能会将压缩过程中的异常处理（如格式不支持、内存溢出）带入上传组件的设计——这些以"相似话题"为伪装进入上下文的信号，造成的干扰往往比明显无关的噪声更难排查。

## 三、核心内容：上下文质量的六个风险维度

### 3.1 从"纯度"到多维度质量

在日常讨论中，我们常用"上下文纯度"（Context Purity）这个直觉描述来指代"会话历史中有多少内容与当前任务相关"——这是一个方便的日常用语。但如果将"纯度"当作一个可精确计算的单轴度量来对待，就会产生两个问题：其一，它暗示存在一个单一的、可线性排序的"干净程度"标尺；其二，它鼓励为这个标尺寻找数学包装，而实际的上下文质量问题分布在上游的多个独立维度上。

以下六个维度各自以不同的方式影响 Agent 在长会话中的执行质量。它们不是相互独立的——低相关性常常与过期信息并存，高冲突率往往伴随状态不一致——但分别对待它们比用一个综合分数更有诊断价值。

### 3.2 维度一：相关性（Relevance）

**定义：** 上下文中的信息与当前任务目标的匹配程度。

**影响机制：** 无关信息占据上下文容量，增加模型在生成每个 token 时需要"略过"的 token 数量。这不是说无关信息会"抢走注意力"——模型可以通过注意力机制高度聚焦于相关内容——而是说长上下文中无关内容的绝对数量增加了模型检索相关信息的难度，在长距离依赖场景下尤其显著。

**典型表现：** Agent 产出中混入之前任务的概念、术语、或未完成的推理片段。

**注意事项：** 相关性是最直观的维度，但不是唯一的维度。一个"完全相关"但相互矛盾的上下文同样会损害输出质量——这就是下一个维度的内容。

### 3.3 维度二：冲突率（Conflict Rate）

**定义：** 上下文中间接或直接相互矛盾的指令、信息或结论的数量与严重程度。

**影响机制：** 当模型在同一上下文窗口中看到"用方案A"和"方案A被否定了"两种信息时——即使它们指向不同的历史时间点——模型需要在没有明确时间标记的情况下自行判断哪个是"最新有效的"。这个判断过程引入了不确定性，而不同的推理路径可能得出不同的结论。

**典型表现：** Agent 在执行中表现出摇摆——先朝一个方向走几步，又突然折返；或者在输出中同时包含相互矛盾的建议。

**与相关性的交互：** 高相关性 + 高冲突率是一个特别危险的组合。信息都是"相关的"，但指向不同的结论，模型没有简单的方式判断取舍。

### 3.4 维度三：新鲜度（Freshness）

**定义：** 上下文中信息的时效性——即信息是否反映当前状态、而非已被更新的过往状态。

**影响机制：** 过时的工具调用结果（如"文件 X 的内容是 Y"，但文件已被外部修改）、已被后续讨论推翻的早期结论、以及基于旧环境变量做出的判断——这些信息在上下文中依然存在，但不再准确。模型通常不会主动质疑自己之前输出的正确性，因此过期信息会在上下文中以"事实"的面貌持续存在。Agent 看到自己 20 轮前写的"当前状态是 A"，它没有理由怀疑这句话——除非外部工具调用返回了矛盾信息并触发了重新评估。

**典型表现：** Agent 基于已被修改的文件内容做决策、使用了已被弃用的 API、或引用了已被用户明确否定的方案。

### 3.5 维度四：状态一致性（State Consistency）

**定义：** 上下文中所描述的系统状态（文件内容、环境变量、服务状态、进程状态等）与实际运行时状态之间的一致程度。

**影响机制：** 这是新鲜度在系统状态层面的具体化。但与"过期信息"不同，状态不一致可能来自模型自己没有参与的外部变更——另一个进程修改了文件、管理员调整了环境变量、定时任务更新了数据库。Agent 的上下文中有"上一次查询时的状态快照"，但那个快照已经过时了，而 Agent 不知道它过时了。

**典型表现：** Agent 读取一个文件、缓存了它的结构、然后基于缓存的结构做操作——但文件在两次操作之间被另一个 Agent 修改了。结果要么是操作失败（好情况），要么是基于错误状态完成了操作但产生了错误结果（坏情况）。

### 3.6 维度五：来源可信度（Source Reliability）

**定义：** 上下文中每条信息的出处及其可靠程度。

**影响机制：** 一个会话中混杂着多种来源的信息：用户明确给出的指令（最高可信度）、文件系统读取的结果（中高可信度）、模型自己的推理输出（中等可信度）、模型在之前步骤中做出的未经证实的假设（低可信度）、以及外部网络搜索返回的未验证数据（可信度取决于来源）。当这些不同可信度的信息在上下文中以同等格式出现时，模型没有天然的机制区分"这是用户说的"和"这是我在第三步推测的"。

**典型表现：** Agent 把自己的推测当作事实来引用，或者把一次失败的搜索结果当作"不存在"的证据。

### 3.7 维度六：证据可恢复性（Evidence Recoverability）

**定义：** 当上下文中的某个结论被质疑或发现错误时，能否从会话历史中追溯到该结论的原始输入和推理链条。

**影响机制：** 在长会话中，一个错误可能在第 15 轮被引入（比如一次工具调用返回了不完整的数据），但直到第 40 轮才被发现（因为基于这个数据的后续推理产生了矛盾）。如果第 15 轮到第 40 轮之间的推理链条是完整的和可追溯的，定位并修复这个错误的成本是可控的。如果中间有信息丢失——比如某个工具调用结果被后续消息覆盖、或者关键推理步骤被会话压缩机制截断——修复就变成了"基于残缺证据重新推理"。

**典型表现：** 用户说"这个结论不对"，Agent 无法追溯"这个结论是怎么得出来的"，只能从头重新推理。

### 3.8 各维度的交互与"纯度"直觉的由来

这六个维度之间的交互解释了为什么"纯度"作为一个直觉概念是有用的：当相关性低、冲突率高、新鲜度低、状态不一致、来源不可靠、证据链断裂——这些维度同时恶化时，我们直觉上感到上下文"很脏"。但如果只用一个数字去量化，就会掩盖不同维度的不同恶化模式和不同修复策略。

例如，一个会话可能相关性很高（所有内容都围绕同一个主题）但新鲜度很低（所有信息都是三天前的工具调用结果）。另一个会话可能相关性很低（多个主题混在一起）但每条信息都是最新的。这两个会话的"问题"完全不同——前者需要重新查询，后者需要任务隔离——但一个综合"纯度"分数会把它们混为一谈。

因此，上下文隔离派发的价值不在于实现某个"纯度阈值"，而在于它从结构上消除了多数维度的恶化源头——一个全新的会话天然具有高相关性（只有当前任务）、零冲突（没有历史矛盾）、高新鲜度（实时状态）、高状态一致性（初始状态是当前的实际状态）。

## 四、实现方案：派发决策与上下文隔离实战

### 4.1 派发决策矩阵

不是所有任务都适合通过新会话派发执行。派发的适用性取决于多个维度的评估。下面给出一个可直接使用的决策矩阵：

| 评估维度 | ✅ 适合派发 | ❌ 不适合派发 |
|---------|------------|--------------|
| **任务独立性** | 自包含，不依赖前面推理链中的中间结论 | 依赖多轮积累的推理过程和上下文 |
| **上下文复杂度** | 任务目标和约束可以在任务描述中完整传达 | 需要大量背景知识，任务描述写不下 |
| **预期交互轮次** | 单轮或少量轮次即可完成 | 需要多轮反馈和迭代修正 |
| **调试敏感度** | 低——结果可以直接外部验证（如文档质量、代码正确性） | 高——需要观察Agent的推理过程来定位问题 |
| **状态依赖** | 无状态，或状态可通过文件/数据库传递 | 依赖紧密耦合的运行状态（如复杂调试场景下的变量追踪） |

#### 使用方法

对每个任务，逐一评估上述五个维度。如果五个维度中的**三个以上**落在"适合派发"列，就优先使用派发方案。如果三个以上落在"不适合派发"列，则考虑在不派发的前提下做上下文裁剪。

**"不确定时"的备用策略：** 先用非派发方式执行第一轮——让主Agent在现有上下文中确认任务边界、识别依赖关系——然后基于第一轮产出的"任务边界说明"，再用派发执行实际工作。这种"先探索后执行"的两阶段策略在很多场景下优于做一次性的派发决策。

### 4.2 反面论证——子Agent什么时候反而更差

上下文隔离派发不是银弹。在某些场景下，派发子Agent不但不会提升质量，反而会显著降低效率甚至产生更差的结果。以下场景需要特别注意：

**场景一：多轮依赖型任务**

调试类任务是最典型的例子。假设主Agent已经通过几轮交互建立了完整的推理链——第一轮发现了错误日志，第二轮定位了故障模块，第三轮验证了修复方案。如果在第三轮之前的任何一个节点将任务派发出去，子Agent将丢失前几轮已经建立的"为什么走到这一步"的全部上下文。它需要从零开始理解问题，不仅浪费了之前的工作，还可能因为获得的信息不完整而得出不同的结论。

**场景二：任务边界切错**

将高耦合度的任务硬拆成独立模块后派发，是常见的错误。假设一个任务是"分析系统性能瓶颈并给出优化方案"。性能分析结果和优化方案之间存在强依赖关系——没有第一阶段的完整分析数据，第二阶段的优化方案就是空中楼阁。如果错误地将这两个阶段拆成两次独立的派发，子Agent拿到半截不自洽的指令，产出的方案会比不拆更差。

**场景三：Token开销错觉**

派发子Agent不是免费的。每次派发都要重新加载 prompt 文件（AGENTS.md、SOUL.md 等，可能几千token）、初始化工具连接、建立新的会话结构。这些开销在主Agent的上下文中已经是"loaded"状态。极端情况下，频繁派发反而增加总的 token 消耗——尤其是在短周期、多次迭代的任务中。

**场景四：跨任务状态共享的上下文成本**

子Agent的执行是一次性的。如果后一次任务依赖前一次子Agent的输出状态，就需要通过外部存储（文件、数据库）做状态传递。这个"序列化→传递→反序列化"的过程本身就在制造新的上下文——主Agent需要管理临时文件路径、版本、清理策略。当状态传递链条变长时，主Agent反而成了"状态搬运工"，上下文质量可能比不派发时更差。

**场景五：可观测性下降**

子Agent的执行过程对主Agent而言是一个黑盒。主Agent能看到任务描述和最终的返回结果，但看不到子Agent的思考过程、中间工具调用、自我反问和修正。一旦执行结果不符合预期，回溯定位根因的难度远高于非派发模式。对于调试敏感度高的任务，这是不可接受的成本。

**场景六：任务描述的"有损压缩"**

主Agent将复杂上下文压缩成一段任务描述文本，不可避免地会丢失信息。压缩率越高，丢失的原始意图和细节越多。子Agent基于压缩后的指令执行，可能在关键细节上偏离主Agent的原始目标。特别是在涉及微妙判断和权衡的任务（如架构设计、技术方案选型）中，这种"压缩损失"的影响尤为显著。

**场景七：高频迭代场景的效率损失**

每次派发都需要启动一个新会话——加载 prompt 文件、初始化工具连接、建立会话上下文。在短周期迭代任务中（如需要反复"试->改->验"多个小变体的代码调试），这个启动开销占总执行时间的比例显著上升，可能导致派发模式的实际效率低于直接在主Agent中执行。

### 4.3 上下文隔离操作指南

承认派发不是银弹之后，我们需要一个更细致的操作框架：**什么时候需要隔离上下文，以及怎么隔离。**

#### 方法论一：新会话承载新任务

最直接的方法也是最可靠的：当一个任务与当前会话中的已有任务没有依赖关系时，直接在新会话中执行。新会话天然避免了历史消息带来的各类干扰。关键工作在于判断"没有依赖关系"的边界——这需要主Agent具备任务边界识别能力。

**具体操作：** 主Agent在收到新任务时，快速扫描现有会话历史，判断当前上下文是否与任务相关。如果无关（例如正在做数据分析和用户突然说"帮我写一份文档"），应该采用派发而非在当前上下文中继续。

#### 方法论二：显式标注上下文边界（中间态，不推荐）

部分框架支持给消息添加元标签或显式标记"以下是无用历史请忽略"。这种方法的优点是快速——不需要创建新会话——但缺点是把"上下文裁剪"的责任丢给了模型，让模型自己判断哪些历史应该被忽略。模型的判断不一定可靠，且这种标注本身也在占用上下文窗口。

**适用场景：** 短期过渡——在无法快速派发的环境中的临时方案。不推荐作为长期策略。

#### 方法论三：提取精华→写入文件→子Agent读文件（推荐）

这是目前最实用、效果最稳定的上下文隔离模式。它的核心思想是：**不要试图通过参数传递上下文，而是通过文件系统传递。**

**执行流程：**

1. **主Agent裁剪：** 主Agent在当前上下文中，将"与当前任务真正相关"的信息提取出来——包括关键结论、数据、约束条件等。这一步的本质是主Agent做一次有损压缩，但压缩的对象是"任务相关的信息"而非"所有历史"。
2. **写入文件：** 将提取后的信息写入一个临时文件（或固定位置的文件）。
3. **派发子Agent：** 通过任务描述告诉子Agent"请读文件 X，基于其中的内容执行任务 Y"。
4. **子Agent执行：** 子Agent读文件，获得纯净的上下文（不带历史噪声），基于此执行。
5. **结果回传：** 子Agent将执行结果写入输出文件，主Agent读文件获取结果。

**关键优势：** 文件作为中介解耦了主Agent和子Agent的上下文。主Agent不需要在参数中压缩所有信息（避免"有损压缩"问题），子Agent获取的是经过裁剪、与任务直接相关的完整信息。同时，文件的持久化特性也使得状态传递可追踪、可审计。

**成本：** 手动管理文件的生命周期——创建、清理、并发写冲突处理。在轻量级实现中，可以用固定命名约定和清理回调来管理。

### 4.4 一个实际案例：上下文隔离派发的端到端流程

以文档撰写任务为例，展示完整的上下文隔离派发流程：

1. **任务接收：** 主Agent在长期会话中收到用户请求"写一篇关于上下文隔离的技术文档"。
2. **上下文评估：** 主Agent快速扫描当前会话历史。发现当前上下文中包含之前任务的文件搜索记录、时间查询记录、关于其他技术方案的讨论。这些对写文档任务都是需要隔离的历史消息。
3. **裁剪决策：** 主Agent评估任务独立性——文档撰写是自包含的，不依赖前面的推理链。符合派发条件。
4. **上下文提取：** 主Agent从当前会话中提取与文档撰写相关的信息（包括讨论记录、暂存文件、大纲）。通过任务描述告诉子Agent"请读文件 X（大纲）和文件 Y（讨论记录），基于这些内容写文档"。
5. **派发子Agent：** 创建子Agent，任务为"请根据大纲文件 X 和讨论记录 Y，写一篇技术文档"。
6. **子Agent执行：** 子Agent在隔离的上下文中读文件、写文档。没有历史噪声干扰。
7. **结果验证：** 主Agent检查子Agent返回的结果，确认质量。

在这个流程中，主Agent的角色从"执行者"转变为"管理者"——它负责上下文评估、裁剪、调度委托，而执行本身由子Agent在隔离的上下文中完成。

#### 文件中介模式的变体与权衡

文件中介存在几种变体，其选择取决于任务的复杂度和对实时性的要求：

**变体一：单文件模式。** 所有上下文写入一个文件，子Agent一次性读取。适用于简单、自包含的任务。优点是实现简单，缺点是文件内容会随着任务复杂度增长而膨胀。

**变体二：结构化多文件模式。** 主Agent将上下文按类型拆分到多个文件——一个放任务说明，一个放参考资料，一个放约束条件。子Agent按需读取。适用于需要精细控制上下文的复杂任务。优点是上下文结构清晰，缺点是需要管理文件间的交叉引用和一致性。

**变体三：增量文件模式。** 主Agent不是一次性写入所有上下文，而是在子Agent执行过程中按需写入。子Agent每完成一个阶段，主Agent评估下一阶段需要什么上下文、写新文件、子Agent继续。适用于迭代式任务（如逐步扩充文档、分阶段调试），优点是上下文精确到每个阶段所需的最小集合，缺点是增加了主Agent的交互轮次和管理负担。

### 4.5 QwenPaw 中的子 Agent 创建模式

> **提示：** 本节的讨论以 QwenPaw 框架的 `spawn_subagent` 为具体案例。不同框架的子Agent创建机制语义不同，请以所用框架的文档为准。

QwenPaw 的 `spawn_subagent` 工具通过 `fork` 参数提供两种子Agent创建模式：

**fork=False（默认）：** 子Agent启动一个全新的、空的会话上下文。它不继承父会话的任何对话历史或持久化状态。子Agent在工作区的原始目录中运行。这是上下文最干净的派发方式——子Agent的初始会话历史只包含任务描述，没有任何历史残留。

**fork=True：** 子Agent同样启动一个全新的对话上下文（不继承父会话的对话历史），但它会接收父会话持久化状态的副本，并在 Git 仓库中使用独立的 worktree 运行，以避免文件变更与父Agent或其他子Agent发生冲突。

**实践中的选择：** 对于大多数纯文档处理、文本生成、分析类任务，`fork=False` 是更简单直接的选择。对于需要访问父会话中累积的持久化状态、或需要在隔离的文件环境中操作的任务，`fork=True` 的 worktree 隔离是一个有价值的特性。但需要注意，持久化状态的继承可能引入隐式依赖——父会话修改了某个全局配置，子Agent在未被告知的情况下继承了这个修改，可能导致行为与预期不一致。

### 4.6 上下文隔离派发的运维考量

将上下文隔离派发引入生产环境后，以下几个运维层面的问题需要提前规划：

**文件生命周期的管理。** 中介文件会在文件系统中持续累积。需要制定清理策略——基于时间（如任务完成后立即清理）、基于空间（设定临时目录上限）、或基于引用计数（文件未被任何活跃子Agent引用时清理）。如果清理不及时，这些文件本身会成为新的噪声源——其他Agent在全局文件搜索时会搜到失效的上下文。

**并发冲突的处理。** 在多Agent场景中，多个子Agent可能同时写入同一个输出目录。如果没有命名空间隔离，一个子Agent可能覆盖另一个子Agent的中间产物。简单的解决方案是按任务ID或时间戳为每次派发创建独立的工作目录。

**可观测性补偿。** 子Agent的执行是黑盒，但运维层面需要知道"它经历了什么"。一个可行的方案是让子Agent在关键节点写入进度文件——类似于日志中的 checkpoint。这样主Agent不需要实时观察子Agent的推理过程，但在排查问题时可以回溯子Agent的执行轨迹。

**上下文缓存策略。** 如果同一个任务背景需要被多个子Agent使用（如一个大型项目的架构说明），每次都由主Agent写文件会造成冗余。可以考虑在文件系统层面做一个轻量级上下文缓存——主Agent先检查缓存中是否有适配的上下文快照，有就直接引用，没有再写。这能显著减少主Agent的上下文裁剪工作量。

## 五、扩展讨论

### 5.1 上下文管理自动化的正循环

从更宏观的角度看，上下文隔离派发不仅是一个技术方案，更代表了一种自动化趋势。

**手动时代：** 人类用户在脑中整理上下文——回忆哪些信息与当前任务相关、哪些历史可以忽略——然后手动写进 prompt 发给 AI。上下文裁剪由人类完成，人在回路中既是瓶颈也是质量保障。

**代理时代：** 主Agent自动完成上下文评估和裁剪工作。它判断"当前任务需要什么信息、不需要什么信息"，然后通过派发将执行交给子Agent。人类从上下文管理的劳动中解放出来，专注于更高层的方向性决策。

**正循环的运作机制：**

```
主Agent裁剪上下文 → 子Agent高质量执行 → 用户对派发模式产生信任 →
用户更主动地使用派发模式 → 主Agent的上下文负担减轻 →
上下文中的历史消息积累速度变慢 → 裁剪时面临的信息量更小 → 裁剪更精准 →
子Agent获得更高质量的输入 → 执行质量进一步提升
```

这个正循环一旦建立，不仅提升单次任务的质量，还通过"反馈环路"持续优化整个系统的上下文管理能力。

**当前状态：** 这是一个设计模式（design pattern），不是框架特性。它的运行依赖主Agent的"自觉性"——准确判断什么时候该派发、要裁剪什么、怎么裁剪。当主Agent自身上下文已被污染时，它的判断质量会下降，正循环可能演变为负循环。

**核心瓶颈：** 主Agent的裁剪质量受其自身上下文污染程度的影响。这是一个递归问题：上下文被污染了的主Agent，做不好上下文裁剪。解决这一递归的工程路径包括：

- 在系统层面设计"健康度检查"——当主Agent上下文出现明显的质量下降信号时，主动将控制权交给一个新会话
- 为关键判断（如派发决策）引入独立的验证步骤——不裁剪直接派发某个子Agent专门评估"当前上下文中是否有足够的任务相关信息"

### 5.2 多Agent框架的上下文管理设计对比

不同框架在上下文管理和子Agent机制上存在显著差异，直接影响上下文隔离派发模式的可落地程度。

#### 框架横向对比

| 维度 | OpenAI Swarm | CrewAI | AutoGen (v0.4) | LangGraph |
|------|-------------|--------|---------------|-----------|
| **上下文传递方式** | Agent切换时共享完整对话历史 | Task定义中显式传递 context 参数 | 对话历史可被裁剪后传递 | 通过结构化 State 在节点间传递 |
| **上下文隔离控制** | ❌ 无原生支持 | ⚠️ 设计阶段可以裁剪 context | ⚠️ 可通过配置对话历史范围手动控制 | ✅ 图结构层面有更强的控制力 |
| **子Agent机制** | Handoff（移交）——当前Agent将控制权转给另一个Agent | 通过 Task 编排——每个 Task 绑定特定 Agent | 嵌套对话——Agent之间独立会话 | 节点执行——每个 node 可以是独立 Agent |
| **异构模型支持** | ❌ 全部Agent共享同一个模型配置 | ⚠️ 可指定 llm 参数，但底层限制在同 API provider | ✅ 每个 Agent 有独立的 llm_config 配置 | ✅ 节点级别可绑定不同的 ChatModel |
| **上下文自动化程度** | 无——开发者手动管理全部上下文传递逻辑 | 低——Task context 需要开发者手动提取和传入 | 中——支持自动摘要和对话历史裁剪 | 中高——State 结构由开发者设计，运行时可灵活读写 |
| **上手复杂度** | 极低——API设计简洁，理念清晰 | 低——面向任务的抽象直观易懂 | 高——配置选项多，学习曲线陡峭 | 高——需要理解图执行引擎和状态管理 |

> **注意：** OpenAI Swarm 已由 [OpenAI Agents SDK](https://github.com/openai/openai-agents-python) 取代。上表保留 Swarm 因为它是许多早期讨论的参考点，但在实际选型时应以 Agents SDK 为准。

#### 核心发现

**没有一个主流框架真正实现了"运行时上下文管理自动化"。**

LangGraph 的 State 设计是最接近上下文隔离派发理念的。开发者可以显式定义 State 的结构——限定哪些信息在节点之间传递、哪些不传递——从而在架构层面避免"历史全部传递"的问题。但 State 结构是静态的：你在设计 Graph 的时候定义它，运行时不自动做上下文裁剪。你需要自己决定"什么信息是任务相关的、什么不是"。

Swarm 和 CrewAI 的简化设计在日常使用中效率很高，但它们共享完整上下文的模式意味着上下文中的干扰信息在所有Agent之间传播——一个Agent的噪声会变成所有Agent的噪声。

AutoGen 的配置灵活性是双刃剑：你可以手动实现上下文裁剪，但没有框架层面的机制保证一致性。

**Gap 分析：** 框架层的缺失给开发者留下了一个设计空间——是否可以通过中间件或 wrapper 实现运行时上下文裁剪？一个理论上可行的方案是：在框架的消息路由层注入一个"上下文过滤器"节点，在消息传递到子Agent之前自动丢弃与当前任务无关的历史消息。但这需要对框架源码有侵入式修改。

### 5.3 模型分层经济学：调度层与执行层

上下文隔离的讨论还可以延伸到模型经济学的维度：不同层级的 Agent 可能需要不同智能等级和不同价格的模型。

#### 调度层：不需要高智商

调度层的核心任务是判断——"这条内容该放哪个分类"、"当前任务的边界在哪里"、"是否需要创建子Agent"、"任务是否完成"。这些任务的特征是：

- **决策空间有限：** 大部分调度决策是二分或三选一
- **不需要创造力：** 不需要生成新内容、不需要架构创新
- **需要的是稳定性和可预测性：** 同一个输入产生同一个输出

在这个约束下，给调度层用顶级模型（如 GPT-4o、Claude Opus）是资源浪费。大量实践经验表明，一个经过良好配置的轻量模型（如 GPT-4o-mini、Claude Haiku）在调度任务上的表现与顶级模型没有本质差异。

#### 执行层：才真吃模型能力

真正需要模型边际智能提升的场景是执行层：

- **文档写作：** 结构的取舍、例子的选择、语言的克制——每个决策都在无数个合理选项中找出最合适的一个
- **复杂代码的设计：** 不是写一段能跑的代码，而是写一段结构清晰、可维护、边界条件完善的代码
- **微妙判断的需求：** 在上下文敏感的任务中，轻量模型可能因为理解偏差而产生偏离目标的结果

在执行层，模型的智能水平直接决定了输出质量的上限。

#### 理想调度模型 vs 当前约束

**理想方案：** 便宜模型（如 GPT-4o-mini、Claude Haiku）做 orchestration（调度、裁剪、路由），贵模型（如 GPT-4o、Claude Sonnet/Opus）做 execution（执行、创作、架构）。

**现实约束：** 大多数主流框架在默认配置下，子Agent使用与主Agent相同的模型配置。这是因为同构架构的设计理念——简化部署和成本管理——但代价是放弃了模型分层经济学带来的效率提升。

**该约束的例外：** AutoGen 允许每个 Agent 配置独立的 `llm_config`，LangGraph 允许节点级别绑定不同的 ChatModel。这意味着在这些框架中，你可以手动实现异构模型调度——但需要开发者侵入式配置。当前还没有框架提供"自动根据任务类型选择模型"的能力。

**给实践者的启发：** 如果你已经使用了支持异构模型配置的框架（AutoGen、LangGraph），你只需要多做一步——为调度层的 Agent 配置一个便宜模型，为执行层的 Agent 配置一个贵模型——就能以较低的成本获得系统整体效率的提升。

### 5.4 Tag与分类系统的调度价值

在多Agent系统中，tag/分类系统不只是元数据管理工具，它们本身就是**调度决策的输入信号**。

当主Agent需要判断"这条内容该放哪个库""这个任务该交给谁执行"时，一个结构化的 tag 分类系统可以直接缩小决策空间。主Agent不需要自己在上下文中搜索、判断、推理——它只需要匹配 tag。

**正向链路：** 好的标签分类系统 → 更精准的任务路由 → 更少的上下文噪声 → 更高的执行质量。

**反向链路：** 没有结构化分类 → 主Agent每次都需要自己"判断这是什么东西" → 每次判断都在制造新的上下文噪声 → 执行质量下降。

这意味着，tag/分类系统本身也是上下文管理的一部分。一个主Agent如果能在上下文中直接识别"这条内容的 tag 是 `Agent工程化/上下文管理`"，它就不需要去回忆"之前有没有类似的内容、应该放哪里"，避免了判断噪声的产生。

### 5.5 上下文质量的负循环与止损策略

上下文质量和派发模式的选择不是一次性决策，它会自我强化。一旦走上正确的方向，系统会越来越好用；一旦走上错误的方向，系统会越来越难纠正。

#### 正循环

正循环的链条是这样的：

父Agent能够准确判断哪些任务适合派发、哪些不适合。对于适合的任务，它能写出精确的任务描述——包含完整的需求描述、约束条件、输出格式、参考示例。子Agent接收到的是隔离的上下文：只有任务描述中的信号，没有历史消息中的噪声。子Agent能够高质量地完成输出——精确、规范、一次通过。

高质量的输出让用户满意。模式稳定后，用户更愿意让父Agent通过派发模式委托子任务，而不是要求"让我看着你一步步做完"。父Agent的负担减轻——它不需要亲自执行每个子任务，只需要做任务切分、任务描述撰写和输出验证。随着父Agent不再亲自执行大量子任务，它的上下文也保持相对干净——没有被各种子任务的中间输出和工具调用日志填充。干净的上下文反过来让父Agent在写任务描述时更精准，进一步提高了子Agent的输出质量，形成一个自我强化的正反馈循环。

**正循环的启动条件：**

- **条件一：** 父Agent具备基本的派发决策能力。这不是要求父Agent能在所有场景下做出完美决策，它需要的是在大多数常见场景中能够判断"这个任务不依赖推理链""这个任务的背景信息可以压缩为任务描述""这个任务不需要多轮迭代"。这个能力要么通过明确的规则定义（AGENTS.md中的决策矩阵），要么通过多次失败后的模式识别来建立。
- **条件二：** 任务描述质量足够好。任务描述是父Agent和子Agent之间唯一的沟通通道。任务描述不精确，子Agent再强也没用。高质量的任务描述不仅包含"做什么"，还包含"不做什么"——明确排除的边缘情况往往比核心需求更能约束子Agent的输出偏差。一条常见的反直觉规则是：写任务描述时，多花30%的功夫在排除不相关方向和约束条件上，这个投入会在子Agent的输出质量上获得数倍回报。
- **条件三：** 用户信任这个模式。初始阶段的用户很可能对派发模式持观望态度。这里需要父Agent给出可验证的证据：子Agent的输出是否符合预期、任务描述是否精准、哪次派发成功哪次失败。前几个子任务的成功，是赢得用户信任的最有力论据。一旦信任建立，用户会更倾向于让系统自主运行，从而加速整个正循环。

#### 负循环

负循环的起点往往是"一次看起来无害的省略"。父Agent的上下文因为各种原因积累了越来越多的历史消息——历史任务残留开始累积、早期失败的尝试记录没有被清理、来自多个子任务的中间回传结果在父Agent的会话中层层堆叠。

积累了过多历史消息的父Agent写不出精确的任务描述。不是因为它不想写好，而是因为它自己的上下文中混入了大量无关信息。它在写任务描述时引用了错误的历史任务数据作为参考、忽略了当前任务的某些约束条件（那些约束被淹没在无关信息中了）、对任务边界的判断产生了偏差。

子Agent接收到一个写得不精确的任务描述，输出出现偏差。父Agent检查子Agent的输出时发现问题，然后选择一个最常见的修复手段——亲自重做。父Agent亲自执行了子Agent本应完成的任务，在这个过程中产生的工具调用日志、中间输出、被纠正的部分、思考过程，全部作为新内容写入了父Agent的上下文，进一步加重了上下文的负载。下一次派发决策时，父Agent面对的是更加拥挤的上下文——任务描述写得更加不精确——子Agent偏差更大——父Agent再次亲自重做——上下文进一步累积——进入一个不断加速的恶性螺旋。

**识别负循环的关键信号：** 连续2到3次派发失败——子Agent的输出总是明显偏离预期，而每次都需要亲自重做或大幅度修改。如果这个模式在短期内反复出现，系统就进入了负循环。

#### 止损策略

负循环一旦建立，在当前会话中修复它的难度极高——因为修复需要"先为主Agent减负"，而在已经被历史消息填满的上下文中评估什么该留什么该删，这个评估本身的质量也受到影响。

一种有效的止损手段是创建一个新的空会话，不继承任何历史。在新会话中，上一轮的所有上下文负载被物理切断。父Agent从一个干净的起点重新开始，改写之前失败的任务描述，重新派发子Agent。

这不等同于"从头再来"。上下文中积累的有价值信息可以通过文件化保存——将前几轮的经验摘要、关键结论和待办事项写到一个外部文件中，新会话的父Agent读取该文件即可恢复最关键的状态。这种策略的核心思想是：保留信息（通过文件），切断噪声（通过新会话）。其他可选策略还包括：摘要式上下文重建（将长会话历史压缩为结构化的任务摘要）、检索式历史（按需检索相关历史片段而非全部携带）、以及状态快照（定期将关键状态固化到文件，清理上下文后从快照恢复）。

## 六、总结

### 6.1 核心观点回顾

多Agent系统中子Agent执行质量高于主Agent的现象，其核心原因在于**上下文中的历史消息在相关性、冲突率、新鲜度、状态一致性、来源可信度和证据可恢复性六个维度上影响了模型的输出质量**。同样的模型在隔离上下文中的表现，往往优于在累积了大量历史消息的上下文中的表现。

上下文质量不需要通过数学公式来量化。本文提出的六个风险维度提供了一个诊断框架——当Agent表现下降时，可以逐一排查是哪个维度出了问题，而不是笼统地说"上下文太长了"或"上下文不干净"。不同维度的恶化有不同的修复策略：相关性低需要任务隔离，冲突率高需要清理矛盾指令，新鲜度低需要重新查询，状态不一致需要同步，来源不可靠需要标注出处，证据链断裂需要重建推理路径。

派发决策不是无脑全上。本文提供的决策矩阵给出了五个维度的判断标准，帮助开发者在"独立自包含任务"和"多轮依赖任务"之间做出区分。反面论证中列出的七个场景，可以作为派发决策前的质量门禁。

"上下文隔离派发"（Context-Isolated Delegation）——主Agent负责评估和裁剪、子Agent负责执行——是目前经过实践验证的设计模式。它不是一个框架特性（目前没有主流框架原生支持），而是一个可以被任何框架采纳的设计模式。

### 6.2 给实践者的快速决策指南

**如果你遇到的情况是：** Agent输出越来越啰嗦、偏离主题、混淆不同任务的内容。

→ **优先检查六个维度的质量。** 查看会话历史的长度和内容构成。如果明显存在多任务混合、大量过期工具调用或交互噪声，考虑将当前任务切分或派发子Agent执行。

**如果你遇到的情况是：** 子Agent反复出错、不理解任务背景、产出偏离预期。

→ **优先检查任务描述是否存在"有损压缩"问题。** 可能是主Agent在任务描述中丢失了关键上下文。考虑改用"提取精华→写入文件→子Agent读文件"的模式（方法论三），而不是继续压缩任务描述。

**如果你遇到的情况是：** 频繁派发但感觉效率没有实质性提升。

→ **检查原子化粒度是否太细。** 参考反面论证的"高频迭代"和"Token开销错觉"两个场景。如果你的任务周期很短（几轮交互即可完成），每次派发的启动开销占比显著，这时合并成更粗粒度的任务可能更高效。

**如果你遇到的情况是：** 团队正在选型多Agent框架。

→ **将上下文管理能力纳入评估维度。** 选择支持异构模型配置的框架（AutoGen、LangGraph），为调度层和执行层预留模型分层的空间。这不仅影响执行质量，还影响 token 成本。

### 6.3 知识缺口与相关研究

以下问题在本文的写作过程中被识别为开放问题，值得进一步探索：

1. **递归派发的收敛性。** 主Agent派发子Agent → 子Agent执行多轮后也被历史消息填满 → 子Agent自己派发子Agent。这个递归链是否能收敛？是否存在一个工程上限——嵌套多少层之后，收益就不再超过派发的开销？

2. **上下文质量的自感知。** 能否让 Agent 感知自身当前的上下文质量状态——比如识别到"相关性正在下降"或"冲突率正在上升"——然后主动触发派发？这种自感知是否会导致新的干扰（"我在想我是不是上下文质量下降了"这个想法本身就在消耗上下文容量）？

3. **框架层的原生支持边界。** 是否存在一种通用的中间件层或 wrapper，能在不侵入框架源码的前提下实现运行时上下文裁剪？这种中间件的性能开销和实现复杂度是否可控？

4. **子Agent上下文质量衰减的积累。** 子Agent执行多轮任务后，自身的上下文也会积累历史消息。它应该在什么阈值下自己做派发？这个递归深度有什么实际工程上限？

5. **异构模型调度的 break-even 分析。** 用便宜模型做裁剪+路由、贵模型做执行，总 token 成本与纯用贵模型的 break-even 点在哪个任务规模和复杂度下出现？小规模任务中异构调度的开销是否高于其带来的效率收益？

#### 值得关注的相关研究

- **[More Skills, Worse Agents?](https://arxiv.org/abs/2605.24050)：** 发现 Skill 库扩张时，上下文长度增加本身对 Agent 表现的影响在统计上接近零；真正的问题是 Skill shadowing（选错 Skill）。**注意：** 这一发现特指 Skill 库扩张场景——在该场景中，Skill 描述文本的语义密度高，简单的长度增加不会显著稀释注意力。在其他场景（如工具调用日志累积、多任务历史混杂、交互噪声堆积），上下文负载的影响模式可能不同，不应将这一发现直接推广。
- **[Less Context, Better Agents](https://arxiv.org/abs/2606.10209)：** 裁剪加摘要能显著改善效果，但证明了在特定工具工作流中选择性保留的有效性，不能从中推出普适的"上下文定律"。
