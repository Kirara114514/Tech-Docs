# 多Agent架构中上下文纯度与执行质量的关系

> **一份关于"为什么子Agent总是比主Agent做得更好"的系统分析**

---

## 一、摘要

在构建多Agent系统时，许多实践者会遇到一个反直觉的现象：同一个模型、同一套工具集、同一组身份指令，通过 `spawn_subagent(fork=False)` 分配的任务，其执行质量几乎总是优于在一个长期会话中运行的主Agent。本文将这一现象归因于**上下文纯度**（Context Purity）——会话历史中任务相关信息与噪声的比例。我们提出"上下文净化派发"（Clean Context Delegation）这一设计模式，并构建了上下文纯度的形式化度量框架、面向实践者的 spawn 决策矩阵、以及与框架选型、模型分层经济学的交叉分析。全文旨在说明：提升多Agent系统执行质量的最直接路径，不是换更好的模型，而是让当前模型工作在更干净的上下文中。

---

## 二、背景：一个反直觉的现象

### 2.1 相同的Prompt，不同的结果

假设你正在构建一个AI写作辅助系统。主Agent已经在一次会话中执行了若干任务——帮用户查了一下当前时间、回顾了之前的笔记、讨论了某个技术方案的可行性、纠正了一次工具调用的参数错误。会话历史已经积累了数十轮消息。此时，用户说："帮我写一篇关于多Agent架构的技术文档。"

有两种处理方式：一是直接用主Agent在当前上下文中执行；二是通过 `spawn_subagent(task="写一篇关于多Agent架构的技术文档", fork=False)` 创建一个子Agent来执行。

实验结果是令人震惊的。主Agent产出的文档中会残留之前讨论中的表述习惯、错误纠正的自我审查痕迹、甚至出现与当前任务无关的引用。而子Agent产出的文档结构清晰、目标明确、语言干净，就像一个完全不同的模型在干活。

关键控制变量完全相同：两个Agent读同样的 `AGENTS.md` / `SOUL.md` / `PROFILE.md` 文件，使用同样的工具集，访问同一个文件系统，甚至背后是同一个模型实例。唯一的变量是**上下文的负载状态**。

这不是一次偶然。在多次复现中，这一差异持续存在。它不是心理作用，不是模型随机性，而是多Agent系统中的一个结构性现象。

### 2.2 排除其他可能的原因

在确定"上下文负载"是根因之前，我们需要严谨地排除其他假设：

**模型差异。** 会不会是子Agent被路由到了更强的模型实例？在现代Agent框架中，子Agent默认继承主Agent的模型配置。如果框架支持异构模型，需要显式指定。在同一个框架实例、同一个模型API密钥、同一时间窗口内，模型不是差异来源。

**Prompt差异。** 子Agent读到的身份指令和主Agent一样——都是从文件系统加载的 AGENTS.md、SOUL.md 等。没有人为子Agent设计过更优的prompt。如果prompt是相同的，那么差异不来自prompt。

**工具集差异。** 子Agent拥有和主Agent完全相同的工具集——文件操作、搜索、子进程执行等。没有为子Agent禁用某些工具，也没有专门给它加工具。

**新鲜感效应。** 这是最容易被忽视的心理学干扰——"新的看起来更好"。但这一现象在跨模型、跨框架、跨任务类型的多次复现中保持稳定，且差异幅度一致。如果是新鲜感效应，随着子Agent会话变长，质量优势应该衰减。但即使子Agent已经执行了若干轮任务，新spawn的子Agent依然表现更好。

排除所有这些可能性之后，方向很明确：差异在上下文负载。

### 2.3 根因：上下文纯度

**上下文纯度**（Context Purity）定义为：当前任务的会话历史中，与任务目标直接相关的信息所占的比例。相关内容的占比越高，上下文纯度越高。

主Agent的上下文污染有多种来源：

- **之前任务的工具调用日志：** 查时间、搜文件、执行脚本——每一次工具调用的输入和输出都完整保留在会话历史中。这些日志对当前任务毫无意义。
- **中间输出和修正过程：** 用户纠正了一个错误——"不对，这个路径错了""参数传错了"——这轮纠错对话占用了若干消息。它在当时有价值，但对新任务完全是噪声。
- **对话开场的无意义问候：** "你好""早上好""我们开始吧"——这些人类社交礼仪在Agent上下文中是零信息量的占位符。
- **多任务混合：** 用户在同一会话中切换了多个主题。每个主题的讨论历史对其他主题都是干扰。

每一条噪声消息都在稀释模型对当前任务的注意力。

相比之下，`spawn_subagent(fork=False)` 创建的是纯净的新会话。它的会话历史只包含一条消息——task参数带来的指令。会话历史长度为1时，如果这条指令与任务目标完全相关，上下文纯度就是1。不存在"之前任务"的残留，不存在纠错过程的自我审查痕迹，不存在多任务混叠。

这就是"同样的模型、同样的prompt、同样的工具集，子Agent做得更好"的完整解释：不是子Agent更聪明，是它的上下文更干净。

## 三、核心内容：上下文纯度拆解

### 3.1 注意力稀释：为什么历史消息会成为负担

上下文纯度之所以影响执行质量，根本原因在于Transformer架构的注意力机制存在一个内在约束：**每个token获得的注意力权重总和是固定的**。

在Transformer的自注意力层中，softmax函数将输入序列中的每个token映射到一个注意力分布，所有token的注意力权重之和为1。这意味着，序列越长，每个token平均分到的权重越少。当无关token占据序列长度时，关键token能获得的关注度就被稀释了。

一个直观的比喻：想象你在嘈杂的食堂里和朋友聊天。背景噪音本身不大——没有人在尖叫或砸桌子——但足够让你偶尔听漏朋友说的关键词。你需要的不是更大的音量，而是更安静的环境。

对于LLM而言，上下文中的无关消息就是"背景噪音"。它不是响亮的干扰，但它持续占据注意力资源，让模型对当前任务关键信息的敏感度下降。这不是模型"不聪明"的表现，而是注意力机制工作方式的结构性结果。

更进一步，注意力稀释存在一个被低估的连锁反应：**已生成内容的崩溃性退化**。LLM 的生成过程是自回归的——每一步的输出依赖于之前所有步的输出。当上下文中的噪声导致模型在某一步出现了理解偏差，这个偏差会沿着生成链条持续放大。因为模型会把自己的错误输出也当作"已生效的上下文"继续推理，噪声从"外部历史"演变为"内部错误"，纯度从模型输入层面被进一步破坏。

从信息论的视角来看，会话历史中的每条消息可以抽象为一个三元组：消息类型（工具调用日志、用户指令、模型回复、系统提示），语义距离（与当前任务目标的语义相似度），和时效性（距离当前消息的轮次偏移）。噪声消息在多维空间中同时具备高语义距离和高时效偏移的特征。上下文纯度的本质是在多维特征空间中做信号分离——识别哪些消息属于当前任务的信号空间。

这使得上下文净化派发不仅仅是"干净 vs 脏"的二分，而是一个连续谱：从长会话的深度污染（多任务混叠 + 多轮纠错 + 工具日志），到短会话的轻度污染（仅含少量无关问候），到纯净会话的零污染。越靠近纯净端，自回归链条的初始状态越理想，对后续每一步的质量影响呈指数级放大。

值得注意的是，注意力稀释并不只在极端场景（128K上下文窗口填满）下才显著。一个只有20轮消息的会话中，如果其中5轮是无关的（跨任务的工具调用、被纠正的中间产物），注意力窗口中被稀释的比例是25%。在每次推理中，这25%的无关 token 都会挤占模型对85%关键内容的关注——不是说"信息够多就行"，而是"噪声的比例决定了注意力分配的效率上限"。

这一效应与模型的上下文窗口大小无关。一个支持128K上下文窗口的模型，如果其中120K都是无关历史，它的任务表现大概率不如一个上下文只有4K但全是任务相关内容的小窗口模型。上下文窗口大不等于上下文质量高——这常被从业者忽视。

从这个角度看，"上下文净化派发"的本质不是发明了一种新机制，而是在承认注意力机制固有局限的前提下，做了一种工程上的规避策略：不给模型执行质量下降的机会。

### 3.2 上下文纯度的度量指标

要讨论"提升上下文纯度"，首先需要回答一个问题：**纯度怎么量化？**

理想的纯度度量需要满足以下条件：

1. **可计算：** 不需要模型内部的hidden states或attention weights，纯属输入输出层面可获取的信息。
2. **可比较：** 不同会话、不同任务之间的纯度值有相对可比性。
3. **与经济指标相关：** 纯度值变化与任务执行质量变化正相关。

我们评估了多种方案，下面逐一分析。

#### 方案一：任务相关性召回率

这是最精确的方案——通过attention weight可视化，计算模型在推理时实际关注的token中、与当前任务相关的比例。但它的致命缺陷是可用性：大多数闭源模型不提供attention weight输出（OpenAI API、Claude API均不支持），且即使开源模型提供，提取attention weight也需要侵入式修改推理流程，不适合生产环境使用。

**精度：高 | 可操作性：极低 | 依赖：模型内省能力**

#### 方案二：上下文压缩比

将当前会话历史压缩为摘要后，计算压缩前后的信息保留率。如果摘要保留了90%的任务相关信息，那么纯度接近0.9。这一方案的可操作性高于方案一，但存在两个问题：一是摘要本身的质量影响度量结果（如果摘要步骤就产生了信息丢失，度量值天然偏小）；二是"任务相关信息"的界定需要人工标注，无法自动化。

**精度：中 | 可操作性：中 | 依赖：高质量的摘要模型**

#### 方案三：任务成功率对比

这是最直接的方案——控制其他变量，逐一减少上下文中的历史消息，观察任务成功率的变化曲线。当减到某一点后成功率不再提升，就找到了当前任务的"最小有效上下文"。这条线以上的历史消息就是噪声。

但它的成本极高：每次度量需要运行多组实验，且结果只能反映该任务在特定条件下的表现，推广性有限。

**精度：最高 | 可操作性：最低 | 依赖：大量实验轮次**

#### 方案四：上下文年龄加权模型（推荐）

给出一个不需要模型内省、不需要人工标注、纯计算的proxy metric。

定义消息 `m_i` 的年龄权重为：

```
W_i = e^(-λ · age(m_i))
```

其中 `age(m_i)` 是消息 `m_i` 在当前会话历史中的位置偏移——从当前消息往前数第几条（当前消息 age = 0，上一条 age = 1，以此类推）。`λ` 是衰减系数，控制年龄权重的衰减速率。

会话的年龄加权纯度定义为：

```
P_session = (1/N) · Σ W_i · rel(m_i)
```

其中 `N` 是会话历史总消息数，`rel(m_i)` 表示消息 `m_i` 是否与当前任务相关。

在 `rel(m_i)` 难以获取的实用场景下，可以简化为：

```
P_session ≈ (1/N) · Σ W_i
```

这一简化假设"旧消息的价值整体低于新消息"。虽然不精确，但在绝大多数实际场景中成立——大部分旧消息本身就是噪声，少量有价值的旧信息也已经被通过文档摘要或文件固化到了当前上下文中。

**为什么推荐它？**

- 不需要模型logprobs、不需要attention weight可视化、不需要人工标注
- 只需要消息序号和一条简单的数学公式
- 计算成本几乎为零，可以在不增加推理延迟的前提下实时评估
- λ衰减系数可以通过方案三（任务成功率对比）做定期校准

**λ的校准方法：**

- 固定所有其他变量（模型、prompt、任务类型、工具集）
- 改变 λ 值运行同一组任务
- 绘制"λ-任务成功率"曲线
- 曲线上的拐点（再增加 λ 不再提升成功率的点）即为该环境的推荐 λ

实际经验表明，在典型的Agent工作流中，λ 取 0.3 ~ 0.5 效果较好——这意味着大约 5~7 轮前的历史消息权重已经降到可忽略水平。

#### 各方案对比总览

| 方案 | 精度 | 可操作性 | 运行成本 | 模型内省依赖 |
|------|------|---------|---------|------------|
| 任务相关性召回率 | 高 | 极低 | 中 | ✅ 需要 |
| 上下文压缩比 | 中 | 中 | 中 | ❌ 不需要 |
| 任务成功率对比 | 最高 | 最低 | 极高 | ❌ 不需要 |
| **年龄加权模型（推荐）** | 中等 | **高** | **极低** | ❌ 不需要 |
| 困惑度偏移 | 中 | 中低 | 低 | ⚠️ 需要logprobs |

**实际推荐组合：** 日常运行用年龄加权模型做持续监测，定期（如每周或每变更一次prompt后）用任务成功率对比校准 λ 值。这种组合在成本和精度之间取得了最佳的平衡。

### 3.3 spawn(fork=True) 与 spawn(fork=False) 的纯度差异

在多Agent框架中，spawn 通常有两种模式：

**fork=False（纯净模式）：** 创建一个完全新新的会话。新会话不继承父会话的任何历史消息，只携带 task 参数中描述的任务指令和环境信息。这是上下文纯度最高的 spawn 模式。

**fork=True（环境继承模式）：** 新会话同样不携带父会话的历史消息，但会继承父会话的运行时环境——包括工作目录状态、Python进程状态、文件系统的临时文件、环境变量等。因此，虽然会话历史层面的纯度同样接近1，但隐式依赖层面可能存在"环境噪声"——父会话遗留的临时文件、被修改的全局变量等。

**核心区别：** 影响纯度的不是 fork 模式，而是"是否携带会话历史"。两种 fork 模式在会话历史层面的纯度都接近1，差异在于 fork=True 引入的环境继承可能会通过隐式路径影响子Agent的行为。

从实践角度看，对于大多数纯文档处理、文本生成、分析类任务，fork=False 是更安全的选择。对于需要继承文件系统状态或运行时上下文的任务（如调试一个正在运行的服务），fork=True 可能更合适——但此时开发者需要意识到环境继承可能带来的隐含依赖问题。

## 四、实现方案：spawn决策与上下文净化实战

### 4.1 spawn决策矩阵

不是所有任务都适合通过 spawn 执行。spawn 的适用性取决于多个维度的评估。下面给出一个可直接使用的决策矩阵：

| 评估维度 | ✅ 适合spawn | ❌ 不适合spawn |
|---------|------------|--------------|
| **任务独立性** | 自包含，不依赖前面推理链中的中间结论 | 依赖多轮积累的推理过程和上下文 |
| **上下文复杂度** | 任务目标和约束可以在task参数中完整描述 | 需要大量背景知识，task参数写不下 |
| **预期交互轮次** | 单轮或少轮（≤2轮即可完成） | 需要多轮反馈和迭代修正 |
| **调试敏感度** | 低——结果可以直接外部验证（如文档质量、代码正确性） | 高——需要观察Agent的推理过程来定位问题 |
| **状态依赖** | 无状态，或状态可通过文件/数据库传递 | 依赖紧密耦合的运行状态（如复杂调试场景下的变量追踪） |

#### 使用方法

对每个任务，逐一评估上述五个维度。如果五个维度中的**三个以上**落在"适合spawn"列，就优先使用 spawn 方案。如果三个以上落在"不适合spawn"列，则考虑在不 spawn 的前提下做上下文裁剪。

**"不确定时"的备用策略：** 先用非spawn方式执行第一轮——让主Agent在现有上下文中确认任务边界、识别依赖关系——然后基于第一轮产出的"任务边界说明"，再用 spawn 执行实际工作。这种"先探索后执行"的两阶段策略在很多场景下优于做一次性的 spawn 决策。

### 4.2 反面论证——子Agent什么时候反而更差

上下文净化派发不是银弹。在某些场景下，spawn 子Agent不但不会提升质量，反而会显著降低效率甚至产生更差的结果。以下场景需要特别注意：

**场景一：多轮依赖型任务**

调试类任务是最典型的例子。假设主Agent已经通过几轮交互建立了完整的推理链——第一轮发现了错误日志，第二轮定位了故障模块，第三轮验证了修复方案。如果在第三轮之前的任何一个节点将任务 spawn 出去，子Agent将丢失前几轮已经建立的"为什么走到这一步"的全部上下文。它需要从零开始理解问题，不仅浪费了之前的工作，还可能因为获得的信息不完整而得出不同的结论。

**场景二：任务边界切错**

将高耦合度的任务硬拆成独立模块后 spawn，是常见的错误。假设一个任务是"分析系统性能瓶颈并给出优化方案"。性能分析结果和优化方案之间存在强依赖关系——没有第一阶段的完整分析数据，第二阶段的优化方案就是空中楼阁。如果错误地将这两个阶段拆成两次独立的 spawn，子Agent拿到半截不自洽的指令，产出的方案会比不拆更差。

**场景三：Token开销错觉**

spawn 子Agent不是免费的。每次 spawn 都要重新加载 prompt 文件（AGENTS.md、SOUL.md 等，可能几千token）、初始化工具连接、建立新的会话结构。这些开销在主Agent的上下文中已经是"loaded"状态。极端情况下，频繁 spawn 反而增加总的 token 消耗——尤其是在短周期、多次迭代的任务中。

**场景四：跨任务状态共享的上下文成本**

子Agent的执行是一次性的。如果后一次任务依赖前一次子Agent的输出状态，就需要通过外部存储（文件、数据库）做状态传递。这个"序列化→传递→反序列化"的过程本身就在制造新的上下文——主Agent需要管理临时文件路径、版本、清理策略。当状态传递链条变长时，主Agent反而成了"状态搬运工"，上下文质量可能比不分 spawn 时更差。

**场景五：可观测性下降**

`spawn_subagent(fork=False)` 的执行过程对主Agent而言是一个黑盒。主Agent能看到 task 参数和最终的返回结果，但看不到子Agent的思考过程、中间工具调用、自我反问和修正。一旦执行结果不符合预期，回溯定位根因的难度远高于非spawn模式。对于调试敏感度高的任务，这是不可接受的成本。

**场景六：task参数的"有损压缩"**

主Agent将复杂上下文压缩成一段 task 描述文本，不可避免地会丢失信息。压缩率越高，丢失的原始意图和细节越多。子Agent基于压缩后的指令执行，可能在关键细节上偏离主Agent的原始目标。特别是在涉及微妙判断和权衡的任务（如架构设计、技术方案选型）中，这种"压缩损失"的影响尤为显著。

**场景七：高频迭代场景的效率损失**

每次 spawn 都需要启动一个新会话——加载 prompt 文件、初始化工具连接、建立会话上下文。在短周期迭代任务中（如需要反复"试->改->验"多个小变体的代码调试），这个启动开销占总执行时间的比例显著上升，可能导致 spawn 模式的实际效率低于直接在主Agent中执行。

### 4.3 上下文净化操作指南

承认 spawn 不是银弹之后，我们需要一个更细致的操作框架：**什么时候需要清理上下文，以及怎么清理。**

#### 方法论一：新会话承载新任务（最基础，最可靠）

最直接的方法也是最可靠的：当一个任务与当前会话中的已有任务没有依赖关系时，直接在新会话中执行。新会话天然拥有最高的上下文纯度。关键工作在于判断"没有依赖关系"的边界——这需要主Agent具备任务边界识别能力。

**具体操作：** 主Agent在收到新任务时，快速扫描现有会话历史，判断当前上下文是否与任务相关。如果无关（例如正在做数据分析和用户突然说"帮我写一份文档"），应该采用 spawn 而非在当前上下文中继续。

#### 方法论二：显式标注上下文边界（中间态，不推荐）

部分框架支持给消息添加元标签或显式标记"以下是无用历史请忽略"。这种方法的优点是快速——不需要创建新会话——但缺点是把"上下文裁剪"的责任丢给了模型，让模型自己判断哪些历史应该被忽略。模型的判断不一定可靠，且这种标注本身也在占用上下文窗口。

**适用场景：** 短期过渡——在无法快速 spawn 的环境中的临时方案。不推荐作为长期策略。

#### 方法论三：提取精华→写入文件→子Agent读文件（推荐）

这是目前最实用、效果最稳定的上下文净化模式。它的核心思想是：**不要试图通过参数传递上下文，而是通过文件系统传递。**

**执行流程：**

1. **主Agent裁剪：** 主Agent在当前上下文中，将"与当前任务真正相关"的信息提取出来——包括关键结论、数据、约束条件等。这一步的本质是主Agent做一次有损压缩，但压缩的对象是"任务相关的信息"而非"所有历史"。
2. **写入文件：** 将提取后的信息写入一个临时文件（或固定位置的文件）。
3. **spawn子Agent：** 通过 task 参数告诉子Agent"请读文件 X，基于其中的内容执行任务 Y"。
4. **子Agent执行：** 子Agent读文件，获得纯净的上下文（不带历史噪声），基于此执行。
5. **结果回传：** 子Agent将执行结果写入输出文件，主Agent读文件获取结果。

**关键优势：** 文件作为中介解耦了主Agent和子Agent的上下文。主Agent不需要在参数中压缩所有信息（避免"有损压缩"问题），子Agent获取的是经过裁剪、与任务直接相关的完整信息。同时，文件的持久化特性也使得状态传递可追踪、可审计。

**成本：** 手动管理文件的生命周期——创建、清理、并发写冲突处理。在轻量级实现中，可以用固定命名约定和清理回调来管理。

---

### 4.4 一个实际案例：上下文净化派发的端到端流程

以文档撰写任务为例，展示完整的上下文净化派发流程：

1. **任务接收：** 主Agent在长期会话中收到用户请求"写一篇关于上下文纯度的技术文档"。
2. **上下文评估：** 主Agent快速扫描当前会话历史。发现当前上下文中包含之前任务的文件搜索记录、时间查询记录、关于其他技术方案的讨论。这些对写文档任务都是噪声。
3. **裁剪决策：** 主Agent评估任务独立性——文档撰写是自包含的，不依赖前面的推理链。符合 spawn 条件。
4. **上下文提取：** 主Agent从当前会话中提取与文档撰写相关的信息（包括讨论记录、暂存文件、大纲）。通过 task 参数告诉子Agent"请读文件 X（大纲）和文件 Y（讨论记录），基于这些内容写文档"。
5. **spawn子Agent：** `spawn_subagent(task="请根据大纲文件 X 和讨论记录 Y，写一篇技术文档", fork=False)`。
6. **子Agent执行：** 子Agent在纯净上下文中读文件、写文档。没有历史噪声干扰。
7. **结果验证：** 主Agent check 子Agent返回的结果，确认质量。

在这个流程中，主Agent的角色从"执行者"转变为"管理者"——它负责上下文评估、裁剪、调度委托，而执行本身由子Agent在纯净上下文中完成。

#### 文件中介模式的变体与权衡

文件中介存在几种变体，其选择取决于任务的复杂度和对实时性的要求：

**变体一：单文件模式。** 所有上下文写入一个文件，子Agent一次性读取。适用于简单、自包含的任务。优点是实现简单，缺点是文件内容会随着任务复杂度增长而膨胀，可能超过子Agent的 context window。

**变体二：结构化多文件模式。** 主Agent将上下文按类型拆分到多个文件——一个放任务说明，一个放参考资料，一个放约束条件。子Agent按需读取。适用于需要精细控制上下文的复杂任务。优点是上下文结构清晰，缺点是需要管理文件间的交叉引用和一致性。

**变体三：增量文件模式。** 主Agent不是一次性写入所有上下文，而是在子Agent执行过程中按需写入。子Agent每完成一个阶段，主Agent评估下一阶段需要什么上下文、写新文件、子Agent继续。适用于迭代式任务（如逐步扩充文档、分阶段调试），优点是上下文精确到每个阶段所需的最小集合，缺点是增加了主Agent的交互轮次和管理负担。

### 4.5 上下文净化派发的运维考量

将上下文净化派发引入生产环境后，以下几个运维层面的问题需要提前规划：

**文件生命周期的管理。** 中介文件会在文件系统中持续累积。需要制定清理策略——基于时间（如任务完成后立即清理）、基于空间（设定临时目录上限）、或基于引用计数（文件未被任何活跃子Agent引用时清理）。如果清理不及时，这些文件本身会成为新的噪声源——其他Agent在全局文件搜索时会搜到失效的上下文。

**并发冲突的处理。** 在多Agent场景中，多个子Agent可能同时写入同一个输出目录。如果没有命名空间隔离，一个子Agent可能覆盖另一个子Agent的中间产物。简单的解决方案是按任务ID或时间戳为每次 spawn 创建独立的工作目录。

**可观测性补偿。** 子Agent的执行是黑盒，但运维层面需要知道"它经历了什么"。一个可行的方案是让子Agent在关键节点写入进度文件——类似于日志中的 checkpoint。这样主Agent不需要实时观察子Agent的推理过程，但在排查问题时可以回溯子Agent的执行轨迹。

**上下文缓存策略。** 如果同一个任务背景需要被多个子Agent使用（如一个大型项目的架构说明），每次都由主Agent写文件会造成冗余。可以考虑在文件系统层面做一个轻量级上下文缓存——主Agent先检查缓存中是否有适配的上下文快照，有就直接引用，没有再写。这能显著减少主Agent的上下文裁剪工作量。

## 五、扩展讨论

### 5.1 上下文管理自动化的正循环

从更宏观的角度看，上下文净化派发不仅是一个技术方案，更代表了一种自动化趋势。

**手动时代：** 人类用户在脑中整理上下文——回忆哪些信息与当前任务相关、哪些历史可以忽略——然后手动写进 prompt 发给 AI。上下文裁剪由人类完成，人在回路中既是瓶颈也是质量保障。

**代理时代：** 主Agent自动完成上下文评估和裁剪工作。它判断"当前任务需要什么信息、不需要什么信息"，然后通过 spawn 将执行交给子Agent。人类从上下文管理的劳动中解放出来，专注于更高层的方向性决策。

**正循环的运作机制：**

```
主Agent裁剪上下文 → 子Agent高质量执行 → 用户对spawn模式产生信任 →
用户更主动地使用spawn模式 → 主Agent的上下文负担减轻 →
上下文污染积累速度变慢 → 裁剪时面临的信息量更小 → 裁剪更精准 →
子Agent获得更高质量的输入 → 执行质量进一步提升
```

这个正循环一旦建立，不仅提升单次任务的质量，还通过"反馈环路"持续优化整个系统的上下文管理能力。

**当前状态：** 这是一个设计模式（design pattern），不是框架特性。它的运行依赖主Agent的"自觉性"——准确判断什么时候该 spawn、要裁剪什么、怎么裁剪。当主Agent自身上下文已被污染时，它的判断质量会下降，正循环可能演变为负循环。

**核心瓶颈：** 主Agent的裁剪质量受其自身上下文污染程度的影响。这是一个递归问题：上下文污染了的主Agent，做不好上下文裁剪。解决这一递归的工程路径包括：

- 在系统层面设计"健康度检查"——当主Agent上下文纯度低于某个阈值时，主动触发 spawn 将控制权交给一个新会话
- 为关键判断（如 spawn 决策）引入独立的验证步骤——不做裁剪直接 spawn 某个子Agent专门评估"当前上下文中是否有足够的任务相关信息"

### 5.2 多Agent框架的上下文管理设计对比

不同框架在上下文管理和子Agent机制上存在显著差异，直接影响上下文净化派发模式的可落地程度。

#### 框架横向对比

| 维度 | OpenAI Swarm | CrewAI | AutoGen (v0.4) | LangGraph |
|------|-------------|--------|---------------|-----------|
| **上下文传递方式** | Agent切换时共享完整对话历史 | Task定义中显式传递 context 参数 | 对话历史可被裁剪后传递 | 通过结构化 State 在节点间传递 |
| **上下文纯度控制** | ❌ 无原生支持 | ⚠️ 设计阶段可以裁剪 context | ⚠️ 可通过配置对话历史范围手动控制 | ✅ 图结构层面有更强的控制力 |
| **子Agent机制** | Handoff（移交）——当前Agent将控制权转给另一个Agent | 通过 Task 编排——每个 Task 绑定特定 Agent | 嵌套对话——Agent之间独立会话 | 节点执行——每个 node 可以是独立 Agent |
| **异构模型支持** | ❌ 全部Agent共享同一个模型配置 | ⚠️ 可指定 llm 参数，但底层限制在同 API provider | ✅ 每个 Agent 有独立的 llm_config 配置 | ✅ 节点级别可绑定不同的 ChatModel |
| **上下文自动化程度** | 无——开发者手动管理全部上下文传递逻辑 | 低——Task context 需要开发者手动提取和传入 | 中——支持自动摘要和对话历史裁剪 | 中高——State 结构由开发者设计，运行时可灵活读写 |
| **上手复杂度** | 极低——API设计简洁，理念清晰 | 低——面向任务的抽象直观易懂 | 高——配置选项多，学习曲线陡峭 | 高——需要理解图执行引擎和状态管理 |

#### 核心发现

**没有一个主流框架真正实现了"运行时上下文管理自动化"。**

LangGraph 的 State 设计是最接近上下文净化派发理念的。开发者可以显式定义 State 的结构——限定哪些信息在节点之间传递、哪些不传递——从而在架构层面避免"历史全部传递"的问题。但 State 结构是静态的：你在设计 Graph 的时候定义它，运行时不自动做上下文裁剪。你需要自己决定"什么信息是任务相关的、什么不是"。

Swarm 和 CrewAI 的简化设计在日常使用中效率很高，但它们共享完整上下文的模式意味着上下文污染问题在所有Agent之间传播——一个Agent的噪声会变成所有Agent的噪声。

AutoGen 的配置灵活性是双刃剑：你可以手动实现上下文裁剪，但没有框架层面的机制保证一致性。

**Gap 分析：** 框架层的缺失给开发者留下了一个设计空间——是否可以通过中间件或 wrapper 实现运行时上下文裁剪？一个理论上可行的方案是：在框架的消息路由层注入一个"上下文过滤器"节点，在消息传递到子Agent之前自动做年龄加权裁剪（如丢弃 age 大于某个阈值的消息）。但这需要对框架源码有侵入式修改。

### 5.3 模型分层经济学：调度层与执行层

上下文纯度的讨论还可以延伸到模型经济学的维度：不同层级的 Agent 可能需要不同智能等级和不同价格的模型。

#### 调度层：不需要高智商

调度层的核心任务是判断——"这条内容该放哪个分类"、"当前任务的边界在哪里"、"是否需要创建子Agent"、"任务是否完成"。这些任务的特征是：

- **决策空间有限：** 大部分调度决策是二分或三选一
- **不需要创造力：** 不需要生成新内容、不需要架构创新
- **需要的是稳定性和可预测性：** 同一个输入产生同一个输出

在这个约束下，给调度层用顶级模型（如 GPT-4o、Claude Opus）是资源浪费。大量实践经验表明，一个经过良好配置的轻量模型（如 GPT-4o-mini、Claude Haiku）在调度任务上的表现与顶级模型没有本质差异。"用跑车送外卖"不是跑车的问题，是分配策略的问题。

#### 执行层：才真吃模型能力

真正需要模型边际智能提升的场景是执行层：

- **文档写作：** 结构的取舍、例子的选择、语言的克制——每个决策都在无数个合理选项中找出最合适的一个
- **复杂代码的设计：** 不是写一段能跑的代码，而是写一段结构清晰、可维护、边界条件完善的代码
- **微妙判断的需求：** 在上下文敏感的任务中，轻量模型可能因为理解偏差而产生偏离目标的结果

在执行层，模型的智商直接决定了输出质量的上限。

#### 理想调度模型 vs 当前约束

**理想方案：** 便宜模型（如 GPT-4o-mini、Claude Haiku）做 orchestration（调度、裁剪、路由），贵模型（如 GPT-4o、Claude Sonnet/Opus）做 execution（执行、创作、架构）。

**现实约束：** 大多数主流框架在默认配置下，子Agent使用与主Agent相同的模型配置。这是因为同构架构的设计理念——简化部署和成本管理——但代价是放弃了模型分层经济学带来的效率提升。

**该约束的例外：** AutoGen 允许每个 Agent 配置独立的 `llm_config`，LangGraph 允许节点级别绑定不同的 ChatModel。这意味着在这些框架中，你可以手动实现异构模型调度——但需要开发者侵入式配置。当前还没有框架提供"自动根据任务类型选择模型"的能力。

**给实践者的启发：** 如果你已经使用了支持异构模型配置的框架（AutoGen、LangGraph），你只需要多做一步——为调度层的 Agent 配置一个便宜模型，为执行层的 Agent 配置一个贵模型——就能以极低的成本获得系统整体效率的提升。这一步的收益可能比你预期的更大，因为它同时提升了调度效率（便宜模型足够用）和执行质量（贵模型用在刀刃上）。

### 5.4 Tag与分类系统的调度价值

在多Agent系统中，tag/分类系统不只是元数据管理工具，它们本身就是**调度决策的输入信号**。

当主Agent需要判断"这条内容该放哪个库""这个任务该交给谁执行"时，一个结构化的 tag 分类系统可以直接缩小决策空间。主Agent不需要自己在上下文中搜索、判断、推理——它只需要匹配 tag。

**正向链路：** 好的标签分类系统 → 更精准的任务路由 → 更少的上下文噪声 → 更高的执行质量。

**反向链路：** 没有结构化分类 → 主Agent每次都需要自己"判断这是什么东西" → 每次判断都在制造新的上下文噪声 → 执行质量下降。

这意味着，tag/分类系统本身也是上下文管理的一部分。一个主Agent如果能在上下文中直接识别"这条内容的 tag 是 `Agent工程化/上下文管理`"，它就不需要去回忆"之前有没有类似的内容、应该放哪里"，避免了判断噪声的产生。

这一视角将元数据管理提升到了基础设施的高度——它不再是"方便查找"的问题，而是"影响系统执行质量"的问题。

## 六、总结

### 6.1 核心观点回顾

多Agent系统中子Agent执行质量高于主Agent的现象，其根因不在模型或prompt的差异，而在**上下文纯度**的差异。同样的模型在干净上下文中的表现，显著优于在污染上下文中的表现。

上下文纯度的形式化度量并非遥不可及。年龄加权模型（Age-Weighted Purity Metric）提供了一个不需要模型内省、不需要人工标注、纯计算的 proxy metric，日常运行成本和理论精度之间的权衡处于可接受的范围。

spawn 决策不是无脑全上。本文提供的决策矩阵给出了五个维度的判断标准，帮助开发者在"独立自包含任务"和"多轮依赖任务"之间做出区分。反面论证中列出的七个场景，可以作为 spawn 决策前的质量门禁。

"上下文净化派发"（Clean Context Delegation）——主Agent负责裁剪、子Agent负责执行——是目前最实用的设计模式。这一模式已经在多套 Agent 工作流中得到验证，其效果稳定、可复现。它不是一个框架特性（目前没有主流框架原生支持），而是一个可以被任何框架采纳的设计模式。

### 6.2 给实践者的快速决策指南

**如果你遇到的情况是：** Agent输出越来越啰嗦、偏离主题、混淆不同任务的内容。

→ **优先检查上下文纯度。** 查看会话历史长度，计算年龄加权纯度。如果纯度小于某个阈值（经验值建议先设为0.3），考虑将当前任务切分或 spawn 子Agent执行。

**如果你遇到的情况是：** 子Agent反复出错、不理解任务背景、产出偏离预期。

→ **优先检查 task 参数是否存在"有损压缩"问题。** 可能是主Agent在 task 参数中丢失了关键上下文。考虑改用"提取精华→写入文件→子Agent读文件"的模式（方法论三），而不是继续压缩 task 描述。

**如果你遇到的情况是：** 频繁 spawn 但感觉效率没有实质性提升。

→ **检查原子化粒度是否太细。** 参考反面论证的"高频迭代"和"Token开销错觉"两个场景。如果你的任务周期很短（几轮交互即可完成），每次 spawn 的启动开销占比显著，这时合并成更粗粒度的任务可能更高效。

**如果你遇到的情况是：** 团队正在选型多Agent框架。

→ **将上下文管理能力纳入评估维度。** 选择支持异构模型配置的框架（AutoGen、LangGraph），为调度层和执行层预留模型分层的空间。这不仅影响执行质量，还影响 token 成本。

### 6.3 知识缺口

以下问题在本文的写作过程中被识别为开放问题，值得进一步探索：

1. **递归裁剪的收敛性。** 主Agent裁剪上下文 → spawn 子Agent → 子Agent执行多轮后也被污染 → 子Agent自己 spawn 子Agent。这个递归链是否能收敛？是否存在一个工程上限——嵌套多少层之后，裁剪的收益就不再超过 spawn 的开销？

2. **λ衰减系数的环境敏感度。** 年龄加权模型中的 λ 是否在不同任务类型（代码生成 vs 文档写作 vs 数据分析 vs 规划推理）间存在显著差异？是否存在一个"最佳 λ 值"与任务复杂度的映射关系？

3. **上下文纯度的在线自感知。** 能否将年龄加权纯度计算为实时 metric，注入 Agent 的 system prompt，让它自己感知"当前上下文纯度太低，应该 spawn"？这是否会导致Agent陷入自我指涉——"我在想我是不是纯度太低了"这个想法本身就在制造更多噪声？

4. **框架层的原生支持边界。** 是否存在一种通用的中间件层或 wrapper，能在不侵入框架源码的前提下实现运行时上下文裁剪？这种中间件的性能开销和实现复杂度是否可控？

5. **子Agent会话历史污染的积累。** 子Agent执行多轮任务后，自身的上下文也会被污染。它应该在什么阈值下自己做 spawn？这个递归深度有什么实际工程上限？

6. **异构模型调度的 break-even 分析。** 用便宜模型做裁剪+路由、贵模型做执行，总 token 成本与纯用贵模型的 break-even 点在哪个任务规模和复杂度下出现？小规模任务中异构调度的开销是否高于其带来的效率收益？
