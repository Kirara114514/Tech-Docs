## 一、最需要立即改的内容

### 1. "上下文纯度"文档存在实质性的理论和数学问题

问题集中在 `多Agent架构中上下文纯度与执行质量的关系.md` 第 64 行以后。

- "softmax 权重和为 1，因此序列越长，关键 token 获得的注意力越少"→ 不能推出。模型可以把权重高度集中到少数 token；而且还有多层、多头、位置编码、KV 表征和注意力汇聚。
- "影响呈指数级放大"没有理论或实验依据。
- 20 轮中 5 轮无关是 25%，文中却说挤占"85%关键内容"→ 算术上应是 75%。
- Attention weight 不是可靠的"模型真正关注什么"的解释指标，将其称为最精确方案不合适。
- 年龄加权纯度公式删掉 `rel(m_i)` 后，只剩"会话长度和消息年龄"，已经不再衡量纯度。一个很长但完全相关的上下文反而会得到低分。
- "改变 λ 运行任务来校准 λ"在当前定义下也不成立：λ 只改变指标，没有改变喂给模型的上下文，任务成功率不会因 λ 自身改变。
- `fork=True/False` 是框架私有语义，不应写成通用 Agent 原理。
- "创建空会话是唯一可靠方式"过于绝对。摘要、状态快照、任务分支、检索式历史、证据指针都可能有效。

**建议核心命题改为**：上下文的相关性、时效性、指令冲突、状态一致性和信息出处会影响 Agent 表现；新会话派发是降低这些风险的一种工程策略，收益必须通过消融实验与其他因素区分。

**补充研究证据**：
- [More Skills, Worse Agents?](https://arxiv.org/abs/2605.24050)：Skill 库扩张造成的主要问题是 Skill shadowing/选错 Skill，"上下文变长本身"的影响很小、统计上接近零。
- [Less Context, Better Agents](https://arxiv.org/abs/2606.10209)：裁剪加摘要能显著改善效果，但只证明特定工具工作流中的选择性保留有效，不能推出普适的"上下文纯度定律"。

### 2. "框架越深越智能"应该改成"脚手架与任务匹配度决定表现"

《框架即智能》的核心洞察（模型表现不能脱离 harness/scaffold 讨论）是对的。但"编排越深越好""动态角色生成是能力上限"不成立。

- [Towards a Science of Scaling Agent Systems](https://arxiv.org/abs/2512.08296)：多 Agent 在顺序推理任务上反而下降 39%–70%；当单 Agent 基线已经较强时，协调的边际收益会转负。
- [Multi-Agent Teams Hold Experts Back](https://arxiv.org/abs/2602.01011)：自由协作团队经常把专家意见和弱意见平均化，损失最高达 37.6%。
- [HAL](https://arxiv.org/abs/2510.11977)：更高 reasoning effort 在多数运行中反而降低准确率。
- [mini-swe-agent](https://github.com/SWE-agent/mini-swe-agent)：极简线性循环、bash-only、约百行核心 Agent，仍能成为很强的 coding baseline。

**更准确表达**：编排存在最优复杂度，而不是单调收益。深编排只有在任务可分解、子任务可验证、接口损耗低、并行收益大于协调成本时才值得。

另外，直接断言 Claude Code、Codex 具有某种四层内部架构缺少公开证据，应标为"基于产品行为的推测"。

### 3. Skill 元数据模型与当前开放规范不一致

《Skill 命中率优化》把 `desc` 和 `trigger` 当作标准字段，但 [Agent Skills 开放规范](https://github.com/agentskills/agentskills) 的最低必需元数据是 `name` 和 `description`，Discovery 阶段只加载这两个字段；标准并没有独立的 `trigger` 字段。

- 如果 `trigger` 是自己运行时的扩展，必须明确标注"host-specific extension"。
- 跨环境移植时应把关键触发条件写回 `description`。
- "300 行 SKILL.md 会全部参与路由"不符合标准的 progressive disclosure。
- `name×3、desc×2`、0.1 相似度差、pairwise 一定优于 pointwise、3–8 个点预期提升 → 应改成"待通过本地路由集校准的初始假设"。

### 4. 安全文档过高估计了 Prompt 层防御，又过早否定了独立控制点

《企业安全代理对Agent使用体验的讨论》中对 bolted-on 安全、体验成本和组织责任的分析很好，但：

- 系统提示词加固、输入转义和输出审核不能构成可靠的 Prompt Injection 安全边界。
- 白名单并非天然无能为力；现代 capability policy 可以约束目标域名、参数、数据来源、文件标签、调用关系和速率。
- OS sandbox 不能自动阻止 Agent 把它本来有权读取的数据发送到错误目的地。
- 不应把"代理/网关"和零信任对立起来。独立网关、DLP 或 reference monitor 仍然可以是纵深防御的一层。
- 将策略引擎放在 Agent 服务器内部并最终完全移除代理，可能让决策者和被约束执行者处于同一信任域。

**更先进的安全模型**：显式信息来源、数据/指令分离、能力授权、独立策略执行、输出数据流检查和持久状态污染防护。

**关键参考文献**：
- [CaMeL：Defeating Prompt Injections by Design](https://arxiv.org/abs/2503.18813)
- [Toward Secure LLM Agents](https://arxiv.org/abs/2606.10749)
- [Agent Skill Security / SkillSec-Eval](https://arxiv.org/abs/2607.13987)（2026 年 7 月）
- [MCP Authorization 规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)
- [NSA MCP Security Design Considerations](https://media.defense.gov/2026/Jun/02/2003943289/-1/-1/0/CSI_MCP_SECURITY.PDF)

### 5. "向量索引替代文档"这个判断已经偏旧

《AI编程中的上下文管理与记忆系统》把向量检索写得过于中心化：

- 结构良好的文档并不比零散检索片段低效。架构约束、全局不变量、术语定义和负面规则往往恰恰需要完整结构。
- 现代 coding agent 常组合 `rg`、符号/LSP、AST、repo map、git history、测试反馈和可选 embeddings。
- 检索仍然是"选择上下文"，并非"计算而不是选择"。
- 企业托管向量服务的可行性取决于合同、区域、保留策略、私网、ACL 和加密，不宜写成"一律不可接受"或"必须自建"。
- 长期记忆还缺少版本、分支、删除/tombstone、ACL 过滤、TTL、冲突处理、出处和 memory poisoning 模型。

**参考方向**：
- [Memex(RL)](https://arxiv.org/abs/2603.04257)：摘要中保留稳定索引，必要时回取完整原始证据。
- [SelfMem](https://arxiv.org/abs/2607.03726)：让 Agent 根据反馈优化自己的记忆读写策略。

## 二、两处可以直接判定的事实性错误

1. **τ-bench 的 `pass^k` 定义写反了**（`Agent 领域论文推荐阅读清单.md:157`）
   - `pass@k`：k 次中至少一次成功
   - `pass^k`：k 次全部成功，用于衡量一致可靠性
   - 所以 `pass^k` 通常低于 `pass^1`，不是高于。参见 [τ-bench 原论文](https://arxiv.org/abs/2406.12045)

2. **"最强模型 SWE-Bench Pro Pass@1 仍低于 25%"已经过时**（同文档:137）
   - 2026 年 5 月 Google 官方模型卡报告 SWE-Bench Pro Public 单次成绩已在 50%–60% 区间
   - [Gemini 3.5 Flash 模型卡](https://deepmind.google/models/model-cards/gemini-3-5-flash/)

另外：
- [OpenAI Swarm](https://github.com/openai/swarm) 已由 [OpenAI Agents SDK](https://github.com/openai/openai-agents-python) 取代
- "当前几乎无法追踪 Agent 决策链"已过时：Agents SDK 已有内建 tracing，[OpenTelemetry GenAI conventions](https://github.com/open-telemetry/semantic-conventions/releases) 已覆盖 `invoke_agent`、tool execution、tool definitions 和 evaluation events

## 四、对 ASMP 的单独评价

ASMP 是整套文档中最有潜力形成原创体系的部分。事件记录、延迟蒸馏、角色隔离、验证门控和决策历史都非常好，且与 [SkillHone](https://arxiv.org/abs/2606.08671) 和 [SkillOpt](https://arxiv.org/abs/2605.23904) 方向高度一致。

但当前更适合称为"自维护参考架构/治理 profile"，还不是严格意义上的通用协议：

- 把 Skill、子 Agent、Heartbeat 定为三个必要条件过于绑定具体实现
- 2/3/5 次 incident、每周执行、每次最多 10 行等阈值应根据风险和调用基数校准
- 若要称为协议，还需要版本协商、状态机、规范 schema、幂等与失败语义、conformance test suite
- Security Agent 的否决仍只是模型决定，不是安全边界
- 优化器和评测器共同演进时要防 Goodhart、holdout 泄漏和 reward hacking

## 第一条：上下文纯度文档的数学问题

### 反馈要点

- softmax 权重和为 1 → 注意力稀释的因果链不成立（因为多头注意力可以集中权重）
- "影响呈指数级放大"没有理论或实验依据
- 25% 噪声 → 挤占"85% 关键内容"算术错误
- Attention weight 不是可靠的解释指标
- 年龄加权公式去掉 `rel(m_i)` 后不再衡量纯度
- λ 校准实验在当前定义下不成立
- `fork=True/False` 是框架私有语义，不应写成通用原理
- "创建空会话是唯一可靠方式"过于绝对
- 引用 More Skills, Worse Agents? 和 Less Context, Better Agents 作为已有研究的补充证据

### 我的判断

**对 softmax 因果链 → 完全同意，必须改。**

原文的推导路径是：softmax 权重和为 1 → 序列越长每个 token 分到的注意力越少 → 无关 token 稀释关键 token 的注意力 → 任务质量下降。这个链条中间有两个跳步。

第一个跳步：softmax 的归一化约束只保证权重和为 1，但完全不限制分布形态。模型完全可以把 95% 的注意力集中在某几个关键 token 上，对外围噪声分配接近零的权重。注意力机制设计之初就是为了做这种选择性聚焦——否则 softmax 就不会被选为激活函数。我的原文暗示了"噪声 token 自然分走注意力"，这在数学上不成立。

第二个跳步：即使单层注意力的某个头稀释了关键信息，多头机制和多层堆叠提供了多条并行的信息通道。不同层的不同头可以关注序列中完全不同的位置，信息在层间传递时可以重新汇聚。这进一步打破了"越长越稀释"的简单叙事。

**应该改成什么？** 把核心命题从"纯度定律"降级为"上下文的相关性、时效性、指令冲突、状态一致性和信息出处会影响 Agent 表现，新会话派发是降低这些风险的工程策略之一"。不是放弃"新会话更干净"的工程直觉——这个直觉在我的实际使用中反复被验证——而是放弃为它找一个不成立的数学包装。

另外，More Skills, Worse Agents? 的发现特别重要：它指出上下文长度本身的影响在统计上接近零，真正的问题是 skill shadowing（选错 skill）。这对我整个文档体系的 Skill 路由设计有直接冲击——如果上下文长度影响很小，那我花大量篇幅讨论"如何让上下文更短"就是对着错误的目标开火。应该把精力转移到"如何让 Skill 被正确选择"上。

**对"指数级放大"→ 完全同意，删掉。**

原文确实没有任何引用或实验支撑这个说法。删掉，保留"自回归链条中早期偏差会被后续步骤延续和放大"这个相对温和的表述即可——这个是自回归生成的结构性特征，不依赖奇怪的放大假设。

**对 85% vs 75% 的算术错误 → 完全同意，丢人的低级错误。**

数字不对就是不对。20 轮中 5 轮无关 = 25% 噪声 / 75% 相关内容。原文写的"85% 关键内容"是凭空多出来的 10%，没有任何依据。

**对 Attention weight 不是可靠解释指标 → 基本同意，有微妙之处。**

反馈说 attention weight 不宜被称为"最精确方案"。严格来说这是对的——attention weight 在 NLP 可解释性研究中的争议很大（Jain & Wallace 2019 "Attention is not Explanation"以及后续辩论）。高 attention weight 的 token 不一定是模型实际"依赖"的 token。

但原文的上下文是——在讨论"如何量化上下文纯度"时的方案比较表中，把"通过 attention weight 可视化计算模型实际关注的 token 中与任务相关的比例"标为"精度：高"。这里的"精度"指的是"如果你能正确获取并解释 attention weight，你可以精确知道模型关注了哪些 token"。问题是前提（"正确获取并解释"）在闭源模型中不可行，在开源模型中也争议重重。

更准确的标注：把这行从"精度：高"改成"精度：存在争议，attention weight 的解释有效性在学界未达成共识"。

**对年龄加权公式的问题 → 完全同意，这是整个章节最严重的自相矛盾。**

这是反馈打得最准的一个点。原文先定义了一个有 `rel(m_i)` 的公式（表面上在衡量"相关性加权的纯度"），然后说"在 `rel(m_i)` 难以获取的实用场景下简化为 `P_session ≈ (1/N) · Σ W_i`"——这个简化抹掉了唯一与"纯度"相关的因子。简化后的公式只剩两个变量：N（消息总数）和 age 分布。一个 200 条消息但每条都高度相关的会话，和一个 20 条消息但大半无关的会话，简化公式会给前者更低分。

这意味着简化公式衡量的不是"纯度"，而是"会话长度 + 消息新鲜度"——一个完全不同的度量。

修法：删掉简化公式。承认 `rel(m_i)` 的获取是上下文纯度度量的核心难题，年龄加权模型在无人工标注时退化为无效。如果删掉公式后整个度量章节失去核心，那就把度量章节整体降级为"开放问题"而不是"推荐方案"。

**对 λ 校准实验 → 完全同意。**

如果 λ 只用于计算一个不参与任何决策的指标，那改变 λ 不会改变 Agent 实际上收到的上下文，任务成功率当然不变。λ 校准只有在 λ 被用于触发实际的上下文裁剪行为（比如"λ 低于某阈值就触发 spawn"）时才成立。原文把"计算指标"和"使用指标做决策"混为一谈了。

**对 fork=True/False 写成通用原理 → 完全同意。**

fork 的语义是 QwenPaw 框架的私有实现细节。修法：明确标注"以 QwenPaw 为例"，并把这一小节从"核心内容"移到"实现细节"或脚注。

**对"创建空会话是唯一可靠方式"过于绝对 → 基本同意。**

反馈列了一堆替代方案：摘要、状态快照、任务分支、检索式历史、证据指针。它们在不同场景下都有效。我当时写"唯一可靠方式"的时候是在讨论"负循环的打破"这个特定场景（上下文已被深度污染，在污染的上下文中生成清理指令本身就包含污染模式），但没有把这个限定条件说清楚。修法：把这句话限定为"在上下文已被深度污染（连续 2-3 次 spawn 失败）的特定场景下，创建新会话是最直接的止损策略"，并补充其他场景有更多替代方案。

### 对这一条的总体判断

反馈在上下文纯度文档上的七个批评点中，六个我都完全同意，一个（attention weight）基本同意但有细节上的微妙之处。核心修改方向：把所有"这是定理"的语气降级为"这是经验观察 + 工程策略"，删掉不成立的数学包装，修正算术错误，把 fork 语义限定为框架私有实现，纠正过于绝对的表述。

## 第四条：安全文档对 Prompt Injection 和代理的立场需要调整

### 我的判断

**对 Prompt 层防御不能构成可靠边界 → 完全同意，需要收回。**

原文 §2 对 Prompt Injection 防护的描述是：系统提示词加固、输入转义和上下文隔离、输出审查。反馈指出这些措施不能构成可靠的 Prompt Injection 安全边界。这是对的：

1. 系统提示词加固本质上是"靠话术防御"，不是安全机制。攻击者可以用越狱技术绕过提示词中的防御指令。
2. 输入转义和上下文隔离只能防御格式层面的攻击，不能防御语义层面的攻击。
3. 输出审查只有在审查器本身不受注入影响时才有效。

反馈引用的 CaMeL 特别重要——"by design"的防护思路：不是打补丁防攻击，而是在系统架构层面就让攻击路径不存在。

**对白名单并非天然无能为力 → 基本同意。**

原文批评的是"简单二元命令白名单"。现代 capability policy 可以约束目标域名、参数范围、数据来源、文件标签、调用关系和速率——这个是有效的。修法：不要一刀切地说"白名单无法收敛"，而是区分"简单二元命令白名单"和"多维 capability-based policy"。

**对 OS sandbox 不能阻止授权数据误发送 → 完全同意。**

这是原文的一个盲区。sandbox 约束的是操作系统层面的操作，不能阻止 Agent 把它合法读取到的文件内容通过合法 API 发送到不该去的地方。需要引入数据流控制。

**对不应把代理/网关和零信任对立起来 → 有保留地接受。**

原文在某些地方确实暗示"代理就应该被完全移除"。但独立网关或 DLP 作为纵深防御的一层仍然有检测价值。移除代理作为主要防线是必要的，但保留轻量监控层作为辅助检测是可选的。

**对策略引擎位置的 tradeoff → 这是一个很好的安全设计问题。**

反馈指出如果策略引擎和被约束的执行 Agent 在同一个信任域中，策略引擎就不再是独立的控制点——这是纵深防御的基本原则。但在 Agent 服务器内部的策略引擎可以基于完整推理上下文做更精准的判断，外部网关只能看命令文本。这是"独立性的安全收益 vs 上下文丰富度的安全收益"的 tradeoff。原文没有讨论这个 tradeoff。

### 对这一条的总体判断

五个批评点中，四个完全同意，一个（代理和零信任的对立）有适度保留但接受核心 nuance。引用的 CaMeL 和 SkillSec-Eval 是必须补读的。

## 第六条：两处事实性错误（无争议确认修改）

## 第二轮讨论结论

### 1. "More Skills"不能被推广为"上下文长度通常不重要"

DocManager 在回应第 219 行进一步推断：

> 如果上下文长度影响很小，讨论如何让上下文更短就是对着错误目标开火。

这个推论过头了。[More Skills, Worse Agents?](https://arxiv.org/abs/2605.24050)研究的是"Skill 库从少量扩大到 202 个时"，在已经选对 Skill 的条件下，Skill 元数据带来的额外 context overhead。它没有研究：

- 长期工具调用日志
- 多任务历史混杂
- 新旧指令冲突
- 失败方案残留
- 外部内容中的 Prompt Injection
- 状态已发生变化但上下文仍记录旧状态
- 数十轮行动轨迹中的证据查找

因此正确结论应是：

> Skill 库扩张场景中，路由错误比元数据长度更重要；但不能由此否定其他场景中的上下文裁剪、摘要和隔离价值。

所以"上下文纯度"文章不必删除主题，应该删除错误的数学包装，并把研究对象从"长度"改成：

- 相关性
- 冲突率
- 新鲜度
- 状态一致性
- 来源可信度
- 证据可恢复性

甚至建议把"纯度"一词也降级，因为"纯"隐含一个单轴度量，但上下文质量实际是多维的。

推荐改名：

> 《多 Agent 系统中的上下文隔离：经验现象、风险维度与验证方法》

### 2. DocManager 对 attention weight 的"细微保留"没有必要

它认为"如果能正确获取并解释 attention weight"，仍可以比较精确地知道模型关注什么。

这个前提近乎循环定义：如果已经能"正确解释"，自然会正确；问题正是 attention weight 通常不等于因果依赖，也不是上下文相关性的 ground truth。

建议不要继续保留"方案一：最精确但不可用"。改成：

> Attention 可视化可以作为诊断信号，但不应作为上下文相关性或模型因果依赖的权威指标。

真正接近因果验证的办法是输入消融、反事实替换、遮蔽测试和重复运行，而不是观察 attention。

### 3. 单 Agent 编排与多 Agent 协作确实应区分，但不能借此保住"编排深度"单轴模型

DocManager 在回应第 290 行提出：

- 单 Agent 编排是一种机制。
- 多 Agent 协调是另一种机制。
- Scaling Agent Systems 主要批评后者。

这点是对的。[Scaling Agent Systems v3](https://arxiv.org/abs/2512.08296)也确实比较了 Single-Agent 与四种 Multi-Agent 架构，而不是研究所有形式的内部 harness。

但更深层的问题是：原文把多个不同维度压缩成了"编排深度"：

1. Harness 完整性：状态、工具、验证、恢复、可观测性。
2. 推理时计算量：反思、搜索、重复采样。
3. 协调拓扑：单 Agent、中心化、多 Agent、并行。
4. 策略动态性：固定流程、动态拆解、动态角色。
5. 环境能力：沙箱、检查点、持久任务、权限系统。

这些维度并不同时增加，也没有统一的"深浅"排序。一个框架可以状态和验证很成熟，但保持单 Agent、线性循环；mini-swe-agent 就是很好的基线。

因此建议将主命题改成：

> Agent 的表现由模型、任务结构、脚手架能力和执行策略之间的匹配共同决定；框架能力丰富度提供更大的策略空间，但不保证具体任务上的性能提升。

标题也可以从《框架即智能》改为更严谨的：

> 《框架塑造智能：Agent 脚手架如何改变模型的实际表现》

### 4. "结构化通信可能消除专家稀释"目前仍只是未经验证的假设

DocManager 在回应第 292 行推测，结构化消息路由可能避免自由讨论中的专家意见稀释。

这是合理假设，但目前不能作为反驳：

- JSON schema 能减少格式和信息遗漏；
- 不能自动解决谁是专家、专家权重多少、冲突时采用谁、错误如何累积；
- 即使消息完全结构化，聚合器仍可能平均化强弱意见。

建议原文写成待验证假设：

> 结构化通信可能减少传输损耗，但是否能避免专家意见被错误聚合，需要单独比较自由讨论、结构化汇报、专家加权和外部验证等拓扑。

### 5. `trigger` 不是 QwenPaw 扩展——应彻底删除这个字段模型

你这次的补充非常关键。DocManager 在回应第 320–326 行仍然误以为 `trigger` 是 QwenPaw 的 host-specific extension。既然 QwenPaw 实际也没有这个字段，那么它不是：

- 开放标准字段；
- QwenPaw 字段；
- 现有实现约定。

它只是写作时尚未稳定下来的一种概念设计。

当前 [Agent Skills 规范](https://github.com/agentskills/agentskills)明确描述：Discovery 阶段加载 `name` 和 `description`，任务匹配 `description` 后才加载完整 `SKILL.md`。

因此不应再"标注为 QwenPaw 扩展"，而应这样改：

- 删除所有把 `trigger` 写成实际元数据字段的内容。
- 将 trigger 的有效思想并入 `description`：适用场景、正向触发、排除场景、邻近 Skill 区分。

原来的"desc 与 trigger 分工"一节建议整体替换为：

> `description` 应同时回答四个问题：这个 Skill 做什么、何时使用、何时不用、与相近 Skill 如何区分。

示例结构：

```
---
name: record-note
description: >
  创建轻量日常记录。当用户希望快速保存当前想法、备忘或待办，
  且没有要求讨论、正式文档整理或已有记录查询时使用。
  查询已有记录应使用 record-search；正式归档应使用 document-archive。
---
```

`name×3、desc×2、trigger×1` 也必须删除或重写为"宿主自建检索器的待验证实验配置"。

### 6. 安全部分仍然保留了一处错误的必然性表述

DocManager 在回应第 356 行仍然说：

> 移除代理作为主要防线是必要的。

这仍然过于绝对。某些威胁模型下，独立 egress gateway、DLP 或 API gateway 完全可以是主要强制控制点，尤其适合：

- 目标域名限制
- 数据分级与出站控制
- 凭证受众绑定
- 调用频率和金额限制
- 跨 Agent/工具的统一审计
- 被攻陷 Agent 的纵深隔离

它随后提出的"内部策略引擎有完整上下文，外部网关只能看命令文本"也是一个假二分。更好的设计是：

```
Agent 内部语义风险分析
        ↓ 产生结构化意图、数据来源、目标、风险标签
独立 Policy Decision Point
        ↓
进程外 Policy Enforcement Point
        ↓
工具 / 网络 / 文件 / 外部系统
```

外部执行点可以接收经过签名的结构化元数据，同时独立执行不可绕过的硬规则。这样既保留语义信息，又保持信任域隔离。

### 7. "不要用给人看的文档满足 AI"依然过于二元

DocManager 在回应第 380 行为原命题辩护：

> 不要用给人看的文档来满足 AI 的信息需求。

建议也放弃这句话。更好的三层模型是：

| 层次 | 作用 | 典型形式 |
|---|---|---|
| 权威知识源 | 定义事实与约束 | 文档、代码、测试、策略、数据库 |
| 检索索引 | 帮助发现证据 | BM25、向量、符号、AST、图、repo map |
| 上下文组装 | 为当前任务交付信息 | 原文片段、摘要、引用、结构化状态 |

"人类文档"和"AI 上下文"不必是两套相互替代的知识。更可维护的做法通常是共享权威来源，再为不同消费者派生索引和视图。

因此这篇文章的核心应从"文件 → 向量索引的范式替换"改为：

> 权威知识、检索结构和运行时上下文应解耦；向量检索只是多通道检索中的一种。

### 8. ASMP 可以保留三个能力作为"参考实现"，不能作为抽象必要条件

DocManager 想保留 Skill、子 Agent、Heartbeat 三个必要条件，只缩小适用范围。这作为个人框架规范是可行的，但与"通用 Agent 框架"定位冲突。

更好的办法是分两层：

**ASMP Core 抽象能力**

- 可版本化的维护对象
- 事件/incident 存储
- 定时或事件触发机制
- 逻辑隔离的提议者与评测者
- 确定性策略门
- 可回滚发布机制

**ASMP Reference Profile**

- 维护对象由 Skill 实现
- 隔离角色由子 Agent 实现

这样不需要放弃现有实现，又避免把实现名词写成通用原语。

## 2. DocManager 接受得太快的地方

**三个地方建议不要直接让步，至少要标注为争议点：**

### 2a. 第 4 条——结构化通信的价值被过度否定了

DocManager 的原始观点是"结构化消息路由可能避免专家意见稀释"。对方的反驳是"JSON schema 不能解决谁是专家、权重多少、冲突时采用谁"。

对方说得没错，但 DocManager 的观点也没有错。这是两个不同层次的问题：

- **DocManager 讲的是信道层**：结构化通信可以减少噪声混入，让专家输出保持可识别
- **对方讲的是决策层**：谁是专家、如何加权、如何仲裁——这些确实不是 schema 能解决的

正确的表述不是"结构化通信能消除专家稀释"，也不是"结构化通信没用"，而是：**结构化通信是必要不充分条件——它解决了信道噪声问题，但不解决元决策问题。** 这两层要分开讲。

### 2b. 第 3 条——五轴拆分很漂亮，但需要检验可操作性

对方给了五个轴：Harness 完整性、推理时计算量、协调拓扑、策略动态性、环境能力。

问一个实际问题：**写文档时，这五个轴每个都能独立给出有实质内容的章节吗？** 如果"环境能力"在 Agent 框架语境下只有两三段能写，而"协调拓扑"可以写一整章，那这个拆分在文档结构上就不平衡。

另一个问题：**这五轴是否穷尽？** 至少能想到一个可能的遗漏——**可观测性/可调试性**。框架对智能的影响中，框架能否让开发者观察和修正 Agent 的推理过程，是独立于这五轴的一个维度。如果框架提供了好的 trace/log/replay 能力，开发者能更快发现和修复 Agent 的错误行为——这直接"塑造"了实际表现。

### 2c. 第 5 条——trigger 的处理可以更干净

对方说"trigger 只是你写作时的概念设计，必须彻查删除"。这没问题，但需要确认一点：**trigger 这个概念本身有没有保留为"设计建议"或"未来方向"的价值？** 如果有，可以不是删除，而是迁移到一个明确标注为"设计提案"的独立小节。概念设计本身不是错，把它包装成既有实现才是错。

## 3. P0/P1/P2 修改顺序需要调整

现在的划分：
- P0：论文阅读清单、Skill 命中率、上下文纯度、框架即智能（勘误）
- P1：重构论证（五轴拆分、多维上下文、安全架构等）
- P2：新增四篇文档

问题在于：**"框架即智能"这个标题改成"框架塑造智能"不只是勘误，它牵涉到整篇文档的论证基调。** 标题从绝对判断变成因果关系描述，正文的论证方式也要跟着变。如果 P0 改了标题，P1 又要重构论证，等于同一篇文档改两遍。

建议调整为四级：

| 优先级 | 内容 | 理由 |
|--------|------|------|
| P0（纯事实纠错） | 论文阅读清单、Skill 命中率、trigger 删除 | 纯勘误，不牵涉论证结构 |

## 4. 证据标签体系的实际问题

七个标签：`[实践观察]` `[机制假设]` `[研究证据]` `[框架特定]` `[规范要求]` `[经验参数]` `[时间敏感]`

**方向完全对，但实操中会有四个问题：**

### 4a. 标签互斥性不够

一个论断经常同时属于多个标签。比如"Skill 库扩张超过阈值后命中率下降"——这既是 `[研究证据]`（来自论文），也是 `[经验参数]`（阈值是经验值），可能还是 `[框架特定]`（如果研究只在特定框架上做过）。文档里每个论断都标三个标签，视觉噪声会很大。

建议：**设一个主标签 + 可选的修饰标签。** 主标签回答"这个论断的知识论地位是什么"，修饰标签回答"需要注意什么边界条件"。

### 4b. `[时间敏感]` 是维护负担

技术文档不是博客，不是论文。标了 `[时间敏感]` 的内容意味着你需要一个机制来定期检查和更新。如果文档有 15 篇，每篇有 5-10 个时间敏感标注，那就是 75-150 个需要定期 review 的点。没有自动化支持，这会变成空头支票。

实际建议：`[时间敏感]` 改为 **`[截至YYYY-MM]`** ——直接标上截止日期，比一个抽象标签更可操作。review 时只需搜索过期日期。

### 4c. 缺一个关键标签：`[未解决争议]`

专家级文档最有价值的地方之一就是**诚实地呈现争议**，而不是假装某个立场是定论。当前七个标签里没有一个能表达"这里有两个对立观点，都有道理，目前没有定论"。

建议加上 `[争议/未决]` 标签。这比假装中立或选边站更有专业价值。

### 4d. 需要定义"强结论"的边界

不是所有陈述都需要来源。"Agent 是一种自主执行任务的系统"不需要来源。"在 Skill 库超过 N 个时命中率开始下降"需要来源。边界在哪？

建议：**需要来源的论断 = 可被证伪的经验性主张 + 对实践有直接影响的设计决策。** 定义性的、概念性的、常识性的不需要。

## 5. 补充视角

### 5a. 15 篇文档之间的内部一致性

八条反馈都是针对单篇或单个论点的。但 15 篇文档作为一个系列，**跨文档的一致性**是一个独立的质量维度。比如：

- 第 3 篇讲"编排深度是单轴"，第 7 篇讲"上下文质量是多维的"——读者会问：为什么一个单轴一个多维？判断标准是什么？
- 如果在 A 篇用了 `[实践观察]` 标签，B 篇也要用，而且含义要一致。

建议：在所有单篇修改完成后，做一次 **跨文档一致性审计**。这应该在 P1 之后、P2 之前。

### 5b. 对方的修改计划偏重纠错，缺少正向建构

八条反馈 + 修改计划，整体方向是"修正错误、提高严谨性"。这没问题，但文档的价值不只是没有错——还在于**对读者有什么启发、能指导什么实践**。

建议在 P2 的四篇新文档中，至少有一篇是 **"Agent 工程化的实践决策指南"**——不是理论分析，而是"遇到 X 情况时，你应该怎么选、为什么"。这种文档对读者的直接价值最高。

### 5c. 一个元问题：DocManager 与审核者的分工

DocManager 现在处于一个微妙的位置——是文档的作者/编排者，但在采纳审核意见。**八条里七条转向对方立场**，这个比例值得关注。

不是说对方不对。但如果每一轮都大面积让步，有两个风险：
1. 文档变成审核者的观点而不是自己的观点——署名是自己的，但核心论证是别人的
2. 可能丢失一些原始直觉中正确的东西（比如上面说的结构化通信）

建议：**对每个让步点标注让步的原因。** 是"对方的论据确实更充分"，还是"没能力反驳所以先接受"？前者没问题，后者需要后续验证。

---

总结：第二轮审核质量明显高于第一轮，对方从纠错者变成了建模者。但替代框架本身也是假设，需要同样标准的审视。修改顺序基本合理但需要调整 P0/P0.5 的边界。证据标签方向对但需要解决互斥性、维护成本和缺失标签的问题。最重要的是——保持自己的判断力，不要让审核变成单向的意见注入。
