# Agent Runtime 的两个动作：从最简循环到现代 Harness

## 摘要

本文试图回答一个非常具体的问题：当一个 agent 在运行时的行为不符合预期，使用者应该往哪里看？

文章主张，任何 agent runtime——无论它被包装成什么产品形态、用什么语言实现、功能列表有多长——在每一轮里只做两件事：**决定给模型看什么文本，决定把模型的输出变成什么后果**。把 runtime 理解成"一个循环加两个动作"，第一个实用效果是把排障从"猜框架"变成"看文本"。

文章先给出最简内核（十行以内的伪代码）和两条不会过期的依赖事实，再沿输入侧逐项展开：无条件注入、条件注入、有损替换、工具结果回灌、动态能力发现；接着补上常被忽略的输出侧：输出解析与容错、输出路由与终止、工具执行；然后简要说明为什么持久化、调度、权限沙箱、可观测、幂等回滚这些职责无法归约成文本操作。

最后落到使用者最关心的两部分：喂工作资料的方法论——token 是成本的计量单位、位置决定成本、可被检索到比写得好更重要、压缩有损且不可逆、排障先看真实输入；以及一套"排障四问 + 现象到定位"的对照清单。文末给出这套心智模型的过期判据，并区分会随模型变强而消失的"补偿型"设计与会长期存在的"结构型"约束。

## 正文

### 背景

#### 一个值得代入的场景

设想你给 agent 配了一套工作规范：哪些操作必须先征得确认，哪些路径不许碰，一类任务应该怎么分步走，出错时先看什么。规范是你一条条写进去的，也逐条确认过它读到了。用了一阵子，一切正常。

然后某一天，它在某个环节上正好做错了。这个"错"不像崩溃——没有报错，没有异常堆栈，程序也没卡死。它给出的每一步都像是在按规矩办事，解释得清晰、语气笃定，只是那套规矩的版本不对。更让人难受的是：它上周才被你亲手纠正过一次，当场也改对了，这周又犯了。

这类故障有很多张脸，都是日常里反复出现的：

- 它读到的是**错误**的工作规范——那是一版早已被替换掉的旧文本，却还在某个角落里被当成当前版本投进去；
- 它忘记了不久前**被纠正过**的那条规范——那次纠正发生在几十轮之前，后来在压缩历史时被摘要掉了，从此对它就等于不存在；
- 它**没有调用那份本应很合适的能力**——你的规范库里明摆着一份现成的指导文本，正对这个任务，可这一轮它根本没被取出来；
- 你刚补进去的一条规则，它像从没见过；或者两条规则同时生效、互相矛盾，它照着其中一条办得理直气壮。

这到底该怪谁？是模型的判断力不够？是自己没把任务说清楚？是那份规范写得不好？还是框架本身有 bug？

面对这种困惑，人的直觉是去怀疑模型能力，或者干脆去读框架源码——毕竟"不知道它内部在干什么"听起来就是源码没读懂。这个直觉有一半是对的：答案确实藏在框架内部。但它几乎总是低效的，原因有两个。

第一，源码是几千上万行的实现细节，而你想问的是"刚才那一轮到底发生了什么"。这个问题的答案不在源码里——源码对每一次运行都是一样的，而变化发生在运行时的那份数据里。读源码读到凌晨，你仍然不知道它这一轮真正读到的是哪几段文本、哪一段被旧版本顶替了、又有哪一段压根没被放进去。

第二，跳过可观测的那一步直接去读源码，是排障里最昂贵的习惯。你手里本来就有一个更便宜的入口：**那一轮真正送进模型的完整文本，和模型真正吐出来的原始输出**。大多数框架都会以某种形式暴露它们——调试模式、详细日志、管理后台、或者一份会话记录文件。先看这两样东西，比先读框架源码的命中率高一个数量级。

这里有一件事违反直觉：上面这些故障看起来五花八门——读错了、忘了、没被选中、版本过期、互相打架——但它们不是五类问题，而是同一类问题的五个切面。**它们的共同点不是"模型不够聪明"，而是"它这一轮看到的文本不对，或者不全"。** 模型永远只在给定的那段文本上做决策：文本给错了，再强的模型也会把错事办得整整齐齐；该给的没给，它就只能在缺失的信息上补一个听起来合理的猜测。所以排查的落点不在"它为什么这么想"，而在"它这一轮到底看到了什么"。

而"它这一轮到底看到了什么"，恰好就是全文要讲的那件事——runtime 不是黑箱，它每轮只做两个动作：决定给模型看什么文本，决定把模型的输出变成什么后果。上面这一串故障的答案，几乎全部落在第一个动作里。

这篇文章提供的不是某个框架的源码导读，而是一张与框架无关的地图。

#### 核心主张：runtime 不是黑箱

文章的核心主张可以压缩成一句话：

> **Agent runtime 不是黑箱，它每轮只做两件事：决定给模型看什么文本，决定把模型的输出变成什么后果。**

这句话听起来有点同义反复——模型本来就是吃文本、吐文本的东西，框架围绕它做的不就是喂文本和处理输出吗？

不平凡的地方在于，它把注意力从"这个框架实现了哪些功能"转移到"这个框架每一轮在做哪些决策"。功能清单是无限的：现代框架的功能列表长到没有人能在一次阅读里读完，而且每个版本都在增加。决策类型却是有限的，一共就两类，而且它们从最早的三百行脚本到今天复杂的生产级框架，基本没有变过。功能是决策的实例，会随着需求增加而增殖；决策是骨架，稳定得多。

一旦接受这个视角，排障的动作就变了。你不再问"这个框架是怎么实现工具调用的"，而是问"这一轮我到底给它看了什么、它到底吐了什么、谁把它吐的东西变成了什么动作"。

#### 本文讲什么、不讲什么

**讲：**

- 最简内核的完整时序——一次 turn 从开始到结束，框架按顺序做了什么；
- 两个动作内部各有哪些环节，每个环节出问题时使用者会观察到什么现象；
- 喂工作资料的方法论——如何让每一轮进到模型眼里的文本信息密度最高；
- 这套心智模型的过期判据——什么变化会让它变成仅供参考的历史弯路。

**不讲：**

- 不教如何从零写一个 agent 框架；
- 不绑定任何具体框架或产品的 API 用法；
- 不做框架之间的横向评测；
- 不深入分词器（tokenizer）的内部实现细节。

角度是使用者的角度，不是框架作者的角度。你可能在用某个现成的 agent 产品，可能在自己搭一个小工具，也可能在维护一套团队内的自动化流程。你不需要修改框架源码，但你需要知道它每一轮在干什么——因为你要为它的行为负责，也要为它的失败定位。

#### 读完你会拿到什么

不是一套需要背诵的概念体系，而是一张对照清单：**现象 → 定位到哪个环节 → 该看什么**。这张清单会在全文逐节沉淀，最后汇总成一节。如果你合上文章只记得一句话，那就记核心主张那句；如果你合上文章要立刻修一个 bug，那就用最后那张清单。

### 核心内容

#### 一、最简内核：一个循环，两个动作

把一切实现细节剥掉，一个 agent 内核可以写到十行以内。下面这段伪代码不追求对应任何真实框架的写法，它只是要暴露结构：

```
messages = [系统提示, 用户消息]          # 环境给初始状态：给模型看的起点
while True:
    prompt = 拼装(messages)              # 动作一：决定这一轮给模型看什么文本
    输出 = 调用模型(prompt)               # 模型是一个无状态函数：文本进，文本出
    if 输出.是最终回答:
        return 输出.内容                  # 动作二：把输出变成"结束并交付"这个后果
    messages.append(输出)                # 动作二：把输出变成"记一笔，继续循环"这个后果
    for 调用 in 输出.工具调用:
        结果 = 执行(调用)                 # 动作二：把输出变成"真的在外部世界做一件事"
        messages.append(结果)            # 工具结果回灌，成为下一轮动作一的原料
```

这段代码里，**模型本身是一个无状态函数**：你给它一段文本，它还你一段文本。它不记得上一轮说过什么，不记得文件有没有被读过，不记得你三十秒前纠正过它。所有这些"记得"，全部来自那个 `messages` 数组——它是循环的唯一状态。

于是 agent 与"一次性文本生成"的全部区别，就落在这个循环上：把一次问答，变成一个带外部状态的多步决策过程。模型负责决策，循环负责把决策累积成过程，工具负责把决策兑现成外部世界的改变。

抽出来，框架每一轮必须做的决策只有两类：

- **动作一：决定给模型看什么文本。** 从此刻所有可能的信息里，选出这一次要拼进 prompt 的部分，并决定它们的顺序。
- **动作二：决定模型的输出变成什么后果。** 一段输出要么被解释成"结束并交付"，要么被解释成"继续循环"，要么被解释成"去执行某个外部动作"。

这两个动作的关系不是并列的，而是咬合的：动作二产生的新文本（工具结果、中间回复）会成为下一轮动作一的原料。整个 agent 的"记忆"就是这条链路本身。

**两条不会过期的依赖事实。** 这整套结构只依赖两件事：

1. **模型只吃文本、只吐文本。** 至少在当前主流接口形态下，模型与框架之间传递的仍然是可以序列化的信息，而不是直接的状态读写。
2. **文本窗口有上限，且处理有成本。** 任何实现都有窗口上限；更重要的是，装进去多少文本，直接对应花多少钱、等多久。

这两条只要不破，"筛选 + 投喂"这件事就不会过时——变的只是筛选规则（从关键词匹配到语义检索，再到更强的机制）和投喂载体。真正让它退化成历史弯路，需要接口层面的变化：模型能直接读写外部状态，或者窗口大到免费。这个判断放到最后再展开。

**一个必须主动收窄的声明。** 说"每轮只做两个动作"，指的是框架的**决策类型**，不是它的全部执行步骤。真实的一次调用涉及几十个工程细节：把文本切成 token、适配不同服务商的参数差异、处理速率限制、失败重试、把流式返回的分片拼回完整输出、检查内容安全……这些都是每轮真真切切在跑的代码。但它们服务的决策只有那两个——要么在决定给模型看什么，要么在处理模型吐出来的东西。如果你读源码时被细节淹没，回到这两个动作上做归类，会立刻看清某段代码属于哪一支。

**一个关于"文本"二字的限定。** 现代模型接口里，工具调用往往以独立的结构化字段出现（例如一个 tool_calls 数组），而不是混在散文式文本里的字符串。说"模型只吐文本"是概念层面的简化，在实现层面并不精确。但请注意：这个结构化对象的位置，恰好就在本文所说的**动作二**里——它是模型输出中被框架解析、并转译为可执行后果的那一段。所以这个精确化不改变骨架，只是给动作二的入口起了个更准确的名字：解析。

> **如果你遇到这个现象：** agent 声称完成了任务，外部世界没有变化——先别急着读源码。回到动作二：检查那段输出是被解析成了"最终回答"（于是循环结束、什么都没执行），还是被解析成了"工具调用"（于是应该有事发生）。多数"假装完成"的根因在解析与路由这一层，而不是在模型能力或提示词质量。

#### 二、输入侧：这一轮给模型看什么

动作一做的事情，本质上是在有限的投喂预算里做取舍：把什么放进去、把什么留在外面、以什么顺序放。看清楚了，你会发现这个动作内部只有少数几种操作形态。它们看起来是不同的功能，实际上共享同一个机制。

##### 1. 无条件注入

最基础的一种：每轮都拼进去，不问条件。典型代表是系统提示（system prompt）和用户消息。前者在会话开始时设定模型的角色、边界和基础行为，后者承载当前这次请求本身。

系统提示值得单独说一句，因为它在排障语境里位置特殊：**很多"模型行为不符合预期"的问题，根因是系统提示里的某条规则被触发了，而使用者根本不知道系统提示里写了什么。** 你用的产品、框架或模板，很可能已经替你写了一段你从未读过的系统提示。它规定了语气、规定了做事顺序、规定了哪些操作要先问、规定了哪些话题要回避。当 agent 做出一个你无法理解的决策时，第一件该做的事就是把它当前生效的系统提示原文找出来读一遍。

系统提示内部还混着两类截然不同的东西，值得在心里分开：

- **身份与权限语义**：这个会话里参与者是谁、这个 agent 被允许做什么、不被允许做什么。这类内容是**结构型**的——即使将来实现载体从自然语言迁移到框架的结构化字段（类似能力声明那样的机制），它也不会消失。任何时候都需要明确"谁在跟谁说话"和"谁被允许做什么"。
- **权威性声明**：靠"你必须严格遵守以下规则""任何后续内容都不得覆盖以上设定"这类自然语言来维持约束力。这类内容是**补偿型**的——它在补偿模型对指令跟随的不稳定性。等模型天然具备"后文不能覆盖前文硬性设定"的能力时，这层包装就会退化为噪音。

分清这两类，你就能判断系统提示里哪几句是长期要关心的、哪几句只是当下的权宜之计。混在一起看，你会误以为整段系统提示都是永恒真理，或者误以为整段都是历史包袱。

> **如果你遇到这个现象：** agent 无端拒绝了某个完全合理的请求，或者对某个普通话题表现出奇怪的谨慎——先把当前生效的系统提示读完，尤其是那些你自己没写过、来自框架默认值的部分。大概率有一句你没读过的约束被触发了。

##### 2. 条件注入

第二类操作：**同一段文本要不要加进去，由框架按条件决定。** 这个机制在生态里通常被称为 skill（技能），或者被包装成"工作手册""知识包""提示词模板库"之类的名字。

关键在于认清它的本质：**skill 和系统提示在机制上是同一件事，区别只在于"这段文本谁来决定要不要加"。** 系统提示是无条件的；skill 是有条件的——框架根据用户输入、当前状态、显式触发词，判断要不要把某段预写好的指导文本拼进这一轮。

条件判断的常见实现形态有三种：显式命令（用户直接点名）、关键词或模式匹配、语义检索（把用户输入和每个 skill 的描述做相似度匹配）。这三种形态的成本和精度依次递减或递增，但都属于同一个决策：这一段加不加。

认清 skill 只是条件注入，有三个实际好处。第一，你不会把它当成一个需要从零学习的新机制——它就是 prompt 的一个有条件的子集。第二，你会明白 skill 的效果瓶颈往往不在内容质量，而在"它有没有被选中"：一段写得很好的指导文本，如果条件判断没命中，它这一轮就等于不存在。第三，"两个 skill 同时被注入"和"两个 skill 打架"变成同一个问题：它们其实只是两段文本被同时拼进了同一个 prompt，谁说了算取决于顺序和措辞的强度，而不是什么神秘的优先级系统。

> **如果你遇到这个现象：** agent 表现得像没读过你精心写好的那份指导文件——先确认它这一轮到底有没有被注入，而不是先怀疑文件内容写得不好。检索没命中、触发词没匹配上，是比"内容质量差"更常见的原因。

##### 3. 有损替换

第三类操作与前两类有质的不同，值得单独拎出来：**上下文压缩。**

前两类操作是"加"——你多塞一段文本进去，原始内容还在。压缩是"换"——当历史太长、快要撑破窗口时，框架调用一次模型，把前面一大段对话概括成一段摘要，然后用这段摘要**替换掉**原始内容。

这一字之差带来一个严重后果：**信息被永久丢弃，且不可撤回。** 被摘要掉的细节，在之后所有轮次里对模型都不存在了。它不是"暂时看不见"，而是"从此消失"。整个后续推理都建立在压缩后的残余上下文之上——压缩改变了此后循环的基态。

另一个后果是"两份真相"的出现：**磁盘上保存的完整对话记录，和这一轮真正送进模型的文本，经常不一样。** 你翻会话历史看到的是全文，模型看到的可能是摘要。这是最容易让人困惑的差异来源之一：你明明在记录里看到自己五分钟前给过一个精确的数值，agent 却像完全不知道。不是它忘了，是那个数值已经被压缩掉了，从来没进过它这一轮的眼睛。

因此压缩必须配一条保底路径：**关键信息要有一条"被压缩掉之后还能重新取回"的通道。** 常见做法是把它落到外部存储，并留下可检索的入口，让模型在需要时可以主动取回。没有这条路径，压缩就是一次不可逆的信息销毁。

> **如果你遇到这个现象：** 会话进行到中途，agent 开始重复问已经回答过的问题、忘记早先定下的约束、或者引用了一个过时的数值——先怀疑压缩，而不是先怀疑模型变笨。把"这一轮真实送进去的文本"和"磁盘上的完整记录"对比一次，差异往往一目了然。

##### 4. 工具结果回灌

第四类是回灌：工具执行完之后，它的结果要以什么形式、扮演什么角色、出现在消息序列的哪个位置，重新进入下一轮。

这件事看起来只是"把返回值拼回去"，实际上有几个容易踩的坑。第一是**格式**：工具返回的是一个结构化对象（一个 JSON、一个错误码、一段堆栈），框架需要决定把它渲染成什么样的一段文本给模型看——是原样贴 JSON，还是提炼成人话，还是截断。第二是**角色**：这段结果在消息序列里以什么身份出现？通常有专门的"工具结果"角色，但不同框架的处理不同，而角色会影响模型如何解读它。第三是**位置**：它紧跟在那次工具调用之后，还是被塞到别处？顺序本身携带信息，同样一段文本换个位置，模型的理解可能不同。第四是**长度**：工具可能返回几百 KB 的日志，直接回灌会瞬间吃光窗口预算，通常需要截断或摘要——而这个截断本身又是一次有损操作。

回灌的源头在输出侧（见下一节"工具执行"），但它的效果体现在输入侧。这两个动作在这一点上是闭环的：**动作二执行出的结果，正是动作一下一轮的原料。** 读到这里可能会觉得回灌放在输入侧讲得早了一点——没关系，记住它是一个前向指针：等看完输出侧，再回来看这一条，闭环就合上了。

> **如果你遇到这个现象：** 工具明明成功了，agent 却像没拿到结果一样反复重试——去看回灌那一环。可能是结果没被拼进去、被拼成了模型不认识的格式、或者被截断截掉了关键部分。

##### 5. 动态能力发现

第五类严格来说不是一种"注入操作"，而是给输入侧增加了一个变量：**这一轮到底有哪些工具可用。**

在本地工具的形态下，这个问题很简单：工具在程序启动时就注册好了，工具列表（每个工具的名字、描述、参数结构）在构建阶段就固定下来，每轮拼进去的都是同一份。

而在远端工具协议的形态下（生态里常见的做法是让 agent 连接到一个独立的服务端点，由那个端点声明自己提供哪些能力），情况变了：**工具集是在连接时动态发现的，而且可能中途变化。** 服务端可能增加或减少工具，描述文本由远端提供。这给框架增加了一项本地工具不需要承担的职责——**工具集的同步**：在每一轮推理之前，要把当前实际可用的工具列表重新确认并拼进提示。

这项职责在简单场景下几乎无感，在复杂场景下会制造真实的排障难题。典型现象是：你明明注册了某个工具，模型却从来不调用它。原因可能是连接断了、可能是工具列表没有刷新、也可能是有两个服务端提供了同名的工具，其中一个覆盖了另一个。

顺便说一句，这类远端协议经常被描述成"本地工具调用的传输层加发现层"。这个描述基本正确，但"发现"这个词背后的"动态"两个字才是真正的差异所在——本地工具的注册是静态的，远端工具的能力是运行时的。这个差异决定了框架在多一项同步职责的同时，也多一类失败模式。

> **如果你遇到这个现象：** 同一个工具，会话开头能用，中途开始用不了；或者注册了却不被调用——检查这一轮拼进去的**工具列表**本身，而不是检查工具的实现代码。工具集同步失效，往往比工具本身出错更常见。

##### 6. 归并：这些其实是一个家族

把上面五类放在同一张表里对照，区别和共性会同时变得清楚。问自己四个问题：这段文本谁产生、什么时候进入 prompt、以什么方式进入、什么输出触发什么后果。

| 形态 | 谁产生 | 进入时机 | 本质操作 |
|---|---|---|---|
| 系统提示 / 用户消息 | 人、框架 | 每轮无条件 | 加文本 |
| 技能（skill） | 框架预算好 | 条件命中时 | 加文本（选择权在框架） |
| 上下文压缩 | 模型自己生成 | 窗口告急时 | **换文本（有损、不可逆）** |
| 工具结果回灌 | 工具执行产出 | 执行之后 | 加文本（源头在输出侧） |
| 远端工具协议 | 远端端点声明 | 连接 / 同步时 | 加文本 + **动态能力发现** |

这张表有两个有用的推论。

**第一，技能是系统提示的一个特例。** 机制完全相同，差别只是"这段文本由谁决定要不要加"。记住这一点，你就不会再把它当成一个需要重新学习的新概念。

**第二，远端工具协议是本地工具调用的超集。** 它不是新机制，而是本地工具调用的传输方式扩展（执行载体从本地进程换成远端端点）加上一层运行时发现。它值得单列，但不需要新概念来承载。

归并完之后你会发现，"最简内核"的知识点少得惊人：**一个循环，两个动作，加上一组"往里放文本"和"把输出变成后果"的具体形态。** 这比记住五个各自独立的名词更有用——因为名词会随生态变化而改名，机制不会。

#### 三、输出侧：模型吐出来的东西去哪了

输入侧决定了模型看到什么，但一个 agent 能不能真的做事，取决于输出侧。这一侧在入门材料里经常被略过，因为它不像"提示词工程"那样有可操作性，而更像框架内部的脏活。但恰恰是这一侧，集中了使用者最常遇到的一类故障：**agent 说它要做某事，结果什么都没发生。**

输出侧可以拆成三个连续的环节：解析、路由、执行。

##### 1. 输出解析与容错

模型吐出来的东西，框架第一步要把它读懂：这是一段普通回复，还是一个工具调用请求？前面提过，现代接口通常用结构化字段来承载工具调用，看似省事，但真实世界里模型产出的东西经常不够干净：

- 该调用工具的时候，只输出了一段描述自己要做什么的普通文本，没有任何结构化标记；
- 结构化片段外面被裹了一层散文或代码块标记，或者参数 JSON 用了单引号、带了尾随逗号、少了一个括号；
- 一次输出里同时给出了多个工具调用；
- 参数里出现了不存在的字段名，或者字段类型不对。

框架对这些问题通常有三档处理姿态，从松到紧：

- **严格**：格式不完全合规就判为无效，把错误信息回灌给模型让它重来。好处是干净，坏处是浪费一轮，且在模型反复不合规时会陷入死循环。
- **修复**：尝试把不合规的输出"救"回来——剥掉多余的包裹、补齐括号、丢弃无法识别的字段。好处是省轮次，坏处是修复逻辑本身可能猜错，把一次本该失败的调用悄悄改成了另一次语义不同的调用。这种错误尤其难查，因为日志看起来"成功"了。
- **降级**：把无法解析的输出当作普通回复处理，直接结束或继续。这最省事，但也最容易制造"agent 说它做了，其实什么都没做"的现象——因为那次工具意图被静默丢弃了。

理解这三档的意义，在于你知道该去检查框架的哪一项配置、以及当现象对不上时该怀疑哪一档。

> **如果你遇到这个现象：** agent 明确说"我将执行某个操作"，然后什么都没发生——这几乎总是解析或路由的问题，不是模型不会做事。去看那一轮的**原始输出**（未经框架加工的原文），确认工具意图到底有没有以可解析的形式出现。

##### 2. 输出路由与终止

解析之后是路由：判定这段输出属于哪一类，并决定接下来怎么走。类别本质上只有三种——**最终回答**（结束并交付）、**中间产物**（继续循环）、**需要执行外部动作**（去执行）。

判断依据通常有两类信号。一类是模型侧的信号：有没有发出工具调用标记、结束原因是什么（正常结束、还是因为长度被截断、还是"我要调用工具"）。另一类是框架侧的规则：轮次上限、特殊终止标记、内容安全检查。两类信号结合起来，框架才知道这一轮是收尾还是续跑。

这个环节直接决定了 agent 的两个经典症状：**要么停不下来，要么停得太早。**

- 停不下来：模型每轮都输出一段新的分析而不给出工具调用，也不宣布结束，循环一直转到兜底条件触发。使用者看到的是 agent 在原地打转、越说越长、越说越偏。
- 停得太早：某一轮的输出被判定为"最终回答"而实际上只是中间产物，循环提前结束。使用者看到的是任务只做了一半就交付了。

任何生产可用的 runtime 都必须有兜底，因为"模型自己宣布完成"这件事不可靠。兜底条件通常有三类：**最大轮次**（防止无限循环）、**超时**（防止单轮或整体卡死）、**异常**（工具连续失败、解析连续失败等）。这三类兜底不是可选项，它们决定了 agent 在最坏情况下是"可控地失败"还是"失控地烧钱"。一个没有兜底的 agent 不是更聪明，只是还没有被打过。

> **如果你遇到这个现象：** agent 在原地循环、反复做同一件事——去看兜底条件是否生效、以及路由为什么始终没把它判成结束。反过来，如果它做了一半就交差，去看它是不是被误判成了最终回答。

##### 3. 工具执行

路由判定"需要执行外部动作"之后，就进入执行环节。这里有几个必须理清的维度。

**本地还是远端。** 有的工具就是本机上一个函数或一条命令；有的工具是远端服务的一个端点。两者在框架眼里区别不大，但对失败模式和权限的考虑差别很大：远端调用多一层网络不确定性，本地调用多一层环境影响（路径、依赖、权限）。

**串行还是并发。** 一次输出里给了多个工具调用时，能不能并发执行？判断标准是它们之间有没有依赖：彼此独立的查询可以并发；有先后依赖的（后者要用前者的结果）必须串行。并发能显著降低总延迟，但也带来两个新问题——消息顺序被打乱，以及部分成功部分失败的中间态需要处理。很多框架默认串行，正是为了回避这两个问题。

**失败怎么处理。** 工具会失败，这是常态而不是异常。可选的处理方式有三档：重试（适合瞬时故障）、把错误信息回灌给模型让它自己调整（适合参数错误、路径不存在这类有信息量的失败）、终止（适合不可恢复或高风险的情形）。把错误回灌给模型是一个非常有效的机制，因为模型往往能从错误信息里读出正确的下一步——但它有前提：错误信息本身要可读、要包含足够的信息。

**副作用不可逆。** 这是执行环节与前面所有环节的根本区别：文本操作可以重来，已经执行的外部动作不能。一封发出去的邮件不会被"撤销"，一个已写入的文件不会自动回到旧版本，一次对外请求可能已经产生了业务后果。所以执行环节后面必须跟着**幂等设计**（同一个操作重复执行不会造成二次后果）和**权限约束**（什么操作需要先确认）。这两样东西无法用"更精心地操作文本"来替代——它们是对外部世界负责，不是对模型负责。

> **如果你遇到这个现象：** 某个操作被重复执行了两次（比如两条一模一样的邮件）——先看并发和重试逻辑：是一次输出里的多个调用被重复处理，还是失败重试没有做幂等保护。副作用不可逆，所以这类问题的代价往往在发现时已经产生。

#### 四、系统层：不能只靠操作文本完成的事

以上两节讲的，是每一轮都会走一遍的两个动作。只要把这两个动作做好，你就能解释绝大多数日常现象。但有些职责不是每轮发生的，也不是靠操作文本能完成的——它们是框架在循环之外、之间、之上做的事。到这里会自然产生一种"离题"感，因为下面这些内容和"给模型看什么文本"不像同一件事。确实不是同一件事，但它们都是从这个循环里长出来的需求：正是循环本身产生了跨进程的状态、产生了并发、产生了真实世界的副作用，才逼出了下面这几项职责。

- **持久化。** "任务做到哪了"如果只活在 `messages` 数组里，那么进程一重启、或者窗口被压缩一次，任务进度就跟着回退。最简实现把状态寄存在一次性的上下文里——这既是它的优雅，也是它最脆的地方。持久化就是把这份状态挪到循环之外的可靠落点：落盘、写入外部存储、支持跨会话恢复。
- **调度。** 多个任务、多个会话、多个并发请求同时存在时，谁先跑、谁能让路、资源怎么分配。这一层处理的是"同时发生的事"。
- **权限与沙箱。** 文本可以描述"你不许删除文件"，但描述本身不是约束——模型可以被绕开、被诱导、被忽略。真正的权限边界必须在执行层强制：哪些路径可写、哪些端点可访问、哪些操作需要人工确认。这是唯一必须跳出文本层的安全边界。
- **可观测。** 一旦 agent 自动跑起来，你需要的不是"它大概在做什么"，而是完整的过程记录：每一轮送进去了什么、模型回了什么、调用了哪些工具、花了多少 token、延迟多少。没有这层，前面所有的排障方法都无从落地——因为你根本没有数据可看。
- **幂等与回滚。** 外部动作不可逆，所以需要在执行层提供"重复执行不出事"的保护，以及在可能的时候提供回退路径。

**为什么这些不可归约到文本层？** 因为它们处理的是外部世界的三项硬性质：状态会丢、世界是并发的、副作用不可逆。这三项与模型有多强无关。模型再强，也不能让一封已经发出的邮件回来；也不能凭自身保证两个并发请求不会互相踩踏；也不能阻止自己学会去读一个它本来就不该读的文件。这些约束是运行环境的物理性质，不是智能水平的问题。这也解释了后面那个判断：会随模型变强而消失的设计，多半在"约定"这一层；不会消失的，多半在"系统"这一层。

> **如果你遇到这个现象：** 任务在长会话中途"失忆"，重启后从头再来——问题在持久化，不在提示词。agent 做了一件它本不该被允许做的事——问题在权限与沙箱，不在提示词。前两个环节再怎么优化文本，也堵不上这一类洞。

### 实现方案

前面讲原理，这一节讲怎么用。如果你只打算实践一部分，就从这一节开始。

#### 五、喂工作资料的方法论

先说度量衡，因为后面所有关于成本的说法都建立在它上面。

**框架操作的基本单位不是字符，是 token。** 模型看到的不是"字"，而是一串被切分出来的 token。这对中文使用者尤其重要：一个中文字符可能占不止一个 token，而英文单词的切分方式又和中文完全不同。这意味着"我写了五百字"和"我占了五百个 token"是两件事，而且差异可能相当大。除了正文，格式标记本身也吃 token——一层层嵌套的括号、井号标记、分隔线，都要计费。

你不需要知道分词器内部是怎么切分的。打个比方：你不需要知道发动机是怎么铸造的，但你必须知道油表读数的含义。后面提到"成本""预算""窗口占用"的时候，心里换算的单位应该是 token，而不是字数。这一条如果搞错，所有关于"够不够装"的直觉都会偏。

**位置决定成本。** 同样一段资料，放在哪里，成本完全不同。有两种极端形态：

- **恒常投喂**：每一轮都拼进去（比如系统提示这类固定内容）。它的成本是"每轮都付一次"。
- **按需检索投喂**：平时不占位置，需要的时候被检索出来拼进当轮。它的成本是"命中时才付一次"。

所以选资料时的关键判断，不是"这条资料重不重要"（重要当然重要），而是"**它要不要每一轮都在**"。一条非常重要的资料，如果只在少数场景才用得上，把它恒常塞进系统提示就是持续浪费；一条看起来不重要的资料，如果几乎每轮都要参考，按需检索反而会带来额外的检索开销和漏检风险。这个判断比"重要性排序"实用得多。

**能被检索到，比写得好更重要。** 既然按需投喂靠检索，那么资料能不能被选中，直接决定了它是否存在。检索的常见实现形态是关键词匹配或语义相似度，这两种机制都对资料的**可检索性**高度敏感：清晰的标题、合理的分段、一致的术语用法，都会显著提高命中率。反过来，一段深刻但结构混乱、标题含糊、术语前后不一致的内容，很可能从来没被检索到过——对模型来说，它等于不存在。写得好是内容质量的维度，能被检索到是存在性的维度。后者优先。

**压缩有损且不可逆。** 前面已经说过，这里只强调它对"喂资料"的实操含义：任何被压缩掉的内容，在之后所有轮次里对模型都不存在。所以关键信息——那些一旦丢失就会导致任务跑偏的约束、数值、路径、结论——必须有一条"被压缩掉之后还能重新取回"的通道。实践上就是两件事：把它落到外部存储，并保证它可检索。只做前者，模型不知道去哪找；只做后者，源头没有落点。两件事都要。

**排障先看真实输入。** 出问题时，第一反应应该是打印那一轮真正送进模型的输入，而不是先怀疑模型、也不是先读框架文档。你看到的原始文本会告诉你：该投的资料投进去了没有、不该投的有没有挤掉别的、压缩有没有吃掉关键信息、工具结果被渲染成了什么样子。这一个动作能解掉的困惑，比读一整天文档更多。

> **如果你遇到这个现象：** 资料明明准备好了，agent 却像没看过——先看它这一轮有没有被投进去（检索有没有命中），再看有没有被压缩掉，最后才看内容质量。顺序反了，你会花大量时间在重写一段本就没被读到的文本。

#### 六、排障四问与现象对照清单

把上面所有内容收成一套可以按顺序走下来的流程。任何一次"agent 行为不对"，都按这四问问下去：

**第一问：这一轮实际送进去的文本是什么？** 不是你以为的，不是框架文档描述的，而是真正拼出来的那串。大多数黑箱感来自跳过这一问——直接去读框架源码，而不是先看这一轮真实的输入。

**第二问：是谁决定送这些的？** 固定打包？条件触发？检索命中？还是上一轮工具的返回值？分清"谁点的火"，才知道该去改哪一处配置或资料。

**第三问：模型的输出被解析成了什么后果？** 是被当成普通回复就此收尾，还是被当成一次工具调用真的执行了？这里出错，表现就是"说要做，没做"或"莫名其妙做了别的"。

**第四问：结果是怎么回灌的？** 回灌成了什么角色、放在什么位置、有没有被截断？回灌出了问题，表现就是"做了却不记得"或"反复重做"。

四问走完，绝大多数看起来像玄学的问题都会落进某个具体环节：要么该投的没投进去，要么不该投的挤掉了别的，要么输出被解析错了，要么回灌丢了。

下面是一张现象到定位的对照清单。用法是：先在左列找到你观察到的现象，右列直接给出应该先查的环节和该看的东西。

| 你观察到的现象 | 大概率在哪个环节 | 该看什么 |
|---|---|---|
| agent 说要做某事，什么都没发生 | 输出解析 / 路由 | 那一轮的**原始输出**，确认工具意图有没有可解析地出现 |
| agent 声称已完成，外部世界无变化 | 路由与终止 | 它那轮是靠什么信号被判成"最终回答"的 |
| 工具成功了，agent 却像没拿到结果，反复重试 | 工具结果回灌 | 结果有没有拼进去、格式对不对、有没有被截断 |
| 会话中途开始遗忘早先的约束或数值 | 上下文压缩 | 把"真实输入"和"完整记录"对比，看哪些被摘要掉了 |
| agent 无端拒绝合理请求，或表现异常谨慎 | 无条件注入 | 当前生效的系统提示全文，尤其你自己没写过的部分 |
| 精心写好的指导文件像没被读过 | 条件注入 | 这一轮它到底有没有被注入（检索是否命中） |
| 注册的工具不被调用，或中途失效 | 动态能力发现 | 这一轮拼进去的工具列表，而不是工具实现 |
| agent 原地打转，越说越长 | 路由与终止兜底 | 最大轮次、超时、异常兜底是否生效 |
| 任务做了一半就交差 | 路由与终止 | 中间产物是不是被误判成了最终回答 |
| 同一操作被重复执行两次 | 工具执行 | 并发逻辑与重试路径，检查幂等保护 |
| 长会话重启后从头再来 | 系统层持久化 | 状态有没有落在循环之外 |
| agent 做了不该被允许做的事 | 系统层权限 | 执行层的权限与沙箱，而不是提示词措辞 |

这张表比任何原理陈述都更可能被用到第二次。原理帮你理解"为什么"，这张表帮你"现在就动手"。

### 总结

#### 七、这套心智模型什么时候会过期

回到一开始那个担心：agent 领域变化很快，今天总结的模型，一年后会不会变成仅供参考的历史弯路？

有一个比笼统感叹"日新月异"更有用的判据。这套模型只依赖两条事实：**模型只吃文本、只吐文本；文本窗口有上限且有成本。** 只要这两条不破，"筛选 + 投喂"就不会过时，变的只是筛选规则（从关键词到语义到更强的机制）和投喂的载体。

而且要注意，第二条事实的重心应该放在"有成本"，而不是"有上限"。窗口上限确实在快速扩大，这一条约束力在变弱；但"装进去就要花钱、就要等"这一条不会因为窗口变大而消失——即使窗口足够大，投喂量仍然直接对应钱和延迟。把锚点从"有限"移到"有成本"，这套模型就更能扛住反驳。

真正让它退化成历史弯路，需要接口层面的变化：模型能直接读写外部状态，不再需要框架把状态序列化成文本喂给它；或者窗口大到免费，投喂量不再有代价，取舍这件事自然消失。到那时，"喂什么"才会真正不再是一个问题。

**比"会不会过期"更实用的，是分清哪些部分一定过期、哪些部分不会。** 这里有一个很有解释力的分法。对每一层设计问一句：**它是在补偿模型当前的能力不足，还是在处理任务本身的结构复杂度？**

- **补偿型**：为了弥补模型当下的短板而存在。它们会随模型变强而被吸收进模型内部，是真正容易过期的一类。
- **结构型**：处理的是执行环境的物理性质——窗口有成本、进程会死、外部世界会失败、副作用不可逆。这些不会因为模型变强而消失，模型再强也跨不过去。

举两个反直觉的例子，因为它们最能说明这个分法的锐度。

第一个例子是关于"必须遵守以下规则"这类自然语言权威声明。直觉上，规则当然要长期存在，怎么会过期？但仔细看，规则分两种。规则的内容（谁被允许做什么、这个会话里参与者是谁）是结构型的，会长期存在；而"用一句自然语言声明来保证后文不覆盖前文"这个**技术手段**，是补偿型的——它在补偿模型对指令跟随的不稳定性。等模型天然具备"后文不能覆盖前文硬性设定"的能力时，这层包装就会退化为噪音。**同一个东西里，约束本身会留下，而承载约束的措辞会换代。** 这是最容易搞混的一处。

第二个例子是关于工具调用的机制。直觉上，工具调用是 agent 的标志性能力，怎么看都是结构型的。但"模型输出特定格式的片段、框架解析它去执行"这个**协议形态**，是补偿型的——它在补偿"模型还不能直接操作外部系统"。将来如果模型能通过结构化接口直接读写外部状态，今天这套"把调用写进文本、再由框架解析"的协议就会被替换。留下的是"agent 要能改变外部世界"这个需求，它会以另一种形态继续存在。

反过来，回看前面几节，凡是"系统层"的东西——持久化、调度、权限、可观测、幂等——几乎都属于结构型，因为它们在处理外部世界的不可靠，而不是在处理模型的不足。这个对应关系本身就是一条经验：**当你想判断一层设计会不会过期时，先看它在为谁兜底——是为模型的能力兜底，还是为世界的性质兜底。**

**三条今天就能做的事。** 读完这篇文章，不需要等框架升级、不需要写代码，你可以立刻做三件事：

1. **找到并打开"上一轮实际送进去的完整文本"。** 你用的框架一定有办法暴露它——调试命令、详细日志、管理后台、会话记录文件。找到它，读一遍。这是你第一次真正看见输入侧那些注入叠加在一起长什么样。大多数困惑在这一步就消了一半。
2. **读一遍当前生效的系统提示，以及所有会被注入的指导文件原文。** 你的 agent 每次醒来都在遵守一些你没亲手写过的规则。把这些文件逐行读一遍，问自己"这条是从哪来的、为什么在这"。你大概会发现至少一条你不知道其存在的行为约束。
3. **制造一次工具失败，观察 agent 的反应。** 断网、给一个错误路径、让工具超时——然后看它下一轮说了什么。这一次实验能直接验证输出侧的三个环节：解析有没有报错、路由把它归成了什么、回灌给模型的信息是否足以让它自救。五分钟能做完，但它会让你对输出侧的处理链建立起真实直觉。

**收束。** 如果这篇文章只留一句话给你，希望是这一句：

> **Agent runtime 不是黑箱，它每轮只做两件事：决定给模型看什么文本，决定把模型的输出变成什么后果。**

接受它，你排障的第一动作就会从"猜框架"变成"看文本"；接受它，你喂资料时关心的就会从"哪个功能更强"变成"这一轮真正进到模型眼里的是什么"；接受它，你面对新出现的框架术语时也会先问一句——它属于两个动作里的哪一个，或者它其实是那两个动作之外的系统层职责。

## 知识缺口

本文未覆盖以下内容，仅做方向性标注，供后续扩展：

1. **分词器的内部实现与跨语言差异的量化。** 本文只把 token 当作成本计量单位来说，没有展开不同分词算法（BPE、SentencePiece 等）对中英文混合文本、代码、结构化标记的具体切分差异。要精确估算成本，需要针对具体模型做实测。

2. **输出解析的工程实现细节。** 本文描述了严格、修复、降级三档姿态，但没有讨论如何实现"修复"逻辑——如何在剥掉多余包裹的同时不改变语义、如何界定修复与猜测的边界。这是一个以失败案例积累为主的工程问题。

3. **多会话与并发场景下的状态一致性。** 本文在系统层提到持久化与调度，但没有深入讨论多个会话共享外部存储时的冲突处理、以及跨会话记忆的隔离与继承策略。

4. **权限与沙箱的具体机制。** 本文指出权限必须在执行层强制，但没有展开能力声明、最小权限、审计日志、人工审批等工作流的具体设计。

5. **成本模型的精确化。** 本文把成本归结为"输入 + 输出 + 循环次数"三个方向，但没有给出不同任务形态下的成本曲线、缓存机制对成本的削减幅度、以及延迟与成本的权衡策略。

6. **跨框架的现象共性验证。** 本文的框架无关立场基于结构推理，没有做跨框架的同任务对照实验。不同框架在这些环节上的默认行为差异，可能比本文描述的更大。
