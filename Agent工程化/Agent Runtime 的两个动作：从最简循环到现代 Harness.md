# Agent Runtime 的两个动作：从最简循环到现代 Harness

## 摘要

本文试图回答一个非常具体的问题：当一个 agent 在运行时的行为不符合预期，使用者应该往哪里看？

文章主张，任何 agent runtime——无论它被包装成什么产品形态、用什么语言实现、功能列表有多长——在每一轮里只做两件事：**决定给模型看什么文本，决定把模型的输出变成什么后果**。把 runtime 理解成"一个循环加两个动作"，第一个实用效果是把排障从"猜框架"变成"看文本"。

出问题的时候，人的第一反应通常不是去看文本，而是怀疑模型（"是不是模型变笨了"）、凭感觉把提示词改得更重（加"你必须"、加感叹号）、去翻框架文档和社区帖子（"这个框架是不是不支持"）、或者干脆认定这是框架的问题。这些反应都很正常，但它们有一个共同点：跳过了同一件便宜得多的事——看这一轮真正送进去的文本，以及模型真正吐出来的原始输出。

这里有一个必须先说清的前提，它决定了后面所有内容的落点：**agent 的典型故障是"做错了"——它动得起来，也做得下去。** 它会照着一份你上周就已经改掉的规矩、一丝不苟地把活干完——因为你改的是文件，而这一轮它读到的仍然是这次会话开始时的那一份；它会把几十轮前刚被纠正过的约束再犯一次；会绕开本该调用的现成能力自己临时拼一个近似做法；会把不该碰的对象碰了、把不该写的地方写了，然后用一段自洽的解释告诉你为什么这么做是对的。它会行动，只是行动的依据不对。所以本文要回答的是两个具体问题：它这一轮是拿着什么在做决策，它吐出来的那段东西又被理解成了什么。

文章先给出最简内核（十行以内的伪代码）和两条不会过期的依赖事实，再沿输入侧逐项展开：无条件注入、条件注入、有损替换、工具结果回灌、动态能力发现。输入侧讲完，会把同一批东西换一个切法再排一遍——按"我们手上要维护的那几个文件"来排：配置文本什么时候被读取、技能的名字与描述怎么决定它会不会被选中、工具的声明怎么决定模型知不知道有这么个能力、远端能力为什么只能等到运行时才知道、对话历史为什么会自己长出压缩的需求。这一节同时回答一个反复被问到的问题：为什么各家框架不约而同地采用了同一套约定。**我们能掌控喂给模型的绝大部分内容，所以"科学地使用一个 agent"，约等于"把每一个输入项维护好"。**

接着补上常被忽略的输出侧：输出解析与容错、输出路由与终止、工具执行；然后简要说明为什么持久化、调度、权限沙箱、可观测、幂等回滚这些职责无法归约成文本操作。

最后落到使用者最关心的两部分：喂工作资料的方法论——token 是成本的计量单位、位置决定成本、可被检索到比写得好更重要、压缩有损且不可逆、按输入项逐个维护、排障先看真实输入；以及一套"排障四问 + 现象到定位"的对照清单。这张清单除了按"注入方式"排，还能对上"你手上要维护的那个文件"。文末给出这套心智模型的过期判据，并区分会随模型变强而消失的"补偿型"设计与会长期存在的"结构型"约束。

## 正文

### 背景

#### 一个值得代入的场景

设想你已经用了一阵子某个 agent。它每天替你读文件、改东西、跑命令、汇报结果，大多数时候都让人省心。你不是空手在用它的——你为它准备过几样东西。

你给它写了一份**规矩文件**。里面写着：哪些操作必须先问你、哪些目录不许碰、一类任务应该怎么分步走、出错时先看什么。很多框架都会默认去读一份放在约定位置的规矩文件，这类文件的名字通常长得像 `AGENTS.md`。这份文件是你一条条写进去的，写完还逐条确认过它读到了。

你给它配了**几个技能文件**。它们平时不占位置，遇到对口的任务时才会被取出来用。每份文件开头都有一行名字和一行说明，用来告诉它"什么时候该用我"，后面才是正文。

你给它**接了几个工具**，还挂了一个**远端服务**。前者让它能读文件、能跑命令、能查数据库；后者让它能访问一些本地实现不了的能力。

你还有**聊天记录**。它上一轮说了什么、工具上一轮返回了什么、你上一条消息纠正了什么，全都记在里面。

这些东西你大概从来没有放在一起看过——它们分散在几个目录、几个配置文件、几个控制台页面里，平时各管各的。但如果你把它们摆在同一张桌子上，会发现一件很朴素的事：

**在一轮里，模型能看到的其实只有这么几样，而且全都是我们放进去的。**

- 那份规矩文件里的文本；
- 被选中之后才被塞进来的技能文件正文；
- 聊天记录，可能已经被压过；
- 上一轮工具返回的结果；
- 一份"你现在能用哪些工具"的清单——你挂的那个远端服务，最后也是变成这份清单里的一行。

除此之外，模型看不到任何别的东西。它不知道你的目录长什么样，不知道你上一条消息之前发生过什么，也不知道你有几份技能文件正躺在那里没被用上。它只看这一段文本，并且只在这段文本上做决策。

而这份清单里的每一项，都有一把开关在我们手里：规矩文件是我们写的，技能文件是我们写的，工具是我们接的，聊天记录是循环自己攒的——怎么攒、什么时候压缩，也是我们配的。

后面你会发现，所谓"用好一个 agent"，绝大部分工作就是把这五项都维护好。

先看一条现实中经常发生的错。

你给那份规矩文件补了一条新规则，比如"改完代码必须跑一遍测试再交"。你写进去，保存，检查了一遍，确认文件里确实有这句话。然后你**没有开新会话**，直接在原来那个对话里继续让它干活。它改完了代码，没有跑测试，直接告诉你做完了。你去问它，它解释得很顺，语气笃定，看不出任何心虚。

这里值得停一下。它没崩，没报错，没有任何异常堆栈；它每一步都像是在按规矩办事——只是那一套规矩，不是你现在手上这份。你改的是文件，而这一轮它读到的，是这次会话开始时读到的那一份。改动的生效时刻是**下一次会话开始的时候**，不是保存的时刻。这件事第一次遇到会很反直觉：你明明看到文件已经变了，它却像完全没看见。

同样的机制还能长出好几张脸：

- 它把几十轮前你纠正过的一条又犯了一次。那次纠正确实发生过，也确实被它接受了；后来聊天记录太长，前面那段历史被概括成一段摘要，那条纠正没被概括进去。
- 技能文件就摆在那个目录里，这个任务正对口，可这一轮它根本没被取出来。它没有停下来问你，也没有报错，而是自己临时拼了一个近似的做法，把活按自己的理解办完了。
- 技能被取出来了，但它办出来的事和技能里写的对不上，明显漏掉了几条。打开那份文件一看，正文里加粗标记有几个星号没闭合、列表层级断在半截——内容一个字都没少，只是被读成了另一个结构。

这些情况发生时，人的反应是很有规律的：怀疑模型不行（"是不是模型被换了、变笨了"）；凭感觉把提示词改得更重（加"你必须"、加感叹号）；去翻框架文档、搜社区帖子（"这个框架是不是不支持这种用法"）；或者干脆认定是框架的问题。这些反应都正常，也都很便宜，但它们有一个共同点：**没有先去看这一轮真正送进去的那段文本，和模型真正吐出来的原始输出。**

这两样东西，大多数框架都有办法给你——调试模式、详细日志、管理后台、一份会话记录文件。先看它们，比先怀疑模型、先改提示词、先翻文档的命中率高得多。因为你要回答的问题不是"这个框架有哪些能力"，而是"刚才那一轮，到底发生了什么事"。前者是关于能力的知识，后者是关于这一次运行的数据——后者只能从这一次运行里读出来。

这篇文章要给的，不是某个框架的功能说明，而是一张与框架无关的地图。

#### 核心主张：runtime 不是黑箱

文章的核心主张可以压缩成一句话：

> **Agent runtime 不是黑箱，它每轮只做两件事：决定给模型看什么文本，决定把模型的输出变成什么后果。**

这句话听起来有点同义反复——模型本来就是吃文本、吐文本的东西，框架围绕它做的不就是喂文本和处理输出吗？

不平凡的地方在于，它把注意力从"这个框架实现了哪些功能"转移到"这个框架每一轮在做哪些决策"。功能清单是无限的：现代框架的功能列表长到没有人能在一次阅读里读完，而且每个版本都在增加。决策类型却是有限的，一共就两类，而且它们从最早的三百行脚本到今天复杂的生产级框架，基本没有变过。功能是决策的实例，会随着需求增加而增殖；决策是骨架，稳定得多。

一旦接受这个视角，排障的动作就变了。你不再问"这个框架是怎么实现工具调用的"，而是问"这一轮我到底给它看了什么、它到底吐了什么、谁把它吐的东西变成了什么动作"。

#### 本文讲什么、不讲什么

**讲：**

- 最简内核的完整时序——一次 turn 从开始到结束，框架按顺序做了什么；
- 两个动作内部各有哪些环节，每个环节出问题时使用者会观察到什么现象；
- 每一种输入项该怎么维护——配置文本、技能文件、工具声明、远端能力；
- 喂工作资料的方法论——如何让每一轮进到模型眼里的文本信息密度最高；
- 这套心智模型的过期判据——什么变化会让它变成仅供参考的历史弯路。

**不讲：**

- 不教如何从零写一个 agent 框架；
- 不绑定任何具体框架或产品的 API 用法；
- 不做框架之间的横向评测；
- 不深入分词器（tokenizer）的内部实现细节。

角度是使用者的角度，不是框架作者的角度。你可能在用某个现成的 agent 产品，可能在自己搭一个小工具，也可能在维护一套团队内的自动化流程。你不需要改动框架本身，但你需要知道它每一轮在干什么——因为你要为它的行为负责，也要为它的失败定位。

#### 读完你会拿到什么

不是一套需要背诵的概念体系，而是一张对照清单：**现象 → 定位到哪个环节 → 该看什么**。这张清单会在全文逐节沉淀，最后汇总成一节。它有一个刻意的设计取向：收录的现象全部是"做错了"的形态——做错了对象、做错了版本、做错了参数、做多了、做少了、做在了不该做的地方。这些正是实际使用中最常见的形态。

清单给的是同一批现象的两种排法：一种按"注入方式"，一种按"你手上要维护的那个文件"。

如果你合上文章只记得一句话，那就记核心主张那句；如果你合上文章要立刻修一个 bug，那就用最后那张清单。

### 核心内容

#### 一、最简内核：一个循环，两个动作

把一切实现细节剥掉，一个 agent 内核可以写到十行以内。下面这段伪代码不追求对应任何真实框架的写法，它只是要暴露结构：

```
messages = [系统提示, 用户消息]          # 环境给初始状态：给模型看的起点
while True:
    prompt = 拼装(messages)              # 动作一：决定这一轮给模型看什么文本
    输出 = 调用模型(prompt)               # 模型是一个无状态函数：文本进，文本出
    if 输出.是最终回答:
        return 输出.内容                  # 动作二：把输出变成"结束并交付"这个后果
    messages.append(输出)                # 动作二：把输出变成"记一笔，继续循环"这个后果
    for 调用 in 输出.工具调用:
        结果 = 执行(调用)                 # 动作二：把输出变成"真的在外部世界做一件事"
        messages.append(结果)            # 工具结果回灌，成为下一轮动作一的原料
```

这段代码里，**模型本身是一个无状态函数**：你给它一段文本，它还你一段文本。它不记得上一轮说过什么，不记得文件有没有被读过，不记得你三十秒前纠正过它。所有这些"记得"，全部来自那个 `messages` 数组——它是循环的唯一状态。

于是 agent 与"一次性文本生成"的全部区别，就落在这个循环上：把一次问答，变成一个带外部状态的多步决策过程。模型负责决策，循环负责把决策累积成过程，工具负责把决策兑现成外部世界的改变。

抽出来，框架每一轮必须做的决策只有两类：

- **动作一：决定给模型看什么文本。** 从此刻所有可能的信息里，选出这一次要拼进 prompt 的部分，并决定它们的顺序。
- **动作二：决定模型的输出变成什么后果。** 一段输出要么被解释成"结束并交付"，要么被解释成"继续循环"，要么被解释成"去执行某个外部动作"。

这两个动作的关系不是并列的，而是咬合的：动作二产生的新文本（工具结果、中间回复）会成为下一轮动作一的原料。整个 agent 的"记忆"就是这条链路本身。

把背景里列的那几样东西对到这段循环上，它们各有位置：那份规矩文件落在开头的**系统提示**里；技能文件的正文要等条件命中，才被拼进 `拼装(messages)`；聊天记录就是那个 `messages` 数组本身，窗口告急时会被压缩替换；工具返回的结果，是被 `append` 回来的那一条；而"你现在能用哪些工具"的那份清单，也是每轮 `拼装` 的时候拼进去的。换句话说，**模型每一轮看到的东西，没有一样是从天上掉下来的——全都是从这里拼进去的。** 记住这个对应关系，本文后半部分还会回来用它。

有一点值得在这里先点出来，因为它决定了后面所有排障思路的形状：**这两个动作的作用是"决定它做的事是什么"。** 动作一出了偏差，它会拿着一份错的信息把事做完；动作二出了偏差，它会去做一件与你预期不同的、但同样有实际后果的事。换句话说，runtime 的每一处偏差，最终都会在外部世界里落下一个"做错了"的痕迹——这也是为什么这类故障几乎总能被查清楚，只要你肯顺着痕迹往回推。

**两条不会过期的依赖事实。** 这整套结构只依赖两件事：

1. **模型只吃文本、只吐文本。** 至少在当前主流接口形态下，模型与框架之间传递的仍然是可以序列化的信息，而不是直接的状态读写。
2. **文本窗口有上限，且处理有成本。** 任何实现都有窗口上限；更重要的是，装进去多少文本，直接对应花多少钱、等多久。

这两条只要不破，"筛选 + 投喂"这件事就不会过时——变的只是筛选规则（从关键词匹配到语义检索，再到更强的机制）和投喂载体。真正让它退化成历史弯路，需要接口层面的变化：模型能直接读写外部状态，或者窗口大到免费。这个判断放到最后再展开。值得补一句的是：第二条事实的重心，其实落在"有成本"三个字上，而不是"有上限"。窗口上限在快速扩大，这一条的约束力在变弱；但只要装进去就要花钱、就要等，取舍这件事就不会消失。

**一个必须主动收窄的声明。** 说"每轮只做两个动作"，指的是框架的**决策类型**，不是它的全部执行步骤。真实的一次调用涉及几十个工程细节：把文本切成 token、适配不同服务商的参数差异、处理速率限制、失败重试、把流式返回的分片拼回完整输出、检查内容安全……这些都是每轮真真切切在跑的代码。但它们服务的决策只有那两个——要么在决定给模型看什么，要么在处理模型吐出来的东西。如果你去翻框架文档、被一连串实现细节淹没，回到这两个动作上做归类，会立刻看清每一处属于哪一支。

**一个关于"文本"二字的限定。** 现代模型接口里，工具调用往往以独立的结构化字段出现（例如一个 tool_calls 数组），而不是混在散文式文本里的字符串。说"模型只吐文本"是概念层面的简化，在实现层面并不精确。但请注意：这个结构化对象的位置，恰好就在本文所说的**动作二**里——它是模型输出中被框架解析、并转译为可执行后果的那一段。所以这个精确化不改变骨架，只是给动作二的入口起了个更准确的名字：解析。

> **如果你遇到这个现象：** agent 明确表示它要去执行某个操作，也确实动了手，但做出来的是另一件事——参数不对、对象不对、路径不对，或者干脆用一套你没预期的方式把事情绕过去了。先别急着怀疑模型，也别急着改提示词。回到动作二：看那段输出被解析成了哪一个工具调用、参数是怎么被读出来的、是谁决定把它当成"要做的事"。多数"做错"的根因在解析与路由这一层，而不是在模型能力或提示词质量。

#### 二、输入侧：这一轮给模型看什么

动作一做的事情，本质上是在有限的投喂预算里做取舍：把什么放进去、把什么留在外面、以什么顺序放。看清楚了，你会发现这个动作内部只有少数几种操作形态。它们看起来是不同的功能，实际上共享同一个机制。

这一节先按"怎么把文本送进去"来分：无条件注入、条件注入、有损替换、工具结果回灌、动态能力发现。把这几副面孔看完之后，这一节的最后一小节再换一个切法——按"我们手上要维护的那几个文件"重排一遍。同一批东西，两张表。

##### 1. 无条件注入

最基础的一种：每轮都拼进去，不问条件。典型代表是系统提示（system prompt）和用户消息。前者在会话开始时设定模型的角色、边界和基础行为，后者承载当前这次请求本身。

系统提示值得单独说一句，因为它在排障语境里位置特殊：**很多"模型行为不符合预期"的问题，根因是系统提示里的某条规则被触发了，而使用者根本不知道系统提示里写了什么。** 你用的产品、框架或模板，很可能已经替你写了一段你从未读过的系统提示。它规定了语气、规定了做事顺序、规定了哪些操作要先问、规定了哪些话题要回避。当 agent 做出一个你无法理解的决策时，第一件该做的事就是把它当前生效的系统提示原文找出来读一遍——注意，这里的典型症状是"它按一条你不知道存在的规则把事情办成了另一个样子"。

系统提示内部还混着两类截然不同的东西，值得在心里分开：

- **身份与权限语义**：这个会话里参与者是谁、这个 agent 被允许做什么、不被允许做什么。这类内容是**结构型**的——即使将来实现载体从自然语言迁移到框架的结构化字段（类似能力声明那样的机制），它也不会消失。任何时候都需要明确"谁在跟谁说话"和"谁被允许做什么"。
- **权威性声明**：靠"你必须严格遵守以下规则""任何后续内容都不得覆盖以上设定"这类自然语言来维持约束力。这类内容是**补偿型**的——它在补偿模型对指令跟随的不稳定性。等模型天然具备"后文不能覆盖前文硬性设定"的能力时，这层包装就会退化为噪音。

分清这两类，你就能判断系统提示里哪几句是长期要关心的、哪几句只是当下的权宜之计。混在一起看，你会误以为整段系统提示都是永恒真理，或者误以为整段都是历史包袱。

**维护这个输入项最常见的坑。** 这类文本有一个决定性的特点：它通常**在会话开始时被读一次，之后整场沿用**。框架自带的默认设置是这样，你写的那份规矩文件通常也是这样。所以这一项的头号问题就是：**改了不生效。** 你在文件里加了一条规则、保存、关掉编辑器，然后回到那个还在进行的会话里继续用——它这一轮读到的仍然是会话开始时的那一份，于是它照旧做法办。这是初学者最常撞的一堵墙，也是"我明明写清楚了它为什么还这样"最常见的真相。

第二个坑是**同源副本**。同一条规矩可能写在两个地方：框架的默认值里一份，你自己的配置文件里一份。两处说法不一致的时候，它会照其中一份办——而你不知道是哪一份。要去查的时候，先问自己"这条规矩一共有几个副本、哪一个才是被真正读进去的那一份"。

> **如果你遇到这个现象：** 你明明改了那份写规矩的文件、也保存了，agent 还是照旧做法办；甚至你把改好的内容原样贴进对话，它下一轮又忘了——先别怀疑模型，去看这一轮真实输入里的那段文本是不是你手上这一版，以及这段文本是**什么时候被读进去的**。如果它是会话开始时读一次、之后沿用的那一类，那么改文件本身不会让当前会话生效，你需要重载，或者开一个新会话。

> **如果你遇到这个现象：** agent 无端拒绝了某个完全合理的请求，或者把一件你明确交代过的事按一条你从没听说过的规矩办了——先把当前生效的系统提示读完，尤其是那些你自己没写过、来自框架默认值的部分。大概率有一句你没读过的约束被触发了，而它已经照着那句话把事做了。

##### 2. 条件注入

第二类操作：**同一段文本要不要加进去，由框架按条件决定。** 这个机制在生态里通常被称为 skill（技能），或者被包装成"工作手册""知识包""提示词模板库"之类的名字。

关键在于认清它的本质：**skill 和系统提示在机制上是同一件事，区别只在于"这段文本谁来决定要不要加"。** 系统提示是无条件的；skill 是有条件的——框架根据用户输入、当前状态、显式触发词，判断要不要把某段预写好的文本拼进这一轮。

条件判断的常见实现形态有三种：显式命令（用户直接点名）、关键词或模式匹配、语义检索（把用户输入和每个 skill 的描述做相似度匹配）。这三种形态的成本和精度依次递减或递增，但都属于同一个决策：这一段加不加。

认清 skill 只是条件注入，有三个实际好处。第一，你不会把它当成一个需要从零学习的新机制——它就是 prompt 的一个有条件的子集。第二，你会明白 skill 的效果瓶颈往往不在内容质量，而在"它有没有被选中"：一段写得很好的文本，如果条件判断没命中，它这一轮就没参与决策，模型只能自己临时拿主意——而临时拿的主意，往往和你写在那份文件里的规矩对不上。第三，"两段技能文本在同一轮被同时注进去"变成同一个问题：它们其实只是两段文本被同时拼进了同一个 prompt，谁说了算取决于顺序和措辞的强度，而不是什么神秘的优先级系统。

**维护这个输入项最常见的坑。** 这里有两个坑，比内容写得不好更常见，也更让人困惑。

**第一，名字和描述对不上，导致命中率低。** 要不要用这份技能，是**选择**这一步决定的；而选择这一步只看它开头那行名字和那行描述，正文它根本不读。如果描述没有准确回答"什么时候该用我"，这份正文就会长期躺在那里选不中——文件写得再好，也不参与任何决策，你只会看到"它该用的时候从来不用"。反过来，描述写得比正文实际的覆盖面更大，它就会在一堆不该用它的轮次里被选中，于是你看到"它这次怎么按另一套办事"。

**第二，正文格式不对，导致被读错。** 加粗的星号没闭合、列表层级断在半截、代码块没关——这些都不影响它被选中，影响的是它**被读懂**。破损的标记会把相邻段落并到一起，条目会被吞掉，模型于是照着读歪的版本办事，结果看起来就像"它没按文件里写的做"。

还有第三种情况：**同一轮里命中了好几份。** 两段文本在同一轮里同时被拼进同一个 prompt，谁的措辞更强、谁的位置更靠后，谁就更容易被采纳——这不是一个优先级系统，而是文本堆叠的副产品。

> **如果你遇到这个现象：** 技能就摆在那里，绝大多数轮次它都没被用上，你手动点名才生效——先去看技能的 name 和 description，它们是不是把"什么时候该用我"写清楚了。选择这一步只看这两样，不看正文。

> **如果你遇到这个现象：** 技能被选中了，可它办出来的事和技能里写的对不上、或者明显漏掉了几条——去看那份正文的格式：加粗标记有没有闭合、列表层级有没有断、代码块有没有关。格式破损不会让它读不到，只会让它读错。

> **如果你遇到这个现象：** agent 办出来的结果和你那份精心写好的指导文件对不上，走的是另一套自认为合理的做法——先确认它这一轮到底有没有被注入，而不是先怀疑文件内容写得不好。检索没命中、触发词没匹配上，是比"内容质量差"更常见的原因。

##### 3. 有损替换

第三类操作与前两类有质的不同，值得单独拎出来：**上下文压缩。**

前两类操作是"加"——你多塞一段文本进去，原始内容还在。压缩是"换"——当历史太长、快要撑破窗口时，框架调用一次模型，把前面一大段对话概括成一段摘要，然后用这段摘要**替换掉**原始内容。

这一字之差带来一个严重后果：**信息被永久丢弃，且不可撤回。** 被摘要掉的细节，在之后所有轮次里对模型都不存在了。它不是"暂时看不见"，而是"从此消失"。整个后续推理都建立在压缩后的残余上下文之上——压缩改变了此后循环的基态。

另一个后果是"两份真相"的出现：**磁盘上保存的完整对话记录，和这一轮真正送进模型的文本，经常不一样。** 你翻会话历史看到的是全文，模型看到的可能是摘要。这是最容易让人困惑的差异来源之一：你明明在记录里看到自己五分钟前给过一个精确的数值，agent 却像完全不知道——更麻烦的是，它不会因此停下来问你，而是会补一个自己觉得合理的数值继续往下做。不是它忘了，是那个数值已经被压缩掉了，从来没进过它这一轮的眼睛。

压缩吃掉的不只是对话。曾经被注入过的技能正文也在历史里，压缩之后，那段正文只剩一句摘要。模型可能还记得结论、却忘了依据，于是自己补一个说得通的版本继续做——你看到的是"它明明知道这条规矩，却按另一套办"。

因此压缩必须配一条保底路径：**关键信息要有一条"被压缩掉之后还能重新取回"的通道。** 常见做法是把它落到外部存储，并留下可检索的入口，让模型在需要时可以主动取回。没有这条路径，压缩就是一次不可逆的信息销毁。

> **如果你遇到这个现象：** 会话进行到中途，agent 开始重复问已经回答过的问题、违反早先定下的约束、或者引用了一个过时的数值并据此继续推进——先怀疑压缩，而不是先怀疑模型变笨。把"这一轮真实送进去的文本"和"磁盘上的完整记录"对比一次，差异往往一目了然。

##### 4. 工具结果回灌

第四类是回灌：工具执行完之后，它的结果要以什么形式、扮演什么角色、出现在消息序列的哪个位置，重新进入下一轮。

这件事看起来只是"把返回值拼回去"，实际上有几个容易踩的坑。第一是**格式**：工具返回的是一个结构化对象（一个 JSON、一个错误码、一段堆栈），框架需要决定把它渲染成什么样的一段文本给模型看——是原样贴 JSON，还是提炼成人话，还是截断。第二是**角色**：这段结果在消息序列里以什么身份出现？通常有专门的"工具结果"角色，但不同框架的处理不同，而角色会影响模型如何解读它。第三是**位置**：它紧跟在那次工具调用之后，还是被塞到别处？顺序本身携带信息，同样一段文本换个位置，模型的理解可能不同。第四是**长度**：工具可能返回几百 KB 的日志，直接回灌会瞬间吃光窗口预算，通常需要截断或摘要——而这个截断本身又是一次有损操作，截掉的那一段，模型永远看不到。

回灌出来的形状，很大程度上取决于工具接口那一头把返回结构声明成了什么样——接口声明写得含糊，这里就会渲染成模型不认识的形状。这条线索后面还会用到。

回灌的源头在输出侧（见下一节"工具执行"），但它的效果体现在输入侧。这两个动作在这一点上是闭环的：**动作二执行出的结果，正是动作一下一轮的原料。** 读到这里可能会觉得回灌放在输入侧讲得早了一点——没关系，记住它是一个前向指针：等看完输出侧，再回来看这一条，闭环就合上了。

> **如果你遇到这个现象：** 工具明明成功了，agent 却像没拿到结果一样反复重试，或者拿到了结果却把它读反了、据一个理解错的值继续往下做——去看回灌那一环。可能是结果没被拼进去、被拼成了模型不认识的格式、或者被截断截掉了关键部分。

##### 5. 动态能力发现

第五类严格来说不是一种"注入操作"，而是给输入侧增加了一个变量：**这一轮到底有哪些工具可用。**

在本地工具的形态下，这个问题很简单：工具在程序启动时就注册好了，工具列表（每个工具的名字、描述、参数结构）在构建阶段就固定下来，每轮拼进去的都是同一份。

而在远端工具协议的形态下（生态里常见的做法是让 agent 连接到一个独立的服务端点，由那个端点声明自己提供哪些能力），情况变了：**工具集是在连接时动态发现的，而且可能中途变化。** 服务端可能增加或减少工具，描述文本由远端提供。这给框架增加了一项本地工具不需要承担的职责——**工具集的同步**：在每一轮推理之前，要把当前实际可用的工具列表重新确认并拼进提示。

这项职责在简单场景下几乎无感，在复杂场景下会制造真实的排障难题。典型现象是：你明明注册了某个工具，模型却从来不调用它——它会用别的方式把手头的活办掉，比如自己拼一段近似的手工操作，于是事情仍然被做完了，只是没走你为它铺好的那条路。原因可能是连接断了、可能是工具列表没有刷新、也可能是有两个服务端提供了同名的工具，其中一个覆盖了另一个。

顺便说一句，这类远端协议经常被描述成"本地工具调用的传输层加发现层"。这个描述基本正确，但"发现"这个词背后的"动态"两个字才是真正的差异所在——本地工具的注册是静态的，远端工具的能力是运行时的。这个差异决定了框架在多一项同步职责的同时，也多一类失败模式。

**维护这两个输入项最常见的坑。** 分成两头说。

**工具接口这一头：** 模型对"世界上有哪些动作可用"的全部认知，只来自每轮拼进去的那份声明——名字、描述、参数结构。名字起得含糊、描述没写清"什么时候用它、什么时候别用它"、参数结构过于宽松（全是字符串、没有枚举、没有必填标记），结果就是两种：要么它根本不用这个工具，自己拼一套近似的做法把事办掉；要么它用了，但参数填得千奇百怪。注意这两种结果都发生在**工具实现完全正常**的前提下——坏的是那份声明，不是那段代码。

**远端接口这一头：** 描述由服务端提供，本地审不到；两个来源提供了同名工具时，其中一个会盖掉另一个；连接断了、或者清单没有刷新，表现成"工具还在，但用不上"。这三类故障有一个共同点：**故障点不在工具实现里，而在清单里。**

> **如果你遇到这个现象：** 模型该用某个工具却始终不用，或者用了但参数反复填错——先看这一轮拼进去的那份工具清单，它对这个工具的**名字、描述、参数结构**是怎么写的，别急着去看工具的实现。

> **如果你遇到这个现象：** 会话开头还能用的工具，中途开始就用不了了；或者你明明接了两个来源，它们各自提供了一个同名工具——去看这一轮的能力清单本身，以及连接和清单同步有没有正常。

##### 6. 归并：这些其实是一个家族

把上面五类放在同一张表里对照，区别和共性会同时变得清楚。问自己四个问题：这段文本谁产生、什么时候进入 prompt、以什么方式进入、什么输出触发什么后果。

| 形态 | 谁产生 | 进入时机 | 本质操作 |
|---|---|---|---|
| 系统提示 / 用户消息 | 人、框架 | 每轮无条件 | 加文本 |
| 技能（skill） | 框架预写好 | 条件命中时 | 加文本（选择权在框架） |
| 上下文压缩 | 模型自己生成 | 窗口告急时 | **换文本（有损、不可逆）** |
| 工具结果回灌 | 工具执行产出 | 执行之后 | 加文本（源头在输出侧） |
| 远端工具协议 | 远端端点声明 | 连接 / 同步时 | 加文本 + **动态能力发现** |

这张表有两个有用的推论。

**第一，技能是系统提示的一个特例。** 机制完全相同，差别只是"这段文本由谁决定要不要加"。记住这一点，你就不会再把它当成一个需要重新学习的新概念。

**第二，远端工具协议是本地工具调用的超集。** 它不是新机制，而是本地工具调用的传输方式扩展（执行载体从本地进程换成远端端点）加上一层运行时发现。它值得单列，但不需要新概念来承载。

归并完之后你会发现，"最简内核"的知识点少得惊人：**一个循环，两个动作，加上一组"往里放文本"和"把输出变成后果"的具体形态。** 这比记住五个各自独立的名词更有用——因为名词会随生态变化而改名，机制不会。

还有一个推论值得单独记一笔，因为它直接支撑本文对故障的判断：这一节列的五个形态，全都是"决定它拿着什么信息去做事"的形态。没有任何一个形态的作用是"让它别做事"。**输入侧的所有偏差，最终都会以"它做错了"的形式暴露出来**——拿着旧规矩去做、拿着被摘要过的残缺信息去做、拿着一个理解反了的工具结果去做。这也是为什么排障要从输入开始，却不能止于输入：输入侧的偏差，是在输出侧兑现成具体错误的。

到这里，这一节是按"怎么注入"切开的。下面换一个切法——按"你手上有几个文件要维护"再排一遍。同一批东西，两张表。

##### 7. 换一个切法：每一种输入项为什么长成这个样子

前面六个小节是按"文本怎么被送进去"分的。现在换一个切法：按**我们手上真正要维护的那几样东西**再排一遍。

先立一个前提：**模型每一轮看到的文本，全部是框架照着我们的配置拼出来的，它没有别的信息渠道。** 它不能自己去读文件，不能自己去连服务，也不会自己发现新能力。所以"我们能喂给它的东西"是**可枚举的**，一共就这么几类：配置文本（prompt，也就是那份规矩文件连同框架的默认设定）、技能文件（skill）、工具接口（tool）、远端接口（mcp），再加上循环自己累积出来的对话历史。

这几类东西加起来，就是它在决策时能接触到的全部世界。由此得出一个判断，本文第二次说这句话：**维护好每一个输入项，就是"科学地使用一个 agent"这件事的全部可操作部分。**

下面每一项都按同一个模板讲：**它长什么样（约定）→ 基于最简循环的机制解释 → 为什么容易出问题 → 为什么各家框架不约而同用这套约定 → 维护时该盯什么。**

| 输入项 | 长什么样 | 由谁、什么时候放进去 | 维护它最常见的坑 | 为什么框架都这么约定 |
|---|---|---|---|---|
| 配置文本（prompt） | 一段每轮都在的文本 | 会话开始时读一次，之后整场沿用 | 快照：改了不生效；两处副本说法不一致 | 前缀稳定才能被缓存（省 token、省延迟）；同一会话内规则中途变化会让前文的决策失去依据 |
| 技能文件（skill） | 名字 + 描述 + 正文 | 描述常驻，正文按需整段注入 | 描述与正文不符 → 选不中；正文格式破损 → 读错 | 选择必须有廉价依据；每轮把每份正文都读一遍才能判断，成本会爆掉 → "索引 + 内容"分离是必然折中 |
| 工具接口（tool） | 名字 + 描述 + 参数结构 | 每轮拼进"你现在能用哪些工具"的清单 | 描述没写清何时用、何时不用 → 不用或乱用；参数结构太宽松 → 参数乱填 | 能力也是"要按需选中的东西"，与技能同构：必须能以一段可比较的文本声明自己 |
| 远端接口（mcp） | 声明协议 + 传输 + 运行时发现 | 连接时，以及每轮之前的同步 | 描述由远端提供无法审；同名冲突；连接断了或清单没刷新 | 远端能力无法在构建期枚举，只能连上去问它有什么 → "发现"必然成为标准动作 |
| 对话历史 | 循环里的那个数组 | 每轮累积，窗口告急时被压缩替换 | 关键约束被压掉，且不可逆 | 窗口有成本 → 取舍不可避免 |

**1. 配置文本 / prompt —— 约定是"快照"。**

**机制。** 回看最简循环的第一行——"环境给初始状态"。初始状态一旦给出去，循环里就再也不会回头看源头：循环内部没有任何一个环节会回去把那个文件重新读一遍，它手上只有 `messages`，而 `messages` 的第一项在循环开始的那一刻就定下来了。所以这类文本天然是**会话开始时读一次、之后整场沿用**。这不是某家的实现选择，而是"先给初始状态，再进循环"这个结构的直接后果。

**为什么容易出问题。** 改的是源头，用的是快照。**改了配置没开新会话，新配置根本没生效，agent 还在按旧配置办。** 这是初学者最常撞的一堵墙：他以为自己在改 agent 的行为，实际上只改了一个**下一场才会生效**的文件。更麻烦的是它不报错——旧规则运行得好好的，你收不到任何信号提示"你这次的修改还没上线"。于是现象就成了那句最让人抓狂的抱怨：我明明写进去了，它怎么还这样。

**为什么各家都这么约定。** 因为快照不是偷懒，是收益。同一场会话内前缀保持不变，请求才可能命中缓存，直接省下 token 和延迟；反过来，如果规则可以在会话中途变化，模型前几轮基于旧规则做出的决策就全部失去依据——一个会话里并存两套规则，比一套旧规则更糟。用一个确定的旧版本，好过一个不确定的新版本。所以几乎所有框架都选择"开场读一次"，把"什么时候重新读"变成一个需要你主动触发的动作。

**维护时该盯什么。** 改完要确认生效：重载，或者开一个新会话。确认这一轮真实输入里的那段文本就是你手上这一版。如果你确实需要热更新，去框架里找那个决定"什么时候重新读配置"的入口，而不是改完文件就当它已经生效了。

**2. 技能文件 / skill —— 约定是"名字 + 描述 + 正文"三件套。**

**机制。** 正文平时不进 prompt，只有被选中时才整段拼进去。这带来一个硬约束：**选择必须有一个廉价的依据**。如果每一轮都要把每份正文读一遍才能判断要不要用，成本会直接爆掉——想象你有几十份技能文件，每份几千字，每轮全读一遍的开销比任务本身还大。所以"描述常驻、正文按需"是必然的折中，它等价于一本书的**目录加正文**：目录要短、要准，正文可以长、可以细。

**为什么容易出问题。** 正因为选择只看名字和描述，**name 和 description 与实际指引内容不匹配，就会直接导致命中率低**——正文写得再好，选不中就不参与决策，你只会看到"它该用的时候从来不用"。第二个坑在正文本身：**格式不对**（加粗的星号没闭合、列表层级断裂、代码块没关）不会让它被忽略，而是让它被读成另一个结构；内容一个字没少，理解却变了。

**为什么各家都这么约定。** 因为这是"要在有限预算下选一段文本"这个需求的最省实现。选择这一步必须在很小的开销内完成，那就只能拿一段摘要式的文本去比；命中之后，再把完整内容加载进来。各家框架在这件事上撞出同一个形状，不是互相抄，是被同一个约束逼出来的——先廉价地判断"要不要"，再昂贵地获取"是什么"。

**维护要点。** 名字要好认；描述要准确回答"什么时候该用我"，而不是复述一遍正文标题；正文格式完整、条目之间不互相矛盾。

**3. 工具接口 / tool —— 约定是"名字 + 描述 + 参数结构"。**

**机制。** 模型不知道世界长什么样，它只知道每轮拼进去的那份能力清单。清单里的每一行就是它对"能做什么"的全部认知——它没有别的办法知道有这么个工具存在。

**为什么容易出问题。** 描述是模型判断"什么时候用这个工具"的唯一依据；描述与实际行为不符，它会按描述去用，工具却做另一件事。参数结构是模型填参的唯一依据；结构太宽松，它只能猜——全是字符串、没有枚举、没有必填标记，等于把"该填什么"交给运气。而参数一旦错了，事情就落回动作二：框架拿到一个名义上合法、语义上不对的调用，照样会去执行，痕迹落在外部世界里。

**为什么各家都这么约定。** 与技能三件套**同构**——能力也是"要按需选中的东西"，所以也需要一份可被比较的文本声明；而参数结构普遍采用"名字 + 类型 + 必填"这种形状，是为了让"模型说的"和"框架要执行的"能对上：模型给出的是一段结构化数据，框架要把它变成一次真正的函数调用，中间必须有共同的形状约定，否则每一次调用都要靠猜。

**维护要点。** 描述里写清"什么时候该用、什么时候别用"；参数结构收紧到你能接受的粒度（枚举、必填、明确类型），把猜的空间压掉。

**4. 远端接口 / mcp —— 约定是"声明协议 + 传输 + 运行时发现"。**

**机制。** 远端能力无法在构建期枚举——本地工具能编译进程序，远端只能连上去问它有什么。一旦能力来自运行时，"每轮之前重新确认一遍清单"就成了必须的标准动作。这也是为什么远端协议的规范里，"列出我提供哪些能力"几乎总是第一个被定义的接口。

**为什么容易出问题。** 描述由远端提供，本地审不到；两个来源可能提供同名工具，一个盖掉另一个；连接断了、或者清单没刷新，表现成"工具还在，但用不上"——模型于是自己拼一套做法把活办掉。这三类故障有一个共同点：**故障点不在工具实现里，而在清单里。** 沿着"去看工具代码"的方向排查，从第一步就走错了。

**为什么各家都这么约定。** 这是"能力不在本地"这一个事实的直接后果。既然只能在运行时知道有什么，就必须有一个动态发现层；既然有动态发现，就必然有同步问题、命名冲突问题、连接失效问题。这些不是在给框架添乱，而是"能力来自外部"这件事本身的价格。

**维护要点。** 确认这一轮拿到的清单是最新的；给同名工具定好归属；远端描述不可审的时候，在本地留一份对照。

**5. 对话历史与压缩 —— 循环里唯一原生的状态。**

它不是我们主动写进去的文件，而是循环自己长出来的：每一轮的输出和工具结果被 append 进去，越滚越长。窗口有成本，所以必须取舍；取舍就是压缩或裁剪，而有损且不可逆。维护它不需要你手动改什么文件，只需要决定一件事：**哪些内容必须有一条"被压掉之后还能取回"的路径。**

把这几项放回最简循环，它们的位置一目了然：配置文本对应"环境给初始状态"那一行；技能正文对应"按条件拼进 prompt"；工具清单对应"拼进 prompt 的能力声明"；远端能力对应"在连接时和每轮之前更新那份清单"；对话历史对应那个被反复 append 的数组本身。所以无论哪一项没维护好，最终都兑现成同一句话：**这一轮它读到的文本不对。** 这也是本文把排障落点放在"看这一轮真实输入"、而不是放在"猜模型"上的原因。

> **如果你遇到这个现象：** 同一个任务重复跑，每次错的地方不一样，而且每次错的都不像同一个原因——先按输入项一个个对一遍（配置文本、技能文件、工具声明、远端能力、对话历史），看哪一项最近被改过、改完有没有生效。一次只改一个输入项，一次只验证一个现象。

#### 三、输出侧：模型吐出来的东西去哪了

输入侧决定了模型看到什么，但一个 agent 能不能真的做事、做得对不对，取决于输出侧。这一侧在入门材料里经常被略过，因为它不像"提示词工程"那样有可操作性，而更像框架内部的脏活。但恰恰是这一侧，集中了使用者最常遇到的一类故障：**agent 确实做了，只是做错了。**

要把话说得更精确一点：输出侧决定的是**这段输出会被变成什么后果**。同一段模型输出，被解析成不同的后果，外部世界呈现的结果会完全不同。典型的错法有这么几种：

- 把一段本该只是"说明"的内容当成了要执行的指令，于是**不该执行的被执行了**；
- 把 A 理解成 B，于是**执行了一件正确的动作的错误版本**；
- 对象、路径、参数取错了，于是**动作本身没错，却作用在了错的靶子上**；
- 同一件事在同一次输出里被要求了两遍，或者下一轮又说了一遍，于是**同一件事被重复执行**；
- 本该走某个现成的正规能力，却由模型自己现拼了一个近似做法——一段临时手写的替代流程、一条绕开工具的捷径——于是**该走的通道没走，走了一条自己造的路**。

最后这条错法有一半的责任在输入侧：那份能力如果在清单里没写清楚，等于没提供——模型不是不肯用，是它压根不知道有这么个东西可用。这条线索在前面讲工具声明的地方已经埋下，后面还会用到。

这五种形态的共同点是：都动了手，而且做错了。这也让输出侧的排障有时反而更省事：外部世界一定留下了痕迹——被改动的文件、被触发的接口、被写脏的数据——你只要顺着痕迹往回推，就能定位到是哪一环把输出解读歪了。

输出侧可以拆成三个连续的环节：解析、路由、执行。

##### 1. 输出解析与容错

模型吐出来的东西，框架第一步要把它读懂：这是一段普通回复，还是一个工具调用请求？前面提过，现代接口通常用结构化字段来承载工具调用，看似省事，但真实世界里模型产出的东西经常不够干净：

- 该调用工具的时候，只输出了一段描述自己要做什么的普通文本，没有任何结构化标记；
- 结构化片段外面被裹了一层散文或代码块标记，或者参数 JSON 用了单引号、带了尾随逗号、少了一个括号；
- 一次输出里同时给出了多个工具调用；
- 参数里出现了不存在的字段名，或者字段类型不对。

框架对这些问题通常有三档处理姿态，从松到紧：

- **严格**：格式不完全合规就判为无效，把错误信息回灌给模型让它重来。好处是干净，坏处是浪费一轮，且在模型反复不合规时会陷入死循环。
- **修复**：尝试把不合规的输出"救"回来——剥掉多余的包裹、补齐括号、丢弃无法识别的字段。好处是省轮次，坏处是修复逻辑本身可能猜错，把一次本该失败的调用悄悄改成了另一次语义不同的调用。这种错误尤其难查，因为日志看起来"成功"了：调用确实发出去了，也确实返回了，只是做的事情和模型本来想做的不是同一件。
- **降级**：把无法解析的输出当作普通回复处理，直接结束或继续。这一档的危险在于它的后果不容易被看见：**框架会带着一个错误的假定继续往前**——被静默丢掉的那次调用意图，会在下一轮里被当成"那件事已经办过了"的既成事实，然后基于这个前提去做下一件事。一步的偏差，被它自己当成了后续所有推理的地基。这是"做错了"最隐蔽的一种来源——错误不在任何一次具体动作里，而在动作与动作之间的那个假定里。

理解这三档的意义，在于你知道该去检查框架的哪一项配置、以及当现象对不上时该怀疑哪一档。三档还有一个共同点值得记一句：**它们改变的是"这段输出变成什么"，而不是"要不要继续"。** 输出总会被变成某个后果，区别只在于变成的是不是你想要的那个。

> **如果你遇到这个现象：** agent 后续的每一步都建立在"那件事已经办妥"的前提上，而它实际做出来的动作是另一个样子、外部状态也对不上——去看那一轮的**原始输出**（未经框架加工的原文），确认工具意图到底是以什么形式出现的、框架把它归到了哪一档姿态。问题不在模型能力，而在它做的事从第一步起就长在一个错的前提上。

##### 2. 输出路由与终止

解析之后是路由：判定这段输出属于哪一类，并决定接下来怎么走。类别本质上只有三种——**最终回答**（结束并交付）、**中间产物**（继续循环）、**需要执行外部动作**（去执行）。

判断依据通常有两类信号。一类是模型侧的信号：有没有发出工具调用标记、结束原因是什么（正常结束、还是因为长度被截断、还是"我要调用工具"）。另一类是框架侧的规则：轮次上限、特殊终止标记、内容安全检查。两类信号结合起来，框架才知道这一轮是收尾还是续跑。

这个环节直接决定了 agent 的两个经典症状：**要么停不下来，要么停得太早。**

- 停不下来：模型每轮都输出一段新的分析而不给出工具调用，也不宣布结束，循环一直转到兜底条件触发。使用者看到的是 agent 在原地打转、越说越长、越说越偏。还有一种更隐蔽的变体：它每一轮都在重新做同一件事——因为它始终没把"这件事已经做完"当成一个可确认的事实。
- 停得太早：某一轮的输出被判定为"最终回答"而实际上只是中间产物，循环提前结束。使用者看到的是任务只做了一半，就被当成完整的交付交了出去。

注意这两个症状是"做错了"的两个极端：一端是做得太多、停不下来，另一端是收得太早、把没做完的当成做完了。它们的共同之处在于，使用者的直接感受都是"结果不对"。

任何生产可用的 runtime 都必须有兜底，因为"模型自己宣布完成"这件事不可靠。兜底条件通常有三类：**最大轮次**（防止无限循环）、**超时**（防止单轮或整体卡死）、**异常**（工具连续失败、解析连续失败等）。这三类兜底不是可选项，它们决定了 agent 在最坏情况下是"可控地失败"还是"失控地烧钱"。一个没有兜底的 agent 不是更聪明，只是还没有被打过。

> **如果你遇到这个现象：** agent 在同一件事上反复执行、越走越偏，或者把半成品当成成品交出来——去看兜底条件是否生效、以及路由为什么把它判成了结束或继续。这里出错的代价通常是"干了多余的活"，或者"把没干完的当干完了"。

##### 3. 工具执行

路由判定"需要执行外部动作"之后，就进入执行环节。这里有几个必须理清的维度。

**本地还是远端。** 有的工具就是本机上一个函数或一条命令；有的工具是远端服务的一个端点。两者在框架眼里区别不大，但对失败模式和权限的考虑差别很大：远端调用多一层网络不确定性，本地调用多一层环境影响（路径、依赖、权限）。

**串行还是并发。** 一次输出里给了多个工具调用时，能不能并发执行？判断标准是它们之间有没有依赖：彼此独立的查询可以并发；有先后依赖的（后者要用前者的结果）必须串行。并发能显著降低总延迟，但也带来两个新问题——消息顺序被打乱，以及部分成功部分失败的中间态需要处理。很多框架默认串行，正是为了回避这两个问题。

**失败怎么处理。** 工具会失败，这是常态而不是异常。可选的处理方式有三档：重试（适合瞬时故障）、把错误信息回灌给模型让它自己调整（适合参数错误、路径不存在这类有信息量的失败）、终止（适合不可恢复或高风险的情形）。把错误回灌给模型是一个非常有效的机制，因为模型往往能从错误信息里读出正确的下一步——但它有前提：错误信息本身要可读、要包含足够的信息。如果回灌的只是一句"操作失败"，模型接下来的选择大概率是换一个同样错的参数再试一次。

**副作用不可逆。** 这是执行环节与前面所有环节的根本区别：文本操作可以重来，已经执行的外部动作不能。一封发出去的邮件不会被"撤销"，一个已写入的文件不会自动回到旧版本，一次对外请求可能已经产生了业务后果。所以执行环节后面必须跟着**幂等设计**（同一个操作重复执行不会造成二次后果）和**权限约束**（什么操作需要先确认）。这两样东西无法用"更精心地操作文本"来替代——它们是对外部世界负责，不是对模型负责。

> **如果你遇到这个现象：** 某个操作被重复执行了两次（比如两条一模一样的邮件）——先看并发和重试逻辑：是一次输出里的多个调用被重复处理，还是失败重试没有做幂等保护。副作用不可逆，所以这类问题的代价往往在发现时已经产生。反过来说，这类痕迹也最好查——外部世界里多出来的那份重复，就是最直接的证据。

##### 4. 归并：为什么输出侧的错总被算到模型头上

三个环节讲完，可以回答一个很自然的问题：输出侧出的错，为什么使用者第一反应总是"模型变笨了"？

原因在于，模型那段输出是整个链条上唯一"看得见的话"。解析是框架的代码，路由是框架的规则，执行是工具的实现——它们都不出声。而 agent 每一轮都会用一段自洽的话告诉你它在做什么，这段话逻辑通顺、语气笃定，读起来完全像是一个想清楚了才动手的人在汇报。于是所有后果都被追溯到那段话上，而真正的岔口藏在它和后果之间那三段框架代码里。

把这个环节看成一个"转译链"会更好用：模型输出是一份**意图**，解析把它变成**结构化请求**，路由把它变成**决策**，执行把它变成**外部事实**。四者一致时你什么都察觉不到；四者不一致时，你能观察到的只有最后那个外部事实，以及第一份意图的自述——中间两步是不可见的。排障要做的，恰恰是把这两个不可见的步骤显式调出来看：原始输出是什么、它被归一成了什么、又被判成了哪一类。

这也解释了为什么本文反复强调"看真实输入、看原始输出"。它们不是两种排查技巧，而是把这条转译链的两端同时打开——一端是模型看到的，一端是模型说的。剩下的中间两环，靠框架的日志和配置去补。两端都打开之后，"它做错了"这件事几乎总能被拆成一个具体的、可复现的偏差。

> **如果你遇到这个现象：** 你反复读 agent 的解释，觉得它讲得头头是道、完全想不通哪里错了——别再读它的解释了，那是链条最上游的自述。去看原始输出和真实的外部痕迹，让两端对上。解释自洽而结果不对，恰恰说明岔口在中间那两步。

#### 四、系统层：不能只靠操作文本完成的事

以上两节讲的，是每一轮都会走一遍的两个动作。只要把这两个动作做好，你就能解释绝大多数日常现象。但有些职责不是每轮发生的，也不是靠操作文本能完成的——它们是框架在循环之外、之间、之上做的事。到这里会自然产生一种"离题"感，因为下面这些内容和"给模型看什么文本"不像同一件事。确实不是同一件事，但它们都是从这个循环里长出来的需求：正是循环本身产生了跨进程的状态、产生了并发、产生了真实世界的副作用，才逼出了下面这几项职责。

- **持久化。** "任务做到哪了"如果只活在 `messages` 数组里，那么进程一重启、或者窗口被压缩一次，任务进度就跟着回退。最简实现把状态寄存在一次性的上下文里——这既是它的优雅，也是它最脆的地方。持久化就是把这份状态挪到循环之外的可靠落点：落盘、写入外部存储、支持跨会话恢复。
- **调度。** 多个任务、多个会话、多个并发请求同时存在时，谁先跑、谁能让路、资源怎么分配。这一层处理的是"同时发生的事"。
- **权限与沙箱。** 文本可以描述"你不许删除文件"，但描述本身不是约束——模型可以被绕开、被诱导、被忽略。真正的权限边界必须在执行层强制：哪些路径可写、哪些端点可访问、哪些操作需要人工确认。这是唯一必须跳出文本层的安全边界。
- **可观测。** 一旦 agent 自动跑起来，你需要的不是"它大概在做什么"，而是完整的过程记录：每一轮送进去了什么、模型回了什么、调用了哪些工具、花了多少 token、延迟多少。没有这层，前面所有的排障方法都无从落地——因为你根本没有数据可看。
- **幂等与回滚。** 外部动作不可逆，所以需要在执行层提供"重复执行不出事"的保护，以及在可能的时候提供回退路径。

**为什么这些不可归约到文本层？** 因为它们处理的是外部世界的三项硬性质：状态会丢、世界是并发的、副作用不可逆。这三项与模型有多强无关。模型再强，也不能让一封已经发出的邮件回来；也不能凭自身保证两个并发请求不会互相踩踏；也不能阻止自己学会去读一个它本来就不该读的文件。这些约束是运行环境的物理性质，不是智能水平的问题。这也解释了后面那个判断：会随模型变强而消失的设计，多半在"约定"这一层；不会消失的，多半在"系统"这一层。

顺带说一句，系统层的故障同样是"做错了"的形态：状态丢了，agent 会拿着一份残缺的进度接着往下办；权限没拦住，它会照样把那件事做掉。系统层缺位造成的后果，最终都会以"它做了一件不该做、或做不到位的事"的形式出现在你面前。

> **如果你遇到这个现象：** 长会话跑到中途，它开始违反早先定下的约束，或者重启之后按一份已经残缺的状态接着办——问题在持久化，不在提示词。agent 把不该碰的东西碰了——问题在权限与沙箱，不在提示词。前两个环节再怎么优化文本，也堵不上这一类洞。

### 实现方案

前面讲原理，这一节讲怎么用。如果你只打算实践一部分，就从这一节开始。

#### 五、喂工作资料的方法论

先说度量衡，因为后面所有关于成本的说法都建立在它上面。

**框架操作的基本单位不是字符，是 token。** 模型看到的不是"字"，而是一串被切分出来的 token。这对中文使用者尤其重要：一个中文字符可能占不止一个 token，而英文单词的切分方式又和中文完全不同。这意味着"我写了五百字"和"我占了五百个 token"是两件事，而且差异可能相当大。除了正文，格式标记本身也吃 token——一层层嵌套的括号、井号标记、分隔线，都要计费。

你不需要知道分词器内部是怎么切分的。打个比方：你不需要知道发动机是怎么铸造的，但你必须知道油表读数的含义。后面提到"成本""预算""窗口占用"的时候，心里换算的单位应该是 token，而不是字数。这一条如果搞错，所有关于"够不够装"的直觉都会偏。

**位置决定成本。** 同样一段资料，放在哪里，成本完全不同。有两种极端形态：

- **恒常投喂**：每一轮都拼进去（比如系统提示这类固定内容）。它的成本是"每轮都付一次"。
- **按需检索投喂**：平时不占位置，需要的时候被检索出来拼进当轮。它的成本是"命中时才付一次"。

所以选资料时的关键判断，不是"这条资料重不重要"（重要当然重要），而是"**它要不要每一轮都在**"。一条非常重要的资料，如果只在少数场景才用得上，把它恒常塞进系统提示就是持续浪费；一条看起来不重要的资料，如果几乎每轮都要参考，按需检索反而会带来额外的检索开销和漏检风险。这个判断比"重要性排序"实用得多。

**能被检索到，比写得好更重要。** 既然按需投喂靠检索，那么资料能不能被选中，直接决定了它会不会参与决策。检索的常见实现形态是关键词匹配或语义相似度，这两种机制都对资料的**可检索性**高度敏感：清晰的标题、合理的分段、一致的术语用法，都会显著提高命中率。反过来，一段深刻但结构混乱、标题含糊、术语前后不一致的内容，很可能从来没被检索到过——而它的后果是 agent 拿别的东西凑合着把事办了。写得好是内容质量的维度，能被检索到是存在性的维度。后者优先。

**压缩有损且不可逆。** 前面已经说过，这里只强调它对"喂资料"的实操含义：任何被压缩掉的内容，在之后所有轮次里对模型都不存在。所以关键信息——那些一旦丢失就会导致任务跑偏的约束、数值、路径、结论——必须有一条"被压缩掉之后还能重新取回"的通道。实践上就是两件事：把它落到外部存储，并保证它可检索。只做前者，模型不知道去哪找；只做后者，源头没有落点。两件事都要。

**排障先看真实输入。** 出问题时，第一反应应该是打印那一轮真正送进模型的输入，而不是先怀疑模型、也不是先翻框架文档。你看到的原始文本会告诉你：该投的资料投进去了没有、不该投的有没有挤掉别的、压缩有没有吃掉关键信息、工具结果被渲染成了什么样子。这一个动作能解掉的困惑，比读一整天文档更多。

**按输入项维护，一次只动一个。** 前面把能喂进去的东西排成了五项，维护它们的动作也可以排成一份很短的清单。除了对话历史不需要你手改，其余四项各有各的检查动作：

1. **配置文本：** 改完确认生效——重载，或者开一个新会话；顺手确认它是不是"每轮都在付成本"的那一类。
2. **技能文件：** 做三件套自查——名字好不好认；描述有没有准确回答"什么时候该用我"；正文格式完不完整（标记闭合、层级不断、代码块关掉）。
3. **工具接口：** 描述里写清"什么时候该用、什么时候别用"；参数结构收紧到你能接受的粒度。
4. **远端接口：** 确认这一次拿到的是当前的能力清单，以及连接是活的。

加一句总纲：**同一条规矩只写一处。** 同一份内容有两个副本的时候，你迟早会看到它照着另一个副本来办。

> **如果你遇到这个现象：** 资料明明准备好了，agent 办出来的东西却和那份资料对不上——它按自己的理解另走了一套做法。先看这一轮它有没有被投进去（检索有没有命中），再看有没有被压缩掉，最后才看内容质量。顺序反了，你会花大量时间在重写一段本就没被读到的文本。如果对不上的是"它压根没用上那份技能"，先回输入侧按输入项对一遍。

#### 六、排障四问与现象对照清单

把上面所有内容收成一套可以按顺序走下来的流程。任何一次"agent 行为不对"，都按这四问问下去：

**第一问：这一轮实际送进去的文本是什么？** 不是你以为的，不是框架文档描述的，而是真正拼出来的那串。大多数黑箱感来自跳过这一问——先去怀疑模型、凭感觉把提示词改得更重、翻框架文档搜社区帖、或者干脆把锅算到框架头上，而不是先看这一轮真实的输入。

**第二问：是谁决定送这些的？** 固定打包？条件触发？检索命中？还是上一轮工具的返回值？分清"谁点的火"，才知道该去改哪一处配置或资料。再往下追一层：**这一份是从哪读来的、什么时候读的？** 如果它属于"会话开始时读一次、之后沿用"的那一类，你改了源头也不会改变这一轮的结果。

**第三问：模型的输出被解析成了什么后果？** 是被当成普通回复就此收尾，还是被当成一次工具调用真的执行了？这里出错的形态几乎全部是"动错了手"：把 A 执行成了 B、参数取错、本该走的能力被换成了一次临时拼凑的近似做法。

**第四问：结果是怎么回灌的？** 回灌成了什么角色、放在什么位置、有没有被截断？回灌出了问题，表现就是它在错的前提上继续往下做，或者把同一件事反复重做几遍。

四问走完，绝大多数看起来像玄学的问题都会落进某个具体环节：要么该投的没投进去，要么不该投的挤掉了别的，要么输出被解析错了，要么回灌丢了。注意这四问的共同指向：它们最后都会汇成同一个可观察的结果——**agent 做了一件不对的事**。四问的作用，是把这个"不对"精确地归到某一层，而不是泛泛地归给"模型不行"。

下面是一张现象到定位的对照清单。用法是：先在左列找到你观察到的现象，右列直接给出应该先查的环节和该看的东西。清单按两种排法给：除了按"注入方式"排，还能对上"你手上要维护的那个文件"。同一现象可能对应两三个环节，从列在最前的那个查起，一次只改一个变量。

| 你观察到的现象 | 大概率在哪个环节 | 该看什么 |
|---|---|---|
| 你改了那份写规矩的文件，agent 还是照旧做法办；把改好的内容贴给它，它下一轮又忘了 | 无条件注入（加载时机 / 快照） | 这一轮真实输入里的那段文本是不是你手上这一版，以及它是什么时候被读进去的；改完有没有重载或开新会话 |
| 它把前几天刚被纠正过的约束又违反了一次 | 有损替换 | 那条纠正还在不在这一轮的真实输入里（有没有被压缩掉） |
| 它绕开你写好的那份指导，自己临时拼了个做法 | 条件注入 | 这一轮它到底有没有被注入（检索是否命中），而不是文件内容写得好不好 |
| 动作本身没问题，但作用在了错的对象 / 错的路径 / 错的参数上 | 输出解析 | 那一轮的**原始输出**，以及参数是怎么被读出来、补全的 |
| 本该调用某个现成能力，它却手写了一段替代流程绕过去 | 输出解析 / 动态能力发现 | 这一轮拼进去的工具列表，以及工具意图有没有以可解析的形式出现 |
| 同一件事被重复执行了两遍（两条一样的通知、两次一样的写入） | 工具执行 | 并发逻辑与重试路径，检查幂等保护 |
| 它基于上一轮的工具结果继续做，但那个结果被它理解反了 | 工具结果回灌 | 结果有没有拼进去、格式对不对、有没有被截断 |
| 会话中途它开始引用过时的数值、把早先定下的约束丢掉 | 有损替换 | 把"真实输入"和"完整记录"对比，看哪些被摘要掉了 |
| 它无端拒绝一个完全合理的请求，或对普通话题异常谨慎 | 无条件注入 | 当前生效的系统提示全文，尤其你自己没写过的部分 |
| 任务只做了一半，它却当成完整的交付交了出来 | 输出路由与终止 | 中间产物是不是被误判成了最终回答 |
| 它在同一件事上原地打转，越说越长、越改越偏 | 输出路由与终止兜底 | 最大轮次、超时、异常兜底是否生效 |
| 长会话重启后，它按一份残缺的状态接着办 | 系统层持久化 | 状态有没有落在循环之外 |
| 它做了一件本不该被允许做的事 | 系统层权限 | 执行层的权限与沙箱，而不是提示词措辞 |
| 技能就在那里、任务也对口，但几乎每轮都没被选中；你手动点名它才用 | 条件注入（选择） | 技能的 name 和 description——选择这一步只看这两样，不看正文 |
| 技能被选中了，但它办出来的事跟技能里写的对不上，或者明显漏掉了几条 | 条件注入（内容） | 技能正文的格式是否完整（加粗标记、列表层级、代码块是否闭合），以及条目之间是否互相矛盾 |
| 该用某个工具却始终不用，或者用了但参数反复填错 | 工具接口 / 动态能力发现 | 这一轮拼进去的工具名、描述、参数结构，而不是工具的实现代码 |
| 会话中途工具的可用性变了：开头能用后来失效；或者两个来源提供了同名工具 | 动态能力发现 | 这一轮拼进去的能力清单本身，以及连接与清单同步是否正常 |
| 同一条规矩你写在了两个地方，两处说法不一致，它挑了一条办 | 输入项维护（唯一权威源） | 这条规矩有几份副本，哪一份是被真正读进去的那一份 |

这张表比任何原理陈述都更可能被用到第二次。原理帮你理解"为什么"，这张表帮你"现在就动手"。两个用法上的提醒：第一，左列全部是可观察的外部现象，如果你观察到的现象不在表里，先问自己"外部世界到底发生了什么变化"，把它描述成一个具体的事实再回来对照；第二，同一现象可能对应两三个环节，从表里列在最前的那个查起，一次只改一个变量。

### 总结

#### 七、这套心智模型什么时候会过期

回到一开始那个担心：agent 领域变化很快，今天总结的模型，一年后会不会变成仅供参考的历史弯路？

有一个比笼统感叹"日新月异"更有用的判据。这套模型只依赖两条事实：**模型只吃文本、只吐文本；文本窗口有上限且有成本。** 只要这两条不破，"筛选 + 投喂"就不会过时，变的只是筛选规则（从关键词到语义到更强的机制）和投喂的载体。

而且要注意，第二条事实的重心应该放在"有成本"，而不是"有上限"。窗口上限确实在快速扩大，这一条约束力在变弱；但"装进去就要花钱、就要等"这一条不会因为窗口变大而消失——即使窗口足够大，投喂量仍然直接对应钱和延迟。把锚点从"有限"移到"有成本"，这套模型就更能扛住反驳。

真正让它退化成历史弯路，需要接口层面的变化：模型能直接读写外部状态，不再需要框架把状态序列化成文本喂给它；或者窗口大到免费，投喂量不再有代价，取舍这件事自然消失。到那时，"喂什么"才会真正不再是一个问题。

**比"会不会过期"更实用的，是分清哪些部分一定过期、哪些部分不会。** 这里有一个很有解释力的分法。对每一层设计问一句：**它是在补偿模型当前的能力不足，还是在处理任务本身的结构复杂度？**

- **补偿型**：为了弥补模型当下的短板而存在。它们会随模型变强而被吸收进模型内部，是真正容易过期的一类。
- **结构型**：处理的是执行环境的物理性质——窗口有成本、进程会死、外部世界会失败、副作用不可逆。这些不会因为模型变强而消失，模型再强也跨不过去。

举几个反直觉的例子，因为它们最能说明这个分法的锐度。

第一个例子是关于"必须遵守以下规则"这类自然语言权威声明。直觉上，规则当然要长期存在，怎么会过期？但仔细看，规则分两种。规则的内容（谁被允许做什么、这个会话里参与者是谁）是结构型的，会长期存在；而"用一句自然语言声明来保证后文不覆盖前文"这个**技术手段**，是补偿型的——它在补偿模型对指令跟随的不稳定性。等模型天然具备"后文不能覆盖前文硬性设定"的能力时，这层包装就会退化为噪音。**同一个东西里，约束本身会留下，而承载约束的措辞会换代。** 这是最容易搞混的一处。

第二个例子是关于工具调用的机制。直觉上，工具调用是 agent 的标志性能力，怎么看都是结构型的。但"模型输出特定格式的片段、框架解析它去执行"这个**协议形态**，是补偿型的——它在补偿"模型还不能直接操作外部系统"。将来如果模型能通过结构化接口直接读写外部状态，今天这套"把调用写进文本、再由框架解析"的协议就会被替换。留下的是"agent 要能改变外部世界"这个需求，它会以另一种形态继续存在。

第三个例子，正好回收前面第三节讲的那套输入项约定。技能为什么普遍长成"名字 + 描述 + 正文"三件套，工具为什么普遍要求声明名字、描述、参数结构，远端能力为什么普遍需要一套动态发现——这些**形状**看起来像 agent 工程的常识，其实都是补偿型的：它们在补偿"选择必须廉价"这一当下的工程约束。将来如果模型能一次性、低成本地感知自己有哪些能力和哪些技能，这层常驻的声明文本就可能被结构化接口取代。但反过来，"必须有取舍，或者必须有索引"这个需求是结构型的——它的根据是"装进去就要花钱、就要等"，这一条不会因为模型变强而消失。所以判断这个新领域里的设计会不会过期，还是同一个问法：**它是在为模型的能力兜底，还是为世界的性质兜底。**

反过来，回看前面几节，凡是"系统层"的东西——持久化、调度、权限、可观测、幂等——几乎都属于结构型，因为它们在处理外部世界的不可靠，而不是在处理模型的不足。这个对应关系本身就是一条经验：**当你想判断一层设计会不会过期时，先看它在为谁兜底——是为模型的能力兜底，还是为世界的性质兜底。**

还有一个值得一提的推论：这套心智模型同时解释了为什么"agent 做错了"会是长期存在的故障形态。因为它的行动力来自模型，而它的行动依据来自框架拼装出来的文本——两边只要有一处对不上，结果就是"动作正确、依据错误"。模型变强会让它更少地犯"能力不够"的错，但不会让它不再犯"依据不对"的错；只要文本仍然是它唯一的输入，依据就仍然可能不对，偏差就仍然会以"做错了"的形式出现在外部世界里。

**三条今天就能做的事。** 读完这篇文章，不需要等框架升级、不需要写代码，你可以立刻做三件事：

1. **找到并打开"上一轮实际送进去的完整文本"。** 你用的框架一定有办法暴露它——调试命令、详细日志、管理后台、会话记录文件。找到它，读一遍。这是你第一次真正看见输入侧那些注入叠加在一起长什么样。大多数困惑在这一步就消了一半。
2. **读一遍当前生效的系统提示、所有会被注入的技能文件原文，以及每一个工具的声明。** 你的 agent 每次醒来都在遵守一些你没亲手写过的规则，也在照着一些你没细看过的说明来选能力。把这些文本逐行读一遍，问自己"这条是从哪来的、为什么在这"。你大概会发现至少一条你不知道其存在的行为约束——而它已经在悄悄影响 agent 做出来的结果。
3. **制造一次工具失败，观察 agent 的反应。** 断网、给一个错误路径、让工具超时——然后看它下一轮说了什么、又做了什么。这一次实验能直接验证输出侧的三个环节：解析有没有报错、路由把它归成了什么、回灌给模型的信息是否足以让它自救。五分钟能做完，但它会让你对输出侧的处理链建立起真实直觉。

**收束。** 如果这篇文章只留一句话给你，希望是这一句：

> **Agent runtime 不是黑箱，它每轮只做两件事：决定给模型看什么文本，决定把模型的输出变成什么后果。**

接受它，你排障的第一动作就会从"猜框架"变成"看文本"；接受它，你喂资料时关心的就会从"哪个功能更强"变成"这一轮真正进到模型眼里的是什么"；接受它，你面对新出现的框架术语时也会先问一句——它属于两个动作里的哪一个，或者它其实是那两个动作之外的系统层职责。而当你发现它的行为不对时，你会直接去看：它这一轮拿到的是什么、它做出来的又是什么。

## 知识缺口

本文未覆盖以下内容，仅做方向性标注，供后续扩展：

1. **分词器的内部实现与跨语言差异的量化。** 本文只把 token 当作成本计量单位来说，没有展开不同分词算法（BPE、SentencePiece 等）对中英文混合文本、代码、结构化标记的具体切分差异。要精确估算成本，需要针对具体模型做实测。

2. **输出解析的工程实现细节。** 本文描述了严格、修复、降级三档姿态，但没有讨论如何实现"修复"逻辑——如何在剥掉多余包裹的同时不改变语义、如何界定修复与猜测的边界。这是一个以失败案例积累为主的工程问题。

3. **"做错了"的完整分类学。** 本文按框架环节组织了故障的定位方式，但没有给出一套独立于框架的错误分类（例如按对象错、参数错、版本错、时机错、通道错来划分），也没有讨论不同类型错误在可观测性上的差异。这类分类如果做出来，可能对自动化检测更有用。

4. **多会话与并发场景下的状态一致性。** 本文在系统层提到持久化与调度，但没有深入讨论多个会话共享外部存储时的冲突处理、以及跨会话记忆的隔离与继承策略。

5. **权限与沙箱的具体机制。** 本文指出权限必须在执行层强制，但没有展开能力声明、最小权限、审计日志、人工审批等工作流的具体设计。

6. **成本模型的精确化。** 本文把成本归结为"输入 + 输出 + 循环次数"三个方向，但没有给出不同任务形态下的成本曲线、缓存机制对成本的削减幅度、以及延迟与成本的权衡策略。

7. **跨框架的现象共性验证。** 本文的框架无关立场基于结构推理，没有做跨框架的同任务对照实验。不同框架在这些环节上的默认行为差异，可能比本文描述的更大。

8. **输入项约定的跨框架差异。** 本文描述了配置文本的快照粒度、技能三件套、工具声明结构、远端能力发现这四类约定的共同形状，但没有做跨框架的横向对照——不同框架在"配置什么时候重新读取""技能选择用什么机制""工具声明的严格程度"上的默认行为可能差别很大。要做精确的迁移判断，需要逐框架核对。
