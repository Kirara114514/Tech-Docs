# 框架即智能：Agent 编排深度如何决定 LLM 的实际表现

## 摘要

大型语言模型（LLM）的能力边界，在 API 层面是固定的——相同的推理参数、相同的底层模型、相同的提示词，产出的"原始智商"不会因调用方的不同而变化。然而在工程实践中，同一模型在不同 Agent 框架中的实际交付效果天差地别。这引出一个被广泛忽视的问题：决定 LLM 应用最终表现的，往往不是模型本身，而是包裹在模型外面的那一层"框架"——它的消息处理管道、它的任务编排策略、它对 LLM 输出的事后校验和修正。本文从薄框架与厚框架两种架构范式出发，系统拆解编排引擎的核心机制——前置处理、中置处理、后置处理三层架构——并深入分析动态角色生成的设计原理、闭源 Agent 产品的壁垒本质，以及编排引擎在延迟、成本和过度工程方面的局限。核心结论是：Agent 框架不是在"调用 LLM"，而是在"管理 LLM 的认知状态"。框架的工程深度，在相当程度上就是 LLM 的实际表现。

## 正文

### 背景

2025 年到 2026 年之间，开发者社区逐渐意识到一个现象：同一时期的旗舰模型——不论是 GPT-4o、Claude Sonnet 还是 Gemini Pro——接入不同的 Agent 框架后，实际交付的工程能力差距显著。在 Claude Code 或 Codex 这类产品中，模型的表现稳定、细腻、一致性高——多文件重构时命名风格统一、复杂 bug 定位后修复精准、长流程任务中中间决策不丢失。而把同一个模型接入某些轻量级 Agent 框架时，交付质量明显下滑：代码能编译通过，但细节粗糙（边界条件覆盖不全、错误处理缺失）；多步骤任务能走完流程，但中间步骤的决策在下游使用时偶有偏差；整体体验不是"不行"，而是"不够好"——这种差异不是能力的鸿沟，而是工程交付的层次之别。

这不是模型在变，是框架在变。

这个现象指向一个工程领域的关键认知：模型能力不等于交付能力。一台发动机的峰值马力是固定的，但在 F1 赛车上和在拖拉机上，跑出来的圈速完全不同。LLM 就是那台发动机，Agent 框架就是整车。API 层面看到的"模型能力"——推理速度、上下文窗口大小、逻辑一致性——只是发动机的标称参数。当这些参数通过不同框架传递到用户面前时，它们经历了截然不同的"传动损耗"和"操控调校"。

把 Agent 框架理解为"让 LLM 干活的工具"，本身没有错。但这个描述过于扁平，掩盖了框架内部真正重要的事。Agent 框架从结构上看是一个消息处理管道——用户的输入进入这个管道，经过一系列变换，变成发送给 LLM 的上下文提示词；LLM 的输出再回流入管道，经过另一系列的筛选、校验、修正和拼接，最终呈现为看似"一气呵成"的回复。用户的表面感受是"我问了一句，LLM 答了一段"，但在框架内部，这一问一答之间可能已经发生了数十次 LLM 调用、数百次工具调用、多次输出的自动修正循环。

这些处理的质量，直接决定了 LLM 能"看到"什么、能"表达"什么。

这一认知的重要性在于它翻转了业界惯常的优化思路。当 Agent 应用的表现不如预期时，工程师的第一反应通常是"换个更强的模型"——从小杯换大杯，从上一代换最新一代。但正如换发动机不解决底盘松散的问题，在消息处理管道存在系统性缺陷时，换模型带来的收益是边际递减的。另一个更隐蔽的问题是产业竞争中的壁垒位置。由于模型本身越来越趋于同质化——多个厂商在相近的参数量级和训练数据量级上产出能力接近的模型——真正产生差异化竞争力的，是"如何用好模型"的系统工程能力。这正是 Agent 框架层的战场，也是闭源 Agent 产品真正投入大量工程资源的地方。

Agent 框架还有一个容易被忽略的双层属性。对外，它是"让 LLM 干活"的工具——这是用户和产品视角。对内，它是一个消息处理管道，在每一次 LLM 调用前后，框架都在做大量的预处理和后处理工作。这种内外视角的分离，造成了评估框架时的认知盲区：用户夸一个 Agent 好用，往往归功于"模型聪明"或"提示词写得好"，但真正串联起整个体验的，是框架在这条管道上每一步所做出的工程决策——给 LLM 看什么文件、不给它看什么文件、它的输出要不要重新审查、两个子任务的结果怎么合并在一起。

这种隐蔽性也解释了为什么市面上大量的"自建 Agent "项目——在 GitHub 上用几百行 Python 把 LLM API 包一层就是"Agent"——和闭源产品的体验差距如此悬殊。显性的东西——代码架构、工具列表、UI 样式——都是可以复制的。隐性的东西——消息管道的内部策略、验证回环的触发条件、上下文裁剪的优先级算法——不会在代码里以显式的算法逻辑出现，而是分散在数百个条件分支和边界处理中，经过数千小时的测试迭代才收敛到稳定状态。

本文试图回答三个递进的问题：框架层到底在做什么，使它能够对 LLM 的实际表现产生如此显著的影响？薄框架和厚框架（管道模型与编排引擎）之间的本质区别在哪里？这种差异在工程实践中的含义是什么——它影响了什么、局限了什么、值得投入什么？

### 核心内容

##### 2.1 可观察的现象：同一模型，不同表现

要理解框架层的价值，最直接的方法是观察同一模型在不同框架中的行为差异。以下场景基于社区公开讨论和工程观察中的典型模式，场景本身做了抽象化，但差异的性质是真实的。

**场景一：跨文件重构。** 假设一个代码库中有三个模块——数据层、业务逻辑层和接口层——需要对一个核心数据结构进行重构，涉及约八个文件的修改。在 Claude Code 这类深度编排框架中执行这个任务时，模型被引导先读取所有相关文件，分析依赖关系图中的变更影响范围，规划好修改顺序（通常是自底向上：先改数据层，再改逻辑层，最后改接口层），然后逐文件执行修改。修改完成后主动运行编译验证，发现遗漏就回环修补。

同样的模型接入一个薄框架时——比如一个简单的工具链包装层——执行质量就开始打折扣。模型读入文件、理解结构、完成任务都没有问题，代码也能编译通过。但细节上会暴露差距：某些边界条件被遗漏（因为一次性处理八个文件的认知负荷压低了模型对每个文件边界的注意力）；中间约定的命名规则在第四个文件之后开始出现不一致（并非完全忘记，而是"足够正确"但不是"完全正确"）；重构完成后没有自动验证，用户需要手动检查。核心差异不是"能不能做"，而是"做得多好"——而"多好"正是区分工程交付品位的标尺。

**场景二：Bug 定位与修复。** 用户报告了一个复杂的运行时异常，堆栈跟踪跨越五个调用层。在深度编排框架下，模型被引导沿着堆栈逐层追溯——先理解最内层异常的直接原因，再向外验证每一层的假设——这是一个结构化的诊断流程，每层验证的结果被记录并在下层推理中被显式引用。在薄框架下，模型同样能沿着堆栈追溯，也能命中正确的 bug 层——但诊断过程的严谨性参差不齐：有时中间层的验证被隐含在推理中而非显式，有时修复补丁只处理了直接原因而未覆盖被连带影响的关联代码。结果大致对，但质量方差更大。

**场景三：多步骤任务的信息保真度。** 考虑一个任务需要五个子步骤顺序产出中间结果，下游步骤依赖上游的决策。两种框架的核心差异不在"信息是否丢失"——现代长上下文模型和框架压缩策略已经让完全丢失信息的情况极为少见——而在于传递中的精度降级。在薄框架的管道模式下，上下文压缩模块会做关键信息保留，但压缩过程本身会引入取舍：模型需要判断"什么信息对下游最重要"，而这一判断的准确性在压缩比高时开始下降。编排引擎的处理方式不同：每个子步骤在独立上下文中执行，先产出完整的结构化结果，再由摘要层明确标注"以下信息对下游关键"，只在必要的时候回引完整原文。这不是"有没有信息"的差别，而是"精度衰减曲线"的陡峭程度差别。

这三个场景揭示的共同模式是：薄框架和厚框架在"能不能完成"层面的差异已经随模型能力提升而显著缩小——今天的旗舰模型即使裸 API 调用也能胜任大多数复杂任务。真正的分界线在"完成质量"的细腻度——一致性、覆盖度、可审计性、对边界条件的自觉。框架层不是让模型从"不行"变"行"，而是让模型从"还可以"变"稳定可靠"——从手写草稿到印刷品之间的那段工程差。

**差异矩阵：** 下表总结了薄框架和厚框架在五个关键维度上的表现差异。这里的"薄框架"和"厚框架"是两种理想类型，实际框架都落在两者之间的连续谱上。

| 维度 | 薄框架（管道模式） | 厚框架（编排引擎） |
|------|-------------------|-------------------|
| 任务拆解 | 无拆解，一次性处理 | 规划层自动拆解为子任务树 |
| 上下文管理 | 全量压缩或手动裁剪 | 按子任务精度注入上下文 |
| 错误恢复 | 依赖模型自我纠正 | 框架验证 + 回环修正 |
| 多文件一致性 | 随任务复杂度边际下降 | 结构化信息路由保持一致性 |
| 执行可审计性 | 只能看最终对话 | 每个子任务独立追踪状态 |

关键洞察是：差异的核心不在"能不能跑通"——薄框架下的输出在今天也能编译通过、逻辑自洽——而在于"工程交付的可靠性"。薄框架下的 LLM 随任务复杂度增长，更频繁地出现细节遗漏、命名漂移、边界条件覆盖不全。这些不是"模型失败了"，而是"模型在信息匮乏的环境中被要求做超出其瞬时能力的事"。框架需要解决的，正是"给模型创造最好的信息环境，让它不需要同时处理所有东西"这一工程问题。

##### 2.2 两种架构范式：管道模型与编排引擎

上一节的现象描述指向一个结构性问题：薄框架和厚框架在信息处理方式上存在根本性差异。这一节将差异抽象为两种架构范式。

**A. 管道模型（Thin Framework）**

管道模型的架构极其简洁：用户输入进入框架，框架附加必要的工具定义和系统提示词，转发给 LLM，LLM 直接产生响应，框架将响应转发给用户。这种架构中，框架的角色本质上是一个"带有工具权限的消息代理"。

管道模型的核心理念是"LLM 已经足够聪明"。工程上的精力主要花在工具定义的质量上——写清楚每个工具的参数、返回值、使用场景——然后信任 LLM 会自行决定何时调用哪个工具。这种理念在某些任务上确实有效：单次信息查询、简单的代码补全、格式转换等场景中，管道模型的高效性令人满意。

但管道模型有结构性的局限。第一个局限来自单次 LLM 调用的认知上限。任何 LLM 在单次推理中能有效处理的上下文深度和任务复杂度是有限的。当任务涉及多个文件、多个步骤、多层决策时，单次调用的方式让模型承受了过高的认知负荷——它既要理解任务全貌，又要记住中途的每一个决策，还要确保输出的一致性和正确性。第二个局限是工具调用错误的不可自愈。LLM 调用了一个工具，结果返回了错误——管道模型只能把这个错误信息塞回上下文，让 LLM 自己决定怎么处理。但 LLM 的"自我纠正"能力是概率性的：它可能正确地重试，也可能无视错误继续下一个步骤，或者做出错误的纠正方向。没有外部的验证和纠正机制，管道模型把正确性的责任完全交给了 LLM 的单次推理质量，而这个质量本身波动很大。

管道模型的工程假设可以总结为三句话：任务是一次性的，上下文是完整的，模型的单次输出大致是正确的。这三个假设对于足够简单的任务是成立的，但对于任何需要多步骤协调的任务，它们是脆弱的。

**B. 编排引擎（Thick Framework）**

编排引擎的架构与管道模型有本质不同。一个典型的编排引擎包含以下几个层次：

- **规划层：** 用户输入先进入规划层，由一个（或多个）规划 agent 解读意图、评估复杂度、决定是否拆解任务。如果需要拆解，规划层输出一个任务树——根节点是总目标，子节点是不可再分的原子任务。
- **执行层：** 任务树的每个叶子节点被分配给一个动态生成的执行 agent。每个执行 agent 在隔离的上下文中工作——它只接收完成自己子任务所需的最小上下文（相关文件片段、上游子任务的结构化输出、指定的工具集）。
- **编织层：** 所有执行 agent 的输出被汇集到编织层，由 reporter agent 负责合并、消解矛盾、补全遗漏。编织层产出的不是"多个子回答的拼接"，而是一个连贯的、经过检验的最终回复。
- **验证环：** 在整个执行过程中，验证节点分布在每一层——子任务的输出在编织前先验证（编译通过、测试通过、断言满足），编织后的最终输出再次经过完整性检验。任何验证失败触发回环——任务回到相应的执行 agent 重新处理。

编排引擎的核心理念是"LLM 需要被引导才能发挥最大能力"。工程上的精力主要花在三个方面：如何决定拆不拆任务、如何为每个子任务构造最优的上下文、如何在子任务之间传递正确且完整的信息。编排引擎不信任 LLM 的单次输出——它把每一次 LLM 调用都当作一个需要精心调校的认知任务，提供最好的输入条件，验证输出的质量。

在编排引擎的视角下，框架的职责不是"把用户输入转给 LLM"，而是"为 LLM 的每一次调用构建最优的工作条件"。这个角色转换是两种范式最根本的分歧。

**C. 中间地带与谱系思维**

管道模型和编排引擎不是非此即彼的对立选项——它们是同一连续谱上的两个端点。现实中的 Agent 框架几乎都落在中间地带的某处。

从纯管道到纯编排的渐进图景大致如下：

- **纯管道：** 用户输入 → LLM 直接响应。没有任何中间处理层。这是最简单的 API 封装。
- **管道 + 简单预处理：** 框架在发送前做了系统提示词的注入、少量历史消息的摘要化，但不做任务拆解。这是当前大量开源 Agent 框架的形态。
- **管道 + 预处理 + 后校验：** 框架在 LLM 输出后加入了一层格式化校验（JSON 解析、schema 验证），但不做任务级拆解。这是 API 网关类产品的常见形态。
- **轻编排：** 框架对任务做了初步的拆解——分"理解阶段""执行阶段""总结阶段"——每个阶段可能有独立的 prompt 模板和上下文策略，但拆解粒度较粗。
- **深度编排：** 完整的规划-执行-编织-验证四层架构，动态角色生成，子任务隔离执行。这是 Claude Code、Codex 等闭源产品的形态。

为什么多数框架停留在中间地带而不是走向深度编排？原因很现实：编排引擎的工程复杂度是指数级增长的。管道模型加一个预处理节点，几百行代码就能搞定。完整的编排引擎需要处理任务树的动态生成、子任务的状态管理、异常隔离、上下文策略的动态调参——每一项都是独立的工程难题。这个成本是编排引擎被少数团队掌握而多数框架选择停留在简化形态的核心原因。

**管道 vs 编排：六维度对比表**

| 维度 | 管道模型 | 编排引擎 |
|------|---------|---------|
| 任务假设 | 一次性可完成 | 需要分解为子任务 |
| LLM 调用次数 | 1~3 次 | 10~100+ 次 |
| 上下文策略 | 全量或手选 | 按子任务动态裁剪 |
| 错误处理 | LLM 自我纠正 | 框架验证 + 回环 |
| 工程复杂度 | 低（百行级） | 高（万行级 + 大量调优） |
| 适用场景 | 查询、简单生成 | 重构、多文件操作、长流程任务 |

核心结论：架构选择不是哲学问题，而是工程问题。取决于任务的复杂度、上下文规模和可靠性要求。管道模型的简单是一种选择——它用工程简洁换取了可靠性的上限。编排引擎的复杂也是一种选择——它用工程投入换取了 LLM 表现的深度提升。

##### 2.3 编排引擎的核心机制：前置、中置、后置三层处理

编排引擎之所以能显著提升 LLM 的实际表现，是因为它用三层处理机制系统地解决了管道模型的核心缺陷：上下文质量、执行可靠性、输出正确性。这三层处理分别在 LLM 调用之前、之中和之后介入。

**A. 前置处理层：为每一次调用构造最优上下文**

前置处理层的职责是确保 LLM 在"开始思考"之前，已经拥有了它所需的全部信息——不多，不少，恰好是完成当前子任务所需要的。

**意图分析与任务拆解。** 用户输入"帮我重构这个模块的认证逻辑"，这句话对人类开发者来说含义清晰——需要读取认证相关的文件、理解现有的认证流程、设计重构方案、逐文件修改、验证改动。但对 LLM 来说，"重构认证逻辑"只是一个模糊的指令。前置处理层的第一步就是将这种模糊指令转化为可执行的任务结构。

具体机制是：用户输入首先进入一个规划 agent。规划 agent 的职责不是"开始重构"，而是"理解需要做什么，并决定怎么做"。对于认证重构的例子，规划 agent 可能输出的任务树如下：

- 根节点：重构认证逻辑
  - 子任务 1：发现所有涉及认证的文件（通过符号搜索和依赖分析）
  - 子任务 2：分析现有认证流程，生成流程文档
  - 子任务 3：基于流程分析设计重构方案
  - 子任务 4：逐文件执行重构（可进一步拆为 4a: 数据层、4b: 逻辑层、4c: 接口层）
  - 子任务 5：编译验证 + 全量测试运行

每个子任务有不同的信息需求。发现文件的子任务需要广度（整个代码库的符号索引），分析流程的子任务需要深度（选定文件的完整内容），执行重构的子任务需要精度（当前文件 + 重构方案摘要 + 上下游文件的接口约定）。前置处理层的第二项职责就是为每个子任务构建精准匹配的上下文。

**上下文预填与裁剪。** 传统管道模型的上下文构造面临一个"全或无"的陷阱：要么把所有可能相关的文件全部塞进上下文（导致上下文窗口膨胀、注意力衰减），要么让 LLM 自己去搜索（导致搜索策略好坏完全依赖单次推理的运气）。编排引擎的上下文裁剪策略介于两者之间——由框架根据任务的结构化分析来决定当前子任务真正需要看到什么。

具体来说，裁剪策略至少包含三个层次：第一，关键文件完整注入（当前子任务直接操作的文件，如要修改的源文件）。第二，依赖文件的结构化摘要注入（不是整个文件，而是函数签名、接口定义、调用关系——足够让 LLM 知道"外部世界长什么样"但不会淹没它）。第三，上游子任务的执行摘要注入（上一个子任务做了什么、产出了什么、对当前子任务有什么约定——保证信息在跨子任务的传递中不丢失）。

**文件发现与结构化注入。** 发现相关文件不是简单地在目录树上 grep 关键词。一个高质量的编排引擎会维护一个代码库的符号索引——类、函数、接口、数据结构的定义位置和引用关系——它可以根据一个变更（比如"改这个函数的返回值类型"）自动推导出所有受影响的文件，并将这些文件的依赖关系图以结构化的格式注入到当前子任务的上下文中。

这三个环节合在一起，前置处理层完成了一个关键的信息准备：规划 agent 决定了任务的结构，上下文裁剪决定了每个子任务看到什么信息，文件发现决定了这些信息从哪里来。LLM 收到的不再是"用户的原始问题 + 一堆可能相关的文件"，而是"一个被精确界定的子任务 + 恰好够用的信息 + 期望的输出格式"。

**B. 中置处理层：执行过程中的防护与路由**

前置处理层保证了 LLM "进来"时信息是好的。中置处理层保证 LLM "运行"时不跑偏。

**工具调用防护。** 编排引擎中的 LLM 拥有工具调用权限——读写文件、执行命令、搜索代码。这些操作都可能产生破坏性后果。中置处理层在每一次工具调用执行前进行风险评估。举例来说，如果 LLM 试图执行一个删除命令，框架会检查删除的范围是否在预期之内——删除的是预期中的临时文件还是意外的整个目录？如果安全风险超出阈值，框架会拒绝执行并要求 LLM 重新规划。这不是"限制 LLM 的创造力"，而是"在 LLM 拥有真实操作能力时，为操作后果增加一层验证"。类比于操作系统的权限管理——进程可以申请任何操作，但内核决定是否放行。

**执行状态追踪。** 编排引擎同时管理多个子任务的执行——可能有的子任务在并行执行，有的在等待上游输出，有的已经完成。中置处理层维护一个全局的"编排状态图"，记录每个子任务的当前状态（等待中、执行中、已完成、已验证、已失败）、它依赖哪些上游子任务、它的输出被哪些下游子任务依赖。这个状态图的价值在于故障恢复——如果某个子任务执行失败或被验证驳回，框架可以精确定位受影响的子任务链，只重新执行受影响的节点，而不是从零开始。

**子 agent 间的信息路由。** 编排引擎中，多个子 agent 之间不是通过自然语言"聊天"来传递信息的——这种方式的信息损耗太大。中置处理层维护一个结构化的消息协议：每个子 agent 的输出被格式化为一个包含执行摘要、完整产物、置信度评分和依赖关系指针的结构化对象。下游子 agent 接收这个结构化对象作为输入的一部分，而不是阅读一大段自然语言叙述。这类似于微服务之间的 API 调用——服务 A 的输出是一个固定 schema 的 JSON，服务 B 解析这个 JSON 后知道自己该做什么。结构化信息路由的保真度远高于自然语言传递，这是编排引擎在多步骤任务中保持信息一致性的关键机制。

**C. 后置处理层：校验、编织与完成度判定**

后置处理层的职责是判断 LLM 的产出是否正确、如何将多个产出合并为连贯回复、以及任务是否真正完成了。

**输出校验与自动修正循环。** 编排引擎对 LLM 输出的默认姿态是"不信任"。不是怀疑 LLM 在故意犯错，而是 LLM 在概率性生成中犯错的可能性高到需要系统性防范。每一次子任务的输出在进入编织层之前，都经过独立于 LLM 的验证节点：代码是否有语法错误？输出的数据格式是否符合约定？关键断言是否满足？这些验证逻辑不是 LLM 驱动的——它是框架层的确定性检查。如果验证未通过，框架会将失败信息（而不是原始输出）回传给该子任务对应的执行 agent，触发重新执行。

这里有一个容易被忽视的细节：回传给 agent 的不是"你搞错了，重新来"这样模糊的指令。高质量的后置处理会精确描述失败——"在文件 src/auth/login.go 第 47 行，函数签名与接口定义不一致：返回值类型为 error，接口期望 (User, error)"。这种精确的失败描述让 LLM 在重新执行时有了具体的修正方向，大幅降低了二次失败的概率。多次验证失败后，框架可能改变策略——比如将任务交给另一个 agent 从不同角度处理，或者扩大上下文中包含的信息范围。

**回复编织。** 所有子任务的输出经过验证后，进入编织层。编织层的职责不是简单的文本拼接——把多个 agent 的输出粘在一起——而是构建连贯的叙述。编织层处理的核心问题包括：矛盾消解（两个子 agent 给出了相互矛盾的信息——比如一个说"该函数已经废弃"另一个说"该函数是核心入口"——编织层需要根据证据权重做出取舍或标记为待确认）；遗漏补全（规划阶段的子任务覆盖范围是否真的完整？编织层对照用户原始需求逐项检查，发现遗漏则追加新的子任务）；自然语言化（将结构化的子任务输出转化为用户在对话中期望看到的自然语言回复——这在技术上很容易被低估，但糟糕的编织会让用户感知到"这回复不是一个人写的"）。

**完成度检测。** LLM 有一个被称为"幻觉性完成"的倾向——它倾向于声称任务已完成，即使实际上存在未满足的约束。编排引擎的完成度检测层不依赖 LLM 的自述，而是基于客观条件：用户原始需求中的所有约束是否都已满足？所有必经验证节点的验证是否都通过？所有产物文件是否已写入目标路径？是否还有未处理的边缘情况？这组检查条件构成了"真完成"的判定标准——不是 LLM 说完成了，而是所有前置条件都满足了。如果条件不满足，编排引擎不返回结果给用户，而是触发补充执行。

**三层协动的工程隐喻。** 把编排引擎的三层处理理解为"导演-灯光-剪辑"的协作可能有助于理解它们的互补关系。前置处理是导演的工作——决定这场戏拍什么、演员拿什么剧本。中置处理是场务的工作——确保拍摄过程中道具到位、演员安全、各部门信息通畅。后置处理是剪辑的工作——拍摄完成后判断素材是否可用、如何组合、最终成片是否符合剧本要求。三者任何一层的短板都会让最终作品的质量大打折扣——即使 LLM（演员）的"演技"再好。

##### 2.4 动态角色生成：框架提供元能力，Agent 做决策

在传统的多 Agent 系统设计中，有一种常见的预设：事先定义好一个固定的角色池——"代码 agent""测试 agent""文档 agent""审查 agent"——当任务到来时，按照预设的分工派活。这种设计思路来自人类团队的隐喻：角色是稳定的，任务是变化的，稳定角色处理变化的任务。

编排引擎的思路是它的反方向：不预设任何角色。理由是，预设的角色是一种"任务拆解方式的固化"——它假设所有任务都可以用同一套角色池来拆解，但这个假设在复杂任务中经常不成立。有些任务需要"编译器专家"角色但不需要"文档 agent"，有些任务需要两个并行的"探索 agent"从不同方向搜索信息然后互相核对。预设角色池限制了任务拆解的可能性空间。

**按需生成子 agent 的机制。** 在编排引擎的视角下，规划 agent 的职责不仅是决定"把任务拆成几个子任务"，还包括"为每个子任务生成一个专用的 agent"。这个生成过程的核心是动态构造 system prompt（系统提示词）——描述这个子 agent 的身份、当前子任务的目标、它可以使用的工具、它产出的期望格式、以及它的工作边界（哪些事不管）。例如对于"分析现有认证流程"这个子任务，规划 agent 可能会生成如下角色的 system prompt：角色的唯一职责是"阅读所有认证相关代码并输出结构化流程文档"，明确说明它不负责修改代码、不负责方案设计、不负责性能分析。

规划 agent 还需要决定子 agent 之间的并行/串行关系。如果两个子任务之间没有数据依赖（比如同时修改两个互不依赖的模块），它们可以并行执行。如果子任务 B 需要子任务 A 的输出作为输入，它们必须串行。规划 agent 产出的任务树中，每个节点标注了依赖关系和可以并行的兄弟节点，编排引擎据此调度执行。

**框架的元能力清单。** 动态角色生成的本质是"框架提供元能力，agent 做决策"。框架本身不决定任务怎么拆——它提供的是元能力集合：

- **spawn（生成子 agent）：** 从一段 system prompt 动态创建一个有独立上下文和工作空间的执行 agent。
- **isolation（工作空间隔离）：** 每个子 agent 在自己的沙箱中工作——它的文件修改、工具调用、中间状态都不影响其他子 agent 的沙箱。这保证了并行子 agent 之间不会产生资源冲突，也保证了失败子 agent 的污染不会扩散。
- **routing（输入输出路由）：** 框架自动处理子 agent 之间的数据传递——上游的输出被结构化后路由到下游的输入。agent 不需要知道"谁在等待我的输出"——它只管产出，框架负责路由。
- **result_recycling（结果回收与合并）：** 所有子 agent 的输出被框架回收，经过验证后进入编织层。如果某个子 agent 失败，它的沙箱被销毁，框架基于失败的诊断信息生成新的子 agent 重新执行。
- **safety_boundary（安全边界）：** 框架在元能力层面执行安全策略——子 agent 可以申请执行任何操作，但框架根据预设的安全规则决定是否放行。安全边界不是 agent 的自我约束，而是框架的硬限制。

**agent 的决策空间。** 在元能力的框架内，agent 拥有相当大的自主决策空间。规划 agent 决定：这个任务需要拆成几个子任务？每个子任务的 system prompt 怎么写？每个子任务需要哪些工具？子任务之间是串行还是并行？执行 agent 决定：在当前子任务中调用哪些工具、以什么顺序、如何判断自己完成了子任务。reporter agent 决定：哪些子任务的产出更可信、如何消解矛盾、最终回复的结构。

这种设计形成了一种分层决策结构：框架层做基础设施级决策（隔离、路由、安全），agent 层做任务级决策（拆解、执行、编织）。框架是"编程语言"，agent 是"用这门语言写的程序"——元能力是原语，agent 用这些原语编写执行计划。

动态角色生成的工程价值在于它释放了框架的能力上限。预设角色池模式下，框架能处理的任务复杂度受限于"角色池是否覆盖了任务所需的所有技能"。动态生成角色模式下，规划 agent 可以为任何任务结构设计专用的角色组合——框架的处理能力不再被预设的角色池限制。这是编排深度的一种最高体现：不仅框架在管理 LLM 的认知状态，框架还为每个具体任务临时锻造最合适的"认知工具"。

##### 2.5 闭源壁垒的本质：不是代码，是"工程苦活"

动态角色生成和三层编排架构在概念上并不神秘——任何有分布式系统经验的工程师都能在听完描述后画出类似的架构图。这引出一个自然的问题：如果这些设计思路都是公开的，为什么闭源 Agent 产品（如 Claude Code、Codex）仍然保持着明显的体验优势？

答案不是"他们有我们不知道的算法"。真正的原因更朴素也更"不性感"：闭源产品的壁垒不在于架构设计，而在于两个需要大量工程人时才能调优的软资产——系统 prompt 和工具调用链。

**系统 prompt 的工程调优。** 编排引擎中的每一个 agent——规划 agent、执行 agent、reporter agent——都有一份精心调校的 system prompt。这份 prompt 不是"描述一下这个 agent 做什么"这样几句话的事。它包含了经过数百次 AB 测试迭代确定的措辞策略——用什么词触发 LLM 的谨慎模式、用什么句式引导结构化输出、哪些行为边界需要反复强调才能被 LLM 可靠遵守。举个具体的例子：让 LLM 在完成子任务后主动退出而不是继续"帮忙"做下一个子任务——这听起来像一个简单的指令，但在实践中需要特定位的措辞和多次迭代才能可靠实现。这种工程调优没有理论天花板，只有工程投入的上限。开源社区可以推演出"应该有这么一份 prompt"，但无法在缺少大量测试数据的情况下把 prompt 调到和闭源产品同样的可靠性水平。

**工具调用链的编排逻辑。** 编排引擎在运行时做出的每一个工具调度决策——当前状态下调用这个工具还是那个工具、调用失败后是重试还是换工具还是向用户求助、多个工具调用之间的最优序列是什么——背后不是"AI 自己想出来的"，而是基于大量真实使用场景中积累的调度知识。这些知识分散在编排引擎的数百个条件判断和策略分支中：代码搜索时，先 grep 还是先读取目录树？文件修改后，什么时候运行增量编译、什么时候运行全量编译？用户报告的错误堆栈中哪一个调用层最可能是根因，应该优先分析？这些决策看起来琐碎，但每一条都对应着真实场景中的失败教训——上一次用策略 A 失败了，分析根因后调整为策略 B，经过验证，策略 B 被永远写入调度逻辑。

**壁垒的工程含义。** 这两个软资产的共同特征是需要"从真实使用中长出来"。这不是一个能用论文解决的问题——没有"最优的 system prompt 公式"，也没有"全局最优的工具调度算法"。它们是由数千小时的迭代、数万次真实使用、无数次的失败分析堆积而成的工程产物。开源社区可以复制架构的骨架，但无法复制这数千小时的血肉。这就是为什么"自建 Claude Code 替代品"在技术上可行——架构层面的东西不复杂——但在实际体验上不可行——工程调优的积累是时间壁垒，不能靠聪明来缩短。

这也解释了为什么闭源 Agent 产品的护城河比传统软件的护城河更难跨越。传统软件的壁垒可能是核心算法的实现、专有数据的积累、或者网络效应。Agent 框架的壁垒是提示词和工具链上的工程认知——这些认知分散在大量的代码细节中，不是任何一个单独的"秘诀"，而是一个整体的"工程体量"。对它发起挑战的方式不是"想出一个更聪明的架构"，而是"也投入数千小时的工程时间"。而这个投入的时间窗口，正是先行者的壁垒。

### 实现方案

##### 编排引擎的最小可行架构

基于前文对核心机制的系统讨论，本节给出一个编排引擎的最小可行架构（Minimum Viable Architecture, MVA）——它不是某个特定产品的架构描述，而是从设计原理中抽象出的可工程化骨架。

**规划层。** 核心组件是一个规划 agent。输入：用户的完整指令。输出：一个结构化的任务树（JSON 或类似格式），包含任务节点的层级关系、每个节点的目标描述、节点之间的依赖关系标注、并行/串行执行标记。规划层的设计要点：规划 agent 的 system prompt 中需要嵌入"复杂度阈值"——如果任务可以被拆解为单个步骤（如"帮我查一下 xx 函数的签名"），直接返回单节点任务树，跳过后续的编排逻辑。

**执行层。** 核心组件是动态生成的 worker agent。框架维护一个 worker 池（不是"角色池"——worker 在被 spawn 之前没有身份，身份由 spawn 时的 system prompt 注入）。执行层的调度器读取任务树的叶子节点，对每个节点执行 spawn 操作，传递该节点的目标描述、约定工具集、上下文字段。spawn 出来的 worker 在隔离的工作空间中执行，产出结构化结果。

**编织层。** 核心组件是一个 reporter agent。输入：所有 worker 的结构化输出 + 用户原始指令。输出：一个连贯的自然语言回复。编织层的设计要点：reporter 的 system prompt 中嵌入完成度检查清单——对照用户原始需求逐项自检。如果发现未覆盖的需求，reporter 不返回"部分完成"——它向调度器请求追加新的 worker 执行遗漏的子任务，形成闭环。

**验证环。** 验证逻辑分布在整个架构中，而非集中在一处。编译验证、测试验证、格式校验作为 worker 输出进入编织层之前的门禁。编织层的完成度检查作为最终回复返回用户之前的门禁。任何一个门禁失败触发回环，回环信息包含精确的失败描述而非模糊指令。

##### 核心工程挑战与应对

编排引擎在概念上清晰，但在工程实现中面临几个棘手的挑战。

**上下文管理策略。** 最核心的工程挑战是上下文构造——在不同子任务需要的上下文差异很大时，如何避免"要么全塞进去、要么全部不给"的二选一陷阱。有效的策略是一个三层上下文模型：

- **滑动窗口层：** 当前子任务直接操作的文件——完整内容注入。数量控制在 3~5 个文件以内。
- **结构化摘要层：** 不直接操作但需要了解的文件——只注入接口签名、类型定义、关键注释。摘要由框架自动生成（不是让 LLM 总结——框架用 AST 解析或正则提取结构化信息）。
- **锚定文件层：** 整个任务中最重要的 1~2 个文件（如核心接口定义）——在任何子任务中都完整注入，作为跨子任务信息一致性的锚点。

**子 agent 通信协议。** 编排引擎中多个 agent 之间的通信必须走结构化协议。协议中的关键字段包括：执行摘要（一两句话描述这个子任务做了什么）、完整产物（代码、文档、数据——子任务的最终输出）、置信度评分（agent 对自己产出的自评估，0~1 之间，帮助编织层做消解判断）、依赖关系指针（标注本子任务依赖了哪些上游子任务的输出，帮助验证环做影响范围分析）。协议的格式是固定的，所有 agent 在生成输出时必须遵守——这在 agent 的 system prompt 中作为硬性要求注入。

**错误传播与隔离。** 一个子 agent 失败不能导致整体编排崩溃。隔离策略的核心是"输出在隔离环境中验证，验证不通过则丢弃并重新 spawn"。具体实施上，每个 worker 完成子任务后，其输出不是直接路爬到下游——先进入本地的沙箱验证（编译、测试、格式校验）。验证通过的输出进入编织层；验证不通过的输出连同沙箱一起销毁，框架基于失败日志生成新的 worker 重新执行。这个策略的关键是"失败的代价只限于一个子任务的沙箱"——上游的已通过验证的输出不受影响，并行的兄弟节点继续执行，编排状态图中的失败节点被替代为新的 worker 实例。

**状态持久化。** 编排过程中的中间状态必须落盘，支持中断恢复和审计。持久化的内容包括：任务树的结构和状态（每个节点的生命周期阶段）、每个子 agent 的输入上下文和输出产物、验证环的每次运行结果（通过/失败 + 失败原因）、编织层的中间合并结果。持久化的工程价值：长时间编排（数十分钟到数小时）可能因为网络波动或服务重启而中断——持久化让中断恢复成为可能，而不是从头重来。同时，持久化也为编排质量的迭代优化提供了数据基础——每次编排的完整决策链可被事后审计，发现系统性的编排策略问题。

##### 降级策略：从编排退化到管道

编排引擎不是一个固定的模式——它是一组可动态选择深度的工作模式。其中最核心的工程判断是"什么时候该编排，什么时候该直接干"。

**退化决策的条件。** 框架在收到用户指令后，评估任务特征：复杂度评分（涉及文件数量、子步骤数量、依赖关系深度）、上下文规模（用户当前上下文窗口中的已有信息是否已经完整覆盖了任务需求）、历史统计（同类任务的历史执行中，编排 vs 直接执行的正确率差异）。如果三项指标都指向"简单任务"——比如单文件修改、单次信息查询、明确的一步操作——编排引擎跳过规划层和编织层，退化到管道模式。退化到管道模式时，编排引擎的降级不是回到"裸 LLM 调用"——降级后管道模式仍然受益于前置处理的极简版（上下文裁剪）和后置处理的快速版（格式验证），只是跳过了拆解、编织、回环修正这些高成本环节。

**分层降级策略。** 更精细的做法是逐层退化而非全有全无。第一层退化：如果任务只需要一次 LLM 调用但调用质量要求高——保留前置处理层的完整上下文裁剪，但跳过规划层的任务拆解。第二层退化：如果任务简单且用户期待低延迟——跳过所有编排处理，走极简管道链路。第三层退化：如果编排引擎自己检测到多次回环修正仍未通过验证——放弃自动修正，将当前的中间状态和失败信息如实呈现给用户，让用户决定下一步。

降级策略的工程哲学是：编排引擎不是用于"让简单任务变更复杂"的——它是用于"当任务复杂到 LLM 单靠自己解决不了时，系统性地提升成功率"。知道什么时候该编排、什么时候该收手——这个判断的准确性和自动化程度，往往比编排机制本身的复杂度更能定义一个编排引擎的实际工程水平。一个编排引擎最难的环节不是"编排"，而是"编排决策"。

### 总结

本文的核心论证围绕一个简单但被低估的命题展开：LLM 的实际表现不是由模型能力单独决定的——模型之上，框架层的信息处理深度在相当程度上设定了表现的上限。

**三个核心结论。**

第一，薄框架与厚框架的本质分歧在于它们对 LLM 的姿态。管道模型信任 LLM 的单次推理可以处理一切——它把框架简化为消息中转。编排引擎将每一次 LLM 调用视为一个需要构建最优条件的认知任务——它用前置、中置、后置三层处理，系统性地解决了上下文质量、执行可靠性和输出正确性三个管道模型的固有缺陷。

第二，动态角色生成是当前编排深度的一种上限体现。框架不预设"代码 agent""测试 agent"这类角色——它只提供 spawn、isolation、routing 等元能力。规划 agent 在元能力的框架内自主决定任务的拆解方式、子 agent 的 system prompt 内容、子 agent 间的执行拓扑和通信协议。这种"框架做基础设施、agent 做决策"的分层结构，让编排引擎的处理能力不受预设角色池的限制，理论上可以对任意复杂度的任务生成最优的认知工具组合。

第三，编排引擎的成本和局限是真实的，必须被正视。延迟放大——编排层数乘上每次 LLM 调用的延迟，薄框架下 2 秒完成的任务在深度编排下可能变成 30 秒。token 消耗——拆解后的子任务需要各自独立的上下文，整体 token 用量约为管道模型的 3~5 倍。过度工程的风险——编排引擎不是银弹，在单轮简单任务、上下文完整的短对话、高频低延迟交互场景中，深度编排非但不带来收益，反而制造了不必要的复杂度和延迟。

**工程启示。** 工程团队在面对"Agent 应用效果不好"的问题时，第一反应不应是换更强的模型。在确认模型本身的 API 层面能力足够的前提下，优化消息处理管道的投入产出比往往更高。具体路径可以是：先建立前置处理的上下文裁剪机制（立竿见影的改善），再引入后置处理的验证回环（大幅降低"看起来完成了但实际有问题"的失败），最后根据任务的复杂度特征决定是否引入完整的编排拆解。

**开放问题与展望。**

可观测性是编排引擎走向生产级应用时面临的一个核心挑战。编排引擎让 LLM 表现更好，但也让系统变得更加不透明——规划 agent 为什么拆这个不拆那个？reporter 为什么合并 A 的产出而丢弃 B 的？如果用户看到的最终结果有问题，问题是出在拆解环节还是执行环节还是编织环节？当前的工具链几乎无法回答这些问题。为编排引擎开发专门的追踪、日志和可视化工具——类似分布式系统中的请求追踪——是一个尚未被充分解决但需求紧迫的方向。

跨领域泛化是另一个需要冷静看待的问题。编排引擎在代码生成领域的优势最为显著，一个关键原因是代码有明确的正确性标准——编译通过、测试通过、类型检查通过，这些是客观的、可自动化的验证条件。迁移到创意写作、战略分析、产品设计等领域时，缺少同类可自动化的正确性标准。编排引擎在这些领域的收益边界在哪里——能改善到什么程度、什么时候编排反而会损害创造性和发散思维——这些问题目前缺少系统的实证研究。

模型能力与编排深度的关系也不是单向的。更强的模型会不会让编排变得不必要？局部来看，如果模型的上下文窗口持续扩大、推理能力持续增强，单次调用就能处理更复杂的任务，编排的收益空间可能收窄。但全局来看，更强的模型也会让编排引擎的规划 agent 变得更精准、执行 agent 变得更可靠、编织 agent 变得更连贯——编排引擎本身也能受益于更强的模型。这两股力量最终的平衡点在哪里，是未来 2~3 年值得持续跟踪的问题。

**收束。** Agent 框架不是在"调用 LLM"，而是在"管理 LLM 的认知状态"。框架的工程深度，在相当程度上就是 LLM 的实际表现——不是锦上添花的附加层，而是决定交付成果上限的核心工程变量。这个认知如果被行业广泛内化，将改变 Agent 应用开发的重心分配：从"等下一个更强的模型出来"转向"把当前模型的条件建到最好"。

## 知识缺口

本文未覆盖以下知识点，仅做方向性标注供后续扩展：

1. **编排引擎的可观测性工具设计：** 编排过程的分布式追踪、agent 决策的可视化、失败溯源的具体方案——这些是实现编排引擎生产级可维护性的关键技术，本文仅做问题指出，未展开具体设计。

2. **上下文裁剪算法的量化评估：** 滑动窗口 + 结构化摘要 + 锚定文件的三层策略的效果如何量化——衡量"裁剪后上下文的信息完整度"是一个尚未有标准方法的问题，本文仅做了策略描述。

3. **多框架横向评测的实证数据：** 本文的对比分析基于架构层面的推理和社区观察，未包含同模型跨框架的标准化评测数据——这类评测在方法学上存在挑战（如何定义"同一个任务"在不同框架中的"成功标准"），但它的缺失限制了结论的精确性。

4. **编排引擎在非代码领域的适用性：** 创意写作、战略分析、用户研究等缺少客观验证标准的领域中，编排引擎的收益和局限——这些领域的编排适配策略可能需要与本文描述的验证回环完全不同的机制。

5. **编排决策的自适应学习：** 什么时候该编排、什么时候该降级——本文给出了启发式条件（复杂度评分、上下文规模、历史统计），但没有讨论基于执行数据的自适应学习方案，即系统根据历史编排的成败自动调整降级阈值。
