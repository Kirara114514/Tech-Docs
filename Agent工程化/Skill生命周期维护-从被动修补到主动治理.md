# Skill 生命周期维护：从被动修补到主动治理

## 摘要

Skill 是个人 Agent 执行复杂任务的核心载体，但当前管理方式普遍停留在"跑通流程 → 写成 skill → 出错了改"的被动模式。这种模式只在错误信号出现时才触发优化，对质量欠佳但未报错的 skill 缺乏改进机制。更根本的问题是：skill 的读者是 LLM 而非人类，人无法直接判断 skill 写得好不好，只能通过任务执行结果来验证。

基于近期的学术研究（MUSE-Autoskill、SkillHone、SkillsVote、SkillGrad、CODESKILL、EvoSkills、HiSME），本文提出一套面向个人用户的 skill 生命周期管理体系，涵盖 Creation、Memory、Management、Evaluation、Refinement 五个阶段，并重点设计了一个基于纯净上下文测试的分层评估框架。核心判断是：skill 维护不应该只有负反馈（出错信号），而应该建立正反馈机制（定期测试、主动诊断、模式识别）。

## 正文

### 背景

#### 当前做法的天花板

在个人 Agent 场景下，skill 是连接用户需求和 Agent 能力的核心桥梁。一条 skill 本质上是一份结构化指令文档，告诉 Agent 在特定场景下该读什么文件、走什么流程、注意什么约束。

当前普遍的 skill 维护方式是：用户引导 Agent 反复尝试某个具体任务直到得到满意结果 → 把执行中的做法和判断规则写成 skill → 后续如果犯错就把踩坑记录补进去。这套流程在 skill 数量较少时能运转，但随着数量增长（从几条到十几条）以及 skill 之间链式调用和文件依赖的引入，局限性开始暴露。

**问题一：只有负反馈，没有正反馈。**

优化触发条件只有"出错了"这一种信号。一条写得不够好但恰好没出大错的 skill——比如入口描述模糊、结构冗余——永远不会被触发优化。这类似于软件工程中的 bug 驱动修复，区别在于软件工程有代码审查、单元测试和性能分析等主动质量保证手段，而 skill 管理目前全部缺失。

**问题二：写得好不好，人说了不算。**

**skill 的读者是 LLM，不是人。** 人类可以判断一篇技术文档是否清晰、结构是否合理——但这些判断依据都是人类阅读经验。LLM 阅读 skill 的方式与人类截然不同——它不是在逐字理解语义，而是在概率空间中匹配指令模式。人觉得"写得很好"的 skill，LLM 执行起来可能一塌糊涂；反之，人觉得"表述奇怪"的 skill，LLM 可能执行得很好。这意味着任何基于人类直觉的 skill 质量判断都是不可靠的。唯一的验证方式是：把 skill 放到纯净环境里让 Agent 执行一次标准任务，看完成效果。

**问题三：单层结构，信息混杂。**

一条 skill 文件通常承载了触发条件、执行流程、路径常量、修改记录、踩坑经验等所有信息。这些内容混在一起，随着时间推移不断膨胀。一个经多次修正的 skill 可能一半内容是对某个特定错误的补充——这对正常执行路径反而是噪声。这被 MUSE-Autoskill 论文称为"提示词垃圾场"：skill 越改越臃肿，质量却没有同步提升。

**问题四：缺乏演化记录，错误路径可能反复出现。**

传统做法只保留 skill 的最终版本。但 LLM 是概率模型，skill 的作用是在推理时拉高正确路径的概率。如果没有同时记录错误路径和排除理由，错误路径在概率空间中仍然是活跃的。例如，如果一条规则只写了"用 git add 具体文件"而没有记录"为什么不能用 git add ."，LLM 可能在某个未受约束的上下文中再次使用 git add .。记录排除理由相当于提供负样本，抑制对应路径的概率。

#### Skill 作为长期资产

MUSE-Autoskill 提出的核心观点是：skill 应该被视为长期资产，而非一次性产物。和代码一样，skill 需要版本控制、测试覆盖、依赖管理和持续优化。不同之处在于，skill 的质量评估难以像编译检查或单元测试那样自动化——评估只能通过另一个 LLM 来完成，而评估本身可能引入偏差。同时，维护者和使用者是同一个 Agent，这让"自我优化"成为可能，但也带来了自验证的循环引用问题：Agent 改完自己的 skill 后，如何确认改对了？

这两个挑战正是近期学术界探索的方向。从 MUSE-Autoskill 到 HiSME，七篇论文从不同角度尝试解决 skill 的评估、优化和治理问题。本文的目标不是完整复现这些论文，而是提取其中对个人 Agent 用户最实用的思路——五阶段生命周期框架、决策链记录结构、分层测试模型——并将其落地为可执行的管理体系。

### 核心内容

#### 五阶段生命周期框架

Skill 的生命周期可以划分为五个阶段：Creation（创建）、Memory（记忆）、Management（管理）、Evaluation（评估）、Refinement（精炼）。这五个阶段构成一个循环——一条 skill 从创建开始，经历与记忆系统的互动和管理，通过评估发现问题，经过精炼得到优化，优化后的版本再次进入评估循环。

##### Creation — 从零构建 Skill

**定义：** 从实际需求出发构造一条新 skill——确定触发条件、执行流程、输入输出接口和依赖知识。

**常见问题：**
- 创建时缺少结构化审视——通常是"跑通了就写下来"，没有经过边界检查（这条 skill 的职责范围是什么？它依赖哪些文件？它会和哪些已有 skill 冲突？）
- 创建后缺少验证——写完后直接使用，等下次执行才知道好不好
- 粒度不统一——有的 skill 非常细（仅三条操作），有的非常粗（覆盖完整多分支流程）

**建议：**
- 创建前回答三个问题：职责边界是什么？依赖哪些文件或数据？被哪些其他 skill 调用？
- 创建后立即写 3-5 个核心场景测试用例——不必是最完善的测试框架，只是在 skill 末尾标记"理想情况下应该能正确处理 X、Y、Z 场景"
- 保持粒度一致：一个 skill 只做一件事。如果一条 skill 需要"做 A，然后判断是否做 B，否则做 C"——拆成多条或用子流程组织

##### Memory — Skill 与记忆系统的互动

**定义：** Skill 和持久化记忆之间的双向信息流动，包含两个方向。

**Direction B（上下文→Skill）：** 记忆系统中的用户偏好、领域规则和历史决策在 skill 执行时被读取和使用。这是当前最紧迫的方向——skill 需要的上下文信息应当被显式声明，而不是靠 LLM"碰巧记住"。

**Direction A（Skill→记忆）：** Skill 执行过程中产生的新经验反哺到记忆系统。这个方向更长期——需要先有可靠的评估机制，才能判断什么样的经验值得反哺。

**建议：** 优先做 Direction B。在 skill 元数据中增加 `memory_dependencies` 字段，显式声明它依赖哪些文件或文件片段（如 `PROFILE.md#分类规则`）。执行 skill 时先读这些依赖段，再开始主体流程。这使依赖关系可审计、可维护。Direction A 在评估机制成熟后再推进。

##### Management — 组织、一致性与淘汰

**定义：** Skill 库的结构化管理——何时创建新 skill、何时合并或淘汰旧 skill、如何保障多 skill 之间的约束一致性、如何管理依赖关系。

**常见问题：**
- 跨文件约束一致性是最大痛点。同一约束可能在多个文件中被以不同措辞提及——Agent 执行时不知道听谁的
- 没有任何依赖声明。一条 skill 改了，无法知道哪些其他 skill 可能受影响

**建议：**

**约束层级化。** 定义显式的优先级体系，并在全局配置文件中声明：
- 全局配置文件：存放全局不变的铁律（安全规则、分类原则、输出风格），所有 skill 必须遵守
- SKILL.md：存放针对特定任务的执行策略。与全局配置冲突时以全局为准
- 其他运行时上下文文件：约束力最弱，仅作参考

关键要点是区分"领域规则"（做什么）和"执行策略"（怎么做）。领域规则收敛到全局文件，执行策略留在 SKILL.md，不复述只引用。这样改规则只需改一处。接受 SKILL.md 中不可避免会有少量全局规则的上下文复述（LLM 执行时需要就近读取），但不允许与全局配置文件矛盾或弱化其约束。

**依赖声明。** 在 skill 元数据中标注 `depends_on`（依赖谁）和 `used_by`（谁依赖我）。即使只是写下来，也已经把隐式依赖变成了显式信息。

**废弃机制。** 一条 skill 不再适用时，不直接删除，在文件名加 `.deprecated` 后缀并标注废弃原因和建议替代 skill。

**一致性检查。** 每次修改全局约束文件后，搜索所有 SKILL.md 中涉及相关内容的段落，逐条确认没有引入新矛盾。

##### Evaluation — 衡量 Skill 质量

**定义：** 系统化地评估 skill 执行任务时的表现，为精炼提供依据。

**当前问题：** 零评估机制。完全依赖"成功了就好，失败了就改"的二进制判定。没有回退机制、没有失败案例积累。

**建议：分层测试模型。**

Skill 的质量是多维度的。根据评估对象的不同特质，将测试分为三个层级：

| 层级 | 测试对象 | 判定方法 | 自动化程度 |
|------|---------|---------|-----------|
| L1 结构化输出 | 分类标签、字段值、格式 | 映射表自动比对 | 完全可自动化 |
| L2 推理质量 | 分析深度、逻辑一致性 | LLM-as-Judge + rubric | 部分可自动化 |
| L3 风格调性 | 措辞、语气、阅读体验 | 人工抽检 | 仅人工 |

**L1 结构化测试**是最基础和最容易落地的一层。它测试 skill 在结构化输出任务上的准确率——给定输入，期望输出特定的结构化数据。例如，对于一个分类 skill，可以定义测试用例集：

- 输入"关于设计模式的一个想法" → 输出 `{ 分类: "架构设计" }`
- 输入"今天通勤路上看到的趣事" → 输出 `{ 分类: "个人记录" }`
- 输入"简历和密码存储在哪里" → 输出 `{ 分类: "私密" }`

L1 测试的执行机制使用子 Agent 模拟纯净环境：创建子会话——不继承父会话任何上下文，只载入待测试的 skill 文件和测试输入，采集输出并与期望结果比对。子 Agent 不会被父会话的历史决策或上下文偏好污染，这是 L1 测试可靠性的关键。

**L2 推理测试**评估 skill 在需要推理和权衡的任务上的表现。可以采用 LLM-as-Judge 方式——用另一个独立的 LLM 会话根据评分 rubric 打分。需要注意：评判者和被评判者使用同一模型时存在同源偏差；rubric 质量直接影响评估可靠性。建议从 L1 开始积累经验，跑通至少一个完整周期后再探索 L2。

**L3 风格测试**涉及措辞、语气等主观维度。当前没有可靠自动化方法，人工抽检即可。

**回归测试。** 每次修改 skill 后，重新执行该 skill 的全部 L1 测试用例。这有两个关键作用：第一，防止退化——修改可能无意中破坏原本正常的功能；第二，积累信心——随着测试用例增长，skill 行为退化的概率将大幅降低。

##### Refinement — 从错误到优化

**定义：** 基于测试结果对 skill 进行诊断、修改和验证的过程。

**当前问题：** 出错了直接改，不记录错在哪、为什么错、修了到底好不好。也没有验证环节——不改完后是否真的修复了问题。

**建议：决策链记录。**

SkillHone 论文提出的决策链结构（Diagnosis → Candidate Revision → Evaluation Evidence → Outcome）对于个人用户可能过于正式，但其核心思路值得简化采用。每次修改在 skill 中以结构化方式记录：

```markdown
## 决策史

### 2026-06-11
- **诊断：** 分类 skill 将技术类内容误判到通用分类
- **根因分析：** 技术关键词匹配规则措辞太软，被表面标签覆盖
- **修改内容：** 新增强制优先级规则
- **评估依据：** 根据用户反馈确认问题根因
- **验证结果：** L1 测试通过率从 3/5 提升到 5/5
```

这个结构提供三个价值：诊断提供负样本标签（下次遇到类似场景要注意）；评估依据记录修改动机；验证结果确认修改有效。

**经验层缓冲机制。** 在"发现错误"和"修改 skill"之间增加一个缓冲环节：

```
发现错误 → 写入经验层（缓冲）→ 积累到阈值 → 诊断 → 候选修改 → 验证 → 更新决策史
```

经验层防止 skill 本体被频繁小修改胀大。触发阈值可以是同一条 skill 积累 3 条以上错误记录，或某个错误在 L1 测试中频繁出现。

#### 七篇论文的系统视角

前文在各个阶段中引用了相关论文。以下做一次横向梳理，帮助理解整个领域的研究脉络。

**评估维度——怎么衡量 skill 好不好：**
- **SkillsVote** 提出归因问题——一次任务成功，到底因为 skill 好，还是 Agent 自己探索得好，还是环境碰巧简单？它要求拆开计算，对"成功就写入 skill"的朴素做法提出质疑
- **SkillGrad** 更激进——把失败轨迹当 loss，错误诊断当 gradient，反复错误模式当 momentum。这本质上是把评估和优化方向绑定在一起

**优化维度——怎么改 skill：**
- **SkillHone** 强调决策链的完整记录——不只保存结论（改了什么），更保存推理过程（为什么这么改）
- **EvoSkills** 认为 skill 生成器和验证器应该一起进化——验证器不强，skill 只会越改越差。这揭示了一个关键制约：优化上限受限于评估质量

**管理维度——怎么治理 skill 库：**
- **CODESKILL** 尝试用强化学习训练 skill 管理策略
- **HiSME** 不止进化 skill，还要进化"进化 skill 的方法"（meta-skill）

**关系梳理：** MUSE-Autoskill 和 SkillHone 互补——MUSE 提供分层结构，SkillHone 提供决策链格式。SkillGrad 和 CODESKILL 在方法论上竞争——前者用梯度下降隐喻指导单 skill 修改，后者用强化学习训练全局管理策略。EvoSkills 和 HiSME 递进——前者证明验证器需与生成器共同进化，后者在此基础上增加 meta-skill 层级。

对于个人用户，不需要一步到位实现 meta-skill 管理。但理解这个递进关系有助于规划实践路径。

### 实现方案

#### 测试框架的设计与实践

测试是整套体系的基石。没有测试，优化就是玄学；有了测试，优化就有了可测量、可验证、可回退的基础。

**测试的三个核心功能：**
1. **检测退化**——回归测试捕获"改了这个，原先能跑过的场景突然跑不过了"
2. **提供验证**——修改后的 skill 必须在测试集上全部通过才能确认改对了
3. **积累案例**——测试用例集合本身就是"正确行为"的定义，积累越多越稳定

**L1 测试的完整实施方案**

每个 skill 维护一组测试用例，标记优先级。高优先级覆盖核心功能场景，中优先级覆盖常见输入变化，低优先级覆盖边界情况。每条 skill 至少 1 个高优先级用例、2-3 个中优先级用例、1-2 个低优先级用例。

使用子 Agent 执行测试的流程：
1. 读取 skill 文件和测试用例库
2. 对每个用例：创建子 Agent（纯净环境，不继承父会话）→ 传入 skill 文件内容 + 测试输入 → 采集输出 → 比对期望结果
3. 生成测试报告：通过数/总数、失败用例详情、失败模式分析

失败模式分析是关键——如果多个用例失败集中在同一种错误类型（比如"本应归入分类 A 但归入了分类 B"），根因可能不在随机波动，而在规则的系统性偏差。这种情况下单独修改一个用例的期望输出没有意义——应该重新审视规则本身的边界条件。

**子 Agent 测试的注意事项：**
- 子 Agent 的纯净环境指不继承父会话上下文，但 skill 本身的指令和路径常量需要被读取，传入时确保是当前版本
- 每个测试用例应设定合理超时（建议 30-60 秒），防止单个用例挂住整个流程
- 测试消耗 Token——5 个 L1 用例约等于一次正常任务调用的消耗量

**回归测试。** 每次修改 skill 后执行全部 L1 测试。这在多个 skill 相互调用时尤其重要——修改分类 skill 可能影响依赖它的讨论管理 skill，而后者本身不直接感知前者的变化。随着测试用例从几个增长到几十个，skill 行为退化的概率将大幅降低。

**L1 测试的局限与 L2 扩展。**

L1 能覆盖的是"可判定"的部分——结构化输出有明确对错标准。但大部分 skill 的价值在推理质量——比如与用户的整轮讨论质量，无法用映射表判定。这是 L2 试图解决的问题。

L2 评估的初步实施步骤：
1. 定义评分维度（如分析深度、覆盖面、逻辑一致性），每个维度 1-5 分
2. 设计评分指引（不是"1 分差"而是"1 分只复述输入没有新增信息；3 分发展了合理论点；5 分指出了未提及的相关维度"）
3. 用独立 LLM 实例按照 rubric 评分
4. 收集多次评分数据追踪趋势

L2 评估受限于同源偏差和 rubric 质量，对个人用户来说更适合作为"定性参考"而非"定量测量"——用来发现趋势性退化，而非精确决策。

#### 一条 Skill 的完整生命周期案例

为展示五阶段框架的整体运作，以一个分类 skill 为例走完完整生命周期。

**Creation：** skill 因实际需求而创建——用户有多类内容需要自动分类归档。初始版本包含关键词匹配表、三步执行流程（关键词匹配 → 规则判断 → 二次验证）。

**Memory：** skill 需要依赖全局配置中的分类规则和安全边界。这些依赖最初没有显式声明——Agent 执行时"碰巧读到"就算读到，读不到就按自己理解执行。按照 Memory 阶段的建议，应添加 memory_dependencies 声明。

**Management：** 全局配置文件中对某类内容的分类规则措辞是"只允许归入 X"，但 SKILL.md 中复述时弱化为"优先归入 X"。当 Agent 先读了自己的 SKILL.md，读到的是"优先"——这比"只允许"弱得多，可能导致误判。修复方案：全局文件为单一信源，SKILL.md 改为引用而非复述。

**Evaluation：** 为该 skill 设计了 L1 测试用例集，覆盖核心场景（技术内容→技术分类、个人记录→通用分类、私密内容→私密分类）。执行使用子 Agent，不继承父会话上下文。

**Refinement：** 发现误判后执行诊断——根因是分类规则对"方法思考类但实际是技术内容"的处理不当。修复后 L1 测试通过率从 3/5 提升到 5/5。决策史完整记录。

**案例启示：** skill 从创建到优化不是线性过程，而是循环迭代——每个阶段都会暴露前一阶段被忽略的问题。越基础的 skill 越值得投入生命周期管理，因为其质量会通过调用链传导到所有上层操作。

#### 行动路线图

以下路线图将五阶段框架落地为可执行步骤，每个阶段标记完成标准和常见问题。

**第一步：搭 L1 测试（约 1 小时）**

目标：建立最基础的 skill 验证能力。

步骤：选择一条结构化输出型 skill → 设计 3-5 个测试用例 → 用子 Agent 手动执行一次 → 将测试用例写入 skill 文件。

完成标准：该 skill 有可执行的 L1 测试用例集，并至少成功执行过一次。
常见问题：测试用例太复杂（过度覆盖边界导致膨胀）或太简单（只覆盖正常路径不覆盖错误路径）。

**第二步：建约束层级（约 30 分钟）**

目标：解决跨文件约束一致性问题。

步骤：在全局配置文件中声明约束优先级 → 梳理核心全局约束是否都在全局文件中且措辞准确 → 逐条检查 SKILL.md 中与全局文件矛盾或弱化约束的表述 → 修正。

完成标准：所有核心约束只在全局文件中出现一次，SKILL.md 引用不复述。
常见问题：复述时无意识弱化措辞——"必须"变成"应该"，"严禁"变成"建议"。

**第三步：显式依赖声明（约 1 小时）**

目标：让 skill 显式声明依赖的上下文文件。

步骤：为每条 skill 添加 memory_dependencies 字段 → 将依赖锁定到文件的指定段落 → 在执行流程中增加"先读依赖段，再执行主体"的步骤。

完成标准：核心 skill 都标注了 memory_dependencies 字段且执行流程中强制读取。
常见问题：声明了依赖但没有在执行流程中强制读取——等于没声明。

**第四步：扩展到 L2 评估（持续）**

目标：覆盖更复杂的推理质量评估，建立经验反馈闭环。

步骤：研究 LLM-as-Judge 的 rubric 设计方法 → 为一条 skill 设计 L2 评分 rubric → 试行修改后同时跑 L1 + L2 → 探索经验反馈机制。

完成标准：至少一条 skill 的 L1 + L2 联合评估流程跑通一次。
常见问题：L2 评分过于依赖单一 rubric 维度；经验收集时把噪声当有效信号反哺。

### 总结

Skill 生命周期维护是个人 Agent 从"能用"到"好用"的关键基础设施。当前"跑通→固化→出错再改"的模式本质上是事件驱动的被动维护，缺乏系统化的质量管理手段。

本文提出的五阶段框架（Creation → Memory → Management → Evaluation → Refinement）将 skill 视为长期资产而非一次性产物，借鉴软件工程实践和近期学术研究，为个人用户提供了可落地的行动路线。框架的两个根本判断：
1. **skill 的读者是 LLM 不是人类**，人无法直接判断 skill 质量，唯一的可信评估方式是纯净环境的任务执行测试
2. **skill 维护需要正反馈机制**——定期测试、主动诊断、模式识别——而不仅仅依靠出错信号

这实际上是一次范式转变——从"写 skill"到"治理 skill"。前者把 skill 当文档，一次写完等出错了再修；后者把 skill 当代码资产，需要测试、版本管理、依赖声明和演化记录。这条路不会让 skill 管理变复杂——它把"不可预测的随机出错"变成"可测量的质量指标"，减少了不确定性带来的心智负担。

框架中讨论的技术——分层测试、子 Agent 纯净环境、约束层级、决策链记录、经验层——每一项在当前的 Agent 框架能力范围内都可以实现。三件可以立刻动手的事：
1. **搭 L1 测试**——从一条 skill 开始，写 3-5 个用例，用子 Agent 跑一次
2. **建约束层级**——定义全局配置文件为约束单一信源，检查 SKILL.md 中的矛盾表述
3. **记录决策史**——每次修改 skill 时记录诊断到验证的完整链

这三件事可以在约一小时内完成。一旦完成，后续的 skill 维护就有了可测量、可验证的基础。
