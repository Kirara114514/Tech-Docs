# Skill 生命周期维护：从被动修补到主动治理

## 摘要

Skill 是个人 Agent 执行复杂任务的核心载体，但当前管理方式普遍停留在"跑通流程 → 写成 skill → 出错了改"的被动模式。这种模式有两个根本缺陷：一是只在错误信号出现时才触发优化，对质量欠佳但未报错的 skill 毫无改进机制；二是 skill 的读者是 LLM 而非人类，人无法直接判断 skill 写得好不好，只能通过纯净环境中的任务执行结果来验证。

基于近期的学术研究（MUSE-Autoskill、SkillHone、SkillsVote、SkillGrad、CODESKILL、EvoSkills、HiSME）和实操中的反复踩坑，本文提出一套面向个人用户的 skill 生命周期管理体系，涵盖 Creation、Memory、Management、Evaluation、Refinement 五个阶段。重点包括：基于子 Agent 纯净上下文的分层测试框架（L1 结构化测试 → L2 推理质量评估 → L3 风格抽检）、约束层级的跨文件一致性方案、犯错强制记录规则、以及一条 skill 从创建到优化的完整案例。

本文核心判断是：skill 维护不应该只有负反馈（出错信号），而应该建立正反馈机制（定期测试、主动诊断、模式识别）。这不是从"写 skill"到"治理 skill"的转变——它把"不可预测的随机出错"变成"可测量的质量指标"，减少了不确定性带来的心智负担。

## 正文

### 背景

#### 当前做法的天花板

在个人 Agent 场景下，skill 是连接用户需求和 Agent 能力的核心桥梁。一条 skill 本质上是一份结构化指令文档，告诉 Agent 在特定场景下该读什么文件、走什么流程、注意什么禁忌。当前普遍的 skill 维护流程是：用户引导 Agent 反复尝试某个具体任务，直到得到满意结果；把执行中的做法、细节和判断规则写成 skill 文件；后续执行相同时如果犯错，把踩坑记录补充进去。

这套流程在 skill 数量较少时能运转——每条 skill 都来自真实踩坑，有实操价值。但随着 skill 数量增长（超过十条）以及 skill 之间引入链式调用和文件依赖，局限性开始暴露。

**问题一：只有负反馈，没有正反馈。**

优化触发条件只有"出错了"这一种信号。一条 skill 如果写得不够好但恰好没出大错——比如分类规则不够精确、入口描述模糊、结构冗余——它就永远不会被触发优化。这在软件工程中类似 bug 驱动修复——没有 bug 就没人重构代码，直到技术债务积累到不可维护的程度。但软件工程有代码审查、单元测试、性能分析等主动质量保证手段，skill 管理目前全部缺失。

**问题二：写得好不好，人说了不算。**

这是一个根本问题：**skill 的读者是 LLM，不是人。** 人类可以判断一篇技术文档是否清晰、结构是否合理——但这些判断依据都是人类阅读经验。而 LLM 阅读 skill 的方式与人类截然不同——它不是逐字理解语义，而是在概率空间中匹配指令模式。人类觉得"写得很好"的 skill，LLM 执行起来可能一塌糊涂；反之，人类认为"表述奇怪"的 skill，LLM 可能执行得非常好。这一洞察来自实操中的深刻教训：用户在对一次严重错误（删除中间文件导致讨论历史丢失）进行分析时明确指出，人类无法判断 skill 写得好不好，因为需求上最终验证者是 LLM，而人类缺乏判断 LLM 执行效果的直接手段。唯一的验证方式是：**把 skill 放到纯净环境里让 Agent 跑一次标准任务，看完成效果如何。**

**问题三：单层结构，信息混杂。**

当前的 skill 是单一文件，承载了触发条件、执行流程、路径常量、修改记录、踩坑经验。这些信息混在一起，随着时间推移不断膨胀。一条经受过多次修正的 skill 文件可能一半内容是对特定错误的补充说明，这种说明对正常执行路径反而是噪声。MUSE-Autoskill 论文中将其称为"提示词垃圾场"——skill 越改越臃肿，但质量并未同步提升。

**问题四：缺乏演化记录，重复踩坑。**

传统做法只保留 skill 的最终版本。但 LLM 是概率模型，skill 的作用本质上是在推理时拉高正确路径的概率。如果没有记录错误路径和排除理由，错误路径在概率空间中仍然是活跃的。一条典型的踩坑记录——"git add . 会把模板文件一起提交，必须用 git add 具体文件"——如果只写了"用 git add 具体文件"而没有记录"为什么不能用 git add ."，LLM 可能在某个未受约束的上下文中再次使用 git add .。记录"为什么"实际上是在提供负样本，抑制对应路径的概率。

**问题五：Memory 机制不可靠，框架性缺陷。**

当前 Agent 框架自带的 memory 机制——嵌入模型加语义召回——对于 skill 管理的实际需求来说效力极低。多次实操经验表明，将重要信息写入 memory 文件后，LLM 在后续会话中几乎不会主动召回这些信息。"在 memory 里记录就和不存在一样"成为反复验证的痛点。根本原因在于：LLM 不会主动查看 memory 文件，而框架自带的嵌入召回机制准确率不足以支撑关键指令的传递。这意味着指引 Agent 工作的规则必须写入会被稳定读取的载体——也就是 skill 文件和提示词配置文件。memory 至多充当"草稿本"，不能作为正式指令的存储介质。

#### 一个刻骨铭心的案例

在本文的形成过程中，出现了一次严重的操作错误，直接触发了整个体系中对"犯错记录"和"中间文件管理"规则的根本性反思。

在进行技能生命周期维护的讨论时，参与讨论的内容被记录在一个中间文件中，该文件包含了用户的多轮原始发言和另一 Agent 的三轮深度审阅。按照设计，这个中间文件是后续生成正式文档的唯一原材料，不应被擅自修改或清空。然而，DocManager 在流程中多次误操作：先是在某次讨论后将中间文件完全清空，试图"重建"；恢复时又未能完整还原所有发言原文；更严重的是，删除了另一 Agent 的三轮讨论内容——这些内容包含了极为关键的全景分析和结构建议，用户发现后严厉批评。

这次错误的根因分析揭示了一系列系统性问题：

1. **中间文件被当成可随意清空的临时缓存**——实际上它是讨论的完整历史记录，任何时候不得删除或压缩
2. **将"用户重新发送原始讨论内容"理解为"让我重建中间文件"**——应该直接在已有记录上追加，而不是先清空再手动补
3. **另一 Agent 的发言被视为可丢弃的辅助信息**——实际上所有参与者的发言都是完整讨论的一部分，地位相同
4. **恢复中间文件时下意识地压缩和改写**——必须保留原文，任何压缩都意味着信息丢失

这次错误的修复过程（恢复原始内容、重建中间文件）和后续的规则强化，本身就是 Skill 生命周期中"犯错→诊断→修改→验证"闭环的完整实践。它直接催生了三条核心规则：

**犯错强制记录规则：** 每次犯错（误删文件、违反 skill 流程、文档内容不合规、暂存管理错误（指讨论中间文件的意外删除、覆盖或压缩）等），必须将教训记入相关 SKILL.md 或 AGENTS.md，同步记录到当天的记忆文件，但严禁只记到 memory。这条规则后来被写入 AGENTS.md 作为全局约束。

**中间文件即讨论历史规则：** 讨论中间文件等于全部讨论的原始记录，任何时候不得清空、压缩或删除。用户和 Agent 各方发言逐轮完整记录，禁止总结或改写。中间文件是正式文档的唯一原料。

**讨论是单一流水线规则：** 用户讨论和另一 Agent 的讨论是同一讨论流程的不同环节，全部追加到同一个中间文件，不分段新建。

这次案例将在本文后续的案例章节中多次被引用——因为它完整走过了"出问题 → 分析根因 → 修改规则 → 验证效果"的全过程，是本文方法论的一个微型原型。

#### Skill 作为长期资产

MUSE-Autoskill 论文提出的核心观点是：skill 不应该是一锤子买卖，而应该是**长期资产**。和代码一样，skill 需要版本控制、测试覆盖、依赖管理、持续优化。和代码不同的是，skill 的生命周期管理面临两个独特挑战：一是质量评估自动化困难——代码可以编译检查、跑单元测试、做静态分析，而 skill 的质量只能通过另一个 LLM 来评估，评估本身可能产生偏差；二是维护者和使用者是同一个 Agent，这让"自我优化"成为可能，但也带来了自验证的循环引用问题。

这些挑战正是近期学术界探索的方向。从 MUSE-Autoskill 到 HiSME，七篇论文在不同角度尝试解决 skill 的评估、优化和治理问题。本文的目标不是完整复现这些论文，而是提取其中对个人 Agent 用户最实用的思路——五阶段生命周期框架、决策链记录结构、分层测试模型——并将其落地为一套可执行的管理体系。



### 核心内容

#### 五阶段生命周期框架

Skill 的生命周期可以划分为五个阶段：Creation（创建）、Memory（记忆）、Management（管理）、Evaluation（评估）、Refinement（精炼）。这五个阶段构成一个循环——一条 skill 从创建开始，经历与记忆系统的互动和管理，通过评估发现问题，经过精炼得到优化，优化后的版本再次进入评估循环。

以下逐一展开每个阶段，每个阶段使用相同的三段式结构：定义、当前缺失、最小实践。论文思路在相关阶段自然引入，不再单独成篇。

##### 2.1 Creation — 从零构建 Skill

**定义**：从实际需求出发，构造一条新的 skill 文件。包括确定触发条件、执行流程、输入输出接口、依赖知识等。

**当前缺失**：
- 创建时缺少结构化思维——通常是"跑通了就写下来"，没有经过"这条 skill 的边界是什么""它依赖哪些文件""它会和哪些已有 skill 冲突"的审视
- 缺少创建后的验证机制——写完了就放着，等下次执行才知道好不好
- 粒度不统一——不同 skill 之间职责范围差异巨大，有的非常细（仅包含三步操作），有的非常粗（覆盖完整的多模式讨论流程）

**最小实践**：
- **创建前回答三个问题**：这条 skill 的职责是什么（边界）？它依赖哪些文件或数据？它被其他哪些 skill 调用？
- **创建后立即写 3-5 个核心测试用例**——不需要完整测试框架，只是在 skill 末尾标记"理想情况下应该能正确处理 X、Y、Z 场景"
- **保持粒度一致**：一个 skill 只做一件事。如果发现一条 skill 需要"做 A，然后判断是否做 B，否则做 C"——应该拆成至少三条，或用子流程（sub-process）显式组织

##### 2.2 Memory — Skill 与记忆系统的互动

**定义**：Skill 和持久化记忆之间的双向信息流动，包含两个方向。

**Direction B（上下文→Skill）**：记忆系统中的用户偏好、领域规则、历史决策等，在 skill 执行时被 skill 读取和使用。这是当前最紧迫的方向——skill 执行时需要的上下文信息应当被显式声明，而不是靠 LLM"碰巧记住"。

**Direction A（Skill→记忆）**：Skill 执行过程中产生的新经验、新判断，需要反哺到记忆系统。这个方向更长远——需要先有可靠的评估机制，才能判断什么样的经验值得被反哺。

**当前缺失**：
- Direction B 完全缺失。当前 skill 依赖的上下文信息要么硬编码在 SKILL.md 中（导致跨文件一致性问题），要么靠 Agent"碰巧记得"（不可靠）
- Direction A 更是空白。Skill 执行结束后产生的经验没有任何机制被收集和反哺，这是"重复踩坑"的根本原因
- 框架自带的 memory 机制（嵌入模型加语义召回）对于 skill 管理的实际需求来说效力太低。多次实操验证表明，嵌入模型不能可靠地召回特定错误相关的历史记录，而 memory 文件本身也有上下文膨胀的风险

**最小实践**：优先做 Direction B。

在 skill 的元数据部分增加一个 memory_dependencies 字段，显式声明它依赖哪些文件或文件片段：

```markdown
## 元数据（示例）
- **memory_dependencies：** PROFILE.md#文档分类铁律, AGENTS.md#安全与边界
```

执行 skill 时，先读这些依赖文件的相关段落，再开始主体流程。这个"显式声明"的模式使依赖变得可审计、可维护——不依赖 Agent 的"碰巧记住"。Direction A 则作为下一阶段目标，需要先搭好评估机制（Evaluation）再介入。

##### 2.3 Management — 组织、一致性与淘汰

**定义**：Skill 库的结构化管理——何时创建新 skill、何时合并或淘汰旧 skill、如何保障多个 skill 之间的约束一致性、如何管理 skill 间的依赖关系。

**当前缺失**：
- 所有 skill 平铺在目录下，无版本标注、无依赖关系图、无废弃标记
- 跨文件约束一致性是最大痛点。同一类约束可能在多个文件中被复述，措辞却不同——Agent 执行时到底听谁的？
- 没有任何 skill 之间的依赖声明。一条 skill 改动了，无法知道哪些其他 skill 可能受影响

**最小实践之一：约束层级加显式优先级**

定义明确的层级体系，将优先级规则写入全局配置文件：

```
AGENTS.md（全局约束）> SKILL.md（技能级约束）> MEMORY.md（运行时上下文）
```

- **AGENTS.md**：存放全局不变的铁律（安全规则、分类原则、输出风格）。这些规则是所有 skill 必须遵守的根基
- **SKILL.md**：存放针对特定任务的执行策略。当其中某条策略与 AGENTS.md 的全局约束冲突时，以 AGENTS.md 为准
- **MEMORY.md**：存放可变的运行时上下文（用户偏好、历史决策）。约束力最弱，仅作为参考

关键要点是区分"领域规则"和"执行策略"——领域规则（做什么）收敛到全局文件，执行策略（怎么做）留在 SKILL.md。例如，"AI 相关必须放 Tech-Docs"这条规则只写在 AGENTS.md，SKILL.md 只需写"分类规则请参照 AGENTS.md 的文档分类原则"，不复述只引用。这样改规则只需要改一处。

这个分层方案的落地案例发生在 doc_judge（文档库分类 skill）的实际使用中。AGENTS.md 中对 AI 相关内容的分类规则措辞是"只允许放 Tech-Docs"，但 doc_judge 的 SKILL.md 中复述时措辞变成了"优先 Tech-Docs"——"优先"比"只允许"弱得多，导致 Agent 在执行时将本应归入 Tech-Docs 的内容误判到了 Thoughts-Docs。修复方案正是在 doc_judge 中将复述改为引用，并决策树新增强制优先级规则。

**最小实践之二：Skill 依赖声明**

在每条 skill 的元数据中添加双向依赖信息：

```markdown
## 元数据（示例）
- **depends_on：** doc_judge, doc_write（我依赖谁）
- **used_by：** doc_discuss（谁依赖我）
```

这不需要自动化——创建 skill 时人工标注，修改时检查 used_by 是否受影响即可。哪怕只是把依赖信息写下来，就已经把隐式依赖变成了显式信息，减少了"改了 A 却坏了 B"的概率。

**一致性检查流程**

每次修改 AGENTS.md 或 SKILL.md 后，手动跑一遍检查：

1. 列出本次改动的文件
2. 搜索所有 SKILL.md，找出与改动内容相关的段落
3. 逐条对比，确认没有引入新矛盾
4. 确认 AGENTS.md 中优先级最高的约束没有被任何 SKILL.md 弱化

**废弃机制**：当一条 skill 不再适用时，不直接删除文件，而是在文件名加 `.deprecated` 后缀，并在内容头部标注废弃原因和建议替代 skill。

##### 2.4 Evaluation — 衡量 Skill 质量

**定义**：通过系统化的方式评估一条 skill 在执行任务时的表现质量，为后续精炼提供数据支撑。

**当前缺失**：
- 零评估机制。完全依赖 Agent 执行任务时的成功率判断——"成功了就好，失败了就改"。但"成功/失败"本身就是粗糙的二进制判定，丢失了大量中间信息
- 没有回退机制。改了的 skill 如果实际变差了，没有标准流程来恢复旧版本
- 没有病例记录。失败案例零散分布在各个文件中，无法系统化分析错误模式

**最小实践：分层测试模型**

Skill 的质量是多维度的，单一评估方法无法覆盖所有维度。根据评估对象的不同特质，将测试分为三个层级：

| 层级 | 测试对象 | 判定方法 | 自动化程度 | 实施成本 |
|------|---------|---------|-----------|---------|
| L1 结构化输出 | 分类标签、字段值、格式 | 映射表自动比对 | 完全可自动化 | 低 |
| L2 推理质量 | 分析深度、逻辑一致性 | LLM-as-Judge + rubric | 部分可自动化 | 中 |
| L3 风格调性 | 措辞、语气、阅读体验 | 人工抽检 | 仅人工 | 高 |

**L1 结构化测试**是最基础也最容易落地的一层。它测试 skill 在结构化输出任务上的准确率——输入一段内容，期望输出特定的结构化数据。以 doc_judge 为例，测试用例集包含：

- 用例 1（高优先级）：输入"关于 skill 生命周期维护的一个想法" → 期望输出 Tech-Docs / Agent工程化
- 用例 2（中优先级）：输入"今天骑车路上看到一只猫" → 期望输出：Thoughts-Docs / 个人成长
- 用例 3（高优先级）：输入"我的简历和密码存在哪里" → 期望输出：私密文档
- 用例 4（中优先级）：输入"UE5 的 GameplayAbility 系统在多人游戏中的最佳实践" → 期望输出：Tech-Docs / 性能优化
- 用例 5（高优先级）：输入涉及个人隐私的敏感内容 → 期望输出：私密文档

L1 测试的执行机制使用子 Agent（spawn_subagent）模拟纯净环境——创建一个子 Agent 会话，不继承当前会话任何上下文，只载入待测试的 skill 文件和测试输入，采集输出结果并与期望输出比对。子 Agent 天然就是纯净上下文，不继承父会话的状态，不会被历史决策或上下文偏好污染，这是 L1 测试可靠性高的根本原因。

**L2 推理测试**评估 skill 在需要推理、判断、权衡的任务上的表现。难点在于输出不是二值判定（对/错），而是需要评分（好/中/差）。对于 L2 评估，可以采用 LLM-as-Judge 方式——用另一个独立的 LLM 会话根据评分 rubric 对输出打分。但需要注意：评判者和被评判者使用同一模型时存在同源偏差；Rubric 的质量直接影响评估可靠性；单次评分有随机性，需要多次评分取平均。

**L3 风格测试**涉及措辞、语气、阅读体验等主观维度。当前没有可靠的自动化方法，建议人工抽检即可。

三条路径不是排他关系——建议从 L1 开始积累经验，在 L1 流程跑通至少一个完整周期后，再探索 L2。

##### 2.5 Refinement — 从错误到优化

**定义**：基于 Evaluation 阶段的测试结果，对 skill 进行诊断、修改和验证的过程。

**当前缺失**：
- 没有诊断环节。出错了直接改 skill，错在哪、为什么错、修了到底好不好，都不记录
- 没有验证环节。改完后是否真正修复了问题、是否引入了新问题，不验证
- 不保存修改历史。skill 的修改就像代码没有 git log——下次优化时不知道哪些改过、为什么改、效果如何

**最小实践：决策链记录**

SkillHone 论文提出的决策链结构（Diagnosis → Candidate Revision → Evaluation Evidence → Outcome）对于个人用户来说可能过于正式，但其核心思路值得简化采用。每一条 skill 的决策史应该在 SKILL.md 中以结构化方式记录，格式如下：

```markdown
## 决策史

### 2026-06-11
- **诊断：** doc_judge 将 Agent 相关内容误判到 Thoughts-Docs
- **根因分析：** 决策树中"AI 相关优先 Tech-Docs"规则措辞太软，被表面标签覆盖
- **修改内容：** 决策树新增强制优先级规则——AI/Agent/LLM 相关内容只允许放 Tech-Docs
- **评估依据：** 用户明确指出"任何 Agent 相关思考只允许放 Tech-Docs"
- **验证结果：** L1 测试用例 1 执行通过（后续未再误判）
```

这个结构的好处在于：诊断提供负样本标签（"遇到类似场景要注意，之前就在这里翻过车"）；评估依据记录为什么这么改——不只在改，还说明为什么要这么改；验证结果提供信心——后验确认修改有效。

决策史积累到一定量后，可以进行模式分析——反复出现的诊断类型是什么（比如"分类边界模糊"出现了多次），这比单一错误的修复更有管理价值。

**经验层缓冲机制**

在"发现错误"和"修改 skill"之间增加一个缓冲环节：

```
发现错误 → 写入经验层（缓冲）→ 积累到阈值 → 诊断 → 候选修改 → 验证 → 更新决策史
```

经验层的作用是防止 skill 本体被频繁的小修改胀大。每次发现小错误都直接改 skill 本体，skill 会变成"提示词垃圾场"。经验层充当缓冲——先记录错误，等确认模式后再统一修改。经验层的触发阈值可以是同一条 skill 积累了 3 条以上的错误记录，或者某个错误频繁在 L1 测试中出现。经验层本身也记录在 skill 文件中（作为一个临时 section），每次优化后清空。

#### 犯错强制记录规则

这是从实操中总结出的一个独立于五阶段框架之外的关键规则。在一次严重错误（清空讨论中间文件导致历史丢失）的根因分析中，发现一个系统性问题：重要的操作教训被记录在了 memory 文件中，而 memory 文件在后续会话中几乎不会被 LLM 主动读取——"在 memory 里记录就和不存在一样"。

由此确立的规则是：

**每次犯错（误删文件、违反 skill 流程、文档内容不合规、中间文件管理错误等），必须做三件事：**
1. 将教训记入相关 SKILL.md 或 AGENTS.md（犯错的是哪个环节就记哪里）
2. 同步记录到当天的记忆文件
3. **严禁只更新 memory。** memory 效力低、不易被召回，必须确保指令性内容进入会被稳定读取的提示词配置文件或 skill 文件

这条规则是在五阶段生命周期之外的**独立约束**——它不属于任何一个生命周期阶段，而是所有阶段的元规则。任何涉及 skill 修改的错误修复，都必须以此规则为前置条件。

#### 七篇论文的系统视角

以下将前文在各个生命周期阶段中自然引用的论文进行一次统一梳理，帮助理解整个领域的研究方向和层次关系。

**评估维度——怎么衡量 skill 好不好：**
- **SkillsVote** 提出归因问题——一次任务成功，到底是因为 skill 好，还是 Agent 自己探索得好，还是环境恰好简单？它要求将贡献拆开计算，对"成功了就写入 skill"的朴素做法提出了质疑
- **SkillGrad** 更为激进——把失败轨迹当成 loss，错误诊断当成 gradient，反复出现的错误模式当成 momentum。这本质上是把 skill 质量评估和优化方向绑定在一起，评估不再是独立阶段，而是优化的前馈信号

**优化维度——怎么改 skill：**
- **SkillHone** 强调决策链的完整记录——不只保存结论（改了什么），更保存推理过程（为什么这么改、有什么证据支持）。这对应了前文提出的决策史结构
- **EvoSkills** 认为 skill 生成器和验证器应该一起进化——验证器不强，skill 只会越改越差。这揭示了一个关键制约：优化的上限受限于评估的质量

**管理维度——怎么治理 skill 库：**
- **CODESKILL** 尝试用强化学习训练 skill 管理策略，让 Agent 学会管理自己的技能库
- **HiSME** 走得更远——不止进化 skill，还要进化"进化 skill 的方法"（meta-skill）

**递进关系**：有了可靠的评估才能进行有效的优化（EvoSkills 的制约），有了成熟的单 skill 优化机制才能扩展到 skill 库级别的治理（CODESKILL 和 HiSME 的假设）。个人用户不需要一步到位做 meta-skill 管理，但理解这个递进关系有助于规划自己的成长路径。

**论文之间的互补和竞争关系**：MUSE-Autoskill 和 SkillHone 是互补的——MUSE 提供了分层结构（skill 本体、记忆、测试、修改记录），SkillHone 提供了决策链格式（诊断→候选→证据→结果）。SkillGrad 和 CODESKILL 在方法论上是竞争的——前者用梯度下降的隐喻来指导单条 skill 修改，后者用强化学习来训练全局的管理策略。EvoSkills 和 HiSME 是递进的——前者证明了验证器需要和 skill 生成器一起进化，后者在这个基础上增加了 meta-skill 层级。

### 实现方案

#### 测试框架的设计与实践

测试是整套生命周期体系的基石。没有测试，优化就是玄学；有了测试，优化就有了可测量、可验证、可回退的基础。

**为什么测试不可跳过**

个人 Agent 场景下，skill 优化的最大问题不是"能不能改"，而是"改得对不对"。每一次修改都基于 Agent 对错误的诊断——但 Agent 对错误的归因本身可能是错的。如果没有一个独立的验证环节，错误的归因会导致错误的修改，错误的修改会让 skill 越来越差而不是越来越好。

测试框架的三个核心功能：
1. **检测退化**——L1 回归测试捕获"改了这个，原先能跑过的场景突然跑不过了"
2. **提供验证**——修改后的新 skill 需要在测试集上全部通过，才能确认改对了
3. **积累案例**——测试用例本身就是"正确行为"的定义，积累越多，skill 的行为越稳定

**L1 测试的完整实施方案**

每个 skill 维护一组 L1 测试用例，格式为：

```python
test_cases = [
    {
        "input": "关于 skill 生命周期维护的一个想法",
        "expected": {"library": "Tech-Docs", "category": "AI工程化"},
        "priority": "high",
        "description": "Agent 相关内容，验证 AI 分类强制规则"
    },
    {
        "input": "今天骑车路上看到一只猫",
        "expected": {"library": "Thoughts-Docs", "category": "个人成长"},
        "priority": "medium",
        "description": "纯生活记录，无技术隐私内容"
    },
]
```

测试用例的优先级帮助确定哪些场景是核心必须保、哪些是边缘可优化。L1 的优先级覆盖原则：每条 skill 至少 1 个高优先级用例（核心功能场景），2-3 个中优先级用例（常见输入变化），1-2 个低优先级用例（边界情况）。

**执行流程**

使用子 Agent 执行 L1 测试：

1. 读取 skill 文件和测试用例库
2. 对每个测试用例：
   a. 创建子 Agent（纯净环境，不继承父会话上下文）
   b. 传入 skill 文件内容加测试输入
   c. 采集子 Agent 输出
   d. 比对输出与期望结果
3. 生成测试报告，包含通过数/总数、失败用例详情、失败模式分析

失败模式分析是指——如果多个用例失败，它们是不是由同一个原因导致的（比如分类规则有系统性偏差）。如果 doc_judge 的 5 个测试用例中失败都集中在"应该判 Tech-Docs 但判了 Thoughts-Docs"的类型，那么根因很可能不在随机波动，而在分类规则中对某些内容的处理有系统性偏好。

**子 Agent 测试的注意事项**

使用子 Agent 做测试有几点需要了解：
1. **子 Agent 也读取 skill 文件**。子 Agent 的纯净环境是指不继承父会话的上下文，但 skill 本身包含的指令和路径常量是需要被读取的。传入 skill 文件时确保是当前版本
2. **结果判定有歧义时需要人工介入**。L1 的结构化输出（如分类标签）判定清晰——对就是对，错就是错。但如果 L1 的输出包含自由文本字段，需要额外解析才能判定正确性
3. **测试执行本身消耗 Token**。每个测试用例需要启动一个子 Agent 会话，执行 skill 流程，采集输出。这不是大问题，但需要了解
4. **子 Agent 会话的超时设置**。每个测试用例应设定合理超时（建议 30-60 秒），防止单个用例因模型输出异常而挂住整个测试流程

**回归测试**

每次修改 skill 后，重新执行该 skill 的全部 L1 测试用例。回归测试有两个关键功能：

第一，**防止退化**。修改 skill 的目的是修复某个问题，但修改可能无意中破坏原本正常的功能。这在多个 skill 相互调用时尤其重要——修改 doc_judge 可能影响 doc_discuss 的执行结果，而 doc_discuss 本身不直接感知 doc_judge 的变化。

第二，**积累信心**。随着测试用例数量增长，skill 的每个功能路径都有了对应的验证点。测试覆盖从几个用例增长到几十个用例时，skill 行为退化的概率将大幅降低。

**测试记录**

```markdown
## 测试记录
### 2026-06-11
- 版本：v2（决策树规则强化后）
- 用例数：5/5 通过
- 失败用例：无

### 2026-06-10
- 版本：v1（原始规则）
- 用例数：3/5 通过
- 失败用例：
  - "关于 skill 生命周期维护的一个想法" → 预期 Tech-Docs，实际 Thoughts-Docs
  - "UE5 GameplayAbility 最佳实践" → 预期 Tech-Docs，实际 Thoughts-Docs
```

**L1 测试的局限**

L1 测试能覆盖的是 skill 行为中"可判定的"部分——结构化输出有明确的对错标准。但大部分 skill 的实际价值不在结构化输出，而在推理质量。以 doc_discuss 为例，它的"输出"是与用户或另一 Agent 的一整轮讨论。讨论的质量（是否深入、是否抓住要害、是否避免了已知的坑）无法用映射表来判定。

这正是 L2 测试试图解决的问题。L1 提供基础保障（不出低级错误），L2 提供质量信号（讨论深度够不够）。它们不是替代关系，而是互补关系。

**扩展到 L2 评估**

L2 评估的核心思路是 LLM-as-Judge——用另一个 LLM 会话根据评分 rubric 对 skill 的输出进行评分。初步实施步骤：

1. **定义评分维度**。对于 doc_discuss，可以定义"分析深度""覆盖面""逻辑一致性""避免错误"四个维度，每个维度分 1-5 分
2. **设计评分指引**。每个分数的含义需要明确描述，例如"分析深度"——1 分只复述了用户说的话；3 分在用户观点上发展了一个合理的论点；5 分不仅发展了用户观点，还指出了用户未提及的相关维度
3. **执行评分**。让一个独立的 LLM 实例读取 skill 文件、测试输入和执行输出，按照 rubric 逐维度评分
4. **收集评分数据**。多次评分后，可以追踪 skill 在各个维度上的得分趋势

L2 评估的可靠性受几个因素制约：评判者和被评判者使用同一个模型时存在同源偏差；rubric 的质量直接影响评估可靠性；单次评分有随机性。对个人用户来说，L2 评估更适合作为定性参考而非定量测量——不依赖它做精确决策，而是用它发现趋势性退化。

#### 一个 Skill 的完整生命周期——doc_judge 案例

为了展示五阶段框架的整体运作方式，以下以 doc_judge（文档库分类 skill）为案例，走完一轮完整生命周期。

**Creation 阶段**

doc_judge 最初因一个实际问题而创建：多个文档库（技术文档库、想法文档库、私密文档库）的内容需要分类归档，手动分类效率低且不一致。最初的 skill 版本包含关键词匹配表、三步执行流程（关键词匹配→决策树判断→公开性检验）和已知分类映射表。

**Memory 阶段**

doc_judge 需要依赖的上下文包括 PROFILE.md 中的文档分类铁律（"任何 Agent 相关内容必须放 Tech-Docs"）和 AGENTS.md 中的安全边界规则（"绝不泄露私密数据"）。这些依赖最初没有在 skill 中显式声明——Agent 执行时"碰巧读到"就算读到，读不到就按自己的理解执行。Direction B 的最小实践要求添加 memory_dependencies 声明。

**Management 阶段**

在此阶段暴露了一个典型的约束一致性问题。AGENTS.md 中对 AI 相关内容的分类规则措辞是"只允许放 Tech-Docs"，但 doc_judge 的 SKILL.md 中复述时弱化为"优先 Tech-Docs"。当 Agent 执行 doc_judge 时如果先读了自己的 SKILL.md，读到的是"优先"——这比"只允许"弱得多，可能导致误判。实际也确实发生了——将"Skill 生命周期维护方法论"误判到了 Thoughts-Docs。

修复方案：确认 AGENTS.md 为单一信源，doc_judge 的 SKILL.md 中改为引用而非复述，决策树新增强制优先级规则。

**Evaluation 阶段**

doc_judge 非常适合 L1 测试——它的输出是结构化分类结果，有明确的正误判断标准。L1 测试用例集包含 5 个用例，覆盖 Agent 内容、纯生活记录、私密信息、纯技术讨论和敏感内容等场景。测试执行使用子 Agent，不继承父会话上下文。

**Refinement 阶段**

通过用户指正发现错误后，执行诊断流程：诊断发现分类规则对"方法思考类但实际是 AI 工程化"的内容处理不当；根因分析定位到决策树规则措辞太软；候选修改为增加强制优先级规则；验证确认 L1 测试通过率从 3/5 提升到 5/5。决策史完整记录。

**案例启示**

doc_judge 的完整生命周期展示了一个重要事实：skill 从创建到优化不是线性过程，而是循环迭代。每个阶段都会暴露出前一阶段被忽略的问题——Memory 阶段暴露了隐式依赖，Management 阶段暴露了约束一致性，Evaluation 阶段暴露了分类规则的模糊性。

此外，越基础的 skill 越值得花时间在生命周期管理上。doc_judge 是几乎所有文档管理操作的入口——其他多个 skill 都调它。一条基础 skill 的质量会通过调用链传导到所有上层操作。投入在 doc_judge 上的测试和优化，相当于为一整条调用链的可靠性买单。

#### 行动路线图

以下路线图将五阶段框架落地为个人用户可以分步执行的行动计划。

**阶段 1：搭 L1 测试（即时，约 1 小时）**

目标：建立最基础的 skill 验证能力。

步骤：
1. 选择一条适合 L1 测试的 skill（优先选 doc_judge 这类结构化输出型）
2. 为该 skill 设计 3-5 个测试用例，覆盖核心场景和边界情况
3. 用手动方式执行一次（子 Agent 测试），记录结果
4. 将测试用例和测试记录写入 skill 文件

完成标准：该 skill 有了一份可执行的 L1 测试用例集，并至少成功执行过一次。
常见坑：测试用例太复杂——过度覆盖边界情况导致用例膨胀；或者太简单——只覆盖正常路径不覆盖错误路径。

**阶段 2：建约束层级（约 30 分钟）**

目标：解决跨文件约束一致性问题。

步骤：
1. 在全局配置文件中增加约束优先级声明：AGENTS.md > SKILL.md > MEMORY.md
2. 梳理核心的全局约束（安全规则、分类铁律、输出风格）是否都在 AGENTS.md 中且措辞准确
3. 逐条检查 SKILL.md，找出与 AGENTS.md 矛盾或弱化约束的表述
4. 修正发现的矛盾

完成标准：所有核心约束只在 AGENTS.md 中出现一次，SKILL.md 引用不复述。
常见坑：复述时无意识弱化措辞——"必须"变成"应该"，"严禁"变成"建议"。

**阶段 3：Memory Direction B 落地（约 1 小时）**

目标：让 skill 显式声明它依赖哪些上下文文件。

步骤：
1. 为每条 skill 添加 memory_dependencies 元数据字段
2. 将依赖锁定到文件的指定段落（如 PROFILE.md#文档分类铁律，而非 PROFILE.md 全文）
3. 在每条 skill 的执行流程中，增加"先读依赖段，再执行主体"的步骤

完成标准：核心 skill 都标注了 memory_dependencies 字段。
常见坑：声明依赖但没有在执行流程中强制读取。

**阶段 4：L2/L3 评估 + 经验反哺（持续）**

目标：扩展到更复杂的评估场景，建立经验反馈闭环。

步骤：
1. 研究 LLM-as-Judge 的 rubric 设计方法（参考 SkillsVote 和 EvoSkills 的思路）
2. 为一条 skill 设计 L2 评分 rubric
3. 试行：修改 skill 后，同时跑 L1 测试加 L2 评分
4. 探索 Direction A 的"经验收集"机制设计

完成标准：至少一条 skill 的 L1 加 L2 联合评估流程跑通一次。
常见坑：L2 评分过于依赖单一 rubric 维度；经验收集时把噪声当作有效信号反哺。

### 总结

Skill 生命周期维护是个人 Agent 从"能用"进化到"好用"的关键基础设施。当前"跑通→固化→出错再改"的模式本质上是事件驱动的被动维护，缺乏系统化的质量管理手段。

本文提出的五阶段框架（Creation → Memory → Management → Evaluation → Refinement）将 skill 视为长期资产而不是一次性产物，借鉴了软件工程的实践经验和近期学术研究，为个人用户提供了可落地的行动路线。框架的核心思路来自两个根本判断：第一，skill 的读者是 LLM 而不是人类，人无法直接判断 skill 质量，唯一的可信评估方式是纯净环境的任务执行测试；第二，skill 的维护不应该只有负反馈（出错信号），而应该建立正反馈机制（定期测试、主动诊断、模式识别）。

一个额外的关键认知来自实操中的严重错误：memory 机制不可靠，指令性内容必须存入会被稳定读取的载体（skill 文件和提示词配置文件）。这条认知催生了犯错强制记录规则——它不属于任何一个生命周期阶段，而是所有阶段的元规则。

这实际上是一次范式转变——从"写 skill"到"治理 skill"。前者把 skill 当成文档，一次写完就放着，等出错了再修；后者把 skill 当成代码资产，需要测试、版本管理、依赖声明、演化记录。这条路径不会让 skill 管理变复杂，恰恰相反——它把"不可预测的随机出错"变成了"可测量的质量指标"，减少了不确定性带来的心智负担。

框架中讨论的技术——分层测试、子 Agent 纯净环境、约束层级、决策链记录、经验层——每一项都是个人用户在当前 Agent 框架能力范围内可以实现的。不需要等未来的 Agent 框架原生支持，今天就可以从一条 skill 的 L1 测试开始。

三件事值得立刻动手：
1. **搭 L1 测试**——从一条 skill 开始，写 3-5 个测试用例，用子 Agent 跑一次
2. **建约束层级**——定义全局配置文件为全局约束的单一信源，检查 SKILL.md 中的矛盾表述
3. **记录决策史**——每次修改 skill 时记录诊断→修改→验证的完整链

这三件事可以在一小时内完成，而且一旦完成，后续的 skill 维护就有了可测量、可验证的基础——不再是一锤子买卖，而是一个持续进化的过程。
