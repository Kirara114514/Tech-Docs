# 资源异步加载的进度管理与用户体验优化

### 背景
资源异步加载的难点从来不只是“如何异步执行”。下载、校验、解压、依赖解析、反序列化、GPU 上传、实例化、脚本初始化、布局计算、Shader 预热和首帧稳定，组成的是一条非线性、受设备与网络强烈影响的链路。用户看到的却往往只是一个进度条、一个等待页面或一个入口阻塞状态。只要后台链路没有被正确建模，异步加载就可能在技术上成立，在体验上失败。

常见问题非常典型：进度条长时间停在 90% 以后，显示 100% 后仍无法进入，弱网下看不到明确反馈，进入场景后第一秒仍然卡顿，取消加载后后台任务继续跑，下载失败只剩一个不动的界面。这些问题并不说明异步机制本身无效，而是说明项目把“后台任务完成情况”误当成了“用户等待体验”。二者有关联，但绝不等价。

进度管理的本质，是把复杂加载链路翻译成用户可以理解、可以等待、可以恢复、可以信任的体验模型。它不是单纯显示百分比，也不是在底层回调上套一层 UI，而是一套等待体验编排系统：知道哪些任务必须先完成，哪些任务可以后补，哪些状态需要反馈，哪些失败可以重试，哪些入口允许取消，哪些指标能证明体验确实改善。

### 核心原理
第一，必须区分系统真实进度和用户感知进度。系统真实进度描述后台任务完成到哪一步，用户感知进度描述用户应如何理解当前等待。底层 progress 值可能只覆盖下载阶段，可能更新粒度不稳定，也可能在依赖解析或实例化阶段完全没有连续反馈。如果直接把它展示给用户，看似真实，实际经常不可解释。用户需要的不是底层每个任务的准确百分比，而是一个与等待结果一致的阶段表达。

第二，线性百分比不天然适合非线性加载链路。资源加载的耗时分布并不均匀：下载受网络影响，解压和反序列化受设备影响，实例化和首帧稳定可能集中在末尾，缓存命中又会让某些阶段瞬间完成。若把所有阶段平均切成百分比，进度条就会频繁跳跃、停滞或假死。进度条本身没有错，错误在于未经建模地把复杂过程压成线性显示。

第三，进度显示必须为末尾成本预留空间。许多“99% 卡住”并不是下载问题，而是下载结束后还要完成实例化、脚本初始化、Shader 预热、布局计算和首帧稳定。如果下载完成就把进度推到接近 100%，用户会误以为系统已经准备好却故意不进入。更合理的模型是把网络阶段、加载阶段、实例化阶段和首帧稳定阶段分开，并为本地准备保留明确进度空间。

第四，最小可进入集比“全部加载完再进入”更重要。不是所有资源都必须在进入前准备完成。大型界面、活动页、大厅、战斗场景都可以拆分为阻塞资源和非阻塞资源。阻塞资源决定用户能否完成第一个合理交互闭环；非阻塞资源可以在进入后按优先级补齐。最小可进入策略的关键不是简单延后工作，而是明确进入前必须稳定到什么程度，进入后哪些缺失可以用占位、降级或渐进替换承接。

第五，失败、重试和取消是进度系统的一等能力。一个只处理成功路径的进度条不是真正的加载系统。弱网、校验失败、CDN 旧缓存、资源清单不一致、用户主动返回、后台补齐超时，都需要明确状态和恢复策略。用户对系统是否信任，不只取决于成功时是否顺滑，也取决于失败时是否可理解、可选择、可继续。

第六，体验优化必须同时看系统账和用户账。系统账记录下载耗时、解压耗时、实例化耗时、内存峰值和资源数量；用户账记录首可视时间、首可交互时间、最长无反馈停滞、取消率、重试率、加载退出率和进入后一秒卡顿率。若只看系统账，可能会优化了某个技术阶段，却没有改善用户真正敏感的等待节点；若只看用户账，又难以定位底层瓶颈。两张账必须一起看。

### 设计思路
正式的进度系统应从阶段模型开始。一个通用模型可以拆成版本检查、资源清单同步、必要资源下载、本地校验与解压、依赖加载、场景或界面实例化、首屏可视稳定、首个交互闭环稳定、后台补齐。不同业务入口可以裁剪这些阶段，但不应把它们混成一个模糊的“加载中”。阶段模型的价值，是让显示层、业务层和资源层共享同一套等待语义。

阶段权重应来自真实链路统计，而不是平均分配。对于战斗场景，实例化和首帧稳定可能占比很高；对于活动页，网络下载和 UI 图集加载可能更敏感；对于大厅，首屏可视和后台补齐的衔接更重要。权重不需要精确到毫秒，但要基于目标平台、典型网络、缓存命中率和入口类型建立。最稳妥的策略是“固定骨架加动态修正”：固定骨架保证进度可解释，动态修正根据缓存、网络速度、设备档位和资源量微调阶段内部推进速度。

一个简化的阶段聚合模型可以这样表达：

```text
visible_progress =
    version_check.weight * version_check.progress +
    download.weight * download.progress +
    local_prepare.weight * local_prepare.progress +
    instantiate.weight * instantiate.progress +
    first_frame.weight * first_frame.progress
```

伪代码的重点不在公式，而在“阶段显式化”。每个阶段都有权重、状态、错误、取消和日志。显示层不直接消费底层资源句柄的 progress，而消费经过编排后的阶段状态。这样才能解释为什么下载完成后仍需要准备场景，也能避免把 100% 提前暴露给用户。

最小可进入集应以“首个可交互闭环”为标准，而不是以“画面刚出现”为标准。进入大厅后，用户至少应能看到主界面、识别角色或核心背景、点击主要入口；进入战斗后，用户至少应能移动、释放技能、看到关键敌我单位和基础反馈；进入背包后，用户至少应能看到主要分类和可操作物品。若只是显示一个半成品场景或大量空白占位，用户仍会把体验评价为加载失败。最小可进入清单需要业务、UI、表现和程序共同定义。

后台补齐必须有优先级队列。进入后仍未加载的资源，应按用户即将看到或即将操作的概率排序：首屏可见资源优先，当前任务相关资源优先，下一个高概率入口资源优先，低频装饰和远处内容后置。补齐队列还要具备节流和取消能力。低端设备上，补齐任务应分散执行，避免进入后第一秒集中实例化；弱网下，非关键下载应暂停或降速；用户切换入口后，过期补齐任务应取消或降级。否则，最小可进入只是把等待从加载页转移到运行时。

失败处理应区分慢、断、错、旧。慢表示网络仍可用但速度低，需要持续反馈和等待预期；断表示连接不可用，需要暂停、重试或提示检查网络；错表示校验失败、清单错误或下载内容不一致，需要重新拉取或切换源；旧表示本地缓存或 CDN 命中旧版本，需要刷新清单或清理缓存。不同状态对应不同提示、日志、重试策略和用户选择。把所有问题都显示成“加载失败”，会让用户和排查人员同时失去上下文。

取消加载不应只关闭 UI。一次加载可能已经启动下载、持有资源句柄、创建临时对象、注册回调、加入后台补齐队列。取消时必须通过加载上下文统一释放或标记废弃。对于不可立即取消的底层任务，也应确保其结果不再提交给已经关闭的界面。成熟实现会为每次加载建立上下文对象，记录任务、句柄、临时资源、回调和状态，使取消、重试、恢复都能围绕同一份上下文执行。

进度文案应服务阶段解释，而不是暴露技术名词。`Deserialize AssetBundle`、`Load Dependencies`、`Instantiate Prefab` 对开发者有意义，对普通用户没有意义。更好的表达是“同步版本内容”“准备场景资源”“加载角色表现”“进入战斗环境”“恢复网络连接”。文案不宜过于频繁变化，也不能与真实阶段矛盾。正在下载时不要写“即将进入”，正在实例化时不要写“资源下载中”。一致性会建立信任。

日志与回放工具是进度系统可运维的关键。每次加载应生成唯一 TraceId，把资源系统、下载器、实例化器、UI 展示、错误处理和用户操作串成一条时间线。时间线至少记录阶段开始与结束、缓存命中、下载速度、重试次数、取消事件、首可视时间、首可交互时间和进入后一秒卡顿。对复杂问题，回放工具比静态截图更有价值，因为加载体验是一种过程体验。团队可以基于回放共同评估哪段等待缺少反馈，哪段进度停滞过久，哪些资源应前置或后补。

业务入口应允许差异化策略。启动登录可以承受更长等待，但必须稳定可靠；战斗进入要求短且确定，因为用户处于高期待状态；背包和活动页如果等待过长，会被感知为交互迟钝；后台补齐如果影响操作，负面感受甚至强于加载页等待。底层进度系统提供统一能力，不同入口在阶段权重、文案、取消能力、最小可进入集和后台补齐策略上应有差异。

### 进阶讨论
进度系统中最容易争议的问题，是“伪进度”是否合理。答案不是简单的是或否。适度平滑、阶段缓动和短时预留是必要的，因为底层任务更新并不连续；但进度显示不能制造明显错误预期，也不能阻塞本可更快交付的可用状态。若系统明明还有大量工作却硬冲到 99%，或已经准备好却为了动画拖延进入，都会破坏信任。体验层允许设计，但设计必须服从真实可用性。

另一个现实限制是不同设备差异。开发机和高速网络下看起来顺滑的进度，在低端机、冷缓存、弱网和高负载场景下可能完全失真。某个本地解压阶段在开发机上一闪而过，在低端机上可能成为主要瓶颈；某个首帧稳定阶段在高端机上几乎无感，在低端机上可能导致明显停顿。因此进度权重和验收必须覆盖目标设备，而不能只在开发环境里确认。

最小可进入策略也有边界。并非所有业务都适合提前进入。实时战斗、强同步副本、多人匹配、规则公平性敏感的玩法，往往必须保证关键资源和交互完全稳定后再开放。相反，大厅、活动页、商城、背包等弱实时界面更适合先交付可用状态再逐步补齐。最小可进入不是越早越好，而是以不破坏首个交互闭环为前提，把非关键资源后移。

后台补齐可能带来新的性能风险。进入场景后继续下载、解压、实例化资源，会与用户操作竞争 CPU、GPU、IO 和网络。若没有优先级、节流和取消，后台补齐会造成进入后卡顿，用户会觉得系统“加载完了还在卡”。因此后台补齐必须与帧预算、资源优先级和入口预测结合。对低端设备，宁可补齐慢一些，也不要破坏当前交互稳定。

失败体验需要保持克制。过度弹窗、频繁重试提示和模糊错误文案都会放大焦虑。可自动恢复的问题应优先在后台重试，并在超过阈值后再提示；需要用户选择的问题应给出明确路径，例如重试、切换网络、返回入口、稍后下载。失败文案应说明当前状态和下一步，而不是只宣告失败。用户不需要理解 CDN、校验 hash 或资源清单，但需要知道系统是否还在处理，以及自己能做什么。

进度指标不能只看平均值。平均加载时间下降，可能掩盖 P95 用户仍然很差；下载阶段变快，可能掩盖首帧稳定更慢；等待页更短，可能掩盖进入后一秒卡顿更高。正式验收应按入口分层观察平均、P90、P95、最长无反馈停滞、取消率、失败率、重试成功率、首可视时间、首可交互时间和进入后卡顿。只有这些指标共同改善，才能说明体验优化真的成立。

还需要警惕“统一进度组件”的过度抽象。底层能力可以统一，例如阶段模型、取消上下文、日志 Trace、错误映射和指标采集；但表现策略不应完全统一。不同业务入口的用户心态不同，等待容忍度不同，失败恢复路径不同。把所有入口都强行套成一个进度条、一句文案、一个重试按钮，工程上整齐，体验上僵硬。好的进度平台应提供统一底座和可配置策略，而不是把所有入口做成同一种等待。

从团队协作看，资源异步加载体验不是资源系统单独能解决的问题。资源系统负责能力，业务负责入口节奏，UI 负责反馈表达，TA 和内容团队负责资源分层，测试负责弱网与低端设备验证，数据侧负责指标观察。若只有底层系统被要求优化，结果通常是把复杂度压在加载器里；若业务入口没有定义最小可进入和后补边界，加载器无法知道什么可以提前交付。正式文档应把这些责任写清楚。


首帧稳定需要被拆成可视稳定和交互稳定。可视稳定表示主要画面已经出现，不再发生明显空白、闪烁、大面积替换和布局跳动；交互稳定表示按钮、输入、角色控制和主要反馈已经可用。不同入口对这两者的要求并不相同。大厅可以先达到可视稳定，再逐步开放部分次要入口；实时战斗则必须在开放控制前达到交互稳定，否则会影响规则公平和操作信任。若进度系统只记录“加载页关闭时间”，就无法判断关闭后的真实体验是否稳定。正式验收应把可视稳定、交互稳定和加载页关闭时间分开记录。

入口分级是进度策略落地的基础。高频强交互入口，例如战斗、主城、背包和核心养成界面，应优先减少无反馈等待，并保证进入后一秒内不卡顿；低频重内容入口，例如大型活动页、剧情回放、资源下载管理页，可以接受更明确的分段等待，但必须给出清楚状态；启动与版本更新入口可以等待较久，却必须保证失败恢复路径完整。入口分级之后，阶段权重、文案、取消能力、失败提示、后台补齐和指标阈值都可以按入口配置，而不必用一个全局进度模板覆盖所有场景。

进度系统还应处理“预加载”和“正式加载”的关系。预加载可以降低用户显式等待，但它不是免费能力。预加载过早会增加内存和网络占用，预加载过晚又无法改善体验；预加载范围过大，会把资源系统拖回“全部提前准备”的旧模式。比较稳妥的做法是根据用户路径概率、入口热度、资源体积和当前设备状态建立预加载预算。高概率入口的小型关键资源适合提前准备，大型低概率资源应保持按需加载。预加载的结果也应进入同一套进度模型：命中预加载时缩短对应阶段，未命中时回退到正常加载，而不是让业务层各自处理。

取消上下文需要覆盖资源句柄和业务承诺。一次加载开始后，业务层往往已经做出某些承诺，例如即将打开界面、即将进入战斗、即将切换场景。若用户取消或网络失败，系统不仅要释放资源，还要撤销这些承诺：关闭临时 UI、停止动画、取消回调、恢复入口状态、清理半初始化对象。否则会出现加载已取消但界面又被回调打开、资源已释放但逻辑仍访问句柄、旧请求结果覆盖新请求结果等问题。上下文对象应包含请求编号、入口类型、阶段状态、资源句柄、回调订阅、临时对象和取消标记，保证每次加载都有清晰生命周期。

弱网策略也应避免“无限重试”。自动重试能减少用户打断，但无限重试会让用户困在不确定等待里。正式策略应设置重试次数、退避间隔、阶段超时和可恢复条件。下载慢时可以继续显示速度和预计状态；连接断开时应暂停并提供重试；校验错误时应清理失败文件再重新拉取；清单过旧时应刷新版本信息。每一种错误都应进入日志和指标，避免线上大量失败只被记录成同一个模糊错误码。这样运维和开发才能判断问题来自网络、CDN、资源清单、缓存还是客户端状态机。

对于展示层，进度曲线应遵守两个约束：不倒退，不提前完成。不倒退是因为用户很难接受进度条从 80% 回到 60%，哪怕底层原因合理；不提前完成是因为 100% 之后继续等待会严重破坏信任。若动态权重修正导致理论进度下降，显示层应保持当前值并调整后续推进速度；若某阶段完成过快，剩余空间可以让给后续阶段，而不是立即冲到末尾。进度条表达的是体验承诺，底层模型可以修正，但承诺不能频繁反悔。

指标验收应形成版本门禁。对于关键入口，至少应设置最大等待时间、P95 等待时间、最长无反馈停滞、加载失败率、重试成功率、取消率、首可视时间、首可交互时间、进入后一秒卡顿率和后台补齐导致的帧峰值。门禁并不意味着所有指标都必须阻断发布，但应能区分阻断、警告和观察。比如战斗入口首可交互超时可以作为阻断，活动页后台图标补齐较慢可以作为警告，低概率弱网重试增加可以进入观察。指标分级能让团队在版本压力下仍然做出有根据的取舍。

最后，进度系统要避免只优化“等待页好看”。等待页动画、文案和视觉包装能缓解焦虑，但如果进入后立即卡顿、资源缺失、点击无响应，用户会把问题归因于整体加载失败。真正的体验边界应从用户点击入口开始，到首个稳定交互完成结束。加载页只是其中一段。把验收范围延伸到进入后一秒、后台补齐完成和取消恢复，才能避免进度优化只停留在表层。

### 总结
资源异步加载的进度管理，本质不是显示一个百分比，而是把复杂加载链路转化为用户可理解、可等待、可恢复、可信任的体验。成熟系统需要区分真实进度与感知进度，建立阶段模型，按数据设置权重，为末尾实例化和首帧稳定预留空间，定义最小可进入集，设计后台补齐、失败重试、取消清理和指标验收。

当项目能稳定回答“用户现在为什么等待、还需要等待什么、失败后如何恢复、何时可以进入、进入后还有哪些后补任务”时，异步加载才真正从技术实现升级为体验基础设施。它减少的不只是等待时长，也减少等待中的不确定感。
