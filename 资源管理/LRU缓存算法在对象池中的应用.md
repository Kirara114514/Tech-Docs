# LRU 缓存算法在对象池中的应用

### 背景

对象池的目标从来不是把对象永久留在内存里，而是在创建成本、命中率、内存预算和运行时稳定性之间建立平衡。许多 Unity 项目在引入对象池后，会把“复用”误解为“尽量保留”。早期项目中，这种做法看起来有效：预热一批特效、子弹、UI 节点或临时对象，用完放回池中，下次再取，GC 和实例化开销都下降。但项目进入中后期后，对象池本身也会膨胀成资源常驻容器，成为新的内存风险。

这种风险通常不是一天出现的。活动资源越来越多，特效变体越来越多，UI 组件越来越碎，历史玩法逐渐累积，曾经高频使用的对象在新版本里变成低频对象，却仍然留在池中。与此同时，新热点对象继续扩容，导致池的总体规模持续上升。此时对象池已经不只是“减少创建销毁”的工具，而开始承担缓存系统的职责：它必须决定哪些对象值得继续常驻，哪些对象应该释放空间。

LRU，Least Recently Used，即最近最少使用，是缓存淘汰中最常见的策略之一。它的基本假设是：最近被使用的对象，在短期未来继续被使用的概率更高；长期未被使用的对象，继续保留的收益更低。这个假设并不总是成立，但在大量具有时间局部性的访问模式中非常实用。对象池一旦具备缓存属性，LRU 就有机会成为池治理的一部分。

不过，把 LRU 引入对象池并不等于给池加一个链表。对象池中的对象不是普通数据缓存，它们可能持有 GameObject、组件状态、材质引用、粒子系统、动画状态、协程、资源句柄和业务上下文。淘汰一个池对象不仅是从容器中删除节点，还可能涉及生命周期回调、资源引用释放、场景归属、异步加载状态、预热策略和性能抖动。因此，LRU 在对象池中的应用必须被视为工程策略，而不是单纯算法题。

本文讨论 LRU 在对象池中的适用边界、核心原理、实现方案和进阶风险。重点是回答：哪些对象池适合 LRU，哪些不适合；对象池中的“最近使用”应该如何定义；如何避免命中率提高但重建抖动更严重；如何把 LRU 与预热、场景切换、资源管理和监控面板结合；如何验证一套 LRU 对象池策略是否真的改善了项目，而不是制造了新的不稳定。

### 核心原理

对象池和缓存本质上都在处理同一个问题：有限预算下，哪些对象值得继续留在内存中等待复用。缓存通常保留数据或计算结果，对象池保留可重新激活的实例。对象类型不同，但治理问题相似：命中率、容量、淘汰、冷热点、重建成本和抖动风险。只有承认对象池也是一种受预算约束的缓存系统，才会意识到“只进不出”的池化策略迟早会失效。

LRU 的适用前提是访问具有时间局部性。也就是说，最近被频繁使用的对象，在短期未来仍有较大概率继续被使用。UI 列表项、战斗飘字、常见弹道、短生命周期特效、活动界面节点、提示气泡等对象，通常具备这种特征。它们的热点会随着场景、玩法和活动阶段变化，LRU 可以帮助对象池逐步遗忘旧热点，把空间让给新热点。

但 LRU 不适合所有池。某些对象虽然低频，但一旦需要就必须零抖动，例如关键 Boss 技能特效、剧情演出节点、复杂角色表现对象、低频但创建极重的资源载体。这类对象如果被 LRU 淘汰，下一次 miss 可能造成明显卡顿。还有一些对象生命周期强依赖场景或模块，应该由场景卸载、模块关闭或资源系统明确释放，而不是交给最近使用时间决定。LRU 适合治理长尾冷对象，不适合替代生命周期设计。

对象池中的 LRU 重点不在排序，而在价值判断。算法语境里，LRU 可以被描述为“访问后移到队头，淘汰队尾”。工程语境里，更重要的是理解队尾对象代表什么：它代表当前阶段保留价值下降的对象。若一个对象长期未被访问，它继续占用池空间的收益降低；若一个对象近期频繁命中，它更可能属于当前热点。LRU 的价值在于让池的常驻内容接近真实使用分布。

然而，最近使用时间不能成为唯一指标。对象价值还与创建成本、内存体积、预热成本、miss 后卡顿风险、资源依赖、场景归属、对象类别和业务重要性有关。一个轻量 UI 节点和一个复杂特效对象即使最后访问时间相同，也不应被同样对待。工业化 LRU 通常需要结合对象分级、权重、最小保留数、保护期、软硬容量上限和资源预算。

对象池引入 LRU 后，最需要警惕的是 thrash，即反复淘汰又反复重建。某些对象位于冷热边界，可能刚被淘汰又被重新需要。如果容量阈值过紧、淘汰时机不合理或热点切换过快，LRU 反而会增加创建销毁峰值。判断 LRU 成功与否不能只看池规模下降，也要看 miss 峰值、重建次数、帧时间波动和玩家可感知抖动。

对象池 LRU 还必须区分实例层和资源层。销毁一个池化 GameObject 实例，不等于它引用的 Prefab、材质、贴图、音频或 AssetBundle 已被释放；释放底层资源，也不等于所有实例都安全销毁。对象池 LRU 主要治理实例常驻，资源卸载应由资源系统根据引用计数、场景生命周期和缓存策略决定。两层混在一起，会导致要么内存没有真正下降，要么下次重建触发完整资源加载，抖动更严重。

### 设计思路

对象池引入 LRU 的第一步，是按对象类别分层。轻量高频对象、中量常用对象、关键重对象、场景专属对象和不适合池化对象，不应共享同一套淘汰规则。轻量对象可以更积极地 LRU；中量对象可采用 LRU 加最小保留数；关键重对象应使用专用池或白名单；场景专属对象应随场景清理；不可可靠重置的对象不应进入通用池。分类比链表实现更重要。

第二步是定义“使用”的语义。对象从池中取出算一次访问，还是归还时算一次访问？对大多数对象池来说，取出代表需求发生，应更新热度；归还代表对象可复用，但不一定代表未来需求。因此常见做法是在 `Get` 时刷新最近访问时间，在 `Release` 时更新可淘汰状态。若只在回收时刷新热度，某些长时间活跃的对象反而可能被误判为冷对象；若活跃对象也参与淘汰，又可能出现生命周期错误。

第三步是建立容量模型。简单的“最多保留 N 个对象”只适合同质对象。大型项目中，对象体积差异很大，更合理的是引入加权容量或内存预算。每类对象可以有估算成本、最小保留数、软上限和硬上限。超过软上限时，系统在安全点温和淘汰；超过硬上限时，系统必须更积极地收缩。这样能避免池在短时间波动中反复创建释放，也能让预算更接近真实内存压力。

第四步是确定淘汰时机。对象池 LRU 不宜在任意时刻立即销毁队尾对象。更稳妥的方式是在安全点执行修剪，例如帧末、战斗波次间隔、界面关闭后、场景稳定后、资源系统空闲时或内存告警后。淘汰动作本身可能触发生命周期回调、组件清理和资源引用变化，如果发生在高峰帧，很容易把原本的优化变成新的卡顿源。

第五步是设计淘汰流程。生产环境中的淘汰不应只有“选队尾并销毁”一步，而应拆成候选选择、风险过滤和实际释放。候选选择根据最近访问时间、对象类别、成本和池状态找出可清理对象；风险过滤检查保护期、最小保留数、场景即将使用、资源预热状态、异步加载依赖和白名单；实际释放执行生命周期清理、断开引用、销毁实例、更新统计并记录原因。这个流程可以避免算法越权决定业务生命周期。

一个简化的伪代码模型可以表达这种边界：

```csharp
public sealed class PoolLruController
{
    public void OnGet(PoolKey key)
    {
        var state = GetState(key);
        state.LastAccessFrame = Time.frameCount;
        state.HitCount++;
    }

    public void OnRelease(PoolKey key, IPooledObject obj)
    {
        var state = GetState(key);
        state.ReturnToIdle(obj);
    }

    public void TrimAtSafePoint(PoolTrimContext context)
    {
        while (context.Budget.IsOverSoftLimit)
        {
            var candidate = SelectColdCandidate(context);
            if (candidate == null || !CanEvict(candidate, context))
                break;

            Evict(candidate, context);
        }
    }
}
```

这段伪代码的重点不是容器实现，而是职责划分。访问更新热度，回收进入空闲集合，修剪发生在安全点，淘汰前有过滤。实际项目中还应记录 miss、重建成本、淘汰原因和对象类别。代码占比不需要高，关键是把 LRU 从“容器操作”提升为“预算调度”。

第六步是与预热结合。预热回答“阶段开始前先准备什么”，LRU 回答“阶段运行后继续保留什么”。两者不冲突。副本开始前可以预热常用技能特效、UI 节点和战斗飘字；运行一段时间后，LRU 根据真实使用情况淘汰冷对象。预热对象可以设置保护期，保护期结束后进入正常 LRU 评估。这样既保证启动稳定，也避免预热内容永久占用池空间。

第七步是与场景和活动阶段结合。热点不是全局恒定的。一个活动期间非常热的对象，活动结束后应尽快降低保留优先级；一个战斗场景中的高频对象，回到主城后可能不再需要。对象池应接收场景切换、玩法进入、活动结束、战斗结算等阶段信号，对相关池执行热度衰减、子池清理或保留数调整。单纯依赖时间自然淘汰，可能让历史热点污染新阶段。

第八步是建立监控面板。至少需要按对象类型展示当前空闲数、活跃数、累计创建、累计销毁、命中率、miss 次数、淘汰次数、重复重建次数、最近访问时间、保留原因和淘汰原因。没有观测数据，LRU 参数只能靠猜。监控面板不必复杂，但必须能解释“为什么保留”和“为什么淘汰”。

第九步是与资源系统建立协议。实例淘汰后是否释放底层资源，应由资源层策略决定。轻量实例可以只销毁 GameObject，保留资源句柄；中量对象可以降低实例常驻但保留资源到场景结束；重量资源可能需要实例池、资源缓存和预加载三层联合治理。对象池 LRU 只解决实例层预算，不应独自决定 AssetBundle、Addressables 句柄或 YooAsset 包裹的卸载。

### 进阶讨论

LRU 最常见的误用，是把它当作所有对象池的默认模板。事实上，对于对象种类少、热点稳定、生命周期清晰的系统，固定容量池可能更可靠。LRU 会增加状态维护、调试、监控和测试成本。如果项目没有冷热点变化问题，过早引入 LRU 只是增加复杂度。是否需要 LRU，应由实际池膨胀、内存压力、长尾对象残留和热点迁移数据决定。

第二个误区是只看命中率。高命中率不一定代表体验稳定。如果为了提升命中率保留了大量重对象，内存压力可能变高；如果为了降低常驻数量而频繁淘汰边缘热点，miss 峰值可能造成卡顿。对象池 LRU 的指标应同时看命中率、miss 峰值、重建成本、帧时间波动、内存曲线和误淘汰次数。单一指标会误导优化方向。

第三个误区是把对象实例淘汰当作内存释放完成。Unity 对象常常引用底层资源，销毁实例并不必然释放贴图、材质、网格或音频。若资源系统仍保留引用，内存不会明显下降；若资源被过早卸载，下次 miss 又要重新加载资源，抖动更大。正确做法是分层治理：实例池负责实例常驻，资源系统负责资产生命周期，二者通过清晰协议协作。

第四个误区是忽略对象重置质量。LRU 只决定保留或淘汰，不能保证对象回池后状态干净。若对象带着旧事件订阅、协程、Tween、动画参数、粒子状态或业务引用回池，即使 LRU 策略完美，也会出现状态污染。对象池治理必须先保证生命周期契约可靠，再讨论淘汰策略。否则，LRU 只是让有问题的对象更频繁地复用。

第五个误区是淘汰时机过于激进。内存超过阈值后立即大量销毁对象，可能造成一帧内的明显抖动。更稳妥的做法是分帧修剪、在安全点修剪、按优先级逐步修剪，并在硬上限触发前通过软上限提前收缩。对象池 LRU 应该像预算调度器，而不是突然执行的大清理。

对象分组也值得深入讨论。一个全局 LRU 队列看起来简单，但很难表达对象差异。更好的方式是按对象类别建立子池，再在全局预算层做协调。轻量对象、重对象、UI 对象、特效对象、场景对象、活动对象可以有不同保留策略。全局预算负责总量，子池策略负责细节。这样既能控制总内存，也能避免重对象被轻对象访问频率淹没。

LRU 还应支持保护期。刚预热或刚创建的对象，可能还没有充分表现出热度，立即参与淘汰容易造成抖动。保护期可以按帧数、时间、场景阶段或使用次数定义。保护期不是永久豁免，而是避免短时间内创建后又立刻销毁。保护期结束后，对象进入正常热度评估。

对于长期运营项目，活动资源的退场策略非常关键。活动上线期间，相关 UI、特效和临时玩法对象可能非常热；活动结束后，它们应快速降级为冷对象。活动系统可以向对象池发送阶段信号，降低相关池的最小保留数，触发热度衰减或标记为优先淘汰。这样 LRU 不只是被动等待访问时间变旧，而能与运营节奏协同。

测试方面，LRU 对象池至少应通过三类专项验证。第一类是热点切换，模拟主城、战斗、活动、返回主城等路径，观察旧热点是否退场、新热点是否稳定命中。第二类是容量挤压，降低预算看系统是否优先淘汰低风险长尾对象。第三类是长时间运行，确认池不会只增不减，也不会因过度淘汰产生重复创建峰值。没有这些测试，LRU 很容易只在正常路径看起来正确。

代码评审时，也不应只检查字典和链表是否正确。更重要的是检查谁能触发淘汰、淘汰发生在哪个阶段、保护期和白名单是否存在、统计是否能解释结果、资源层是否有明确协议、重复回收和活跃对象是否被排除。容器正确只是基础，策略入口才是上线稳定性的关键。


还可以为对象池 LRU 增加一层“成本账户”。每个池不只记录数量，还记录估算内存、最近 miss 平均耗时、实例创建耗时、销毁耗时和资源依赖状态。这样淘汰决策就不会只看谁最久没有使用，而能判断清理它能释放多少预算、下次重建会付出多大代价。对于轻量对象，LRU 可以更积极；对于重建成本高但占用可接受的对象，则可以提高保护水位。成本账户让对象池从简单容器变成可解释的运行时预算系统。

在多人协作项目中，还应把 LRU 策略写入资源和玩法规范。哪些对象允许进入通用 LRU 池，哪些对象必须使用专用池，哪些对象需要最小保留数，哪些对象在活动结束后要主动降级，都不应只藏在代码里。策划、TA、特效和程序共同维护这些规则，能减少“某个对象为什么被清掉”的沟通成本。LRU 策略越透明，越容易在版本迭代中持续调参。

验收标准也应明确。合格的 LRU 对象池不只是长度符合预算，而是在热点切换后内存曲线能回落，在高峰阶段不会出现明显重建尖峰，在长时间运行后不会累计历史冷对象，在关键对象上不会发生误淘汰，在资源卸载上不会与 Addressables、AssetBundle 或 YooAsset 的引用规则冲突。只要这些条件没有被验证，LRU 就仍然只是代码层面的优化尝试，而不是可以依赖的工程机制。


正式上线时，LRU 参数还应支持灰度和回滚。对象池淘汰策略一旦过于激进，可能只在特定机型、特定玩法路径或长时间运行后暴露问题。将软上限、硬上限、保护期和对象分类阈值配置化，并保留快速关闭 LRU 或切回固定容量策略的能力，可以显著降低上线风险。运行时治理策略越接近基础设施，越需要可回退设计。

### 总结

LRU 在对象池中的价值，是让对象池从静态堆积转向动态治理。它可以根据真实访问热度，逐步淘汰长尾冷对象，把内存空间留给当前更有价值的热点实例。对于对象类型多、热点变化频繁、版本内容长期累积的项目，LRU 能有效缓解对象池无限膨胀的问题。

但 LRU 不是对象池的万能默认方案。它必须建立在对象分类、生命周期契约、容量预算、淘汰安全点、资源层协议和可观测性之上。只有当团队能够同时观察命中率、miss 成本、重建峰值、内存曲线和淘汰原因时，LRU 才会成为稳定的治理工具，而不是新的抖动来源。对象池优化的最终目标不是保留更多对象，也不是淘汰更多对象，而是在真实项目约束下持续维持复用收益与内存预算的平衡。
