# 资源依赖关系优化：减少包体与内存占用

### 背景
资源依赖关系是大型 Unity 项目中最容易被低估的资源治理对象。包体膨胀、补丁过大、内存峰值异常、场景切换后资源无法释放，表面上常常像是贴图过大、模型过重或加载时机不合理，深层原因却经常藏在依赖图里：一个轻量界面通过 Prefab 嵌套拖入整套大厅表现资源，一个活动入口误用主线公共图集，一个配置资产把尚未开放的玩法资源带进首包，一个共享材质让多个业务模块在运行时共同持有不该常驻的底层纹理。单个节点看起来都能解释，整条链合起来就会造成长期稳定的成本放大。

依赖问题的麻烦在于它不总是以错误形式出现。构建能通过，编辑器能预览，运行也能显示正确画面，但包体、补丁、下载、加载、驻留和卸载路径已经偏离业务边界。项目规模越大，越容易出现“局部复用合理、整体依赖失控”的局面。资源依赖优化因此不是简单删除引用，也不是把所有资源都拆碎，而是让资源归属、打包边界、加载边界、释放边界和业务生命周期尽可能一致。

本文把资源依赖关系视为一张可治理的图，而不是一组零散文件。核心问题不是“引用数量能不能减少”，而是“哪些引用应该存在、哪些引用会传播成本、哪些引用会妨碍释放、哪些共享会把局部变化扩散成全局变化”。只有从这个角度出发，减少包体与内存占用才不会停留在一次性清理，而能沉淀为项目长期的资源工程能力。

### 核心原理
依赖优化的第一条原则，是依赖边界要服务业务边界。资源复用本身不是问题，错误复用才是问题。公共按钮、通用材质、字体、图集、Shader、配置资产都可能被多个模块使用，但它们不应因为“方便”而无条件进入全局共享层。一个资源是否适合共享，至少要看三个条件：是否被多个模块稳定使用，变更频率是否足够低，进入共享层后是否会扩大补丁传播和运行时驻留范围。只要其中任一条件不成立，共享都可能从节省体积变成扩大成本。

第二条原则，是直接依赖往往只是表面，间接依赖才是主要风险。开发者在 Inspector 中容易看到一个 Prefab 直接挂了哪个材质或图集，却不容易在日常工作里看到材质又引用了哪些纹理，图集又包含了哪些跨模块图标，配置对象又嵌套了哪些子配置和预制体。包体和内存很少只被第一层引用决定，真正决定成本的是整条依赖链的闭包。一个小入口一旦拥有深层依赖，就会在构建时带入更多资源，在运行时保留更多对象，在补丁时传播更多变化。

第三条原则，是打包边界和运行时加载边界必须协同。AssetBundle、Addressables 或 YooAsset 的资源组设计如果只按目录、文件类型或制作习惯划分，却不考虑运行时是否一起加载、是否一起释放、是否一起更新，就会出现构建看似整齐、运行时成本很差的问题。某些资源被打成一个包，但运行时只需要其中很小一部分；某些资源在目录上分散，但运行时总是一起加载；某些活动资源独立分包，却因为依赖公共层而持续拉起主线资源。依赖优化必须同时看构建账和运行账。

第四条原则，是内存问题经常不是“加载太早”，而是“依赖导致卸不掉”。当某个场景退出后仍有大量资源驻留，问题可能不是加载系统没有执行释放，而是仍有引用链把这些资源保留下来。保留链可能来自对象池、静态缓存、异步句柄、配置资产、公共材质、UI 图集或调试工具。依赖图如果只覆盖构建阶段，不覆盖运行时引用保留，就无法解释为什么某些资源理论上应该释放却迟迟不释放。减少内存占用必须把依赖治理延伸到生命周期治理。

第五条原则，是补丁传播也是依赖成本。热更新项目中，一个公共图集或共享 Prefab 的小变更可能导致多个包、多个模块、多个平台同时更新。把资源放入共享层并不只意味着运行时复用，也意味着版本变化传播范围扩大。依赖越广，变更越容易从局部事项变成版本事项。评估共享资源时，如果只看当前包体节省，不看未来补丁传播，就会低估长期维护成本。

### 设计思路
依赖治理应从资源归属开始。每个正式资源都应有明确 owner、业务模块、生命周期、平台范围和是否允许共享的判断。资源没有归属，就没有边界；没有边界，就很难判断某条引用是否越权。对于图集、字体、材质、Shader、公共 Prefab、配置资产这类高风险节点，归属应更加明确，因为它们天然容易成为多模块依赖的汇合点。共享层不是临时收纳区，而是需要审批、审计和退出机制的正式层级。

第二步是建立依赖图的双向视角。第一种视角是从资源看上游：某个异常资源为什么会被带入，它经过了哪些 Prefab、材质、配置、图集或脚本资产。第二种视角是从包看下游：某个 Bundle 或资源组里包含哪些资源，它们分别属于哪些模块，哪些资源占比最高，哪些链路最深，哪些内容不应同包。只看上游能解决个案，却难以做包体治理；只看下游能知道哪个包大，却难以定位哪条引用链造成问题。成熟工具应同时支持两种查询。

第三步是把依赖风险分级。错误依赖是业务边界明显不该发生的引用，例如活动 A 引用活动 B 的私有资源；重依赖是单条链路带入过大体量，例如一个轻量界面拖入整套高分辨率图集；脆弱依赖是当前能运行但未来变更风险高，例如多个模块依赖一个频繁修改的公共 Prefab；传播依赖是热更新中最危险的类型，一个小资源变更会连带多个包更新。不同风险的处理方式不同：错误依赖应阻断或立即修复，重依赖需要评估拆分收益，脆弱依赖需要明确 owner 与变更规则，传播依赖要结合补丁策略重设共享边界。

第四步是治理 Prefab 嵌套。Prefab 复用能提升制作效率，但也容易把结构复用误变成静态依赖复用。一个活动按钮复用大厅按钮 Prefab，表面上节省制作成本，实际可能拖入大厅图集、动效、音效、特效节点和默认动画控制器。正确做法不是禁止复用，而是拆开“编辑期便于预览的结构”和“运行时必须静态绑定的依赖”。编辑期可以通过预览模板或装配工具保持可视化，运行时则通过资源清单、插槽、弱引用或按需加载绑定表现内容。这样既保留制作效率，也控制依赖传播。

第五步是治理材质、Shader、图集和字体。它们看起来像底层资源，实际常常是依赖污染源。公共材质可能引用平台不需要的贴图，图集可能混入活动图标，字体可能带入大字符集和 fallback 字体，Shader Variant 可能被错误保留。治理这些资源时，重点不是把它们都私有化，而是明确共享理由、使用范围、变更频率和拆分边界。公共资源越底层，越需要审计，因为它的每一次失控都会被更多模块放大。

第六步是治理配置资产。ScriptableObject、表格导出的配置资产、关卡索引和玩法清单经常被误认为只是数据，但只要字段中保存了 Prefab、Texture、AudioClip 或其他 UnityEngine.Object 强引用，它们就会参与构建依赖。应区分纯数据字段、强资源引用字段和资源标识字段。核心常驻资源可以强引用；条件性资源、热更资源、未开放资源和按需资源更适合使用资源 ID、地址或受控弱引用。弱引用不是把风险推到运行时，而是要配套构建期校验，检查资源是否存在、归属是否正确、是否越权进入资源组。

第七步是让打包单元对齐运行时单元。资源组不应只按照文件夹划分，也不应只按照资源类型划分，而应结合业务入口、加载阶段、释放阶段和补丁粒度。首包资源、常驻资源、场景资源、活动资源、角色资源、UI 资源、可选下载资源的生命周期不同，它们的依赖边界也应不同。若一个 Bundle 在运行时总是被局部使用，却包含多个生命周期不同的资源，说明分组可能过粗；若一个业务入口需要启动大量细碎请求，说明分组可能过细。依赖优化不是越拆越好，而是让拆分粒度与生命周期匹配。

第八步是建立构建门禁。门禁不应只统计总包体大小，还应检查跨模块依赖、重复打包风险、公共资源增长、热点 Bundle 变化、补丁传播范围、依赖链深度、资源组越权和配置资产强引用。门禁结果可以分为阻断、警告和例外。阻断项用于确定错误，例如活动私有资源被其他模块引用；警告项用于提示需要评审的问题，例如公共图集增长过快；例外项用于经过确认的特殊资产。没有门禁，依赖治理会退化成事后排查；没有例外机制，门禁又会逼迫团队绕过规则。

第九步是保留优化前后对比。每次拆分共享图集、移除错误引用、调整资源组、修改配置引用方式，都应记录包体变化、补丁传播变化、加载请求变化、内存驻留变化和卸载后残留变化。依赖优化很容易陷入“结构更干净但收益不明确”的状态，前后对比能帮助团队判断某项重构是否值得。若拆分带来的收益很小，却显著增加请求数量和维护复杂度，就不应把它视为成功优化。

一个简化的依赖审计流程可以这样表达：

```text
for each changed_asset:
    collect direct_dependencies
    expand transitive_dependencies
    map dependencies to owner, bundle, lifecycle
    report cross_module_edges
    report heavy_edges
    report patch_propagation
    block illegal_edges
```

这段伪代码的重点不在实现细节，而在审计顺序：先展开依赖闭包，再映射归属、打包和生命周期，最后判断风险。只统计文件大小或只列出直接引用，都不足以支撑正式的资源依赖治理。

### 进阶讨论
依赖优化存在一个常见反对意见：拆分会增加复杂度，甚至导致加载请求变多。这个反对意见成立。过度拆分会带来更多资源组、更多句柄、更多版本关系、更多网络请求和更复杂的调试成本。依赖治理的目标不是把所有链路拆到最细，而是让依赖结构与业务生命周期一致。如果两个资源总是一起加载、一起更新、一起释放，把它们拆开未必有收益；如果两个资源只是在制作期一起预览，运行时却生命周期不同，就应该避免强绑定。

另一个容易被忽视的现实限制，是内容生产效率。美术和策划需要直观预览，TA 需要维护可理解的模板，程序需要可控的加载单元。如果依赖规范要求所有资源都通过复杂地址和运行时装配才能看到结果，制作效率会明显下降，团队可能会绕过规则。更合理的做法是把编辑期体验和运行时依赖分离：编辑期提供组合预览、校验提示和自动装配；构建期根据规则生成运行时清单；运行时按生命周期加载真实资源。这样规范不会与生产效率正面对抗。

共享资源的退出机制也很关键。许多公共图集、公共材质和公共 Prefab 失控，不是因为它们进入共享层时完全错误，而是因为项目演进后用途已经变化，却没有人清理。共享层需要定期审计：是否仍被多个模块稳定使用，是否已有更小的替代共享单元，是否因为历史兼容保留了无效资源，是否变更频率过高。共享层如果只有进入没有退出，最终会变成长期依赖负债。

热更新场景下，依赖优化必须把补丁传播作为一等指标。一个资源放在公共包里，也许能减少初始重复，但如果它频繁变化，每次都会触发大范围下载，那长期成本可能高于局部重复。反过来，某些真正稳定的基础资源即使体量不小，也适合公共化，因为它们能减少重复并保持低变更。共享与私有不是绝对优劣，而是要在初始包体、增量补丁、运行时驻留和维护成本之间取平衡。

运行时内存验证应追踪保留链。仅仅看到某张贴图仍在内存中，不足以判断问题；需要知道它由哪个加载句柄持有，是否仍被对象池中的对象引用，是否被静态缓存保留，是否通过公共材质被其他模块间接持有，是否因为异步任务未完成而延迟释放。依赖工具如果能从构建依赖延伸到运行时保留链，团队就能把“为什么打进包”和“为什么卸不掉”连接起来，减少盲目释放和重复加载。

依赖治理还需要面对版本节奏。大型项目不适合一次性全库重构，因为资源数量大、风险高、验证成本重。更稳妥的顺序是先治理公共层，再治理热点模块，最后治理长尾资源。公共层的错误会被全局放大，热点模块直接影响玩家常见路径，长尾资源则适合在版本间持续收敛。按照收益和风险排序，依赖优化才不会变成漫无边界的清扫工程。

典型案例可以说明依赖问题的本质。假设一个活动入口按钮复用大厅主界面的公共按钮 Prefab。该 Prefab 直接引用大厅 UI 图集、点击音效、动画控制器和一套高亮特效。活动包本来只需要一个小图标和按钮底图，却因为这个复用关系把大厅公共资源带入活动包。优化方案不是简单压缩大厅图集，而是拆开按钮结构和大厅表现：活动按钮使用轻量按钮基类，图标、底图、音效和动效由活动资源组按需绑定；大厅按钮保留大厅专属表现，但不作为所有按钮的静态依赖模板。这个调整通常比压缩几张图更有效，因为它改变了依赖方向。

另一个典型案例是配置表带入未开放玩法资源。一个玩法配置资产为了编辑方便，直接引用所有玩法入口图标、预览 Prefab、引导特效和音频。即使当前版本只开放其中一部分，构建系统也可能把全部强引用资源带入首包。更合理的设计是首包只强引用已开放玩法的必要资源，未开放玩法使用资源 ID 或独立资源清单，并在功能开放时通过热更新提供。配置仍然保持统一管理，但资源依赖不再无条件全量进入。

这些案例共同说明，依赖优化不是资源压缩的附属工作，而是架构治理的一部分。它要求团队同时理解内容生产、构建系统、加载系统、热更新机制和运行时生命周期。任何只从单点文件大小出发的优化，都容易错过真正的成本传播路径。


依赖治理还需要一组稳定的指标语言。仅仅说“包体变大”或“依赖太乱”无法推动协作，必须把问题拆成可比较的指标，例如资源组体积、依赖闭包体积、跨模块依赖数量、公共层增长率、重复打包风险、单资源变更传播包数、加载入口拉起资源数、退出后残留资源数、资源组内 owner 混杂度、配置资产强引用数量。这些指标不要求一开始全部自动化，但至少应成为评审和复盘时的共同语义。指标的意义不是制造报表，而是让团队知道某次优化究竟改善了哪一种成本。

工具数据模型也应围绕依赖图设计，而不是围绕文件列表设计。每个节点至少应记录资源路径、资源类型、所属模块、owner、资源组、平台、是否首包、是否常驻、变更频率和历史体积；每条边至少应记录引用方向、引用来源、是否强引用、是否运行时按需引用、是否跨模块、是否进入构建产物。具备这些信息后，工具才能回答更有价值的问题：某个资源为什么进入首包，某次改动会传播到哪些包，某个模块退出后哪些资源仍被其他模块保留，某个公共图集是否已经不再适合公共化。没有这些维度，依赖分析只能停留在“谁引用了谁”的低层查询。

异常处置流程应尽量短而清楚。第一步确认异常类型，是错误依赖、重依赖、脆弱依赖还是传播依赖；第二步定位责任边，而不是只定位最终的大资源；第三步给出可选方案，包括私有化、拆分、弱引用、延迟绑定、迁移到更合适的共享层或调整打包组；第四步评估收益与副作用，包括包体、补丁、加载请求、运行时驻留和制作效率；第五步在版本中落地并保留前后对比。这个流程能避免依赖优化变成纯经验争论，也能避免每次问题都从头排查。

还要避免把依赖治理简化成程序工具问题。工具可以发现异常，但资源边界通常由制作流程决定。图集怎么合并、Prefab 怎么复用、配置字段怎么设计、活动资源怎么归档、公共层由谁维护，这些决策都发生在日常内容生产中。若资源规范只在构建失败时才出现，团队会把它视为阻碍交付的后置检查；若规范在资源创建、评审、接入和复盘中持续出现，它才会成为生产方式的一部分。依赖优化最难的部分不是扫描脚本，而是把正确的依赖意识嵌入资源流转过程。

在大型项目中，依赖治理最终应形成分层责任。业务模块负责自己的私有资源不越界，公共层维护者负责共享资源的进入与退出，构建系统负责发现结构异常，运行时资源系统负责验证加载与释放，版本管理负责评估补丁传播。任何一个环节缺位，依赖图都会重新变得不可控。清晰的责任边界能让问题被就地解决，而不是每次都堆到版本末期由少数人集中救火。

### 总结
资源依赖关系优化的核心，是把不可见的引用链变成可解释、可审计、可约束的工程对象。它直接影响包体、补丁、下载、加载、驻留和卸载行为。若依赖边界失控，项目就会持续遭遇小功能拖大包、小改动出大补丁、退出后卸不掉的运行时问题；若依赖边界与业务、打包和生命周期一致，资源系统就能从被动承受膨胀，转向主动治理成本。

成熟的依赖治理应做到几件事：资源有归属，依赖可追踪，共享有边界，配置引用受控，打包单元与运行时单元对齐，构建门禁能发现异常，运行时验证能解释保留链，版本复盘能衡量收益。它不是一次性清理，也不是越拆越细，而是在可维护复杂度内，让资源成本沿着正确的业务边界流动。
