# 大型项目的资源命名与组织规范

### 背景

大型 Unity 项目中的资源问题，表面上常表现为包体膨胀、依赖失控、资源难找、重复制作、热更新边界不清、外包接入困难和跨团队协作摩擦。但这些问题的共同根源往往非常基础：资源没有清晰身份。命名随意、目录语义混乱、共享与私有边界模糊、临时资源混入正式资产、源文件与生成物混放，最终会让构建系统、资源系统、审计工具和团队协作都难以稳定运行。

在项目早期，资源少、团队小、上下文共享充分，即使命名不严谨，大家也能靠记忆和口头沟通解决问题。一个 Prefab 放错目录，一个贴图命名含糊，一个临时测试资源留在工程里，短期未必造成明显事故。但当项目进入中后期，资源数量上升到数万级，活动版本持续迭代，多平台和多语言并行推进，外包团队开始交付内容，热更新和构建流水线要求稳定时，早期的小混乱会集中放大。

资源命名与组织规范的真正作用，不是让仓库看起来整齐，而是为资源建立可解释、可追踪、可治理的身份体系。一个资源的名称和路径应帮助团队判断它属于哪个模块、服务什么用途、是否可共享、是否有平台或语言变体、处于什么生命周期、是否可以热更新、是否可以删除、是否属于生成物。只要这些信息无法稳定表达，资源管理就会长期依赖个人记忆。

因此，大型项目的资源规范必须同时服务人和工具。它既要让新成员、外包团队、策划、美术、TA、客户端和测试能够理解资源归属，也要让构建脚本、依赖审计、热更新分组、资源扫描、命名检查和发布流水线可以自动处理。只给人看的规范很容易随人员变动失效；只给机器看的规范又会让协作成本上升。成熟规范必须在可读性和可执行性之间取得平衡。

本文讨论大型项目资源命名与组织规范的设计原则和落地方式。重点不是给出一套唯一命名表，而是说明为什么命名要表达身份，为什么目录要表达归属，为什么共享资源必须有准入机制，为什么生命周期信息要制度化，为什么规范必须进入工具链，以及如何处理历史资源和例外情况。

### 核心原理

资源命名的首要目标不是简短，而是表达身份与边界。一个正式资源名至少应帮助团队判断模块归属、资源类型、具体用途、变体信息和生命周期状态。必要时，它还应表达平台、语言、品质档、皮肤、活动或审核版本。命名不是越长越好，但必须足够稳定、足够明确，能够被人理解，也能被脚本解析。

目录结构的本质，是让资源归属成为显式事实。目录不应只按“谁制作”或“资源来自哪里”划分，因为构建、热更新和运行时系统真正关心的是资源服务哪个业务模块、是否共享、是否属于活动、是否是平台差异资源、是否是生成物、是否处于归档或废弃状态。目录首先应回答“这是哪个模块的、给谁用”，再回答“它是什么类型”。

共享资源必须是显式共享，而不是默认所有人都能引用。许多项目会把 `Common`、`Shared`、`Public` 目录变成无底洞。任何模块只要觉得某个资源“以后可能也会用”，就顺手放进去。短期看方便，长期会导致共享目录膨胀、所有权不清、依赖边界模糊、变更影响不可预测。共享资源应有准入条件、负责人、变更审查和退出机制。

模块私有资源应尽量贴近业务模块。代码模块、策划功能和资源目录长期错位，会显著增加定位成本。某个玩法模块的贴图、材质、Prefab、动画、特效和 UI 头像如果散落在多个全局目录里，后续任何修改都很难判断影响范围。更稳妥的方式是让模块私有资源在模块目录内闭环，再按类型细分。这样代码、配置和资源的责任边界更一致。

资源类型规范要与运行时系统对齐，而不只是与制作流程对齐。美术制作会关注贴图、模型、材质、动画；运行时系统则关注 UI、角色、特效、关卡、活动、公共表现和流式内容。规范如果只按制作类型组织，后期构建和维护会频繁跨目录寻找关联资产。大型项目需要同时考虑制作结构和运行时结构，尽量让两者在可接受范围内对齐。

变体命名必须正规化。平台、语言、品质档、地区审核、皮肤、活动主题、节日包装、渲染管线差异等都会产生资源变体。如果变体只靠目录混放、手工备注或个人习惯维护，系统很快会出现错用、重复、漏打包和热更新边界不清。变体应使用受控后缀、固定段位或元数据表达，并限制组合方式。

生命周期信息必须纳入资源规范。资源不是只有“存在”一种状态。大型项目中至少会存在正式资产、预埋资产、临时调试资产、活动周期资产、待废弃资产、历史归档资产、自动生成资产和本地缓存资产。若这些状态不能被目录、命名、清单或元数据表达，就会出现不敢删、误删、生成物污染源文件等问题。

源资源、生成资源和缓存资源必须严格分离。图集产物、烘焙结果、导表结果、Shader Variant、自动生成配置与人工维护源文件混放，会让版本管理和审计非常痛苦。团队可能误改生成物，也可能在构建时覆盖人工内容。规范必须明确什么可以进入版本库，什么只存在于构建产物或本地缓存，什么由流程生成且禁止手工编辑。

规范必须工具化。只写在文档里的规范很难长期有效。命名扫描、路径合法性检查、共享目录准入检查、变体格式校验、临时资源扫描、生成物误提交检测、跨模块引用审计，都应逐步接入提交、构建或评审流程。工具不一定一开始就阻断所有问题，但至少要能稳定报告和提醒。

### 设计思路

资源规范设计应先定义资源身份模型，再反推命名结构。一个资源名需要表达哪些维度，取决于项目如何治理资源。常见维度包括模块、用途、类型、变体、状态。模块表达归属，例如 `battle`、`home`、`guild`、`shop`；用途表达功能语义，例如 `skill_button`、`reward_icon`、`boss_warning`；类型表达资源类别，例如 `prefab`、`tex`、`mat`、`anim`、`audio`；变体表达平台、语言、品质或皮肤；状态表达临时、归档、废弃或生成物。

一个可执行的命名模型可以是“模块_用途_类型_变体_状态”。这不是要求所有文件都写满五段，而是规定语义位置。轻量资源可以省略不需要的变体段，临时资源可以通过目录表达状态，生成物可以通过生成目录表达身份。关键是团队必须明确哪些语义由文件名表达，哪些由路径表达，哪些由元数据或清单表达。表达位置稳定后，工具才能解析。

目录模型建议区分业务层、共享层、平台层和生成层。业务层按功能模块组织资源，服务日常开发和责任归属；共享层只存放经过审查、具备明确负责人的公共资源；平台层承载必须按平台、渠道、语言或审核版本差异化维护的资源；生成层存放图集、烘焙、导表、Shader Variant 等流程产物。这样的结构比全局 `Textures`、`Prefabs`、`Materials` 更适合长期协作。

业务层内部可以再按资源类型组织。例如 `Battle/Prefabs`、`Battle/Textures`、`Battle/Animations`、`Battle/Effects`、`Battle/Audio`。这保留了制作效率，也不破坏模块归属。资源类型适合作为模块内的二级或三级结构，而不适合作为整个项目的一级结构。一级结构应优先表达治理边界。

共享资源目录必须设置准入门槛。资源进入共享层前，应确认至少两个以上稳定模块需要复用，资源语义足够通用，负责人明确，变更影响可评估，版本兼容要求清楚。共享资源的命名应避免绑定短期活动或具体业务场景。例如一个通用按钮背景应表达视觉层级和组件角色，而不是使用某次活动代号。共享不是临时复用的借口，而是正式资产治理决策。

变体表达应使用受控词表。平台可以统一为 `android`、`ios`、`pc`；语言可以统一为 `zh_cn`、`en`、`ja`；品质可以统一为 `low`、`mid`、`high`；状态可以统一为 `tmp`、`archive`、`deprecated`、`generated`。受控词表的意义是减少同义词和个人缩写。没有受控词表，脚本扫描、搜索和外包协作都会不稳定。

禁用词也应进入规范。`new`、`old`、`final`、`copy`、`test`、`use`、`ok` 这类词在正式资产中几乎没有治理价值，只会制造歧义。它们可以存在于临时隔离目录，但不应进入正式构建资源。类似地，个人姓名缩写、口头代号和阶段性简称也不应出现在正式资产名中，除非它们已经成为项目公开词表的一部分。

资源移动和重命名必须有迁移流程。大型 Unity 项目尤其要注意 `.meta` 和 GUID 稳定性。随意移动、删除再导入或批量重命名可能导致 Prefab 断链、引用丢失、图集重打、补丁异常和多人分支冲突。迁移应先建立映射表，确认引用范围，分批执行，迁移后做引用扫描和构建验证，最后清理旧路径。规范不是鼓励随意重命名，而是让重命名有安全路径。

临时资源、废弃资源和归档资源应有独立通道。临时资源应限制在临时目录，不得进入正式包；待废弃资源应有观察期、负责人和删除计划；归档资源应只读保存，避免继续被新功能引用。项目只会新增资源而没有退出机制，最终一定会积累大量不敢删除的历史内容。规范必须覆盖资源退出，而不是只规定资源进入。

工具化落地可以分阶段。第一阶段只做扫描报告，列出命名不合法、路径不合法、禁止词、临时资源、共享目录无负责人等问题。第二阶段把高风险问题接入构建告警。第三阶段将正式包中的临时资源、跨模块私有引用、生成物误提交等问题设为阻断。循序渐进比一开始全量阻断更容易让团队接受。

外包交付也应有独立模板。外部团队应拿到目录模板、命名示例、禁止词、源文件与引擎文件分离规则、贴图和 Mesh 导出要求、变体表达方式、临时资源处理方式和问题反馈格式。外包资源不应等进入项目后再由主团队人工整理。入口越规范，后续返工越少。

历史包袱需要分阶段处理。新规范不可能一次性改完所有旧资源。更现实的方式是：新资源强制遵守规范；旧资源在修改、迁移、重打包或进入共享层时逐步改造；高风险共享资源优先治理；低风险长尾资源标记为历史目录；工具同时兼容旧路径但鼓励新命名。规范成熟不是仓库立刻完美，而是旧系统持续向健康状态收敛。

### 进阶讨论

最常见的反模式，是按资源类型建立巨大仓库。全项目只有 `Textures`、`Models`、`Prefabs`、`Audio` 这类一级目录，看起来简单，实际切断了业务归属。任何一次业务修改都需要跨多个目录寻找资源，所有权和依赖边界都越来越模糊。资源类型分类必要，但更适合作为模块内部结构，而不是项目顶层结构。

第二个反模式，是把公共目录变成无所有权区域。共享资源如果没有负责人，所有模块都能使用，却没有模块愿意承担变更风险。共享层应比业务层更严格，而不是更随意。越是被多人依赖的资源，越需要稳定命名、版本意识、变更审查和影响评估。

第三个反模式，是用个人缩写和口头代号命名正式资源。小团队内部可能都理解某个简称，但新成员、外包团队、自动化工具和半年后的维护者未必理解。正式资产应使用团队公开认可的词表。局部口头语言不能进入长期资产身份体系。

第四个反模式，是让临时资源混入正式构建。`test`、`tmp`、`copy`、`final2` 这类资源一旦进入正式目录，就很难判断是否可删。更糟糕的是，它们可能被 Prefab 或配置间接引用，成为构建中的隐形依赖。临时资源必须有隔离区，并通过构建扫描防止进入正式包。

第五个反模式，是将生成物当作源文件维护。自动生成资源应由流程重建，而不是由人手工编辑。生成物可以进入构建产物或缓存目录，但应尽量避免与源资源混放。若确实需要提交生成物，也要清楚标记其来源、生成规则和禁止手工修改范围。

命名规范还要处理“过度规范”的风险。过深目录、过长命名、过多段位、过严阻断，可能让团队为了满足规则而降低效率。规范应服务治理，不应变成形式主义。评估规则是否合理，可以看新成员是否能执行、外包是否能理解、工具是否能检查、错误是否能修复。如果规则必须依赖大量口头解释，说明它还不够工程化。

规范评审应关注可执行性，而不是只看规则是否完整。可以抽取真实资源做演练：一个新活动 UI、一组角色模型、一批平台差异贴图、一份待废弃旧资源，让不同成员按规范判断路径和命名。如果结果不一致，应先修正规范和示例，而不是要求大家靠默契对齐。


还应为资源规范建立“责任可追踪”机制。大型项目中，资源常常被多人、多模块、多版本共同使用，如果没有 owner 信息，问题出现后很难判断谁有权修改、谁负责验证、谁承担回滚。owner 不一定必须写在文件名中，可以通过目录负责人表、资源清单、标签系统或构建数据库维护。关键是任何共享资源、平台差异资源、历史归档资源和高风险活动资源，都必须能追踪到负责团队或负责模块。

依赖边界也应纳入组织规范。一个模块可以引用公共资源，但不应随意引用另一个模块的私有资源。若确实需要复用，应先把资源提升到共享层，或建立明确的依赖关系。否则，模块之间会通过资源引用形成隐性耦合，后续某个模块删除或调整资源时，另一个模块可能在构建或运行时突然出错。资源目录不仅是存放结构，也是依赖边界的表达。

在热更新项目中，命名与组织还会影响补丁粒度。若活动资源与常驻资源混放，共享资源与模块私有资源混放，生成物与源文件混放，构建系统很难稳定判断本次变更应该进入哪个包。一个小改动可能牵连大范围资源重打包，导致补丁体积膨胀。资源规范如果从一开始就表达模块、生命周期和变体，就能显著降低热更新差异计算的复杂度。

资源规范还应配套“删除安全”流程。删除资源前，应通过引用扫描、构建验证、运行时路径检查和历史版本影响评估确认安全。对于可能被配置表、脚本字符串、Addressables 地址、YooAsset Location 或外部清单引用的资源，不能只依赖 Unity 引用扫描。删除流程越正式，仓库越敢清理历史资源；没有删除流程，资源库只会不断膨胀。

最后，规范应有版本号和变更记录。资源规范本身也会迭代，新增平台、新增语言、新增构建方式、新增资源类型都会改变规则。若规范变更没有版本管理，团队很容易出现新旧规则混用。每次规范变更都应说明影响范围、迁移要求、兼容策略和工具更新时间。这样规范才是可维护的工程资产，而不是一次性文档。


规范落地还需要度量指标。可以跟踪命名违规数量、临时资源进入正式包次数、共享目录无 owner 资源数量、跨模块私有引用数量、历史资源清理数量、外包交付一次通过率、资源重命名导致的引用问题次数、补丁异常膨胀次数。这些指标能说明规范是否真的改善了工程状态。如果规范只让文档变厚，却没有让违规减少、定位更快、补丁更稳定，那它就没有真正发挥作用。

落地节奏应避免一次性压垮团队。更稳妥的路径是先治理新增资源，再治理高风险共享资源，然后逐步迁移历史资源；先让工具报表可见，再把高风险项接入构建阻断；先提供示例和模板，再要求外包和新成员执行。资源规范是长期治理，不是一次整理仓库。越是大型项目，越需要把规范当成持续演进的系统，而不是短期清洁行动。

对于已经混乱的项目，第一目标也不应是立刻“变整齐”，而是建立可控边界。先冻结新的不规范入口，建立资源身份模型，找出最危险的共享目录、临时资源、生成物混放和跨模块引用，再逐步迁移。只要新增问题被控制住，历史问题就有机会被分批消化；如果新增问题仍在持续产生，再大规模整理也会很快回到混乱状态。


规范的最终目标不是约束创作自由，而是让创作结果能被长期生产系统稳定承接。只要这一点被团队理解，命名和目录规则就不再是额外负担，而是降低返工、误删和发布事故的基础保障。

### 总结

大型项目的资源命名与组织规范，本质上是在为资源建立长期稳定的身份系统。它既服务人，也服务工具；既影响日常协作，也影响构建、热更新、依赖审计和历史治理。只要资源的归属、用途、类型、变体和生命周期被清楚表达，团队就能更快定位资源、更安全控制依赖、更稳定推进版本演进。

成熟规范不会停留在文档中，而会进入目录结构、命名词表、共享准入、例外登记、迁移流程、外包验收和自动化校验。规范的价值不是增加管理成本，而是减少长期不确定性。资源越多、团队越大、版本越长，越需要让资源身份从“人脑记忆”变成“工程事实”。
