# 企业安全代理对Agent使用体验的讨论

## 摘要
公司开始使用"龙虾"（类OpenClaw的Agent平台），但为了安全在中间套了一层安全代理和Desktop桥接应用，导致使用体验极差。本文记录了该架构的分析、暴露的问题和最终判断——安全、能力、体验三者在此架构下形成了不可能三角。

## 正文

### 架构现状

```
[本地文件] ←→ [Desktop桥接应用] ←网络→ [安全代理] ←→ [服务器OpenClaw]
                      ↑                            ↑
             "顺手维护的小组"                "安全部门管控"
```

OpenClaw部署在服务器上，绑定到每个员工。员工通过办公账号连接到服务器上的OpenClaw实例。为了安全，中间套了一层安全代理进行审计和流量管控。Desktop桥接应用负责让云端Agent具备操作本地文件/命令的能力。

### 已暴露的问题

#### 一、沙箱隔离导致的Git推送问题
OpenClaw运行在沙箱用户下，与电脑主用户不一致。Git会拒绝沙箱用户的指令。虽然桥接软件给了被套了一层的命令执行能力，但实际执行会被拦截。安全代理把正常Git命令也拦了。

#### 二、Token安全反模式
Git Token原本配置在用户环境变量里——这是标准做法。但沙箱访问不了用户变量，Agent读不到。被迫把Token写在更不安全的地方：明文写在skill或py脚本里。结果是Token泄露风险反而增大。更讽刺的是，安全代理防住了git push命令，但管不住requests直接调GitHub API。

#### 三、Desktop应用的显示bug
对话界面偶尔无法显示Agent的思考和工具调用日志。OpenClaw本身就经常卡住。看不到执行进度意味着无法区分"Agent在思考"还是"真的卡住了"还是"显示渲染崩了"。这种不确定性焦虑比单纯慢更消耗心力。

#### 四、维护团队问题
Desktop应用由"抽调的一个小组"维护，该小组可能还要干别的工作，"顺手维护"。团队动力不足，bug修复周期长。OpenClaw在快速迭代，桥接层永远在追赶。

### 架构再思考

Desktop的初衷是给云端Agent提供本地文件/命令执行能力。桥接方式为：Agent调用proxyread这类自定义指令 → Desktop收到 → 本地执行 → 结果返回云端。

但安全性上来说，不管怎么桥接，文件内容都会同时存在客户端和云端沙箱里。这层桥接的真正作用可能只是"让OpenClaw的源文件远离用户"——用户看不到也改不了Agent的Prompt和技能。

### 核心矛盾：沙箱身份死局

- Desktop如果以当前登录用户身份跑 → 安全隔离名存实亡
- Desktop如果以沙箱用户身份跑 → Git用不了、环境变量读不到
- 白名单命令列表 → 维护成本高，永远追不上需求

在需要完整本地能力的场景里，远程执行+沙箱桥接的方式，理论上就存在不可能三角——安全、能力、体验三者不可兼得。

### 最终判断

企业Agent可能也就这样了。沙箱用户身份这个底层限制动不了，上面再怎么优化都是打补丁。本质是"企业买单的安全，开发者承担代价"——安全团队的考核指标里没有"开发者体验"这一项。而且这套方案也并不真的安全：Token被逼到明文写在脚本里，安全代理防住了git push但拦不住requests直调API。
