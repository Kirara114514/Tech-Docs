| 术语 | 含义 |

## 一、系统背景与设计目标

### 1.1 需求来源

在角色扮演场景中，用户期望的不只是"和一个 AI 聊天"，而是一个**有内部关系的多角色世界**。这个世界的核心需求包括：

- 多个角色 Agent 各自拥有独立人格、记忆和关系网络
- 角色之间能够自发通信——不是用户逐一指挥，而是角色基于自身动机主动联系彼此
- 用户切换聊天对象时，新对象能感知"刚才别人跟他聊了什么"
- 所有对话都能沉淀为可检索的长期记忆

### 1.2 核心挑战

QwenPaw 是一个单会话（single-session）Agent 平台。每个 Agent 一次只能绑定一个 session，不存在跨 session 共享上下文的原生机制。这带来了几个根本性约束：

1. **Agent 无法跨 session 操作**：一个 Agent 在回复用户时，无法同时向另一个 Agent 的 session 写入消息
2. **无 session 级别 hook**：平台插件系统仅支持启动/关闭/控制命令级别的钩子，不存在"收到用户消息时执行"的 pre-hook
3. **Session JSON 不对称持久化**：Agent 间通信的 session 文件只存在于被调用方的工作区，调用方不保存
4. **Channel 推送的单向性**：通过平台 channel 机制推送的消息不进入 Agent 的 session JSON，Agent 在后续对话中无法知道自己发过什么

### 1.3 设计目标

在上述约束下，设计一套完整的多 Agent 协作系统，满足：

| 目标 | 含义 |
|------|------|
| 独立人格 | 每个角色 Agent 拥有自身的 SOUL、PROFILE、AGENTS 配置文件 |
| 自发通信 | 角色之间能按通信协议主动联系彼此 |
| 记忆闭环 | 所有对话（用户↔角色、角色↔角色）都能进入长期记忆 |
| 记忆感知 | 角色在与用户对话时能感知其他角色最近的通信内容 |
| 隐私分级 | 记忆条目按隐私等级标注，通信时按阈值过滤 |
| 自动化调度 | 通过定时任务驱动角色间自发互动 |

## 二、Agent 架构：四层配置模型

每个角色 Agent 由四个配置文件定义。这种分层设计将"不变的事实""可变的人格""执行规则""通信协议"解耦。

### 2.1 四层配置

| 文件 | 职责 | 更新频率 |
|------|------|---------|
| `PROFILE.md` | 稳定事实：身份、年龄、家庭关系、路径索引 | 很少 |
| `SOUL.md` | 人格内核：情绪逻辑、关系动力、深层动机 | 偶尔 |
| `AGENTS.md` | 执行规则：互动口吻、隐私叙事触发规则、行为边界 | 偶尔 |
| `agent通讯skill.md` | 通信协议：如何读对方记忆、如何构造消息、session 路由 | 随通信架构升级 |

### 2.2 隐私分级系统

每个角色的 AGENTS.md 中定义了隐私叙事处理规则，核心机制如下：

- 每条记忆条目标注 `privacy=0.00-1.00` 的值，越高越私密
- 日常对话 → `privacy=0.10-0.35`
- 亲密互动 → `privacy=0.40-0.60`
- 高度私密内容 → `privacy≥0.85`，仅在特定触发条件下展开
- 家人通信中禁止高隐私内容——这是硬约束

通信前必读协议要求：通信方从对方 memory 中读取时，按随机生成的 `privacy_threshold` 过滤，阈值以上的记录不可见。

### 2.3 管家与工具人的角色分离

系统中有两个特殊 Agent 不属于角色层：

| Agent | 职责 | 有无角色人格 |
|-------|------|-------------|
| 管家 | 与用户直接协作：文档管理、系统维护、技术实现 | 有 |
| 工具人 | 定时调度管道：接收 cron 触发→读取上下文→构造系统消息→分发给角色 Agent | 无 |

工具人的核心设计原则是"中立管道"——不扮演、不闲聊、不发表意见。它只做数据搬运：从文件读取对话上下文和记忆摘要，填入固定模板，发送给目标角色 Agent。

## 三、通信系统

### 3.1 通信协议：agent通讯skill

每个角色 Agent 的工作区根目录下有一个 `agent通讯skill.md`，定义了完整的家人通信流程。

通信流程分为五个阶段：

```
阶段①  用户 ↔ 角色A（正常聊天）
         ↓ 用户要求"去问问B"，或角色A自主想联系家人
阶段②  执行「通信前必读」协议
         ↓ 读 B 的 memory 文件，至少 10 条尽量 20 条，按隐私阈值过滤
阶段③  构造消息（固定模板：发送者、接收者、阈值、对方近况、联系原因）
         ↓
阶段④  通过 chat_with_agent 发送，收到 B 的回复
         ↓
阶段⑤  用自己的话告诉用户 B 说了什么
```

### 3.2 通信前必读协议

这是整个记忆感知系统的基础。每次通信前，角色 A 必须：

1. 随机生成 `privacy_threshold=0.00-1.00`
2. 用 `read_file` 直接读取 B 的 memory 文件的**绝对路径**（不用模板变量，避免 Agent 无法正确替换）
3. 只提取 `privacy ≤ threshold` 的记录
4. 至少收集 10 条，尽量 20 条；不足时向前追溯最多 7 天
5. 严禁用 `chat_with_agent` 代替 `read_file` 获取对方记忆

### 3.3 Session 路由：固定 session_id

Agent 间通信使用 `chat_with_agent` 工具，每次调用指定固定的 `session_id`：

```
family-{A的agent_id}-{B的agent_id}
```

如 Agent A 联系 Agent B 时使用 `family-A_id-B_id`。

固定 session_id 的好处：
- 通信历史可追溯，同一个关系对的对话累积在同一文件中
- 心跳系统可按 session 文件名模式匹配，自动发现所有通信记录
- 避免 session 文件膨胀

### 3.4 工程发现：chat_with_agent session 的非对称持久化

经过实验验证，`chat_with_agent` 的 session JSON 文件**只存在于被调用方（目标 Agent）的工作区**，调用方不保存。这意味着：

- Agent A 调 `chat_with_agent(to_agent="B")` 后，session 文件写入 `B/sessions/`，不在 `A/sessions/`
- Agent B 调 `chat_with_agent(to_agent="A")` 后，session 文件写入 `A/sessions/`

这不是 bug——是平台的设计特性。要获取两个方向的完整对话，必须扫描**双方**工作区的 sessions 目录。心跳预处理器在设计时已考虑这种非对称性，采用双向覆盖策略。

## 四、自动化调度系统

### 4.1 架构演进

自动化调度经历了三个版本：

**v1（废弃）**：工具人→A→B 链式传递。A 收到系统消息后联系 B，B 再联系 C。问题：链式传递导致无限对话，且用户收不到任何通知。

**v2（废弃）**：工具人→A 做两件事——(1)联系一个家人 (2)通过 channel send 给用户发通知。问题：channel send 消息不进入 Agent 的 session JSON，Agent 在后续对话中不知道自己发了什么。

**v3（当前）**：工具人→A 做一件事——联系一个家人聊天一轮。对话内容由心跳系统自动扫描 session JSON 并同步到双方 memory。用户下次与任意角色聊天时，角色读取自己的 memory 就能感知之前的通信。

### 4.2 工具人的 cron 调度

工具人通过 QwenPaw 的 cron 系统实现定时触发：

- 每天凌晨 4:00：工具人运行 Python 脚本生成当天的通信任务分配方案（JSON）
- 任务分配：28-40 个通信任务均匀分布在全天，每次间隔 ≥10 分钟，每个角色每天 3-8 次
- 分配算法：偏差平方加权 + 随机抖动，避免每人次数完全相同
- 时间加权：凌晨降低权重，避免夜间骚扰

每个 cron 触发时，工具人执行的子流程：

```
cron 触发 → 工具人收到消息（含目标角色 ID）
    ↓
步骤 1：解析目标角色
步骤 2：读取目标角色的 heartbeat_pre_full.txt（预处理的对话摘要）
步骤 3：读取目标角色的 memory（最近 20 条）
步骤 4：获取当天天气（通过浏览器访问天气网站）
步骤 5：构造系统消息（含天气、对话上下文、记忆摘要、可选联系人列表）
步骤 6：submit_to_agent 发送（异步，不等待回复）
步骤 7：删除 cron 结束
```

### 4.3 异步分发：submit_to_agent vs chat_with_agent

工具人向角色 Agent 分发系统消息使用 `submit_to_agent`（异步）而非 `chat_with_agent`（同步）。原因：

- `chat_with_agent` 会阻塞等待角色回复，角色回复可能耗时数秒至数十秒，阻塞工具人的 cron 执行
- `submit_to_agent` 提交后立即返回，工具人可以马上删除 cron 结束，不占用平台资源
- 角色是否需要回复、回复什么内容，由心跳系统事后扫描处理

## 五、心跳记忆系统（v4）

### 5.1 设计动机

早期设计中，Agent 在每次回复后需要自己手动将对话写入 memory 文件。这带来了两个问题：

- **遗漏**：Agent 可能忘记写，或在角色扮演中优先回复用户而跳过写 memory
- **职责混乱**：记忆保存和角色互动耦合在一起，Agent 需要在"做自己"和"做记录员"之间切换

心跳系统的核心思想是**职责分离**——Agent 只负责互动，记忆更新由一个外部轮询进程统一管理。

### 5.2 心跳预处理器

心跳预处理器的核心是一个常驻 Python 进程（`heartbeat_watcher.py`），每 5 秒轮询一次所有关心的 session JSON 文件的修改时间。

**关心的文件范围**：

- 用户私聊 session：文件名包含 `telegram--{用户ID}` 的 JSON 文件
- Agent 间通信 session：文件名包含 `family-` 且不含工具人 ID 的 JSON 文件

**预处理流程**：

```
检测到 mtime 变化 → 等待文件大小稳定（防半写入 JSON）
    ↓
遍历每个关心的 session JSON → 提取纯对话文本
    ↓
过滤规则：
  - 跳过 system/tool/function 角色
  - 跳过工具人调度模板（含 "【系统消息】" 等关键词）
  - 跳过纯操作叙述（短文本 + 操作动词）
  - 跳过空 assistant 消息
    ↓
按 Agent 归属归类：
  - 用户私聊 → 按 session 文件所在 workspace 归属
  - Agent 间通信 → 文件名中出现的所有 agent_id 均为参与方
    ↓
去重 + 排序 → 每个 Agent 生成当前全量文本
    ↓
对比各 Agent 的上次已处理版本 → 生成增量（delta）
    ↓
增量不为空的 Agent → 通知
```

### 5.3 增量 diff 与防死循环

心跳系统面对的一个关键问题是：Agent 收到通知后写 memory，这个操作本身可能触发新的文件变更，导致死循环。

防护机制：

1. **增量检测**：只在新对话出现时才通知——Agent 自身的文件操作不会产生新的对话文本
2. **心跳消息过滤**：心跳系统发出的 `【SYSTEM OVERRIDE】` 消息在预处理阶段被关键词过滤
3. **通知间隔**：同一 Agent 两次通知之间至少间隔 30 秒
4. **Pending 队列**：被防抖跳过的增量不丢失，累积到下次通知时合并发送
5. **文件稳定等待**：检测到 mtime 变化后先等文件大小稳定再读取，防止读取半写入的 JSON

### 5.4 通知机制

心跳预处理器通过 QwenPaw CLI 向有增量的 Agent 发送通知：

```
qwenpaw agents chat --from-agent gCyY4j --to-agent {agent_id} \
  --session-id heartbeat-gCyY4j-{agent_id} \
  --text "【SYSTEM OVERRIDE - 心跳记忆同步】..."
```

通知消息采用 `【SYSTEM OVERRIDE】` 前缀，Agent 的通信协议将其识别为系统级指令而非普通聊天。消息内容是指令式的——读取 delta 文件、按时间戳追加到对应日期的 memory 文件、完成后只回复"已同步 X 条"。

每个 Agent 的 prev（已处理标记）独立管理——通知成功仅提交该 Agent 自己的状态，不影响其他 Agent。

### 5.5 Memory 文件结构

每个 Agent 的 memory 按日期分文件：`memory/YYYY-MM-DD.md`。

心跳系统按对话时间戳的日期前缀将条目写入对应日期的文件，确保跨天边界处理正确——23:55 和 00:05 的对话分别写入不同日期的文件。

## 六、工程教训

### 6.1 链式传递的失败

v1 架构中尝试让 Agent A 联系 B、B 再联系 C 的链式传递。失败原因：

- 每个 Agent 的回复都是一次完整的"思考-表达"循环，链式传递会导致指数级对话展开
- 中间 Agent 可能偏离原始意图，传递的信息逐级失真
- 用户无法追踪对话蔓延到了哪里

教训：Agent 间通信应该是一对一的、单轮的。复杂信息流应由系统层面（工具人 + 心跳）管理，而非 Agent 自行传递。

### 6.2 Channel 推送的不可靠性

v2 架构中尝试用 `qwenpaw channels send` 让 Agent 向用户推送通知。失败原因：

- `channels send` 是 channel 层的单向推送，消息到达用户但不进入 Agent 的 session JSON
- Agent 在后续对话中不知道自己发过什么通知
- 平台不支持 session 级别 hook 或跨 session 上下文共享

教训：所有需要 Agent 后续感知的操作，必须通过 session 内消息（`chat_with_agent` / `submit_to_agent`）实现。Channel 推送只适用于不需要 Agent 记忆的纯通知场景。

### 6.3 模板变量的不可靠性

早期 agent通讯skill 中写的是 `{B的workspace}/memory/YYYY-MM-DD.md` 这样的模板变量。实践中发现 Agent 无法正确替换这些变量——因为 Agent 不具备"变量求值"的编程能力。

解决方案：将所有路径硬编码为绝对路径。每个 Agent 的通信 skill 中列出它可能联系的每一个其他 Agent 的完整 memory 路径表。

### 6.4 Agent 配置丢失

`qwenpaw agents delete` + `create` 会导致 `agent.json` 中的 channel 配置（如 Telegram Bot Token）丢失。此后所有 Agent 的增删改走直接修改 `agent.json` 文件的路由，不再使用 delete/create 命令。

## 七、系统全景

### 7.1 数据流

```
用户 ──Telegram──→ 角色 Agent（互动、角色扮演）
                       ↓ 通信时读对方 memory
                       ↓ 通过 chat_with_agent 发消息
                   其他角色 Agent ←── 回复

工具人 ←── cron 定时触发
    ↓ 读预处理文件 + memory + 天气
    ↓ submit_to_agent（异步）
角色 Agent ←── 系统消息（天气、上下文、联系人列表）
    ↓ 自主选择联系人通信

心跳预处理器 ←── 轮询所有 session JSON（5秒间隔）
    ↓ 提取纯对话 → diff → 生成 delta
    ↓ qwenpaw agents chat（CLI）
角色 Agent ←── SYSTEM OVERRIDE 指令
    ↓ read_file delta → write_file memory
```

### 7.2 文件与进程

| 组件 | 位置 | 职责 |
|------|------|------|
| 角色配置文件 | `{workspace}/AGENTS.md, SOUL.md, PROFILE.md` | 人格与行为定义 |
| 通信协议 | `{workspace}/agent通讯skill.md` | 家人通信流程 |
| 心跳指令 | `{workspace}/HEARTBEAT.md` | 心跳触发时的执行步骤 |
| 对话预处理 | `heartbeat_watcher.py` | 常驻进程：轮询→预处理→通知 |
| 分配脚本 | `cron_plan_generator.py` | 每日通信任务随机分配 |
| 长期记忆 | `{workspace}/memory/YYYY-MM-DD.md` | 按日存储的记忆条目 |
| 会话记录 | `{workspace}/sessions/*.json` | QwenPaw 自动生成 |

### 7.3 职责分离原则

| 职责 | 执行者 |
|------|--------|
| 角色互动 | 角色 Agent |
| 记忆更新 | 心跳预处理器（py） |
| 定时调度 | 工具人 Agent + cron |
| 系统维护 | 管家 Agent |

Agent 不需要知道心跳的存在，不需要知道预处理器在运行，不需要在每次回复后手动写 memory。心跳系统和角色系统完全解耦——这是整个架构稳定性的基础。

## 八、总结

本系统在 QwenPaw 单会话 Agent 平台上，通过外挂轮询进程、固定 session 路由、增量 diff 比对、隐私阈值过滤、职责分离设计，构建了一个完整的多 Agent 角色扮演系统。

核心创新点：

1. **通信前必读协议**：每次 Agent 间通信前强制读取对方 memory，实现跨 Agent 记忆感知
2. **心跳预处理 + 增量通知**：用外部 Python 进程轮询 session JSON，生成增量后通过 CLI 通知 Agent 补写 memory——解决了 Agent 自觉写 memory 的不可靠性
3. **隐私分级 + 阈值过滤**：记忆条目按 0.00-1.00 标注隐私等级，通信时按随机阈值过滤，实现可控的信息暴露
4. **工具人中立管道**：将调度逻辑与人设解耦，工具人只做数据搬运，不参与角色互动
5. **职责分离**：谁互动、谁记忆、谁调度——三个系统独立运行，互不耦合

系统的局限在于依赖外部进程（heartbeat_watcher.py）常驻运行，且 memory 更新存在 5-30 秒的延迟（轮询周期 + 通知间隔）。未来如果 QwenPaw 支持 session 级别 hook，可以将心跳逻辑内嵌到平台内部，实现真正的事件驱动。
