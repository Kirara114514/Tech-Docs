# 五 Agent 角色扮演系统的上下文共享架构：从会话隔离到群体记忆的工程实践

### 背景
多 Agent 角色扮演系统的核心困难，不是让多个 Agent 分别开口说话，而是让它们在隔离会话中形成可信的群体连续性。单个 Agent 与用户对话时，系统只需要维护一条上下文链；多个 Agent 同时存在时，用户会自然期待它们彼此知道一部分共同事件，保留一部分私有记忆，并在后续交互中表现出稳定的关系和信息差。这个期待很接近人类社交，却与多数 Agent 平台的默认架构相冲突。

默认架构通常把会话视为隔离容器。用户与 Agent A 的对话、用户与 Agent B 的对话、Agent A 与 Agent B 的通信，往往属于不同 session。一个 session 中发生的事件不会自动进入另一个 session。隔离本身是合理设计，它能降低串线、泄露和上下文污染风险；但在群体角色系统中，隔离会产生“群体失忆”：某个 Agent 刚刚参与过跨 Agent 讨论，用户切换到它的私聊窗口时，它却像完全不知道这件事。

如果直接打通所有上下文，问题会更严重。全量共享会破坏私密性，使每个 Agent 都看到所有内容；盲目复制上下文会扩大 token 成本和行为污染；把所有记忆都写入公共区，则会让信息差和角色边界消失。多 Agent 系统真正需要的不是取消隔离，而是在隔离之上建立一个受控的群体记忆层：信息可以跨 session 传播，但传播范围、可见程度、持久化方式和回收机制都必须可治理。

本文讨论的是这类系统的工程架构，而不是角色设定本身。重点在于：如何在会话隔离的约束下建立群体记忆，如何设计跨 Agent 通信协议，如何处理隐私分级，如何让记忆写入更稳定，如何避免历史会话污染新规则，如何在概率性 LLM 行为之上构造可运维的工程系统。

### 核心原理
第一，群体记忆不应等同于共享上下文。共享上下文是把一段对话直接暴露给另一个会话；群体记忆则是把事件抽象为可传播、可过滤、可持久化的记录。前者简单但危险，后者复杂但可治理。多 Agent 系统需要的是“事件层”而不是“聊天记录层”：记录谁在何时与谁发生了什么、事件重要性如何、隐私等级如何、是否允许被其他 Agent 读取，而不是把完整对话无差别复制出去。

第二，信息层必须独立于会话层。session 隔离意味着每条会话都有自己的上下文历史；若希望信息跨 session 流动，就不能依赖 session 自身，而应建立独立存储，例如按 Agent 分区的 memory 文件、数据库事件表或向量化记忆索引。会话负责生成即时回应，信息层负责保存可被未来会话查询的事实摘要。二者分离后，系统既不破坏平台隔离，又能让后续会话在需要时读取已沉淀的信息。

第三，访问控制应放在协议层，而不是完全交给 Agent 自行判断。让 Agent 在自然语言推理中临时决定“这条信息能不能告诉对方”，会受到上下文、情绪、任务压力和提示词漂移影响。更稳妥的设计，是让每条记忆带有结构化隐私评分、可见范围、事件类型和过期规则。跨 Agent 通信前，系统按协议过滤可读记忆，再把结果交给发送方或接收方。推理层可以解释信息，但不应成为唯一的权限边界。

第四，LLM 工具调用是概率性行为，不能假设每轮都会按要求保存记忆。即使提示词明确要求“对话后写入记忆”，模型也可能因为上下文拥挤、任务转移、历史模式污染或工具调用成本而跳过。工程系统应接受这种不确定性，并通过格式约束、强提示、外部检查、失败补偿和定期巡检提高可靠性。目标不是幻想 100% 确定性，而是把遗漏率控制在可接受范围内，并保证遗漏能被发现和修复。

第五，历史会话会形成行为惯性。LLM 在长会话中不仅阅读当前规则，也会从历史轮次中学习“这个会话通常怎么行动”。如果过去几十轮都没有保存记忆，新提示突然要求保存，模型可能继续沿用旧模式。修改提示词后仍不生效，不一定是规则写错，也可能是 session 历史污染。多 Agent 系统调试时必须区分“在旧 session 中测试新规则”和“在新 session 中测试新规则”，否则会把历史惯性误判为架构失败。

第六，群体记忆必须保留信息差。角色系统的真实感往往来自不完全共享：某些事件是公共事实，某些事件只对特定关系可见，某些事件暂时不可传播，某些秘密可能在特定通信中被偶然发现。如果所有记忆都公开，群体会变成一个共享脑；如果所有记忆都私有，群体又会失去联动。隐私分级的目标不是单纯保护信息，而是维持“可控的不对称”。

### 设计思路
一个可落地的架构可以分成四层：会话层、记忆层、通信层和治理层。会话层处理用户与 Agent、Agent 与 Agent 的即时对话；记忆层保存结构化事件摘要；通信层负责跨 Agent 消息发送、上下文收集和可见信息过滤；治理层负责检查记忆写入、监控行为退化、处理历史污染和管理规模扩展。四层分离后，系统不会把所有复杂性塞进提示词，也不会依赖单个 Agent 的自觉。

记忆层的基本单位应是事件摘要，而不是完整文本。每条记录至少包含时间、参与者、事件摘要、来源会话类型、重要性、隐私评分、可见范围、生命周期和关联标签。摘要应短，能支撑未来回忆即可，不应把完整私聊内容暴露给其他 Agent。对于角色扮演场景，摘要还要区分事实、态度、承诺、冲突、秘密、关系变化和待办。不同类型的信息在传播时应有不同规则。

一个简化的记忆记录可以这样表达：

```text
- time: 21:35
  actor: AgentA
  target: AgentB
  event_type: discussion
  privacy: 0.42
  importance: 0.70
  summary: AgentA 与 AgentB 讨论了某个计划的风险，并形成了待确认事项。
  visible_to: group_threshold
  expires: none
```

伪代码或结构示例的价值在于明确边界：Agent 可以参与生成摘要，但系统应尽量固定字段和校验规则。字段稳定后，读取、过滤、审计和回放才有基础。如果记忆只是自然语言段落，后续协议很难可靠判断它是否可见、是否过期、是否重要。

通信层应采用“通信前上下文收集”协议。发送方准备联系目标 Agent 时，先读取自己的近期记忆和目标 Agent 可见的近期记忆，再根据隐私阈值筛选可引用内容，最后构造结构化消息。消息中应明确发送者、目标、通信原因、可见背景、当前问题、希望对方回应的范围和是否需要写入记忆。接收方回应后，也应将本次通信摘要写入自己的记忆层。这样信息不依赖 session 自动流动，而是通过协议完成可控传播。

隐私分级可以采用连续评分，而不是二元公开/私密。二元模型过于粗糙：所有“不公开”的内容都会被同样隐藏，无法表达“可以告诉亲近对象但不能告诉所有人”的差异。连续评分可以让系统通过阈值控制可见性，例如 0.00 表示公开事实，0.50 表示中等敏感，0.90 表示高度私密。通信时为不同关系或不同场景生成阈值，只有评分低于阈值的记录才会进入上下文。

为了保留偶然性，阈值可以带少量随机扰动，但随机性必须受控。完全固定会让信息流动过于机械；完全随机会破坏安全感。更稳妥的方式是以关系强度、通信类型和事件重要性为中心值，再加入窄范围扰动。这样系统既能保持“有些事偶尔被提起”的自然感，又不会让高隐私信息轻易扩散。高隐私记录还可以设置硬上限，即使随机阈值较高也不得传播。

记忆写入要从“任务提醒”升级为“响应格式的一部分”。如果提示词只是说“请记得保存”，模型很容易跳过；如果每次回应格式都要求包含公开回应和内部记忆摘要两个部分，写入就从额外任务变成输出完整性的要求。更进一步，系统可以在每轮结束后检查是否出现记忆摘要字段，缺失时触发补写流程或下一轮提醒。对概率性模型来说，格式约束通常比抽象命令更可靠。

治理层需要监控四类退化。第一是记忆遗漏：连续多轮没有写入摘要。第二是通信退化：Agent 不再主动发起必要通信。第三是隐私泄露：高隐私记录被低阈值通信引用。第四是历史污染：新规则发布后旧 session 仍沿用旧行为。每类退化都应有检测信号和处置路径。没有治理层，多 Agent 系统会在初期看起来很生动，运行一段时间后逐渐失去一致性。

历史污染的处理应制度化。规则大改后，不能只在旧会话中追加提示词并期待行为立刻改变。应评估是否需要重置 session、清理持久化上下文、迁移有效记忆到独立记忆层，并用新会话验证规则。旧会话中的错误行为模式越长，越需要重置而不是继续补提示。对多 Agent 系统而言，session 是运行状态的一部分，不是透明容器。

规模扩展需要提前规划通信拓扑。五个 Agent 全互联时，潜在通信关系已经不少；十个 Agent 全互联会产生更复杂的关系、权限和 session 映射。全互联适合小规模群体，但不适合无限扩展。更大的系统可以采用分层路由、主题频道、公共公告板、关系图过滤或中心协调者。拓扑设计决定信息传播成本，也决定隐私控制难度。

### 进阶讨论
这类系统最常见的反对意见，是“为什么不直接把所有 Agent 的上下文放在一起”。短期看，全量共享最简单，长期看它会破坏角色边界、制造隐私泄露、扩大 token 成本，并让所有 Agent 越来越像同一个意识的不同口吻。多 Agent 的价值恰恰在于视角差异和信息不对称。工程架构应保护这种差异，而不是为了实现方便把它抹平。

另一种反对意见是“隐私评分太复杂”。这个担忧成立，因为评分确实会增加标注和调试成本。但没有显式评分，系统仍然需要隐式判断信息能否传播，只是判断散落在自然语言推理中，更难审计。结构化评分的意义不在于绝对精确，而在于让权限问题可观察、可调整、可回放。即使评分有误，也比完全不可见的临场判断更容易修复。

记忆摘要也存在失真风险。摘要越短，越可能丢失语气、条件和上下文；摘要越长，越接近复制原始对话，隐私和成本都会上升。比较稳妥的策略是分层保存：日常记忆使用短摘要，高重要事件额外保存扩展摘要，敏感事件只保存抽象事实和访问条件。系统还可以允许 Agent 在需要时请求更多上下文，但必须经过更严格的权限检查。

跨 Agent 通信不应过度频繁。为了制造群体感，系统可能倾向于让 Agent 大量互相聊天；但通信过多会消耗成本、污染记忆、制造无意义同步，并让角色显得过度关注彼此。通信触发应有明确条件，例如新事件与对方强相关、存在待确认事项、对方拥有必要信息、关系状态需要更新。通信频率本身也应成为指标，过低会失联，过高会噪声化。

还要区分“主动通信”和“被动可见”。某些事件不需要立刻通知其他 Agent，但应在未来对方查询时可见；某些事件必须立即通知；某些事件只应留在本 Agent 的私有记忆里。把所有共享都做成立即通信，会造成信息风暴；把所有共享都做成被动查询，又会让群体反应迟钝。成熟系统应同时支持事件推送、按需查询和公共公告三种模式。

概率性工具调用意味着系统必须设计补偿机制。即使记忆写入可靠率达到较高水平，也仍会有遗漏。补偿可以来自下一轮自检、定时巡检、对话结束钩子、外部守护进程或人工审计。若平台不支持 hook，就要在可用机制中尽量构造近似闭环，例如在每次通信协议中强制读写双方记忆，并定期检查 memory 文件更新时间。不能因为无法达到完美，就放弃工程化治理。

从安全角度看，群体记忆层也是风险集中点。它保存多个 Agent 的交互摘要，若权限控制错误，泄露范围会比单条会话更大。因此记忆层应支持最小可见、按需读取、敏感字段脱敏、访问日志和删除机制。角色系统中的“秘密”不仅是叙事元素，也是权限模型中的敏感数据。把叙事秘密当普通文本处理，会让系统天然不安全。

从体验角度看，群体记忆不能表现得过于机械。用户期待 Agent 记得重要事件，但不期待每个 Agent 像数据库一样复述所有记录。读取记忆后，Agent 仍应根据自身视角、关系和当前情境选择表达。工程层提供事实和边界，表现层负责自然化。若每次切换对话都机械列举“我知道某某刚刚说了什么”，群体感反而会变弱。


事件模型还应区分事实记忆、关系记忆和任务记忆。事实记忆描述已经发生的客观事件，例如某次通信讨论了一个方案；关系记忆描述 Agent 之间的态度变化、信任变化或冲突状态；任务记忆描述后续需要跟进的事项。三类记忆的传播规则不同。事实记忆可以按隐私评分传播，关系记忆更依赖通信双方和当前关系，任务记忆则需要确认责任方和截止条件。若所有记忆都使用同一套字段，系统会难以判断哪些内容应被主动提醒，哪些内容只需被动查询。

权限审计需要保留“为什么这条记忆被看见”的解释。跨 Agent 通信时，系统不应只把筛选后的记忆塞进上下文，还应在日志中记录筛选依据：通信双方是谁、阈值是多少、哪些记录被选中、哪些记录因隐私评分过高被排除、是否存在硬性不可传播标记。这样一旦出现信息泄露或信息缺失，就能回放协议判断问题来自评分、阈值、关系配置还是摘要生成。没有审计日志，隐私分级会变成黑箱，调试成本会非常高。

回放调试是多 Agent 系统稳定化的关键工具。一次用户切换对话后发现某个 Agent 不知道前情，排查时需要看到完整链路：原始事件是否被写入记忆，写入的摘要是否足够清楚，通信前是否读取了目标记忆，隐私过滤是否排除了关键记录，接收方是否把通信写入自己的记忆，后续私聊是否读取了本地记忆。只看最终回复无法定位问题，因为失败可能发生在链路任何一段。回放工具把一次跨 session 信息传播拆成可观察步骤，才能让群体记忆从“像是有效”变成“可以验证”。

指标体系也应围绕群体连续性设计。除了常规的响应质量，还应记录记忆写入率、关键事件召回率、跨 Agent 通信触发率、通信后双方记忆一致率、隐私误泄率、隐私误挡率、历史污染复发率和过期记忆残留率。写入率说明系统是否保存事件；召回率说明后续能否用上事件；一致率说明通信是否形成闭环；误泄和误挡说明隐私边界是否合理。没有这些指标，团队只能通过主观感觉判断系统是否“有群体感”。

规模化拓扑可以按三种模式演进。第一种是全互联，适合小群体，所有 Agent 都可以互相通信，关系自然但链路数量随规模快速增长。第二种是中心路由，适合中等规模，由一个协调节点负责汇总公共事件和转发关键信息，成本更低但可能形成单点偏置。第三种是主题频道，适合大规模，把记忆按项目、事件或关系域分区，Agent 只订阅与自己相关的频道。三种模式没有绝对优劣，选择取决于群体规模、隐私要求和交互密度。

记忆生命周期同样重要。并非所有事件都应永久存在。短期闲聊、临时状态、已解决任务和过期关系判断如果长期保留，会让 Agent 的行为越来越沉重，也会提高检索噪声。记忆层应支持过期、降权、归档和合并。高频低价值事件可以定期合并为概括性状态；已完成任务可以保留结论而删除过程；敏感事件可以设置更短保留期。群体记忆不是越多越好，而是越能支撑未来合理行为越好。

在实现层面，记忆检索应避免只按时间倒序读取。最新事件不一定最相关，最重要事件也不一定最新。更好的做法是结合时间、参与者、事件类型、重要性、隐私评分和当前任务进行综合排序。若系统支持向量检索，还要防止语义相似但权限不匹配的记录被召回。检索先过权限，再做语义相关性排序，会比先检索再过滤更安全，因为后者可能在中间日志或模型上下文中暴露不该出现的内容。

最后，群体记忆系统必须承认“记得”和“表达”是两回事。Agent 读取到某条记忆，并不意味着它应该直接说出来。它需要判断当前对话是否适合提及、提及到什么程度、是否会暴露其他 Agent 的私密信息、是否会让用户感到突兀。工程层负责提供可用事实和边界，表达层负责把事实转化为自然回应。若系统只追求高召回，而不考虑表达时机，群体记忆会变成机械引用；若只追求自然表达而不保证召回，群体又会重新失忆。成熟体验来自两者共同稳定。

### 总结
五 Agent 角色扮演系统的上下文共享，本质是会话隔离、安全边界、群体连续性和信息不对称之间的平衡问题。直接共享上下文会破坏边界，完全隔离又会造成群体失忆。更稳妥的架构是在 session 之外建立受控记忆层，用结构化事件摘要、隐私评分、通信前上下文收集、写入闭环和治理监控来支撑跨 Agent 信息流动。

这种架构的关键判断是：多 Agent 系统需要的不是一个更大的上下文窗口，而是一套可治理的信息传播协议。只要记忆有结构、访问有边界、通信有流程、退化可检测、历史污染可处理，多个 Agent 才能在不丧失各自独立性的前提下形成可信的群体记忆。
