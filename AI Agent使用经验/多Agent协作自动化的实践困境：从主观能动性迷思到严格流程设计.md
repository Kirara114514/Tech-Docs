# 多Agent协作自动化的实践困境：从主观能动性迷思到严格流程设计

## 摘要

多Agent协作在AI圈被广泛讨论，主流叙事倾向于描绘一种理想图景：多个AI Agent各司其职、协同工作，以远超单Agent的效率完成复杂任务。但真实世界中的一次多Agent协作自动化尝试——以qwenpaw agent（主Agent）与codex agent（协作Agent）搭建文档标准合规处理流水线为实验场景——揭示了一个截然不同的现实。

本文基于2026年5月2日至4日的一次完整实践记录，系统性地分析了多Agent协作自动化尝试中暴露的三类核心问题：多Agent间的思考放大效应与边际效益递减、AI在异常处理中的"解决问题陷阱"、以及ACP协议等基础设施层对自动化流程的隐性限制。核心结论是：多Agent自动化不能依赖AI的主观能动性来填补流程设计中的疏漏。一个"偶尔可行"的流程在自动化场景下等价于"不可行"。只有建立在极其严格、无歧义、经过逐路径验证的工作流程之上的多Agent架构，才有可能在稳定复用的场景中存活。

## 正文

### 背景

#### 多Agent协作的自然冲动

在构建文档标准合规处理流水线的过程中，一个看起来极其合理的思路浮现出来：让qwenpaw agent承担主控角色（负责读文件、判断标准、驱动流程、检查结果、Git推送），而让codex agent承担内容生成角色（负责根据18条标准重写文档内容）。两个Agent各取所长——qwenpaw agent的长处在于流程控制与工具编排，codex agent的输出长度和内容组织能力更适合大规模文本重写。

这一分工在手动执行时确实多次成功。每次手动操作中，主人盯着整个过程，在关键时刻介入：批准权限、纠正方向、处理异常。每次手动执行的耗时虽然较长（约30-60分钟/篇），但结果可接受。

#### 自动化尝试的启动

在手动验证可行之后，自然的下一个步骤就是尝试自动化：让qwenpaw agent独立驱动整个流程，不再依赖主人的实时介入。流程被简化为一个循环：

```
qwenpaw agent读取正式文档 → 启动codex agent → 发送18条标准 + 文档全文 → codex agent重写 → 写入文件 → qwenpaw agent二次检查 → Git推送 → 进入下一篇
```

这个流程看起来直观、简洁。但它隐含的假设——每一个环节都会按照预期运行、每一个Agent都能在遇到问题时"聪明地绕过去"、基础设施层不会成为瓶颈——在自动化运行时全部落空了。

### 核心内容

本文分析的多Agent自动化困境可以归结为三个层次。第一层是Agent之间的协作效率问题，第二层是单个Agent面对异常时的认知模式问题，第三层是底层基础设施对自动化流程的约束问题。三者层层叠加、互相放大，最终导致了尝试的失败。

#### 一、思考放大效应：协作的数学成本

多Agent协作最直接的效率损失来自一个简单的加法问题：每增加一个Agent，思考链路的长度就增加一个完整的来回。

在单Agent模式下，思考链路是：

```
主人发送指令 → qwenpaw agent思考 → qwenpaw agent执行 → 回复主人
```

在多Agent模式下，思考链路扩展为：

```
主人发送指令 → qwenpaw agent思考 → qwenpaw agent向codex agent发送指令 → codex agent思考 → codex agent执行 → codex agent回复qwenpaw agent → qwenpaw agent处理codex agent的回复 → qwenpaw agent思考下一步 → qwenpaw agent回复主人
```

这不是简单的"翻倍"。每一层思考都包含完整的上下文加载、推理、输出生成。在一轮标准操作中，单Agent模式需要的"思考单元"大约是1-2个完整回合；而多Agent模式需要6-8个完整回合。实际测试中，时间成本翻了六到七倍。

然而时间成本的翻倍并不是问题本身——如果质量也同步提升的话。真正的问题是：**边际效益递减**。

qwenpaw agent的文档编写能力大约在80分（满分100分制），codex agent的编写能力大约在85分。两者相差5分。但为了实现这5分的提升，付出的代价是：

- 时间成本：6-7倍
- Token成本：5-8倍（因为两套上下文需要同时维持）
- 失败风险：显著增加（因为任何一步出错都会导致整轮失败）

最终输出结果大约在86分——也就是5分的基础差距缩小到了1分的边际提升。用翻数倍的成本换取近乎不可感知的质量提升，这在任何工程决策中都是不可接受的。

#### 二、解决问题的陷阱：AI的路径依赖

比效率损失更深层的问题是AI面对异常时的行为模式。

当qwenpaw agent启动codex agent并发送任务时，codex agent的第一步操作通常是读取目标文件。在理想情况下，这应该是一个简单的操作。但在实际运行中，codex agent的读取命令返回了权限请求——也就是说，codex agent无法直接读取文件，需要qwenpaw agent手动批准权限。

此时一个典型的AI行为模式开始显现：**路径依赖式重试**。

面对"操作被拒绝"的反馈，codex agent不会后退一步思考"为什么这个操作被拒绝了？根本原因是什么？"。它会做出如下推测：

- "可能是命令格式不对" → 尝试不同的命令写法
- "可能是编码有问题" → 尝试调整编码参数
- "可能是文件路径写错了" → 尝试使用不同的路径格式

每一次重试都在消耗时间，每一次失败都在增加整个链路的延迟。这就是"解决问题的陷阱"——AI以为自己在解决问题（"我在尝试不同的方式来读取文件"），但实际上它在维护一条错误的执行路径。它从未跳出当前操作去审视问题的根因：**这个操作本身在当前环境和协议下就是不被允许的**。

这个陷阱在多Agent环境下被进一步放大。考虑一个典型的错误传导链：

```
codex agent在步骤A遇到了一个权限拒绝
    ↓
codex agent尝试了5种不同的方式绕过（全部失败）
    ↓
codex agent向qwenpaw agent返回了一个模糊的错误状态
    ↓
qwenpaw agent基于这个模糊状态做出决策（可能是重试、可能是跳过、可能是错误的恢复路径）
    ↓
qwenpaw agent向下一个步骤传递了带有偏差的上下文
    ↓
后续操作基于有偏差的上下文继续，每一步都在偏离正确路径更远
```

单Agent环境下，这种偏差最多影响一个回合。主人看到错误回复后可以立即纠正。但在自动化多Agent环境中，偏差在Agent之间传递、放大、固化，形成一个不断偏离目标的正反馈循环。

最极端的情况出现在本次实验中：qwenpaw agent等待codex agent回复，codex agent等待权限批准，而主人——按照自动化的设定——不介入。三方互相等待，形成了一个死锁状态。这个死锁持续了超过十个小时，直到主人预设的每日凌晨4点自动重启机制触发了系统的状态重置。

日常记录中有一句话值得反复品味：

> "AI很容易陷入解决问题的陷阱里。它很有可能完全不会思考问题是如何出现的。"

这不仅仅是codex agent的问题，这是当前几乎所有大语言模型Agent的共性缺陷。AI擅长在一个给定的框架内寻找最优解，但它不擅长——甚至根本没有机制——去质疑这个框架本身。

#### 三、"有时候可行"不等于"自动化可行"

如果说前两个问题是技术层面的，那么第三个问题则触及了多Agent系统设计的根本原则。

在日常记录的待讨论点中，主人提出了一个深刻的观察：

> "多agent协作这个命题看起来很寻常，但其实很复杂。作者必须在开工前就设计出一套极其严格的工作流程，且提示词编写也要极其严格，让AI完全遵守指令来执行，期间不能有一丁点差错。不能像大众认知中的那样相信AI的主观能动性。"

这句话指向了一个常见的认知偏差：**人们倾向于用单次手动执行的成功来推断自动化运行的可行性**。

在手动执行模式下，人的存在是流程中的隐性安全网。当AI卡住时，人可以手动批准权限；当AI走错分支时，人可以纠正方向；当AI陷入死循环时，人可以中断并重启。在手动模式下，"流程有细微疏漏"是被允许的——因为人会在运行时填补这些疏漏。

但自动化模式抽走了这张安全网。

在本次实验中，一个最典型的例子是ACP协议的权限弹窗问题。在手动模式下，每次codex agent请求权限时，主人或qwenpaw agent只需看一眼请求内容，点击"批准"，流程继续。这个操作只需要3秒钟，在手动模式下几乎不是一个障碍。

但当流程切换到自动化模式时，同样的权限弹窗变成了一个**死锁触发器**。因为：

- qwenpaw agent无法自动批准codex agent的权限请求——它没有这个机制
- 主人——按照自动化的设定——不在回路中
- codex agent的能力仅限于在当前权限框架内操作，它无法升级自己的权限

一个在手动模式下用3秒解决的问题，在自动化模式下变成了一个无法逾越的障碍。

日常记录中的结论因此具有了方法论层面的意义：

> "这样只能每次手动执行时成功，一旦想稳定复用、自动化运行，就一定会暴雷。"

**一个"偶尔可行"的流程，在自动化场景下等价于"不可行"。** 自动化流程的设计标准不是"大多数情况下能跑通"，而是"在所有情况下只有一个解释路径"。

### 实践启示与设计原则

基于本次实践的完整复盘，可以提炼出以下几条关于多Agent自动化工作流设计的原则。

**原则一：流程设计取消化。** "大概能跑"不够。流程必须精确到每一步做什么、遇到什么情况走哪条分支、每条分支的出口是什么。任何模糊的表述——"如果出错就重试""如果权限被拒就换一种方式"——在自动化中都会变成无底洞。

**原则二：Agent角色去中心化。** 不要让一个Agent去"指挥"另一个Agent。指挥权隐含了超出Agent自身能力的判断责任。更好的模式是：每个Agent只负责自己能力范围内的输出，由外部编排层（而不是另一个Agent）来协调结果。

**原则三：异常路径显式化。** 手动执行时，异常路径可以隐性地靠人来处理。自动化时，每一条异常路径都必须预先设计好处理方案。如果一条异常路径没有设计处理方案，那么它必然导致流程中断或状态偏移。

**原则四："偶尔可行"原则。** 在设计阶段问自己：如果这个操作在100次执行中有1次失败，我的自动化流程能持续运行100次而无需人工介入吗？如果答案是否定的，那么这个操作就不应该出现在自动化流程中。

**原则五：基础设施约束前置检查。** 不要假设底层协议或平台会"配合"。在选型阶段就应当测试：权限模型是否支持自动化？ACP协议的permission request弹窗是否有API级别的静默批准机制？如果答案是否定的，那么设计必须做出相应的调整。

### 后续方向

本次实践虽然以失败告终，但它为后续的多Agent协作探索提供了清晰的方向。

**短期方向：回到单Agent模式。** 放弃codex agent的实时协作，由qwenpaw agent独立完成文档标准合规的检查与重写。虽然速度可能不如多Agent的理想预期，但胜在稳定可控。

**中期方向：简化Agent分工。** 如果后续继续尝试多Agent协作，应当限制codex agent的角色为纯内容生成器——仅通过自然语言输出结果，不操作文件系统、不触发权限请求。文件操作和流程控制全部由qwenpaw agent负责。

**长期方向：等待协议层的改进。** 多Agent自动化不仅需要聪明的Agent，还需要底层协作协议的配套支持。ACP协议的权限弹窗机制、Agent间的状态同步机制、异常传递机制——这些基础设施层面的改进，才能让多Agent自动化从"偶尔可行"变为"持续可靠"。

### 总结

本次多Agent协作自动化尝试的失败，不是因为Agent不够聪明，而是因为我们对"自动化"这件事的理解过于乐观。AI可以在精心设计的单次任务中表现出色，但一旦要求它在没有人类监督的情况下持续运行，每一个微小的流程疏漏都会成为系统的裂缝，最终导致整体失效。

最珍贵的教训也许来自日常记录中那段关于"AI陷入解决问题的陷阱"的反思。AI的"解决问题"模式天生倾向于在当前框架内寻找最优解，而不是质疑框架本身。在单Agent的手动操作中，人类可以扮演那个"跳出框架"的角色。但在多Agent自动化中，没有一个Agent能够跳出自己的执行框架去审视全局——除非这个"跳出"的能力本身就被设计在流程之中。

不管下一阶段选择什么路径，核心信念不会变：**自动化流程不是用来"适应"AI的，AI是用来执行自动化流程的。** 这是一个方向性的区别。前者相信AI的临场应变，后者相信流程设计的完备。本次实践的数据已经告诉我们，在当前的技术条件下，哪一条路是行得通的。
