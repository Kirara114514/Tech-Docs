# Agent 框架本身对模型编码能力的影响：从一个现象出发的思考

- **记录时间：** 2026-06-23
- **记录类型：** 想法
- **相关分类：** Agent与AI工程化
- **状态：** 待讨论

## 内容
观察到 Codex / Claude Code 这类 agent 框架，无论接入什么模型，编码表现都还不错；但 OpenClaw 这类框架，单纯做编程任务就明显差一截。这引出一个问题：差距到底从哪来？

初步想法：我们对 LLM 的直觉认知是「一问一答」。把 LLM 接入一个 app（比如 OpenClaw）之后，也延续了这种模式——用户发一条消息，框架把消息转发给 LLM，然后解析 LLM 的回复，执行指令或把文本返回给用户。但这太初级了。框架其实可以做更多。

## 初步思考
框架可以在「用户消息 → LLM」之间做大量前置操作：理解任务意图、拆解子任务、注入系统级上下文、预判工具调用链。也可以在「LLM 回复 → 用户」之间做后置处理：解析结构化输出、校验结果、编排多轮子 agent 调用、对中间结果做验证和纠偏。甚至可以在多个子 agent 之间形成发送→解析→再发送→再解析的循环，每一跳都能对收发内容做加工。

这个想象空间很大。Codex / Claude Code 在编程任务上的优势，很可能不是模型本身的差距，而是框架层在任务拆解、工具编排、上下文管理等环节上的工程深度。

## 待讨论点

3. 框架层的想象空间边界在哪——多少事情应该由框架做，多少由模型本身承担？
4. 子 agent 间的消息加工和路由能否提炼成通用范式？
