## 内容

我想讨论一个话题：一个最简 agent 框架在原理上究竟是如何实现的，以及怎样在这个最小内核上"添砖加瓦"，一步步演进成一套合格的 harness（智能体运行框架）。

讨论这个话题有三个目的：

1. **温故而知新**——把已有的碎片认知重新串成一条完整的链路，看自己到底理解到哪一层。
2. **作为备忘**——记录下来，之后可以随时翻回来对照。
3. **分享给同行**——这个话题对有兴趣的人应该是有价值的，希望能被独立理解。

同时有一个必须提前说明的前提：**agent 领域日新月异，说不定一年后这套思想就变成了仅供参考的历史弯路。** 所以讨论时要注意普适性和宏观视角——不能只盯着当前某个框架的具体实现，否则写出来的东西很快就过期。

## 初步思考

- **为什么要从"最简"开始。** 最小内核（大概就是：一个能对话的模型 + 一个循环 + 工具调用）是所有复杂 harness 的基线。复杂度不是凭空设计的，而是从这个内核上长出来的。先看清基线，后面每一层新增才有立足点。
- **"添砖加瓦"的路径，本质上是一份问题清单。** 上下文管理、工具编排、错误恢复、状态持久化、权限边界、可观测性、子任务分解……每一块砖背后都是一个真实遇到过的问题。搞清楚"因为遇到了什么问题才加这一层"，比记住"某框架有哪几个模块"更有价值。
- **普适性与时效性的张力。** 具体实现会过期，但"为什么需要这一层"的约束大多来自模型能力与任务复杂度之间的缺口。这类约束比 API 形状稳定得多。把讨论锚在约束上，而不是锚在某个框架的目录结构上。
- **备忘 + 分享的双重目的，对写法有要求。** 正文必须零私有上下文——不依赖只有自己知道的内部工具名、项目名、路径。一个不认识作者的读者应该能独立读懂。
