# AI编程的上下文管理与记忆系统

## 摘要
本文探讨在工业化AI编程场景下，如何构建企业级的上下文管理与记忆系统。从向量化代码检索（Claude Context MCP）出发，讨论关于"以语义单元替代文件单元"投喂AI的核心理念重构，以及多Agent协作场景下的上下文分层与动态检索策略。

## 正文

### 背景

AI编程进入工程化阶段后，如何让AI有效理解大型项目结构成为核心痛点：

1. **上下文窗口瓶颈** — 大型项目的源码量远超任何模型的上下文窗口，即便200K tokens也很快触顶
2. **注意力稀释** — 上下文越满，模型注意力越分散，关键信息被"大海捞针"
3. **tokens成本** — 每次新会话都要重新"喂"项目背景，成本随上下文线性增长
4. **skill切分困境** — 过去做法是把文档和核心脚本喂给AI梳理成skill，但当模块之间职责模糊时，分skill也是难事；模块庞大时skill文档太长，对LLM性能是极大考验

### 现有方案：Claude Context MCP

zilliztech/claude-context（1.1万 stars，MIT协议）是Zilliz/Milvus团队开源的解决方案。

**架构：**
```
项目源码 → 文件扫描 → BM25 + dense vector混合索引 → Milvus存储
                                                       ↓
AI编码助手 (Claude Code/Cursor/Qwen Code等) ← MCP协议 ← MCP Server
```

**核心工具：**
- `index_codebase` — 扫描并索引整个代码库，BM25 + 稠密向量混合检索
- `search_code` — 自然语言查询代码
- `clear_index` — 清除索引
- `get_indexing_status` — 查看索引进度

**设计特点：**
- 混合检索（BM25精准匹配 + Dense Vector语义匹配）解决代码场景的独特需求：变量名精确匹配+语义相似搜索
- 兼容多平台：Claude Code、Cursor、Windsurf、Gemini CLI、Qwen Code、VS Code、JetBrains等
- 按项目维度隔离索引

**不足：**
- 依赖于Zilliz Cloud（托管Milvus），企业自建方案需自行部署
- 本质上是"智能搜索"工具，不是"代码理解"工具——缺少调用链分析和模块依赖关系感知
- 没有跨会话的长期记忆能力

### 核心理念重构：从文件单元到语义单元

当前主流做法是将文档和代码以"文件"为基本单元投喂给AI（README、Skill文档、架构说明）。但这本质上是"给人看文档"的思维方式。

**人与AI读取文档的差异：**

| | 人 | AI |
|---|---|---|
| 理解方式 | 从头到尾线性阅读 | 需要精确命中相关片段才能正确推理 |
| 长文档 | 慢慢翻、慢慢消化 | 长上下文 → 注意力稀释 → 幻觉率上升 |
| 模块边界 | 靠目录、命名规范区分 | 纯靠token距离和embedding相似度 |
| 跨模块引用 | 能翻页查 | 上下文不够时直接断链 |

**结论：对AI的上下文投喂，不应该再用"文件"作为基本单元。** 应该用**语义单元**替代：
- 不是"把Skill-A.md喂给AI"
- 而是"把函数/接口/类/配置/规范各自向量化，AI需要什么检索什么"

### 上下文分层模型

在多Agent协作场景下，上下文管理需要分层设计：

```
┌─────────────────────────────────────────────┐
│  第一层：指令层（不可选，每次必带）             │
│  - 安全边界、身份约束、输出格式                 │
│  例子：DocManager的AGENTS.md                  │
├─────────────────────────────────────────────┤
│  第二层：结构背景（可选，按任务类型检索）        │
│  - 代码库的语义索引（函数/类/模块关系）          │
│  - 项目规范和架构决策记录                       │
│  - 存储形式：向量数据库，按任务语义检索          │
├─────────────────────────────────────────────┤
│  第三层：会话记忆（可选，按关联度筛选）          │
│  - 历史决策原因、用户偏好修正                   │
│  - 存储形式：RAG检索 + 时间衰减权重             │
├─────────────────────────────────────────────┤
│  第四层：执行上下文（每次任务独立，用完即弃）     │
│  - 当前任务的源码片段、临时讨论                  │
└─────────────────────────────────────────────┘
```

关键难点在第二层和第三层——它们的**检索策略**决定了系统质量。

### 多Agent协作的上下文传递问题

当前主流的多Agent协作模式是：A Agent理解全貌 → 拆任务 → B Agent得到干净的独立子任务 → B执行。

但这种"干净的上下文"隐藏了一个假设：**被拆出来的子任务，其所需的全部上下文信息，A都已经包含并传递了。**

这在很多场景下不成立：
- B收到了"重构UserService的数据库层"，但B不知道公司规范要求所有数据库操作必须走AuditInterceptor
- B在改代码时需要理解某个模块的设计决策来源，但这个决策记录在C Agent前几天的对话里
- 跨模块依赖关系中，改A模块可能影响B模块，但B的上下文里没有A的信息

所以核心问题转化为：**哪些上下文是"背景知识"（该随任务固定传送），哪些是"噪声"（该过滤掉）？**

### 代码检索的特殊性与动态路由

代码上下文的检索与知识文档的检索是两回事：

| | 知识文档检索 | 代码上下文检索 |
|---|---|---|
| 查询意图 | "什么是工厂模式？" | "改这个函数会影响什么？" |
| 检索手段 | 语义检索效果好 | 需要调用链、依赖关系 |
| 匹配粒度 | 段落级别 | 函数/类/模块级别 |
| 关联维度 | 主题关联 | 调用关系、依赖关系、继承关系 |

同一段代码，不同Agent的不同问题需要**不同的检索策略**：
- Agent问"这个函数干嘛的" → 语义检索就够了
- Agent问"改了它会不会炸" → 需要依赖图谱
- Agent问"这个接口的规范是什么" → 需要精确匹配+规范文档

这引出一个更深的问题：**能否在检索时，不靠预先的"任务类型"分类，而是根据问题本身的特征动态选择检索策略？**

### 总结

AI编程进入工业化阶段后，上下文管理与记忆系统从"辅助功能"变成了"底层基础设施"。关键方向包括：

1. **语义化投喂** — 以语义单元替代文件单元，摆脱"给人看的文档"思维
2. **多层上下文** — 指令层、结构背景、会话记忆、执行上下文的四层分离
3. **动态检索策略** — 根据问题特征选择不同的检索策略（语义/精确/图谱）
4. **企业级自建** — 数据安全要求下，向量数据库必须自建，不可依赖第三方托管服务
5. **打破刻板印象** — OpenClaw的memory文档+超大JSON会话文件只是单个软件工程的设计，不是标准答案
