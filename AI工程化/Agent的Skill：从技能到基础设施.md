# Agent 的 Skill：从技能到基础设施

## 摘要

Skill 机制是 Agent 框架中一项关键设计——它允许 Agent 在运行时按需加载特定能力，而不必将所有知识塞入提示词。本文从"Skill 到底是什么"出发，逐步深入 Skill 的内在分层、核心价值、分发机制设计空间、组合冲突挑战，以及在 MCP、function calling 等行业标准化趋势中的位置。目标不是写一份操作手册，而是为读者建立一个理解 Skill 的完整心智模型——它不仅仅是"防呆文档"，更是上下文预算管理的手段、能力的模块化封装，以及未来 Agent 生态的基础设施。

## 正文

### 背景

#### 一个熟悉的困境

假设你想让一个通用 Agent 帮自己管理文档库。你需要它知道：文档分三个库（Tech-Docs、Thoughts-Docs、私密文档），每个库有各自的模板和命名规则，写入文件必须用 Python UTF-8 编码，做完要 Git 推送，推送失败要重试。光是"写一条日常记录"这个简单动作，背后就涉及七八条规则、三四个子步骤。

如果你把这些规则全部塞进 Agent 的 system prompt，会发生什么？

第一，**上下文窗口被大量领域知识侵占**。Agent 在闲聊、答疑、简单查询时，这些规则毫无用处，却白白占用推理空间。第二，**知识的组织方式与 Agent 的认知方式不匹配**——所有规则平铺在一个平面文档里，Agent 在需要时检索不到具体的规则。第三，**能力的边界不清晰**——系统 prompt 里既包含安全约束、又包含领域规则、又包含工具使用说明，Agent 很难区分"这是必须遵守的"和"这是按需使用的"。

这就是 Skill 要解决的问题。但 Skill 这个概念本身，在 Agent 框架领域也是一个相对新的抽象——它不像"插件"、"函数调用"、"工具"那样有清晰的技术传承，而是 Agent 框架设计者在实践中独立演化出来的设计模式。它来自一个朴素的观察：当 Agent 的 system prompt 超过几千字时，推理效果开始下降，尤其当这些 prompt 中的大部分内容与当前任务无关时，下降更加明显。解决方案也朴素：让 Agent 只在需要的时候才读取它需要的指令。

#### Skill 的起源与演化

Skill 机制最早出现在一些实验性的 Agent 框架中——开发者发现，与其把"如何操作文件"、"如何调用 API"、"如何格式化输出"等规则写在主 prompt 里，不如拆成独立文档，让 Agent 在需要时自己读。这听起来像一个微不足道的工程决策，但它改变了 Agent 能力的组织方式。

最初的 Skill 只是简单的"readme 文件"——一些文本说明，Agent 在启动时全部读取。后来逐步演化出 desc 字段（用于分发和路由）、SKILL.md 规范（标准化的文档结构）、依赖声明（Skill 之间的调用关系）等更结构化的设计。

这个演化路径与软件工程中"过程式 → 模块化 → 面向对象"的演进有相似之处：从平铺一切到封装，从封装到标准化接口，从标准化接口到组合与可替换。不同之处在于，这一演化在 Agent 框架中发生得非常快——从"readme 文件"到"结构化 Skill 体系"的跨度，可能只经历了几个月。

#### 从全量知识注入到按需加载

在传统软件开发中，模块化设计是一个常识：你不会把所有功能写进一个文件，而是拆成独立的模块，编译时链接或运行时动态加载。Agent 的 Skill 机制本质上是同一个思路在 AI 系统中的应用——只是这里的"模块"不是代码文件，而是**可被 Agent 读取的指令文档**。

一个 Skill 的基本结构由两部分组成：

- **desc（描述）**：一段简短说明，告诉框架和 Agent "这个 Skill 是做什么的"，作为分发和路由的依据
- **SKILL.md**：完整的执行指引文档，包含所有细节规则、步骤、约束、边界条件

Agent 在执行某个任务时，先通过 desc 判断哪些 Skill 与当前任务相关，然后读取对应的 SKILL.md 获取完整指令。这个机制把"能力的声明"和"能力的执行"解耦了。

#### 一个更精确的类比

Skill 之于 Agent，类似动态链接库（DLL/so）之于程序。DLL 不会被编译进主程序，而是在运行时按需加载；可以被多个程序共享；可以独立升级替换而不影响主程序。Skill 同样：不写进 Agent 的 system prompt，按需读取和执行；同一个 Skill 可以被不同的 Agent 使用；可以独立更新而不影响 Agent 的其他能力。

这个类比比"插件"或"工具"更准确——Skill 不仅定义了 Agent 能做什么（调用外部工具），还定义了 Agent 应该以什么方式做（行为指令、输出格式、安全约束），这正是 DLL 作为"可执行代码模块"的特征。

### 核心原理

#### Skill 的内在分层

一个被遗漏的重要视角是：Skill 本身不是同质的。根据其职能的不同，Skill 可以划分为两类：

**被动型 Skill（知识注入）**

这类 Skill 的核心作用是扩展 Agent 的"所知"——它不改变 Agent 的工具调用能力，而是补充领域知识、行业规范、编码约定、配置信息等。Agent 加载这类 Skill 后，行为上不会新增"能做什么"，而是"知道什么"发生了变化。

举例：一份描述文档命名规则的 Skill，加载后 Agent 知道"文件名要用中文、不加日期前缀、放在对应分类文件夹下"——但 Agent 本身的工具调用能力没有增加，只是行为更加精确了。

**主动型 Skill（工具调用/副作用）**

这类 Skill 的核心作用是扩展 Agent 的"所能"——它定义了 Agent 如何使用外部工具、调用 API、操作文件系统、执行有副作用的操作。Agent 加载这类 Skill 后，获得了新的行为能力。

举例：一份描述如何使用 Git 推送的 Skill，加载后 Agent 知道"先 git add，再 git commit -m，最后 git push origin main"——Agent 新增了管理版本控制的能力。

两类 Skill 的管理方式、加载策略、冲突模式完全不同。被动型 Skill 主要面临信息重叠问题（两个 Skill 给出矛盾的领域知识），主动型 Skill 主要面临工具冲突问题（两个 Skill 争抢同一个外部工具）。在后续讨论中，这个分层会反复被引用。

#### 三层价值：Skill 的核心贡献

**第一层：降低执行方差（作为副产品而非定义）**

这是 Skill 最容易被感知的价值，也是最容易被误解为"定义"的价值。当一个任务有复杂的步骤和大量细节时，Skill 通过在文档中明确写出每一步的规则和约束，将 Agent 的执行结果从不稳定的随机过程转变为可预期的稳定输出。

举个例子：写一个文档到文件系统，涉及"用什么编码"、"路径格式是什么"、"写完后要不要验证"、"要不要推送"等十几个决策点。没有 Skill 时，Agent 每轮推理都独立做这些决策，偏差大；有 Skill 时，Agent 直接按指引执行，方差急剧缩小。

但理解这个价值的关键是：**降低方差不是 Skill 的本质，而是它作为可执行指令集的自然结果**。把 Skill 定义为"防呆文档"是本末倒置——它描述了 Skill 的效果，而不是定义。

**第二层：路由指令层——desc 的本质**

这是 Skill 机制中最容易被忽视、但事实上最关键的设计点。desc 看起来像"一段简介"，但在实际运行中，它承担的角色是**分发元指令**——框架层通过 desc 判断是否应该把该 Skill 的 SKILL.md 注入到 Agent 的上下文中。

这个判断的重要性怎么强调都不过分。如果 Agent 没有读到 SKILL.md，那么 Skill 内部再精妙的逻辑都是无用的。desc 的质量直接决定了 Skill 的发现率，SKILL.md 的质量决定了 Skill 的完成率。两者是串联关系：一个优秀的 desc 被错误路由到一个平庸的 SKILL.md，结果平庸；一个糟糕的 desc 导致一个优秀的 SKILL.md 从未被读到，结果是零。

所以在设计 Skill 时，desc 的编写是一项被严重低估的技能。好的 desc 应该：

- **以触发条件开头**：不是"本 Skill 介绍了文档写入的规则"，而是"当你需要将内容写入文件系统时，使用本 Skill..."
- **明确 ROI**：告诉 Agent 读了有什么好处、不读会踩什么坑
- **精炼但准确**：让 Agent 在几十个字内判断出"这个 Skill 跟我的当前任务相关"

**第三层：上下文预算管理——核心价值的正面论证**

如果把 Agent 的上下文窗口看作一个有限的资源预算，那么 Skill 的核心贡献不是"增加了能力"——而是**让有限的能力预算分配得更高效**。

在不使用 Skill 的情况下，所有领域知识、工具说明、行为约束都被平铺在系统 prompt 中。无论 Agent 当前处理什么任务，它都必须处理这些信息的认知负载。这就像一个人的工作记忆里同时塞着"怎么写 Python 文件"、"怎么用 Git"、"物理引擎的坐标变换公式"和"今天午饭吃什么"——大量的信息互相争抢有限的注意力。

有了 Skill 后，Agent 的认知负载模式从"全量加载"变为"按需加载"：

- 日常闲聊时，上下文里只有通用的行为规范和少量核心知识
- 需要写入文档时，Agent 读取 doc_write 的 SKILL.md，注入编写规则
- 需要归档时，Agent 读取 doc_archive 的 SKILL.md，注入归档流程
- 执行完后，SKILL.md 的内容不再占用后续推理的上下文

这种按需加载的模式，本质上是在 Agent 的认知架构中引入了一个**懒加载机制**——不是所有知识都在线，而是在需要的时刻才被调入工作记忆。

#### Skill 与提示词工程的关系

一个常见的误解是：Skill 是对提示词工程（prompt engineering）的替代。实际上，Skill 解决的是**提示词的组织、注入时机和注入量**的问题，而不是"要不要用提示词"的问题。

换言之：没有 Skill 的情况下，系统 prompt 就是一份平面的、全量加载的提示词。有了 Skill 后，提示词被拆分为"基础 prompt + 按需注入的子 prompt（SKILL.md）"两级结构。

用数据库的 analogy 来理解：没有索引的全表扫描（平面系统 prompt）vs 有索引的按需查询（desc 路由 + SKILL.md 加载）。Skill 引入了索引层，让提示词的检索效率从 O(n) 降到了 O(log n) 甚至 O(1)。

#### Skill 与其他能力扩展方案的对比

把 Skill 放在更大的技术图景中对比，有助于理解它的定位和边界。以下从几个关键维度对比当前主流的能力扩展方案：

**与传统插件的对比**

传统插件系统（如 IDE 插件、浏览器扩展）的核心模式是"开发者编写代码 → 框架加载执行"。插件的本质是代码模块，在编译或加载时被集成到宿主程序中。

Skill 的核心模式是"编写指引文档 → Agent 读取并执行"。Skill 的本质是指令文档，Agent 通过 LLM 的阅读理解来执行。这个差异决定了：

- 插件能做 Skill 做不到的事（如 OS 级别的系统调用、直接的内存操作）
- Skill 能做插件做不到的事（如根据上下文灵活调整执行策略、自动适应规则变化）
- Skill 的创建门槛远低于插件（写文档比写代码容易得多）

**与 RAG（检索增强生成）的对比**

RAG 解决的是"Agent 在推理时如何获取外部知识"。它的工作流是：用户问题 → 检索数据库 → 获取 top-K 相关段落 → 注入上下文。RAG 侧重的是"知识的即时获取和注入"。

Skill 解决的是"Agent 如何获取和使用能力"。它的工作流是：用户任务 → Agent 判断需要什么能力 → 匹配 Skill → 读取 SKILL.md → 按指令执行。Skill 侧重的是"行为能力的封装和按需加载"。

两者不矛盾。一个典型的 Agent 可能同时使用 RAG（获取领域知识）和 Skill（获取执行指令），知识流动和能力执行是两条独立的管线。

**与微调（Fine-tuning）的对比**

微调是"改变模型本身的能力"——通过在特定数据集上继续训练，让模型在某个领域表现更好。微调的效果一旦固化就无法通过提示词快速调整。

Skill 是"不改变模型，改变模型的输入"——通过在上下文中注入指令来引导模型行为。Skill 的效果是完全可逆的和可组合的。

微调适合"需要深度内化的能力"（如一个行业特有的术语和概念体系），Skill 适合"需要灵活配置的能力"（如文档的编写规范、工具的调用流程）。在实践中，微调和 Skill 也常常配合使用：微调让模型理解领域语言，Skill 让模型按领域规范行动。

### 设计思路

#### desc 分发的设计空间

这是 Skill 机制中技术含量最高、也是最值得深入讨论的环节。当前主流实现（包括 QwenPaw、CoPaw 等框架）大概率采用**全量 desc 推送 + Agent 自行路由**的模型。

以实际数据为例：一个典型的 Agent workspace 中包含约 29 个 Skill。desc 长度从 50 字到 941 字不等，全量推送的 desc 文本约 6000-8000 字。在 128K 上下文窗口下，这部分开销占比不到 10%；但当 Skill 数量增长到 100+ 或上下文窗口较小时，这个占比会显著增加。

但全量推送不是唯一的方案。以下是对不同分发模型的系统性分析：

**模型一：全量推送（当前主流）**

所有 Skill 的 desc 在 Agent 初始化或每轮对话前被注入到上下文中。Agent 自行判断当前任务需要哪些 Skill，按需读取 SKILL.md。

- 优点：实现简单，Agent 可以看到所有能力选项，不会遗漏
- 缺点：desc 数量多时占用认知负载；Agent 需要自行从大量 desc 中选择相关性，这是对推理能力的不必要消耗
- 适用场景：Skill 数量 < 50 个，上下文窗口足够大

**模型二：语义检索（embedding top-K）**

在框架层引入轻量级 embedding 模型（如 bge-small），对用户输入做 embedding 后与所有 Skill 的 desc embedding 做相似度匹配，只将 top-K 的 desc 注入给 Agent。

- 优点：上下文开销大幅降低（从 6000 字降到 1000 字以内）；延迟在毫秒级，比多一轮 LLM 调用便宜得多
- 缺点：召回风险——embedding 匹配失败时，相关 Skill 永远不会被 Agent 看见；依赖 embedding 模型的质量和领域覆盖
- 适用场景：Skill 数量 > 50 个，需要精确路由

**模型三：两阶段加载（索引 + 按需拉取）**

框架层维护一个极轻量的"能力索引"——每个 Skill 只暴露一行签名（例如 `"doc_writing: 文档编写与归档"`，30 字以内）。Agent 在推理过程中看到这个索引，发现自己需要某个能力时主动声明需求，框架再注入对应的完整 desc 或 SKILL.md。

- 优点：上下文开销降到极致（29 个 Skill × 30 字 + 实际命中的 Skill 全文）；结合了全量推送的"可见性"和按需加载的"经济性"
- 缺点：需要 Agent 具备主动声明需求的能力（"知道自己不知道什么"是 LLM 的已知弱项）
- 适用场景：Skill 数量中等，Agent 具备较强的自我认知能力

**模型四：原生 tool calling**

框架将每个 Skill 注册为一个 tool（对应 LLM 的 function calling 接口），暴露 `name` + `description` + `parameters`。Agent 在推理过程中自行决定是否调用某个 tool，调用时框架动态加载 Skill 的执行逻辑。

- 优点：与 LLM 的原生能力对齐；`description` 天然就是精简的 desc；参数定义了输入接口
- 缺点：对 Skill 的建模要求较高——不是所有 Skill 都能被建模为一个 tool（行为指令类 Skill 不适合）
- 适用场景：偏工具调用的主动型 Skill

**小结：设计空间不是一个二选一的问题**

全量推送 vs embedding 筛选是一个伪二选一。实际的设计空间包含多个维度（推送程度 → 索引 → 签名 → tool 注册），不同维度适合不同类型的 Skill。最现实的方案可能是混合模式：工具调用类 Skill 走 tool calling，行为指令类 Skill 走两阶段加载，通用知识类 Skill 走 embedding 检索。

#### 分层路由的可行性

当 Skill 数量进一步增长（到几百个级别），纯 embedding 检索会面临精度瓶颈。可行的应对是**层级式路由**：

1. **粗分类层**：用极轻量的规则（关键词匹配、正则）或分类器，将用户输入先划分到 5-10 个领域
2. **精检索引层**：只在匹配的领域内做 embedding 精排
3. **最终加载层**：Agent 在 top-K 中自行选择加载完整 SKILL.md

这种分层路由在存储和检索领域有成熟的实践（如搜索引擎的倒排索引 + 向量检索），直接迁移到 Skill 分发中即可。

#### Skill 与原生 tool calling 的集成模式

一个值得单独讨论的问题是：框架原生的 function calling（tool calling）与 Skill 机制如何协同工作。这两者不是一个替代关系，而是不同抽象层级的能力扩展方式。

**差异在哪里**

Function calling 是 LLM 协议的底层能力——模型在推理过程中发现"需要调用一个外部函数"，然后以结构化参数的形式发出调用请求，框架拦截后执行并返回结果。这是一个同步的、一次性的交互模式。

Skill 是更高层的能力编排——一个 Skill 可能包含多个步骤，每个步骤可能调用多个 tool，也可能不调用任何 tool（纯知识注入）。Skill 的执行是异步的、多步骤的、有状态的。

用一个类比来理解差异：function calling 是 CPU 指令集（原子操作），Skill 是程序（一系列指令的编排）。

**集成的三种模式**

第一种模式是**Tool 作为 Skill 的执行引擎**。Skill 的 SKILL.md 定义"做什么"，背后的 Python 脚本（如果有）通过 tool 被调用。Agent 读取 SKILL.md 后，按步骤调用对应的 tool，每个 tool 完成一个原子操作。这是目前大多数框架采用的方式——Skill 提供指引和编排逻辑，tool 提供执行能力。

第二种模式是**Skill 注册为 Tool**。框架将每个 Skill 映射为一个 tool，暴露精简的 desc 作为 tool 的 description，Agent 通过 function calling 机制决定是否调用。调用时框架注入 SKILL.md 全文，Agent 按指令执行。这种模式下，Skill 的发现完全交由 LLM 的 function calling 路由，框架不需要额外做 desc 分发。

第三种模式是**Tool 作为 Skill 的发现入口**。框架注册一个特殊的 tool——比如 `request_capability(domain, task)`——Agent 在推理中遇到需要额外能力时，通过这个 tool 声明需求，框架匹配 Skill 后注入 SKILL.md。这是最灵活的方案，但对 Agent 的自我认知能力要求最高。

**实践中的选择**

三种模式不互斥。在实际框架中，最合理的方案是混合使用：

- 对已经明确注册的工具类 Skill（如 PDF 处理、文档生成），走模式一，Skill 定义编排逻辑，tool 提供原子能力
- 对行为指令类 Skill（如回复风格规范、安全约束），走模式二，注册为一个只包含 `description` 的 tool，但内部触发的是 SKILL.md 注入而非函数执行
- 对 Agent 自主探索场景，走模式三，提供 `request_capability` 让 Agent 在需要时主动发现

这个混合方案的要求是框架层面能够区分"tool 调用"和"Skill 加载"两种交互模式，而不是将所有 agent 的行为都归一为 tool calling。

### 进阶讨论

#### Skill 组合的挑战

在实际使用中，Agent 很少在同一时刻只加载一个 Skill。多数任务需要多个 Skill 协同工作——文档归档需要 `doc_judge` → `doc_document_create` → `git_push` 的链式调用。链式调用中，前一个 Skill 的输出作为后一个 Skill 的输入，指令之间可能存在冲突。

根据冲突的来源和表现形式，可以分为三类：

**行为指令冲突**

Skill A 说"回复要简洁"，Skill B 说"输出要详尽"——Agent 同时加载两个 Skill 时，会在两个互相矛盾的指令间摇摆。这类冲突的严重程度为中度：Agent 通常不会报错，但输出质量会下降。

**工具调用冲突**

Skill A 和 Skill B 都试图控制同一个外部工具（如都试图操作文件系统、都试图发送网络请求）。这类冲突的严重程度为高度：可能产生不可逆的副作用（如数据丢失、重复推送等）。

**上下文污染**

Skill A 的领域术语在 Skill B 的语境中有不同的含义。这类冲突的隐蔽程度最高——不会报错、不会产生明显的异常行为，但长期看会导致 Agent 的概念混淆。

**应对方向**

解决 Skill 组合冲突不是一个纯文档层面的问题，但文档层面可以做两件事：**建立分类框架**（让冲突可以被识别和讨论）和**提出设计方向**（让框架设计者有路可走）。

目前业界和实践中涌现了几种思路：

1. **命名空间隔离**：每个 Skill 的指令在自己的作用域内生效，不互相穿透。问题是 LLM 天然不擅长严格的作用域隔离——它倾向于把所有注入的信息当成一个整体来理解。

2. **优先级仲裁**：框架层定义通用优先级规则（如"后加载的覆盖先加载的"、"工具调用类 > 行为指令类"），在冲突时做仲裁。这个方案需要框架层的协同，不是一个 Skill 能独立做到的。

3. **分层注入**：框架层定义一套"基础行为规范"（回复风格、安全边界、输出格式等），其优先级天然高于任何 Skill。Skill 只能在基础规范的约束下定义自己的行为。这相当于宪法 vs 法律的关系——Skill 不能违反框架层的基础规范。

4. **组合契约**：框架预定义常见的 Skill 组合，提前验证这些组合下的指令一致性。这在 Skill 数量少时可行，但组合爆炸会让维护成本失控。

**保守判断**：短期内最务实的是方案 3（分层注入）+ 方案 2 的简化版（框架定义通用优先级规则）。长期看，如果 Skill 生态足够大，方案 4 的"组合契约"模式会变得必要。

#### desc 质量的量化

多次提到"desc 质量决定发现率"，但如何衡量一个 desc 写得好坏？以下是一些可操作的评估维度：

- **触发率**：给定一批任务，该 Skill 被 Agent 正确触发的比例
- **误触率**：该 Skill 被 Agent 在不合适的场景下调用的比例
- **歧义度**：让多个 Agent 判断"这个 desc 是否应该触发"的一致率——一致率越低，歧义度越高
- **信息密度**：desc 中实际用于路由判断的有效信息占比 vs 冗余/装饰性文字占比

如果框架层能采集这些统计数据，Skill 作者就能有数据驱动地优化 desc，而不是凭感觉写。

#### Skill 的生命周期管理

一个 Skill 从被创建到被废弃，经历完整的生命周期。理解这个生命周期对于设计 Skill 和优化框架都很有帮助。

**创建阶段**

Skill 的创建涉及三个产出物：desc（分发签名）、SKILL.md（执行指引）、以及可能配套的资源文件（模板、脚本、配置文件）。创建时机可以是开发者手动编写、框架自动生成、或从其他 Agent 导入。

创建阶段的设计决策会直接影响 Skill 后续的使用效果，尤其是 desc 的质量——因为 desc 一旦发布并被框架索引，修改 desc 会影响正在使用该 Skill 的所有 Agent 的路由行为。

**加载阶段**

加载发生的时机有两种：显式加载（Agent 主动声明需要某个 Skill）和隐式加载（框架根据 desc 匹配自动注入）。加载时框架需要做版本检查——如果 Agent 的当前会话中已经加载了旧版 Skill，是否需要先卸载再加载新版？

加载阶段的核心问题是延迟。如果每次需要 Skill 时才读取 SKILL.md（IO 操作），加上去重和缓存机制的设计，对整体响应时间的影响需要控制。

**执行阶段**

Skill 的执行不是简单地"按照文档做"，而是 Agent 将 SKILL.md 中的指令与当前上下文结合的推理过程。这个阶段最容易暴露的问题：

- **指令的二义性**：SKILL.md 中的自然语言描述可能被 Agent 以不同方式解读
- **上下文的冲突**：SKILL.md 中的规则与 Agent 当前上下文中其他指令的矛盾
- **边界的模糊**：Skill 的执行结果应该影响哪些状态、不改变哪些状态

执行阶段的设计建议是：SKILL.md 中对于关键约束使用"必须/禁止"等明确程度标记，对建议性内容使用"建议/推荐"等弱约束标记，让 Agent 能区分指令的强制程度。

**卸载阶段**

Skill 执行完毕后，其内容应该从 Agent 的上下文中退出。卸载不是简单的文本删除，而是状态的恢复——加载 Skill 可能改变了 Agent 的工具绑定、输出格式偏好、行为约束等，卸载时需要恢复到加载前的状态。

这个环节在实践中几乎被所有框架忽略。当前的主流做法是"靠上下文窗口自然淘汰"——SKILL.md 的内容随着对话的推进逐渐被 Agent 的短期记忆"遗忘"。这在短对话中不成问题，但在长会话中，Skill 的执行效果可能因为上下文信息的衰减而逐轮降低。

**更新阶段**

Skill 的版本管理是一个更棘手的问题。当 SKILL.md 的内容更新后：

1. 当前正在执行的 Agent 会话是否应该获取新版本？
2. 如果应该，如何在不断开推理流程的情况下完成"热更新"？
3. 旧版本产生的中间状态（如缓存的文件路径、临时变量）如何处理？

这些问题目前缺乏系统的工程实践，也是 Skill 生态从"有趣"走向"可靠"必须跨越的障碍。

#### Skill 的设计原则与最佳实践

结合前文的分析，一套看似合理的设计原则开始浮现。这些原则并非绝对真理，而是在当前技术条件下经过实践检验的指引。

**原则一：desc 写触发条件，不写效果**

好的 desc 以"当...时"开头，告诉 Agent 什么情况下使用这个 Skill。糟糕的 desc 以"本文档介绍了..."开头，像一个文档摘要而不是路由签名。

示例：

```
好：当你需要将讨论内容归档为正式文档时，使用本 skill
差：本 skill 介绍了文档归档的流程和规范
```

前者是触发指令，后者是内容摘要。Agent 在路由决策时只需要知道"当前任务是否匹配这个触发条件"。

**原则二：SKILL.md 按步骤组织，不是按概念组织**

Agent 按顺序执行指令的效率远高于从概念解释中自行提炼流程。SKILL.md 应该按照执行顺序组织，而不是按照知识体系组织。每个步骤用明确的标题分层，步骤之间用顺序号或逻辑承接关系串联。

**原则三：明确区分强制约束和推荐行为**

在 SKILL.md 中使用不同的语气和标记来区分"必须这么做"和"建议这么做"。Agent 对指令的加权策略不同——强制约束应该出现在步骤描述中，推荐行为可以放在备注或注意事项中。

**原则四：每个 Skill 只做一件事**

单体 Skill 的问题与单体架构的问题一样：功能耦合、难以测试、组合时冲突概率高。一个 Skill 只聚焦一个原子任务——比如"写入文件"就不应该同时负责"验证文件"和"推送代码"。验证走另一个 Skill，推送走第三个 Skill，通过链式调用串联。

**原则五：声明依赖关系**

如果 Skill A 的执行依赖 Skill B 的成果，应该在 SKILL.md 中明确声明。这不仅帮助 Agent 理解调用顺序，也为框架层的依赖分析和冲突检测提供了数据。

这些原则在实践中需要根据具体场景调整，但作为初始设计指引，它们可以有效降低 Skill 的质量方差。

#### Skill 与安全边界

Skill 的一个重要但常被忽略的职责是**定义安全边界**。当 Agent 获得通过 Skill 执行复杂操作的能力时，哪些可以做、哪些不能做、哪些需要先问用户，应该在 Skill 的约束中明确声明。

**安全边界的分层**

安全约束在 Skill 体系中天然分为三层：

1. **框架层安全约束**：运行时强制执行的安全策略，如"禁止删除用户文件"、"禁止对外发送未授权消息"。这是铁律，任何 Skill 都不能违反。

2. **Skill 层安全约束**：Skill 作者在 SKILL.md 中声明的安全规则，如"执行此操作前先确认用户意图"、"操作完成后验证结果"。这些约束只在这个 Skill 的生效范围内有效。

3. **Agent 层安全约束**：Agent 自身的推理安全策略——即使框架和 Skill 都没有明确禁止某个操作，Agent 也应该基于通用安全原则自行判断。

这三层安全边界的关系类似容器安全模型：框架层是宿主机的安全策略（不可绕过），Skill 层是容器的安全配置（在框架约束内生效），Agent 层是应用进程自身的安全意识（在三层中优先级最低但也最灵活）。

**Skill 中的操作分级**

一个实用的设计模式是在 SKILL.md 中将操作进行分级，让 Agent 在执行不同级别的操作时采取不同的策略：

| 操作级别 | 特征 | 执行策略 |
|---|---|---|
| 无副作用 | 只读取、只查询、只计算 | 直接执行，无需确认 |
| 低副作用 | 创建新文件、写入新内容 | 执行后验证结果 |
| 中副作用 | 修改已有内容、覆盖文件 | 先列出变更再执行 |
| 高副作用 | 删除文件、发送消息、调用外部 API | 必须先问用户 |

这套分级机制可以有效防止 Agent 在执行复杂 Skill 时"做了不该做的事"，同时避免每次操作都问用户带来的体验损害。

**白名单 vs 黑名单思维**

在 Skill 的安全边界设计中，白名单思维（"明确列出允许的操作"）比黑名单思维（"列出禁止的操作"）更可靠。原因很简单：黑名单永远无法穷举所有不安全行为，而白名单限定了行为空间后，Agent 在空间内的任何操作都是可控的。

但这在实践中很难做到极致。多数 Skill 采取混合策略：框架层用白名单限死边界（"哪些工具有权限，哪些没有"），Skill 层用黑名单做补充约束（"即使有工具权限，此操作仍需谨慎"）。

当前业界对 Agent 能力的标准化有明确的技术演进趋势：

- **Anthropic MCP（Model Context Protocol）**：一个标准化的协议，定义了 Agent 如何发现、认证、调用外部工具。MCP 更侧重"工具发现的标准化"，讨论的是 Agent 与外部世界的交互协议。
- **OpenAI function calling**：在 LLM 层面对工具调用做了原生支持，Agent 通过 `function_call` 参数声明要调用的工具。这是最底层的能力扩展方式。
- **LangChain tools**：在应用框架层对工具做了封装，提供了一套统一的工具注册和调用接口。

这些方案与本文讨论的 Skill 的关系是：**Skill 是一个更广义的能力封装概念**——它包含但不限于"工具调用"。一个 Skill 可以定义 Agent 的行为风格、领域知识、输出约束，这些是 function calling 和 MCP 无法涵盖的。

在技术栈中的具体定位：

- MCP 定义了**Agent 如何发现和使用外部工具**（通信协议层）
- function calling 定义了**LLM 如何发出工具调用请求**（推理交互层）
- Skill 定义了**Agent 应该在什么条件下、以什么方式、按照什么规则使用这些能力**（行为编排层）

所以 Skill 并不是这些方案的替代品，而是对它们的**补充和编排**——在通信协议和推理接口之上，提供了一个能力编排和行为约束的抽象层。

#### 一个具体的 Skill 实践：从讨论到归档的完整流程

为了将这些抽象讨论落地，以一个真实的 Skill 使用场景为例。这个例子来自实际使用中的文档管理 Agent——它负责管理三个文档库，每天执行文档写入、修改、归档等操作。

**场景：将一条关于 Agent Skill 的日常讨论归档为正式文档**

**使用的 Skill 链：**

1. **doc_judge**：判断内容的文档归属。通过三步流程（关键词匹配 → 决策树 → 公开性检验）确定这段讨论属于 Tech-Docs/AI工程化。

2. **doc_stash**：在讨论过程中存储中间内容。每次讨论的要点被追加到暂存文件中，标记发言人、时间戳和讨论状态。

3. **doc_review_with_toolman**：归档前让另一个 Agent（墨锋）审阅讨论内容。固定三轮，每轮追问和回应都追加到暂存文件。

4. **doc_document_create**：读取暂存文件，按模板生成正式文档。文档正文遵循 15 条自查标准，确保独立文章质量而非对话总结。

5. **git_push**：将生成的文档推送到远端 Git 仓库。

6. **doc_archive**：最终的归档流程——创建正式文档 → 创建历史记录 → 删除原始日常记录 → Git 推送 → 清理检验。

**这个流程揭示了几个重要事实：**

第一，Skill 是高度内聚的。每个 Skill 只负责一个原子任务（判断、暂存、审阅、编写、推送），组合起来完成复杂任务。链式调用中，前一个 Skill 的输出文件路径作为后一个 Skill 的输入参数。

第二，Skill 的粒度设计直接影响组合灵活度。如果把"判断→暂存→审阅→编写→推送→归档"写成一个超大 Skill，虽然减少了一次调用的数量，但失去了中间状态的可见性和可调试性。当某个步骤失败时（如 Git 推送失败），细粒度的 Skill 组合允许只重试失败的步骤而不是整个流程。

第三，Skill 之间存在隐式依赖。`doc_document_create` 假设暂存文件已经被 `doc_stash` 写入且非空。`doc_archive` 假设 `doc_document_create` 已经成功返回文件路径。这些依赖没有在框架层显式声明，而是通过 SKILL.md 中的文字描述来保障——这正是文档型指令集的局限性，也是未来可以工程化改进的方向。

**这个实践案例的推广价值**：它说明了一个 Skill 生态从"设计"到"落地"需要的不是单一框架的完美设计，而是三个层次的成熟度同时到位——框架层的分发能力、Skill 作者的文档编写质量、Agent 对 Skill 指令的阅读理解能力。这三者中任何一个成为短板，都会限制 Skill 的实际可用性。

- **Skill 的版本管理与兼容性**：Skill 更新后，Agent 的短期记忆（当前会话上下文）里残留的旧版 Skill 行为模式可能导致行为不一致。跨会话的 Skill 版本切换是否有状态泄漏的风险？目前缺乏系统讨论。
- **多 Agent 系统中的 Skill 共享模型**：在多 Agent 系统中，Skill 的所有权、权限、可见性怎么设计？一个 Agent 创建的 Skill 能否被另一个 Agent 发现和使用？目前没有成熟的模型。
- **实际的数据验证**：本文对 desc 分发的推测（"大概率全量推送"）缺乏实际的 token 使用量统计和 Skill 使用频率分布数据。如果能补上这些数据，论证的说服力会显著提升。

### 总结

回到开头的问题：为什么不能把规则全塞进 system prompt？

因为 Agent 的认知资源是有限的。需要将有限的工作记忆分配给当前最重要的任务，而不是被所有可能但不一定相关的规则淹没。

Skill 提供了一个优雅的解决方案：**把能力封装成按需加载的模块（SKILL.md），通过精简的签名（desc）做路由和分发，让 Agent 在需要时获取完整指引，不需要时不浪费认知资源。**

这不是"要不要用提示词"的问题，而是"提示词怎么组织、什么时候注入、注入多少"的问题。Skill 引入了索引和懒加载机制，将提示词的管理从 O(n) 的全量平面模式提升到了 O(log n) 的按需检索模式。

Skill 的三个核心价值——降低执行方差、路由指令、上下文预算管理——层层递进，一个比一个深刻。理解这三层价值的设计者，才能设计出好的 Skill；理解这三层价值的框架开发者，才能设计出好的分发机制；理解这三层价值的 Agent，才能真正发挥 Skill 的潜力。

梳理全文，可以提炼出几条核心认知：

**认知一：Skill 不是文档，是可执行的指令集。** 它改变 Agent 的行为，而不只是提供信息。所以编写 Skill 时的思维模式不应该是"怎么写一份用户手册"，而是"怎么定义 Agent 在某个任务中的执行协议"。

**认知二：desc 和 SKILL.md 是两个独立的设计问题。** desc 决定发现率（Agent 能否找到这个 Skill），SKILL.md 决定完成率（找到之后能否正确执行）。两个问题需要的技能不同，不能混为一谈。当前社区对 SKILL.md 的重视程度远高于 desc，但实际瓶颈更可能在 desc 端——一个 Agent 找不到的 Skill 写得再好也没有意义。

**认知三：Skill 的分发机制本身就是一个设计空间。** 全量推送只是最简单的实现，不是唯一解。当 Skill 数量增长时，框架层需要引入更差异化的分发策略——embedding 检索、两阶段加载、tool calling 注册、分层路由——不同的策略适合不同类型的 Skill 和不同规模的生态。

**认知四：Skill 的出现重新定义了提示词工程的边界。** 在 Skill 出现之前，提示词工程的核心问题是"怎么写好一份 prompt"。在 Skill 出现之后，问题变成了"怎么组织一个 prompt 系统"——基础 prompt、按需注入的 Skill、Skill 之间的组合与冲突处理，这是一个从"单文件"到"多模块"的范式转换。

最后，用一个更短的类比收束：**如果把 Agent 比作操作系统，Skill 就是它的驱动程序。插上驱动，硬件能用；拔下驱动，系统不崩溃。驱动可以独立升级，可以多个程序共用，可以在不重启系统的情况下热插拔。**

Agent 的 Skill，就是这场 AI 操作系统生态中正在被构建的基础设施。它不可能在一个晚上就变成完整的系统——但它的设计方向和工程实践，正在让 Agent 从一个"能做很多事但什么都不太靠谱"的通用工具，进化为"在特定领域持续稳定输出"的专业助手。这种演化不需要等下一个大版本的模型更新，而是可以通过更好的 Skill 设计和分发机制，在现有模型能力的基础上实现。

这是 Skill 作为"能力模块化"的最终意义：它让 Agent 的能力进化从"等待模型变强"变成了"设计更好的 Skill"，从等待 GPU 算力的突破，变成了等待更好的工程思维。在可预见的未来，Skill 的设计质量会成为 Agent 能力上限的一个关键变量，甚至可能比模型本身的参数规模更重要——因为 Skill 决定了同样的模型能力，在具体场景下能发挥出百分之几。
