# Unity 3D 数学进阶话题与性能优化：从算法到工程治理

## 摘要
当项目规模扩大后，3D 数学问题不再只是“公式会不会写”，而会演变为数据如何组织、物理模拟如何稳定、查询规模如何降低、计算热点如何证明、批量处理如何落地、调试工具如何可视化、团队规范如何沉淀。对象数量从几十增长到几千，AI 感知从单目标变成群体扫描，物理对象从简单盒子变成复杂角色控制器，地图从小关卡变成开放世界时，向量、矩阵、射线、碰撞和几何算法都必须进入系统设计层面。

本文作为 Unity 3D 数学与物理基础的进阶治理篇，围绕空间数据结构、物理步长、碰撞检测模式、数值稳定性、数学性能优化、GC 控制、数据布局、Unity.Mathematics、Job System、Burst、Compute Shader、程序化生成、AI 数学、可视化调试、性能基线和团队数学基础设施展开。重点不是堆叠高阶名词，而是建立判断框架：什么时候直接遍历，什么时候上空间结构；什么时候依赖物理引擎，什么时候先做数学粗筛；什么时候用 Job/Burst，什么时候保持简单；什么时候优化公式，什么时候优化数据规模。

## 正文

### 背景
完成向量、旋转、坐标系、射线碰撞和几何算法的学习后，开发者已经具备解决大多数局部空间问题的工具。但真实项目不会停在局部问题上。一个距离判断可能被 AI 系统每帧调用几十万次；一个射线查询可能被相机、瞄准、交互和遮挡系统同时使用；一个看似无害的物理设置可能在低帧率下造成穿透；一个曲线采样工具可能被程序化生成、相机轨迹和编辑器批量调用。此时，问题的核心不再是公式，而是规模、生命周期、数据布局和验证方式。

进阶数学治理需要回答四类问题。第一，数据如何组织，才能避免全场遍历。第二，模拟如何稳定，才能避免抖动、穿透和帧率相关行为。第三，计算如何优化，才能在不破坏规则正确性的前提下降低成本。第四，团队如何沉淀，才能让几何、物理、AI、调试和性能基线成为共享基础设施，而不是个人经验。

### 核心原理
#### 一、进阶的核心是系统边界，而不是更复杂的公式
初学 3D 数学时，重点是点积、叉积、四元数、射线、矩阵和包围体。进入项目级开发后，重点会变成：哪些计算属于规则层，哪些属于表现层；哪些是热点，哪些只是低频逻辑；哪些应该依赖物理引擎，哪些应该自己做数学过滤；哪些逻辑应该放在 FixedUpdate，哪些应该放在 Update；哪些优化必须用目标设备验证。工程视角没有单一公式，但它决定系统能否长期稳定运行。

高级技术只有在边界清楚时才有价值。空间哈希、八叉树、Job、Burst、Compute Shader、BVH 都不是越早使用越好。若对象数量不大、数据变化不复杂、可读性更重要，简单遍历可能是更好的工程选择。反之，当规模明显超过单线程直接遍历能力，仍坚持简单写法也会成为瓶颈。

#### 二、空间数据结构用于减少候选对象数量
如果场景只有 20 个敌人，遍历所有目标做距离判断完全可接受。如果场景有 5000 个可交互物、2000 个单位、10000 个掉落物，每帧全量遍历就会成为灾难。空间数据结构的目标是把“全场遍历”变成“只查附近”。

常见结构包括 Uniform Grid、Spatial Hash、Quadtree、Octree、BVH 和 KD-Tree。它们不是越高级越好，而要根据对象分布、动态程度、查询类型和实现成本选择。对象少时直接遍历；对象多且分布相对均匀时，统一网格或空间哈希通常最实用；对象多且静态时，可以考虑四叉树、八叉树或 BVH；大量射线对静态几何时，BVH 更合适；动态单位频繁移动时，空间哈希往往比树结构更稳。

#### 三、统一网格与空间哈希适合动态对象附近查询
统一网格把世界划分为固定大小的格子，每个对象根据位置放入某个格子。查询附近对象时，只检查周围格子。空间哈希是统一网格的稀疏版本，不为所有格子分配数组，而通过哈希表只存有对象的格子。

适用场景包括 2D/2.5D 地图、大量均匀分布单位、掉落物、弹幕、采集物和服务端 AOI 粗略管理。优点是实现简单、插入删除便宜、查询可预测；缺点是格子大小难选，对象分布极不均匀时效率下降，超大对象跨多个格子需要特殊处理。工程落地时必须提供可视化，显示格子、对象数量和查询范围，否则很难调参。

#### 四、四叉树、八叉树和 BVH 更适合低频变化或静态数据
四叉树用于 2D，八叉树用于 3D。它们将空间递归划分为更小区域，当某区域对象数量超过阈值时继续细分。它们适合对象分布不均匀、大范围空间查询、静态或低频更新对象、场景剔除和编辑器工具。缺点是实现复杂，动态对象频繁移动会导致更新成本，树退化时需要重建或平衡策略。

BVH 不固定切空间，而是根据对象包围体建立层次。父节点包围子节点，查询时如果射线或范围不与父节点相交，就能跳过整个子树。BVH 适合光线追踪、大量三角形求交、静态复杂网格、自定义碰撞加速和程序化网格查询。一般玩法开发未必需要手写 BVH，但理解它有助于理解 MeshCollider、渲染剔除和复杂查询的加速思想。

#### 五、FixedUpdate 与 fixedDeltaTime 决定物理模拟节奏
Unity 的物理模拟按固定时间步推进。`FixedUpdate` 与渲染帧率不是一回事。帧率高时，多个渲染帧之间可能没有物理步；帧率低时，一帧内可能执行多次 FixedUpdate 追赶物理时间。与 Rigidbody 相关的力、速度、MovePosition、MoveRotation 和物理状态闭环逻辑通常应放在 FixedUpdate。

`fixedDeltaTime` 不是越小越好。减小步长可以提高物理精度，但会增加 CPU 成本。普通项目不应轻易修改全局 fixedDeltaTime。高速物体优先考虑连续碰撞、Raycast、SphereCast 或局部扫掠方案，而不是全局提高物理频率。任何全局步长改动都必须在目标设备压力测试，并观察低帧率下多次 FixedUpdate 是否造成峰值卡顿。

#### 六、碰撞检测模式要服务具体速度与精度需求
高速物体穿透薄墙是离散碰撞的典型问题。Rigidbody 的 Collision Detection Mode 可以缓解，但成本不同。Discrete 便宜，适合大多数物体；Continuous 适合高速动态物体对静态或运动学物体的穿透防护；Continuous Dynamic 更贵，适合高速动态物体之间。

高速子弹的最佳方案未必是动态刚体连续碰撞。许多射击游戏会使用 Raycast 或 SphereCast 表示一帧内的弹道段，这更可控，也更便于做穿透、反弹和命中排序。连续碰撞模式不是万能补丁，应结合对象数量、速度、碰撞体厚度和玩法需求选择。

#### 七、数值稳定性问题来自时间步、碰撞体、质量和移动方式共同作用
物理不稳定常见表现包括物体抖动、角色卡墙、高速穿透、堆叠物体爆炸、关节疯狂甩动、斜坡移动异常和网络同步发散。常见原因是直接修改 Transform 移动 Rigidbody、FixedUpdate 与 Update 混用状态、碰撞体太薄或太复杂、质量比例极端、时间步过大、Solver Iterations 不足、非均匀缩放影响碰撞体、物体初始重叠或施加力过大。

处理时应先简化碰撞体，确认移动方式正确，降低速度或使用扫掠检测，检查 Layer Collision Matrix，检查质量、阻尼、摩擦、弹性，必要时调整 Solver 参数，并使用 Physics Debugger 和 Gizmos 可视化。不要一开始就调全局参数掩盖局部设计问题。

#### 八、数学性能优化应先减少规模，再优化公式
优化顺序非常重要。推荐流程是：用 Profiler 确认热点；减少调用次数；降低候选数量；缓存不变结果；使用平方距离；避免 GC Alloc；整理数据布局；使用 Job/Burst 或 Compute Shader；最后才考虑公式近似。不要一开始就手写近似三角函数，也不要在没有数据时假设某个 API 一定慢。

例如 AI 找最近敌人，不应对全场目标调用 `Vector3.Distance`。更稳的方案是先通过空间结构得到附近候选，再用平方距离比较，最后只对需要显示、衰减或排序的少量对象计算真实距离。规模控制通常比公式微优化更有收益。

#### 九、GC 优化要关注数学代码周边
数学运算本身不一定产生 GC，但周边写法会产生：每帧 new List、RaycastAll 返回数组、LINQ 查询、字符串拼接日志、装箱、闭包、接口枚举、临时数组排序。高频数学与物理查询中应复用数组和 List，使用 NonAlloc 查询，避免 LINQ，日志加条件编译，缓存比较器和委托，预分配容量，用 Clear 而不是反复 new。

GC 问题通常不是算法公式本身，而是实现习惯。越靠近热路径，越要检查分配。

#### 十、数据布局决定批量计算的上限
当数量上来后，瓶颈常常不是单个公式，而是数据访问方式。MonoBehaviour 分散在内存中，组件查询和对象引用跳转会降低缓存效率。面向批量计算的思路是：从对象上采集必要数据，写入连续数组，批量计算，再写回结果。

例如 AI 感知评分可以把目标位置、阵营、威胁值快照为结构体数组。这样后续更容易迁移到 Job/Burst，也更方便做性能测试。数据布局优化通常比在对象图中到处调用 Transform 更稳定。

#### 十一、Unity.Mathematics、Job System 与 Burst 适合大规模可批处理问题
`UnityEngine.Vector3` 适合常规 MonoBehaviour 业务。对于大规模数学计算，`Unity.Mathematics` 提供 `float3`、`quaternion`、`float4x4` 和 `math` 函数，更接近 SIMD 和 Shader 风格，也更适合 Burst 编译。

适用场景包括大量点距离计算、批量可见性测试、程序化网格生成、大量弹幕轨迹、粒子或单位行为评分、空间结构更新、自定义物理近似。但不要为了技术先进把所有代码都改成 Job。Job/Burst 有数据转换成本、调度成本和调试成本，只有批量规模足够大且数据能整理成 NativeArray 等连续结构时，收益才明显。

#### 十二、Compute Shader 是 GPU 大规模并行方案，不是通用替代品
Compute Shader 适合 GPU 上的大规模并行任务，例如粒子模拟、布料近似、群体行为、图像处理、体素或地形生成、大量无强分支的并行计算。但它不适合所有数学计算，因为存在数据传输成本、平台兼容性、调试难度和 CPU 玩法逻辑同步复杂等问题。

选择 Compute Shader 前要问：数据规模是否足够大，是否可以并行，是否需要频繁读回 CPU，目标平台是否支持，调试工具是否具备，是否已有更简单的 Job/Burst 方案。GPU 方案若需要频繁回读 CPU，收益可能被同步成本抵消。

#### 十三、程序化生成需要可复现、可缓存、可调试
程序化生成依赖噪声、细胞自动机、L-System、Voronoi、Delaunay、随机采样等数学工具。工程要点是随机种子必须可控，生成过程应可复现，参数要可视化调试，离线生成与运行时生成要分开评估，大规模生成需要分块和异步，生成结果要能序列化或缓存，规则层随机与表现层随机要区分。

如果生成结果影响玩法，必须能复盘；如果只影响表现，也应保证目标设备性能可控。程序化内容不是随机堆叠，而是受约束的内容生产系统。

#### 十四、AI 数学必须可解释
AI 系统大量使用数学：距离用于接近和威胁评估，点积用于视野角度，射线用于视线遮挡，曲线用于路径平滑，图论用于寻路，概率用于行为选择，评分函数用于目标选择和技能释放，空间结构用于快速找附近目标。

AI 评分必须可调试。建议在编辑器或调试面板中显示每项分数、距离、角度、遮挡结果、最终权重和选择理由。否则策划只会感觉“AI 很怪”，程序也很难定位。数学驱动的 AI 越复杂，越需要透明度。

#### 十五、可视化调试是高阶系统的基础设施
越高阶的数学系统，越需要可视化。应可视化空间网格、八叉树节点、AI 视野、查询半径、射线命中、路径曲线、法线与切线、速度与加速度、包围盒、生成区域、物理接触点。调试可视化不应只是临时 Debug.DrawLine，而应成为工具：支持开关、选中对象过滤、颜色区分、数值标签、运行时开关和关键帧记录。

没有可视化的数学系统，排查成本会随着项目规模快速上升。

#### 十六、性能优化必须保护规则正确性
优化有适用范围。平方距离适合比较，但不适合代替真实距离进入线性衰减公式；近似角度适合表现，但不适合严格命中判定；降低检测频率适合 AI 感知，但不适合即时格挡；缓存可以减少计算，但必须处理数据失效。

错误示例：

```csharp
float damage = baseDamage - sqrDistance * falloff;
```

如果设计需要线性距离衰减，应先得到真实距离：

```csharp
float distance = Mathf.Sqrt(sqrDistance);
float damage = baseDamage - distance * falloff;
```

若要避免开方，就应重新设计衰减曲线并与策划确认，而不是偷偷替换。

#### 十七、性能优化必须有基线
没有基线的数据不是优化，而是猜测。每次优化前后应记录测试场景、对象数量、平台设备、平均帧耗时、峰值帧耗时、GC Alloc、CPU/GPU 瓶颈、内存变化、误差范围和玩法影响。

优化文档至少说明问题、方案、结果和限制。例如 AI 感知每帧遍历 3000 个目标，改为空间哈希加分帧检测后，主线程耗时从 4.8ms 降到 0.7ms，但感知最多有 0.2 秒延迟。这样的记录才构成工程闭环。

### 设计思路
#### 一、空间哈希落地方案
空间哈希适合动态对象附近查询。核心是把世界位置映射到格子坐标：

```csharp
Vector2Int GetCell(Vector3 position)
{
    return new Vector2Int(
        Mathf.FloorToInt(position.x / cellSize),
        Mathf.FloorToInt(position.z / cellSize));
}
```

实现时要维护格子到对象列表、对象到当前格子的反向索引。对象移动后更新格子，查询半径换算成格子范围，返回候选集后仍用平方距离精确过滤。必须提供调试视图显示格子占用和查询范围。

#### 二、物理移动规范
Rigidbody 控制建议采用输入缓存加 FixedUpdate 应用：

```csharp
public sealed class RigidbodyMotor : MonoBehaviour
{
    [SerializeField] private Rigidbody rb;
    [SerializeField] private float speed = 5f;

    private Vector3 desiredMove;

    public void SetInput(Vector3 move)
    {
        desiredMove = Vector3.ClampMagnitude(move, 1f);
    }

    private void FixedUpdate()
    {
        Vector3 delta = desiredMove * speed * Time.fixedDeltaTime;
        rb.MovePosition(rb.position + delta);
    }
}
```

规则是输入在 Update 采集，物理位移在 FixedUpdate 应用，不直接修改动态 Rigidbody 的 Transform，高速位移使用扫掠检测，表现平滑通过插值或渲染层处理。

#### 三、数学工具库目录建议
建议建立统一目录：

```text
Runtime/
  Math/
    MathConst.cs
    FloatCompare.cs
    GeometryUtil.cs
    CurveUtil.cs
    SpaceConvertUtil.cs
    PhysicsQueryUtil.cs
  Debug/
    DebugDraw.cs
    GeometryGizmos.cs
  Tests/
    GeometryUtilTests.cs
    CurveUtilTests.cs
```

每个工具函数都应说明输入空间、输出空间、是否允许零向量、是否返回平方距离、epsilon 策略、典型用途和不适用场景。

#### 四、性能基准场景
建立 BenchmarkScene，例如 RangeQuery、Raycast、DistanceCheck、CurveSampling、AIScoring、SpatialHash。每个场景提供对象数量配置：100、1000、5000、10000、50000。输出耗时、GC Alloc、命中数量、查询次数、峰值和平均值。性能测试必须能在目标设备运行，不能只看编辑器。

#### 五、优化决策流程
推荐流程：

```text
发现问题
 -> Profiler 确认热点
 -> 判断是算法规模、数据布局、GC、物理查询还是渲染问题
 -> 设计最小优化方案
 -> 验证正确性
 -> 压测性能
 -> 记录结果和限制
 -> 沉淀工具或规范
```

没有 Profiler 数据时不要先优化。直觉可以作为线索，但不能作为结论。

#### 六、代码评审清单
进阶数学和物理代码提交时检查：是否有明确空间语义；是否区分规则层和表现层；是否使用平方距离但没有误用到真实距离公式；是否处理零向量和退化几何；是否有 epsilon 策略；是否产生 GC；是否可视化调试；是否有单元测试或测试场景；是否在目标规模验证；是否需要空间结构；是否真的需要 Job/Burst/Compute；是否写明适用范围和限制。

#### 七、团队落地路线
初期团队先做 GeometryUtil、SpaceConvertUtil、PhysicsQueryService、DebugDraw 和常见算法文档。中期补空间哈希、AI 感知批处理、曲线工具、性能基准场景和自动化测试。后期再考虑 Job/Burst 批量化、Compute Shader、自定义空间树、程序化生成工具链和运行时性能监控。路线不要反过来。没有基础工具和测试，过早引入复杂并行技术会显著增加调试成本。

### 进阶讨论
进阶数学治理的第一类取舍，是简单直接与可扩展之间的取舍。对象少时直接遍历最清晰；对象多时空间结构必要。过早抽象会让小项目变复杂，过晚治理会让大项目卡在性能瓶颈中。判断依据应是数据规模、增长趋势、调用频率和目标设备，而不是技术偏好。

第二类取舍，是精度与稳定之间的取舍。更小 fixedDeltaTime、更高 Solver Iterations、更复杂 Collider 和连续碰撞模式都可能提升精度，但也会增加成本。很多稳定性问题应先通过移动方式、碰撞体设计和局部扫掠解决，而不是直接提高全局模拟成本。

第三类取舍，是 CPU 与 GPU 的工作分配。Job/Burst 适合 CPU 批量数学，Compute Shader 适合 GPU 大规模并行。若结果需要频繁回到 CPU 参与玩法决策，Compute Shader 可能不合适；若数据无法整理成连续数组，Job/Burst 收益也会受限。选择并行方案时，应把数据流和同步成本一起计算。

第四类取舍，是优化与规则正确性的取舍。性能优化不能偷偷改变玩法曲线、命中精度和响应时机。降低 AI 感知频率会引入延迟，使用平方距离可能改变衰减语义，分帧检测可能影响即时反应。所有这类变化都应显式记录并与设计目标对齐。

最后，进阶治理必须沉淀为团队基础设施。MathUtil、GeometryUtil、PhysicsQueryService、SpaceConvertUtil、DebugDrawSystem、BenchmarkScene、单元测试、编码规范和 Cookbook，能让常见算法不再依赖个人发挥。团队共享能力越强，项目中的空间问题、物理问题和性能问题越可控。

历史项目推进进阶治理时，应避免一次性替换所有基础系统。更稳的路线是先建立观测能力和基准场景，确认哪些系统真的存在规模问题，再逐步把重复算法收敛到公共工具层。比如先统计 AI 感知调用次数和候选数量，再决定是否引入空间哈希；先记录物理查询 GC 和缓冲区溢出，再决定是否统一 NonAlloc；先测量曲线采样和路径系统开销，再决定是否批量化。没有观测的重构，很容易变成风险很高的架构改造。

进阶治理还需要区分运行时系统和编辑器工具。编辑器工具可以接受更高单次计算成本，但必须提供清晰可视化和可复现结果；运行时系统更关注稳定帧耗时和低端机表现；构建管线或离线生成则可以把重计算前移，用缓存和序列化换取运行时轻量。把这三类场景混在一起，会导致优化目标冲突。

此外，团队应为数学工具建立变更纪律。底层函数一旦被多个系统依赖，修改 epsilon、返回语义、坐标空间或边界包含规则，都可能影响技能、AI、相机和物理。公共数学工具的修改应有测试、回归说明和版本记录，不能像普通业务脚本一样随手调整。
最终，进阶优化的价值不只在于单次性能收益，而在于让项目面对规模增长时仍有清晰的选择路径、验证路径和回滚路径。这样复杂技术才不会成为少数人的隐性知识，而会成为团队可以持续使用的工程资产。
当工具、基线、可视化和评审规则共同存在时，团队就能在直接遍历、空间结构、Job/Burst、Compute Shader 和离线生成之间做出有证据的取舍，而不是被技术名词牵着走，也不会被短期热点反复打乱工程节奏和交付节奏与维护节奏。

## 知识缺口
- 空间结构选型、Job/Burst 收益、Compute Shader 可行性、物理稳定参数、性能预算和基准阈值会随 Unity 版本、平台、数据规模、渲染管线和项目架构变化；正式方案应以项目锁定版本、目标设备和实测基线为准。

### 总结
进阶数学与优化的核心，不是掌握更多听起来高级的名词，而是能在复杂项目中做正确选择。对象少时直接遍历就够；对象多时考虑空间结构；物理不稳定时先检查时间步、移动方式和碰撞体；数学热点出现时先减少规模，再考虑平方距离、缓存、批量化、Job/Burst 或 Compute Shader；优化前后必须有数据验证。

成熟的 Unity 开发者不只是会写公式，还要知道公式属于哪个系统、运行在哪个生命周期、会不会分配内存、在目标设备上是否稳定、能不能被调试、能不能被团队复用。数学基础设施一旦沉淀下来，项目中的空间问题、物理问题和性能问题都会更可控。
