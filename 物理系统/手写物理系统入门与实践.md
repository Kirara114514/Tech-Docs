# 手写物理系统入门与实践

### 背景

手写物理系统的价值并不在于重新制造一个通用物理引擎。成熟引擎已经把碰撞检测、约束求解、稳定性修正、多线程调度和平台适配做到了很高的工程密度，普通项目没有必要用一套自制系统去替代它。真正值得手写的场景，是项目对物理行为有明确的可控性要求：平台跳跃需要稳定的落地判定，格斗动作需要精确的受击窗口，弹幕或子弹需要确定性轨迹，Replay 和网络同步需要复现同一帧的结果，教学或工具项目需要把物理过程拆开观察。

因此，手写物理系统的第一原则是缩小目标。一个入门系统不应该一开始追求完整刚体动力学、复杂多边形碰撞、旋转惯量、摩擦锥、关节约束和连续碰撞的全量能力，而应该先回答三个基本问题：物体如何在固定时间步中运动，两个简单形状如何判断接触，接触发生后如何用稳定而可解释的方式改变速度与位置。只要这三个问题被讲清楚，一个极简系统就已经具备了工程意义。

内置物理系统通常以黑盒形式暴露接口，调用方设置质量、摩擦、弹性、碰撞层级，然后等待模拟结果。黑盒接口适合通用生产，但不适合解释异常。当角色贴墙抖动、箱子堆叠爆开、高速子弹穿墙、浮动物体逐渐漂移时，只看 API 很难判断问题来自时间步、碰撞形状、速度积分、接触法线、冲量求解还是位置修正。手写系统的训练意义正在这里：它把物理模拟拆成可观察的阶段，让问题不再被笼统地归因于“物理不稳定”。

本篇文档讨论的是一套用于学习和轻量定制的二维物理系统。它不是通用引擎，也不承担复杂生产级刚体模拟的全部责任。目标是构建一个包含刚体状态、固定步进、AABB 与圆形碰撞、接触生成、冲量响应、位置修正和基础调试能力的系统，并说明每个环节背后的取舍。只要系统边界清楚，它就可以成为项目中的局部物理层，也可以成为理解成熟物理引擎的入口。

### 核心原理

#### 一、物理系统本质上是离散时间中的状态推进

游戏中的物理模拟不是连续真实世界，而是在一系列离散时间点上更新状态。每一帧或每一个固定物理步，系统读取当前状态，计算外力、速度变化、位置变化、碰撞关系和约束修正，然后得到下一步状态。这个过程看似简单，却决定了物理系统的全部稳定性。

如果时间步长不固定，同一段运动会因为帧率波动产生不同结果。速度积分是乘以 `dt` 的过程，碰撞检测也依赖本步位移。当 `dt` 时大时小，穿透深度、接触顺序和修正幅度都会变化。一个在 120 FPS 下稳定的角色控制器，可能在 30 FPS 下穿墙或弹飞，并不是因为公式错了，而是因为离散步长改变了约束求解的条件。

固定时间步的意义，是让系统在稳定粒度下推进。渲染帧可以波动，物理帧必须尽量稳定。常见做法是使用累积器：把渲染帧传入的时间累积起来，每次消耗固定的 `fixedDt` 执行一次物理步。这样可以让不同渲染帧率下的物理行为更接近，也便于回放、测试和同步。

极简步进可以表达为：

```text
accumulator += frameDelta
while accumulator >= fixedDt:
    step(fixedDt)
    accumulator -= fixedDt
```

这段伪代码背后的重点不是循环，而是物理系统与渲染系统解耦。渲染负责表现，物理负责状态。若把两者混在一起，调试时就很难区分画面插值问题和真实状态问题。

#### 二、刚体状态应保持小而稳定

入门物理系统的刚体不需要一开始拥有完整引擎级属性。一个可用的二维刚体至少需要位置、速度、质量、逆质量、碰撞体、弹性系数和静态标记。质量用于决定外力如何转化为加速度，逆质量用于让冲量计算更直接，静态标记用于表达不会被推动的世界物体。

逆质量是一个关键设计。质量越大，同样冲量带来的速度变化越小；质量为零或无穷大时，对象可以视为静态。与其在公式中不断处理质量除法，不如把 `inverseMass` 存为核心属性。动态物体有正逆质量，静态物体逆质量为零。这样，求解器只需要按逆质量分配速度和位置修正即可。

刚体状态越复杂，入门系统越容易失控。旋转、角速度、惯量张量、材质组合、睡眠机制、摩擦模型和关节约束都很重要，但它们会显著增加调试空间。学习阶段应先保持线性运动的闭环稳定：重力能让物体下落，碰撞能阻止穿透，冲量能反映反弹，位置修正能消除残余重叠。这个闭环稳定后，再逐步加入旋转和摩擦。

#### 三、积分方法决定能量误差的形态

物理系统需要把力变成速度，再把速度变成位置。最简单的积分方式是显式欧拉：先用当前速度更新位置，再用加速度更新速度。它容易理解，但在弹簧、重力和碰撞系统中能量误差明显，可能导致系统逐渐发散。

游戏中更常用半隐式欧拉：先更新速度，再用新速度更新位置。它仍然简单，但在许多实时场景下比显式欧拉稳定。对于入门系统，半隐式欧拉通常是更合适的默认选择。它不能消除所有误差，却能让力、速度和位置的关系更符合实时模拟需求。

伪代码如下：

```text
if body.dynamic:
    velocity += force * inverseMass * dt
    position += velocity * dt
```

这里需要强调一个经常被忽略的点：积分不是碰撞响应。积分只是预测物体在没有约束时会去哪里；碰撞检测和求解是在预测之后纠正不合法状态。如果把碰撞响应写进积分阶段，系统会很快变成难以维护的特判集合。

#### 四、碰撞检测分为宽阶段和窄阶段

碰撞检测的直接做法是两两比较所有物体。对象数量为 `n` 时，检测对数量约为 `n²/2`。在几十个对象以内，这种方式简单、可靠、方便调试；当对象数量上升时，它会成为明显瓶颈。

成熟物理引擎通常把碰撞检测拆成宽阶段和窄阶段。宽阶段用廉价包围体快速筛掉不可能相交的对象对，窄阶段再对候选对象执行精确形状检测。入门系统可以先使用暴力遍历，但架构上仍应保留宽阶段接口。这样后续从暴力遍历替换为空间哈希、均匀网格或扫描排序时，不会影响求解器。

对于圆形碰撞，核心是两圆心距离是否小于半径之和。对于 AABB，核心是两个轴向区间是否重叠，并选择重叠更小的轴作为接触法线。圆形适合球、弹丸和简化角色；AABB 适合格子、平台和轴对齐矩形。它们不覆盖复杂形状，但足以说明接触生成的关键概念：法线、穿透深度、接触点和碰撞双方。

#### 五、接触不是布尔结果，而是求解依据

很多初学实现会把碰撞检测写成 `true/false`。这只能回答是否相交，不能回答如何修正。真正进入求解阶段时，系统需要知道碰撞法线、穿透深度、接触点、碰撞双方以及材质参数。接触数据的质量决定求解质量。

法线方向必须稳定。若同一对物体在相邻帧生成相反法线，冲量方向会跳变，物体就会抖动。穿透深度不能随意取值，因为位置修正会按它移动物体。接触点对于无旋转系统影响较小，但一旦加入角速度，它会决定力矩和转动效果。即使入门系统暂不处理旋转，也应该把接触点作为结构保留下来。

接触结构可以简化为：

```text
Contact:
    bodyA
    bodyB
    normal
    penetration
    point
```

这一结构让检测器和求解器解耦。检测器只负责描述“发生了什么”，求解器只负责决定“如何处理”。这种分层比把检测和响应写在同一个函数里更容易扩展。

#### 六、冲量法解决的是速度约束

碰撞响应常用冲量法。冲量可以理解为在极短时间内施加的动量变化。两个物体沿碰撞法线相互靠近时，求解器计算一个冲量，使它们在法线方向的相对速度不再继续靠近，并根据弹性系数决定反弹程度。

冲量公式的直觉是：相对速度越快，所需冲量越大；两个物体越轻，速度变化越明显；弹性越高，分离速度越大。静态物体逆质量为零，因此不会被推动。两个动态物体则按逆质量分摊速度变化。

入门系统的核心约束可以表达为：

```text
relativeVelocity = velocityB - velocityA
normalSpeed = dot(relativeVelocity, normal)
if normalSpeed < 0:
    impulse = -(1 + restitution) * normalSpeed / (invMassA + invMassB)
```

这段公式只处理法线方向。它没有处理摩擦，也没有处理旋转，因此不会产生真实的滚动、滑动和角动量变化。但它足以说明碰撞响应的最小闭环：先判断是否正在靠近，再施加使其分离的冲量。

#### 七、位置修正解决的是残余穿透

冲量改变速度，但它不能自动消除已经发生的穿透。由于离散步进的存在，两个物体可能在检测时已经重叠。如果只修改速度，物体可能需要多帧才慢慢分开，或者在重力作用下持续嵌入地面。位置修正就是为了解决这类残余穿透。

最简单的位置修正是按穿透深度沿法线把物体推开，并按逆质量分配位移。为了避免过度修正，通常会设置允许微小穿透的 `slop` 和修正比例 `percent`。`slop` 用于容忍浮点误差和微小接触，`percent` 用于避免一次性推开导致振荡。

位置修正不是物理真实，而是实时模拟中的稳定性手段。过强会让物体弹跳或产生漂移，过弱会让堆叠下沉。入门系统需要把这些参数暴露为调试项，而不是写死在深层函数里。

#### 八、连续碰撞检测解决的是隧穿问题

离散碰撞检测只检查每个时间点的位置。若一个物体在一步内从墙的一侧移动到另一侧，且两个端点都没有重叠，系统就会漏掉碰撞。这就是高速物体的隧穿问题。

解决思路不是简单缩小所有时间步，因为这会提高全局成本。更合理的方式是只对高速、小尺寸或关键对象启用连续碰撞检测。连续检测会考虑物体在时间步内扫过的路径，寻找最早接触时间。对于圆形子弹，可以把圆沿速度方向扫过的区域近似为胶囊；对于 AABB，可以用 swept AABB 计算进入和离开时间。

入门系统可以先不完整实现 CCD，但必须在设计中留出速度阈值和检测策略的扩展点。否则项目一旦出现高速对象，系统就只能通过降低全局步长或扩大碰撞体来掩盖问题。

### 设计思路

#### 一、先定义系统边界

一套可维护的手写物理系统，应该在文档和代码中明确写出“不支持什么”。例如：第一版只支持二维线性运动；只支持圆形和 AABB；不支持旋转；不支持复杂多边形；不支持稳定多层堆叠；不替代角色控制器；不用于大规模可破坏场景。边界越清楚，后续使用者越不容易把它当成通用引擎。

系统边界不是保守，而是工程责任。物理系统一旦进入玩法层，许多问题都会被误认为“调个参数就能好”。若没有边界，轻量系统会被不断塞入摩擦、旋转、斜坡、平台、牵引、关节、流体、载具，最终变成既不稳定也不好替换的局部引擎。

#### 二、按阶段组织 PhysicsWorld

`PhysicsWorld` 不应只是一个装对象的列表，而应该明确表达物理步的阶段顺序。推荐顺序是：清理上一帧接触，累积外力，积分速度和位置，执行宽阶段，执行窄阶段，生成接触，求解速度约束，执行位置修正，写回调试数据。

阶段顺序固定后，调试就有了坐标。若物体穿透，可以检查窄阶段是否生成接触；若接触存在但仍穿透，可以检查位置修正；若物体弹飞，可以检查冲量和弹性；若帧率变化导致结果不一致，可以检查固定步进和最大子步限制。

#### 三、用数据结构隔离对象状态和算法

手写系统容易把逻辑写进对象方法，例如让刚体自己检测碰撞、自己求解、自己绘制调试线。这种写法短期方便，长期会造成耦合。更稳妥的做法是让刚体保存状态，让碰撞体保存形状，让检测器生成接触，让求解器修改速度和位置。

这种隔离还有一个好处：同一套算法可以用于不同对象来源。对象可能来自 Unity 组件，也可能来自纯数据配置，还可能来自关卡编辑器生成的运行时数据。只要转换成物理世界需要的状态结构，系统就能运行。物理层不应反向依赖具体玩法对象。

#### 四、调试可视化必须作为核心功能

物理系统的错误很难只靠日志判断。接触法线、穿透深度、碰撞体范围、宽阶段候选对、速度方向、位置修正向量都应该能在 Scene 视图或调试叠层中看到。没有可视化的物理系统，很容易把几何错误误判为求解错误。

调试信息应按阶段区分颜色和开关。例如宽阶段候选对用浅色线，真实接触点用高亮点，法线用箭头，位置修正用另一种颜色。这样可以快速看出是候选过多、法线错误、接触丢失还是修正方向反了。

#### 五、参数要有物理含义和工程范围

`fixedDt`、重力、弹性、最大速度、穿透容忍、修正比例、最大子步数、CCD 阈值都不应成为神秘数字。每个参数都要有含义、默认值和建议范围。尤其是位置修正参数，应该通过测试场景确定，而不是在真实关卡里反复试。

最大子步数同样重要。若某一帧卡顿，累积器可能需要执行很多物理步追赶时间。无限追赶会导致卡顿更严重，形成螺旋。合理做法是设置最大子步数，超过后丢弃或截断部分累积时间，并记录告警。物理系统必须为实时性服务，而不是为了补完每一毫秒牺牲整帧稳定。

#### 六、测试场景要覆盖失败模式

入门物理系统至少需要以下测试场景：圆形相撞、AABB 相撞、动态物体撞静态墙、多个物体落到地面、不同质量物体相撞、高速物体穿过薄墙、斜向撞击、连续小穿透、低帧率模拟和长时间静置。每个场景都对应一种常见失败模式。

测试不一定要写成复杂自动化，早期可以是可重复运行的 Unity 场景。但场景必须固定初始条件，避免每次手动摆放。若系统将来用于网络同步或 Replay，则应增加输入序列回放和状态哈希比较，确认同样输入能得到同样结果。

#### 七、与 Unity 内置物理保持边界

手写系统若运行在 Unity 中，必须明确它和内置 PhysX/Physics2D 的关系。两套物理系统同时驱动同一对象，会产生冲突。推荐方式是手写系统维护自己的状态，渲染对象只从该状态同步 Transform；若需要与 Unity 碰撞体交互，应通过查询接口或桥接层转换，而不是让两个系统同时写位置。

这条边界尤其影响角色控制。若角色用自制碰撞，地面用 Unity Collider，二者之间必须有明确采样和转换流程。否则 Transform 更新顺序、FixedUpdate 顺序和碰撞回调顺序都会影响结果。

### 进阶讨论

#### 一、手写系统不是越完整越好

手写物理系统最常见的失败，不是功能太少，而是过早追求完整。完整刚体引擎需要处理旋转惯量、接触流形、摩擦约束、休眠、岛求解、关节、连续碰撞、形状缓存、宽阶段动态树和平台确定性。每一项都能单独成为复杂主题。若项目只是需要可控的平台跳跃或简单弹幕碰撞，写到这一步反而会损害可维护性。

更好的策略是按需求形成分层：基础层负责确定性运动和简单碰撞；玩法层负责角色规则；桥接层负责与 Unity 对象同步；调试层负责可视化；扩展层只在必要时加入空间分区、CCD 或摩擦。系统的稳定来自清晰边界，而不是功能堆叠。

#### 二、摩擦比弹性更难处理

弹性碰撞只需要处理法线方向的速度，摩擦还要处理切线方向。静摩擦要阻止轻微滑动，动摩擦要限制滑动速度，二者在堆叠和斜坡场景中都会影响稳定性。若用过于简单的速度衰减替代摩擦，系统可能在平地上看似可用，却在斜面、堆叠和连续接触中表现异常。

入门系统可以先不实现真实摩擦，而是在玩法层使用明确规则。例如平台角色的水平速度由控制器管理，物理系统只负责垂直落地和墙体阻挡。这样做并不“物理真实”，但在工程上更可控。只有当项目确实需要箱子滑动、斜坡摩擦或堆叠稳定时，再考虑加入切线冲量。

#### 三、确定性要求会改变实现选择

如果系统用于单机视觉效果，浮点误差通常可以接受。如果系统用于网络同步、录像回放或多人战斗判定，确定性就会变成核心约束。不同平台、不同编译器、不同数学库和不同执行顺序都可能造成浮点差异。物理对象遍历顺序若不固定，也会让接触求解结果不同。

确定性系统需要固定对象排序、固定随机源、固定时间步、避免未定义遍历顺序，并考虑定点数或受控浮点策略。它还需要状态快照、输入回放和校验机制。手写系统在确定性方面有优势，因为状态空间小、算法可控；但只有在设计初期把确定性作为目标，它才会真正可复现。

#### 四、空间分区要服务对象分布

空间哈希和均匀网格是轻量物理系统常用宽阶段方案，但它们不是万能优化。若对象分布均匀、大小接近，网格非常有效；若对象大小差异巨大，或集中在少数区域，网格可能产生大量候选对。动态树更适合复杂分布，但实现复杂度也更高。

因此，宽阶段优化前应先观察真实场景。对象数量、平均速度、碰撞体尺寸、地图大小和热点区域都会影响选择。一个只有几十个碰撞体的平台跳跃关卡，用暴力遍历可能比引入复杂空间结构更稳。优化应以数据为依据，而不是以算法名称为依据。

#### 五、连续碰撞检测应只用于关键对象

CCD 成本高于离散检测，且实现复杂。若所有对象都启用 CCD，轻量系统会失去简单性。更实际的策略是只对高速、细小、玩法关键对象启用，例如子弹、冲刺角色、投射物或关键机关。普通箱子、地面和慢速物体仍使用离散检测。

CCD 的结果也不只是“是否碰撞”，还包括碰撞发生的时间点。正确做法是在时间步内推进到接触时间，处理碰撞，再用剩余时间继续模拟或停止。若只在检测到路径相交后强行回退到某个估算位置，可能引入新的抖动。

#### 六、位置修正会改变玩法手感

很多物理系统把位置修正视为底层细节，但它会直接影响手感。平台角色落地时是否“吸住”地面，贴墙时是否抖动，箱子堆叠时是否慢慢弹开，都与修正策略有关。修正比例越高，穿透消除越快，但视觉上更容易出现跳变；修正比例越低，运动更柔和，但可能残留嵌入。

对于玩法系统，可以把修正策略按对象类型区分。角色控制器可能需要更强的地面贴合和更稳定的墙面法线，普通动态物体可以接受较自然的分离过程。底层物理系统提供通用修正，玩法层再根据语义做控制，是比在底层写满角色特判更好的结构。

#### 七、手写系统需要退出条件

如果自制系统的需求逐渐扩展到复杂刚体、旋转堆叠、真实摩擦、关节、车辆、破坏和大规模场景，就应该重新评估是否继续自研。成熟物理引擎的价值在于多年积累的边界处理和性能优化。轻量系统适合可控子问题，不适合无边界膨胀。

退出条件可以提前写入技术规范：当对象规模超过某个阈值、当需要三维旋转刚体、当需要稳定多层堆叠、当需要复杂关节、当维护成本超过接入成熟方案时，应切换到内置物理或专业库。提前定义退出条件，能避免系统在惯性中变成项目负担。

#### 八、从教学系统走向生产系统需要补齐工程设施

教学系统只要能跑通原理即可，生产系统还需要序列化、版本迁移、调试开关、性能统计、异常告警、场景校验和回归测试。尤其是物理系统，一次参数调整可能影响大量关卡。没有回归场景，稳定性就会依赖人工体验。

生产化还需要处理资源生命周期。对象创建、销毁、禁用、复用、场景切换和热重载都会影响物理世界状态。若系统只关注 Step 算法，而忽略对象管理，就会在真实项目中出现残留碰撞体、重复注册、空引用和状态不同步。



#### 九、接触持久化能显著改善稳定性

极简系统通常每一帧重新生成接触，然后立即求解。这种方式足以解释基本碰撞，但在持续接触场景中会产生不稳定。例如箱子放在地面上时，理论上它每一帧都处于接触状态；如果接触法线、接触点或求解顺序在相邻帧轻微变化，箱子就可能出现微抖。接触持久化的思想，是把上一帧的接触信息作为下一帧的参考，让持续接触具有连续性。

在入门系统中，接触持久化可以做得很轻。系统为碰撞双方生成稳定的键值，例如两个刚体的唯一编号组合；当下一帧仍然检测到同一对接触时，复用上一帧的部分调试信息和求解统计。若后续实现摩擦或迭代求解，还可以保存上一帧累计冲量，用于 warm starting。这样求解器不必每一帧从零开始，堆叠和静止接触会更稳定。

不过，持久化也会带来生命周期问题。对象销毁、禁用、切换场景或碰撞体尺寸变化时，缓存接触必须被清理。否则系统会把过期接触带入下一帧，造成不可解释的位移修正。也就是说，接触缓存不是纯算法优化，它要求物理世界具备明确的注册、注销和版本控制机制。

#### 十、对象生命周期必须先于性能优化设计

许多手写系统一开始只关注 Step 算法，等接入项目后才发现真正复杂的是对象生命周期。运行时对象会创建、销毁、池化、禁用、换场景、切换碰撞层、修改碰撞体尺寸，还可能从外部系统强制传送位置。每一种变化都会影响物理世界内部状态。

可靠的做法是让物理对象有明确的注册入口和注销入口。注册时分配稳定编号，写入初始状态，并建立碰撞体与刚体关系；注销时清理接触缓存、宽阶段索引和调试记录。对象池复用时必须重置速度、外力、接触状态和休眠标记。传送位置时应标记宽阶段代理需要更新，并选择是否清理当前接触。

这类规则看似与物理公式无关，却决定系统能否在真实项目中长期运行。一个只在测试场景中创建固定对象的系统，很容易在关卡动态加载后暴露残留状态。物理系统越底层，越不能依赖使用者“记得按正确顺序调用”。

#### 十一、玩法控制器和物理求解器要分工明确

手写物理经常服务于角色、弹幕、机关等玩法对象。此时最容易出现的架构问题，是玩法控制器和物理求解器互相覆盖状态。控制器想直接设置位置，物理系统也想根据速度积分位置；控制器想吸附地面，求解器又想按穿透深度推开；控制器想取消水平速度，冲量响应又可能恢复一部分速度。

更稳定的分工是：物理系统负责几何合法性和基础动力学，玩法控制器负责意图和规则。角色想向右移动，不应直接跳过碰撞写 Transform，而应生成期望速度或位移，由物理系统在约束下推进；角色落地、贴墙、上坡等语义可以由控制器读取接触结果后决定，但不应破坏物理世界的状态一致性。

如果项目需要非真实但稳定的角色控制器，可以把角色从通用刚体中分离出来，使用专门的 kinematic body。它不参与普通质量冲量，而是通过 sweep、投影和地面法线规则移动。这样既能复用碰撞检测，又能避免角色手感被通用刚体模型牵制。

#### 十二、错误处理要暴露为工程信号

物理系统出现异常时，不能只让画面表现出抖动、飞出或穿墙。系统应主动记录工程信号：某一帧子步数达到上限，某个对象速度超过阈值，某个接触穿透深度异常，某次位置修正过大，某个对象连续多帧处于非法重叠，宽阶段候选对数量突然升高。这些信号能帮助团队在问题进入内容生产前发现风险。

日志也要控制粒度。每帧打印所有接触会造成噪声，真正有用的是聚合统计和可切换的对象级追踪。调试面板可以显示当前物理对象数量、候选对数量、真实接触数量、平均求解耗时、最大穿透深度和最大修正位移。开发者选择某个对象后，再显示它的速度、接触法线和最近几帧状态。

这些设施让手写物理系统从“能运行的算法”变成“能维护的模块”。物理错误通常不是单点异常，而是多个小误差在时间中累积。没有工程信号，问题只能靠肉眼复现；有了统计和追踪，错误才有被定位的路径。

### 总结

手写物理系统的核心，不是把成熟引擎的接口重新写一遍，而是用最小结构理解物理模拟的因果链：固定时间步决定状态推进的稳定粒度，刚体状态承载可计算的质量和速度，碰撞检测生成可求解的接触数据，冲量法修正速度约束，位置修正清理离散步进带来的穿透，调试可视化让错误能被定位。

一套好的入门系统应该小、透明、可验证。它支持简单形状、线性运动、基础碰撞和有限修正；它清楚说明不支持的能力；它把检测、求解和同步拆开；它通过固定测试场景验证常见失败模式。这样的系统即使功能有限，也能在项目中承担可控子问题，并帮助开发者理解内置物理引擎的行为。

真正的实践重点，是始终把手写物理放在正确位置：它是定制化、确定性和原理学习的工具，而不是盲目替代成熟引擎的工程冲动。只要边界明确、阶段清晰、参数可解释、调试可观察，它就能从一个学习练习变成可靠的技术资产。
