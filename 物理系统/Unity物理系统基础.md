# Unity物理系统基础

## 摘要
Unity 物理系统的基础，并不是记住 Rigidbody、Collider、Trigger、Physics Material 等组件各自有哪些属性，而是理解这些组件共同构成了一条实时物理流水线：物体是否参与模拟、使用什么形状参与碰撞、在哪些层之间产生交互、由物理还是脚本控制运动、碰撞事件如何产生、查询如何执行、性能预算如何分配。本文从基础组件出发，系统解释 Unity 物理系统的核心语义、常见配置、控制方式、碰撞事件、查询路径、性能边界和调试方法，目标是帮助开发者建立“能正确使用物理系统”的底层心智，而不是停留在参数清单式使用。

## 正文

### 背景
Unity 物理系统之所以容易上手，是因为它把复杂的刚体模拟和碰撞检测包装成了直观组件。给物体加 Collider，它就有了物理形状；加 Rigidbody，它就能受重力、力和碰撞影响；勾选 Is Trigger，它就能变成触发区域；设置 Physics Material，它就能改变摩擦和反弹。对简单项目而言，这些操作足以完成大量功能。

但问题也正来自这种易用性。很多开发者会把物理系统当成“组件开关集合”，而没有意识到这些开关背后对应的是模拟对象、碰撞形状、接触生成、约束求解、事件回调和性能成本。于是项目中会出现一些典型问题：高速物体穿透、角色被刚体推飞、触发器事件偶尔不触发、MeshCollider 用在动态物体上导致性能下降、脚本直接改 Transform 破坏刚体状态、Layer 矩阵长期不清理导致无意义碰撞越来越多。

因此，Unity 物理系统基础最重要的不是“知道每个属性在哪里”，而是理解这些属性表达了什么工程语义。Rigidbody 表示该对象是否由物理系统管理运动；Collider 表示它用什么几何形状进入碰撞世界；Layer Matrix 表示哪些对象有资格互相检测；Trigger 表示需要事件检测但不需要实体阻挡；Physics Material 表示接触响应参数；FixedUpdate 表示物理更新节奏。只有这些语义清楚，物理系统才能稳定服务玩法，而不是成为不可解释的黑盒。

### 核心原理
#### 一、Rigidbody 决定物体是否进入刚体模拟
Rigidbody 是 Unity 物理系统中最关键的组件之一。一个对象只有 Collider 而没有 Rigidbody，通常可被视为静态碰撞体；加上 Rigidbody 后，它才会以动态或运动学对象的形式进入物理模拟。动态刚体由物理系统根据力、速度、碰撞和约束推进状态；Kinematic 刚体则不由物理力驱动，而由脚本或动画控制，但仍能参与碰撞检测与触发事件。

这个区分非常重要。动态刚体适合可被推动、下落、碰撞响应的对象；Kinematic 刚体适合平台、电梯、受脚本控制的机关、动画驱动但需要碰撞交互的对象；静态 Collider 适合地形、墙壁、不可移动障碍。若对象类型选错，后续再调参数往往都很难稳定。

#### 二、质量、阻力和速度是物理语义，不只是手感参数
Mass 表示质量，影响相同力作用下的加速度和碰撞响应；Drag 与 Angular Drag 表示线性和角向阻尼；Velocity 与 AngularVelocity 表示当前运动状态。这些参数会进入物理求解过程，不应随意拍值。质量差过大、阻力过高、速度过快，都可能让系统更难稳定。

项目中最好建立相对尺度。例如普通箱子、角色、车辆、投射物大致处在什么质量范围，常见移动速度上限是多少，哪些对象允许被冲量推动。缺少尺度规范时，物理系统会出现大量局部看似合理、组合后非常奇怪的问题。

#### 三、Collider 决定物理世界看到的形状
Collider 并不一定等于模型形状。事实上，游戏中更推荐用简单碰撞体近似视觉模型。Box、Sphere、Capsule 等原始碰撞体成本低、接触稳定；MeshCollider 能表达复杂几何，但成本和稳定性都更敏感。动态物体应尽量使用原始碰撞体或凸包组合，复杂非凸 Mesh 更适合静态环境。

这个原则不是为了偷懒，而是因为物理系统需要在实时预算内处理大量碰撞。视觉模型越复杂，不代表物理形状越应该复杂。碰撞体的目标是提供足够好的交互近似，而不是完全复刻渲染网格。

#### 四、Trigger 表示检测关系，不表示阻挡关系
Collider 勾选 Is Trigger 后，它不再产生实体阻挡，而是产生进入、停留和离开的触发事件。触发器适合范围检测、拾取区域、技能区域、剧情触发、交互提示、检测体积等场景。它不适合用来承载需要物理阻挡的墙体或地面。

Trigger 的一个常见误区是认为它“更轻所以都用 Trigger”。事实上，Trigger 仍然需要进入碰撞检测流程，只是不进入常规接触求解。若大量触发器无层级过滤、无频率控制，同样可能造成性能问题。Trigger 是语义工具，不是无成本工具。

#### 五、Collision 与 Trigger 事件依赖明确条件
碰撞事件要求双方都有 Collider，并且至少一方有 Rigidbody。触发事件要求至少一方 Collider 勾选 Trigger，并且同样需要符合物理事件触发条件。很多“为什么不触发”的问题，往往不是代码回调错，而是组件组合不满足事件产生条件，或者 Layer Matrix 已经禁止了两层之间的交互。

因此，排查碰撞事件时应先检查组件组合、Rigidbody 类型、Trigger 设置、Layer Matrix、对象是否激活、是否在物理步中移动，而不是直接怀疑回调函数。

#### 六、Physics Material 影响接触响应，不只是视觉体验
Physics Material 控制摩擦和弹性。它能让表面更滑、更粘、更弹，但这些参数也会影响求解稳定性。高摩擦和高弹性在一些场景中会制造抖动、反复弹跳或接触不稳定。物理材质应按玩法需求分级设计，例如默认地面、冰面、弹性体、不可反弹体，而不是每个对象随意设置。

Combine 模式也很重要。两个物体接触时，摩擦和弹性如何合成，会影响最终接触效果。项目应统一默认组合规则，避免局部材质之间产生难以预期的交互。

#### 七、Layer Collision Matrix 是基础性能工具
Layer Matrix 决定哪些层之间需要碰撞检测。它是最容易被忽视、也最有价值的基础优化手段。玩家不需要和 UI 碰撞，特效检测体不需要和地形所有细节交互，拾取物可能只需要和玩家检测，敌人感知触发器可能不需要和其他敌人互相触发。只要这些关系没有被层级过滤，物理系统就会处理大量无意义候选对。

Layer 设计应作为项目规范，而不是各功能临时添加。层越多越不一定好，关键是层的语义清晰、矩阵可维护、变更有评审。

#### 八、Collision Detection 模式应按风险启用
Discrete 是默认离散检测，性能好但高速物体可能穿透；Continuous 和 Continuous Dynamic 能降低高速穿透风险，但成本更高。它们不是越高级越好，而是要按对象风险选择。高速关键投射物、玩家强感知物体、重要机关可以使用连续检测；普通低速道具不应无差别启用。

如果大量对象需要连续检测，通常说明项目存在更根本的建模或速度尺度问题，应先检查时间步、碰撞体厚度、速度上限和玩法需求。

#### 九、FixedUpdate 是物理交互的主要阶段
物理系统按固定时间步更新，FixedUpdate 是处理物理驱动逻辑的主要入口。持续施力、刚体移动、物理查询同步等逻辑通常应放在 FixedUpdate 或明确物理阶段中。Update 更适合采集输入、处理表现和缓存意图。若在 Update 中直接改刚体 Transform，又在 FixedUpdate 中参与物理模拟，就可能导致状态不连续。

基础规则是：物理状态尽量由物理阶段写，表现状态由渲染阶段读。不要让多个阶段同时争夺同一刚体。

#### 十、AddForce、Velocity 和 MovePosition 表达不同控制语义
AddForce 表示施加力或冲量，让物体按物理规则响应；直接设置 Velocity 表示强行指定速度；MovePosition / MoveRotation 更适合 Kinematic 或受控刚体的平滑移动；直接改 Transform 则可能绕过物理系统的连续状态管理。它们不是随便替换的 API，而是不同控制模型。

若希望物体像真实刚体一样被推动，使用力和冲量更合适；若希望角色严格按输入速度移动，可能需要受控速度或 CharacterController；若希望平台按轨迹运动，Kinematic + MovePosition 更稳。控制语义明确，物理问题会少很多。

#### 十一、物理查询是另一条重要能力线
Raycast、SphereCast、CapsuleCast、OverlapSphere、CheckBox 等查询能力常用于地面检测、目标筛选、技能命中、相机遮挡和交互检测。它们不一定需要刚体模拟，但同样依赖 Collider 和 LayerMask。查询越多，越需要频率控制和层级过滤。

物理查询应避免在每帧对大量对象无差别执行。常见优化包括缓存 LayerMask、降低检测频率、批量化查询、用空间分区预筛、只在状态变化时查询。查询成本是物理系统的一部分，不能忽略。

#### 十二、睡眠机制是动态刚体性能的重要保障
刚体在接近静止时可以进入睡眠，减少持续解算成本。项目中大量动态对象若长期无法睡眠，例如因为轻微抖动、脚本不断写速度、父节点移动、接触不稳定，就会持续消耗物理预算。优化时应检查对象是否能自然休眠，是否存在无意义唤醒。

对装饰性动态物体、掉落物、碎片等，可以考虑短时间物理后转静态或禁用 Rigidbody。不是所有曾经动态的对象都需要永久动态。

### 设计思路
#### 一、先按对象类型选择物理身份
每个对象接入物理前，应先判断它是静态碰撞体、动态刚体、Kinematic 刚体、Trigger 区域、查询辅助体还是纯视觉对象。身份确定后，再配置 Rigidbody、Collider 和 Layer。不要先加组件再靠调参猜行为。

#### 二、建立碰撞层规范
项目应统一定义 Player、Enemy、Environment、Projectile、Pickup、Trigger、UI、VFX 等层的语义，并维护 Layer Collision Matrix。新增层或改矩阵应经过评审，因为它会影响全项目碰撞关系和性能。

#### 三、优先用简单碰撞体组合
动态对象优先使用 Box、Sphere、Capsule 或多个简单 Collider 组合。复杂 MeshCollider 主要用于静态环境。若视觉形状复杂，先问交互是否真的需要同等复杂的物理形状。

#### 四、把物理控制方式写进代码规范
动态刚体尽量通过力、速度或物理接口控制；Kinematic 刚体通过 MovePosition/MoveRotation 或明确轨迹控制；避免在普通 Update 中频繁直接修改带 Rigidbody 对象的 Transform。规范能减少大量偶发问题。

#### 五、为物理查询建立封装
地面检测、技能命中、交互扫描、AI 感知等常用查询最好集中封装，统一 LayerMask、最大距离、触发器策略和调试绘制。这样既能减少重复代码，也能便于统计查询次数。

#### 六、建立基础调试习惯
使用 Scene 视图 Collider 可视化、Debug.DrawRay/DrawLine、接触点日志、Layer 矩阵检查、Rigidbody 状态面板和 Profiler 物理模块。物理问题如果不可视化，排查效率会很低。

#### 七、用样例场景验证基础规则
建议保留几个小场景验证基础规则：动态箱体堆叠、高速投射体、Trigger 区域、Kinematic 平台、角色地面检测、Layer 矩阵过滤。每次升级 Unity 或调整物理全局参数后，用这些场景快速回归。

### 进阶讨论
#### 一、Unity 物理基础的难点不在 API，而在边界
Rigidbody、Collider、Trigger 都很容易使用，但什么时候该用、什么时候不该用才是难点。项目中很多问题来自把通用物理用于不适合的场景，例如用动态刚体控制强手感角色，或让 UI 类提示体进入复杂碰撞层。基础能力越简单，越需要边界意识。

#### 二、物理真实性不是最高目标
游戏项目追求的是可信、稳定、可控的交互，而不是完全真实。某些地方应降低真实性换取手感，例如角色移动和技能命中；某些地方应增加物理反馈增强表现，例如碎片、机关和道具。Unity 物理系统应服务玩法，而不是反过来支配玩法。

#### 三、全局参数调整必须谨慎
Fixed Timestep、Solver Iteration、默认接触偏移、全局重力和默认材质都会影响大量系统。不要为了局部问题随意调整全局参数。若必须调整，应通过样例场景和性能基线验证。

#### 四、物理系统最容易被内容增长拖垮
早期几个刚体、几个触发器都没问题，后期大量道具、怪物、技能体、机关和查询叠加后，性能会突然变差。因此基础阶段就应建立层级过滤、查询封装和对象分级，否则内容增长会持续放大物理成本。

#### 五、触发器事件不是业务状态的唯一来源
Trigger 可以检测进入离开，但业务逻辑不能完全依赖单次触发事件而不做状态校验。对象禁用、场景切换、传送、层级变化都可能让事件链变复杂。关键业务最好在触发事件之外保留可校验状态，例如范围内对象集合或周期性一致性检查。

#### 六、验收标准
一个团队若能稳定区分静态 Collider、动态 Rigidbody、Kinematic、Trigger 和查询体，知道何时用力、速度、MovePosition 或脚本控制，能维护 Layer Matrix，能用简单碰撞体替代复杂 Mesh，能通过调试工具解释碰撞和触发事件，那么可以认为 Unity 物理基础已经进入工程可用阶段。反之，若仍然主要靠“加组件试试看”，物理系统会持续制造偶发问题。

#### 七、2D 与 3D 物理系统不能混用
Unity 的 2D 物理和 3D 物理是两套系统。Rigidbody2D、Collider2D、Physics2D 与 Rigidbody、Collider、Physics 不互相触发。很多初学问题来自混用了 2D Collider 和 3D Rigidbody，或者用 Physics.Raycast 检测 2D 场景。项目应在模块层明确使用哪套物理体系，并避免同一玩法链路混用。

如果项目同时包含 2D UI 交互、2.5D 角色和 3D 场景，更需要明确哪些检测走 Physics2D，哪些走 Physics3D，哪些只是 UI Graphic Raycast。物理体系边界不清，会造成大量“为什么检测不到”的低级但高频问题。

#### 八、Trigger 生命周期要处理对象禁用和销毁
Trigger Enter/Exit 很直观，但对象被禁用、销毁、切场景或直接传送时，不一定总能按业务预期收到完整进入和离开事件。因此，关键业务不应只依赖 OnTriggerExit 清理状态。范围检测系统最好维护当前集合，并在对象禁用或区域销毁时做兜底清理。

例如拾取区域、技能范围、交互提示和安全区判定，都应考虑对象突然消失的情况。Trigger 是事件入口，不应是唯一状态真相。

#### 九、物理材质应形成项目级预设
如果每个 prefab 都手动创建 Physic Material，项目很快会出现大量近似但不同的摩擦和弹性配置，调试时很难判断接触行为为什么不同。更好的做法是建立项目级材质预设，例如 DefaultGround、IceSurface、BouncyObject、NoFriction、CharacterFoot，并由统一规范说明适用场景。

物理材质预设还能帮助测试复现问题。若某个斜坡打滑或某个弹跳异常，团队可以快速定位到材质组合，而不是在每个对象上查零散参数。

#### 十、物理查询应避免“看起来轻所以随便用”
Raycast 和 Overlap 很方便，但每帧大量使用同样会形成性能负担。常见问题包括每个敌人每帧射线检测玩家、每个 UI 提示每帧 Overlap、每个子弹同时做物理模拟和额外射线补偿。查询应有频率控制、空间预筛和层级过滤。对于 AI 感知，可以不必每帧检测所有单位；对于地面检测，可以减少重复查询并缓存结果。

查询封装还有一个价值：统一 QueryTriggerInteraction 策略。某些查询是否命中 Trigger，应由业务明确决定，而不是每处代码使用默认行为。

#### 十一、常见失败案例一：动态刚体直接改 Transform
一个箱子有 Rigidbody，同时脚本在 Update 中持续写 transform.position。表面上物体移动了，但物理系统对速度、碰撞和插值的预期被破坏，可能出现穿透、接触抖动或碰撞事件异常。正确做法应根据需求选择：动态刚体用力或速度，Kinematic 刚体用 MovePosition，纯脚本对象则不要让它作为动态刚体参与求解。

#### 十二、常见失败案例二：所有对象都放在 Default 层
项目初期所有 Collider 都在 Default 层，短期看省事，后期玩家、敌人、投射物、拾取物、触发器、环境全部互相检测。性能下降只是一个问题，更大的问题是交互语义混乱。投射物命中拾取物、触发器互相触发、特效碰撞体进入不该检测的范围，都会随内容增长出现。Layer Matrix 应尽早治理。

#### 十三、常见失败案例三：MeshCollider 承担动态交互主体
美术模型很复杂，开发者直接加 MeshCollider 并让它移动或参与动态交互。结果检测成本高、接触法线碎、堆叠不稳定。更合理的做法是用多个简单 Collider 近似，或在资源制作阶段提供专门的低模碰撞体。物理形状应为交互服务，而不是复刻视觉网格。

#### 十四、基础物理系统也需要文档化
即便只是基础组件，也应有项目级文档说明：常用 Layer、物理材质预设、动态刚体数量建议、查询封装入口、角色控制策略、Trigger 生命周期处理、2D/3D 使用边界。没有文档时，每个功能都会重新发明一套物理用法，最终产生隐性不一致。

#### 十五、角色控制应优先明确是物理角色还是逻辑角色
角色是最容易误用物理系统的对象之一。若角色完全交给动态刚体，推动、斜坡、台阶、墙角和网络同步都会变得难控；若角色完全脚本移动，又可能缺少自然碰撞反馈。项目应明确角色控制模型：使用 CharacterController、Kinematic Rigidbody、动态刚体，还是自定义控制器。不同模型对应完全不同的碰撞、地面检测和外力响应策略。

一旦角色模型确定，其他系统就应围绕它设计。例如技能击退是否直接改速度，移动平台如何带动角色，墙体碰撞如何修正，跳跃是否由物理重力控制。角色控制边界不清，会让物理问题扩散到整个玩法层。

#### 十六、物理系统与动画系统要避免争抢 Transform
动画、Timeline、Root Motion、IK 和物理刚体都可能想修改对象姿态。若动画在一帧中写骨骼或根节点，物理又在固定步中修正刚体，最终可能出现抖动、穿插或姿态回弹。对需要动画与物理混合的对象，应明确谁是主控：动画驱动物理代理，还是物理驱动动画表现。

布娃娃、受击反馈、Root Motion 角色和物理机关都需要这类边界。基础物理文档虽然不必深入高级动画物理融合，但必须提醒团队不要让多个系统无序写同一 Transform。

#### 十七、物理事件回调应保持轻量
OnCollisionEnter、OnTriggerEnter 等回调很方便，但不应在回调中执行大量复杂业务、资源加载或 UI 重建。物理回调最好只收集必要事实，然后交给业务系统在合适阶段处理。否则物理事件峰值可能直接放大成主线程卡顿。

例如大量子弹命中时，如果每个回调都立即实例化特效、播放音效、刷新 UI、发事件，性能会非常不稳定。更好的做法是聚合命中事件，再批量处理表现和业务结果。

#### 十八、物理对象池需要重置状态
带 Rigidbody 和 Collider 的对象进入对象池后，再次取出前必须重置位置、速度、角速度、睡眠状态、碰撞忽略关系、材质引用、Trigger 状态和订阅关系。很多“第二次生成才出问题”的物理 bug，本质上是对象池没有清理旧物理状态。

因此，物理对象池应有专门 ResetPhysicsState 方法，而不是只 SetActive(false/true)。对象池越常用于投射物、掉落物和特效碰撞体，这条规则越重要。

#### 十九、物理基础学习应配合可视化练习
学习物理组件时，只看 Inspector 参数很难形成直觉。更好的方式是建立几个可视化练习：绘制 Rigidbody 速度向量、绘制碰撞法线、绘制射线查询、显示 Trigger 范围内对象、显示 Layer 过滤结果。可视化能帮助开发者把抽象参数和实际行为联系起来。

这种练习对团队培训很有价值。很多物理误用不是缺知识，而是缺少对中间状态的可见性。

#### 二十、物理基础的最终目标是减少“偶发”问题
物理 bug 往往被描述成偶发：偶尔穿透、偶尔不触发、偶尔抖动、偶尔被弹飞。基础规范的价值，就是把这些偶发问题转化为可解释的规则问题。组件组合是否满足事件条件，层级是否允许碰撞，控制方式是否一致，查询是否命中 Trigger，时间步是否合理。只要这些基础问题有固定检查路径，偶发感就会明显降低。


#### 二十一、物理基础规范应进入 Prefab 审查
很多物理问题来自资源接入阶段，而不是代码阶段。Prefab 是否错误挂了多个 Rigidbody，Collider 是否过于复杂，Layer 是否正确，Trigger 是否有业务说明，物理材质是否来自预设，都应在资源审查中检查。若这些问题等到运行时才发现，修复成本会更高。

#### 二十二、基础物理系统要和性能预算绑定
项目应给不同场景设定大致预算，例如活跃动态刚体数量、每帧查询数量、可见 Trigger 数量、复杂 Collider 数量。预算不需要一开始很精确，但必须让开发者知道物理不是无成本能力。只要预算存在，内容增长时就更容易提前发现风险，并把物理问题转化为可复盘、可评审、可持续维护的工程规范，避免基础系统在项目后期变成只能依赖个人经验排查的隐性风险。

### 总结
Unity 物理系统基础的核心，是理解组件背后的物理语义和工程边界。Rigidbody 决定对象是否进入刚体模拟，Collider 决定物理形状，Trigger 表达检测而非阻挡，Physics Material 控制接触响应，Layer Matrix 决定哪些对象有资格互相检测，FixedUpdate 则提供物理更新节奏。只要这些基础语义清楚，开发者就能更稳定地设计交互、排查碰撞、控制性能，并避免把物理系统误用成不可解释的黑盒。
