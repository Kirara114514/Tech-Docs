## 讨论摘要
讨论了公司内部Agent平台（类 OpenClaw Agent 平台）因安全代理和Desktop桥接应用导致的使用体验问题。架构为：本地 → Desktop桥接应用 → 安全代理 → 服务器OpenClaw。实际暴露的问题包括沙箱用户导致Git推送失败、Token被逼到明文存储、Desktop显示bug导致调试黑盒、维护团队动力不足等。深入分析了Desktop桥接的实质作用——不是保护用户数据，而是保护OpenClaw源文件不被用户接触。最终判断：沙箱用户身份这个底层限制动不了，企业Agent的安全、能力、体验三者形成了不可能三角。

## 关键收获
1. Desktop桥接的真正作用是"让OpenClaw的源文件远离用户"，不是保护用户数据——文件内容无论如何都会传到云端沙箱
2. Token安全反模式：为了安全把Token从环境变量逼到明文脚本，安全代理防住了git push但拦不住requests直调API
3. 沙箱用户身份是架构级的死局：以当前用户身份跑则安全名存实亡，以沙箱身份跑则能力被阉割，白名单命令维护成本永远追不上需求
4. 本质是组织问题：安全团队和开发团队目标不一致，中间缺少能拍板重新设计的人
