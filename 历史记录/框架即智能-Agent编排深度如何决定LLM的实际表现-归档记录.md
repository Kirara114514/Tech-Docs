## 讨论摘要
讨论围绕一个核心命题展开：同一 LLM 在不同 Agent 框架（Codex/Claude Code vs OpenClaw）中表现差异巨大，根因不在模型本身，而是框架层的工程处理深度。四轮递进中，从最初的观察与命题，到辨析不同框架的定位差异和闭源壁垒本质，再到被用户纠正从"静态角色池"转向"动态角色生成"——规划 agent 在运行时按需生成子 agent 的 system prompt 和任务边界。审阅Agent三轮评估补充了成本与反面论证（延迟方差、token 成本 3-5 倍、过度工程场景、编排失败降级策略）、OpenClaw 的公平定位，以及基于架构推理的论证策略。最终产出「框架即智能」为核心论点的正式文档。

## 关键收获
1. 框架架构范式的差异是"管道模型（薄框架）"与"编排引擎（厚框架）"的哲学差距，不是功能多寡
2. 编排引擎的核心是框架提供元能力 + agent 做动态决策的分层模式——不预设角色池，规划 agent 按需动态生成子 agent
3. 框架层处理按流水线位置分前置/中置/后置三层，共同特征是不"增强智能"，而是"消除噪声、降低犯错率、提高信息密度"
4. 编排引擎的成本（延迟方差、token 3-5 倍）只在"不拆解就做不对"时值得；薄框架在单轮简单任务中有确定性优势
5. 闭源壁垒的本质不是代码，而是系统 prompt + 工具调用链的工程调优——产品方法论泄露比代码抄袭更致命
