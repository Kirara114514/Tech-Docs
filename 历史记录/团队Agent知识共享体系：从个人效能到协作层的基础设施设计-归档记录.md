## 讨论摘要

回顾《个人Agent与工业化Agent》那篇文档后，讨论发现那篇文档解决的问题本质上是 infrastructure 层面的团队化（共享仓库、分层、权限），而非 collaboration 层面的团队化（信息对齐、冲突预判、知识孤岛打破）。讨论由此深入知识共享体系的四个核心维度：

1. **上传端心理摩擦**：下载容易上传难，类比开源社区的 lurker vs contributor 问题。Skill 共享面临草稿态→发布态的责任焦虑、契约缺失导致的防御性膨胀。
2. **技术护城河博弈**：知识共享最大受益者（团队）与最大成本承担者（个人）利益对立。知识分三层——通用模式、项目特定知识、核心算法——每层需要不同的共享策略。
3. **维护归属与衰减治理**：Skill 会随时间衰减，孤儿 Skill 比没有 Skill 更危险。系统自动检测三种衰减模式，维护纳入模块交接流程。
4. **安全与系统维度**：依赖管理、权限隔离、环境可移植性、竞争性 Skill 治理等被忽略的维度。

讨论最终产出四层功能方案（Layer 1 零成本 Git 脚本 → Layer 4 可选增强）、Skill Schema 草案、安全模型、组织落地清单。

## 关键收获
1. 基础设施团队化（管道）≠ 协作团队化（水流），混淆两者会导致"搭了系统但协作没变"的困境
2. 上传端瓶颈核心不是技术，是心理和组织——草稿态/发布态分离、契约化质量边界、agent 辅助生成草稿是三条缓解路径
3. 技术护城河分三层：通用模式鼓励共享、项目特定知识权限控制、核心算法共享思路不共享代码；补充论证——护城河有保质期，不共享的知识对个人也会过时
4. 安全模型：格式约束缩小攻击面 + 运行时权限隔离限制后果 + 信任边界兜底，三层足够覆盖 5-20 人团队
5. 四层功能方案 MVP 2 周可上线（纯 Git + 脚本），不需要后端、不需要数据库；晋升有标准（Layer 1→2 需 10 个活跃 Skill + 3 位上传者 + 运行 2 周）

## 审阅记录（与审阅Agent三轮讨论）

**审阅Agent第一轮核心观点：**

遗漏维度：
1. Skill 间的依赖与组合——需 depends_on 字段和版本兼容性
2. 安全与信任边界——prompt injection 防御、secret 扫描、权限声明
3. 上下文依赖/可移植性——同一 Skill 在不同 agent 环境上行为可能完全不同
4. 竞争性 Skill 治理——同一问题多个解法并存还是合并

功能层级调整：下载计数和贡献者统计提至 Layer 1-2，Agent 辅助生成 Skill 草稿降至 Layer 3。

落地最大阻力：组织层面，非技术。核心是管理层真实优先级、冷启动种子内容、持续维护制度化。

护城河补充：知识三层分类、护城河保质期论证、网络效应（共享对个人的净收益为正）。

**审阅Agent第二轮核心观点：**

Prompt injection：格式约束 + 运行时权限隔离 + 信任边界，不需要做 LLM-based 恶意检测。

依赖声明 Schema：name + version(semver) + depends_on(required/optional/global) + tested_with(model/platform/harness/required_tools)。

知识管理员：80% 机械 + 20% 判断，兼职每周 15-30 分钟。"过期但有人用"标记为 unmaintained 而非归档。

环境声明：四个必要字段即可，不需要完整环境快照。下载时自动对比，不匹配警告而非阻断。

网络效应量化：搜索命中率为核心指标，被采纳率和时间节省估算为辅助，bus factor 和知识保全为定性论证。

**审阅Agent第三轮确认：** 共识整体准确。三处修正（Layer 2 交叉引用、三层策略加团队内部限定、量化指标扩展）+ 两处补充（晋升标准 + "不做"清单）。文档可据此撰写。
