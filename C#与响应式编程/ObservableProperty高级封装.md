# ObservableProperty 高级封装

## 摘要

`ObservableProperty<T>` 的价值不只是让一个字段“可订阅”。在 Unity 与 C# 响应式架构中，真正困难的不是把值变化通知出去，而是让状态写入具备边界、校验、来源、旧值语义、生命周期和可追踪性。基础 `ReactiveProperty<T>` 能表达“当前值是什么”以及“值变化时通知谁”，但当项目进入中大型阶段，状态往往需要回答更多问题：谁有权写入，为什么写入，旧值是什么，重复写入是否有效，非法值如何处理，变化是否需要静默，订阅何时释放，派生状态如何计算，问题发生时如何回溯来源。如果这些规则散落在 UI、业务服务和订阅者中，响应式状态会从解耦工具变成隐式副作用网络。

本文围绕 `ObservableProperty<T>` 的高级封装展开，核心论点是：高级封装的目标不是替代响应式库，而是把状态变化从普通通知提升为可治理的领域事件。文章先分析为什么基础响应式属性在真实项目中会遇到写入失控、语义缺失和调试困难；再解释旧值建模、写入边界、比较器、校验器、变更上下文、派生属性、批量更新和线程亲和性的核心机制；随后提出一套适合 Unity 工程的设计思路，包括只读暴露、受控写入、生命周期绑定、审计埋点、静默更新和事务化传播；最后讨论适用边界和反模式。目标是建立一套专业、可维护、可扩展的响应式状态封装方法。

## 正文

### 背景

#### 一、基础响应式属性解决了通知问题，却没有解决治理问题

响应式属性的基础能力很清楚：保存一个当前值，并在值变化时向订阅者发出通知。对小型功能而言，这已经足够。比如一个按钮是否可点击、一个文本是否显示、一个简单设置项是否变化，直接使用 `ReactiveProperty<T>` 或类似抽象，能显著减少手写事件和刷新代码。

但项目规模扩大后，状态问题会从“怎么通知”转向“怎么治理”。同一个属性可能被 UI 输入、网络同步、配置加载、GM 命令、存档恢复和业务规则同时修改；订阅者可能需要知道旧值和新值；某些值需要范围限制或格式校验；某些变化应该刷新 UI，但不应该触发动画；某些状态只能由服务层写入，不能由视图层直接修改。基础响应式属性通常不会替团队回答这些问题。

如果仍然把原始可写属性直接暴露给所有模块，响应式传播会放大写入混乱。传统字段被错误修改时，影响可能停留在局部；响应式属性被错误修改时，变化会沿订阅链扩散到 UI、缓存、日志、红点、网络和派生状态。也就是说，响应式能力越强，写入边界就越重要。

因此，`ObservableProperty<T>` 的高级封装应从一开始就把问题定义为状态治理，而不是语法包装。它不只是“值 + 订阅”，而应是“值 + 写入协议 + 变化语义 + 生命周期 + 诊断能力”的组合。

#### 二、状态变化需要语义，而不仅是新值

很多状态变化不能只看新值。血量从 80 变到 50，语义是受伤；从 20 变到 50，语义是治疗；从 1 变到 0，可能触发死亡；从 0 变到 1，可能触发复活。房间人数从 1 变到 0 与从 0 变到 1，也代表完全不同的业务状态。若属性只通知新值，订阅者就要各自缓存旧值并推断变化方向，最终产生重复逻辑和不一致判断。

除了旧值，新值之外，还需要上下文。一次状态变化可能来自用户操作、服务器同步、默认值初始化、存档恢复、调试命令或派生计算。不同来源应该触发不同副作用：用户操作可能需要埋点，服务器同步可能需要校验版本，存档恢复可能需要静默刷新，调试命令可能需要记录日志。如果封装层无法携带这些上下文，外围模块就只能通过临时标记和全局变量绕路。

因此，高级 `ObservableProperty<T>` 至少应让变化对象包含旧值、新值和最小上下文。上下文不一定复杂，但要能表达“为什么发生”和“如何对待”。这能把状态变化从裸通知提升为有语义的事件。

#### 三、Unity 项目让状态生命周期更复杂

Unity 中状态并不总是跟普通对象生命周期一致。`MonoBehaviour` 会启用、禁用、销毁；对象池会回收再激活；场景切换会销毁视图但保留全局服务；ViewModel 可能随界面打开关闭反复创建；热更新对象可能与主工程对象有不同生命周期；异步加载和网络回调可能在视图关闭后才返回。

响应式属性一旦被订阅，就会形成引用关系。若派生属性、订阅令牌和响应式流没有被释放，就可能造成重复刷新、旧界面收到新事件、对象无法回收或状态链路继续运行。基础 `ReactiveProperty<T>` 本身提供订阅能力，但不会自动知道 Unity 对象何时应该释放订阅。

因此，高级封装必须考虑生命周期归属。属性本身是否可释放，派生属性是否释放源订阅，订阅者是否有生命周期容器，静态状态是否跨场景保留，ViewModel 关闭后是否停止传播，这些都是工程设计的一部分。没有生命周期治理，响应式状态越多，泄漏和幽灵回调越难排查。

### 核心原理

#### 一、ObservableProperty 的核心是受控写入

`ObservableProperty<T>` 最重要的能力不是订阅，而是受控写入。订阅只是让外部知道变化；写入决定系统状态如何改变。若谁都能直接设置 `Value`，就无法统一校验、日志、权限、来源和异常处理。高级封装应把写入收口到明确方法中，例如 `Set`、`TrySet`、`ApplyChange` 或领域命令。

受控写入有三个层次。第一层是只读暴露：外部可以读取当前值和订阅变化，但不能直接改值。第二层是策略写入：写入前经过比较器、校验器和权限检查。第三层是上下文写入：每次写入必须携带来源、原因或事务信息。项目不一定一开始实现全部层次，但关键业务状态至少应具备只读暴露和统一写入入口。

这个原则能显著改善架构边界。UI 层不应随意修改服务器权威状态；动画回调不应直接推进领域状态；网络同步不应绕过校验；调试工具也应留下变更来源。只要写入口统一，这些规则就可以在一处执行。

#### 二、比较器决定变化语义

判断“值是否变化”并不总是简单的 `Equals`。浮点数可能需要误差阈值，向量可能需要按距离比较，列表可能需要版本号，配置对象可能需要按关键字段比较，状态枚举可能在相同值但不同上下文下仍需触发。比较器不是实现细节，而是变化语义的一部分。

例如音量从 0.500001 变到 0.500002，通常不应触发 UI 刷新；但匹配状态从“匹配中”再次写入“匹配中”，如果上下文代表重新开始匹配，可能需要触发计时器重置。简单去重会丢失业务语义，完全不去重又会造成重复刷新。成熟封装应允许比较策略可配置，必要时比较器可以同时参考值和上下文。

比较器还影响性能。复杂对象深比较可能很贵，放在高频写入路径会造成开销。某些状态更适合通过版本号或引用变化判断，而不是每次递归比较。设计 `ObservableProperty<T>` 时，应把比较策略作为显式参数，而不是隐藏在默认实现里。

#### 三、校验器把领域规则前移到状态边界

很多属性都有合法范围。等级不能小于 1，血量不能低于 0，音量应在 0 到 1 之间，昵称不能为空，服务器地址必须符合格式，背包容量不能小于已有物品数量。若这些校验散落在 UI 输入框、网络回包和业务按钮中，不同入口很容易规则不一致。

校验器的作用是把规则收束到状态边界。任何写入都先经过统一校验，再决定是否接受。校验结果不应只有成功或失败，还可以包含修正后的值和失败原因。例如血量小于 0 可以被夹取到 0；昵称非法应拒绝并返回错误；旧版本配置可以接受但标记为迁移值。不同状态有不同策略，封装层应提供扩展点，而不是把规则写死。

校验失败需要可见。静默拒绝会让调用方困惑，也会让 UI 难以展示错误。`TrySet` 可以返回写入结果，包含成功、未变化、非法、只读、被修正、权限不足等状态。这样状态封装不仅负责“能不能写”，还负责告诉外部“为什么不能写”。

#### 四、变更上下文让调试和审计成为可能

状态变化最难排查的问题通常不是“变成了什么”，而是“谁改的、为什么改、处在哪个流程里”。变更上下文可以包含 reason、source、silent、timestamp、transactionId、operator、stackTrace 等信息。并不是每个项目都要完整记录，但关键状态至少应有最小来源和原因。

变更上下文能服务三个目标。第一，调试。开发版可以显示最近 N 次变化，快速定位错误写入来源。第二，审计。关键状态变化可以进入埋点或日志，辅助复盘。第三，策略分流。订阅者可以根据上下文决定是否播放动画、是否提示用户、是否写入存档。

上下文设计要避免无约束字符串泛滥。原因和来源最好使用枚举、常量或结构化标签，方便统计和过滤。自由文本可以作为补充说明，但不应成为唯一协议。否则后期很难做自动分析。

#### 五、派生属性需要依赖管理

响应式架构中很多属性是派生出来的。`CanSubmit` 依赖账号、密码和网络状态；红点状态依赖多个子系统；战力依赖等级、装备、技能和 Buff；按钮显示依赖活动开关、玩家等级和资源状态。若每个派生状态都在 UI 层临时订阅和组合，逻辑会散落且难以测试。

高级封装可以提供 `ComputedProperty` 或依赖声明，让派生关系集中表达。派生属性需要解决三个问题。第一，依赖释放：派生属性销毁时必须释放源订阅。第二，循环依赖：A 依赖 B，B 又间接写回 A 时需要告警或防护。第三，重复计算：多个源属性同一帧变化时，派生属性是否应该合并计算。

派生属性不只是便利工具，它能帮助团队建立状态层级。哪些是原始领域状态，哪些是派生状态，哪些是视图状态，只要层级清楚，订阅者就不需要到处重复组合逻辑。

### 设计思路

#### 一、对外只暴露只读观察接口

高级 `ObservableProperty<T>` 的基础设计是读写分离。拥有状态的对象持有可写入口，外部只获得只读接口。只读接口可以包含当前值、变化流和订阅方法，但不包含直接写入。这样 UI、外部系统和订阅者不能绕过状态拥有者修改值。

读写分离能让状态所有权清晰。领域模型负责修改领域状态，ViewModel 负责修改视图状态，服务层负责修改服务状态。若某个外部模块确实需要请求修改，应通过命令或服务方法，而不是直接写属性。这样可以保留响应式观察能力，同时不破坏领域边界。

一个最小模型可以是：内部 `ObservableProperty<T>`，外部 `IReadOnlyObservableProperty<T>`。前者提供 `TrySet`，后者只提供 `Current` 和 `Changes`。接口设计比类名更重要，只要只读边界清楚，底层使用 UniRx、R3 或自研实现都可以替换。

#### 二、写入结果要可表达

`Set` 返回 `bool` 只能表达成功或失败，不足以支撑复杂业务。更好的做法是定义写入结果，例如 `Changed`、`Unchanged`、`Rejected`、`Corrected`、`ReadOnly`、`InvalidContext`。结果中可以包含最终值、错误信息和校验码。

这样 UI 表单可以根据失败原因显示提示，网络同步可以区分重复包和非法包，调试工具可以记录被拒绝的写入。对于关键状态，失败写入本身也是重要信号。比如客户端频繁尝试写入服务器权威属性，可能说明架构边界被误用。

写入结果还可以参与测试。单元测试不必订阅事件才能判断行为，只需调用 `TrySet` 并断言结果。状态封装越明确，测试越直接。

#### 三、区分普通更新、静默更新和事务更新

并非所有写入都应触发同样副作用。普通更新代表业务状态变化，应通知订阅者；静默更新用于初始化、存档恢复、服务器快照对齐等场景，可能更新当前值但不触发某些 UI 动画或提示；事务更新用于一组属性共同变化，避免中间态被订阅者观察。

静默更新不应理解为“偷偷改值”。它应在上下文中明确标记，让订阅者和日志知道发生过变化，只是某些副作用选择忽略。事务更新也不必复杂，可以通过 `BeginUpdate/EndUpdate` 或批处理上下文收集变化，结束时统一发布。

Unity UI 特别需要这类能力。切换角色、恢复存档、打开界面初始化时，大量属性会同时变化。如果每个属性立刻驱动布局、动画和红点刷新，容易出现界面抖动和性能峰值。批量更新能让界面在稳定状态下响应。

#### 四、生命周期容器是默认配套

`ObservableProperty<T>` 本身、派生属性、订阅关系都应可释放。订阅方法返回 `IDisposable`，ViewModel 或 MonoBehaviour 持有生命周期容器，界面关闭或对象回收时统一释放。没有释放机制的响应式系统，短期工作正常，长期必然出现重复订阅和泄漏。

生命周期容器应与 Unity 生命周期匹配。`OnEnable` 创建的订阅在 `OnDisable` 释放；`Awake` 创建且对象整个生命周期都需要的订阅在 `OnDestroy` 释放；对象池回收时释放外部订阅；跨场景全局状态不要订阅短生命周期对象，除非有明确释放令牌。

派生属性的生命周期也要明确。若派生属性属于 ViewModel，它应随 ViewModel 释放；若属于全局模型，它应跨界面保留；若只是临时 UI 计算，不应注册到全局状态链。生命周期不清，是响应式系统维护困难的主要原因之一。

#### 五、调试面板与变化历史应进入开发期工具

高级封装天然适合做调试工具。开发版可以为关键属性记录最近若干次变化，包括旧值、新值、来源、原因、是否静默、时间和调用栈摘要。调试面板可以按状态名查看变化历史，也可以按来源筛选。

这类工具能显著降低排障成本。UI 显示错误时，可以直接看到属性最近被谁改过；状态反复震荡时，可以看到是否存在反馈环；某个属性频繁静默更新时，可以判断初始化流程是否混乱。比起在各处加临时日志，统一入口记录更稳定。

当然，生产环境应控制开销。详细调用栈和字符串日志可以只在开发版开启；高频属性可以只记录采样或计数；敏感数据不应进入通用日志。调试能力要可配置，而不是一刀切。

#### 六、线程策略必须明确

Unity 项目中的状态写入可能来自主线程，也可能来自网络、文件 IO 或后台任务。若属性变化最终驱动 Unity 对象，写入和派发就应回到主线程。否则订阅者在回调中访问 Unity API 可能出错。

封装层可以提供线程策略：只允许主线程写入，越界写入在开发版报错；或允许后台写入，但把通知切回主线程；或为纯数据层属性允许任意线程，但订阅者必须声明调度器。关键是不能让线程行为保持隐式。

响应式状态一旦跨线程，顺序也需要定义。后台连续写入多个值，主线程如何合并？是否保留所有变化？是否只保留最新值？这些问题要按业务语义处理。下载进度可以合并，交易状态不能丢弃，调试日志可以批量。

### 进阶讨论

#### 一、ObservableProperty 与普通事件的关系

普通事件适合表达离散事实，`ObservableProperty<T>` 适合表达有当前值的状态。按钮点击、任务完成、资源加载失败，这类事件本身不一定需要当前值；血量、音量、连接状态、表单合法性则天然有当前状态。若事件需要订阅者频繁查询当前值，可能更适合建模为属性；若属性变化只是偶发通知且不需要保留当前值，普通事件更轻。

不要把所有事件都改造成属性，也不要把所有属性都拆成事件。建模标准是：系统是否需要随时读取当前值，是否需要旧值比较，是否需要写入治理。如果答案是肯定的，属性封装更合适；否则事件可能更简单。

#### 二、ObservableProperty 与领域模型的边界

`ObservableProperty<T>` 不应吞掉领域模型。它可以承载状态变化和通知，但领域规则仍应有清晰归属。例如“玩家是否可以升级”不应只写在等级属性的校验器里，还应属于玩家成长系统的规则。属性封装负责防止非法写入和传播变化，领域服务负责决定何时发起写入。

如果把大量业务逻辑堆进属性类，属性会变成上帝对象。相反，如果属性只负责值和通知，业务规则又全部散落在外围，治理也失败。合理边界是：属性负责通用状态治理，领域服务负责业务决策，ViewModel 负责视图组合。

#### 三、过度封装会损害简单性

高级封装不是所有变量的默认选择。局部临时值、一次性计算结果、纯内部缓存、小型组件私有状态，未必需要旧值、上下文、校验和审计。把所有字段都变成复杂 `ObservableProperty<T>`，会增加样板代码、对象分配和理解成本。

因此，团队应制定适用标准。关键业务状态、跨模块状态、需要审计的状态、需要派生组合的状态适合高级封装；纯局部实现细节不需要。封装是为了治理复杂度，而不是制造仪式感。

#### 四、响应式链路需要防止反馈环

响应式状态最容易形成反馈环：A 变化触发 B，B 变化又触发 A；订阅者收到状态变化后写回同一属性；派生属性意外变成源属性。轻微反馈环会造成重复刷新，严重时会造成状态震荡或递归调用。

封装层可以提供基本防护，例如开发版重入检测、同帧重复写告警、事务 ID 追踪、循环依赖检测。业务层也应避免在订阅者中直接回写同一状态。若确实需要反馈，应通过命令队列或状态机显式建模，而不是隐式订阅链。

#### 五、性能关注点在传播链而非赋值本身

`ObservableProperty<T>` 的性能成本主要来自变更对象分配、上下文字符串、日志记录、复杂比较、订阅链级联和派生计算，而不是普通赋值本身。高频属性应使用轻量上下文、结构体变更对象、可关闭日志和简单比较器。低频关键状态则可以保留更多审计信息。

性能优化应基于 profiling。若状态变化触发 UI 布局、资源加载或大量派生计算，真正瓶颈可能在订阅者，而不是属性封装。封装层提供耗时统计和订阅者数量统计，可以帮助定位传播链中的热点。

#### 六、验收标准

一个成熟的 `ObservableProperty<T>` 设计应满足以下标准：关键状态写入权限明确；对外只读暴露；旧值、新值和最小上下文统一表达；比较、校验和静默策略可配置；订阅和派生属性有生命周期释放；开发期可以追踪变化来源；高频路径不会产生不可接受的分配；团队规范明确哪些状态适合高级封装。

若一个封装只是包了一层 `ReactiveProperty<T>`，但仍然谁都能写、没有上下文、没有失败结果、没有生命周期归属、没有调试能力，它就不是高级封装，而只是命名包装。真正的高级不在 API 花哨，而在状态复杂度是否被稳定治理。


#### 七、实现方案：最小可用封装应覆盖写入上下文与只读暴露

一个可落地的最小实现不需要一开始支持所有高级能力，但必须体现三个基本原则：外部只读、内部受控写入、变化携带上下文。下面的示例使用短代码展示结构方向，实际项目可以替换底层响应式库。

```csharp
public readonly struct ChangeContext
{
    public ChangeContext(string source, string reason, bool silent = false)
    {
        Source = source;
        Reason = reason;
        Silent = silent;
    }

    public string Source { get; }
    public string Reason { get; }
    public bool Silent { get; }
}

public readonly struct Change<T>
{
    public Change(T oldValue, T newValue, ChangeContext context)
    {
        OldValue = oldValue;
        NewValue = newValue;
        Context = context;
    }

    public T OldValue { get; }
    public T NewValue { get; }
    public ChangeContext Context { get; }
}
```

这个模型看起来朴素，但已经比只暴露新值更适合工程化。旧值用于判断变化方向，上下文用于区分用户输入、服务器同步和静默恢复，`silent` 用于订阅者决定是否触发表现副作用。若项目后续需要扩展，可以继续加入事务 ID、时间戳、操作者、调试堆栈或校验结果。

#### 八、写入 API 应表达失败原因，而不是只返回 false

高级封装的写入入口最好不要只有 `bool Set(T value)`。布尔值无法表达失败原因，也无法区分“值未变化”和“非法写入”。更合理的做法是定义写入结果。示意如下：

```csharp
public enum SetResultKind
{
    Changed,
    Unchanged,
    Rejected,
    Corrected,
    ReadOnly
}
```

在 UI 表单、配置导入和网络同步场景中，这种结果非常有用。`Unchanged` 可以避免重复提示，`Rejected` 可以显示错误，`Corrected` 可以记录输入被归一化，`ReadOnly` 可以暴露越权写入。状态系统若能清楚表达失败，比简单吞掉失败更容易维护。

#### 九、反模式：为了统一而把所有字段都变成 ObservableProperty

高级封装很容易被误用为统一风格。项目一旦决定响应式化，就可能把大量局部变量、临时缓存、算法中间结果都改成 `ObservableProperty<T>`。这会带来额外对象、订阅关系和认知负担。更严重的是，真正关键的状态会被淹没在大量不重要的可观察字段中，审计和调试也失去重点。

因此，规范中应明确适用条件。适合高级封装的状态通常具有跨模块订阅、需要旧值、需要校验、需要来源追踪、需要派生组合或需要生命周期管理等特征。不满足这些条件的内部实现细节，保持普通字段即可。克制使用是高级封装能长期有效的前提。

#### 十、反模式：订阅端承担过多状态规则

另一个常见问题是封装只负责通知，规则仍然散落在订阅者中。比如每个订阅者都判断血量是否小于 0，每个 UI 都判断字符串是否合法，每个系统都自己缓存旧值。这说明封装没有真正承担状态治理。订阅者应主要响应已经被建模好的变化，而不是重新解释原始值。

如果多个订阅者都在写相同判断，通常应该把判断上移到属性边界、派生属性或领域服务。否则响应式只是把“到处写 if”的问题换成“到处订阅后再写 if”。

#### 十一、反模式：让 ObservableProperty 直接承载复杂领域流程

与规则过散相反，另一个极端是把所有业务流程都塞进属性类。例如属性内部直接发网络请求、播放动画、修改资源、推进任务流程。这会让属性从状态单元膨胀成业务控制器，破坏单一职责。

更合理的分工是：属性负责保存状态、校验写入、发布变化；领域服务负责决定何时写入；表现层订阅变化并执行表现；基础设施层负责日志和审计。属性可以提供钩子，但不应知道所有业务后果。否则封装越高级，耦合越严重。

#### 十二、验收清单：一次属性封装设计评审应问什么

在代码评审或架构评审中，可以用以下问题检查 `ObservableProperty<T>` 是否真的合格。第一，这个状态的所有者是谁？第二，外部是否只能只读观察？第三，写入是否有统一入口？第四，非法值如何处理？第五，重复写入是否触发？第六，是否需要旧值和来源？第七，是否存在静默更新或批量更新场景？第八，订阅何时释放？第九，派生状态是否可能形成反馈环？第十，开发期如何追踪谁修改了它？

如果这些问题大多答不上来，说明封装还停留在语法层。真正可进入正式项目的状态封装，应能在这些问题上给出明确、稳定、可测试的答案。


### 总结

`ObservableProperty<T>` 的高级封装，本质上是对响应式状态的工程治理。基础响应式属性解决通知问题，高级封装解决状态边界、写入权限、变化语义、校验策略、调试追踪、生命周期和传播控制问题。它让状态不再只是一个会通知的值，而成为有所有权、有规则、有上下文的领域状态单元。

在 Unity 项目中，这种治理尤其重要。对象生命周期复杂，UI 与业务状态交织，网络和异步回调频繁，状态变化常常需要驱动多处表现。如果没有统一封装，状态来源不明、重复订阅、静默副作用和反馈环会不断积累。通过只读暴露、受控写入、变更上下文、批量更新和生命周期容器，可以显著降低响应式系统的长期维护成本。

同时，高级封装也要保持克制。不是所有字段都值得变成复杂属性。它应优先用于关键业务状态、跨模块状态、需要审计的状态和派生组合状态。对简单局部值，普通字段、普通事件或基础响应式属性仍然更合适。

最终判断标准是：封装是否让状态变化更可解释、更可验证、更可追踪。如果答案是肯定的，`ObservableProperty<T>` 就不只是语法糖，而是项目状态系统的重要基础设施；如果答案是否定的，它就只是另一层复杂包装。

## 知识缺口

1. 不同响应式库（UniRx、R3、自研实现）在属性生命周期、调度器和 GC 压力上的差异，需要结合项目框架实测。
2. 批量更新、事务上下文和派生属性循环检测的最佳实现方式，取决于项目状态规模和 UI 刷新模型。
3. 开发期变更追踪与生产期性能之间的平衡，需要通过 profiling 和线上日志策略进一步细化。
4. 网络权威状态、客户端预测状态和本地视图状态如何分层建模，需要结合具体同步框架设计。
