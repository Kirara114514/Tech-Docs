# C# 表达式树与性能优化

## 摘要

表达式树是 C# 中连接“运行时动态性”和“接近静态调用性能”的重要机制。它把一段逻辑表示为可分析、可组合、可转换的数据结构，再在合适的运行环境中编译为委托或解释执行。与普通反射相比，表达式树的关键价值不在于“写法更高级”，而在于它可以把昂贵的成员查找、参数适配、装箱拆箱和调用分派前置到构建阶段，使运行阶段只承担一个稳定委托或解释器的执行成本。对 Unity 项目而言，表达式树既可能用于数据绑定、序列化访问器、配置化规则、动态筛选和属性映射，也可能因为 IL2CPP、AOT、热更新边界、缓存失效和调试困难而成为隐蔽风险源。

本文围绕表达式树的性能优化价值展开，核心论点是：表达式树不是反射的无条件替代品，而是一种把动态逻辑转化为可缓存执行计划的工程工具。它的收益来自“结构化表示 + 一次构建 + 多次复用”，风险则来自“构建成本高 + 平台能力差异 + 过度抽象”。文章先说明反射、委托和表达式树在调用链上的本质差异，再分析表达式树节点、Lambda 编译、缓存键、访问器生成、IL2CPP 降级和可观测性设计，最后给出 Unity 项目中选择表达式树的边界判断与实现方案。

## 正文

### 背景

#### 一、动态访问为什么会成为性能问题

C# 项目中经常会遇到一种矛盾：业务层希望保持灵活性，运行时根据类型、字段名、配置路径、规则表达式或 UI 绑定关系决定访问逻辑；性能层则希望调用路径尽量静态，避免反射、装箱、分派和字符串查找反复出现在热路径中。这个矛盾在 Unity 项目中更明显，因为 Unity 的运行环境同时受到帧率预算、移动端 CPU、GC 压力、IL2CPP AOT、资源热更新和编辑器/真机差异的约束。

典型场景包括：根据配置字段把角色属性绑定到 UI；从表格中读取字段名并生成属性访问器；序列化系统需要快速读写对象成员；战斗公式需要根据配置动态求值；调试工具需要在运行时查看对象内部状态；热更新层需要把字符串路径映射到 C# 对象成员。最直接的方案是反射：通过 `Type.GetProperty`、`PropertyInfo.GetValue`、`MethodInfo.Invoke` 完成动态调用。反射的优点是通用，缺点是每次调用都可能重复承担元数据查找、访问检查、参数数组构造、装箱拆箱和异常包装成本。

如果这些操作只发生在编辑器工具、加载阶段或低频调试入口，反射成本通常可以接受。问题出现在高频路径：每帧刷新大量 UI 绑定、每次反序列化读写成千上万字段、每个战斗 tick 评估大量动态规则、每个实体更新时按字符串路径读取属性。此时单次反射调用即使只慢几微秒，乘以大量对象和帧数后也会变成明显开销，并可能产生额外 GC。

表达式树正是在这种矛盾中有价值。它允许系统在运行时仍然根据类型和成员信息构建逻辑，但把“如何访问”编译或解释成一个可复用执行计划。换句话说，反射偏向“每次动态决定并调用”，表达式树偏向“先动态生成计划，再重复执行计划”。这个差异决定了表达式树的性能优化本质。

#### 二、表达式树不是语法糖，而是代码的数据结构

表达式树的核心概念是把代码表示为对象图。一个 `x => x.Level + 1` 的 Lambda，在普通委托中会直接成为可执行方法；在表达式树中，它会被表示为一组节点：参数节点表示 `x`，成员访问节点表示 `x.Level`，常量节点表示 `1`，二元运算节点表示加法，Lambda 节点表示整个函数边界。每个节点都有明确类型和子节点关系，因此表达式树可以被检查、转换、缓存、翻译或编译。

这也是表达式树与普通委托的重要区别。委托只表达“可以调用”，不表达“内部做了什么”；表达式树表达“逻辑结构是什么”，因此可以被框架分析。LINQ Provider 能把表达式树翻译为 SQL，序列化框架能根据成员访问表达式生成访问器，规则系统能遍历节点判断是否允许某些操作，缓存系统能为结构相同的表达式建立复用计划。

这种结构化能力使表达式树适合构建框架层能力，而不是普通业务层的日常写法。若逻辑在编译期已经确定，直接写 C# 方法最简单、最快、最可维护；若只是绑定一个已知签名的方法，`Delegate.CreateDelegate` 往往比表达式树更直接；若只做低频反射，表达式树的构建成本可能不值得。表达式树真正适合的是“逻辑形状运行时确定，但确定后会重复执行”的场景。

#### 三、Unity 环境放大了表达式树的边界问题

在普通 .NET 服务端程序中，表达式树常通过 `Compile()` 生成动态方法，借助 JIT 获得接近手写委托的性能。但 Unity 项目不能直接套用这一经验。Unity 编辑器、Mono 后端、IL2CPP 后端、移动端平台、主机平台、裁剪设置和热更新方案都会影响表达式树的可用性。

IL2CPP 最大的差异在于 AOT。运行时动态生成 IL 并 JIT 编译通常不可用或受限，某些 `Expression.Compile()` 路径可能退化为解释执行，也可能在特定平台、Unity 版本或裁剪配置下失败。即使某些表达式可以运行，也不能把编辑器下的表现直接视为真机表现。表达式树一旦进入跨平台运行时逻辑，就必须设计平台差异处理。

此外，Unity 的性能问题不只看 CPU。表达式树构建阶段会分配大量节点对象，编译阶段可能有明显峰值开销，缓存字典会占内存，闭包和泛型适配可能引入额外对象，错误堆栈也比手写代码难读。若表达式树框架缺少统计和诊断，很容易出现“上线后能跑但没人敢改”的黑盒状态。

因此，Unity 中使用表达式树的前提不是“它比反射快”，而是要回答四个问题：是否存在足够多的重复调用来摊薄构建成本；目标平台是否支持所选执行方式；缓存键和生命周期是否可靠；出现失败时是否有可诊断、可降级的路径。只有这四个问题成立，表达式树才是优化工具；否则它可能只是把简单问题复杂化。

### 核心原理

#### 一、反射慢在哪里，表达式树快在哪里

要理解表达式树的性能价值，必须先拆开反射调用链。以属性读取为例，反射通常需要根据字符串或元数据对象定位属性，检查访问权限，准备目标对象和参数数组，处理值类型装箱，调用内部运行时入口，再把结果以 `object` 形式返回。即使 `PropertyInfo` 已经缓存，`GetValue` 本身仍然保留了通用调用路径，因为它必须支持各种类型、各种访问器、异常包装和运行时检查。

表达式树的优化思路是把这些通用性前置。构建表达式时已经确定目标类型、成员、参数类型和返回类型；编译或解释计划时可以生成更直接的访问逻辑；调用时不再需要通过 `object[]` 传参，也不需要每次重新解析成员路径。若生成的是强类型委托，调用成本接近普通委托调用。

例如，一个 `Func<Player, int>` 类型的等级读取器，在构建阶段已经确定 `Player.Level` 成员，运行阶段只接收 `Player` 并返回 `int`。相比 `PropertyInfo.GetValue(player)`，它避免了返回值装箱和通用反射入口。若调用次数足够多，这个差距会被放大。

但“快”只发生在运行阶段。表达式树构建和编译本身并不便宜。创建节点对象、解析成员、构造 Lambda、执行 `Compile()` 或生成解释计划，都需要成本。因此表达式树的性能公式应写成：总成本 = 构建成本 + 编译/解释计划成本 + 单次执行成本 × 调用次数。只有调用次数足够高，低执行成本才能抵消高构建成本。

#### 二、表达式树的节点模型决定了它可以被分析和转换

表达式树由节点组成。常见节点包括参数、常量、成员访问、方法调用、二元运算、条件表达式、类型转换、Lambda、New、MemberInit、Block 等。每个节点都描述一小段语义，组合起来形成完整逻辑。这种节点模型使表达式树成为一种中间表示，类似编译器内部的抽象语法树。

节点模型带来两个重要能力。第一，表达式树可以被遍历。通过 `ExpressionVisitor`，框架可以检查一个表达式是否只访问允许的成员，是否包含方法调用，是否出现闭包常量，是否使用了不支持的平台 API。第二，表达式树可以被改写。例如把空值检查自动插入成员访问链，把某些方法调用替换为安全版本，把常量折叠，把重复子表达式提取出来。

这也是表达式树优于字符串公式的地方。字符串公式需要先解析，且语义检查容易散落在自定义解析器中；表达式树已经具有类型信息和节点类型，可以用 C# 类型系统参与约束。对于配置化规则而言，表达式树能在灵活性和类型安全之间取得折中。

不过节点模型也有边界。表达式树并不能表示所有 C# 语言特性，尤其是一些较新的语法糖最终未必能以表达式树形式保留。表达式树表达的是可被 `System.Linq.Expressions` 支持的表达式子集，而不是完整 C# 程序。复杂控制流、异步状态机、局部函数、模式匹配细节等并不适合直接纳入表达式树框架。若规则逻辑已经接近脚本语言复杂度，应考虑 DSL、Lua、代码生成或正式脚本系统，而不是强行堆叠表达式树。

#### 三、Compile 的本质是把结构转换为执行计划

`Expression<TDelegate>.Compile()` 的目标是把表达式树转换为可调用委托。在支持 JIT 的 .NET 环境中，常见实现会生成动态方法或等价执行结构，使后续调用走接近手写代码的路径。性能收益来自两个方面：一是类型和成员访问已固定，二是通用反射调用被替换为委托调用。

但 `Compile()` 不是免费优化开关。它可能触发动态方法生成、IL 发射、闭包对象构造和运行时验证。复杂表达式的编译耗时可能达到毫秒级，且会产生内存分配。若在帧循环中构建并编译表达式树，性能会比反射更差。表达式树优化的第一铁律是：构建和编译必须离开热路径。

在 Unity 中还要区分编辑器、Mono 和 IL2CPP。编辑器中 `Compile()` 成功且性能良好，不代表 IL2CPP 真机也相同。IL2CPP 环境通常不能依赖运行时 JIT 生成新代码。不同 Unity 版本和运行库实现可能采用解释器、受限编译或直接不支持某些表达式。工程上不应写出“IL2CPP 一定支持动态编译”或“IL2CPP 一定完全不可用”的绝对判断，而应把平台能力纳入测试矩阵，并为关键路径准备替代方案。

可行的替代方案有三类。第一，预生成代码：在编辑器或构建阶段扫描类型并生成强类型访问器源码，运行时直接调用。第二，解释执行：使用表达式树节点解释器逐节点求值，牺牲性能换取平台兼容。第三，混合策略：编辑器和 Mono 使用编译委托，IL2CPP 使用预生成访问器或解释器。选择哪种方案取决于调用频率、平台范围和维护成本。

#### 四、缓存是表达式树性能优化的核心

表达式树的收益取决于缓存。没有缓存，表达式树通常不配谈性能优化。缓存的对象可以是编译后的委托、解释执行计划、成员访问器、表达式结构分析结果，也可以是预生成访问器的查找表。缓存的目标是保证昂贵构建只发生一次，后续调用直接复用。

缓存键设计是最容易出错的部分。简单场景中，缓存键可以是类型 + 成员名 + 访问模式，例如 `Player.Level.Getter`。复杂规则中，缓存键需要表达规则结构，而不是某次参数值。若把参数值纳入缓存键，缓存会爆炸；若缓存键缺少成员路径、返回类型或平台模式，可能错误复用执行计划。

例如，`x => x.Level > threshold` 中，`threshold` 如果是运行时参数，就应作为委托参数；如果被捕获为闭包常量，则每个不同阈值可能形成不同表达式结构，导致缓存失控。工程上应尽量把可变值参数化，把稳定结构缓存化。换句话说，缓存的是“规则形状”，不是“某次规则输入”。

缓存还要考虑生命周期。Unity 编辑器中，程序集重载、Enter Play Mode 设置、热更新域、资源卸载和场景切换都可能使缓存失效。若缓存持有旧类型、旧委托或旧对象引用，可能造成访问异常或内存泄漏。表达式树框架应提供清理入口，并在类型系统变化时重新构建缓存。

#### 五、表达式树与委托创建、反射、代码生成的关系

表达式树常被拿来与反射比较，但它不是唯一替代方案。若目标只是把一个已知方法转成委托，`Delegate.CreateDelegate` 通常更直接，构建成本更低，语义更清楚。若目标是高频字段访问，代码生成或源生成器可能比表达式树更稳定，尤其在 IL2CPP 下。若目标是编辑器工具，反射可能已经足够。

可以按动态性和执行频率划分选择边界。编译期已知且高频：直接代码或源生成。运行时确定但会高频复用：表达式树或预生成访问器。运行时确定但低频：反射。规则逻辑复杂且需要策划可编辑：DSL、Lua、可视化节点或专用规则引擎。需要跨平台 AOT 稳定：优先预生成代码，其次解释执行，谨慎依赖 `Compile()`。

表达式树的最佳位置，是比反射更结构化、比代码生成更灵活、比脚本系统更轻量的中间地带。它适合构建访问器、简单规则、谓词过滤、排序键、对象映射和数据绑定，不适合承载大型业务脚本或复杂状态机。

### 设计思路

#### 一、先判断是否真的需要表达式树

引入表达式树前，应先做场景判断。第一，调用是否足够高频。如果只在加载时调用几十次，反射更简单。第二，逻辑是否运行时确定。如果逻辑编译期已知，直接代码更可靠。第三，目标平台是否允许所选执行方式。若必须覆盖 IL2CPP 移动端，不能只依据编辑器测试。第四，团队是否愿意维护缓存、诊断和降级。表达式树框架一旦成为基础设施，就需要长期维护。

一个实用阈值是：表达式树适合“构建一次，至少调用成百上千次”的逻辑。这个阈值不是绝对数字，而是提醒设计者关注摊销。如果构建成本无法摊销，表达式树只是在增加复杂度。

对 Unity 项目而言，优先考虑以下适用场景。第一，序列化/反序列化中的成员 getter/setter。第二，UI 数据绑定中稳定路径的属性读取。第三，配置规则中结构简单、调用频繁的数值表达式。第四，编辑器中生成运行时代码或校验配置。第五，动态排序、过滤和对象映射。对于复杂战斗逻辑、任务脚本、剧情条件和热更新业务规则，应谨慎评估是否需要更正式的脚本系统。

#### 二、访问器生成应强类型化

表达式树最常见的 Unity 用法，是生成属性或字段访问器。访问器应尽量强类型化，例如 `Func<TTarget, TValue>` 和 `Action<TTarget, TValue>`，而不是统一使用 `Func<object, object>`。强类型访问器能减少装箱拆箱，调用时也更安全。

但框架层有时需要统一存储访问器，这时可以在外层做一次适配。内部缓存强类型委托，外部暴露对象接口。高频调用路径应尽量避免对象接口，低频管理路径可以使用统一包装。若所有调用都走 `object`，表达式树的性能优势会被装箱和类型转换抵消一部分。

访问器生成还要处理值类型。若目标对象是结构体，属性 setter 涉及复制语义，`Action<object, object>` 很容易只修改装箱副本而不是原始值。对于结构体，应尽量避免通用对象 setter，或使用 `ref` 语义、源生成代码、专用容器来保证写回正确。表达式树能生成复杂访问器，但不能消除值类型语义本身的陷阱。

#### 三、缓存键应表达结构而不是输入

缓存访问器时，键通常包含目标类型、成员路径、访问类型、返回类型和平台执行模式。例如同一个 `Player.Level`，在 Mono 下可能缓存编译委托，在 IL2CPP 下可能缓存解释计划或预生成访问器。执行模式不同，不应共用同一缓存项。

缓存规则表达式时，键应表达规则结构。比如“属性 A 大于参数 p”是一种结构，“属性 A 大于 10”和“属性 A 大于 20”如果把常量直接写进树中，就会形成两个结构。若这些阈值来自配置且数量很多，应把阈值设计为参数，让同一个执行计划接收不同输入。否则缓存会随配置规模线性膨胀。

缓存还应有容量策略。数据绑定访问器通常数量有限，可以常驻；玩家自定义筛选、GM 工具公式、临时调试表达式可能数量不稳定，应设置 LRU 或按场景清理。没有上限的表达式缓存，本质上是潜在内存泄漏。

#### 四、IL2CPP 下优先设计预生成与降级

若项目目标包含 IL2CPP，表达式树方案必须从设计阶段就考虑 AOT。最保守的策略是：运行时不依赖动态编译，核心热路径使用预生成代码。编辑器工具可以扫描类型和配置，生成 getter/setter、规则函数或映射表；运行时只加载这些预生成访问器。

解释执行适合低频或非关键路径。自定义 `ExpressionVisitor` 可以把表达式树转换为解释计划，运行时逐节点求值。解释执行通常慢于编译委托，但可能仍快于每次完整反射，且跨平台更稳定。对于 UI 绑定、调试显示、低频配置判断，它可能足够。

混合策略应明确写入代码，而不是靠隐含平台判断散落各处。可以定义统一接口 `IRuleExecutor` 或 `IAccessorFactory`，在不同平台选择 `CompiledExpressionExecutor`、`InterpretedExpressionExecutor` 或 `GeneratedAccessorExecutor`。这样上层业务不关心执行方式，平台差异集中在基础设施层。

#### 五、构建阶段预热，运行阶段只调用

表达式树不应在 `Update`、`LateUpdate`、频繁回调、序列化内层循环或战斗 tick 中构建。正确做法是在初始化阶段预热：加载配置后构建规则；进入界面前构建绑定访问器；加载存档前准备序列化访问器；编辑器构建时生成代码。运行阶段只做委托调用或解释计划执行。

预热阶段应记录耗时和失败项。如果某条规则构建失败，应在进入正式运行前暴露，而不是在战斗中第一次触发时才报错。对资源驱动规则而言，预热也是配置校验的一部分：成员路径是否存在，类型是否匹配，平台是否支持，缓存是否命中，都应在预热时确认。

#### 六、可观测性是表达式树框架的必要部分

表达式树框架如果没有可观测性，很难长期维护。至少应记录四类指标：构建数量、构建耗时、缓存命中率、执行模式分布。若存在解释执行和编译执行两种路径，还应统计各自比例。若存在失败规则，应记录规则 ID、目标类型、成员路径、失败原因和降级方式。

这些指标不仅用于性能优化，也用于排查平台差异。编辑器中全部走编译委托，真机中大量走解释执行，性能差异就能从指标中看到；缓存命中率过低，说明缓存键设计可能错误；构建耗时集中在某个界面打开时，说明预热时机需要调整。

错误信息也要面向业务可读。表达式树报错常常包含内部节点和泛型类型，如果直接抛给业务层，定位成本很高。框架应把底层异常包装为“规则 X 的成员路径 A.B.C 不存在”“字段类型 int 不能赋值 string”“IL2CPP 模式不支持该节点类型”等可行动信息。

### 进阶讨论

#### 一、表达式树不是性能优化的第一选择

性能优化应优先选择简单路径。若可以直接写代码，不要为了动态而动态；若可以在构建期生成代码，不要把问题拖到运行时；若可以改变数据结构减少访问次数，不要只优化访问方式。表达式树解决的是“动态访问重复执行”的问题，而不是所有性能问题。

例如 UI 列表卡顿，根因可能是布局重建、Canvas 批次、资源加载或对象实例化，而不是属性读取方式。若把优化重点放在表达式树访问器上，可能只优化了总耗时的很小部分。表达式树应建立在 profiling 之后，而不是作为预设答案。

#### 二、表达式树与源生成的取舍

源生成在 AOT 平台上通常更稳定。它把动态性前移到编辑器或构建阶段，运行时直接调用生成代码。缺点是灵活性下降，生成流程需要接入构建系统，代码量增加，类型变化后要重新生成。表达式树则保留运行时构建能力，适合配置变化较多、编辑器工具和中低频动态逻辑。

一种成熟做法是二者结合：开发阶段用表达式树快速验证规则形状，发布阶段把稳定规则转为生成代码；编辑器中允许动态构建和调试，真机中只运行预生成访问器；未命中预生成代码的低频规则走解释执行，并记录告警。这样既保留迭代效率，又降低发布风险。

#### 三、表达式树与热更新的边界

热更新环境中使用表达式树需要额外小心。若热更新层类型与主工程类型跨域交互，表达式树生成的委托可能持有旧程序集类型，热更新后缓存必须失效。若热更新方案本身使用解释器或 IL 虚拟机，表达式树编译委托的收益可能被跨域调用成本抵消。

因此，热更新项目应明确表达式树运行在哪一侧。主工程侧可为稳定类型生成访问器，热更新侧可通过接口调用；热更新侧如果需要动态规则，可能更适合使用热更新语言自身的函数或 DSL。不要让表达式树缓存跨越热更新生命周期而缺少清理机制。

#### 四、规则系统要限制表达式能力

如果表达式树用于配置化规则，必须限制允许的节点和方法。开放任意方法调用会带来安全、性能和可维护性风险。规则系统应定义白名单：允许访问哪些类型、哪些成员、哪些运算符、哪些纯函数；禁止文件 IO、网络、随机副作用、对象创建和复杂循环。

表达式树本身只是表示能力，不负责治理能力边界。若没有白名单和校验，配置规则可能逐渐演化成不可控脚本。此时表达式树既没有脚本系统的完整调试工具，也没有手写代码的静态约束，维护成本会快速上升。

#### 五、内容正确性比调用速度更重要

表达式树优化经常让注意力集中在调用速度上，但工程中更常见的问题是结果正确性。成员路径是否处理空值，类型转换是否符合预期，枚举和数值是否安全转换，浮点比较是否稳定，集合索引是否越界，结构体 setter 是否写回，平台间执行结果是否一致，这些都比单次调用快几个百分点更关键。

因此，表达式树框架应配套测试。每条重要规则都应有手写基准或样例输入输出；访问器应覆盖字段、属性、私有访问限制、继承、接口和值类型；平台测试应覆盖编辑器、Mono、IL2CPP 和目标设备。没有测试的表达式树优化，往往只是把错误藏得更深。

### 总结

表达式树的价值不在于替代所有反射，也不在于展示高级语法，而在于把运行时动态逻辑转化为可缓存、可分析、可复用的执行计划。它通过结构化表示降低重复反射调用成本，通过编译委托或解释计划改善高频访问性能，通过节点模型支持规则检查和转换。但这些收益只有在“构建一次、多次复用、平台可控、缓存可靠”的前提下才成立。

在 Unity 项目中，表达式树应被视为基础设施工具，而不是普通业务写法。适合它的场景包括数据绑定访问器、序列化 getter/setter、简单配置规则、动态筛选排序和编辑器生成辅助；不适合它的场景包括低频调用、复杂脚本逻辑、未经验证的 IL2CPP 热路径和可以直接静态实现的业务逻辑。

工程实践上，应先通过 profiling 确认反射或动态访问确实是瓶颈，再选择表达式树、委托创建、源生成、解释执行或脚本系统。若选择表达式树，必须同时设计强类型访问器、结构化缓存键、初始化预热、IL2CPP 降级、缓存失效、错误包装和可观测性指标。表达式树的性能优化不是一个 `Compile()` 调用，而是一整套围绕动态逻辑生命周期的工程设计。

最终判断标准很简单：如果表达式树让系统在保持必要动态性的同时减少热路径成本，并且没有牺牲平台稳定性、可诊断性和内容正确性，它就是合适的；如果它只是把反射调用包装成更复杂、更难调试的抽象，它就不是优化，而是新的技术债。

## 知识缺口

1. 不同 Unity 版本、不同 .NET Profile 和不同 IL2CPP 平台对 `Expression.Compile()` 的具体支持和退化行为需要以项目目标版本实测为准。
2. 表达式树解释执行与反射调用在具体项目中的性能关系受规则复杂度、装箱情况和缓存策略影响，需要通过 profiling 量化。
3. 源生成、表达式树和热更新解释器之间的最佳组合方案依赖项目构建管线，本文只给出原则性取舍。
4. 复杂配置规则是否应继续使用表达式树，还是升级为 DSL 或脚本系统，需要结合策划编辑需求、调试工具和安全边界进一步评估。
