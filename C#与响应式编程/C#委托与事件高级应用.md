# C# 委托与事件高级应用

## 摘要

委托与事件是 C# 中构建回调、通知、解耦通信和扩展点的核心机制。在 Unity 项目中，它们出现在 UI 按钮回调、状态变化通知、模块间通信、资源加载完成、网络回包转发、对象生命周期管理和响应式框架之中。委托让“调用哪个方法”可以被运行时组合，事件则在委托基础上增加发布者边界，限制外部只能订阅或取消订阅，不能随意清空或触发调用链。它们的价值不只是语法便利，而是为系统提供一种受控的间接调用模型。

本文围绕委托与事件在 Unity 工程中的高级应用展开，核心论点是：事件不是“无耦合通信”，而是一种需要治理的受控耦合。它能降低直接依赖，却会引入生命周期、调用顺序、异常传播、线程切换、调试追踪和事件风暴等新问题。文章先说明委托和事件为什么成为 Unity 通信基础，再分析多播委托、`event` 封装、闭包捕获、订阅引用、`UnityEvent`、弱事件和响应式流的底层机制；随后提出事件边界、生命周期绑定、强类型消息、异常隔离、主线程调度和可测试性设计；最后给出适用场景与替代方案。目标不是重复语法教程，而是建立一套可长期维护的事件治理框架。

## 正文

### 背景

#### 一、Unity 项目为什么离不开委托与事件

Unity 项目天然充满“某件事发生后通知另一段逻辑”的需求。角色血量变化后 UI 要刷新，按钮点击后业务要响应，资源加载完成后场景要继续，网络回包到达后模型要更新，对象被回收时订阅要解除，任务状态改变后红点系统要重新计算。如果所有调用都写成直接引用，模块之间会迅速形成密集依赖：UI 直接知道战斗对象，战斗对象直接知道音效系统，资源系统直接知道业务流程，最终任何局部改动都可能牵动大量代码。

委托与事件提供了一种中间层。发布者只负责在状态变化时发出通知，订阅者自行决定是否响应。发布者不必知道订阅者是谁，订阅者也不需要改变发布者内部逻辑。这种间接调用让系统获得扩展性。例如同一个“血量变化”事件可以同时触发 UI 刷新、受击音效、屏幕震动和日志记录；新增一个订阅者不需要修改血量组件。

但这种解耦不是免费获得的。事件隐藏了调用关系，调用链不再像普通函数调用那样直观；订阅者生命周期若长于发布者或短于发布者，都会出现漏回调或泄漏风险；多播委托中某个订阅者异常可能影响后续订阅者；异步和多线程场景还会引入主线程调度问题。事件越全局，调试越困难；订阅越随意，系统越难维护。

因此，Unity 中使用委托与事件的核心不是“能不能通知”，而是“通知边界是否清楚，生命周期是否受控，异常是否隔离，调用关系是否可追踪”。事件系统的成熟程度，往往决定一个项目的模块通信能否长期稳定。

#### 二、事件是受控耦合，不是无耦合

很多项目把事件总线或发布订阅理解为“解耦神器”，这是一种危险误解。事件确实减少了发布者对订阅者的直接引用，但订阅者仍然依赖事件语义，发布者仍然承诺某些状态变化会发出通知。事件名称、参数结构、触发时机、触发次数、调用线程、异常策略，都构成了隐式或显式契约。

如果契约没有被设计，事件会变成隐形耦合。订阅者不知道事件何时触发，发布者不知道谁在监听，调试时很难判断某个行为是由哪条事件链导致。全局事件总线滥用后，系统表面上没有直接引用，实际却到处通过字符串或消息类型互相影响。

因此，事件应被视为一种受控耦合。它适合表达“状态拥有者向外声明状态变化”，不适合表达任意模块之间的隐秘命令。一个健康的事件设计应能回答：谁拥有事件，谁允许发布，谁允许订阅，事件参数代表事实还是命令，订阅者异常如何处理，订阅何时释放，是否允许跨线程触发。

#### 三、Unity 生命周期放大了事件风险

普通 C# 程序中，事件泄漏已经是常见问题；Unity 中风险更高。`MonoBehaviour` 有 `Awake`、`OnEnable`、`Start`、`OnDisable`、`OnDestroy` 等生命周期；对象可能被销毁，也可能只是禁用；对象池会反复激活和回收；场景切换会销毁大量对象；静态管理器可能跨场景存活；热更新对象和主工程对象还可能拥有不同生命周期。

这些生命周期差异直接影响订阅管理。若对象在 `OnEnable` 订阅，却没有在 `OnDisable` 取消订阅，对象池回收后仍可能收到回调；若在 `Start` 订阅，却在 `OnDestroy` 取消，禁用期间仍可能响应事件；若订阅静态事件却忘记清理，场景切换后旧对象可能被引用而无法释放；若 Lambda 订阅没有保存引用，取消订阅可能失败。

因此，Unity 项目不能只依赖“记得 `-=`”这种人工纪律。成熟项目应建立生命周期绑定机制，例如订阅返回 `IDisposable`，对象销毁时统一释放；或者在基类中维护订阅令牌；或者使用响应式框架的 `AddTo`。事件生命周期管理是架构问题，不只是编码习惯。

### 核心原理

#### 一、委托是类型安全的调用引用

委托可以理解为带签名约束的方法引用。它规定参数类型和返回值类型，任何匹配签名的方法都可以被赋给委托变量。与普通函数指针相比，C# 委托是对象，能持有目标实例、方法信息和调用列表，因此既可以引用静态方法，也可以引用实例方法，还可以组合多个订阅者。

委托的类型安全非常重要。`Action<int>` 表示接收一个 `int` 且无返回值的调用，`Func<Player, bool>` 表示接收 `Player` 并返回布尔值的调用。编译器会检查签名匹配，避免很多运行时错误。相比反射式 `Invoke`，委托更适合高频稳定调用。

在 Unity 工程中，委托常用于策略注入、异步回调、生命周期通知、条件判断和轻量扩展点。比如资源加载接口接收完成回调，状态机节点接收进入/退出委托，排序系统接收比较函数，UI 组件暴露点击回调。它的本质价值是把“行为”作为参数传递，从而让调用者不必硬编码具体执行逻辑。

#### 二、多播委托是顺序调用链

C# 委托可以多播。多个方法通过 `+=` 加入调用列表，调用委托时会按顺序依次执行。事件底层也常依赖多播委托。这个机制看似简单，却有几个工程含义。

第一，调用顺序通常与订阅顺序相关，但不应让业务强依赖这种顺序。若某个逻辑必须先于另一个逻辑，应使用显式流程、优先级队列或管线，而不是依赖谁先订阅。第二，若某个订阅者抛出异常，普通多播调用会中断后续调用。生产级事件系统若希望订阅者之间隔离，应遍历调用列表并逐个 try/catch。第三，委托调用是同步的，发布者会被所有订阅者阻塞。

这意味着事件发布不是“发出去就结束”。发布者实际上承担了订阅者执行时间和异常风险。若一个事件可能有多个不可信订阅者，就应该设计异常隔离和耗时监控。否则一个看似无害的 UI 事件可能因为某个订阅者做了资源加载而阻塞主线程。

#### 三、event 关键字保护发布者边界

委托字段如果直接公开，外部代码可以赋值覆盖、清空调用链，甚至直接触发调用。这会破坏发布者边界。`event` 关键字在委托基础上增加访问限制：外部只能订阅和取消订阅，不能直接赋值或触发事件。事件只能由声明它的类型内部触发。

这种限制的意义不只是语法安全，而是所有权表达。谁拥有状态，谁发布事件。外部模块可以观察状态变化，但不能伪造状态变化。比如 `Health.OnChanged` 应由血量组件在血量真实变化时触发，而不是任意外部对象直接 Invoke。否则事件语义会失真，订阅者无法信任它代表真实事实。

因此，正式代码中应优先暴露 `event`，而不是公开委托字段。若需要更复杂的订阅控制，可以自定义 `add/remove` 访问器，在其中记录日志、限制重复订阅或返回诊断信息。事件封装的目标是维护发布者的语义权威。

#### 四、订阅会形成引用关系

事件订阅不是纯粹的消息关系，它会形成对象引用。实例方法订阅事件时，委托会持有目标对象引用；只要发布者仍然持有该委托，订阅者就可能无法被 GC 回收。若发布者是全局管理器或静态事件，订阅者是场景对象，忘记取消订阅就会造成泄漏或销毁对象被回调。

Unity 中这种问题尤其隐蔽。一个 `MonoBehaviour` 被 `Destroy` 后，其托管对象不一定立刻消失；如果仍被静态事件引用，回调中访问 Unity 对象可能表现为“看似 null”或抛出异常。对象池场景中，对象未销毁但已回收，如果仍响应全局事件，也会出现禁用对象执行逻辑。

解决这类问题的核心是让订阅具备所有权。谁订阅，谁持有释放令牌；谁拥有生命周期，谁负责释放。订阅 API 最好返回 `IDisposable`，由生命周期容器统一释放。这样订阅不再是散落的 `+=` 和 `-=`, 而是可管理资源。

#### 五、UnityEvent 是序列化友好事件，不是高性能默认选项

`UnityEvent` 的价值在于编辑器可视化和序列化。策划或美术可以在 Inspector 中绑定响应方法，Prefab 可以保存事件连接，组件可以暴露无需代码接线的回调。这非常适合按钮点击、动画事件、低频交互和工具型组件。

但 `UnityEvent` 与原生 C# 事件不是同一类优化目标。它需要支持序列化、持久化调用、编辑器绑定和动态参数处理，因此调用路径通常更重，调试和重构也有额外风险。不同 Unity 版本和绑定方式下开销不同，不能简单用固定倍数概括，但高频运行路径不应默认使用 `UnityEvent`。

一个实用原则是：面向 Inspector 配置、低频交互和设计师接线，可以使用 `UnityEvent`；面向高频状态变化、框架内部通信和大量对象通知，优先使用原生 C# 事件、委托、显式接口或响应式流。

### 设计思路

#### 一、先定义事件所有权

事件设计的第一步是确定所有权。一个事件应由最了解状态变化的对象发布。血量变化由血量模型发布，背包内容变化由背包系统发布，资源加载进度由加载任务发布，按钮点击由按钮组件发布。不要让外部协调器随意代替状态拥有者发布事件，否则事件会失去事实来源。

所有权还决定命名。表示事实的事件应使用过去式或状态变化语义，例如 `HealthChanged`、`ItemAdded`、`LoadCompleted`；表示请求的命令不应伪装成事件，例如 `OpenPanelRequested` 可以是消息，但它不等于面板已经打开。事实事件和命令消息混淆，会让订阅者对系统状态产生误判。

事件文档应说明触发时机。是在值变化前还是变化后触发？初始化时是否触发一次？重复设置相同值是否触发？对象禁用时是否触发？场景卸载时是否触发完成事件？这些问题不明确，订阅者就会写出防御性代码，事件系统也会逐渐混乱。

#### 二、使用强类型消息

事件参数应尽量强类型化。`object` 参数和字符串事件名虽然灵活，但会把类型检查推迟到运行时，也增加文档依赖。强类型消息能让编译器参与检查，并让订阅者明确知道事件包含哪些信息。

对于简单事件，可以直接传基础值，例如 `event Action<int> HealthChanged`。对于复杂事件，建议定义不可变消息结构，例如包含旧值、新值、变化原因、来源对象和时间戳。不可变消息能避免订阅者修改事件数据影响其他订阅者。

消息结构不应无限膨胀。如果一个事件参数越来越大，说明事件语义可能不够单一。此时应拆分事件，或改为显式查询模型状态。事件参数的职责是描述这次变化的必要上下文，而不是把整个系统状态塞给订阅者。

#### 三、生命周期绑定应成为基础设施

Unity 项目应避免把取消订阅完全交给人工记忆。更稳妥的做法是封装订阅 API，使订阅返回释放令牌，然后把令牌绑定到对象生命周期。示意模式如下：

```csharp
// 订阅返回 IDisposable，生命周期结束时统一 Dispose。
// token = eventSource.Subscribe(OnChanged);
// lifetime.Add(token);
```

代码示例可以很短，重点是机制：订阅是资源，资源必须释放。`OnEnable` 订阅应对应 `OnDisable` 释放；跨场景对象订阅静态事件时，应对应显式生命周期容器；对象池对象回收时，应释放所有外部订阅。生命周期绑定越统一，事件泄漏越少。

对于 Lambda 订阅，要特别注意取消订阅。`source.Event += x => Handle(x)` 和 `source.Event -= x => Handle(x)` 不是同一个委托实例，取消不会生效。若需要取消，应保存委托变量，或使用返回令牌的封装 API。这个细节在 Unity 项目中非常常见，也是事件泄漏的重要来源。

#### 四、异常隔离要按事件类型设计

默认多播委托中，一个订阅者异常会中断后续订阅者。是否接受这种行为，取决于事件类型。对于核心流程事件，例如保存数据、支付确认、状态机转换，异常中断可能是合理的，因为系统不应在不一致状态下继续。对于通知型事件，例如 UI 刷新、音效播放、日志记录，某个订阅者异常不应影响其他订阅者。

因此，事件系统应区分“强一致事件”和“广播通知事件”。前者可以让异常向上传播，后者应隔离订阅者异常并记录日志。若使用自定义事件总线，可以通过事件类型配置异常策略；若使用原生事件，可以在发布者内部遍历调用列表实现隔离。

异常隔离还应配合耗时监控。一个订阅者没有抛异常，但执行了昂贵操作，同样会阻塞发布者。开发版可以记录事件派发耗时和订阅者耗时，帮助发现事件链中的隐藏性能问题。

#### 五、跨线程事件必须回到 Unity 主线程

Unity API 大多要求主线程调用。网络回包、文件 IO、SDK 回调或后台任务完成时，如果直接触发事件，并且订阅者访问 Unity 对象，就可能出现线程错误。事件系统不能假设所有发布都发生在主线程。

跨线程事件应进入主线程调度层。后台线程只投递消息或任务，主线程在 `Update` 或 PlayerLoop 阶段统一派发。这样订阅者可以安全访问 Unity 对象，事件顺序也更可控。若某些事件允许后台处理，应明确标注，并限制订阅者不能调用 Unity API。

主线程调度还要考虑队列积压。如果后台事件产生速度高于主线程消费速度，应设置限流、合并或丢弃策略。例如下载进度事件可以合并，只保留最新进度；日志事件可以批量处理；关键状态事件则不能丢弃。事件系统需要根据语义选择策略。

#### 六、全局事件总线要有边界

全局事件总线方便，但最容易滥用。它让任何模块都可以发布和订阅任何消息，短期减少引用，长期增加隐式耦合。若没有边界，事件总线会变成全局可变状态的另一种形式。

全局事件总线适合跨领域的系统级通知，例如登录状态变化、语言切换、全局配置刷新、场景加载阶段变化。不适合承载局部对象内部事件，例如某个敌人的血量变化、某个 UI 控件的内部状态、某个临时流程的步骤推进。这些局部事件应归属具体对象或局部上下文。

如果项目使用事件总线，应建立命名空间、消息类型白名单、发布权限和调试工具。至少要能查询某个事件有哪些订阅者、最近由谁发布、发布次数和耗时。没有观测能力的事件总线，很容易成为最难排查的系统。

### 进阶讨论

#### 一、事件与命令的区别

事件描述已经发生的事实，命令表达希望发生的动作。`HealthChanged` 是事件，表示血量已经变化；`ApplyDamage` 是命令，表示请求造成伤害。混淆二者会导致系统语义混乱。若订阅者收到事件后再决定是否允许该事实发生，说明它其实应该参与命令处理或规则校验，而不是订阅事实事件。

在 Unity 业务中，这个区分很重要。按钮点击可以被视为输入事件，但“打开商城”更像命令；任务完成是事实事件，但“领取奖励”是命令；资源加载完成是事实事件，但“开始加载”是命令。事件系统不应承担所有流程控制，否则系统会变成难以追踪的链式反应。

#### 二、事件与响应式流的取舍

UniRx、R3 或其他响应式框架把事件提升为可组合的数据流，提供过滤、合并、节流、生命周期绑定和异步组合能力。对于 UI 输入、状态变化、异步流程和复杂订阅链，响应式流比普通事件更有表达力。

但响应式也有成本。链式操作过多会增加阅读难度；调试调用链需要工具和经验；过度响应式化会让简单逻辑变得抽象。普通事件适合简单通知和局部解耦，响应式流适合需要组合、节流、取消和生命周期管理的连续事件。选择时应看问题复杂度，而不是统一偏好某种范式。

#### 三、弱事件不是万能解法

弱事件通过 `WeakReference` 避免发布者强引用订阅者，看起来可以解决泄漏。但弱事件也有代价：调用前需要检查目标是否仍存在，调试更复杂，订阅者可能在预期之外被回收，性能也不如普通委托直接。Unity 中对象生命周期又包含托管对象和引擎对象双重语义，弱引用未必能完全表达对象是否可用。

因此，弱事件适合少数长生命周期发布者与短生命周期订阅者之间的松散通知，不应替代正常生命周期管理。更推荐的基础做法仍然是显式释放令牌、生命周期容器和订阅审计。弱事件是补充机制，不是默认事件模型。

#### 四、调用顺序不应成为隐式协议

多播委托按订阅顺序调用，但业务不应依赖这种隐式顺序。若系统要求“先校验，再修改，再通知，再刷新 UI”，应使用显式流程或管线。事件更适合通知已经发生的事实，而不是组织严格有序的业务事务。

如果确实需要顺序，可以设计带优先级的事件系统，但这会增加复杂度。优先级一旦开放，模块之间可能通过调整优先级互相抢占，形成新的隐式耦合。优先级事件应只用于少数框架级场景，例如输入处理、渲染扩展或启动流程，不应成为普通业务事件默认能力。

#### 五、事件系统也需要测试

事件代码常被认为“不好测”，但它实际上非常需要测试。至少应覆盖订阅、取消订阅、重复订阅、发布顺序、异常隔离、对象销毁后不再回调、跨线程调度回主线程、事件参数不可变等场景。测试可以使用普通 C# 类完成，不必依赖 Unity 场景。

可测试性来自设计。若事件发布散落在 `MonoBehaviour` 中且强依赖场景对象，测试会很困难；若核心状态模型是普通 C# 类，Unity 组件只负责桥接，测试就容易得多。事件系统的可测试性，反过来会推动业务逻辑从场景对象中解耦出来。

#### 六、事件可观测性决定排障成本

事件系统应提供最小观测能力。开发版可以记录事件发布次数、最近发布时间、订阅者数量、派发耗时和异常订阅者。全局事件总线尤其需要调试面板，否则很难排查“谁发布了这个事件”“为什么这个订阅者还在”“为什么某个事件一帧触发几百次”。

观测能力不一定进入发布版，但开发期必须存在。事件系统的问题往往表现为间接症状：UI 重复刷新、对象销毁后仍响应、某个模块莫名执行、帧时间偶发抖动。没有观测时只能搜索代码；有观测时可以直接定位事件链。


#### 七、高频事件要先质疑是否应该存在

并不是所有状态变化都应该被设计成事件。高频事件尤其需要谨慎，例如每帧位置变化、每个实体属性微小波动、每个 UI 元素布局更新、每个动画采样点通知。如果这些变化直接通过事件广播，订阅者数量一旦增加，就会形成难以预测的帧时间抖动。事件系统看似解耦，实则把成本扩散到了所有订阅者。

对高频变化，通常有三种替代思路。第一，拉模式：订阅者在自己的更新节奏中读取状态，而不是由发布者每次推送。第二，合并模式：一帧内多次变化只发布一次最终结果，例如 UI 脏标记。第三，分层模式：底层高频变化不发全局事件，只在跨越阈值、状态切换或需要外部响应时发布事件。这样事件表达的是有业务意义的变化，而不是所有内部细节。

这条原则在 Unity UI 中尤其重要。数值连续变化时，不一定每次变化都刷新文本、布局和动画；可以使用脏标记、节流、合帧更新或差异阈值。事件系统越靠近热路径，越要从“通知所有变化”转向“通知值得响应的变化”。

#### 八、重复订阅和闭包捕获是 Unity 事件常见隐患

重复订阅常发生在 `OnEnable` 中。如果对象每次启用都 `+=`，但禁用时没有对称 `-=`, 同一个处理器会被调用多次。表现可能是按钮点击触发两次、音效重复播放、网络请求重复发送。由于事件调用本身没有默认去重，系统不会自动提醒。框架层可以在开发版检测重复订阅，或者在订阅容器中记录来源。

闭包捕获则常发生在循环绑定 UI 或动态创建按钮时。若 Lambda 捕获了循环变量或临时对象，所有回调可能引用同一个最终值，或者持有本应释放的对象。现代 C# 对部分循环变量捕获已有改进，但闭包生命周期仍然需要谨慎。对于长期存在的事件订阅，最好使用命名方法或显式保存委托变量；对于临时 Lambda，应确保释放令牌随对象生命周期结束。

这些问题的共同点是：事件代码写起来很短，错误却会在很远处显现。按钮重复响应、对象无法回收、旧界面收到新事件，表面上像业务 bug，本质上往往是订阅管理 bug。正式项目应把重复订阅检测和订阅来源记录纳入事件基础设施。

#### 九、发布者也要承担事件质量责任

事件治理不能只要求订阅者“记得解绑”。发布者同样需要承担质量责任。发布者应保证事件只在状态真实变化时触发，保证参数完整且一致，保证触发时对象处于可观察的稳定状态，保证文档说明事件是否可能重入。若发布者在状态修改一半时触发事件，订阅者读取到的可能是不完整状态；若发布者在销毁过程中触发事件，订阅者可能访问到半失效对象。

重入问题也需要注意。某个订阅者在处理事件时可能再次修改发布者状态，导致同一事件递归触发。轻则重复刷新，重则栈溢出或状态错乱。对于可能重入的事件，发布者应设计防护：延迟派发、队列化、状态锁、或明确禁止订阅者在回调中修改同一状态。事件越接近核心状态模型，越需要考虑重入。

因此，事件不是发布者把责任“广播出去”。恰恰相反，发布者拥有事件语义，就必须保证事件质量。订阅者可以自由响应，但发布者必须提供稳定事实。


### 总结

委托与事件是 C# 和 Unity 工程中非常重要的通信基础。委托提供类型安全的行为引用，多播委托提供顺序调用链，`event` 关键字保护发布者边界，`UnityEvent` 提供编辑器序列化能力，响应式流提供更强的组合能力。它们共同解决的是“如何让模块在不直接硬编码对方的情况下响应变化”。

但事件不是无成本解耦。它会引入生命周期、异常传播、调用顺序、线程切换、全局总线滥用和调试追踪问题。成熟项目应把事件视为受控耦合，明确事件所有权、触发时机、参数结构、订阅释放和异常策略。

在 Unity 中，事件治理尤其要重视生命周期。`OnEnable/OnDisable`、对象池、场景切换、静态事件、Lambda 订阅和跨线程回调都会影响事件可靠性。把订阅封装为可释放资源，并绑定到生命周期容器，是减少泄漏和幽灵回调的关键。

最终，委托与事件的高级应用不在于写出复杂事件系统，而在于选择合适的通信粒度：局部状态用对象事件，跨模块通知用受控消息，严格流程用显式命令或管线，高频路径用直接调用或缓存委托，编辑器接线用 `UnityEvent`。只有边界清楚、生命周期受控、异常可观测，事件系统才会成为解耦工具，而不是隐藏耦合的温床。

## 知识缺口

1. 不同 Unity 版本、不同绑定方式下 `UnityEvent` 与原生 C# 事件的性能差异需要结合目标平台实测，不能用固定倍数概括所有情况。
2. UniRx、R3 与自研事件系统在生命周期绑定、调试工具和 GC 压力方面的实际取舍，需要按项目框架进一步评估。
3. 对象池、热更新和跨场景静态管理器组合下的事件泄漏检测，需要配套工具或运行时审计机制进一步完善。
4. 多线程事件调度与 Unity PlayerLoop 集成的最佳方案，取决于项目网络库、异步框架和主线程任务队列设计。
