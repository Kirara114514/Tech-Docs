# ReactiveProperty 详解

## 摘要

`ReactiveProperty<T>` 是 Unity 响应式编程中最常用的状态抽象之一。它的价值不在于把普通字段换成更“高级”的写法，而在于把“当前状态”和“状态变化通知”放进同一个可订阅边界中。对 Unity 项目而言，血量、金币、连接状态、加载进度、按钮可用性、表单合法性、红点状态等都不是孤立变量，而是会驱动 UI、逻辑分支、派生状态和跨模块协作的持续状态。`ReactiveProperty<T>` 让这些状态具备统一的观察、组合和生命周期管理方式。

本文围绕 `ReactiveProperty<T>` 的工程使用展开，核心论点是：`ReactiveProperty<T>` 不是事件总线，也不是所有字段的默认替代品，而是一种用于表达“当前值持续存在且需要被观察”的状态容器。文章先分析传统字段、事件和回调在复杂 Unity 状态管理中的问题，再解释 `ReactiveProperty<T>` 的当前值语义、初始推送、只读暴露、去重比较、派生状态、生命周期释放和调度边界；随后提出状态建模、ViewModel 归属、订阅释放、派生状态组织和调试策略；最后讨论与普通属性、事件、`Subject<T>`、集合状态和高级封装之间的取舍。目标是帮助团队建立稳定、克制、可维护的响应式状态使用规范。

## 正文

### 背景

#### 一、Unity 状态复杂度来自变化传播

Unity 项目中，很多问题不是值本身复杂，而是值变化后要通知谁、何时通知、通知后谁负责刷新。角色血量变化会影响血条、受伤效果、死亡判定、音效和任务条件；背包变化会影响列表、红点、资源计数和引导系统；网络状态变化会影响按钮可点、重连提示和界面遮罩。一个字段从 A 变成 B，背后可能牵动多个模块。

传统写法通常把状态保存和变化通知拆开：字段保存当前值，事件通知变化，UI 或其他模块订阅事件。小规模时可以接受，但项目变大后容易出现字段和事件不同步、事件漏发、重复刷新、订阅释放不清、派生状态到处手写等问题。更糟的是，新接入的界面常常需要手动读取当前值并订阅后续变化，否则会出现初始 UI 与真实状态不一致。

`ReactiveProperty<T>` 把当前值和变化通知统一起来。订阅者不仅能在值变化时收到通知，也能在订阅时获得当前值，从而让 UI 初始化和后续刷新走同一条路径。它的意义不是节省几行事件代码，而是让“状态作为数据流”成为明确模型。

#### 二、ReactiveProperty 表达的是状态，不是瞬时事件

理解 `ReactiveProperty<T>` 的第一条边界，是区分状态和事件。状态有当前值，事件是一次发生。当前血量、当前登录状态、当前冷却剩余、当前按钮是否可点，这些都适合用属性表达；按钮刚点击一次、奖励刚领取一次、音效刚播放一次、怪物刚死亡一次，这些更适合用事件流、命令或消息表达。

如果把瞬时事件塞进 `ReactiveProperty<T>`，会出现语义扭曲。比如用 `ReactiveProperty<bool>` 表示按钮点击，点击后设为 true，为了下一次点击又要改回 false；新的订阅者可能一接入就收到上一次 true，误以为刚发生点击。这类问题不是 API 错误，而是建模错误。

因此，团队应先判断对象是否需要“当前值”。若需要当前值，并且后续订阅者也应知道当前状态，`ReactiveProperty<T>` 合适；若只是一次性通知，则应使用事件或 `Subject<T>`。

#### 三、响应式能力会放大架构质量

`ReactiveProperty<T>` 能让状态传播更清楚，也能让错误传播更快。如果状态所有权不清、写入入口随意、订阅生命周期混乱，那么响应式化只会让问题更隐蔽。比如公开可写属性后，任何模块都能修改状态；多个订阅者在回调中继续写其他状态，形成反馈环；对象池对象重复订阅，导致同一变化触发多次。

因此，响应式编程不能替代架构设计。它要求团队更清楚地定义状态归属、写入边界、订阅释放和派生关系。`ReactiveProperty<T>` 是状态建模工具，不是自动整理混乱代码的工具。

### 核心原理

#### 一、当前值语义是 ReactiveProperty 的基础

`ReactiveProperty<T>` 保存当前值，同时向订阅者推送变化。与普通事件不同，订阅者通常会立即收到当前值。这对 UI 初始化非常有利：界面打开时订阅状态，马上能得到当前血量、当前金币、当前按钮可用性，不必额外调用一次刷新方法。

但立即推送也容易误用。订阅回调如果包含播放动画、发送埋点、弹窗、发网络请求等副作用，就可能在初始化时误触发。状态初始化同步与真实业务变化不是同一件事。对于只应在后续变化时触发的副作用，需要使用跳过初始值、变化上下文、旧值比较或专门事件流。

因此，当前值语义既是优势也是约束。使用 `ReactiveProperty<T>` 时，必须明确订阅回调是否能处理初始值。如果不能，就说明这段逻辑可能不应该直接订阅原始状态。

#### 二、只读暴露保护状态所有权

`ReactiveProperty<T>` 同时提供读取、写入和订阅能力。如果直接公开可写实例，任何调用方都能修改值，状态所有权会失控。正式项目中，通常应内部持有可写属性，对外暴露 `IReadOnlyReactiveProperty<T>` 或只读封装。

这种做法让外部可以观察状态，但不能随意修改状态。修改必须通过领域方法、命令或服务接口。例如玩家血量由战斗模型修改，UI 只能观察；登录状态由登录服务修改，按钮只观察；红点状态由红点系统计算，界面只绑定。这样状态写入可以统一校验、记录日志和维护边界。

只读暴露是响应式状态工业化的基础。如果团队仍然到处公开可写 `ReactiveProperty<T>`，后续再谈复杂封装、派生状态和调试工具都会很困难。

#### 三、去重比较影响通知正确性

很多响应式属性会避免相同值重复通知，减少无意义刷新。但“相同”并不总是默认 `Equals`。浮点数需要容差，向量可能需要距离阈值，列表引用不变但内容变化可能仍需刷新，复杂对象可能根据版本号判断。比较策略决定哪些变化被系统看见。

如果比较过严，该通知时不通知；如果比较过松，不该刷新的时候频繁刷新。比如 UI 文本只关心整数变化，战斗位置同步可能只关心超过阈值的移动，配置对象可能用版本号代表内容变化。比较器是业务语义的一部分，而不是纯性能优化。

关键状态应明确比较策略，并通过测试覆盖。不要默认所有类型都适合 `EqualityComparer<T>.Default`，也不要为了省事关闭所有去重。

#### 四、派生状态是 ReactiveProperty 的重要价值

`ReactiveProperty<T>` 可以通过 `Select`、`Where`、`CombineLatest` 等操作符构建派生状态。比如账号和密码共同决定登录按钮是否可用，血量和连接状态共同决定战斗界面是否可操作，多个任务状态共同决定红点是否显示。派生状态把原本散落在 UI 中的条件判断收束为可命名、可订阅、可测试的状态。

派生状态的价值在于显式表达依赖关系。但如果派生逻辑散落在各个 View 和 Presenter 中，又会变成新的隐式复杂度。关键派生状态应收敛到 ViewModel、状态模型或专门聚合层，而不是让每个订阅者自己组合。

派生状态还要考虑生命周期和循环依赖。派生属性订阅了源属性，必须释放；派生链不能无意写回源状态；多个源状态同一帧变化时，可能需要合并通知，避免 UI 重复刷新。

#### 五、生命周期管理是使用底线

订阅必须释放。Unity 中对象生命周期复杂：界面打开关闭、对象池复用、场景切换、全局单例跨场景存在。订阅如果绑定错生命周期，就会出现旧对象回调、重复刷新或内存泄漏。

`AddTo`、`TakeUntilDestroy` 等工具很有用，但它们不能替代生命周期判断。对象池对象不一定销毁，禁用也不等于销毁；跨场景状态订阅短生命周期 View，需要明确释放点；ViewModel 创建的派生属性也要随 ViewModel 释放。使用响应式状态时，必须能回答每个订阅归谁拥有、何时释放。

生命周期归属不清，是响应式代码难维护的主要原因之一。团队规范应把释放策略作为必选项，而不是事后补救。

### 设计思路

#### 一、把 ReactiveProperty 放在状态组织层

`ReactiveProperty<T>` 最自然的归宿是 ViewModel、Presenter、状态模型、Facade 或状态聚合节点。这些层负责组织状态并对外传播。把属性散落在各种 `MonoBehaviour`、工具类和回调类中，会让状态来源越来越分散。

View 层应尽量只消费只读状态，业务服务通过方法修改状态，状态模型负责保存和组合。这样，新成员能快速找到状态源头，问题排查也更容易从状态模型开始。响应式状态应成为架构的一部分，而不是脚本局部技巧。

#### 二、区分原始状态、派生状态和事件流

状态体系应分层。原始状态来自业务事实，例如血量、金币、连接状态；派生状态由原始状态计算，例如是否死亡、按钮是否可点、是否显示红点；事件流表示一次性动作，例如按钮点击、任务完成、播放提示。

这三类抽象不应混用。原始状态应有明确写入者；派生状态应只读计算；事件流不应持有当前值。只要分类清楚，响应式链路就会更容易理解。

#### 三、订阅回调保持轻量

订阅回调适合做表现刷新、轻量协调和状态转发，不适合承载复杂事务。若订阅中执行多步业务、写多个状态、发网络请求、触发复杂流程，系统会变得难以追踪。复杂逻辑应提升为命令、服务或状态机。

尤其要避免在订阅回调中写回同一状态或多个核心状态。若确实需要响应某个状态变化发起流程，应通过明确命令或调度器处理，并做好重入防护。

#### 四、为关键状态建立调试入口

关键状态应支持调试。可以记录最近写入来源、订阅数量、派生关系、变化次数和最后更新时间。开发版可以显示状态面板，帮助定位“谁改了值”“谁还在订阅”“为什么没刷新”。

调试能力对响应式系统尤其重要，因为调用链不再像普通函数那样直观。没有观测工具时，排查只能靠搜索订阅代码；有状态调试入口时，可以直接从状态源头查看传播路径。

#### 五、集合状态使用专门集合抽象

`ReactiveProperty<List<T>>` 不是列表状态的默认好选择。列表内容变化时，如果引用不变，属性未必通知；如果每次替换整表，UI 可能只能全量刷新。对于动态列表，应该考虑 `ReactiveCollection<T>`、差量事件、列表 ViewModel 或不可变列表配合版本号。

只有当列表作为整体快照使用时，`ReactiveProperty<IReadOnlyList<T>>` 才比较合适。例如筛选结果整体替换、排行榜快照更新、配置列表重新加载。若需要插入、删除、移动、单项刷新，差量模型更合适。

#### 六、线程调度要在边界明确

Unity UI 订阅通常需要在主线程执行。若状态由网络或后台任务更新，必须明确调度策略。可以规定状态写入只能在主线程，也可以在订阅端使用主线程调度，还可以在状态封装中统一切回主线程。关键是不能假设所有回调天然安全。

线程问题往往在编辑器中不明显，在真机和高并发环境中暴露。越靠近 Unity 对象的状态，越应严格要求主线程写入或主线程观察。

### 进阶讨论

#### 一、ReactiveProperty 与普通属性的取舍

普通属性适合局部状态和不需要订阅的值。若某个值只在一个类内部使用，或变化不会驱动外部模块，就没有必要响应式化。`ReactiveProperty<T>` 的引入应基于传播需求，而不是风格统一。

判断标准可以很简单：是否需要多个订阅者，是否需要当前值自动同步，是否需要派生组合，是否需要生命周期管理。如果都不需要，普通属性更清晰。

#### 二、ReactiveProperty 与事件、Subject 的取舍

事件和 `Subject<T>` 适合瞬时通知，`ReactiveProperty<T>` 适合持续状态。按钮点击、一次性提示、任务完成、伤害飘字更像事件；当前血量、当前加载进度、当前登录状态更像属性。

如果一个通知需要新订阅者立刻拿到当前值，它更像状态；如果新订阅者不应该收到过去发生的事，它更像事件。这个判断能避免大量模型错位。

#### 三、ReactiveProperty 与 ObservableProperty 的关系

`ReactiveProperty<T>` 提供基础状态观察能力；`ObservableProperty<T>` 或自定义封装通常进一步提供旧值、新值、变更原因、校验和写入权限。二者不是替代关系，而是层级关系。

项目可以先使用 `ReactiveProperty<T>` 建立基础响应式状态，当关键状态开始需要审计、旧值语义、来源追踪和写入限制时，再向上封装。不要一开始就为所有状态引入复杂封装，也不要在复杂状态里长期裸用基础属性。

#### 四、响应式操作符要服务语义

操作符不是越多越好。`Select`、`CombineLatest`、`DistinctUntilChanged`、`Throttle` 等应服务明确语义：映射派生状态、组合条件、过滤重复、节流高频变化。过长的链式表达式会降低可读性。

关键组合流应命名为中间状态或提取方法。响应式代码的目标是让状态关系更清楚，而不是把所有逻辑压缩成一条难读的链。

#### 五、高频状态需要审查传播成本

高频状态并非绝对不能响应式化，但必须审查传播成本。每帧变化的状态如果只有本地使用，不应包装；如果需要跨模块传播，也要控制订阅数量、分配、去重和调度。UI 层常用脏标记、节流或阈值过滤减少高频刷新。

性能问题通常不在属性赋值本身，而在订阅链、布局刷新、派生计算和对象分配。使用响应式状态时，应通过 profiling 找到真实成本。

#### 六、验收标准

一个成熟的 `ReactiveProperty<T>` 使用方案，应满足以下标准：状态和事件区分清楚；关键状态只读暴露；写入入口有所有者；订阅生命周期明确；派生状态有归属；高频状态经过成本评估；调试时能找到写入来源和订阅关系；操作符链路可读可测试。

如果项目虽然大量使用 `ReactiveProperty<T>`，但谁都能写、谁都在订阅、状态和事件混用、释放靠记忆，那么说明团队只掌握了语法，没有真正掌握工程化使用方式。


#### 七、实现方案：只读暴露与受控写入的最小示例

下面的示例展示的是边界思想，而不是完整框架。关键点是内部可写、外部只读、写入通过领域方法完成。

```csharp
public sealed class PlayerState
{
    private readonly ReactiveProperty<int> _hp = new ReactiveProperty<int>(100);
    private readonly ReactiveProperty<bool> _isDead = new ReactiveProperty<bool>(false);

    public IReadOnlyReactiveProperty<int> Hp => _hp;
    public IReadOnlyReactiveProperty<bool> IsDead => _isDead;

    public void ApplyDamage(int damage)
    {
        if (damage <= 0 || _isDead.Value)
        {
            return;
        }

        _hp.Value = Math.Max(0, _hp.Value - damage);
        _isDead.Value = _hp.Value == 0;
    }
}
```

这个例子很短，但已经体现了正式项目中最重要的实践：外部不能直接写血量，死亡状态由模型内部派生，UI 只能订阅。若后续需要旧值、来源和校验结果，可以在这个边界上继续封装，而不是让外部到处直接写属性。

#### 八、反模式：用 ReactiveProperty 表示一次性动作

用 `ReactiveProperty<bool>` 表示按钮点击、弹窗播放、奖励领取完成等一次性动作，是常见误用。它会迫使开发者手动复位，或者让新订阅者收到历史动作。一次性动作更适合事件流、命令或消息。状态容器不应承担瞬时事件语义。

如果团队发现某个 `ReactiveProperty<bool>` 总是在 true 和 false 之间来回跳，只为了制造一次通知，就应该重新审视模型。它大概率不是状态，而是事件。

#### 九、反模式：订阅回调成为业务流程中心

另一个常见问题是所有逻辑都写在订阅中。A 状态变化后订阅里修改 B，B 变化后订阅里调用服务，服务返回后又修改 C。短期看像数据流，长期看是隐式流程。复杂业务流程应有显式命令、服务或状态机，不应隐藏在订阅链中。

订阅回调越轻，响应式系统越稳定。它适合刷新表现、同步简单派生状态、触发轻量协调；不适合承担事务、网络请求、跨系统写入和复杂分支。若必须做这些事，应把订阅作为入口，立即转交给明确的流程对象。

#### 十、反模式：公开可写属性以换取开发便利

公开可写 `ReactiveProperty<T>` 是很多项目早期的便利写法。它让所有模块都能快速接入状态，但也让所有模块都能修改状态。随着项目扩大，状态来源会变得不可追踪。UI 改业务状态，工具脚本改运行时状态，网络回包和本地预测互相覆盖，最终很难判断值为什么变。

真正的响应式架构不是“谁都能订阅和写入”，而是“谁都能观察，但只有所有者能写入”。这条边界如果不建立，后续所有调试工具都只能补救，而无法从根本上解决问题。

#### 十一、反模式：操作符链过长且没有命名

响应式操作符很强大，但过长链式表达式会降低可读性。尤其是多个 `CombineLatest`、`SelectMany`、`Throttle`、`Where` 混在一起时，读者很难理解最终语义。关键派生状态应命名，中间条件应拆出方法或属性。

例如 `CanSubmit`、`CanOpenBattlePanel`、`ShouldShowRedDot` 这些派生状态本身就是领域概念。把它们命名出来，比把所有条件压进按钮绑定里更有维护价值。响应式代码应让业务语义更清楚，而不是更像谜题。

#### 十二、状态调试工具应围绕三类问题设计

`ReactiveProperty<T>` 相关问题通常分三类。第一，值被谁改错了。第二，值已经变了但订阅者没响应。第三，订阅者不该存在却仍在响应。调试工具也应围绕这三类问题设计。

对第一类问题，可以记录关键状态写入来源。对第二类问题，可以显示订阅者数量和派生状态关系。对第三类问题，可以在对象销毁后收到回调时告警，或在开发版维护订阅归属信息。工具不一定复杂，但至少应让团队不用靠全文搜索来排查所有响应式问题。

#### 十三、团队规范：哪些状态应该响应式化

团队可以用一个简单清单判断状态是否应使用 `ReactiveProperty<T>`。若状态需要驱动 UI，可能被多个模块观察，需要派生组合，需要新订阅者立即获得当前值，或需要与生命周期绑定，那么它适合响应式化。若状态只是局部中间变量、纯算法缓存、一次性动作或内部临时标志，则不应默认响应式化。

这份清单能避免两个极端：一端是完全不用响应式，导致状态传播全靠手写事件；另一端是所有字段都响应式化，导致订阅链膨胀。克制使用，才是长期项目中更专业的选择。

#### 十四、验收清单：一次 ReactiveProperty 设计评审应问什么

一次状态设计评审可以问以下问题：这个值是状态还是事件？当前值对新订阅者是否有意义？谁拥有写入权？是否对外只读？是否需要旧值语义？是否有派生状态？订阅在哪里释放？是否可能在对象池或场景切换后残留？是否存在高频刷新成本？调试时如何知道谁写了这个值？

如果这些问题能回答清楚，`ReactiveProperty<T>` 的使用通常比较稳；如果答不上来，即使代码能跑，也可能在后期变成隐患。



#### 十五、与 MVVM、红点和 UI 刷新的结合方式

`ReactiveProperty<T>` 在 Unity 中最稳定的落点之一，是 ViewModel 层。ViewModel 将领域状态转换为界面可直接消费的状态，例如按钮是否可点、文本是否显示、红点是否亮起、列表是否为空。View 只订阅这些只读状态并刷新表现，不直接组合复杂业务条件。

以红点系统为例，底层可能有任务完成、背包新增、活动开启、等级限制等多个状态。如果每个 UI 节点自己订阅所有来源并判断红点，逻辑会非常分散。更合理的是在状态聚合层形成 `HasRewardRedDot`、`HasInventoryRedDot` 等派生属性，再由 UI 绑定。这样红点规则有单一来源，UI 只负责显示。

UI 刷新也类似。列表是否为空、加载中是否显示遮罩、提交按钮是否可点，都应尽量成为命名状态，而不是在 View 中临时拼条件。`ReactiveProperty<T>` 与 MVVM 的结合，本质上是把“界面规则”从场景脚本中提升为可测试的状态模型。只要这个层次建立起来，响应式属性就不再是零散工具，而是 UI 架构的一部分。


### 总结

`ReactiveProperty<T>` 的真正价值，在于为 Unity 状态驱动系统建立统一语义。它把当前值和变化通知放在同一边界中，使 UI 初始化、状态刷新、派生组合和跨模块观察更清晰。使用得当，它能降低状态传播的解释成本，让 ViewModel 和状态模型更容易维护。

但它不是所有字段的默认替代品，也不是事件总线。它适合表达持续存在的当前状态，不适合表达一次性事件；适合放在状态组织层，不适合散落在所有脚本里；适合配合只读暴露和生命周期管理，不适合公开可写实例让所有模块随意修改。

在工程实践中，团队应重点治理五件事：状态所有权、初始值语义、订阅释放、派生状态归属和调试可观测性。只要这些边界清楚，`ReactiveProperty<T>` 就能成为可靠的状态建模工具；如果这些边界缺失，它只会把原本可见的复杂度包装成更隐蔽的订阅链。

最终判断标准是：使用 `ReactiveProperty<T>` 后，状态流向是否更清楚、初始化是否更稳定、派生关系是否更可读、生命周期是否更可控。如果答案是肯定的，它就是合适的；如果只是为了响应式风格而响应式化，则应回到更简单的属性、事件或命令模型。

## 知识缺口

1. UniRx、R3 与其他响应式库在 `ReactiveProperty<T>` 初始推送、去重策略、生命周期工具和调度器方面存在差异，需要按项目实际框架确认。
2. 对象池、热更新 ViewModel 和跨场景全局状态组合下的订阅释放策略，需要结合项目 UI 框架进一步规范。
3. 高频状态响应式化的性能边界需要通过 profiling 判断，本文只给出原则性评估维度。
4. 关键状态调试面板、订阅归属图和写入来源追踪的具体实现，需要结合项目工具链设计。
