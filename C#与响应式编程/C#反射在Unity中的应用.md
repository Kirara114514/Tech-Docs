# C# 反射在 Unity 中的应用

## 摘要

反射是 Unity 工程中极具双重性的能力。它可以让框架在运行时读取类型、字段、属性、方法和特性信息，从而支撑编辑器工具、自动注册、配置绑定、序列化映射、调试面板和依赖注入等基础设施；也可能因为使用边界不清而引入性能抖动、字符串脆弱性、IL2CPP/AOT 兼容问题、代码裁剪失效和长期维护成本。反射既不是必须禁用的危险 API，也不是可以随处使用的动态捷径。它更适合作为“元数据到运行时结构”的转换工具：在低频、可验证、可缓存的阶段发现信息，再把执行路径退回到委托、接口、注册表或生成代码。

本文围绕 C# 反射在 Unity 中的正确定位展开，核心论点是：反射的工程价值不在于绕过静态类型系统，而在于把分散的类型声明转化为框架可消费的结构化信息。文章先分析 Unity 项目为什么会需要反射，再解释反射的调用成本、元数据机制、AOT 与裁剪风险；随后提出运行时反射与编辑器反射分层、统一入口、缓存委托、扫描白名单、保留策略和可观测性建设等设计原则；最后给出适用边界和替代方案。目标不是罗列 API 用法，而是建立“何时该用、如何收束、如何验证、何时替代”的判断框架。

## 正文

### 背景

#### 一、Unity 项目为什么会走向反射

Unity 项目早期通常以直接引用和手写连接为主。脚本知道自己依赖哪些组件，UI 知道自己绑定哪些字段，初始化流程知道自己要调用哪些模块。随着项目规模扩大，这种显式连接会逐渐暴露重复劳动：每新增一个配置类都要手写注册，每新增一个消息处理器都要修改路由表，每新增一个编辑器字段都要写绘制逻辑，每新增一个模块都要接入启动流程。此时，项目自然会寻找一种“根据类型声明自动完成连接”的机制。

反射正好提供了这种能力。它可以在运行时或编辑器阶段读取程序集中的类型，识别带有特性的类和方法，获取字段、属性、构造函数和方法信息，并据此构建注册表、访问器、绑定关系或工具界面。比如扫描 `[AutoRegister]` 特性建立服务注册，扫描 `[Config]` 字段生成配置映射，扫描 `[Button]` 方法生成 Inspector 按钮，扫描所有实现某接口的类型建立命令处理器列表。

这些需求的共同点是，它们依赖“类型元数据”而不是“具体业务分支”。如果不用反射，也可以通过手写注册、接口表、代码生成或配置表完成。但反射往往是最直接的第一步，因为它不需要额外构建流程，能快速把声明式信息转为运行时行为。

问题在于，反射在降低手工接线成本的同时，也削弱了编译期可见性。字段改名后字符串路径不会报编译错误，方法签名变化后扫描器可能到运行时才失败，IL2CPP 裁剪可能移除反射访问的成员，私有成员访问可能绕过架构边界。反射一旦从框架层扩散到业务层，就容易把系统变成隐式约定的集合。

因此，Unity 项目使用反射的关键不在于“会不会用 API”，而在于是否能让反射只承担适合它的职责：发现元数据、建立索引、生成访问计划，而不是在业务逻辑中随意动态调用。

#### 二、反射最适合解决的是框架层问题

反射的高价值场景通常位于框架层、工具层和诊断层。编辑器工具可以用反射扫描字段并绘制自定义面板；资源审计器可以扫描类型上的规则特性；启动框架可以发现模块入口；配置系统可以读取字段标注；测试工具可以发现验证器；调试面板可以临时展示对象状态。这些场景往往具备三个特点：调用频率低、通用性要求高、元数据价值大。

反射不适合作为普通业务逻辑的默认手段。逐帧更新、动画状态计算、批量实体循环、UI 列表刷新、战斗结算内层循环、对象池高频创建回收，这些路径更需要静态调用、缓存委托、生成代码或显式接口。反射放在这些位置时，性能风险会随对象数量和帧率放大，且排查成本高。

更重要的是，反射不应成为绕过架构边界的工具。它可以访问私有字段、动态调用方法、绕过普通依赖关系，但这些能力如果被业务层随意使用，会破坏封装。成熟项目应把反射视为基础设施能力，由少数统一入口管理，而不是让每个模块都写自己的 `GetField`、`GetMethod` 和 `Invoke`。

#### 三、编辑器反射和运行时反射是两类问题

Unity 的编辑器环境和运行时环境目标不同。编辑器反射强调开发效率、信息完整性和工具灵活性，允许较高扫描成本，也可以读取更多元数据。运行时反射强调性能、平台一致性、裁剪兼容和异常可控。把编辑器反射习惯直接搬到运行时，是许多 Unity 项目踩坑的根源。

一个更稳妥的方向是“编辑器反射前移，运行时消费结果”。例如，编辑器阶段扫描 UI 绑定特性并生成绑定代码；构建前扫描配置类并生成字段访问表；资源导入时扫描验证规则并生成索引；运行时只读取生成物或注册表。这样既保留反射的自动发现能力，又把运行时动态性降到最低。

这也是大型 Unity 项目常见的治理思路：反射不一定消失，但它的位置前移，职责收窄。它负责发现和生成，而不是在玩家运行时反复查询和调用。

### 核心原理

#### 一、反射读取的是元数据，不是普通业务状态

C# 程序集不仅包含可执行代码，也包含类型元数据。类型名称、命名空间、基类、接口、字段、属性、方法、构造函数、特性等信息都可以通过反射读取。反射 API 的本质，是让程序在运行时查询这些元数据，并在一定权限范围内执行与元数据相关的操作。

这解释了反射为什么适合做框架发现。框架层不需要提前知道所有业务类型，只要业务类型通过接口、基类、特性或命名约定暴露自身身份，框架就能在扫描阶段识别它们。反射把“编译期写在类型上的声明”转化为“运行期可操作的注册信息”。

但元数据访问不是免费的。程序集扫描需要枚举类型，成员查找需要遍历和匹配，特性读取可能创建特性对象，方法调用需要处理参数、访问检查和异常包装。若每次业务执行都重新查询元数据，系统就会不断重复本应一次完成的工作。

因此，反射的正确性能模型不是“反射能不能用”，而是“元数据发现发生在哪里，发现结果如何被缓存，执行阶段是否还依赖反射”。成熟方案通常只在初始化、编辑器构建或工具执行阶段使用反射发现，随后把结果转换为字典、委托、索引表或生成代码。

#### 二、反射慢的原因需要拆开看

“反射很慢”是一个过于粗糙的说法。反射成本由多个部分组成：程序集扫描、类型枚举、成员查找、特性实例化、动态方法调用、参数数组创建、装箱拆箱、访问检查和异常包装。不同操作成本差异很大，优化策略也不同。

一次启动阶段扫描几百个类型，可能完全可接受；每帧对上千个对象执行 `GetField`，就很危险。读取一次特性用于生成注册表没有问题；在 UI 刷新中反复读取特性则没有必要。`MethodInfo.Invoke` 的成本通常高于已缓存委托调用；但如果只在调试命令中调用一次，优化它没有意义。

性能优化的关键是把反射路径分成发现阶段和执行阶段。发现阶段允许较高成本，因为它低频且可记录；执行阶段应尽量使用缓存结果。若某个反射结果需要高频执行，应在发现阶段转为委托或生成代码。若无法转为稳定执行路径，就应重新评估该需求是否适合反射。

#### 三、字符串驱动削弱了编译期保障

反射常与字符串一起出现，例如按字段名查找成员、按类型名创建对象、按方法名调用入口。这种写法灵活，但会让编译器失去保护能力。字段重命名、方法签名变化、命名空间调整、程序集拆分，都可能绕过编译检查，直到运行时才暴露。

减少字符串脆弱性的方式有三类。第一，使用特性和接口代替裸字符串。框架扫描实现了某接口或标注了某特性的类型，而不是按名字猜测。第二，把字符串集中到注册表或生成代码中，避免散落在业务代码。第三，构建启动校验和编辑器校验，让错误尽早暴露。

反射不是不能使用字符串，而是不能让字符串成为无治理的协议。只要某个字符串决定了框架行为，它就已经是协议的一部分，应当被集中管理、验证和测试。

#### 四、IL2CPP、AOT 和代码裁剪是 Unity 反射的前置约束

Unity 发布环境常见 IL2CPP 和 AOT。AOT 意味着运行时不能像 JIT 环境一样随意生成和编译新代码；代码裁剪意味着未被静态引用的类型或成员可能在构建产物中被移除。反射访问的目标如果没有被保留，编辑器中能找到的成员，真机包中可能不存在。

普通反射查询并不必然在 IL2CPP 下失效，但动态泛型构造、私有成员访问、动态委托创建、表达式编译、未保留构造函数等路径都需要谨慎验证。特别是通过 `MakeGenericMethod` 动态调用泛型方法时，如果某些泛型实例没有被 AOT 生成，运行时可能失败。通过字符串创建类型时，如果类型被裁剪，也会失败。

因此，任何进入运行时产物的反射方案都必须设计保留策略。常见方式包括 `link.xml`、`PreserveAttribute`、显式静态引用、编辑器生成代码、注册表导出和热更新补充元数据。反射需求应能被导出为保留清单，而不是靠经验手工补。

#### 五、反射成熟方案通常会退回到委托、接口或生成代码

初级反射方案往往以 `GetMethod` 加 `Invoke` 结束；成熟方案通常只把它作为发现步骤。发现目标成员后，框架会转为 `Delegate.CreateDelegate`、表达式树访问器、预生成代码或显式接口。这样运行阶段不再承担通用反射调用成本，也能更早暴露签名错误。

例如模块入口可以在扫描阶段转为 `Action` 列表；配置字段可以在构建阶段生成 setter；消息处理器可以扫描后建立 `messageId -> handler` 映射；UI 绑定可以生成强类型绑定类。反射负责发现，委托或生成代码负责执行。这个分工是反射工业化的核心。

### 设计思路

#### 一、集中反射入口

项目应避免业务代码到处直接调用反射 API。更稳妥的做法是建立少数统一入口，例如 `TypeRegistry`、`AttributeScanner`、`ReflectionAccessorFactory`、`EditorMetadataScanner`。业务模块通过声明特性、实现接口或注册配置表达需求，由统一入口完成扫描、校验、缓存和日志。

集中入口有三个收益。第一，性能可控：所有扫描和缓存都能统一预热，避免高频路径临时查找。第二，平台可控：所有运行时反射需求都能导出保留清单。第三，可维护性更强：团队能知道项目中哪些地方依赖反射，而不是在业务代码中到处搜索字符串。

集中入口不等于所有反射都写成一个巨大工具类。更好的方式是按职责拆分：特性扫描器负责发现，访问器工厂负责生成 getter/setter，注册表负责保存结果，诊断模块负责输出可观测信息。边界越清楚，越不容易变成新的黑盒。

#### 二、使用白名单扫描程序集

程序集扫描必须有边界。全项目扫描看起来方便，但会带来启动成本不可控、第三方程序集误入、平台差异和语义不清等问题。正式项目应使用白名单：只扫描明确纳入框架协议的程序集、命名空间或类型集合。

例如模块注册只扫描 `Game.Runtime` 和 `Game.Features`，编辑器工具只扫描 `Game.EditorTools`，热更新扫描只扫描已加载的热更新程序集。白名单应写入配置或代码，并在文档中说明纳入条件。这样，当项目拆分程序集或接入插件时，反射系统不会悄悄改变行为。

扫描白名单还应配合错误策略。对于必须注册的模块，扫描失败应阻断启动；对于可选工具，扫描失败可以告警跳过；对于签名不匹配的特性方法，应直接报出清晰错误。不能把所有异常都吞掉，否则反射问题会在更远处表现为业务缺失。

#### 三、用特性设计协议，而不是随意装饰

特性是 Unity 反射系统中常见的协议入口。`[AutoRegister]`、`[ModuleEntry]`、`[BindView]`、`[ConfigField]`、`[CommandHandler]` 这类特性一旦被扫描器使用，就不再只是注释，而是框架协议。它们的目标位置、是否允许多个、参数含义、继承行为、冲突处理和执行顺序都需要设计。

例如初始化特性如果允许标在多个静态方法上，就要定义顺序；如果允许标在类上，就要定义构造方式；如果同时存在类级和方法级标注，就要定义优先级；如果签名不合法，要决定是编辑器报错还是运行时报错。特性的设计质量直接决定反射系统的稳定性。

因此，特性应尽量少而明确。不要为每个临时需求增加一个模糊特性，也不要让一个特性承担过多含义。若特性参数开始膨胀，可能说明框架协议需要拆分或升级为显式配置。

#### 四、扫描阶段完成校验，执行阶段只使用缓存

反射系统应在扫描阶段尽可能完成校验：类型是否实现接口，方法是否静态，返回值是否符合要求，参数数量是否正确，字段是否可写，构造函数是否存在，特性是否冲突，目标平台是否保留。校验失败应给出具体位置和原因。

执行阶段则只使用缓存结果。缓存可以是 `Action`、`Func<T>`、字段访问器、类型工厂、路由表或预生成代码引用。执行阶段不应再做成员名查找，也不应反复读取特性。这样能把错误前移，把运行时路径变短。

一个简化的模块入口注册示例如下：

```csharp
[AttributeUsage(AttributeTargets.Method)]
public sealed class ModuleEntryAttribute : Attribute { }

// 扫描阶段：校验 static void Method()，转为 Action 并缓存。
// 执行阶段：只遍历 Action 列表，不再调用 MethodInfo.Invoke。
```

示例的重点不是代码形式，而是阶段划分：反射只负责发现和校验，运行时只执行已缓存的稳定结构。

#### 五、为运行时反射建立保留策略

任何需要进入真机运行的反射访问，都应能回答三个问题：目标类型是否会被裁剪；目标成员是否会被保留；泛型实例是否会被 AOT 生成。若不能回答，就不应进入发布路径。

保留策略可以分层。公共协议类型通过显式接口和静态引用保留；反射访问的私有成员通过 `Preserve` 或 `link.xml` 保留；大量配置类型通过编辑器导出保留清单；泛型实例通过生成桥接代码或补充元数据保留。保留规则应与扫描规则同源，避免扫描器发现了类型，但打包保留清单没有同步。

在 CI 或构建流程中，可以增加反射验证步骤：模拟扫描目标程序集，输出需要保留的类型和成员；检查 `link.xml` 或生成代码是否覆盖；在 IL2CPP 测试包中执行关键注册和访问器构建。这样能把平台问题提前到构建阶段。

#### 六、建立最小可观测性

反射系统必须可观测。至少应记录扫描了哪些程序集、发现多少类型、注册多少入口、跳过多少候选、失败原因是什么、缓存命中率如何、是否触发降级路径。开发版可以提供调试面板显示当前注册表和访问器缓存。

可观测性最能降低维护成本。反射问题往往不是直接崩溃，而是某个模块没注册、某个字段没绑定、某条命令没路由。没有日志时只能猜测；有结构化观测时，可以直接看到扫描范围、匹配结果和失败原因。

错误信息应面向业务可读。不要只抛出底层 `TargetInvocationException`，而应说明“模块入口 Game.X.Init 签名不合法，期望 static void 且无参数”“配置字段 Player.Level 未被保留”“程序集 Game.Feature 未加入扫描白名单”。这类信息能让反射从黑盒变成可维护基础设施。

### 进阶讨论

#### 一、反射与显式注册的取舍

显式注册最稳定，反射注册最省手工。小项目或关键路径可以优先显式注册，因为它受编译器保护，行为清楚。中大型项目中，模块数量和配置类型变多后，手工注册会增加遗漏风险，此时反射或代码生成能降低重复劳动。

取舍标准是变化频率和风险等级。高风险核心模块适合显式注册或生成代码；数量多、模式一致、低频初始化的模块适合反射扫描；需要跨平台稳定执行的路径适合编辑器反射加运行时代码生成。反射不是显式注册的敌人，而是手工连接成本过高时的自动化补充。

#### 二、反射与代码生成不是对立关系

代码生成常被理解为反射的替代品，但更准确地说，它是反射规模化后的自然延伸。编辑器阶段通过反射发现类型和特性，再生成运行时代码或注册表，能同时获得自动化和稳定性。反射负责发现，生成代码负责发布环境执行。

例如 UI 绑定可以扫描字段特性生成 `ViewBinder.g.cs`；配置系统可以扫描数据类生成强类型读写器；命令系统可以扫描处理器生成路由表。这样运行时不再依赖全程序集扫描，也更适合 IL2CPP。代价是构建流程复杂、生成物需要管理，但对中大型项目通常值得。

#### 三、反射与热更新边界

热更新方案会让反射问题更复杂。主工程反射热更新程序集时，需要确认程序集加载顺序、类型名稳定性、补充元数据和裁剪保留。热更新代码反射主工程类型时，需要避免依赖私有字段和不稳定实现。跨程序集的反射协议越隐式，热更新维护成本越高。

更稳妥的做法是用接口、特性和注册表定义跨边界协议。主工程提供稳定接口和注册入口，热更新侧显式注册或通过受控扫描接入。不要用私有字段名、字符串类型名和随意方法名作为长期协议。热更新已经增加了动态性，反射应帮助收束协议，而不是继续扩大不确定性。

#### 四、反射不应掩盖架构设计不足

反射最危险的滥用，是把它当作绕过依赖设计的后门。例如为了访问某个状态而读取私有字段，为了省注册步骤而全局扫描所有类型，为了快速调用而按字符串执行任意方法。这些做法短期方便，长期会让系统边界失效。

健康的反射使用应服务架构边界：通过特性声明模块身份，通过接口约束行为，通过注册表集中管理，通过生成代码固化执行路径。若某个需求只是因为正常接口不好用而转向反射，应该先重新审视接口设计，而不是直接使用反射突破封装。

#### 五、反射方案的验收标准

一个可长期维护的 Unity 反射方案，应满足六个标准。第一，使用场景明确，主要服务框架层、工具层或低频初始化。第二，扫描范围有白名单，不做无边界全局扫描。第三，扫描、校验、缓存、执行阶段分离，热路径不做临时查找。第四，IL2CPP、AOT 和裁剪策略明确，并经过真机验证。第五，错误信息可读，扫描结果可观测。第六，存在替代方案评估，能说明为什么不用显式注册、接口、多态或代码生成。

若这些标准无法满足，反射方案即使当前能运行，也更接近原型技巧，而不是工业化能力。反射的成熟不体现在 API 使用熟练，而体现在团队能否长期控制它的边界和副作用。


#### 六、常见反模式：把反射当作临时通道长期保留

Unity 项目中反射失控往往不是因为某一次错误决策，而是因为大量临时通道被长期保留下来。最典型的反模式是“先用字符串跑通，之后再说”。例如某个界面为了快速绑定字段，直接按字段名查找组件；某个 GM 工具为了快速调用功能，直接按方法名 Invoke；某个配置系统为了省注册表，启动时全程序集扫描所有类型。这些做法在原型阶段可能有效，但如果没有后续收束，就会逐渐变成正式架构的一部分。

临时反射通道长期化会带来三个后果。第一，重构成本上升。字段名、方法名、程序集名和命名空间都可能成为隐式协议，重命名时编译器无法保护。第二，排障路径变长。业务结果异常时，需要同时检查字符串、扫描范围、特性、裁剪、缓存和执行顺序。第三，团队知识变得隐性化。新成员很难知道某个私有字段为什么不能改名，因为依赖关系并不体现在普通引用图中。

治理这类反模式的关键，是为临时反射设定退出机制。若某个反射路径只是用于验证想法，应明确标记为 EditorOnly 或 DebugOnly；若它会进入正式流程，应在评审时补齐特性协议、扫描白名单、缓存层和保留策略；若它进入高频路径，应转为委托、接口或生成代码。临时方案不是不能出现，但不能无声地变成长期基础设施。

#### 七、落地流程：从需求到发布的反射治理链路

一个反射需求进入项目时，可以按五步治理。第一步是定位阶段：判断它属于编辑器工具、运行时初始化、调试诊断还是高频业务路径。编辑器工具可以更灵活，运行时初始化需要缓存，高频路径原则上不直接使用反射。第二步是定义协议：决定用接口、基类、特性还是显式注册表达接入关系，避免裸字符串散落。

第三步是扫描与校验：限定程序集白名单，扫描候选类型，验证签名、访问权限、返回值、参数和特性冲突。第四步是执行计划生成：把可执行目标转为委托、访问器、注册表或生成代码，并记录缓存键和失效策略。第五步是发布验证：检查 IL2CPP、AOT、代码裁剪、热更新补充元数据和真机行为，并把失败信息纳入构建或启动日志。

这条链路的意义在于，它把反射从“写几行 API”变成了可评审的工程流程。只要每个反射需求都能说清楚所处阶段、协议形式、扫描范围、执行计划和发布验证方式，反射就不会轻易扩散为不可控隐患。

#### 八、与 Unity 序列化系统的关系

Unity 自身序列化系统已经提供了一套字段发现、Inspector 展示和资源持久化机制。自定义反射系统若不理解 Unity 序列化规则，很容易与引擎行为冲突。例如 Unity 默认序列化字段有可见性、类型支持、嵌套对象、`SerializeReference`、重命名迁移和编辑器刷新等规则；普通 C# 反射看到的字段集合，并不等于 Unity 实际会序列化的字段集合。

因此，涉及 Inspector、配置对象和资源数据时，反射系统应明确是读取 C# 元数据，还是模拟 Unity 序列化语义。若目标是绘制工具面板，应考虑 `SerializedObject` 与 `SerializedProperty`；若目标是生成配置访问器，应考虑字段重命名和旧资源迁移；若目标是运行时读写数据，应避免直接修改 Unity 序列化私有状态。反射可以补充 Unity 序列化能力，但不应假装自己天然等价于 Unity 序列化系统。

#### 九、反射权限边界与私有成员访问

反射能够访问非公开成员，但工程上应把这件事视为最后手段。私有字段和私有方法之所以私有，是因为它们不承诺稳定协议。框架若依赖私有成员，就会把实现细节提升为事实接口，后续重构会受到隐藏约束。尤其在 Unity 组件和第三方库中，私有成员还可能随版本升级变化，反射访问会变成脆弱依赖。

确实需要访问私有成员时，应满足更高标准：访问点集中封装，原因写入文档，失败时有明确错误，版本升级有验证测试，发布平台确认可用。若只是为了图方便，应优先调整公共接口、增加显式注册或使用友元程序集等更清晰的方式。反射访问私有成员不是能力展示，而是架构债务，只有在收益大于长期维护成本时才值得承担。


### 总结

反射在 Unity 中的正确定位，是把类型元数据转化为框架可消费的结构化信息。它适合编辑器工具、自动注册、配置绑定、序列化映射、调试诊断和低频初始化；不适合随意进入逐帧热路径，也不适合成为绕过架构边界的通用后门。

工程上，反射应遵循“发现与执行分离”的原则：编辑器或初始化阶段扫描类型、读取特性、校验签名、建立缓存；运行阶段使用委托、接口、注册表或生成代码执行。这样既能保留反射带来的自动化能力，又能降低性能、平台和维护风险。

在 Unity 发布环境中，IL2CPP、AOT 和代码裁剪必须被视为设计前提。任何运行时反射都应有保留策略、真机验证和可观测信息。编辑器成功不等于发布成功，Mono 成功不等于 IL2CPP 成功，能找到类型不等于能安全调用。

最终，反射不是一种风格选择，而是一种基础设施能力。基础设施必须有边界、有缓存、有验证、有日志、有替代方案。只要这些条件成立，反射可以显著提升 Unity 项目的工具化和框架化水平；如果这些条件缺失，反射就会把短期便利转化为长期技术债。

## 知识缺口

1. 不同 Unity 版本、Managed Stripping Level 和目标平台对反射元数据保留的具体表现需要结合项目构建配置实测。
2. HybridCLR 等热更新方案下，主工程与热更新程序集之间的反射边界、泛型补充元数据和保留策略需要按项目方案单独验证。
3. 反射缓存、委托访问器和代码生成方案在具体项目中的性能差异受调用频率、装箱情况和平台后端影响，需要通过 profiling 判断。
4. 哪些反射协议应升级为代码生成，哪些保留运行时扫描，需要结合团队构建流程、模块规模和平台范围进一步制定规范。
