# 栈详解：后进先出的受限容器与工程化应用

### 背景

栈是一种看似简单却非常基础的数据结构。它只允许在一端压入和弹出元素，遵循后进先出规则。这个限制让栈无法像数组那样随机访问，也无法像队列那样表达先来先服务，但它换来了极强的状态顺序表达能力：最近进入的上下文最先退出，最近打开的界面最先关闭，最近执行的命令最先撤销，最近遇到的左括号最先匹配。

在 Unity 项目中，栈并不只存在于算法题里。UI 面板返回、编辑器 Undo/Redo、运行时建造撤销、Transform 层级遍历、资源依赖扫描、表达式解析、剧情脚本校验、富文本标签验证、DFS 搜索和调试调用链，都可以用栈表达。栈的价值不是存储更多数据，而是强制系统按“最近状态优先处理”的方式组织逻辑。

很多栈相关 bug 也来自这个规则被破坏。空栈弹出、返回栈保存已销毁面板、撤销栈引用失效对象、递归遍历导致调用栈溢出、单调栈比较符号写反、辅助栈与主栈不同步，表面看是代码细节，深层看都是状态进入和退出关系没有被严格维护。

本文以 Unity / C# 工程为语境，系统讨论栈的核心原理、常见算法、工程设计和高级边界。目标不是重复 `Push`、`Pop` 的 API，而是说明什么时候一个问题天然适合栈，怎样把栈封装成稳定状态机，以及如何避免它在长生命周期系统中变成引用和历史状态的隐性风险。

### 核心原理

#### 一、栈的本质是受限访问带来的顺序确定性

栈只允许从栈顶插入和删除。这个限制看似减少能力，实际上增强了推理能力。只要数据进入栈，就意味着它必须在后进入的数据之后才能被处理。函数调用栈、括号匹配、页面返回和撤销系统都依赖这一点。

因此，栈适合表达嵌套、回退、最近上下文和未完成状态。若业务需要随机删除中间元素、按优先级取出元素、按时间先后处理元素，栈就不是合适结构。选择栈之前，应先确认问题是否真的具有后进先出语义。

#### 二、数组栈是默认高效实现

常见栈实现使用数组和计数器。入栈把元素写到数组末尾，出栈从末尾取出元素并减少计数。数组栈缓存友好，常数低，`Push` 在容量充足时是 `O(1)`，扩容时会发生一次 `O(N)` 拷贝，因此整体是均摊 `O(1)`。

Unity 热路径中应关注容量规划。每帧创建小栈、不断扩容、Pop 后不清理引用，都会带来额外成本。对于临时搜索和解析场景，可以复用栈并预设容量；对于引用类型元素，弹出后应释放内部引用，避免长生命周期栈持有不再需要的对象。

#### 三、链表栈并不天然更适合 Unity

链表栈每个元素由节点保存，理论上不需要数组扩容。但在 C# 和 Unity 中，每次创建节点都可能产生托管分配，且链表内存不连续，缓存局部性较差。除非有非常特殊的容量和插入需求，普通运行时逻辑通常不应优先选择链表栈。

这体现了算法理论和工程现实的差异。链表栈在教材中很清晰，但在实时项目中，分配和缓存行为往往比单次扩容更重要。基础容器选型不能只看复杂度符号，还要看内存模型。

#### 四、C# Stack<T> 是普通业务默认选择

`Stack<T>` 提供 `Push`、`Pop`、`Peek`、`TryPop`、`TryPeek` 和 `Clear` 等接口。普通单线程业务中，它通常是最稳妥选择。`TryPop` 和 `TryPeek` 适合把空栈作为正常分支处理，避免用异常控制流程。

但 `Stack<T>` 不是线程安全容器，也不承诺 `Clear` 后释放内部容量。遍历 `Stack<T>` 时，顺序通常从栈顶到栈底，这与很多人对集合遍历的直觉不同。正式代码应避免把遍历顺序当成业务输出，除非封装明确说明。

#### 五、递归本质上依赖调用栈

递归函数每进入一层，运行时都保存返回地址、局部变量和上下文；函数返回时再逐层弹出。这就是调用栈。树遍历、DFS、语法解析和依赖扫描都可以自然写成递归，但深度不可控时会导致栈溢出。

显式栈可以把递归改写为迭代。这样不仅避免调用栈限制，也更容易控制暂停、分帧和中断。Unity 中遍历深层 Transform、扫描资源依赖或处理大型图结构时，显式栈通常比递归更安全。

#### 六、括号匹配体现“最近未闭合状态”

括号匹配是栈的经典例子。遇到左括号压栈，遇到右括号时必须匹配最近的左括号。若栈为空或类型不对应，表达式非法；遍历结束后栈仍不为空，也说明有未闭合括号。

这个模型可扩展到富文本标签、剧情脚本块、表达式解析和编辑器配置校验。只要问题中存在“打开/关闭”“进入/退出”“开始/结束”的嵌套关系，栈就很可能是正确抽象。

#### 七、最小栈说明辅助状态必须同步

最小栈要求在普通栈操作之外，随时 `O(1)` 获取当前最小值。实现方式通常是维护一个辅助栈，主栈每次变化时，辅助栈同步记录当前最小值。这里的关键不是技巧，而是主状态和辅助状态必须同生命周期更新。

这对工程很有启发。Undo/Redo、UI 返回栈、解析器状态栈常常也有辅助状态，例如当前焦点、层级深度、校验上下文和统计信息。只要辅助状态和主栈不同步，系统就会出现难以解释的错乱。

#### 八、单调栈用栈维护未解决问题

单调栈不是普通 LIFO 的直接应用，而是用栈保存“尚未找到答案的元素”。当新元素出现时，它可能解决栈顶元素的问题，例如下一个更大元素、股票跨度、每日温度、柱状图最大矩形等。每个元素最多入栈一次、出栈一次，因此整体是线性复杂度。

单调栈的关键是比较符号和重复元素策略。严格大于、大于等于、严格小于、小于等于会产生不同答案。工程中若用单调栈处理地形高度、时间序列或性能采样，必须先定义相等值如何处理。

#### 九、表达式求值需要操作数栈和运算符栈

表达式解析常用栈处理优先级和括号。简单计算器可以用操作数栈保存值，用运算符栈保存等待执行的运算。遇到更低优先级运算符时，先结算栈顶高优先级运算；遇到括号则改变结算边界。

在 Unity 工具中，技能公式、配置表达式、条件判断和剧情脚本都可能使用类似思想。但正式项目不应随意手写复杂表达式语言。若表达式影响核心逻辑，应有明确语法、错误报告、测试和安全边界。

#### 十、DFS 使用栈表达深度优先

深度优先搜索可以用递归，也可以用显式栈。显式栈版本更适合控制顺序、避免调用栈溢出、加入 visited 集合和做分帧处理。图搜索、资源依赖、场景层级、行为树调试路径都可能使用 DFS。

压栈顺序会影响遍历顺序。如果希望结果与递归版本一致，通常需要反向压入子节点。这个细节经常被忽略，导致算法结果虽然覆盖相同节点，但顺序不同，进而影响编辑器展示或可重复测试。

### 设计思路

#### 一、把栈封装成领域状态，而不是裸容器

UI 返回栈不应只是 `Stack<GameObject>`；更好的设计是 `NavigationStack`，元素是面板控制器或页面记录。Undo 栈也不应只是对象引用集合，而应是命令对象集合。解析栈应保存语法上下文，而不是散乱字符串。

领域封装的好处是可以集中处理空栈、生命周期、清理、日志和调试信息。裸栈分散在各处时，每个调用者都要记住同一套规则，长期必然出错。

#### 二、UI 返回栈要处理面板生命周期

UI 返回栈的常见语义是：打开页面时入栈，返回时关闭当前页面并回到上一个页面。问题在于，页面可能被外部关闭、场景切换销毁、弹窗覆盖、系统强制重置或深链跳转替换。若栈里保存裸引用，就容易出现返回到无效页面。

稳定做法是由 UI 管理器统一维护栈，入栈元素包含页面 ID、控制器引用、恢复参数和有效性检查。页面销毁或场景切换时同步清栈或移除失效项。返回操作不能只 `Pop`，还要验证目标是否仍可恢复。

#### 三、Undo/Redo 要记录可逆命令

撤销重做通常使用两个栈。执行新命令后压入 undo 栈并清空 redo 栈；撤销时从 undo 栈弹出执行反操作，再压入 redo 栈；重做则反向移动。关键在于命令对象必须记录足够状态，能够可靠恢复。

编辑器工具中最常见的问题是命令只保存对象引用，不保存旧值；对象被删除后撤销失败；拖拽每一帧都生成命令导致历史爆炸；执行新命令后忘记清空 redo。撤销系统不是栈本身，而是栈和命令模式的组合。

#### 四、显式栈适合大型遍历和分帧处理

递归遍历深层结构简单，但不可暂停，也不易控制每帧工作量。显式栈可以把剩余工作保存在容器中，每帧处理一部分。这对大规模场景扫描、编辑器校验、资源依赖分析和运行时工具非常有用。

分帧处理时，栈不仅是数据结构，也是任务状态。它需要支持取消、进度记录、异常恢复和对象失效检查。把递归改成显式栈后，系统可控性会明显提高。

#### 五、热路径栈要复用并清引用

临时算法栈如果每帧创建，会产生分配；如果复用但不清理引用，又可能延长对象生命周期。正确做法是根据元素类型和使用频率决定策略：值类型临时栈可复用容量，引用类型栈在 Clear 或 Pop 时应确保内部引用被释放或生命周期可接受。

在 C# 标准 `Stack<T>` 中，`Clear` 会清空元素引用，但容量可能保留。容量保留对复用有利，对长期大峰值后的小对象场景可能浪费内存。核心系统应观察容量峰值。

#### 六、线程边界要明确所有权

普通 `Stack<T>` 不适合多线程同时读写。若后台线程、Job 和主线程共享栈，必须使用锁、并发集合或阶段化转移。很多时候更好的做法是每个线程维护本地栈，阶段结束后合并结果，而不是让所有线程争用同一个栈。

Unity 主线程对象也不能随意从后台线程访问。即使栈容器本身线程安全，栈中保存的对象也可能不是线程安全的。并发问题不能只看容器 API。

### 进阶讨论

#### 一、栈是状态机的影子

很多系统表面上使用栈，本质上是在维护状态机路径。UI 页面栈是导航状态机，Undo 栈是编辑操作状态机，解析栈是语法状态机，调用栈是执行状态机。若状态转移规则不清楚，栈只会把错误记录下来，而不会自动让系统正确。

因此，设计栈系统时应先画清楚状态进入、退出、取消和重置规则。尤其是 UI 和 Undo 这类用户可见系统，必须定义异常路径：强制关闭、跳转、清空历史、对象失效、场景切换时如何处理。

#### 二、栈深度是重要指标

栈深度能反映系统复杂度。调用栈过深可能导致溢出，UI 栈过深可能说明导航关系混乱，Undo 栈过大可能说明命令合并缺失，解析栈过深可能说明输入结构异常。核心栈系统应记录最大深度和异常深度告警。

很多问题不是单次 Push/Pop 错，而是深度长期不回落。比如 UI 打开页面后未正确关闭，Undo 命令持续增长，临时遍历栈因环结构无限扩张。深度观测能提前发现这些问题。

#### 三、栈和队列经常需要配合

栈表达最近优先，队列表达先进先出。很多系统同时需要二者。例如编辑器扫描可以用队列做广度遍历，用栈记录当前路径；任务系统用队列处理事件，用栈记录回退上下文；解析器用栈保存语法结构，用队列读取 Token 流。

正确结构往往不是“只用一种容器”，而是让每种容器表达一种访问规则。栈的使用边界越清晰，与其他结构协作越自然。

#### 四、单调栈不是通用优化模板

单调栈适合一类“当前元素可以解决之前未解决元素”的问题。若问题不具备这种关系，强行套单调栈会让代码难懂且错误。判断条件是：每个元素是否只需要被未来第一个满足条件的元素解决；被解决后是否再也不需要回到栈中。

如果答案需要多次回看、范围查询、动态更新或删除，单调栈可能不适合。此时线段树、树状数组、排序结构或堆可能更合适。

#### 五、撤销系统要考虑内存上限

Undo 栈保存的是历史状态。历史越完整，内存越大。关卡编辑器中，一个命令可能保存大量对象快照；运行时建造系统中，一次操作可能涉及多个实体。若不设上限，撤销栈会成为内存风险。

可行策略包括命令合并、历史上限、快照压缩、只保存差异、分组命令和定期截断。撤销系统必须在可恢复性和内存预算之间平衡。栈只是历史顺序，不能替代历史数据设计。

#### 六、UI 返回栈要区分返回和关闭

关闭当前面板不一定等于返回上一页面。弹窗关闭、确认框关闭、系统提示关闭，可能不应改变页面导航；而页面返回应恢复上一页面状态。若所有关闭都简单 `Pop`，UI 栈会很快错乱。

因此，UI 系统应区分模态弹窗栈、页面导航栈和临时覆盖层。不同栈有不同恢复规则。一个全局混合栈虽然实现简单，但长期难以维护。

#### 七、显式栈要防止环结构无限增长

树结构遍历通常不需要 visited，图结构或对象引用网络则必须防环。资源依赖、Prefab 引用、行为树跳转、状态机图都可能存在环。显式栈如果没有 visited 或深度限制，会无限增长。

判断是否需要 visited，要看数据是否保证无环。不能因为“通常是树”就忽略边界。编辑器工具尤其应该对异常结构给出诊断，而不是卡死。

#### 八、栈系统要提供调试快照

当 UI 返回错误、撤销失败或解析异常时，最有用的信息通常是当前栈内容。领域栈应提供调试快照，显示从栈顶到栈底的元素、状态、创建来源和有效性。没有快照，问题只能靠断点和猜测。

调试快照不一定在发布包开启，但开发版和编辑器工具应具备。栈的优势是顺序清楚，调试工具也应该把这种顺序展示出来。

#### 九、知道何时不用栈

如果业务要处理最早进入的元素，应该用队列；如果要处理优先级最高的元素，应该用堆；如果要随机查找，应该用哈希表；如果要保留完整顺序并频繁遍历，列表更合适。栈只适合最近状态优先。

很多容器误用来自“临时能跑”。把栈用在不符合 LIFO 的场景中，后续会不断出现从中间取元素、删除历史项、倒序遍历等需求。那说明一开始选型就错了。



#### 十、表达式解析中的栈要提供错误定位

公式、条件表达式和配置脚本一旦进入项目，就不能只返回“解析失败”。栈在解析过程中保存了尚未闭合的上下文，因此它天然可以提供错误定位：哪个括号未闭合，哪个运算符缺少操作数，哪个语法块没有结束，当前嵌套层级在哪里。

编辑器工具中，这类诊断比算法本身更重要。策划或技术美术看到的是配置文本，不是解析器内部状态。解析栈如果能在失败时输出上下文路径、行列位置和期望 Token，就能大幅降低协作成本。正式工程里的栈，不应只是内部容器，也应服务可诊断性。

#### 十一、命令合并决定 Undo 栈是否可用

撤销系统如果每次鼠标移动、每次字符输入、每次数值微调都创建一条命令，撤销体验会非常差，内存也会膨胀。命令合并的意义，是把一段连续操作视为一个逻辑动作。例如拖拽物体从 A 到 B，只需要一条命令记录起点和终点；连续输入文字可以按提交或停顿时间合并。

合并策略必须由业务定义。位置拖拽、画笔涂抹、文本输入、批量选择和参数滑动的合并边界不同。Undo 栈只保存历史顺序，真正决定可用性的，是命令粒度是否符合用户心智。

#### 十二、栈中对象应避免保存易失引用

长生命周期栈如果保存 Unity 对象引用，就要面对销毁、场景卸载、对象池复用和热重载问题。UI 返回栈保存面板对象，Undo 栈保存场景对象，工具栈保存资源对象，都可能在弹出时发现引用已经失效。

更稳妥的方式是保存稳定 ID、路径、快照或可验证句柄，并在弹出时重新解析或验证。必须保存引用时，也应提供有效性检查和失效清理。栈的顺序再正确，也无法保证对象生命周期正确。

#### 十三、固定容量栈适合底层热路径

某些热路径可以使用固定容量栈，例如小规模解析、物理临时接触处理、有限深度状态机、短路径 DFS。固定容量避免扩容和分配，但必须定义溢出行为。溢出可以返回失败、记录告警、扩展到备用容器或中止当前任务。

固定容量栈不是为了“更底层”而使用，而是为了让成本可预测。只要系统能证明最大深度，固定容量非常适合；如果深度不可控，强行固定容量会把问题变成偶发失败。

#### 十四、对象池和栈复用要小心脏状态

复用栈可以减少分配，但复用前必须清空所有状态。解析栈、遍历栈、命令临时栈若在异常路径提前返回，可能没有被清空。下一次使用时，残留元素会造成非常隐蔽的错误。

因此，临时栈复用应配合 `try/finally`、作用域对象或统一租借归还接口。对象池中的栈不仅要清空 Count，也要确保内部引用不会保留大对象。复用是优化，前提是状态边界严格。

#### 十五、栈和路径记录可以结合

在树或图遍历中，栈除了保存待处理节点，还可以保存当前路径。资源依赖扫描、Prefab 层级校验、行为树调试和剧情节点分析，都需要知道“如何走到当前节点”。路径栈能在发现错误时输出完整链路。

这比只输出错误节点更有价值。例如循环依赖不是单个资源的错误，而是一条路径的错误；UI 嵌套异常也需要完整父链。栈天然记录进入顺序，因此适合构建这类诊断信息。

#### 十六、调用栈和业务栈不要混淆

调用栈由运行时维护，业务栈由系统显式维护。递归写法依赖调用栈，简单清晰，但不利于暂停、恢复和分帧；显式栈稍复杂，却能把任务状态暴露给系统。两者不是优劣关系，而是控制权不同。

如果任务可能长时间运行、需要进度条、需要取消、需要跨帧，显式栈更合适。如果任务规模小、结构天然递归且边界可控，递归更可读。工程选择应基于控制需求，而不是一律禁用递归或一律追求显式栈。

#### 十七、单调栈适合离线分析多于运行时状态管理

单调栈常用于数组问题，例如下一个更大元素、柱状图最大矩形和接雨水。这类问题通常是一次性分析已有序列。它不太适合频繁动态插入删除的在线场景，因为单调性依赖线性扫描过程。

如果 Unity 项目中有高度图分析、性能采样后处理、时间序列统计，单调栈可能很有用；如果数据持续动态变化，可能需要树状数组、线段树或堆。理解单调栈的适用形态，比背模板更重要。

#### 十八、栈的调试显示应从栈顶开始

人排查栈问题时，通常最关心栈顶，因为下一步处理的就是它。调试面板和日志应显示栈顶、栈深、最近若干元素、元素有效性和创建来源。对于 UI 栈，还应显示页面状态；对于 Undo 栈，应显示命令名称和合并组；对于解析栈，应显示嵌套上下文。

这种显示方式能直接服务排错。若只打印 Count，开发者仍然不知道错误状态在哪里。栈的可解释性来自顺序，调试工具也应尊重这个顺序。

#### 十九、栈系统要有重置协议

场景切换、登录退出、编辑器停止播放、玩法模式重启、资源域卸载，都可能要求清空栈。不同栈的重置时机不同：UI 导航栈随界面域重置，Undo 栈随编辑目标变化重置，解析临时栈随任务结束重置，全局调试栈可能跨场景保留。

如果没有重置协议，栈会把旧上下文带进新流程。很多“返回到了上一个场景的页面”“撤销了已经不存在的对象”“解析器状态莫名残留”的问题，都来自重置边界不清。正式栈系统必须定义所属生命周期。



#### 二十、栈的测试要覆盖异常路径

栈测试不能只验证正常压入和弹出。正式项目至少要覆盖空栈 Pop、空栈 Peek、连续 Push 后顺序、Clear 后行为、重复 Clear、容量扩展、引用类型元素清理、异常路径提前退出、对象失效后弹出、跨场景重置、Undo 新命令后 redo 清空等情况。

对于单调栈，还要测试重复元素、严格比较和非严格比较；对于 UI 栈，要测试弹窗、页面、深链跳转和强制关闭；对于解析栈，要测试未闭合括号、额外右括号和嵌套错误。栈的 API 简单，不代表测试简单。真正的风险都在边界路径。

#### 二十一、栈内存要关注“历史保留”

栈常常保存历史状态，而历史状态天然容易增长。Undo 栈保存操作历史，UI 栈保存导航历史，解析错误栈保存上下文，遍历栈保存待处理节点。若没有上限和清理策略，栈会随着使用时间增长。

内存治理应按栈类型设计。Undo 栈可设置最大命令数或最大内存量；UI 栈可限制页面深度；临时遍历栈可在任务结束后归还；调试栈可在发布包关闭或截断。栈越长，越说明系统需要明确历史保留策略。

#### 二十二、UI 多栈模型更符合复杂界面

复杂 UI 往往不只有一个栈。页面导航是一条栈，模态弹窗是一条栈，提示 Toast 可能是队列，临时覆盖层可能是独立集合。把所有东西都塞进一个返回栈，会让返回键行为变得不可预测。

更好的方式是分层处理：返回键先处理模态弹窗，再处理页面导航，再处理系统退出；每一层有自己的栈或队列。这样用户心智更清楚，代码也更容易解释。栈不是 UI 管理的全部，但非常适合表达其中的嵌套层。

#### 二十三、运行时建造系统的撤销需要快照边界

运行时建造、关卡编辑、摆放家具和技能编辑等系统，经常需要撤销。这里的命令不仅要记录对象位置，还可能记录对象创建、删除、父子关系、资源引用、网格占用、导航更新和事件通知。若命令只记录 Transform，就无法完整恢复。

因此，撤销命令应以业务事务为单位。一次建造操作从开始到提交之间可能影响多个系统，Undo 栈中应保存能够回滚整个事务的记录。栈保证最近事务先撤销，事务设计保证撤销内容完整。两者缺一不可。

#### 二十四、栈可以作为解析器安全边界

解析富文本、脚本块、表达式和自定义配置时，栈深度可以作为安全限制。若输入恶意构造极深嵌套，解析器可能消耗大量内存或时间。设置最大嵌套深度，可以防止异常输入拖垮工具或运行时。

这在编辑器导入和在线文本处理中很实用。深度超过上限时，系统应给出明确错误，而不是继续压栈直到内存或调用栈出问题。栈深度不只是调试指标，也是安全边界。

#### 二十五、栈的可视化能帮助教学和协作

对于算法教学、编辑器工具和调试面板，可视化栈内容非常有帮助。括号匹配可以显示当前未闭合括号，表达式解析可以显示运算符栈和操作数栈，UI 管理器可以显示页面栈，Undo 系统可以显示命令历史。

可视化不必复杂，只要能清楚展示栈顶、栈底、元素摘要和状态有效性，就能减少大量沟通成本。数据结构进入项目后，不只是程序员内部实现，也会成为跨角色协作的解释工具。

#### 二十六、栈封装应避免泄漏可变内部状态

如果领域栈对外暴露内部 `Stack<T>`，调用者就能绕过封装随意 Push、Pop 或 Clear，破坏状态机规则。更好的方式是只暴露业务方法，例如 `OpenPage`、`GoBack`、`ExecuteCommand`、`Undo`、`BeginScope`、`EndScope`。

这种封装让栈的 LIFO 规则与业务约束绑定在一起。调用者不需要知道内部是否使用栈，也不能跳过生命周期校验。越是核心的栈系统，越不应该把容器本身暴露给外部。

### 总结

栈通过后进先出的限制，把嵌套、回退、撤销、递归和最近状态优先处理表达得非常清楚。它的 API 很简单，但正式工程中真正重要的是状态语义：谁入栈，谁出栈，何时清空，失效对象如何处理，辅助状态如何同步，栈深度是否受控。

在 Unity 项目中，栈可以支撑 UI 返回、Undo/Redo、显式 DFS、富文本校验、表达式解析、单调栈算法和编辑器工具。要让它可靠落地，必须封装领域语义、处理生命周期、预设容量、避免空栈异常、观察最大深度，并为调试提供快照。真正掌握栈，不是会调用 `Push` 和 `Pop`，而是能识别并维护“最近进入的状态必须最先退出”这一系统契约。
