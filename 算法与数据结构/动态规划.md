# 动态规划

### 背景

动态规划是算法学习中最容易被误解的主题之一。很多人把它理解成“写一个 dp 数组，再背几个转移方程”，结果遇到新问题时仍然无从下手。真正的动态规划不是模板集合，而是一种问题建模方式：当一个大问题可以被拆成相互重叠的子问题，并且子问题的结果能够在不依赖历史路径细节的情况下复用时，就可以用表格或记忆化把指数级重复计算压缩成可控复杂度。

在 Unity 和游戏开发中，动态规划并不像栈、队列、哈希表那样每天都直接出现在运行时代码里，但它仍然非常重要。背包类资源选择、技能组合优化、路径代价规划、关卡切分、字符串相似度、动画状态序列、经济系统离线分析、编辑器工具中的最优分组，都可能借用 DP 思想。即使最终不使用 DP，理解它也能帮助开发者识别“当前问题是否存在可复用的子结构”。

动态规划难的地方不在代码，而在状态定义。状态定义错了，后续转移、初始化、遍历顺序和空间优化都会跟着错。状态定义正确后，很多实现只是机械填表。本文围绕状态、无后效性、转移方程、Base Case、遍历顺序、记忆化、自底向上、空间压缩和工程边界展开，目标是把 DP 从题解套路还原成可推理的建模方法。

### 核心原理

#### 一、动态规划的核心是复用子问题结果

暴力递归之所以慢，通常不是因为递归本身，而是因为它重复计算了相同子问题。斐波那契是最简单例子：`Fib(5)` 会反复计算 `Fib(3)`、`Fib(2)`。如果把这些子问题结果保存起来，后续再遇到同一状态就直接读取，复杂度会大幅下降。

动态规划的本质就是用空间换时间。它不是让问题消失，而是把重复分支合并。只有当子问题会重复出现时，DP 才有价值。如果每个子问题只出现一次，记忆化并不会带来明显收益。

#### 二、最优子结构说明大问题可以由子问题组成

最优子结构指大问题的最优解可以由子问题的最优解推导而来。例如背包问题中，前 i 个物品在容量 c 下的最优值，可以由“不选第 i 个物品”和“选第 i 个物品”两个子问题比较得到。打家劫舍中，前 i 间房屋的最优值，可以由抢或不抢当前房屋推导。

没有最优子结构的问题，不适合直接 DP。若局部子问题的最优选择会破坏全局条件，或大问题需要保留复杂历史，状态必须扩展到能表达这些历史约束，否则转移会失真。

#### 三、重叠子问题决定是否值得存表

重叠子问题意味着不同路径会访问同一个状态。动态规划通过缓存状态结果避免重复。若问题可以拆成子问题，但子问题之间互不重叠，例如普通分治排序，DP 的意义就不大。

判断重叠子问题的一个方法，是先写暴力递归调用树。如果树中大量相同参数重复出现，说明可以记忆化。如果调用树基本不重复，优化方向可能是剪枝、分治或贪心，而不是 DP。

#### 四、状态是对子问题的充分描述

状态是 DP 的核心。一个状态必须包含求解该子问题所需的全部信息，且不包含多余历史。比如 `dp[i]` 可以表示前 i 个元素的最优值；`dp[i][c]` 可以表示前 i 个物品、容量 c 下的最优值；`dp[l][r]` 可以表示区间 `[l,r]` 的最优结果。

状态不足会导致转移错误。例如路径问题如果只记录当前位置，却不记录剩余资源或已访问集合，就可能把本不等价的情况合并。状态过多则会导致维度爆炸。好的状态定义是在正确性和复杂度之间取得平衡。

#### 五、无后效性是状态可复用的前提

无后效性指给定当前状态后，未来决策只依赖状态本身，而不依赖到达该状态的具体路径。如果两个路径到达同一个状态，但未来可选项不同，那么这个状态定义就是不充分的。

游戏问题中无后效性尤其容易被破坏。例如角色到达某格子时，如果已经拾取的钥匙不同，后续可走门就不同；如果只用坐标作为状态，就会错误合并。必须把钥匙集合、资源量或其他影响未来的因素加入状态。

#### 六、状态转移方程表达选择关系

转移方程回答“当前状态如何由更小或更早的状态推导”。它不是凭空写公式，而是对当前决策的枚举。打家劫舍的转移来自抢或不抢当前房屋；背包的转移来自选或不选当前物品；编辑距离的转移来自插入、删除、替换。

写转移时应先用自然语言描述选择，再写公式。公式只是压缩表达。若无法说清当前状态有哪些选择，转移方程通常也不会可靠。

#### 七、Base Case 是递推的地基

Base Case 是最小子问题的答案。没有正确初始化，后续状态即使转移公式正确，也会建立在错误基础上。背包中容量为 0 时价值为 0；编辑距离中空串变成长度 j 的串需要 j 次插入；区间 DP 中长度为 1 的区间通常代价为 0。

Base Case 还决定数组边界。很多 DP bug 来自下标偏移和初始化不完整。正式实现前，应单独写出最小输入、空输入和边界输入的结果。

#### 八、遍历顺序必须满足依赖关系

自底向上 DP 的填表顺序不是随意的。计算当前状态前，它依赖的前驱状态必须已经计算。线性 DP 通常从小到大；背包一维压缩时，01 背包容量要逆序，完全背包容量要顺序；区间 DP 通常按区间长度从短到长。

遍历顺序错误时，代码可能仍能运行，但语义已经变了。01 背包顺序遍历容量，会让同一物品在同一轮被重复使用，变成完全背包。理解遍历顺序，比记住模板更重要。

#### 九、记忆化和填表是同一思想的两种形态

自顶向下记忆化从目标问题出发，递归求需要的子问题，并缓存结果。它直观，适合状态空间很大但实际访问较少的问题。自底向上填表按依赖顺序计算所有必要状态，避免递归开销，适合状态空间规则且需要完整结果的场景。

二者没有绝对优劣。记忆化更接近暴力思考，适合先验证状态；填表更适合性能稳定和空间优化。很多问题可以先写记忆化，再转成迭代。

#### 十、空间优化必须建立在依赖范围清楚之上

若当前状态只依赖前一行或前几个状态，就可以用滚动数组或少量变量压缩空间。斐波那契可压到两个变量，打家劫舍可压到两个变量，背包可压到一维数组。

但空间优化会降低可读性，也更容易写错遍历顺序。工程中应先保证二维或完整表版本正确，再优化空间。若数据规模不大，保留完整表有时更利于调试和解释。

### 设计思路

#### 一、从暴力递归开始识别状态

解决 DP 问题时，可以先写暴力递归，不急着优化。递归函数参数往往就是状态候选，返回值就是状态含义。然后观察哪些参数组合重复出现，哪些历史信息会影响未来，哪些可以被压缩。

这种方法比直接套模板更可靠。DP 最难的是建模，暴力递归能暴露问题结构。即使最终不用递归实现，递归思考仍然有价值。

#### 二、用一句话定义 dp 含义

每个 DP 都应先写清楚 `dp[i]` 或 `dp[i][j]` 的含义。含义必须包含范围、约束和目标。例如“前 i 个物品、容量不超过 c 时的最大价值”，而不是模糊写成“背包最大值”。含义越精确，转移越容易推导。

如果一句话说不清状态含义，就不要继续写代码。很多 DP 错误都是从模糊状态开始的。

#### 三、把选择枚举转化为转移

定义状态后，列出当前状态最后一步可能发生什么。线性 DP 常看“最后一个元素选不选”；区间 DP 常看“最后一次合并在哪里”；序列 DP 常看“以哪个位置结尾”；背包 DP 常看“当前物品选不选”。

选择枚举完整，转移方程才完整。漏掉一种选择，结果会偏小或偏大；重复计算一种选择，复杂度会增加。正式文档和代码注释应解释选择来源，而不是只写公式。

#### 四、用小样例手推表格

DP 非常适合手推。用小输入画出表格，检查初始化、遍历顺序和转移结果。背包可以画物品和容量表，编辑距离可以画两个字符串的矩阵，区间 DP 可以画区间长度。

手推表格能发现许多下标错误。尤其是二维 DP，一旦看清第一行、第一列和填表方向，代码会稳定很多。

#### 五、根据问题类型选择典型模型

常见 DP 模型包括线性 DP、背包 DP、区间 DP、树形 DP、状态压缩 DP、数位 DP、序列 DP 和字符串 DP。模型不是死模板，而是状态组织方式。识别模型能帮助快速找到状态维度和遍历顺序。

例如“前 i 个元素”通常是线性 DP；“容量限制”通常是背包；“区间合并”通常是区间 DP；“子集选择”可能是状态压缩；“树上选择”可能是树形 DP。模型识别是经验积累的结果。

#### 六、工程中优先限制状态规模

DP 容易出现状态爆炸。一个状态维度多乘一个参数，空间和时间都会成倍增长。工程中应先估算状态数量和转移数量。若状态规模过大，要考虑剪枝、分层、近似、贪心、启发式或离线预计算。

游戏运行时尤其不能无节制 DP。很多优化问题适合编辑器或构建阶段处理，而不是每帧运行。动态规划是强工具，但要放在正确阶段。

### 进阶讨论

#### 一、DP 和贪心的区别在于是否能安全丢弃历史

贪心每一步选择局部最优，并假设不会影响全局最优。DP 保留多个子问题结果，在必要时比较不同选择。若问题满足贪心选择性质，贪心更简单；若局部选择会影响后续，DP 更安全。

例如零钱兑换中，如果硬币系统不是规范币制，贪心可能失败，DP 更可靠。判断能否贪心，需要证明局部选择不会破坏全局，而不是凭直觉。

#### 二、DP 和搜索的边界并不绝对

记忆化搜索本质上就是搜索加缓存。许多复杂 DP 问题可以先写 DFS，再加 memo。状态空间不规则时，记忆化比数组填表自然；状态空间规则时，自底向上更高效。

Unity 工具中，如果状态只会访问很小一部分，记忆化搜索可能比完整表更合适。比如某些配置组合优化，只需要从少量目标状态反推，不必填满整个空间。

#### 三、状态压缩适合小规模集合

状态压缩 DP 用 bitmask 表示集合，常见于旅行商、钥匙收集、子集选择。它能把“已选择哪些元素”放入状态，但复杂度通常与 `2^N` 相关，只适合 N 较小的场景。

游戏中如果要处理少量开关、钥匙、技能组合或小规模队伍搭配，状态压缩可能有用。但一旦元素数量上升，就必须换模型或做剪枝。状态压缩不是万能，它只是把集合历史压成整数。

#### 四、区间 DP 关注最后一次分割

区间 DP 常用于合并石子、矩阵链乘、回文区间和某些解析问题。它的状态通常是 `dp[l][r]`，转移枚举区间内的分割点。遍历顺序一般按区间长度从短到长。

区间 DP 的难点是理解“最后一步”。很多区间问题不是从左到右做决策，而是问整个区间最后由哪两个子区间合并而来。只要抓住最后一次分割，转移就清晰很多。

#### 五、树形 DP 依赖父子关系

树形 DP 在树结构上自底向上或自顶向下传递状态。典型问题包括树上选择、最大独立集、路径统计和层级资源分配。Unity 中组织层级、技能树、行为树和场景树都可能出现类似问题。

树形 DP 要特别注意父节点和子节点的状态关系。某些问题需要记录“选父”或“不选父”，某些问题需要 rerooting。树结构如果可能有环，就必须先确认它真的是树，否则 DP 假设会被破坏。

#### 六、DP 的可解释性很重要

DP 结果往往只是一个数值，但工程中经常需要解释选择路径。例如背包选择了哪些物品，编辑距离对应哪些操作，关卡切分为什么得到某个方案。此时 DP 表需要额外保存 parent 或 decision 信息。

保存决策会增加空间，但能显著提升调试和工具价值。编辑器优化工具如果只输出分数，不输出方案路径，就很难被内容团队信任。

#### 七、浮点 DP 要谨慎处理比较

某些工程问题会用浮点代价做 DP，例如路径评分、布局优化、动画匹配。浮点比较存在精度误差，`min` 和 `max` 的结果可能因细微差异产生不稳定选择。若结果需要可复现，应使用定点数、量化代价或稳定 tie-breaker。

这对回放、联网和构建工具很重要。算法看似正确，数值不稳定也会导致结果难以复现。

#### 八、DP 不应替代业务约束建模

有些问题看起来可以用 DP 优化，但真正困难的是业务目标不清。例如“最优技能组合”如果没有明确评分函数，“最佳资源加载顺序”如果没有明确代价模型，DP 无法给出有意义答案。算法只能优化已定义目标。

因此，在工程中使用 DP 前，先定义目标函数、约束和可接受近似。没有业务模型的 DP，只会把模糊需求变成复杂代码。



#### 九、背包问题的本质是资源约束下的选择

背包模型并不只存在于算法题。它表达的是在有限资源约束下，从一组候选中选择若干项，使收益最大或成本最小。容量可以是重量、时间、内存、预算、能量、行动点或任意可离散化资源。01 背包表示每项最多选一次，完全背包表示每项可以重复选择，多重背包表示每项数量有限。

工程中使用背包思想时，首先要确认资源是否可以离散化。如果容量是连续浮点值，直接 DP 可能不合适，需要量化或换模型。其次要确认容量范围是否可承受。背包复杂度通常与容量大小相关，容量过大时需要优化、近似或改用其他算法。

#### 十、最长子序列类问题强调“以谁结尾”

最长递增子序列、最长公共子序列、最长回文子序列等问题，都要求开发者区分子串和子序列。子串连续，子序列不连续。许多序列 DP 的状态含义与“以 i 结尾”或“前 i 个元素”有关。

例如最长递增子序列的朴素 DP 可以定义 `dp[i]` 为以第 i 个元素结尾的最长递增子序列长度。这个定义很关键，因为它让状态能比较所有前驱。若只定义“前 i 个元素中的 LIS”，转移会更难直接表达最后一个元素的关系。

#### 十一、字符串 DP 要重视边界行列

编辑距离、最长公共子序列、通配符匹配、正则简化匹配都属于常见字符串 DP。它们通常使用二维表，第一维表示字符串 A 的前 i 个字符，第二维表示字符串 B 的前 j 个字符。第一行和第一列对应空串，是最容易写错的部分。

这类问题的工程价值在于模糊搜索、文本差异、配置比较和工具辅助。运行时使用时要非常谨慎，因为二维表成本随两个字符串长度乘积增长。大规模候选搜索应先做粗筛，再对少量候选执行 DP。

#### 十二、路径规划中的 DP 要区分有环和无环

网格最短路径、最小路径和、三角形路径等问题常用 DP，因为状态依赖方向明确，不会回到未来状态。但一般图上最短路若存在环，就不能简单按二维表填充，而需要 Dijkstra、Bellman-Ford 或搜索算法。

这说明 DP 要求依赖关系可排序。若状态之间存在循环依赖，就需要额外迭代、拓扑排序或换算法。游戏地图中如果只能向右向下移动，DP 很自然；如果可以任意方向移动，普通 DP 就不再适用。

#### 十三、状态压缩 DP 要关注位运算语义

当状态包含“某些元素是否已被选择”时，可以用 bitmask 表示集合。第 k 位表示第 k 个元素是否存在。这样可以把集合状态压成整数，便于做数组索引和快速转移。

但状态压缩的可读性较差，且复杂度通常是 `O(2^N)` 或更高。正式项目中，如果使用 bitmask DP，应封装位操作，写清楚每一位的业务含义，并限制 N 的范围。否则后续维护者很难判断某个整数状态代表什么。

#### 十四、树形 DP 要先确认树的根和方向

树形 DP 通常需要选择一个根，从叶子向根汇总，或从根向叶子传递。根的选择会影响实现方式，虽然不一定影响最终答案。父子关系、是否允许选相邻节点、是否需要记录父状态，都会决定状态维度。

Unity 中技能树、科技树、行为树和场景层级都可能借用树形 DP。需要注意的是，Unity Transform 层级是树，但资源引用图未必是树。只要存在共享引用或循环，就不能直接套树形 DP。

#### 十五、DP 表可以保存答案路径

很多 DP 教程只返回最优值，但工程中经常需要知道最优方案。例如背包要知道选了哪些资源，编辑距离要知道具体修改操作，关卡切分要知道分割点，任务调度要知道选择顺序。此时需要在更新 dp 时保存决策来源。

保存路径可以用 parent 表、decision 表或回溯规则。它会增加空间，但能显著提升可解释性。编辑器工具和策划工具尤其需要方案路径，因为使用者不能只接受一个分数。

#### 十六、DP 调试应可视化状态表

DP 错误通常来自状态含义、初始化或遍历顺序。可视化表格能快速暴露问题。二维 DP 可以输出矩阵，背包可以输出容量行，区间 DP 可以输出按长度填充的上三角，状态压缩 DP 可以输出 mask 和含义。

在工具链中，若 DP 用于自动配置或优化，建议提供调试模式显示状态变化和决策来源。这样算法结果不再是黑箱，内容团队也更容易理解为什么系统选择某个方案。

#### 十七、DP 适合离线优化多于实时高频

许多游戏问题可以用 DP 得到更优解，但不一定应该在运行时使用。比如资源打包分组、关卡切块、技能树推荐、经济表校验、文本差异、构建顺序优化，都可以在编辑器或构建阶段完成。运行时只消费结果。

这类离线 DP 非常有价值，因为它不受每帧预算限制，可以换取更好的内容质量和更强工具能力。把 DP 放到离线阶段，是工程化使用 DP 的常见方式。

#### 十八、实时 DP 要有硬预算

若 DP 必须运行时执行，就要有硬预算：最大状态数、最大迭代次数、最大内存、最大时间片和失败策略。没有预算的 DP 在小样例中表现很好，在真实数据中可能突然爆炸。

实时系统可以使用分帧计算、缓存结果、状态剪枝、近似算法或提前终止。只要 DP 进入玩家可感知流程，就必须按性能系统治理，而不是按题解代码直接运行。

#### 十九、DP 与缓存系统要区分

有些代码给函数加了缓存，就称为动态规划。严格说，记忆化是 DP 的一种实现方式，但前提仍是状态具有可复用子问题结构。如果缓存的是随机请求结果，可能只是普通缓存，而不是 DP。

这一区分很重要。普通缓存关注命中率、淘汰和生命周期；DP 关注状态依赖、转移和无后效性。不要把所有“存一下结果”的代码都归为 DP，否则会混淆设计目标。

#### 二十、DP 需要和业务代价模型绑定

动态规划优化的是明确目标函数。如果目标函数不准确，DP 会非常认真地给出错误方向的最优解。比如自动装备推荐，如果评分函数只看攻击力，就会忽略生存、套装和技能循环；资源加载顺序如果只看距离，就会忽略遮挡和即将使用的剧情资源。

因此，使用 DP 前要先确认代价模型是否代表真实业务价值。算法只能在模型内最优，不能替代业务判断。模型越复杂，越需要可解释输出和人工校验。



#### 二十一、不是所有“最优”问题都适合 DP

看到“最大”“最小”“最优”并不自动意味着动态规划。有些问题有贪心性质，有些问题需要图搜索，有些问题状态空间过大，有些问题目标函数会随外部环境变化。DP 适合的是状态可离散、依赖可排序、子问题可复用的问题。

如果状态必须包含大量历史，或者未来决策依赖完整路径，DP 可能会退化成指数级状态。此时更现实的方案可能是启发式搜索、局部优化、模拟退火、整数规划工具或人工规则。算法选型要从问题结构出发，而不是从关键词出发。

#### 二十二、复杂度估算应在编码前完成

写 DP 前应估算状态数和每个状态的转移数。总时间通常约等于状态数乘以转移数，空间约等于状态表大小。若 `dp[i][j][k]` 的三个维度分别是 1000、1000、100，就已经不可接受。

复杂度估算能提前阻止错误方案。很多 DP 在小样例中正确，在真实数据中无法运行，不是实现问题，而是状态维度从一开始就超预算。正式工程中，复杂度估算应写进设计说明。

#### 二十三、空间压缩会降低可解释性

滚动数组和一维压缩能减少空间，但会让状态表不可见，也更容易写错遍历顺序。对面试或竞赛，空间压缩常被追求；对工程工具，完整表有时更好，因为它能支持调试、回溯和解释。

是否压缩空间，应根据数据规模和可解释性需求决定。若状态表并不大，保留完整表可以降低维护成本。若状态表巨大，压缩是必要优化，但应配合注释和测试保护遍历顺序。

#### 二十四、DP 的测试要覆盖边界和路径

DP 测试不能只测一个正常样例。应覆盖空输入、单元素、最大容量为 0、不可达状态、重复元素、极端代价、并列最优、多种路径得到同一状态、需要回溯方案的情况。背包要测容量边界，字符串 DP 要测空串，区间 DP 要测长度为 1 和 2 的区间。

如果 DP 输出方案，还要验证方案与最优值一致。只测分数不测路径，容易出现值正确但回溯错误的情况。工具型 DP 尤其需要路径测试。

#### 二十五、DP 结果要能解释失败状态

很多 DP 问题存在不可达状态。例如某金额无法由硬币组成，某任务组合不满足约束，某路径无法到达。系统不应只返回默认值，而要区分“最优值为 0”和“状态不可达”。常见做法是使用无穷大、负无穷、nullable 或显式状态枚举。

不可达状态处理不清，会导致工程 bug。比如把不可达当成 0，系统可能认为某个方案免费可行；把未初始化当成有效值，也会污染后续转移。DP 表中的哨兵值必须有明确语义。

#### 二十六、DP 可以用于内容校验而不只是求最优

动态规划还可以判断可行性。例如某资源组合是否能在预算内满足需求，某剧情条件是否存在合法路径，某文本是否能被规则解析，某技能释放序列是否能达到目标状态。可行性 DP 不一定求最大值或最小值，而是判断状态能否到达。

这类应用在编辑器工具中很有用。它能提前告诉内容团队某个配置无解，而不是等运行时暴露。DP 的价值不只在优化，也在证明可行或不可行。

#### 二十七、DP 与缓存复用要考虑版本

如果 DP 结果被缓存，例如关卡分析结果、资源分组结果、推荐方案或路径代价表，就必须绑定输入版本。配置变化、资源变化、规则变化后，旧 DP 表可能失效。没有版本校验的缓存，会让系统使用过期最优解。

因此，离线 DP 工具应记录输入哈希、规则版本、生成时间和参数。运行时读取结果时也应校验版本。动态规划结果一旦资产化，就进入资源管理范畴。



#### 二十八、DP 文档应保留状态定义而不是只保留代码

动态规划代码如果没有状态定义、转移解释和遍历顺序说明，维护成本会很高。后续开发者很难判断某个循环为什么正序、某个初始化为什么是无穷大、某个维度为什么要多一格。因此，正式代码旁边应至少保留状态含义、转移来源和边界条件。

这种文档化不是冗余，而是 DP 可维护性的核心。DP 的复杂性主要在建模层，不在语法层。只看代码往往看不出模型假设。

### 总结

动态规划的本质，是在最优子结构和重叠子问题存在时，通过状态缓存复用子问题结果。它的难点不在写数组，而在定义能完整描述子问题且满足无后效性的状态，再根据选择关系推导转移方程、Base Case 和遍历顺序。

在正式工程中，DP 应被视为建模工具而不是题解模板。它适合离线优化、编辑器工具、有限规模组合问题、字符串差异、背包选择和某些规划问题；不适合目标不清、状态爆炸或实时预算无法承受的场景。真正掌握 DP，是能够解释为什么某个状态足够、为什么转移完整、为什么遍历顺序正确，以及为什么这个问题值得用 DP 而不是贪心、搜索或简单模拟。
