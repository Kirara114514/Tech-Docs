# 树与二叉树

### 背景

树是表达层级关系的核心数据结构。数组和链表适合表达线性顺序，栈和队列适合表达受限访问顺序，而树适合表达“一个根向下分化出多个子结构”的关系。文件目录、组织架构、UI 层级、场景对象层级、行为树、语法树、资源依赖的局部层级，都可以用树来建模。只要一个对象天然拥有父子关系，树就是首先需要考虑的抽象。

树与图很接近，但树比一般图更受约束。树通常只有一个根，除根外每个节点只有一个父节点，任意节点到根的路径唯一，不存在环。正因为约束更强，树上的许多问题可以用递归自然表达，也能得到更清晰的不变量。二叉树进一步限制每个节点最多只有左右两个子节点，使许多算法可以围绕“当前节点、左子树、右子树”三部分展开。

在 Unity 项目中，树并不是纯算法概念。Transform 层级本身就是树；UI 元素嵌套也是树；行为树把 AI 决策拆成选择、顺序、条件和动作节点；四叉树和八叉树把空间递归划分；资源或配置系统有时也会形成近似树状的组织结构。理解树结构，可以帮助开发者看清递归更新、局部变换、层级传播和遍历顺序背后的共同规律。

树结构的难点在于，局部关系简单，整体行为却可能复杂。每个节点只知道父节点和子节点，但一次遍历会决定整棵树的访问顺序；一次递归会把局部返回值逐层组合；一次删除可能影响整个子树；一次层级移动可能改变坐标、生命周期、渲染顺序或事件传播。树的工程风险往往来自“局部操作影响整片子树”。

本文从树与二叉树的核心原理出发，重点讨论层级建模、二叉树遍历、二叉搜索树、平衡与退化、递归和迭代的权衡，以及游戏工程中使用树结构时的边界。目标不是堆叠题解，而是建立判断能力：何时用树表达层级，如何选择遍历顺序，如何识别递归不变量，如何避免树结构在运行时退化为性能或维护问题。

### 核心原理

树由节点和边组成。节点保存数据，边表达父子关系。根节点没有父节点，叶子节点没有子节点。节点的深度是它到根的边数，节点的高度是它到最远叶子的边数，树的高度通常指根节点高度。深度强调从上往下的位置，高度强调从下往上的规模。许多树算法都在这两个方向之间转换。

树的第一个重要性质是路径唯一性。在树中，从根到任意节点只有一条路径。这让递归天然成立：处理一个节点时，只需要考虑它的子树，而不必担心从另一条路径再次回到同一节点。一般图遍历需要 visited 集合避免环，树遍历通常不需要，前提是结构确实是树而不是共享节点或带环的对象网络。

第二个重要性质是子问题相似。任意节点都可以看作一棵子树的根，因此“处理整棵树”的逻辑通常可以写成“处理当前节点，并以同样方式处理每个子节点”。这就是树递归的基础。递归函数的关键不在语法，而在定义清楚返回值代表什么，以及当前节点如何用子树结果构造自己的结果。

二叉树是每个节点最多有两个子节点的树，通常称为左子节点和右子节点。左右并不只是数量限制，它还引入了顺序语义：左和右的位置不同，遍历顺序也不同。许多算法依赖这种顺序，例如二叉搜索树要求左子树所有值小于当前节点，右子树所有值大于当前节点。

满二叉树、完全二叉树和平衡二叉树容易混淆。满二叉树通常强调每个非叶节点都有两个子节点；完全二叉树强调除最后一层外都填满，最后一层从左到右连续填充，这使它适合用数组表示，也是堆结构的基础；平衡二叉树强调左右子树高度差受控，目的是避免操作复杂度退化。它们关注的不是同一件事：满关注形态，完全关注存储布局，平衡关注性能边界。

遍历是树算法的基本操作。前序遍历按“根、左、右”访问，适合先处理父节点再处理子节点，例如复制树、序列化结构、从上向下传播状态。中序遍历按“左、根、右”访问，对普通二叉树只是特定顺序，但对二叉搜索树具有重要意义：它会产生升序序列。后序遍历按“左、右、根”访问，适合先处理子节点再处理父节点，例如释放资源、计算子树规模、删除层级对象。

层序遍历是广度优先遍历。它用队列逐层访问节点，适合按深度处理层级关系，例如 UI 层级扫描、树的最小深度、按层展示、逐层扩散。深度优先遍历关注一条分支走到底，广度优先遍历关注同一层一起处理。选择遍历方式，本质上是选择信息传播方向。

二叉搜索树是一种带顺序约束的二叉树。对任意节点，左子树所有节点值小于该节点，右子树所有节点值大于该节点，且左右子树本身也必须满足同样性质。这个递归约束使查找可以像二分一样逐步缩小范围。理想平衡情况下，查找、插入、删除接近 O(log n)；若树退化成链表，则变成 O(n)。

验证二叉搜索树不能只检查“左孩子小于根、右孩子大于根”。因为约束作用于整棵子树，而不只是直接孩子。正确方式是递归传递上下界，或利用中序遍历必须严格递增这一性质。这个例子说明树问题常常需要维护跨层不变量，不能只看局部父子关系。

平衡是树结构性能的关键。二叉搜索树如果插入有序数据，会不断向一侧增长，最终退化成链表。AVL 树、红黑树等平衡树通过旋转和颜色或高度约束维持近似平衡。工程中通常不手写这些结构，而使用标准库的有序集合或字典实现；但理解平衡的原因，有助于判断为什么某些树操作能保证对数复杂度。

递归和迭代是树遍历的两种实现方式。递归代码简洁，直接表达子树关系，但深树可能导致调用栈溢出，且递归开销在热路径中可能不可忽略。迭代通常用显式栈或队列模拟递归，代码更长，但能更好地控制内存、暂停恢复和分帧执行。工程中选择哪种方式，要看树深度、调用频率和可维护性。

树的修改操作比遍历更容易出错。插入节点不仅要把子节点挂到父节点上，还要维护父指针、深度缓存、子树大小、脏标记和事件订阅。删除节点也不只是从父节点列表移除，它可能意味着释放整棵子树、迁移子节点、断开外部引用或触发资源卸载。树结构越靠近运行时对象生命周期，这些副作用就越需要显式设计。

树的空间复杂度也与形态有关。递归 DFS 的额外空间是 O(h)，h 是树高；平衡树中 h 约为 log n，退化树中 h 可达 n。BFS 的空间取决于最宽层，最坏可达 O(n)。因此不能只说“遍历树空间 O(log n)”或“O(n)”，必须说明树形态和遍历方式。

树的时间复杂度同样依赖形态。遍历任意树通常需要访问每个节点一次，因此是 O(n)；但查找、插入和删除是否能达到 O(log n)，取决于路径长度是否受控。树不是天然高效，只有在结构约束与操作目标匹配时才高效。对树的判断也应始终同时包含语义和规模两条线：语义决定能否用树，规模决定这棵树能否长期运行。

### 设计思路

设计树结构时，首先要确认层级关系是否真实存在。树要求一个节点只有一个父节点，如果一个对象需要被多个父节点共享，结构就已经接近图或 DAG。资源引用、技能依赖、任务前置条件常常看起来像树，但实际可能存在共享依赖。强行用树表示共享关系，会造成重复节点、重复计算或删除语义混乱。

其次要确定节点数据和边语义。节点保存的是纯数据、场景对象、行为逻辑、资源引用，还是运行时状态？父子边表示空间包含、生命周期归属、执行顺序、逻辑依赖，还是显示层级？同样是树，Transform 层级与行为树的边语义完全不同。边语义不清晰，遍历顺序就无法正确解释。

遍历顺序应由业务语义决定。需要父状态先下发时，用前序；需要先收集子节点结果再汇总时，用后序；需要按深度逐层处理时，用层序；需要从有序二叉搜索树导出升序结果时，用中序。不要把遍历当成固定模板，遍历顺序就是业务因果顺序。

短示例可以说明后序的汇总语义：

```text
function compute_size(node):
    if node is null:
        return 0
    left_size = compute_size(node.left)
    right_size = compute_size(node.right)
    return left_size + right_size + 1
```

这个函数的返回值定义非常清楚：返回以当前节点为根的子树节点数量。当前节点的结果依赖左右子树结果，因此必须后序。很多树递归都可以用同样方式设计：先定义返回值，再决定当前节点如何组合子树。

如果树可能很深，应避免无控制递归。Unity 场景层级、程序生成内容、用户导入文件目录都有可能形成深链。递归遍历在正常层级下清晰，但在不受控输入上可能栈溢出。工具链可以用递归简化实现，运行时核心逻辑则应考虑迭代、深度限制或分帧遍历。

对子树操作要明确生命周期。删除一个节点是否删除全部子节点？移动一个节点是否继承变换？禁用父节点是否禁用子节点？行为树中的节点失败是否中断后续兄弟节点？这些问题不是数据结构本身能回答的，必须由系统语义定义。树结构只是表达层级，操作语义需要额外规则。

二叉搜索树的设计要先确认是否真的需要自己维护。若只是键值查找，哈希表通常更快；若需要有序遍历、范围查询、前驱后继，平衡搜索树才有价值。普通 BST 作为学习结构很重要，但工程中裸 BST 容易退化，除非输入顺序受控或能接受最坏 O(n)。

在需要层级空间分区时，应区分二叉树、四叉树、八叉树和 BVH。二叉树适合二分决策或有序键；四叉树适合二维空间递归划分；八叉树适合三维空间；BVH 适合包围体层级。它们都是树，但划分规则、更新成本和查询模式不同。选择结构前应先看空间维度和查询类型。

树结构的调试应可视化。只靠日志很难发现父子关系错误、重复挂载、循环引用、深度异常或遍历顺序错误。工程中应能显示节点 ID、父节点、深度、子节点数量、子树大小和关键状态。行为树、UI 树、场景树尤其需要可视化，否则调试会非常低效。

如果树会频繁修改，需要维护辅助信息。子树大小、高度、脏标记、包围盒、缓存结果、版本号都可以减少重复遍历，但它们会引入一致性问题。每次插入、删除、移动节点时，都必须更新相关缓存或标记祖先失效。缓存树信息的难点不在计算，而在失效传播。

只读树和可变树的接口也应分开。只读树可以暴露遍历器、查询函数和路径定位；可变树则需要插入、删除、移动、替换、清空子树等操作，并保证每个操作后结构仍然合法。如果一个系统允许外部随意修改子节点列表，就很难维护父指针和缓存一致性。更稳妥的方式是通过受控 API 修改树，让不变量集中在一个模块中维护。

树与对象引用结合时，要防止隐式环。理论上的树没有环，但代码对象可能因为父指针、事件订阅、共享引用或外部列表形成环。遍历时若沿错误引用方向走，可能进入循环。工程实现中，应清楚区分“树边”和“辅助引用”，并在调试工具中检测非法结构。

### 进阶讨论

树递归的关键是局部不变量。判断一棵树是否平衡，需要每个节点知道左右子树高度，并在发现不平衡时提前返回。判断是否为 BST，需要每个节点知道自己允许的上下界。求最近公共祖先，需要每个节点返回“当前子树是否包含目标以及可能的祖先”。这些问题表面不同，本质都是定义好子树返回值。

最近公共祖先体现了树路径唯一性的价值。如果两个目标分别出现在某节点的左右子树中，该节点就是最近公共祖先；如果都在同一侧，则答案向那一侧上浮。这个逻辑在一般图中会复杂得多，因为路径不唯一；在树中，唯一父路径让“分叉点”成为清晰概念。

行为树与算法二叉树有相同的递归形态，但语义不同。行为树节点通常返回成功、失败或运行中，组合节点根据子节点返回状态决定是否继续执行。它不是为了查找或排序，而是为了组织决策流。理解后序、前序和短路执行，可以帮助设计更可控的 AI 行为树。

Transform 树的性能问题常常来自层级传播。父节点变换变化后，子节点世界矩阵可能需要更新；启用禁用父对象会影响子对象；查找子节点可能需要遍历层级。深层级和频繁重挂载会带来隐藏成本。树结构在编辑器中直观，但运行时不一定便宜。

树结构与内存布局之间存在张力。指针式树容易表达动态结构，但节点分散在内存中，缓存局部性差。数组式树适合完全二叉树，例如堆，父子索引可以通过公式计算，缓存友好且无额外指针。选择表示方式时，要看树是否接近完全、是否频繁插入删除、是否需要按层访问。

序列化树需要保留结构信息。前序序列如果不记录空节点，可能无法唯一还原二叉树；前序加中序在值唯一时可以重建树；层序加空位也可以表达结构。工程中序列化场景树、行为树或配置树时，应明确保存节点类型、子节点顺序、空位或子节点数量，否则反序列化会丢失结构。

树的“高度”是许多性能问题的隐含变量。平衡树高度低，递归栈浅，查找路径短；退化树高度接近节点数，操作退化。对动态数据结构，应持续关注高度或深度分布。对于场景层级，也应避免无意义的极深嵌套，因为它会放大遍历、变换传播和调试成本。

多叉树比二叉树更贴近很多工程场景。文件目录、UI 层级和场景树通常每个节点有任意数量子节点。二叉树算法不能机械套到多叉树上，但递归思想可以迁移：把“左子树、右子树”改成“所有子节点集合”。对于多叉树，子节点顺序是否有意义，是一个必须明确的设计点。

树与 DAG 的边界在资源系统中很常见。一个材质可以被多个对象引用，一个贴图可以被多个材质引用，一个配置节点可以被多个逻辑模块依赖。若结构允许共享子节点，它就不再是严格树。此时删除、引用计数、遍历去重和循环检测都需要图的思维，而不能只用树递归。

树算法测试应覆盖形态差异。空树、单节点、满树、完全树、左斜树、右斜树、深链、重复值、非法 BST、极端高度、非平衡结构都应测试。只用漂亮的平衡树测试，会掩盖栈溢出、退化复杂度、边界判断和上下界传递错误。

工程中还要警惕“树越抽象越好”的误区。通用 TreeNode 可以快速建模，但不同系统对节点生命周期、子节点顺序、查询方式和缓存字段的需求不同。行为树节点、UI 节点、空间树节点和表达式树节点不一定应该共用同一套基类。共享抽象应来自真实重复，而不是名称相同。

树结构的价值在于把层级关系显式化。它让父子传播、递归组合、局部替换、子树缓存和分层调试变得可行。但树也会引入深度、退化、级联更新和所有权问题。成熟的树设计不是只会遍历，而是知道每条边代表什么，每个节点拥有什么，每次操作会影响哪一片子树。

树还常被用来表达优先级决策，但并非所有决策都适合树。若决策条件之间存在大量交叉依赖，树会被迫复制分支，维护成本迅速上升；若决策需要从多个来源综合评分，表格、规则系统或效用 AI 可能更合适。树适合层级清晰、父子约束强、执行顺序明确的系统。识别这个边界，能避免把所有复杂逻辑都塞进一棵越来越难维护的树里。

在性能诊断中，树的成本通常以“整棵子树”为单位出现。移动一个父节点、刷新一个 UI 面板、重新计算一个空间节点、更新一个行为树分支，都可能触发其下所有子节点的处理。因此树的优化重点经常不是单个节点更快，而是减少受影响子树范围、缓存未变化分支、延迟处理不可见分支，以及把高频变化节点放在更浅或更独立的位置。

### 总结

树是表达层级关系的基础结构，二叉树是最经典的受限形式。它们的核心在于根、子树、路径唯一性和递归子问题。前序、中序、后序和层序遍历不是死记顺序，而是不同的信息传播方式：先父后子、左根右、先子后父、逐层推进。

二叉搜索树通过顺序约束把查找路径压缩到一侧子树，平衡时具有对数级性能，但退化时会变成链表。验证、插入、删除和范围查询都必须维护整棵子树的不变量，而不只是局部父子关系。平衡树存在的意义，就是把树高控制在可接受范围内。

在工程中，使用树结构前要确认关系是否真的是树，节点是否只有一个父级，子节点顺序是否有意义，操作是否会级联影响子树，递归深度是否可控，缓存信息如何失效。Unity 的 Transform、UI、行为树和空间分区都体现了树结构的力量，也暴露了深层级、动态修改和调试可见性的成本。

掌握树与二叉树，不是为了背题解，而是为了建立层级建模能力。只要能清楚说明节点、边、子树、遍历顺序和不变量，就能把树从算法练习转化为可维护的系统结构。树的每一次设计都应同时回答两个问题：它为什么必须是层级结构，以及这棵树在最坏形态下是否仍然可控。

树的好处在于清晰，风险也在于清晰带来的级联影响。每个父子关系都应被认真对待。
