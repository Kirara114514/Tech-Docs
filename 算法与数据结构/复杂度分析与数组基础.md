# 复杂度分析与数组基础

### 背景

复杂度分析是理解算法效率的基本语言。它不试图回答某段代码在某台机器上具体运行多少毫秒，而是回答当输入规模增长时，计算成本会以什么趋势增长。这个区别非常重要：具体耗时受硬件、编译器、运行时、缓存、数据分布和系统负载影响，而复杂度关心的是增长规律。增长规律一旦失控，再快的机器也只是把问题推迟到更大的输入规模上暴露。

数组是理解复杂度最好的起点。它结构简单，却包含了许多底层性能问题：连续存储带来快速随机访问，也带来插入删除移动成本；固定长度带来稳定布局，也带来扩容复制；索引访问看似 O(1)，却仍然受到越界检查、缓存命中、元素大小和内存局部性的影响。通过数组，可以把抽象的大 O 记号与真实的工程代价连接起来。

在游戏开发中，复杂度分析并不是面试题专属知识。一个单位列表每帧遍历一次可能没问题，嵌套遍历所有单位与所有技能范围就可能造成帧率下降；一个数组查找在编辑器工具中可以接受，在运行时热路径中就可能成为抖动来源；一个临时数组分配在单次调用中微不足道，在每帧多次调用时会变成 GC 压力。复杂度分析帮助开发者提前识别这些增长风险。

很多性能问题并不是因为某段代码“慢”，而是因为它在错误的规模下使用了错误的增长模型。O(n) 的逻辑在 n 很小时可能比复杂数据结构更快，O(n^2) 的逻辑在几十个元素时也可能完全可接受；但如果 n 随关卡规模、玩家数量、资源数量或帧频持续增长，原本看似无害的循环会迅速成为系统瓶颈。复杂度的意义，就是在问题变大之前看见趋势。

本文以数组为基础讨论复杂度分析，重点解释时间复杂度、空间复杂度、常见增长阶、数组操作的真实成本，以及工程中如何根据访问模式选择数据结构。目标不是背诵符号，而是建立一种判断能力：面对一段代码时，能看出它的成本来自哪里，随规模如何变化，是否值得优化，以及优化会用什么代价交换什么收益。

### 核心原理

复杂度分析的核心对象是输入规模。输入规模通常记作 n，但 n 并不总是数组长度。在图算法中，规模可能包括顶点数 V 和边数 E；在二维地图中，规模可能是行数乘列数；在资源系统中，规模可能是资源数量和依赖边数量；在游戏 AI 中，规模可能是单位数量、候选目标数量和行为分支数量。分析复杂度前，必须先定义规模是什么。

大 O 记号描述增长上界。它忽略常数项和低阶项，关注规模足够大时占主导地位的增长项。例如 3n+20 与 n 都属于 O(n)，n^2+100n 属于 O(n^2)。这种忽略不是说常数不重要，而是说在长期增长趋势上，最高阶项决定系统能承受的规模。工程上仍然要关注常数，因为游戏热路径中的常数开销会影响帧时间；但常数优化无法拯救错误的增长阶。

常见时间复杂度可以按增长速度理解。O(1) 表示成本不随输入规模变化，例如数组按索引读取。O(log n) 表示每一步大幅缩小问题规模，例如二分查找。O(n) 表示线性扫描，例如遍历数组。O(n log n) 常见于高效排序。O(n^2) 常见于两层全量比较。O(2^n) 和 O(n!) 常见于枚举组合或排列，规模稍大就不可接受。

时间复杂度不是执行语句数量的机械相加，而是对控制流增长规律的抽象。单层循环通常是 O(n)，两层独立嵌套循环通常是 O(n^2)，但两层循环并不必然就是 O(n^2)。如果内层循环总次数随外层合计仍然是 n，例如双指针从两端向中间移动，那么整体仍是 O(n)。分析时应关注所有循环变量在整个执行过程中总共移动多少次，而不是只看缩进层级。

递归复杂度要看递归树。每次递归只处理一个规模减一的问题，可能是 O(n)；每次把问题分成两个一半并在线性时间合并，可能是 O(n log n)；每次分裂成两个规模减一的问题，可能指数级增长。递归还会产生调用栈空间，哪怕没有显式创建数组，也可能有 O(n) 或 O(log n) 的额外空间。

空间复杂度衡量额外内存随规模增长的趋势。原始输入本身通常不计入额外空间，除非算法必须复制它。原地算法通常只使用常数额外空间，但原地不等于一定更快，因为原地操作可能需要更多数据移动或更复杂的控制逻辑。空间换时间是常见优化，例如用哈希表把查找从 O(n) 降到平均 O(1)，代价是 O(n) 额外空间。

数组的核心特性是连续存储和索引访问。对于固定类型元素，数组可以通过起始地址、元素大小和索引计算元素位置，因此随机访问是 O(1)。这个 O(1) 来自内存布局，而不是语法便利。链表也能表示序列，但访问第 i 个元素需要从头逐个走过，时间是 O(n)。数组的优势来自地址可计算性。

连续存储同时带来缓存局部性。现代 CPU 读取内存时往往会把相邻数据一起加载到缓存中。顺序遍历数组通常比遍历分散对象引用更友好，原因不是大 O 不同，而是内存访问模式不同。在 Unity 或 C# 环境中，数组、List<T>、NativeArray 等结构在热路径中的表现差异，往往与连续内存、装箱、引用间接访问和 GC 压力有关。

数组的插入和删除成本来自移动元素。如果在数组中间插入一个元素，后面的元素必须整体后移；删除中间元素时，后面的元素必须前移以保持连续顺序。因此中间插入删除通常是 O(n)。如果顺序不重要，可以用末尾元素覆盖被删除位置，把删除降到 O(1)，但代价是破坏元素顺序。这个取舍在对象池、实体列表和临时候选集合中很常见。

动态数组的扩容成本需要摊还分析。List<T> 看起来支持追加元素，但底层容量不足时会申请更大的数组并复制旧元素。单次扩容是 O(n)，但如果容量按倍数增长，多次追加的平均成本可以摊还为 O(1)。这并不意味着扩容没有代价；在帧内突然扩容仍可能造成尖峰。因此对已知规模的列表预设容量，是工程上简单有效的优化。

复杂度有最好、平均和最坏情况之分。线性查找如果第一个元素命中，最好情况是 O(1)；如果目标不存在，最坏情况是 O(n)。哈希表平均查找接近 O(1)，但在严重冲突时可能退化。快速排序平均 O(n log n)，最坏 O(n^2)，虽然实际实现会通过随机化、三数取中或内省排序降低风险。讨论复杂度时，应说明自己指的是哪种情况。

数组相关问题常见的优化思想包括双指针、滑动窗口、前缀和、差分、二分查找和哈希辅助。它们并不是孤立技巧，而是利用数组的顺序、连续性和可索引性减少重复工作。双指针用两个位置协同移动，避免重复扫描；滑动窗口维护一个动态区间；前缀和把区间求和变成两次读取；二分查找利用有序性把线性搜索降为对数级。

复杂度分析必须结合数据约束。n 等于 100 时，O(n^2) 只有一万级操作，可能完全可接受；n 等于 100000 时，O(n^2) 就几乎不可用。反过来，为几十个元素引入复杂索引结构，可能让代码更难维护且没有收益。算法选择不是追求最低大 O，而是在规模、频率、实现复杂度、内存成本和正确性之间取平衡。

### 设计思路

分析一段代码时，第一步是找到输入规模和热路径。输入规模决定增长趋势，热路径决定优化优先级。启动时运行一次的 O(n^2) 检查可能可以接受，每帧运行的 O(n^2) 检查则需要谨慎。编辑器工具、构建脚本、运行时逻辑和服务器逻辑对性能的要求不同，复杂度分析必须放在调用频率中理解。

第二步是区分必要工作和重复工作。必要工作是无论如何都必须看一遍的数据，例如统计数组总和至少要访问每个元素一次。重复工作是可以通过保存中间结果、改变遍历顺序或使用辅助结构减少的成本。例如频繁查询区间和时，每次从头累加是重复工作；使用前缀和后，每次查询只需读取两个位置。

第三步是识别数组操作的实际语义。读取、写入、追加、插入、删除、查找、排序、复制、切片，看起来都在操作数组，但成本完全不同。按索引读写是 O(1)，无序查找是 O(n)，中间插入删除是 O(n)，排序通常至少 O(n log n)，复制是 O(n)。很多性能问题来自把“数组操作”当成同一类成本。

第四步是判断是否需要保序。保序会显著影响数组删除和合并策略。如果列表只是临时候选集合，可以用尾元素覆盖删除，快速但乱序；如果列表用于 UI 展示、回放、确定性同步或优先级处理，就不能随意破坏顺序。复杂度优化不能脱离业务语义，否则会把性能问题变成正确性问题。

第五步是决定是否用空间换时间。两数之和从双重循环优化到哈希表，是典型的空间换时间：原本 O(n^2) 的比较变成 O(n) 遍历，代价是 O(n) 字典空间。这个思想在游戏中也常见，例如用字典缓存资源 ID 到对象的映射，用网格桶减少空间查询范围，用查表避免重复计算。但缓存会带来失效、同步和内存占用问题，不能只看查询复杂度。

第六步是考虑数据布局。对于大量简单数值，连续数组通常比对象列表更适合高频遍历；对于频繁插入删除且不需要随机访问的场景，链式或池化结构可能更合适；对于按键查找，哈希表或排序数组加二分可能更合适。数据结构选择本质上是把最常见的操作变便宜，把不常见操作的成本留在可接受范围内。

下面用一个短示例说明复杂度分析的思路：

```text
for enemy in enemies:
    for target in targets:
        if distance(enemy, target) < range:
            record target
```

如果敌人数量是 E，目标数量是 T，那么这段代码是 O(E*T)。当 E 和 T 都很小时，它简单可靠；当二者随关卡规模增长时，就需要空间分区、网格桶、四叉树、物理 Overlap 查询或阵营分组来减少候选目标数量。优化点不是把 distance 写得更快，而是减少不必要的配对比较。

数组遍历优化也要注意边界条件。二分查找要求数组有序；滑动窗口通常要求窗口移动具有单调性；前缀和适合区间聚合但不适合频繁单点修改与复杂查询同时存在的场景；双指针常依赖排序或可单调推进的条件。如果前提不成立，技巧会给出错误结果。

在 Unity 中，使用数组或 List<T> 时应关注分配位置。每帧创建新数组、调用会产生临时数组的 API、在循环中使用 LINQ、频繁 ToArray，都可能造成 GC 压力。复杂度符号无法直接表达 GC，但空间复杂度意识会提醒开发者：额外空间不是抽象数字，它会在运行时转化为分配、复制和回收成本。

预分配容量是一种低风险优化。如果知道一个列表通常会保存 500 个元素，就不要从默认容量开始反复扩容。对象池也可以减少频繁创建销毁带来的分配成本。但预分配不是越大越好，过度预留会浪费内存并降低缓存效率。空间与时间之间总是存在取舍。

排序数组是一个值得重视的中间选择。无序数组查找是 O(n)，哈希表平均 O(1)，排序数组查找 O(log n)，但插入可能 O(n)。如果数据构建后很少变化、查询频繁，排序数组加二分可能比哈希表更节省内存且更稳定。如果数据频繁增删，维护有序性成本可能过高。

复杂度分析还应覆盖失败路径。许多代码在命中时很快，失败时却必须扫描全部数据。例如查找某个不存在的对象、等待某个条件永远不满足、从候选列表中过滤掉全部元素。运行时问题常常出现在失败路径，因为失败路径更接近最坏情况。测试时应主动覆盖目标不存在、数组为空、元素重复、容量边界和极端规模。

文档、代码注释和接口命名也可以帮助复杂度控制。对于公共工具函数，若它会线性扫描或复制数组，应在文档中说明；对于看似简单但成本较高的属性，不应伪装成廉价访问。团队共享代码中，复杂度信息不透明会导致函数在错误场景中被高频调用。

### 进阶讨论

大 O 分析有意忽略常数，但工程不能完全忽略常数。两个 O(n) 算法可能因为内存访问、分支预测、虚函数调用、装箱、缓存命中和 SIMD 机会不同而表现差距巨大。数组顺序遍历通常常数小，链表遍历虽然同为 O(n)，但每个节点可能分散在内存中，缓存表现较差。大 O 决定规模上限，常数决定当前体验。

复杂度也不等于性能结论。O(log n) 的二分查找在很小数组上未必比线性扫描快，因为二分包含分支和随机访问，而线性扫描连续且简单。对于几十个元素的短数组，简单循环往往更清晰也足够快。只有当规模或调用频率达到阈值时，更低复杂度才会显现优势。

摊还复杂度容易被误用。动态数组追加的摊还 O(1) 并不代表每一次追加都是 O(1)。扩容那一次会复制全部元素，可能造成帧尖峰。实时系统不仅关心平均成本，也关心最坏帧时间。因此在运行时高频路径中，即使摊还复杂度良好，也应避免不可预测的扩容。

最坏情况分析在安全和稳定性要求高的系统中更重要。平均 O(1) 的哈希表如果遭遇大量冲突，性能会下降；递归算法如果输入退化，可能栈溢出；快速排序如果枢轴选择不佳，可能退化到 O(n^2)。游戏客户端通常可以接受某些平均情况假设，但服务器、工具链和资源构建系统更需要稳定的最坏情况边界。

数组的连续内存优势在多线程和数据导向设计中更加明显。Unity 的 Jobs、Burst 和 ECS 思路强调结构化、连续、可批量处理的数据布局。原因并不是数组语法更简洁，而是连续数据便于缓存预取、并行切分和向量化。复杂度分析告诉我们操作次数，数据布局决定这些操作能否高效执行。

二维数组也需要理解存储顺序。逻辑上是二维，内存中仍然是一维连续区域或一组引用。按行优先顺序遍历通常更接近内存布局，缓存更友好；频繁跨列跳跃可能增加缓存未命中。对于大地图、纹理数据、网格权重和寻路代价场，遍历顺序会影响真实性能。

数组复制是隐藏成本的常见来源。切片、拼接、转换、排序前复制、防御性拷贝、返回新集合，都可能是 O(n) 时间和 O(n) 空间。接口如果频繁返回数组副本，调用方可能以为只是读取属性，实际每次都产生整段复制。复杂度意识要求把这些隐式复制显式化。

原地算法的优势是节省空间，但可读性和错误风险也更高。三次反转旋转数组、原地分区、双指针覆盖删除，都依赖精确的索引边界。若业务代码对可维护性要求更高，使用额外数组可能更清晰。算法训练中追求 O(1) 空间，工程中则要权衡错误概率、团队理解成本和性能收益。

缓存不是万能解法。缓存能减少重复计算，但会引入失效问题。数组内容变化后，前缀和、索引表、排序结果和查找字典都可能过期。若更新频繁，维护缓存的成本可能超过查询收益。判断是否缓存，需要看读写比例、数据变化频率和错误后果。

复杂度优化应优先处理数量级问题。把 O(n^2) 降到 O(n log n) 往往比微调循环更有价值；把每帧全量扫描改为事件驱动，可能比优化扫描函数更有价值；把不必要的临时数组删除，可能比手写更复杂的算法更有价值。优化顺序应从增长模型、调用频率、分配行为和数据布局依次展开。

测试复杂度假设需要构造规模曲线。只测一个小规模样本无法证明增长趋势。可以用 100、1000、10000 等不同规模观察耗时增长是否接近预期；也可以统计循环次数、候选数量、分配字节和扩容次数。性能诊断不应只看最终耗时，还应看成本来源是否符合复杂度分析。

在算法学习中，数组基础经常被低估。数组看似简单，却是二分、排序、双指针、滑动窗口、前缀和、堆、哈希桶、图邻接表等结构的底层基础。理解数组的连续性、索引、移动和扩容，能够解释大量高级结构为什么这样设计。数据结构学习不是从复杂结构开始，而是从数组这类基础结构中看见成本规律。

### 总结

复杂度分析是一种关于增长的判断工具。它帮助开发者从“这段代码现在能跑”进一步看到“这段代码在规模扩大、频率提高、数据分布变化时是否仍然可靠”。大 O 记号关注主导增长项，空间复杂度关注额外内存趋势，最好、平均和最坏情况帮助说明算法在不同输入下的边界。

数组是理解复杂度的基准结构。它通过连续存储实现 O(1) 随机访问，通过顺序布局获得良好缓存局部性，但在中间插入删除、扩容复制和无序查找上存在 O(n) 成本。数组不是低级结构，而是许多高性能系统的核心基础。

工程中的复杂度选择必须结合规模、频率、语义和维护成本。小规模数据可以选择简单清晰的 O(n) 方案，高频大规模数据则需要更严格的增长控制。空间换时间、预分配、缓存、排序数组、哈希表和空间分区都可以优化成本，但它们也会引入内存占用、失效管理和复杂度。

真正掌握复杂度分析，不是记住 O(1)、O(n)、O(n log n) 的排序，而是在看到代码时能判断成本来自哪里，看到数据结构时能理解它便宜和昂贵的操作，看到性能问题时能先修正增长模型，再考虑常数优化。数组基础提供了最清晰的训练场，也为后续理解链表、栈、队列、哈希表、树、堆和图打下了共同语言。
