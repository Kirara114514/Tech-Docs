# 图与搜索

### 背景

图是用来表达“关系”的结构。数组强调连续位置，链表强调前后连接，树强调层级归属，而图强调任意对象之间可以存在多种连接方式。只要问题的关键不再是单个对象本身，而是对象之间如何互相到达、互相依赖、互相影响，就已经进入图模型的范围。

在游戏与实时交互系统中，图并不是只出现在寻路算法里。关卡房间之间的门、任务节点之间的前置条件、技能之间的解锁关系、资源包之间的依赖链、AI 行为状态之间的迁移、剧情分支之间的可达关系，都可以被抽象成图。寻路只是最直观的场景，因为它把顶点、边、代价和目标都摆在了玩家可见的空间上；但真正重要的是图提供了一种把复杂关系变成可计算问题的方法。

很多初学者把图与搜索理解为一组题型：DFS、BFS、Dijkstra、拓扑排序、并查集、最小生成树。这样的学习顺序可以帮助记忆，却容易遮蔽图算法的共同内核。图搜索的本质不是背诵遍历模板，而是在一个状态空间里维护“已经确认的信息”和“尚待扩展的边界”。栈、队列和优先队列只是边界管理策略不同；访问标记、距离数组、父节点记录和入度统计只是确认信息的具体形式。

因此，图与搜索的核心问题可以归结为三层：第一，如何把现实问题准确建模为顶点与边；第二，如何选择合适的数据结构表达这些关系；第三，如何用搜索策略在可控成本内得到正确结论。任何一层建模错误，后面的算法实现都会变成局部正确但整体无效的代码。

这也是图算法在工程中容易出错的原因。一个 BFS 函数本身可能只有几十行，但它是否能给出正确结果，取决于“相邻”的定义是否正确，边权是否真的可忽略，状态是否只由位置决定，图是否会动态变化，搜索结果是否允许过期，路径是否需要稳定可复现。图算法的工程难点往往不在代码长度，而在抽象边界是否清晰。

本文把图与搜索放在工程语境中讨论，重点不是罗列所有算法，而是解释为什么不同搜索策略会产生不同性质的结果，如何在 Unity 或一般游戏系统中选择表示方式，如何识别常见的建模陷阱，以及如何把图搜索从面试题模板提升为可靠的系统设计能力。

### 核心原理

图由顶点和边组成。顶点表示对象、位置、状态或抽象阶段，边表示两个顶点之间存在某种关系。边可以有方向，也可以无方向；可以有权重，也可以无权重；可以静态存在，也可以由运行时规则临时生成。图模型的表达力强，正是因为它对关系形态的限制很少。

无向图适合表达对称关系，例如两个房间之间互通、一段道路可以双向通行、两个对象属于同一个连通集合。有向图适合表达不对称关系，例如任务 A 必须先于任务 B、资源包 A 依赖资源包 B、状态 Idle 可以切到 Chase 但 Chase 不一定能直接切回 Idle。带权图把关系扩展为有代价的连接，权重可以代表距离、时间、风险、消耗、拥挤程度或设计上的偏好。

图的第一项关键判断是“顶点到底是什么”。在网格寻路中，顶点可以是格子坐标；在导航网格中，顶点可以是多边形区域或门户边；在任务系统中，顶点可以是任务节点；在资源加载中，顶点可以是资源包或资产引用；在 AI 决策中，顶点可以是行为状态。顶点选错后，边的定义会随之扭曲，算法也会被迫处理大量补丁逻辑。

第二项关键判断是“边到底表示什么”。边不是两个对象之间随便存在的联系，而是算法允许从一个状态转移到另一个状态的依据。比如地图上相邻的两个格子并不一定有边：如果中间有不可穿越障碍、门未开启、单位体型过大、地形高度差超过限制、当前角色没有通行权限，那么它们在当前搜索问题里就不相邻。图建模必须服务于目标问题，而不是服务于视觉上的接近。

图的存储方式通常有三类。邻接矩阵用二维矩阵记录任意两点是否有边，查询两点连接关系的成本是常数，空间成本却是顶点数量的平方，适合顶点数量较少、边很密集、频繁判断两点是否直接相连的场景。邻接表只记录真实存在的边，空间成本接近顶点数加边数，遍历某个顶点的邻居非常高效，是多数稀疏图的默认选择。隐式图不预先保存全部边，而是在搜索时由规则生成邻居，例如网格四方向移动、棋盘合法走法、状态机可转移集合，这在游戏中尤其常见。

DFS 与 BFS 的区别不只是一个用栈、一个用队列。DFS 优先深入当前分支，适合探索结构、检测环、枚举可能路径、处理递归依赖和完成后序逻辑。BFS 按层扩展，适合寻找无权图最短步数、传播影响、计算距离层级和处理多源扩散。二者都可以遍历连通区域，但它们给出的额外信息不同：DFS 更强调路径形态和回溯结构，BFS 更强调层级距离和最早到达。

访问标记是图搜索的基本防线。树遍历不需要担心回到父节点之外的祖先，但图中存在环，若不记录已访问顶点，搜索可能无限循环。更细致地说，访问标记的时机也影响结果。BFS 通常应在节点入队时就标记，而不是出队时才标记，否则同一个节点可能被多个前驱重复入队，导致队列膨胀并破坏父节点记录的确定性。DFS 在递归场景中还经常区分“正在访问”和“访问完成”，用于检测有向图中的环。

连通分量是图结构分析的基础概念。无向图中，如果一组顶点两两可通过路径到达，并且无法再加入更多顶点，这组顶点就是一个连通分量。游戏中可以用它判断区域是否可达、地图是否被障碍切断、联盟关系是否形成多个孤立阵营、房间网络是否存在断裂。连通性问题有时用 DFS/BFS 足够，有时更适合用并查集处理大量动态合并查询。

拓扑排序解决的是有向无环图中的依赖顺序问题。它不是一般排序，而是在“边表示先后约束”的前提下，给出一种满足所有依赖关系的线性顺序。资源构建、技能解锁、任务链、对话条件、构建流水线都可能需要拓扑排序。若图中存在环，拓扑排序不存在；这时错误不是排序失败这么简单，而是系统依赖关系本身出现了自我引用。

最短路径问题比“从 A 到 B 找路”更丰富。无权图中，每条边代价相同，BFS 的第一次到达就是最短步数。带非负权重的图中，Dijkstra 通过优先队列不断确认当前最小距离顶点，适合边权表示距离或时间的场景。A* 在 Dijkstra 的基础上加入启发函数，用对目标距离的估计引导搜索方向，常用于寻路。启发函数越准确，搜索越集中；但如果启发函数破坏必要约束，就可能失去最优性。

并查集处理的是集合合并与连通性查询。它不负责找具体路径，而是快速回答两个元素是否已经属于同一连通集合。路径压缩和按秩合并让它在大量操作中接近常数时间。它适合动态构建连通区域、检测无向图加边是否形成环、实现 Kruskal 最小生成树，也适合在地图生成后快速判断区域分组。

搜索中的“状态”不一定等于“顶点”。这是工程中最容易被忽略的原则。角色站在同一个格子上，是否拥有钥匙、剩余体力多少、当前阵营身份、是否触发机关，都会改变后续可达性。若把状态简化成位置，算法会错误地剪枝，把本应不同的状态当成同一个节点。很多复杂寻路、解谜和策略问题，本质上不是在地图图上搜索，而是在“位置加条件”的状态图上搜索。

搜索边界由数据结构决定。栈让最新发现的节点先扩展，队列让最早发现的节点先扩展，优先队列让当前代价最低或估值最优的节点先扩展。选择容器就是选择搜索的偏好，也决定算法能保证什么结论。用普通队列处理带权最短路径会把代价差异抹平；用优先队列处理无权层级传播则可能增加不必要成本。

图算法的正确性依赖明确的不变量。BFS 的不变量是按距离层逐步扩展，因此第一次出队或第一次入队通常代表最短步数。Dijkstra 的不变量是每次弹出的最小距离顶点已经不会被更短路径改写，因此边权必须非负。拓扑排序的不变量是入度为零的节点没有未满足前置依赖。并查集的不变量是每个集合有一个代表元，合并只改变集合归属，不表达路径细节。理解这些不变量，才能在变体场景中判断算法能否直接套用。

复杂度分析也必须结合图规模。邻接表遍历 DFS/BFS 的时间复杂度通常是 O(V+E)，其中 V 是顶点数，E 是边数。邻接矩阵遍历邻居时常常需要扫描整行，可能变成 O(V^2)。Dijkstra 在优先队列实现下通常接近 O(E log V)。但在游戏中，理论复杂度只是下限，内存分配、缓存局部性、GC、对象引用、动态障碍更新、帧预算和调试可视化都会改变真实表现。

### 设计思路

设计图搜索系统时，应先定义问题语义，再选择算法和容器。最常见的错误是先决定“这里用 BFS”或“这里用 A*”，然后再把业务硬塞进算法模板。更稳妥的顺序是：确定顶点代表什么，确定边代表什么，确定边是否有方向和权重，确定搜索目标是可达性、最短步数、最低成本、依赖顺序、连通分组还是枚举方案。

如果目标只是判断两个区域是否连通，DFS、BFS 和并查集都可能可用。静态一次性判断时，DFS/BFS 简单直接；大量在线查询时，先构建并查集更合适；需要具体路径时，并查集不够，因为它只回答是否连通。算法选择必须匹配输出需求，而不能只看输入结构相似。

如果目标是无权最短路径，BFS 是自然选择。关键实现点是把起点加入队列时设置访问标记，并记录父节点或距离。父节点用于还原路径，距离用于判断层级。若存在多个起点，例如火焰传播、声波扩散、敌人威胁范围、多入口区域覆盖，应把所有起点同时入队，这就是多源 BFS。多源 BFS 的本质不是循环跑多次 BFS，而是让所有源点共同形成第零层。

如果目标是带权最短路径，应明确权重是否非负。非负权重可用 Dijkstra；带有启发方向的寻路可用 A*；存在负权时，Dijkstra 的不变量失效，需要重新评估问题建模。游戏寻路通常不会使用负权边，因为“越走总代价越小”的设定会让路径选择产生反直觉结果，也容易形成算法难以解释的循环。

如果目标是依赖排序，应把边方向定义清楚。常见约定有两种：从前置节点指向后续节点，或从节点指向它依赖的前置节点。两种都可以，但入度计算和输出含义必须一致。资源系统、任务系统和构建系统尤其需要保持方向一致，因为方向混乱会导致循环检测错误，甚至把应该先加载的资源排到后面。

图表示方式应根据访问模式选择。邻接表适合遍历邻居，邻接矩阵适合频繁查询任意两点是否直接相连，隐式图适合规则清晰且规模较大的状态空间。Unity 中许多地图类问题不需要事先生成完整图：格子地图可以通过坐标偏移生成邻居，导航网格可以通过相邻多边形生成候选区域，行为状态机可以通过当前状态和条件动态返回可转移状态。隐式图能节省存储，但会把成本转移到邻居生成函数上，因此邻居生成必须足够稳定、可测试、可缓存。

搜索结果应包含足够的解释信息。只返回“找到路径”通常不够，工程系统还需要知道路径节点、总代价、失败原因、搜索消耗、访问节点数量、是否因为预算耗尽提前结束。失败原因尤其重要：目标不可达、起点非法、目标被占用、图数据过期、预算不足、边权异常，都会要求不同的上层处理策略。

实时系统要控制搜索预算。完整搜索可能在小地图上毫无压力，却在开放世界、大量单位同时寻路或动态障碍频繁变化时造成帧抖动。常见方案包括限制每帧扩展节点数、把搜索拆成可恢复任务、缓存常用路径、按区域分层搜索、使用粗图先规划大方向再在局部细化、对低优先级单位降低搜索频率。算法正确并不等于系统可用，帧预算是游戏工程中的硬约束。

路径搜索还要处理动态世界。门会打开，桥会断裂，单位会阻挡通道，地形代价会因为技能或天气变化而改变。静态路径在生成后可能立即过期。可靠系统通常需要路径有效性检查、局部重规划、图版本号、障碍更新事件和降级策略。对于频繁变化的环境，完全预计算的图可能反而不如局部生成邻居更灵活。

调试可视化是图搜索系统的重要组成部分。应能显示顶点、边、权重、开放集合、关闭集合、最终路径、不可达区域和失败位置。没有可视化时，图算法错误常常表现为角色“绕远路”“卡住”“走不到”“忽然放弃”，很难从日志直接定位。把搜索过程画出来，通常比增加更多日志更有效。

数据所有权也需要明确。图数据可以由关卡编辑器生成，可以由运行时系统构建，也可以来自资源配置。无论来源如何，都应避免多个系统各自维护一份含义相近但不同步的图。导航图、遮挡图、任务依赖图和资源依赖图虽然都叫图，却不能随意共用同一套结构；共享的是抽象方法，不一定是同一份数据模型。

在代码层面，图搜索接口应尽量把“邻居获取”与“搜索策略”分离。这样同一套 BFS 或 A* 框架可以用于网格、房间网络、状态空间和资源依赖，只要邻居函数、代价函数和目标判断可替换。分离并不意味着过度抽象，而是让算法依赖稳定的最小契约：给定一个状态，能枚举后继；给定一条边，能计算代价；给定一个状态，能判断是否满足目标。

短示例可以说明这种分离思想。伪代码如下：

```text
frontier.push(start)
mark start as visited

while frontier is not empty:
    current = frontier.pop()
    if current satisfies goal:
        return reconstruct_path(current)

    for next in neighbors(current):
        if next is invalid or already confirmed:
            continue
        record parent and cost
        frontier.push(next)
```

这段代码没有绑定具体容器。`frontier` 如果是栈，更接近 DFS；如果是队列，就是 BFS；如果是按总代价排序的优先队列，就是 Dijkstra；如果按“已消耗代价加启发估计”排序，就是 A*。同一个框架背后的差异，集中体现在边界如何排序、何时确认节点、如何更新代价。

实现时还要谨慎处理重复发现。同一个节点可能通过不同前驱到达。无权 BFS 中，第一次发现通常就是最短步数，可以直接标记；带权搜索中，后发现的路径可能更便宜，因此需要距离表和松弛逻辑，不能简单地用一个布尔 visited 阻止所有更新。把 BFS 的访问标记方式搬到 Dijkstra 或 A* 中，是许多路径错误的来源。

对于 Unity 项目，还要注意托管内存分配。搜索过程中频繁创建节点对象、列表、元组或闭包，可能引发 GC 抖动。高频寻路系统应复用容器、使用结构化数据、限制临时分配，并把搜索节点与场景对象解耦。图搜索依赖的是 ID 和状态，不应直接在算法内部频繁访问复杂的 GameObject 层级。

### 进阶讨论

隐式图是游戏工程中最实用也最容易误解的图。网格地图看似没有提前保存边，但四方向或八方向偏移实际上就是边生成规则。棋盘走法、技能释放范围、推箱子状态、回合制行动空间，都可以通过规则临时生成邻居。隐式图的优势是节省存储并能反映实时条件，缺点是每次生成邻居都要重新检查合法性，若检查逻辑复杂，搜索成本会迅速上升。

显式图与隐式图之间并没有绝对优劣。房间网络、传送点网络、任务依赖、资源引用通常适合显式存储，因为边数量有限且语义稳定。大规模网格、状态空间和动态规则通常适合隐式生成，因为提前列出全部边成本高，而且许多边只在特定状态下存在。工程上常见的混合方案是显式保存粗粒度结构，隐式生成局部细节。

A* 的启发函数值得单独讨论。启发函数估计当前节点到目标的剩余成本。如果估计从不超过真实成本，A* 可以保持最优性；如果估计过高，搜索会更贪心，可能更快但不一定最短。游戏中有时会故意使用带偏好的估计，例如让角色倾向大路、避开危险、减少转弯、保持阵型。此时目标已经不再是数学意义上的最短路，而是更符合设计意图的路径。重要的是承认这种变化，而不是仍然宣称结果最优。

搜索稳定性在多人游戏和回放系统中很关键。邻居枚举顺序、优先队列的并列处理、浮点权重误差都会影响最终路径。两个代价完全相同的候选节点，如果每次排序结果不同，就可能导致单位路径抖动或客户端不同步。稳定的 ID、固定邻居顺序、明确的 tie-breaker 和整数化成本，都是提高确定性的常见手段。

图搜索不应替代物理查询和导航系统的职责。物理系统负责碰撞、遮挡和空间检测，导航系统负责可行走区域，图搜索负责在抽象关系中寻找路径或结论。如果把所有空间细节都塞进图搜索，算法会变得臃肿；如果完全忽视物理和导航数据，路径又会穿墙、贴边或无法执行。正确做法是让图的边来自可信的通行规则，并在执行阶段继续验证。

动态障碍会让“最短路径”变成时间相关问题。当前最短路径可能因为另一个单位移动而不可用，绕行路径可能在下一秒又变差。对于大量移动单位，逐个执行完整 A* 可能成本过高，也可能导致互相阻塞。常见处理包括局部避障、流场、群体导航、路径共享、优先级调度和短周期重规划。图搜索负责宏观路径，局部运动仍需要专门系统协同。

依赖图中的环并不总是坏数据，但一定需要明确解释。在资源依赖中，环通常代表错误，因为 A 依赖 B，B 又依赖 A，会让加载或打包顺序无法成立。在剧情或状态机中，环可能是正常循环，例如巡逻、战斗、恢复再回到巡逻。区别在于算法目标：拓扑排序要求无环，状态机运行允许有环。不能因为看到环就一概删除，也不能在需要拓扑排序的系统中容忍环。

负权边是许多路径算法的边界条件。Dijkstra 不能处理负权，因为一个已确认最短的节点可能在后续通过负权边得到更低成本。游戏设计中若想表达奖励、顺风、加速或资源收益，通常不应直接把边权设为负数，而应重新设计成本函数，或把问题建模为收益最大化、约束规划或动态规划。算法的数学前提被破坏时，代码继续运行并不代表结果可信。

状态空间爆炸是图搜索的现实限制。位置、钥匙、背包、时间、敌人状态、机关开关都纳入状态后，顶点数量可能呈指数增长。解决方式不是盲目优化循环，而是缩小状态维度、使用启发式剪枝、分阶段求解、预计算局部结果、限制搜索深度或改用专门规划算法。深度优先并不意味着搜索越深越好，真正的深度是把影响正确性的状态保留下来，把无关变量排除出去。

测试图算法不能只测正常路径。应准备孤立节点、空图、单节点图、自环、多重边、非连通图、完全图、长链图、宽层图、存在多个同价路径的图、存在不可达目标的图、存在环的依赖图、权重极端不均的图。许多搜索错误只在边界图上暴露，例如访问标记时机错误、父节点覆盖错误、入度统计方向错误、优先队列重复节点处理错误。

图算法的输出也需要业务解释。最短路径不一定是最好的游戏路径，最小生成树不一定是最自然的道路网络，拓扑排序的某个合法结果不一定符合策划期望的展示顺序。算法给出的是满足形式约束的答案，业务系统还要决定答案是否符合体验目标。工程中的图搜索既是计算问题，也是设计问题。

有些场景并不需要完整图算法。少量固定节点的依赖可以用简单规则判断，极小范围的敌人检测可以用物理查询，线性任务链不需要拓扑排序，只有父子关系的层级结构不需要一般图。使用图模型的收益在于表达复杂关系；如果关系并不复杂，过度引入图框架会增加理解成本。

图与搜索真正的高级能力，是在看似不同的问题之间识别同一种结构。岛屿数量是连通分量，腐化传播是多源 BFS，课程安排是拓扑排序，地图寻路是带约束最短路径，资源打包是依赖图，联盟合并是并查集。掌握这些对应关系后，算法不再是孤立题目，而是一套可迁移的建模语言。

### 总结

图与搜索的核心价值，是把复杂关系转化为可计算的结构。顶点定义对象或状态，边定义可转移关系，权重定义转移代价，搜索策略定义扩展顺序。只要这四个要素清晰，许多看似不同的问题都能被统一分析。

DFS、BFS、Dijkstra、A*、拓扑排序和并查集并不是互相孤立的技巧。它们分别服务于不同问题：DFS 擅长结构探索与回溯，BFS 擅长无权最短层级，Dijkstra 擅长非负权重下的最低成本路径，A* 用启发函数提高目标导向搜索效率，拓扑排序处理有向无环依赖，并查集处理集合合并与连通性查询。选择算法之前，应先确认问题要求的输出与算法保证是否一致。

在游戏工程中，图算法的关键风险来自建模偏差和运行时约束。位置不一定等于状态，相邻不一定等于可达，最短不一定等于最好，静态路径不一定能在动态世界中持续有效。可靠的图搜索系统需要清晰的图语义、可控的搜索预算、稳定的数据结构、必要的可视化调试，以及对失败情况的明确表达。

把图学好，不是为了记住更多模板，而是为了拥有一种处理关系复杂性的思维方式。面对地图、资源、任务、状态、剧情、阵营或传播问题时，先问清楚“节点是什么、边是什么、代价是什么、目标是什么”，再选择搜索策略。这个顺序一旦建立，图算法就会从题目库里的知识点，变成工程系统中可以反复使用的分析工具。
