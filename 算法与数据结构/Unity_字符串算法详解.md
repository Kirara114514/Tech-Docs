# 字符串算法详解：匹配、回文、滑动窗口与工程性能

### 背景

字符串在 Unity 项目中同时属于算法对象和工程对象。算法层面，它是匹配、回文、滑动窗口、动态规划、前缀树和多模式搜索的经典载体；工程层面，它又出现在 UI 文本、日志、资源路径、配置 Key、本地化、聊天、协议字段、搜索框和编辑器工具中。很多字符串问题并不是“怎么写一段查找代码”，而是数据规模、调用频率、编码规则、分配行为和业务语义共同作用后的系统问题。

C# 的 `string` 不可变，这让字符串安全、可共享、可作为 Key，但也意味着拼接、截取、替换和格式化都会产生新字符串。Unity 运行时尤其敏感：每帧刷新文本、热路径拼接日志、频繁 `Substring`、反复 `ToLower`、运行时线性扫描本地化表，都会把看似微小的字符串操作转化为 GC、UI 重建和帧时间波动。

字符串算法也容易被过度使用。KMP、Rabin-Karp、Manacher、Trie、Aho-Corasick 都很重要，但它们不是越复杂越好。短文本、低频调用、标准库已优化的普通查找，通常不需要手写复杂算法；当文本长、模式多、调用频繁、性能边界明确时，复杂算法才有进入工程的理由。

本文以 Unity / C# 项目为语境，系统讨论字符串处理的核心原理、常见算法模型、工程设计边界和性能治理方法。目标不是罗列算法名词，而是建立判断能力：何时用内置 API，何时用滑动窗口，何时需要 KMP 或 AC 自动机，何时问题根本不在算法而在字符串分配和 UI 刷新。

### 核心原理

#### 一、字符串不可变性决定了性能边界

C# 字符串创建后不能修改。任何拼接、替换、截取、格式化都会生成新对象。不可变性带来线程安全、共享和作为哈希 Key 的便利，也让字符串操作在热路径中容易制造临时分配。理解字符串不可变性，是所有工程优化的前提。

循环中使用 `+` 拼接大量文本，会产生一系列中间字符串。`StringBuilder` 可以减少中间对象，但最终 `ToString` 仍会生成结果字符串。它不是无分配魔法，而是降低重复构造成本的工具。若文本每帧都需要重建，即使使用 StringBuilder，也可能仍然过于昂贵。

#### 二、字符、代码单元和用户可见字符不是同一件事

C# 的 `char` 是 UTF-16 代码单元，不一定等于用户看到的一个字符。某些 emoji、组合音标和扩展字符可能由多个代码单元组成。`Length` 返回的是代码单元数量，不是显示字符数量，也不是字节长度。

这对聊天、昵称、本地化、输入限制和文本截断非常重要。按 `char` 截断可能把代理项对切开，导致乱码或显示异常；按 `Length` 限制昵称可能对不同语言不公平；协议字段若限制字节长度，又不能直接使用字符数量。字符串算法若进入用户文本领域，必须先明确处理单位。

#### 三、比较规则是字符串系统的业务契约

字符串比较并不只有一种语义。资源路径、配置 Key、协议命令通常需要文化无关的 Ordinal 比较；玩家输入、搜索框和本地化文本可能需要更复杂的大小写、规范化或语言规则。若比较规则不统一，缓存命中、查表、搜索和协议解析都会出现不一致。

工程中应优先把比较器固定在容器或服务边界，例如 `StringComparer.Ordinal` 或 `StringComparer.OrdinalIgnoreCase`。不要在调用点反复 `ToLower` 或 `ToUpper`，这既会分配，也会把比较规则分散到各处。比较规则一旦成为业务契约，就应文档化。

#### 四、双指针适合边界收缩问题

双指针用两个索引从两端或同向推进，适合反转、过滤、回文判断、压缩和有序数组合并。它的核心价值是避免重复扫描，把嵌套判断压缩为线性过程。字符串中常见的回文验证、忽略非字母数字比较、原地字符数组处理，都可以用双指针表达。

双指针的关键是边界更新要和状态同步。跳过字符后是否继续比较，左右指针何时停止，空串和单字符如何处理，都必须明确。字符串不可变时，所谓“原地修改”只能发生在 `char[]`、`Span<char>` 或构建缓冲上，而不是原始 `string`。

#### 五、滑动窗口适合连续子串约束

滑动窗口维护一个连续区间，右指针扩张，左指针收缩，窗口内状态用计数表、哈希表或数组维护。它适合无重复字符最长子串、最小覆盖子串、异位词查找、固定长度匹配等问题。其本质是把“枚举所有子串”的高复杂度问题，转化为状态可增量维护的线性扫描。

滑动窗口最容易错在状态定义。窗口内哪些字符被计数，何时收缩，`left` 是否允许回退，计数减到零是否删除，匹配数如何更新，这些都必须服务同一个不变量。写滑动窗口不是套模板，而是先定义窗口合法条件。

#### 六、回文问题要区分需求规模

回文检测可以用双指针。最长回文子串可以用中心扩散，复杂度 `O(N^2)`，空间 `O(1)`，对多数短文本足够清晰。Manacher 可以在线性时间求最长回文子串，但实现复杂，边界和映射容易出错，维护成本高于普通方法。

因此，工程中只有在长文本、强性能要求或算法训练场景下，才应考虑 Manacher。对于 UI 文本、编辑器小工具和普通输入校验，中心扩散或简单双指针往往更可读、更容易验证。算法复杂度不是唯一标准，维护成本同样重要。

#### 七、KMP 解决的是重复匹配回退问题

KMP 的核心是前缀表。当前匹配失败时，不把主串指针回退，而是根据模式串的最长相等前后缀调整模式串位置。这样可以保证线性复杂度。它适合需要可控复杂度、自定义匹配或算法教学的场景。

但在普通 C# 工程中，单模式字符串查找通常优先使用内置 `IndexOf`。标准库实现经过优化，也更易读。只有当项目需要跨平台可解释行为、特殊匹配规则、重复大量搜索同一模式或必须讲清算法过程时，手写 KMP 才更有意义。

#### 八、Rabin-Karp 用哈希加速匹配候选

Rabin-Karp 使用滚动哈希比较固定长度窗口，先用哈希筛候选，再做实际字符串比较确认。它适合多模式、固定长度模式或需要快速滑动比较的场景。它的优势来自哈希增量更新，而不是跳过最终确认。

工程上必须处理哈希冲突。哈希相同不代表字符串相同，因此命中后仍需逐字符或切片比较。若忽略这一步，算法会在极低概率或恶意输入下产生错误。Rabin-Karp 的正确使用，是“哈希筛选 + 精确确认”。

#### 九、Trie 和 AC 自动机适合多模式集合

当需要在文本中匹配大量关键词时，逐个 `IndexOf` 会重复扫描文本。Trie 可以共享前缀，适合前缀查询、自动补全、命令系统和资源路径搜索。Aho-Corasick 在 Trie 上增加失败指针，可以一次扫描文本匹配多个模式，适合敏感词、关键词检测和日志扫描。

这类结构的代价是内存和更新复杂度。词库很小或调用低频时，直接查找更简单；词库大、文本长、调用频繁时，Trie 或 AC 才值得建设。客户端敏感词系统还要考虑误判、词库热更新、大小写和多语言规范化。

#### 十、编辑距离是字符串差异的动态规划模型

编辑距离衡量一个字符串通过插入、删除、替换变成另一个字符串的最小代价。它是动态规划典型问题，适合拼写纠错、模糊搜索、相似度比较和编辑器辅助工具。标准二维 DP 复杂度为 `O(MN)`，空间也可从二维优化为滚动数组。

在 Unity 工程中，编辑距离不宜无节制地用于运行时热路径。模糊搜索如果候选很多，应先通过前缀、长度、分词或索引做粗筛，再对少量候选计算编辑距离。否则算法正确但成本不可控。

### 设计思路

#### 一、先区分算法文本和用户文本

算法题中的字符串通常假设字符集简单、长度明确、输入干净。用户文本则包含多语言、emoji、组合字符、大小写、空白、标点、全角半角和编码边界。正式项目必须先判断处理对象属于哪一类。

资源路径、配置 Key 和协议字段可以按 Ordinal 语义处理；聊天、昵称和本地化展示则需要更谨慎。把用户文本按算法题里的 `char` 模型处理，是很多显示和截断问题的根源。

#### 二、热路径避免临时字符串

UI 数值、战斗日志、网络消息、AI 调试、排行榜刷新等路径中，应避免重复拼接和格式化。可以使用事件驱动、脏标记、缓存上一次文本、复用 StringBuilder、TextMeshPro 的数值格式化接口，或把详细日志延迟到真正需要输出时再生成。

关键原则是：没有变化就不要生成新字符串，不显示就不要格式化，不输出就不要拼接。很多字符串性能问题并不需要复杂算法，只需要减少无意义构造。

#### 三、UI 文本刷新要和数据变化绑定

每帧给 UI 文本赋值，即使内容相同，也可能触发布局或渲染相关更新。倒计时、血量、金币、伤害飘字和排行榜都应使用脏标记或事件驱动。数值变化时更新，未变化时保持现状。

对高频数值显示，还应控制显示精度和刷新频率。例如倒计时按 0.1 秒或 1 秒更新，伤害数字使用对象池，排行榜批量刷新而不是逐项即时重建。字符串优化常常要和 UI 系统一起看，而不是只看拼接代码。

#### 四、查找算法选择要基于规模

单次短文本查找使用 `IndexOf`；大量固定模式可以考虑预处理；大量关键词可考虑 Trie 或 AC；需要模糊匹配再考虑编辑距离；回文长文本才考虑 Manacher。算法选择应由文本长度、模式数量、调用频率、是否可预处理和维护成本共同决定。

复杂算法在小规模场景中可能没有收益，反而增加 bug 面。工程里的“高级算法”应服务明确瓶颈，而不是展示技巧。

#### 五、本地化 Key 应独立于显示文本

本地化系统应使用稳定 Key 查表，而不是把中文或英文显示文案当 Key。显示文本会调整、翻译和润色，若作为 Key，会导致资源引用和逻辑查找不稳定。Key 应具备命名规范、唯一性检查、缺失检查和语言切换刷新机制。

本地化查表应在加载阶段构建哈希索引，运行时避免线性扫描。语言切换时，UI 应通过事件或绑定系统刷新，而不是每帧查表。字符串在这里既是数据，也是资源管理边界。

#### 六、日志字符串要有级别和构造边界

日志常被低估。即使日志级别关闭，如果调用点已经完成字符串插值或拼接，分配仍然发生。热路径日志应使用条件编译、级别判断前置、延迟格式化或结构化参数。发布包应关闭不必要的详细日志。

调试信息当然重要，但日志系统应保证“不开就不构造”。否则日志会成为隐藏的字符串分配源，尤其在战斗、网络和 AI 循环中。

### 进阶讨论

#### 一、Unicode 正确性和性能经常冲突

按用户可见字符处理文本，比按 `char` 处理更正确，但成本更高。聊天、昵称和本地化输入需要正确性；资源 Key、协议字段和内部命令更需要稳定与性能。系统应按文本类型选择处理单位，而不是所有字符串都使用同一套规则。

例如内部资源路径可以禁止 emoji 和复杂规范化，使用 Ordinal 比较；玩家昵称则需要处理显示宽度、屏蔽词和截断边界。明确文本域，比试图写一个万能字符串工具更可维护。

#### 二、Substring 和切片策略影响 GC

频繁 `Substring` 会创建新字符串。解析协议、扫描日志、处理配置和文本分词时，如果只是临时查看片段，可以考虑索引范围、`ReadOnlySpan<char>` 或一次性解析到结构化数据中。是否使用 Span 取决于 Unity 运行时和目标平台支持，但思想是相同的：不要为了短暂视图制造长期对象。

对于正式数据管线，最好在加载阶段完成解析，把运行时热路径从字符串处理转成 ID、枚举、索引或结构化字段。字符串适合入口和配置，不一定适合高频逻辑核心。

#### 三、正则表达式不是免费工具

正则适合表达复杂文本模式，但解析、回溯和分配成本可能较高。简单前缀、后缀、包含、分割和固定格式解析，不一定需要正则。若确实使用正则，应考虑预编译、缓存实例、限制输入长度和避免灾难性回溯。

Unity 项目中的正则常见于编辑器工具、导入校验和离线处理。运行时热路径应非常谨慎。很多时候，手写一个小型状态机比复杂正则更可控。

#### 四、多模式匹配需要词库治理

AC 自动机和 Trie 的难点不只是算法实现，还包括词库来源、大小写规则、全半角、简繁转换、动态更新、误判处理和命中解释。敏感词过滤如果只关注匹配速度，会忽略内容治理问题。

词库更新频繁时，重建自动机的成本和时机要明确；多语言项目中，不同语言可能需要不同匹配规则；客户端过滤还要考虑被绕过风险。字符串算法只解决匹配问题，不解决内容策略。

#### 五、字符串作为 Key 要和哈希表规范一致

本地化 Key、资源路径、协议字段和命令名通常会进入 Dictionary。此时字符串算法与哈希表设计相连：比较器要统一，大小写规则要固定，Key 不能运行时随意拼接，缺失 Key 要有诊断信息。

如果一个系统同时在不同地方用 Ordinal、OrdinalIgnoreCase 和 ToLower 后比较，迟早会出现缓存不命中或重复记录。字符串 Key 应进入项目级规范，而不是由每个模块自行决定。

#### 六、算法题实现要避免误导工程写法

算法题常为了表达核心思想，直接使用 `Substring`、`Dictionary<char,int>` 或简化字符集。工程中这些写法未必合适。固定 ASCII 字符集可以用数组代替字典；长文本应减少切片；热路径应避免临时集合；用户文本不能简单按 char 计数。

学习算法时可以先追求清晰，落地工程时必须再做一次语境转换。把题解直接搬到项目热路径，是许多性能和边界 bug 的来源。

#### 七、字符串处理应进入性能预算

字符串性能问题往往分散在 UI、日志、配置、网络和资源系统中，单个调用点不显眼，累积起来才形成 GC 和 CPU 压力。项目应在关键场景中观察字符串分配、UI 文本刷新次数、日志量、配置解析耗时和本地化查表命中率。

只有指标可见，优化才不会变成经验猜测。若发现字符串分配集中在 UI，则优先治理刷新；集中在日志，则治理日志构造；集中在解析，则考虑预处理和结构化数据。不同来源需要不同方案。



#### 八、协议与配置解析应从字符串转为结构化数据

很多系统在入口处接收字符串，但不应该在核心逻辑中长期保留字符串判断。网络协议字段、配置表字段、资源路径、命令参数和脚本表达式，都适合在加载或解析阶段转换成枚举、整数 ID、结构体或预计算索引。这样运行时逻辑就不必反复做字符串比较和解析。

这种转换的价值不只是性能，也包括错误前置。配置缺字段、字段拼写错误、协议命令不存在、资源路径不规范，都可以在加载阶段暴露，而不是运行到某个玩法分支才发现。字符串越靠近系统入口，越应尽快被规范化；越靠近高频逻辑，越应减少字符串参与。

#### 九、搜索框和自动补全要按交互频率设计

编辑器搜索、背包搜索、好友搜索、命令补全和资源浏览器都依赖字符串匹配。若数据量小，直接线性扫描配合 `IndexOf` 足够简单；若数据量大且输入每次变化都触发搜索，就需要索引、前缀树、分词或缓存上一次结果。

搜索系统还要考虑交互延迟。用户输入一个字符就全量扫描十万条资源，体验会抖动；但构建复杂索引也会占用内存和加载时间。更实际的方案往往是分层：短列表直接扫，大列表预构建索引，输入防抖，结果分页，后台异步更新。

#### 十、格式化字符串要关注文化与确定性

数值、日期和货币格式化会受到文化设置影响。游戏 UI 中的显示格式可以按本地化规则变化，但协议字段、存档、日志机器解析和资源导出应使用固定文化或明确格式。否则同一数值在不同区域环境下可能产生不同字符串。

这类问题很隐蔽。调试日志看起来只是文本，后续若被工具解析，就变成数据接口。正式工程中应区分“给玩家看的格式”和“给机器读的格式”。前者服务语言体验，后者服务稳定性和可解析性。

#### 十一、字符串池化要谨慎使用

字符串驻留或自定义字符串池可以减少重复字符串，但也可能让内存生命周期变长。资源 Key、协议常量、配置字段等有限集合适合集中管理；玩家输入、聊天内容和动态日志则不适合无脑池化。错误池化会把短生命周期文本变成长生命周期引用，造成内存增长。

因此，池化策略必须基于数据来源和重复率。若字符串集合有限、重复高、生命周期接近全局，池化可能有收益；若字符串无限、动态、用户生成，池化通常风险更高。字符串优化不应只看分配次数，也要看保留时间。

#### 十二、文本截断应区分字节限制、字符限制和显示限制

服务器字段可能限制字节数，昵称系统可能限制用户可见字符数，UI 框可能限制显示宽度。这三种限制完全不同。按字节截断可能切断 UTF-8 多字节字符，按 UTF-16 `Length` 截断可能切断代理项，按字符数量截断仍可能因为宽字符导致 UI 溢出。

正式项目应为不同限制建立不同工具。协议层按编码后的字节安全截断，输入层按文本元素处理，UI 层按排版宽度和字体测量处理。把所有场景都写成 `s.Substring(0, max)`，迟早会在多语言和 emoji 输入中出问题。

#### 十三、KMP 的前缀表要讲清“回退到哪里”

KMP 常被背成模板，但真正理解点在于前缀表表达的是“当前已经匹配的模式前缀，在失败后可以保留多少”。它避免主串回退，是因为已经比较过的字符信息被模式串自身结构复用了。若只记代码，不理解这个不变量，前缀表边界很容易写错。

工程中如果要手写 KMP，应把前缀表构建和匹配过程拆开测试。空模式、单字符模式、重复字符模式、完全不匹配、部分重叠匹配都要覆盖。KMP 的难点不是复杂度，而是边界正确性和维护者是否能看懂。

#### 十四、Rabin-Karp 适合候选过滤，不适合单独判定

滚动哈希在大文本中非常有用，但它的命中只是候选。尤其在内容安全、协议解析或资源校验中，哈希冲突即使概率低，也不能被当成不可能。命中后必须回到精确比较，或者使用足够强的校验组合。

如果系统不能容忍误判，Rabin-Karp 就必须以“快速筛选器”的身份出现，而不是最终裁决者。这个原则和哈希表冲突处理类似：哈希负责缩小范围，相等比较负责最终正确性。

#### 十五、编辑距离应先缩小候选集合

编辑距离的代价随两个字符串长度乘积增长。若对所有候选都计算完整编辑距离，模糊搜索会非常昂贵。更合理的流程是先按长度差、前缀、首字母、分词、类别或索引做粗筛，再对少量候选计算编辑距离。

编辑距离还要根据业务定义代价。插入、删除、替换是否等价，大小写是否等价，中文拼音或同音字是否特殊处理，都会改变结果语义。算法公式只是基础，搜索体验取决于业务代价模型。

#### 十六、字符串算法应配合测试语料

字符串处理不能只用英文短样例测试。正式项目至少应覆盖空串、长串、重复字符、大小写、空白、标点、中文、日文、韩文、emoji、组合字符、全角半角、路径分隔符、非法输入和超长输入。若涉及本地化，还应覆盖不同语言文本长度差异和 UI 溢出。

这些测试语料能提前暴露很多问题：截断错误、比较规则不一致、窗口算法按 char 误判、日志格式不可解析、搜索结果不稳定。字符串系统越接近用户输入，测试语料越重要。

#### 十七、文本工具链比运行时算法更适合承担重处理

很多字符串工作可以离线完成，例如本地化 Key 校验、资源路径规范化、敏感词自动机构建、搜索索引构建、剧情文本格式检查、配置字段枚举化。把这些工作放到导入、构建或编辑器阶段，可以显著降低运行时成本。

运行时应尽量消费已经结构化、索引化和校验过的数据。算法不是只能在运行时发挥价值，很多时候它更适合进入工具链。这样既提高性能，也让错误更早暴露。

#### 十八、字符串处理需要明确所有权

一个字符串字段由谁生成、谁规范化、谁比较、谁展示、谁缓存，必须清楚。资源路径由资源系统规范化，本地化 Key 由本地化系统管理，聊天文本由输入和安全系统处理，日志文本由日志系统格式化。若每个业务模块都自行处理字符串，规则必然分裂。

所有权清楚后，字符串工具函数才不会无限膨胀成杂物箱。正式项目需要的是领域服务，而不是到处可调用但语义不明的字符串工具集。



#### 十九、字符串分配要能定位到来源

看到 GC 分配来自字符串，并不等于已经找到问题。字符串可能来自 UI 赋值、日志插值、路径拼接、异常构造、LINQ、正则、Substring、ToString 或本地化格式化。优化前必须定位来源，否则容易在无关位置做微优化。

Unity Profiler、Memory Profiler、深度采样和自定义计数都可以帮助定位。核心模块可以记录每帧文本刷新次数、日志构造次数、格式化次数和本地化查表次数。字符串优化越靠后期，越需要证据，而不是凭感觉重写所有文本代码。

#### 二十、规范化应在边界完成

路径斜杠统一、大小写规则、去除首尾空白、全角半角转换、Unicode 规范化、Key 命名检查，都属于规范化。规范化应尽量在数据进入系统的边界完成，例如资源导入、配置加载、玩家输入提交、网络消息解析，而不是在每次查询时临时处理。

边界规范化能把错误前置，也能减少运行时重复工作。若每次查字典前都 `Trim`、替换斜杠、转小写，说明系统没有在入口处建立契约。正式工程更需要稳定入口，而不是无限补救的调用点。

#### 二十一、热更新文本要考虑版本兼容

本地化表、公告文本、活动配置和远程资源 Key 可能通过热更新下发。字符串系统如果只关注运行时查找速度，而忽略版本兼容，就可能出现客户端代码期待某个 Key、远端文本表却缺失或格式变化的情况。缺失 Key 应有明确降级文本、错误上报和版本校验。

对带占位符的文本，还要验证参数数量和类型。`{0}`、`{name}`、富文本标签、换行和颜色标记都可能因为翻译或配置错误导致显示异常。文本热更新不是单纯替换字符串，而是带格式契约的数据更新。

#### 二十二、富文本和标记语言需要专门解析边界

TextMeshPro 富文本、聊天表情标记、颜色标签、道具链接和自定义占位符，都会让字符串从普通文本变成带结构的文本。此时简单的查找、截断和长度计算可能破坏标签结构，导致显示错误或安全问题。

如果项目大量使用富文本，应建立标记解析和校验工具。截断时不能切断标签，过滤时不能破坏嵌套，搜索时要区分显示文本和标记文本。字符串算法一旦遇到结构化文本，就不能只按线性字符数组处理。

#### 二十三、字符串系统也需要降级策略

当搜索索引未构建完成、敏感词词库加载失败、本地化 Key 缺失、远程文本格式错误或日志系统过载时，系统应有降级策略。可以回退到默认语言、显示占位符、跳过非关键搜索、限制日志频率或使用保守过滤。没有降级策略的字符串系统，会在边界数据异常时影响用户体验。

降级不等于掩盖错误。开发版应明显暴露问题，线上版应保护体验并上报诊断信息。字符串系统离用户很近，错误处理必须同时考虑可见表现和工程排查。

### 总结

字符串算法连接了算法理论和 Unity 工程现实。双指针、滑动窗口、KMP、Rabin-Karp、Manacher、编辑距离、Trie 和 AC 自动机都各有价值，但它们必须服务明确的数据规模和调用模式。复杂算法不是默认答案，内置 API、预处理、结构化数据和减少分配往往更重要。

在正式项目中，字符串处理的核心是四件事：明确文本语义，控制临时分配，选择合适算法，建立工程规范。资源路径、配置 Key 和协议字段要使用稳定比较规则；用户文本要考虑 Unicode 和显示边界；UI 文本要事件驱动；日志要避免关闭后仍拼接；本地化要使用稳定 Key 和预构建索引。只有把这些约束纳入设计，字符串系统才会既正确又可维护。
