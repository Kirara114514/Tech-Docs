# 排序算法详解

### 背景

排序是把一组数据按照某种比较规则重新排列的过程。它看似只是基础算法，却贯穿工程系统的许多层面：排行榜需要按分数排序，背包需要按类型和稀有度排序，渲染对象需要按材质或深度排序，AI 候选目标需要按威胁或距离排序，任务列表需要按优先级排序，资源构建流程需要按依赖和时间排序。只要系统需要“先后关系”，排序就会出现。

排序算法的学习价值不在于记住每一种实现，而在于理解同一个目标为什么会有多种成本模型。冒泡、选择、插入、归并、快速、堆、计数、桶、基数排序都能产生有序序列，但它们在时间复杂度、空间消耗、稳定性、数据适应性、缓存表现、实现复杂度和最坏情况保障上差异很大。排序是算法权衡的集中展示。

工程中真正的问题通常不是“如何写一个排序”，而是“应该排序什么、按什么键排序、数据规模多大、是否需要稳定、是否允许额外内存、是否在热路径、是否有大量重复键、是否接近有序、是否能利用整数范围”。如果这些条件没有定义清楚，盲目选择某个经典算法并不能保证正确或高效。

游戏开发尤其需要谨慎看待排序。排序常常出现在每帧逻辑中，例如战斗目标筛选、透明物体排序、UI 列表刷新、寻路开放集合维护、对象池回收候选选择。一次排序的成本可能不高，但在高频调用、多对象同时执行和临时分配叠加后，会转化为帧时间尖峰或 GC 压力。排序不是孤立操作，而是系统数据流的一部分。

本文按原理与工程选择重写排序算法，重点解释排序的评价指标、比较排序的共同下限、典型算法的设计思想、稳定性和空间权衡，以及在 Unity/C# 项目中如何更可靠地使用排序能力。目标不是鼓励手写所有算法，而是建立判断能力：知道内置排序适合什么，知道特殊数据何时可以更快，知道排序需求本身何时可以被替代。

### 核心原理

排序首先依赖顺序关系。对于数字，顺序通常清晰；对于对象，需要通过比较器定义排序键。比较器必须满足基本一致性：如果 A 小于 B，B 小于 C，那么 A 应小于 C；相等关系应稳定可解释；同一输入在同一状态下应返回同样结果。比较器不稳定或依赖变化中的外部状态，会让排序结果不可预测，甚至使某些排序实现出现异常行为。

评价排序算法通常看四个指标。第一是时间复杂度，描述排序成本随元素数量增长的趋势。第二是空间复杂度，描述额外内存需求。第三是稳定性，即相等键元素在排序后是否保持原有相对顺序。第四是适应性，即算法是否能利用“数据接近有序”“键范围有限”“重复元素很多”等输入特征。

比较排序只通过两两比较确定顺序。任何基于比较的一般排序，在最坏情况下都需要 Ω(n log n) 次比较。这个下限来自决策树模型：n 个元素有 n! 种可能排列，比较结果形成二叉决策树，要区分所有排列，树高至少接近 log2(n!)，也就是 n log n 级别。因此快速排序、归并排序、堆排序等通用比较排序很难在一般意义上突破 O(n log n)。

非比较排序通过利用数据结构特征绕开比较下限。计数排序利用整数值域统计频次，桶排序利用数据分布把元素分配到区间，基数排序按位处理整数或定长键。它们能在特定条件下达到线性或接近线性复杂度，但代价是对数据类型、值域范围、分布形态或额外空间有要求。它们不是“更高级的通用排序”，而是更依赖前提的专用排序。

冒泡排序通过相邻元素反复交换，把较大元素逐步移动到末尾。它的原理直观，稳定，空间 O(1)，但平均和最坏时间复杂度都是 O(n^2)。即使加入“本轮无交换则提前结束”的优化，也只是在已排序或接近已排序时变快。工程中很少直接使用冒泡排序，它更多用于说明相邻交换和稳定性的概念。

选择排序每轮从未排序区间选出最小元素放到前面。它的比较次数始终接近 n^2/2，但交换次数最多 n 次，因此在写入成本特别高时有一定解释价值。普通选择排序不稳定，因为把最小值交换到前面时可能跨过相等元素。它简单、原地、空间 O(1)，但难以利用已有有序性。

插入排序维护一个已排序前缀，把新元素插入正确位置。它最坏和平均是 O(n^2)，但在接近有序数据上接近 O(n)，常数小、实现简单、稳定、原地。许多工业排序会在小数组或递归分治的末端使用插入排序，因为当规模很小，复杂算法的递归和分区开销可能超过收益。

快速排序的核心是分区。选择一个枢轴，把小于枢轴的元素放到一侧，大于枢轴的元素放到另一侧，然后递归处理左右区间。它平均 O(n log n)，原地性好，缓存表现通常不错，是许多场景中非常快的排序思想。风险在于分区极度不平衡时会退化到 O(n^2)，因此实际实现通常使用随机枢轴、三数取中、三路分区或内省排序来控制最坏情况。

归并排序的核心是稳定合并。它把数组不断二分，分别排序后再把两个有序区间合并。归并排序始终保证 O(n log n) 时间，稳定性容易保证，适合链表排序和外部排序，也适合需要稳定结果的多键排序。代价是通常需要 O(n) 额外空间；对于内存敏感的运行时热路径，这个空间成本不能忽略。

堆排序利用二叉堆维护最大值或最小值。先把数组建成堆，再不断取出堆顶放到末尾。它保证 O(n log n) 时间，额外空间 O(1)，最坏情况稳定可靠，但通常不稳定，缓存局部性和常数表现往往不如快速排序。堆排序的思想在优先队列中更常用，尤其适合反复取最小或最大元素，而不一定适合一次性完整排序。

计数排序适合整数值域较小的场景。它统计每个值出现次数，再按值域顺序输出。如果需要稳定排序，可通过前缀计数确定每个元素的最终位置，并从后向前填充输出数组。它的时间复杂度是 O(n+k)，空间复杂度也是 O(n+k) 或 O(k)，其中 k 是值域范围。若 k 远大于 n，计数排序会浪费大量空间。

桶排序把数据分配到若干桶中，对桶内分别排序后再合并。它依赖数据分布较均匀这一前提；如果所有元素落入同一个桶，性能会退化为桶内排序的复杂度。桶排序常用于浮点数、分数区间或可均匀映射到范围的数据。它体现了一个重要思想：先用粗分组降低局部排序规模。

基数排序按位处理键，例如从个位到高位依次进行稳定排序。它适合整数、定长字符串或可拆分为固定位段的键。时间复杂度通常写作 O(d(n+k))，d 是位数，k 是每位的取值范围。基数排序的关键条件是每一轮必须稳定，否则低位排序结果会被高位处理破坏。

稳定性在多键排序中非常重要。如果先按次要键排序，再用稳定排序按主要键排序，次要键顺序会在主要键相等时保留下来。UI 列表、排行榜、资源排序、日志展示都可能依赖这种性质。如果排序不稳定，相同分数的玩家、相同稀有度的物品或相同优先级的任务可能每次顺序不同，造成体验抖动或难以复现的问题。

排序也可以被部分选择替代。如果只需要前 K 个元素，不一定要完整排序全部数据。可以用堆维护 K 个候选，或用快速选择找到第 K 大位置，再局部处理。完整排序会产生比需求更多的工作。许多性能优化不是换一个排序算法，而是避免不必要的全量排序。

### 设计思路

设计排序方案时，第一步是确认排序目标。是要完整有序，还是只要最大值、最小值、前 K 个、分组后的局部有序、稳定展示顺序、确定性同步顺序？不同目标对应不同成本。只要最大值时，线性扫描 O(n) 就够；只要前 K 个时，堆或选择算法常常比全量排序更合适；需要可重复展示时，稳定性和 tie-breaker 比平均速度更重要。

第二步是确认数据规模和调用频率。几十个元素偶尔排序，直接使用内置排序即可；几万个元素每帧排序，必须重新思考数据流；小数组大量重复排序，插入排序或预排序维护可能更合适；构建期大量数据排序，可以接受更多内存换取稳定性。排序成本必须乘以调用频率，才是真实系统成本。

第三步是确认排序键。排序对象通常不应在比较器中反复计算昂贵属性。例如每次比较都调用距离计算、字符串解析、组件查找或资源访问，会把排序成本放大。更好的方式是先提取排序键，缓存为轻量结构，再排序索引或键值对。比较器应尽量纯粹、廉价、稳定。

第四步是确认是否需要稳定排序。若排序用于 UI 或玩家可见列表，稳定性经常有价值；若排序用于内部选择且相等元素无差别，可以选择不稳定但更快或更省空间的算法。稳定性不是抽象指标，它直接影响重复键场景下的结果可预测性。

第五步是确认是否可以利用数据特征。接近有序的数据适合插入排序或增量维护；整数范围很小适合计数排序；键由多个固定范围字段组成时可以考虑基数思想；重复元素很多时三路快排能减少无意义分区；数据分布均匀时桶排序可能有效。通用算法负责稳妥，特化算法负责吃透前提。

第六步是确认内存和分配约束。归并排序、计数排序、基数排序通常需要额外数组；内置排序和 LINQ 排序可能产生分配或延迟枚举成本；每帧创建比较器闭包也可能带来 GC。Unity 热路径中，应尽量复用列表、避免临时数组、避免在排序比较器中捕获变量或访问复杂对象。

短示例可以说明“先缓存键再排序”的思想：

```text
for unit in units:
    candidates.add({ id: unit.id, distance: squared_distance(unit, player) })

sort candidates by distance
take first k ids
```

这个方案避免在比较器中重复计算距离，也避免直接排序复杂对象。若只需要最近 K 个单位，还可以进一步使用固定大小堆，减少全量排序成本。关键不在代码形式，而在把排序键从对象系统中剥离出来，让排序处理轻量数据。

对于 Unity/C#，一般应优先使用经过测试的内置排序，而不是手写通用排序。`Array.Sort` 和 `List<T>.Sort` 在现代 .NET 实现中通常采用内省排序思想，即以快速排序为主体，在递归深度过大时切换到堆排序，在小区间使用插入排序，从而兼顾平均性能和最坏情况保障。需要注意的是，具体实现会随运行时版本变化，文档不应把某个版本细节当成永恒事实。

`List<T>.Sort` 通常是不稳定排序。如果业务需要稳定排序，不能只依赖它保留相等元素顺序。可以使用稳定排序实现，或在比较键中加入原始序号作为最后 tie-breaker。加入原始序号虽然会让“不稳定排序”在结果上表现得确定，但这实际上是把相等关系拆成了严格顺序。

排序比较器必须避免返回矛盾结果。常见错误是用 `a - b` 作为比较结果，在整数范围大时可能溢出；或比较浮点数时没有处理 NaN；或在比较过程中读取会变化的对象状态；或把随机数放进比较器。比较器错误会让排序结果不可信，严重时可能触发运行库异常。

多条件排序应明确优先级。例如排行榜可能先按分数降序，再按完成时间升序，再按玩家 ID 升序保证确定性。若只按分数排序，相同分数玩家的顺序可能在不同平台或不同运行中变化。确定性排序在网络同步、回放、测试快照和资源构建中尤其重要。

对于频繁更新的数据，可以考虑维护有序结构，而不是每次全量排序。例如排行榜只新增少量成绩，可以二分插入；优先队列适合反复取最小值；平衡树适合动态有序集合；分桶结构适合有限优先级。全量排序是批处理思路，不一定适合增量更新系统。

### 进阶讨论

排序的最优选择往往不是单一算法，而是混合策略。工业级排序很少只使用教科书中的纯快速排序或纯插入排序。小区间用插入排序，常规区间用快速排序，递归过深用堆排序，是典型混合思想。混合策略说明：算法选择可以随子问题规模和运行状态变化，而不是在入口处一次性决定到底是哪一种。

比较排序的 O(n log n) 下限并不意味着所有排序都无法更快。下限只适用于一般比较模型。如果数据是 0 到 255 的颜色编号，计数排序可以线性完成；如果实体优先级只有少量等级，分桶就可能比通用排序更合适；如果数组已经基本有序，插入排序接近线性。前提越具体，算法越有机会突破通用限制。

稳定性与确定性不是同一个概念。稳定性指相等键保持原相对顺序，确定性指同样输入每次输出一致。不稳定排序也可以通过完整 tie-breaker 获得确定结果；稳定排序如果输入顺序本身不确定，也无法保证跨系统一致。多人游戏和构建系统通常需要确定性，而 UI 展示常常同时需要稳定性和确定性。

排序前的过滤和分组常常比排序本身更重要。若有一万个目标，但只有一百个在有效范围内，先过滤再排序会大幅降低成本。若只需要按阵营、类型或区域分别展示，先分组再局部排序可能比全局排序更便宜。排序输入规模 n 的来源，应成为优化的第一目标。

缓存排序结果需要处理失效。排行榜、背包、技能列表、资源依赖结果都可以缓存，但当分数、物品属性、语言文本、资源引用或过滤条件变化时，缓存必须重新排序。缓存策略要定义清楚：哪些字段变化会使顺序失效，是否允许延迟刷新，是否需要增量更新。

浮点排序有额外风险。NaN 与普通数的比较可能不满足直觉，近似相等值的 tie-breaker 可能影响稳定性，平台差异也可能导致边界顺序不同。如果排序结果参与同步或回放，应尽量使用整数化键、固定精度或明确的二级键。只用浮点距离排序大量对象，容易在相等或接近相等时产生顺序抖动。

排序还会影响用户感知。UI 列表如果每次刷新都让相同优先级项目跳动，用户会觉得界面不稳定；敌人目标选择如果排序 tie-breaker 不清晰，AI 可能频繁换目标；透明物体排序如果粒度不够，可能出现渲染错误。排序结果不是纯数据，它会进入玩家体验。

堆与排序的关系需要区分。堆可以用于堆排序，但更常见用途是优先队列。寻路中的开放集合不需要每轮把全部候选排序，只需要能快速取出当前最小估值节点。用堆维护优先级通常比反复对列表排序更合适。把“需要最小值”误解成“需要排序”，会制造不必要成本。

外部排序是另一个重要边界。当数据无法全部放入内存时，归并思想更有优势：先分块排序写出，再多路归并。资源构建、日志处理、数据分析可能遇到这种情况。游戏运行时较少直接处理外部排序，但工具链和构建管线中会出现类似问题。

排序算法的正确性测试不应只使用随机数组。应测试空数组、单元素、已排序、逆序、全部相等、大量重复、负数、极端值、接近有序、奇偶长度、比较器相等键、需要稳定性的对象序列。快速排序尤其需要测试退化输入，计数排序需要测试值域边界，基数排序需要测试位数差异和负数处理方案。

手写排序在工程中应保持克制。除非有特殊数据前提、平台限制、分配约束或教学目的，通用排序应优先交给标准库。标准库排序经过大量边界测试和优化，手写实现更容易在边界条件、稳定性、递归深度和比较器处理上出错。理解算法的价值，是为了正确使用和诊断，而不是重复制造基础设施。

排序需求也可能暴露数据模型问题。如果系统频繁对同一批对象按同一键排序，说明数据可能应该以有序结构存储；如果每帧排序只是为了找到少量目标，说明应该维护候选集合或空间索引；如果排序比较器需要访问多个系统，说明排序键应提前归一化。排序性能问题常常是数据流设计问题的症状。

另一个容易忽略的问题是排序时机。数据变化时立即排序可以让读取逻辑简单，但可能在短时间内重复排序；读取前延迟排序可以合并多次修改，但会让第一次读取承担尖峰成本。对于 UI、资源列表和战斗目标集合，常见方案是使用 dirty 标记：数据变化时只标记顺序失效，真正需要展示或查询时再排序，并在排序后清除标记。这样能把排序成本放到明确的边界上，也更容易做性能统计。

### 总结

排序算法的核心不是“哪一种最快”，而是不同前提下的成本权衡。冒泡排序直观但低效，选择排序交换少但不稳定，插入排序适合小规模和接近有序数据，快速排序平均性能好但需要防止退化，归并排序稳定且最坏情况可靠但需要额外空间，堆排序空间稳定且最坏情况好但常数和稳定性不占优，计数、桶、基数排序则依赖特定数据特征。

排序方案选择应从需求出发：是否需要完整排序，是否需要稳定性，是否有确定性要求，数据规模和调用频率如何，排序键是否昂贵，是否能利用值域或分布，是否能接受额外空间。许多场景只需要前 K 个、最大值、最小值或局部分组，不需要全量排序。

在 Unity/C# 项目中，通用排序优先使用标准库，特殊热路径再根据数据特征设计专用方案。比较器要廉价、稳定、一致，排序前应尽量减少输入规模，排序后要考虑缓存失效和结果确定性。排序不只是算法题，它是数据流、性能预算和用户体验之间的一座桥。

真正掌握排序，是能够解释为什么某个算法适合某个场景，为什么某个看似更低复杂度的方案在前提不满足时会失败，为什么稳定性和 tie-breaker 会影响工程结果。排序算法的深度，恰恰体现在这些权衡之中。
