# 游戏中常用的排序算法对比

### 背景

排序几乎贯穿所有游戏项目。排行榜要按分数排列，背包要按品质和类型排列，自动锁敌要按距离、方向和威胁选择目标，渲染系统要处理材质批次与透明物体顺序，资源工具要列出体积最大的资产，战斗统计要按伤害或贡献展示结果。很多需求表面上都像“把数据排一下”，但真实工程里，排序从来不只是调用一个通用函数。

游戏中的排序有三个特点。第一，排序经常发生在实时系统中，必须考虑帧预算、临时分配和调用频率。第二，排序结果往往直接影响体验，尤其是 UI、排行榜、锁敌和 AI 决策，顺序抖动会被玩家感知。第三，排序条件常常不是单一数字，而是多字段、多规则、多阶段筛选后的综合顺序。复杂度表只能回答一部分问题，不能替代业务判断。

因此，游戏排序的核心问题不是“快速排序、归并排序、堆排序谁更好”，而是“当前需求是否真的需要全量排序”。有些场景只需要最优目标，有些只需要前 K 个候选，有些只需要稳定展示顺序，有些需要离线导出的可重复结果，有些适合增量维护，有些可以利用有限整数范围直接分桶。算法选择必须从需求形态开始，而不是从算法名开始。

在 Unity 或 C# 项目中，直接使用 `Array.Sort`、`List<T>.Sort`、LINQ 排序或自定义比较器很方便，也很容易掩盖真实成本。比较器里的一次距离计算、组件访问、字符串比较或配置查询，可能比排序框架本身更贵。每帧重新排序一个略有变化的列表，也可能比维护局部顺序浪费得多。排序优化往往不是换算法，而是减少候选、缓存排序键、降低刷新频率和明确稳定性规则。

本文从游戏开发视角对常用排序算法与排序策略进行对比，重点讨论通用排序、插入排序、快速排序、归并排序、堆排序、计数/桶/基数排序，以及 Top K、增量维护和稳定展示等工程方案。目标是把排序从抽象知识还原为可用于项目决策的判断框架。

### 核心原理

排序需求的第一层判断，是是否需要完整有序结果。完整排序会组织所有元素的全局顺序，但很多游戏系统并不需要这么多信息。自动锁敌只需要最佳目标或少量候选，资源诊断只需要最重的若干项，AI 决策只需要当前最优行为，导航候选只需要低代价前沿。若只需要局部结果，全量排序就是过度计算。

第二层判断是排序键的成本。理论复杂度通常假设比较是常数时间，但游戏对象比较往往不是简单整数比较。锁敌比较可能计算距离和夹角，UI 比较可能读取本地化文本，资源比较可能访问导入信息，战斗目标比较可能读取多个组件状态。比较器越重，排序中反复调用比较器的成本越高。此时预计算排序键常常比更换排序算法更有效。

第三层判断是稳定性。稳定排序会保持相等键元素的原相对顺序。对排行榜、背包、任务列表、编辑器导出和日志面板来说，稳定性直接影响可解释性。如果相同分数、相同品质或相同优先级的项目每次刷新顺序都不同，即使算法正确，用户也会觉得系统不稳定。稳定性不是附加属性，而是某些产品输出的组成部分。

第四层判断是更新频率。一次性离线排序、进入界面时排序、每秒排序、每帧排序，属于完全不同的工程问题。排序频率越高，越应该关注增量维护、dirty 标记、延迟刷新、局部插入和缓存键。很多排序性能问题不是单次排序太慢，而是排序被放进了不该高频执行的循环。

第五层判断是数据分布。接近有序的数据适合插入排序或增量修复；键范围有限的数据适合计数或分桶；大量重复键的数据需要明确 tie-breaker；均匀分布的数值可能适合桶排序；多位整数或固定宽度键可以考虑基数排序。通用比较排序忽略数据特征，专用排序则依赖数据特征。

通用内置排序通常应作为默认起点。现代运行时的通用排序往往是混合策略，会结合快速排序、堆排序和插入排序等思想，兼顾平均性能、小数组表现和最坏情况控制。除非有明确数据特征或性能证据，手写通用排序很少比标准库更可靠。工程上应先建立基线，再做专用优化。

插入排序在游戏项目中比名声更有价值。它的最坏复杂度是 O(n^2)，但在小规模或接近有序数据上非常高效，且实现简单、稳定、常数低。UI 列表小幅变化、目标优先级相邻帧变化有限、编辑器面板插入少量元素，都适合这种思想。插入排序代表的是“利用已有顺序”，而不是每次把数据当成完全无序。

快速排序的优势是通用性和平均表现。它原地性好、缓存表现通常不错，在大量普通数据上速度很快。但它不稳定，且需要处理枢轴选择、重复元素和退化输入。实际工程中不应把“快排平均快”当作唯一理由自行实现快排。更合理的理解是：许多标准库吸收了快排的优势，也通过混合策略规避了它的风险。

归并排序的价值在于稳定性和可预测性。它通常需要 O(n) 额外空间，但时间复杂度稳定为 O(n log n)，并且天然适合稳定排序、多键排序、链表排序和外部排序。对于面向玩家或工具链的可解释输出，归并类思想常常比不稳定但平均更快的方案更合适。排序结果需要被信任时，稳定性往往比少量速度差异更重要。

堆排序与堆式思路更适合优先级维护和 Top K。完整堆排序原地、最坏 O(n log n)，但不稳定，常数和缓存表现未必优秀。堆真正常用的场景，是反复取最大/最小、维护固定容量候选、实现优先队列。寻路开放集合、前 K 目标、性能诊断热点项、资源最大项，都可以用堆避免全量排序。

计数排序、桶排序和基数排序适合规则化键。游戏中很多排序键其实是离散的：品质等级、阵营、优先级段、格子编号、层级、状态枚举、帧号、资源类型。若键范围小且明确，计数或分桶可能接近线性；若键可按位拆分，基数排序可以避免昂贵比较。但这些方法依赖前提，值域太大或分布太偏时会浪费空间或退化。

Top K 与部分排序是游戏排序中最容易被忽视的方案。如果只要前十名，不需要让第十一名到最后一名完全有序；如果只要最近目标，不需要排序所有目标。快速选择、固定大小堆、局部分区、阈值过滤都可以减少工作量。很多“排序优化”真正应该改成“选择问题建模”。

排序还必须考虑确定性。多人同步、回放系统、自动化测试、资源构建和日志对比都需要同样输入得到同样输出。比较器应避免随机性、浮点边界不确定和未定义并列顺序。即使使用不稳定排序，也可以通过明确的二级键、三级键和原始 ID 让结果确定。

### 设计思路

设计游戏排序方案时，第一步是给需求分类。可以分为完整排序、稳定展示、Top K、单个最优、增量维护、离线导出、有限值域分桶和优先队列维护。需求分类越明确，算法选择越自然。没有分类时，团队往往会把所有问题都交给全量排序，既浪费性能，也忽略稳定性和可解释性。

第二步是缩小输入规模。排序之前应先过滤掉不可能参与结果的元素。锁敌先过滤阵营、距离、视野和可攻击状态，再排序剩余候选；资源诊断先限定类型和目录，再找最大项；UI 列表先应用搜索和分类筛选，再排序展示项。把 n 降下来，通常比在原 n 上更换排序算法更有效。

第三步是设计排序键，而不是直接写复杂比较器。多条件排序应先明确主键、次键和最终 tie-breaker。例如排行榜可用分数降序、完成时间升序、玩家 ID 升序；背包可用品质降序、类型顺序、获得时间、实例 ID；锁敌可用可攻击优先、角度、距离、威胁值和稳定 ID。排序键清晰，结果才可解释。

第四步是预计算昂贵字段。如果比较器每次都调用 `Vector3.Distance`、查找组件、读取配置或拼接字符串，排序会反复付出相同成本。应先生成轻量候选结构，把距离平方、威胁分、类型顺序、显示名键等计算好，再排序这些结构。这样不仅更快，也更容易测试排序规则。

第五步是明确刷新策略。对 UI 列表和目标列表，可以用 dirty 标记表示顺序失效，真正展示或查询时再排序；对每帧变化的目标候选，可以限制刷新频率或只在关键状态变化时重排；对大量对象，可以分帧处理。排序频率是设计参数，不应隐含在每个更新函数里。

第六步是决定稳定性和确定性。面向玩家或工具的排序，通常应有稳定且可解释的并列规则；内部临时选择可以更关注速度，但仍应避免随机抖动。若使用不稳定排序，应通过完整排序键消除真正相等的比较结果，或明确业务上允许并列项位置变化。

短示例可以说明排序键前置的思路：

```text
for target in visible_targets:
    key.attackable = can_attack(target)
    key.angle = angle_to_crosshair(target)
    key.distance = squared_distance(player, target)
    key.id = target.stable_id
    candidates.add(target, key)

sort candidates by attackable desc, angle asc, distance asc, id asc
```

这里排序算法不是重点，排序键模型才是重点。它把业务规则从比较器细节中抽出来，让策划、测试和程序都能理解为什么某个目标排在前面。

对 Top K 场景，应提供专门工具，而不是到处手写全量排序后截断。固定容量堆、快速选择或局部分区都可以作为项目工具库能力。排行榜前 N、最近 N 个敌人、最大 N 个资源、最高 N 条日志，都适合统一抽象。这样既减少重复代码，也能统一边界处理。

对离线工具链，应优先考虑可重复性。导表、资源扫描、构建报告、自动化检查不在主帧预算里，速度通常不是唯一目标。它们更需要稳定排序、明确 tie-breaker、跨平台一致和日志可比对。工具链排序若每次输出顺序不同，会制造无意义 diff，增加团队成本。

对运行时热路径，应测量真实数据。随机数组上的排序基准意义有限，应该使用项目中的实际数据规模、实际比较器和实际平台。需要统计排序次数、候选数量、比较器调用次数、临时分配、耗时分布和最坏帧尖峰。排序优化没有测量，很容易变成直觉争论。

对接近有序数据，应优先考虑增量维护。相邻帧中目标列表、UI 项、冷却技能、队伍成员顺序通常不会完全打乱。可以用局部插入、位置调整、延迟重排或稳定容器维护顺序。把时间连续性纳入设计，往往比每帧全量排序更符合游戏运行特征。

对有限值域数据，应考虑分桶而不是比较。品质、等级、阵营、优先级段、渲染层、资源类型都可以天然分桶。若最终只需要按等级组展示，先分桶再组内排序可能比全局比较排序更便宜也更清晰。分桶还能让业务规则更显式，例如“传说品质永远在史诗品质之前”。

### 进阶讨论

游戏排序中的最大误区，是把算法复杂度表当作唯一依据。复杂度表不能告诉你比较器有多贵，不能告诉你排序是否每帧触发，不能告诉你并列项抖动是否会伤害体验，也不能告诉你玩家是否需要稳定顺序。复杂度是基础，不是结论。

另一个误区，是过早手写排序。手写快排、归并或堆排序可能看起来更可控，但也带来边界 bug、维护成本和平台差异。除非已经证明标准库无法满足特定需求，否则应优先优化排序前后的数据流：减少候选、缓存键、降低频率、明确稳定性。很多时候，排序算法本身不是瓶颈。

稳定性在游戏中经常被低估。背包中两个同品质物品如果每次刷新位置互换，玩家会觉得不可靠；排行榜中同分玩家顺序乱跳，会引发解释问题；编辑器导出顺序不稳定，会制造版本差异；战斗统计并列项不稳定，会让测试复现困难。稳定排序或明确 tie-breaker 是产品质量的一部分。

确定性比稳定性更宽。稳定排序保留原顺序，但如果原顺序来自非确定性集合，结果仍可能不确定。多人同步和回放系统需要每个平台、每次运行得到一致结果，因此排序键应包含稳定 ID，比较器不能依赖哈希迭代顺序、对象地址、随机数或未规范化浮点差异。

浮点排序要谨慎。距离、角度、评分常常是浮点数，极接近值可能因为精度产生不稳定顺序。锁敌和 AI 目标选择尤其容易因此抖动。可以使用距离平方避免开方，可以设置阈值分段，可以增加稳定 ID 作为最终键，也可以对评分做整数化或固定精度处理。

排序与筛选的边界应清晰。若排序前没有筛选，排序会承担过多无关元素；若筛选条件写进比较器，比较器会变重且规则难以理解。更好的流程通常是：先过滤合法候选，再计算排序键，再排序或选择，再输出结果。这个流水线比单个复杂比较器更可维护。

排序与缓存也要一起设计。缓存排序结果能减少重复计算，但必须处理失效。影响排序键的字段变化时，应标记列表失效；只影响展示内容但不影响顺序的字段变化，不应触发重排。过度粗糙的 dirty 标记会导致频繁重排，过度精细的依赖追踪则可能增加复杂度。需要根据系统规模折中。

渲染排序与玩法排序的目标不同。渲染排序可能关注批次、材质、深度和状态切换；玩法排序关注决策质量；UI 排序关注可读性；工具排序关注可重复性。把同一套排序策略套给所有系统，会忽略各自目标。排序算法对比必须放回具体系统语境。

堆式结构适合持续维护优先级，但并不适合所有展示排序。优先队列可以快速取出最小项，却不保证内部完整有序。如果 UI 需要展示完整有序列表，堆并不是直接替代；如果系统只是反复取下一个任务，堆则很合适。数据结构能力必须匹配输出形式。

分桶策略的可解释性很强。把物品先按品质桶分组，再在每个桶内按类型和时间排序，往往比一个长比较器更容易理解。分桶也有助于调试，因为每一层规则都可单独检查。对于策划配置驱动的排序，分桶和显式权重表常常比硬编码比较器更合适。

排序测试不应只检查结果是否升序。应测试并列项稳定性、空列表、单元素、已排序、逆序、大量重复、极端距离、浮点相等、目标失效、排序键变化、跨帧刷新和不同平台一致性。尤其是面向玩家的排序，测试应覆盖“顺序是否可解释”，而不是只覆盖数值大小。

排序优化还要关注分配。LINQ 的 `OrderBy` 风格在工具代码中很方便，但在运行时热路径中可能产生额外分配和枚举开销。闭包比较器、临时列表、ToArray、字符串转换都可能进入 GC。高频排序应尽量复用容器和键结构，避免隐式分配。

排序结果的生命周期也需要定义。有些排序结果只在当前帧有效，有些可以缓存到数据变化，有些可以跨会话保存。锁敌结果可能需要短时间稳定，避免目标来回跳；UI 排序结果需要在列表打开期间稳定；构建报告需要长期可比对。生命周期不同，刷新策略也不同。

还要区分排序结果是给机器消费，还是给人消费。机器消费更关注选择正确性和性能边界；人消费更关注稳定、可解释和符合直觉。比如 AI 内部选择可以接受只要评分最高即可，但背包和排行榜必须让用户看懂并列项为什么这样排列。排序结果一旦进入用户界面，就不再只是算法结果，而是交互设计的一部分。

最终，排序成熟度体现在团队是否有统一问题清单：是否需要全量排序，是否只需 Top K，是否要求稳定，比较器是否昂贵，数据是否接近有序，值域是否有限，刷新频率是否合理，结果是否面向玩家，是否需要跨平台确定。只要这套清单稳定存在，大多数排序选择都会更清楚。

### 总结

游戏中的排序算法对比，真正重要的不是背下每个算法的复杂度，而是理解排序背后的业务约束。完整排序、Top K、增量维护、稳定展示、离线导出和优先级队列是不同问题，不能都用同一种思路解决。

通用内置排序应作为默认基线，插入排序适合小规模和接近有序数据，快速排序思想适合通用平均性能，归并排序强调稳定和可解释，堆适合优先级和 Top K，计数/桶/基数排序适合有限值域和规则化键。算法没有脱离场景的冠军，只有与需求匹配的方案。

工程上更可靠的排序设计，应先缩小候选集合，再预计算排序键，然后根据稳定性、确定性、刷新频率和输出形式选择策略。很多性能问题来自排序频率过高、比较器过重、候选过多或需求建模错误，而不是排序算法本身太差。

成熟的排序方案服务于性能、体验和可维护性。它能解释为什么某个元素排在前面，能在并列项中保持稳定，能在高频路径中控制成本，也能在工具链中产生可重复结果。排序不是一个孤立函数，而是游戏系统行为的一部分。只要排序规则会影响玩家判断、工具输出或运行时决策，它就应该像其他核心规则一样被设计、测试和记录，而不是隐藏在临时比较器里。排序规则越清晰，性能优化、体验验收和后续维护与跨团队协作就越容易达成一致，也越容易长期演进和复盘。排序规则应成为系统契约的一部分。
