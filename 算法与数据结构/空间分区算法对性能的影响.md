# 空间分区算法对性能的影响

### 背景

空间分区算法对性能的影响，远不只是少做几次距离判断。游戏系统中，碰撞检测、AI 感知、邻居查询、可见性裁剪、音频影响范围、弹道筛选、导航候选、大地图 Streaming 都会遇到同一个问题：如果每次查询都让所有对象彼此相见，再高效的后续逻辑也会被候选集规模拖垮。空间分区真正解决的是“谁根本不该进入本次计算”。

当对象数量很少时，线性遍历通常简单可靠。一个场景里只有几十个敌人，逐个判断距离可能完全可以接受。但随着单位数量、地图范围、查询频率和系统数量同时增长，全量扫描会迅速暴露上限。尤其是当多个系统都在重复做空间筛选时，候选集爆炸会成为共同瓶颈。

空间分区的价值在于把对象按空间关系组织起来，让系统先在宏观层面排除大片无关区域，再对局部候选做精确判断。它并不会让单次碰撞公式更快，也不会让 AI 决策更聪明；它让后续逻辑面对更小、更相关的数据集，从而改变系统可扩展上限。

但是，空间分区不是免费优化。一旦引入网格、空间哈希、四叉树、八叉树、BVH 或 BSP，系统就必须承担构建、更新、迁移、重建、边界处理、数据布局和调试可视化成本。静态场景中收益很高的结构，在高动态对象场景中可能因为维护成本过高而失去优势。查询收益和维护成本必须一起评估。

本文讨论空间分区如何影响性能，重点不是罗列结构优缺点，而是分析候选集缩减、维护成本、对象分布、动态性、数据布局、Streaming 协作和可观测性如何共同决定实际收益。目标是把空间分区从“算法选择”提升为“工程基础设施设计”。

### 核心原理

空间分区的第一项收益是降低候选集规模。若没有分区，距离查询、碰撞粗筛、视野感知和邻居搜索通常需要遍历全部对象。引入分区后，查询只访问与目标区域相交或邻近的格子、节点、桶或包围体。后续精确判断次数减少，整体链路成本随之下降。

候选集缩减比单次计算优化更重要。把一次距离判断从昂贵实现改为平方距离比较当然有价值，但如果候选对象从一万个降到一百个，收益通常更大。空间分区的本质不是优化公式，而是避免把无关对象送进公式。

第二项收益是改善数据局部性。合理分区后，同一空间区域内对象可以更集中地存放和访问，查询路径更短，缓存命中更稳定。若实现仍然依赖大量分散对象、指针跳转和临时分配，空间结构的理论优势会被数据布局抵消。算法结构和内存结构必须同时考虑。

第三项收益是提供空间语义。分区边界可以服务于 Streaming、可见性、触发器管理、区域激活、音频混响和工具可视化。空间分区不只是运行时查询加速器，也可以成为多个系统共享的空间理解层。共享语义越清晰，系统之间重复计算越少。

同时，空间分区会引入维护成本。静态对象只需构建一次，动态对象则需要在移动、生成、销毁、缩放或跨边界时更新归属。对象越动态，结构越复杂，维护成本越可能吞噬查询收益。许多分区方案失败，不是查询不够快，而是更新路径与场景行为不匹配。

均匀网格适合对象分布较均匀、查询半径相对固定、更新频繁且需求较简单的场景。它实现简单、调试直观、更新便宜，常用于单位邻近查询、掉落物管理、简单碰撞粗筛和局部感知。网格的关键参数是格子大小。格子太大，候选集过多；格子太小，跨格查询和空格维护成本上升。

空间哈希适合大范围、稀疏、动态的对象集合。它不需要为整个世界预分配网格，只为实际占用的格子建立映射，适合投射物、临时交互体、稀疏单位和无限或半无限地图。它保留了网格更新简单的优点，同时减少空区域浪费。代价是哈希冲突、桶管理和坐标映射需要谨慎处理。

四叉树和八叉树适合密度差异明显的二维或三维空间。它们通过按需细分，让高密度区域更细，低密度区域更粗，比固定网格更适应非均匀分布。它们适合可见性、区域查询和中低动态对象管理。但频繁移动、跨节点对象和反复分裂合并会增加维护复杂度。

BVH 以对象包围体为组织核心，适合射线检测、碰撞粗筛、复杂几何和渲染可见性。它不是先切空间再放对象，而是把对象按包围体层级组织起来。静态 BVH 在查询上非常高效，动态 BVH 则需要处理 refit、局部旋转或重建策略。对象尺寸差异越大，BVH 的建模价值越明显。

BSP 和语义化分区适合静态关卡、室内外区域、房间走廊和 Streaming 边界明确的场景。它的价值不只在查询速度，还在于边界可解释。一个区域结构可以同时服务可见性、加载、触发器和编辑器工具。对于大关卡，语义分区往往比纯几何分区更容易与内容生产协同。

对象分布比复杂度公式更能决定收益。均匀分布、热点聚集、稀疏分布、尺寸差异、移动频率、查询半径和查询热点都会改变结构表现。一个理论上优秀的结构，如果项目数据分布不匹配，也可能表现平平。空间分区选型必须基于真实样本，而不是基于结构名声。

空间分区的复杂度应按全链路评估。查询耗时、候选数量、更新迁移、插入删除、重建频率、内存占用、空节点比例、跨边界对象数量、GC 分配和目标平台缓存表现都需要纳入。只测查询速度是不完整的；只测构建速度也是不完整的。

空间分区还会改变系统之间的责任边界。没有空间索引时，各系统往往各自扫描对象；有了空间索引后，查询入口可能被集中到一个服务层。这个服务层一旦承担过多职责，例如同时做阵营过滤、状态过滤、对象生命周期管理和结果排序，就会变得臃肿。更好的方式是让空间结构负责空间候选，业务系统负责业务过滤。职责越清晰，结构越容易复用。

对大型项目来说，空间分区的收益还体现在统一语言上。关卡、资源、AI、物理和渲染都需要谈论“区域”“邻近”“可见”“活跃范围”。如果每个系统都有不同边界定义，协作成本会很高；如果上层区域概念统一，底层索引可按系统拆分，团队既能共享空间语义，又不必被单一结构限制。

### 设计思路

设计空间分区系统时，第一步是明确查询类型。是点查询、范围查询、邻域查询、射线查询、包围体相交、视锥裁剪，还是最近邻？不同查询适合不同结构。邻域查询常用网格或哈希，射线和包围体更适合 BVH，语义区域查询可能适合 BSP 或人工区域划分。

第二步是分析对象动态性。静态环境、低频移动对象、高频移动对象和瞬时对象不应使用同一套策略。静态场景可以使用构建成本较高但查询高效的结构；高频移动对象更适合更新轻量的网格或空间哈希；瞬时投射物可能只需要短生命周期桶管理。

第三步是采样真实分布。应记录对象密度热力图、平均查询半径、最大查询半径、对象尺寸分布、移动速度、跨区频率和热点区域。没有这些数据，格子大小、树深度、节点容量和重建阈值都只能靠猜。空间分区高度依赖场景分布，猜测很容易失真。

第四步是设置可退化策略。热点区域对象过多时如何处理，树过深时是否停止分裂，对象跨多个格子时如何去重，动态对象太多时是否降级为粗网格，重建成本过高时是否分帧处理，这些都应提前设计。没有退化路径的分区结构，长期运行中很容易失控。

第五步是将静态与动态分开。静态场景几何可以走 BVH、BSP 或烘焙区域，动态对象可以走空间哈希或动态网格。把所有对象塞入同一个结构，通常会让结构既不适合静态优化，也不适合动态更新。混合结构在工程上常常更现实。

第六步是考虑数据布局。高频空间查询应尽量减少托管对象跳转、临时列表分配和复杂引用链。连续数组、结构化索引、对象 ID、复用缓冲区和批量遍历可以显著改善实际表现。空间分区的性能不只来自减少候选，也来自候选访问方式是否友好。

短示例可以说明网格查询的基本思路：

```text
cell = world_to_cell(position)
for each neighbor_cell around cell:
    for object in neighbor_cell.objects:
        if precise_test(object):
            add_to_result(object)
```

这段伪代码的关键不是循环本身，而是候选集合来自邻近格子，而不是来自全场景。精确测试仍然存在，但它只发生在小范围候选上。空间分区的设计重点，就是让这个候选集合足够小且维护成本可控。

对跨边界对象要有明确策略。大对象可能覆盖多个格子或多个树节点；若只放在一个节点中，查询可能漏检；若放在多个节点中，查询可能重复返回。常见方案包括多格登记、松散四叉树、上浮到共同父节点、查询结果去重。选择哪种方式取决于对象尺寸差异和查询频率。

对 Streaming 系统，应让空间分区与加载边界互相支持。若查询分区和资源加载分区完全错位，运行时会在两个空间理解之间来回转换。大型地图通常需要在区域边界、子场景、可见性和查询结构之间建立一致关系，至少要明确它们如何映射。

对工具链，应优先提供可视化。开发者需要看到格子占用、树节点范围、BVH 包围体、查询命中路径、热点区域、空节点比例和重建事件。空间分区如果不可视化，很快会变成黑箱。底层结构越关键，可观测性越重要。

对接口层，应避免直接暴露内部结构。调用方通常不需要知道对象位于哪个格子或哪个 BVH 节点，只需要请求某个区域内的候选。内部结构可以从网格换成哈希，从哈希换成树，外部接口仍保持稳定。空间分区若过早把内部节点暴露给业务系统，后续优化会非常困难。

对多线程，应提前考虑读写冲突。空间结构常常被大量查询读取，同时又有对象移动写入。可以采用双缓冲索引、分帧提交、读写锁、命令队列或静态/动态分层来降低冲突。若在主线程高频写入、工作线程高频读取，又没有清晰同步策略，空间分区会从性能优化变成并发风险。

对生命周期，应明确对象何时进入和离开索引。生成时登记、禁用时移除、销毁时清理、跨场景时迁移、缩放变化时更新包围体，这些规则必须一致。空间索引最难排查的错误之一，就是对象已经不存在却还留在桶里，或对象已经移动却仍在旧位置被查询到。索引生命周期应和对象生命周期解耦但同步。

### 进阶讨论

空间分区并不自动提升性能。若对象数量很少、查询频率很低或维护成本很高，分区结构可能带来负收益。项目早期过早引入复杂结构，会增加实现和调试成本。正确做法是根据规模增长路径选择合适复杂度，而不是为了“以后可扩展”直接上最复杂方案。

网格大小是最常见的调参陷阱。格子过大时，每个格子内对象过多，候选缩减有限；格子过小时，查询需要访问更多格子，动态对象跨格频繁，管理成本上升。理想格子大小通常与典型查询半径和对象尺寸有关，而不是随意取一个看起来整齐的数。

空间哈希的哈希函数和桶结构会影响真实表现。坐标映射需要处理负坐标、大世界精度、整数溢出和哈希冲突。桶内对象如果长期不清理或频繁分配列表，也会产生隐藏成本。轻量结构不代表可以随意实现，越是基础结构，越需要稳定边界。

四叉树和八叉树的分裂策略应避免抖动。如果对象在边界附近来回移动，节点反复分裂合并会造成尖峰。可以使用松散边界、迟滞阈值、最小更新时间或分帧重构降低抖动。树结构的优雅不应建立在频繁重建上。

BVH 的静态和动态版本应区别对待。静态 BVH 可以花更多时间构建高质量层级；动态 BVH 更关注 refit 和局部调整。若动态对象太多，完全重建可能不可接受；若长期只 refit 不重建，层级质量会下降。重建策略本身就是性能设计的一部分。

空间分区与物理引擎已有结构可能重叠。Unity 物理系统本身会维护 broadphase 结构，很多查询可以直接利用物理 API。若项目又建立一套并行空间索引，需要明确它解决的是物理 broadphase 之外的问题，例如 AI 感知过滤、非碰撞对象、工具数据或跨系统缓存。重复索引会带来同步成本。

不同系统不一定应该共享同一空间结构。物理关注碰撞体，AI 关注可感知目标，可见性关注渲染对象，音频关注声源范围，Streaming 关注资源块。它们可以共享上层区域概念，但底层索引粒度和数据字段往往不同。强行统一会让结构臃肿。

空间分区也可能改变系统架构。引入区域之后，事件可以按区域广播，对象可以按区域激活，资源可以按区域加载，调试可以按区域统计。空间结构从优化工具变成组织工具后，其边界设计就会影响内容生产流程。此时需要更慎重地定义区域语义。

可观测指标应长期采集。平均候选数、最大候选数、查询次数、更新次数、重建耗时、格子占用分布、跨格对象比例、热点区域和空节点比例，都能帮助判断结构是否健康。没有这些指标，空间分区只能靠体感调参。

目标平台差异会改变选型。桌面平台可能更能承受复杂结构和内存占用，移动平台更敏感于缓存、分配和尖峰，主机平台可能对 Streaming 和线程调度有不同约束。空间分区必须在目标平台上验证，不能只在开发机上得出结论。

对象尺寸差异也是重要变量。若小物体和巨大物体混在同一格子体系中，巨大物体可能覆盖大量单元，造成重复登记和查询去重成本；若把巨大物体只登记在一个单元，又可能导致漏查。常见处理方式是按尺寸分层索引，或让大对象进入单独结构。尺寸分层能让小对象查询保持轻量，也能避免少数大对象污染普通格子。

查询半径变化同样会影响结构效率。若大多数查询半径很小，细粒度网格收益明显；若经常出现大范围扫描，细粒度结构反而需要访问大量单元。可以为不同半径建立不同路径，例如小半径走网格，大范围走区域层级或预计算区域列表。让所有查询使用同一粒度，往往会让某一类查询长期不划算。

混合结构往往比单一结构更适合量产项目。可以用粗网格管理大范围区域，用 BVH 管理静态几何，用空间哈希管理动态对象，用语义分区服务 Streaming。混合结构的代价是接口边界更复杂，但收益是每种结构只处理自己擅长的问题。

空间分区测试应覆盖极端场景。包括所有对象集中在一个小区域、对象均匀铺满、对象高速穿越边界、大对象跨越多个单元、频繁生成销毁、查询半径极大、空场景、密集热点和切场景重建。只在理想分布下测试，会掩盖真实风险。

最重要的是，空间分区改变的是系统上限。它让项目在对象数量和查询频率增长后仍有余地，但也要求团队投入结构维护、调试工具和指标建设。没有可维护性支撑的空间分区，很难长期服务复杂项目。

空间分区还需要和内容生产节奏匹配。如果关卡编辑器无法显示分区边界，策划就很难理解为什么某些区域性能差；如果资源导入工具无法检查对象密度，问题会到运行时才暴露；如果自动化测试不覆盖大规模对象分布，结构退化会在后期才出现。性能基础设施必须进入内容流程，而不是只停留在运行时代码里。

最后，空间分区不应被看作一次性实现。随着玩法、地图规模、单位数量和目标平台变化，原有参数可能失效。格子大小、节点容量、重建阈值、缓存策略和可视化指标都应允许调整。可调、可测、可回退，是空间分区长期可用的关键。

### 总结

空间分区算法对性能的核心影响，是减少进入后续计算的候选对象数量。它把问题从“如何更快处理所有对象”改为“如何尽早排除无关对象”。这一转变决定了碰撞、AI、可见性、音频、Streaming 等系统在规模增长后的上限。

不同结构适合不同场景。均匀网格简单稳定，空间哈希适合稀疏动态对象，四叉树和八叉树适合非均匀空间，BVH 适合包围体查询和射线类问题，BSP 与语义分区适合静态关卡和区域治理。没有通用冠军，只有与数据分布、动态性和查询类型匹配的方案。

空间分区不是免费优化。查询收益必须与插入、删除、迁移、重建、内存占用、数据布局和可视化成本一起评估。若只看查询速度，很容易在更新路径或维护成本上付出更大代价。

成熟的空间分区设计，应建立在真实样本、目标平台、可观测指标和清晰退化策略之上。它既是性能优化工具，也是空间语义基础设施。只有当它能被测量、调试、维护和与内容流程协同时，才真正能支撑项目长期扩展。

换句话说，空间分区不是把对象装进某棵树或某张网格就结束，而是让项目拥有一套持续回答“对象在哪里、谁可能相关、哪些区域值得计算”的能力。这个能力越稳定，系统规模增长时越不容易失控，也越容易在新玩法、新关卡和新平台上继续复用，并保持可验证、可调试、可回归的性能边界，并能持续指导内容生产和运行时调优与跨平台验证和长期回归、版本演进和团队协作与质量追踪机制体系。
